# 2. Платформа (landing zone)

**Зачем слой.** Платформа — общий «пол», на который потом ставят продукты: кластер Kubernetes, вход с VIP, классы дисков, DNS, секреты, способ наката. Её описывают **один раз на контур**, не в каждой карточке Kafka.

Термин **landing zone** — заготовка контура: сеть-минимум, идентификация, оркестрация, диски. У нас сеть в деталях вне рамок; три требования Task_6 заменяют «нарисовать VLAN».

**Как закрыть.** Подтвердить предложенное, закрыть **РЕШИТЬ**. Пулы нод можно начать с минимума и добавить `data-*` на слое 3, если политика размещения этого потребует.

Зависимость: роль бэкап-ЦОДа из слоя 1. Если там «только хранилище копий» — Kubernetes в бэкап-ЦОД **не** ставим.

| Требование | Статус |
|---|---|
| Пара HAProxy **3.4.3** + Keepalived + VIP на 1 ЦОД | **ЗАФИКСИРОВАНО** |
| VIP = ControlPlaneEndpoint Kubernetes (:6443, TCP passthrough) **и** край HTTP(S) | **ЗАФИКСИРОВАНО** |
| Kafka :9092 через этот HAProxy **не** публикуем | **ЗАФИКСИРОВАНО** |

Keepalived (VRRP) — программа, которая держит **VIP** (виртуальный IP): при смерти одного HAProxy адрес переезжает на второй. В `sample/` отдельного файла Keepalived нет — это зависимость края. Занести в каталог (слой 5).

## 2.3. Диски

| Требование | Статус |
|---|---|
| StorageClass `local-ssd`: RWO, локальный SSD, CSI, для stateful-операторов | **ЗАФИКСИРОВАНО** |
| StorageClass `shared-fs`: RWX, **только** по списку исключений | **ЗАФИКСИРОВАНО** |
| Swift на своих дисках, не через CSI | **ЗАФИКСИРОВАНО** |
| NFS не использовать как диск etcd / Kafka / Postgres / Prometheus | **ЗАФИКСИРОВАНО** |
| Dev — те же **имена** классов, меньше тома | **ЗАФИКСИРОВАНО** |

Простыми словами: **RWO** — том одной ноде; **RWX** — том сразу нескольким нодам (общий диск). **CSI** — драйвер, через который Kubernetes заказывает диски.

| Вопрос | Статус | Черновик |
|---|---|---|
| Кто реализует `local-ssd` (имя CSI)? | **РЕШИТЬ** | Можно отложить имя драйвера, но нельзя отложить требование: локальный SSD, не NFS. Иначе операторы Kafka/Postgres встанут на «общий NAS» и вы получите другой класс сбоев. |
| Список исключений для `shared-fs` | **РЕШИТЬ** | Пока пустой. Кандидат на обсуждение (не решение): общий data dir GeoServer, если будет ≥2 реплики. Не добавлять в список, пока не закроете строку GeoServer в слое 3. |
| Диски Swift / сырые диски VM | **ПРЕДЛОЖЕНО** | Отдельные диски на VM (или физика), XFS — как в `sample/OpenStack Swift.md` (для стенда). Не PVC Kubernetes. **Допущение.** |

## 2.4. DNS

| Требование | Статус |
|---|---|
| Внутри кластера — CoreDNS / `cluster.local` | **ЗАФИКСИРОВАНО** |
| Снаружи — зона контура; имена на VIP и на сервисы, включая advertised listeners Kafka | **ЗАФИКСИРОВАНО** |
| Клиенты ходят по FQDN, не по Pod IP | **ЗАФИКСИРОВАНО** |

**Advertised listeners** Kafka — адреса, которые брокер **сам сообщает** клиенту после первого контакта. Если там Pod IP, клиент вне кластера отвалится. Поэтому внешние имена брокеров должны быть в зоне контура.

| Вопрос | Статус | Черновик |

| Кто внешний DNS (AD / PowerDNS / BIND ЦОДа)? | **РЕШИТЬ** | Достаточно «зона есть, записи на VIP делает команда ЦОДа». Иначе слой 6 не знает, куда класть имена. |

## 2.7. Черновик пулов нод

**Пул нод** — группа машин с одной ролью и одинаковыми дисками. Планировщик сажает поды в пул, не «на ноду 3».

| Пул | Роль | Статус | Зачем |
|---|---|---|---|
| `control-plane` | Управление кластером | **ПРЕДЛОЖЕНО** | API, etcd, scheduler. Прикладные нагрузки сюда не кладём (или явно решаем иначе). |
| `worker-general` | Обычные приложения | **ПРЕДЛОЖЕНО** | Stateless, мелкие сервисы. |
| `worker-data-localdisk` | Stateful с `local-ssd` | **ПРЕДЛОЖЕНО как кандидат** | Завести, **если** слой 3 положит Kafka/Postgres/OpenSearch в этот кластер. Если все stateful уедут на VM — пул не нужен. |
| Ноды GeoData / Luxms | Остров | не пул платформы | Свои машины, своя ОС. |
