# 4. Эталонные топологии

**Зачем слой.** Не 36 уникальных схем, а несколько **классов**. Продукт = «класс N + размеры». Схему инстансов (как в Task_6 / Kubernetes.md) рисуем для класса один раз и для **исключений**, которые в класс не лезут.

**Как закрыть.** Согласовать список классов. Колонку «кто сюда попал» заполнять **после** слоя 3 (не заранее из ландшафта).

Пока слой 3 не закрыт, списки «кто» оставляем пустыми или с пометкой «кандидат».

---

## Общие правила всех классов

| Правило | Статус |
|---|---|
| На схеме — инстансы и роли, **без потоков** данных | **ЗАФИКСИРОВАНО** (Task_6) |
| Под: runtime (K8s / не K8s) + **пул нод**, не «нода 3» | **ЗАФИКСИРОВАНО** |
| DaemonSet: «на каждой ноде» пула | **ЗАФИКСИРОВАНО** |
| После схемы: ОС = свойство платформы; исключения вендора — отдельной строкой | **ЗАФИКСИРОВАНО** |
| После схемы: таблица пулов, которые встретились | **ЗАФИКСИРОВАНО** |
| Prod: минимальный HA. Путь роста — текстом, не лишними узлами на схеме | **ЗАФИКСИРОВАНО** |
| Dev: тот же класс, меньше CPU/RAM/диск; кворум не сжимать до 2 | **ЗАФИКСИРОВАНО** |

Цвета легенды — когда дойдёте до картинок, взять ту же палитру, что уже используете в карточках (серый оркестрация, жёлтый край, …). Сейчас палитру не размножаем.

---

## Класс A. Stateless в Kubernetes

**Смысл.** Несколько одинаковых копий, диск либо нет, либо пустой. Упал под — Kubernetes поднял другой.

| | Prod (минимум HA) | Dev |
|---|---|---|
| Объект | Deployment (или аналог) | тот же |
| Реплики | ≥2 | **2**, на **2** нодах |
| Антиаффинити | не две реплики на одну ноду | то же |
| Диск | обычно нет; конфиг — ConfigMap/Secret | то же |

Путь роста: увеличить replicas / HPA (автошкала по метрикам), не меняя класс.

Кто сюда (заполнить после слоя 3): _

Кандидаты, не решение: Spring Cloud Gateway, Argo CD (если подтвердите), часть UI.

---

## Класс B. Stateful с оператором в Kubernetes

**Смысл.** У потока есть имя и диск (`local-ssd`, RWO). Оператор знает роли (broker / primary / replica).

| | Prod | Dev |
|---|---|---|
| Диск | `local-ssd`, не NFS | то же имя класса, меньше том |
| Кворум голосующих | нечётный, обычно **3** | **3** маленьких |
| Пул | скорее `worker-data-localdisk` | то же, слабее машины |

Путь роста: добавить брокер/реплику **по мануалу оператора**; шарды — отдельно, не с первого дня.

Кто сюда: _

Кандидаты, не решение: Kafka+Strimzi, Flink Operator, Vault Raft — если слой 3 подтвердит.

**Слабое место класса.** Local disk привязывает под к ноде: умерла нода — диск не уехал сам. Нужен понятный runbook (как чинить), его пишут в слое 6, не на схеме.

---

## Класс C. Кластер на VM / железе (systemd)

**Смысл.** Нет оператора или нужны сырые диски. Ставим пакеты, держим кворум сами.

| | Prod | Dev |
|---|---|---|
| Механизм | пакеты, не Compose | то же |
| Кворум | обычно 3 | 3 маленьких VM |
| Балансировка входа | VIP/HAProxy площадки, если это HTTP(S); Kafka :9092 — **не** через тот HAProxy | то же |

Кто сюда: _

Кандидаты: GitLab package; возможно ClickHouse/OpenSearch/Postgres, **если** слой 3 выберет VM.

---

## Класс D. Кольца дисков / объектное хранилище

**Смысл.** Надёжность = несколько копий **на разных дисках/машинах**, не «PVC в Kubernetes».

| | Prod | Dev |
|---|---|---|
| Runtime | VM или физика | те же роли, меньше диски |
| CSI | нет (Task_6) | нет |
| Репликация данных | как велит продукт (у Swift — replica factor) | тот же factor, меньше объём |

Путь роста: добавить диск/машину в кольцо, не «включить все фичи».

Кто сюда: _

Кандидат: OpenStack Swift платформы. **Не смешивать** со Swift другой версии внутри GeoData, пока слой 5 не решит (это уже шаринг, не класс).

---

## Класс E. Вендорский остров

**Смысл.** Свой инсталлятор, свои версии K8s/БД/шины. **Не** кладём в платформенный кластер 1.36.4 и **не** шарим его Kafka/PG «чтобы сэкономить», пока вендор это не разрешает.

| | Prod | Dev |
|---|---|---|
| Способ | документация вендора | **тот же** способ, меньше машины |
| Quickstart вендора | нельзя заменить «нашим» Helm, если вендор так не ставит | нельзя на Dev поставить c8run/Compose, если Prod — другой вид |

Кто сюда: _

Кандидаты из sample: GeoData, Luxms BI, SafeLine (Compose как исключение вендора). Wazuh — после слоя 3.

**Критично.** Остров даёт второй Kubernetes / вторую Kafka. Это цена совместимости, не ошибка. Её нужно принять явно.

---

## Класс F. Агент на каждой ноде

**Смысл.** Смотреть нужно ядро **этой** машины: один под (или процесс) на ноду.

| | Prod | Dev |
|---|---|---|
| K8s | DaemonSet | тот же |
| Вне K8s (VM GitLab, Swift, острова) | агент пакетом, если продукт это умеет | то же |

Кто сюда: _

Кандидат: Falco на Linux-нодах платформенного кластера. OTel Collector agent — если выберете схему agent+gateway.

---

## Класс G. Край площадки (уже зафиксирован)

Не выдумываем заново: пара HAProxy + Keepalived + VIP на ЦОД. Dev — та же пара, меньше CPU/RAM.

Схему края можно нарисовать **один раз** на контур, когда дойдёте до картинок. Порядок WAF ↔ HAProxy — дырка слоя 2.

---

## Что не является отдельным классом

- **Open Telemetry SDK** — нет инстанса.
- **Один контейнер Docker Compose** — не класс боя.
- **c8run / SAIO / single-node OpenSearch** — стенды; в Prod не переносить.

---

## Когда рисовать отдельную mermaid на продукт

Только если продукт **ломает** класс (несколько ролей, которые нельзя подписать «как в классе B»). Типичные кандидаты **после** заполнения «кто»: Swift, GitLab не-all-in-one, Camunda со вторичным поиском, остров GeoData целиком.

Пока не закрыты слои 1–3, файлов `*.schema.md` в этой папке не создаём — иначе появятся картинки «из головы».
