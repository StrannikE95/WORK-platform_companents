Мне нужно описать способ развертывания ПО для ИТ-ландшафта перед началом разработки.

+ Считаем, что уже есть:
    + Dev - 1 ЦОД
    + Prod - 2 ЦОД + 1 ЦОД под бэкапы
    + Система виртуализации (умеем создавать VM)
    + Список развертываемого ПО см. в папке \sample\
    + Источник состава ПО — только \sample\. Файл integrations\IT-landscape.md не использовать как опору: он собирался для общей картины и может содержать незамеченные допущения.

+ Сеть в деталях (VLAN, IP-план, модель ЦОД) — вне рамок. Фиксируем три платформенных требования на 1 ЦОД:
    + Вход. Пара HAProxy 3.4.3 + Keepalived + VIP. VIP = ControlPlaneEndpoint Kubernetes (:6443, TCP passthrough) и край HTTP(S). Сейчас HAProxy есть — доводим до пары с VIP, если это ещё не так. Kafka :9092 через один HAProxy не публикуем. Dev — та же пара+VIP, меньше CPU/RAM.
    + Диски. В Kubernetes два StorageClass: local-ssd (RWO, локальный SSD, CSI) для stateful-операторов; shared-fs (RWX) только по списку исключений, не по умолчанию. Swift на своих дисках, не через CSI. NFS не используем как диск etcd/Kafka/Postgres/Prometheus. Dev — те же имена классов, меньше тома.
    + DNS. Внутри кластера — CoreDNS / cluster.local. Снаружи — зона контура (prod.… / dev.…): имена на VIP и на сервисы, включая advertised listeners Kafka. Клиенты ходят по FQDN, не по Pod IP.

+ Требования к развертыванию:
    + На Dev должен быть такой же способ развертывания, что и на Prod для возможности воспроизвести ошибку. Например:
        + Ошибка из-за вида инсталляции (на Prod всё в кубере, а на Dev — на 1 VM по квикстарту)
            + Типа при накате обновления что-то может отработать по-разному и т.д.
        + Ошибка из-за параллельной работы 2 под/нод (на Prod N-под на разных нодах, а на Dev вообще нода с 1 инстансом)
        + Правило паритета: тот же механизм установки и та же роль-модель. Dev уменьшает ёмкость (CPU/RAM/диск), а не меняет вид инсталляции.
        + Stateless (шлюз, UI, веб): на Dev минимум 2 реплики на 2 нодах — чтобы была балансировка нужного типа и отказ одной ноды.
        + Системы с кворумом (большинство голосов: Kafka KRaft controller, etcd / Kubernetes control plane, ClickHouse Keeper, Vault Raft, OpenSearch cluster manager, PostgreSQL с автофейловером Patroni/CNPG и аналоги): на Dev оставляем нечётный кворум, обычно 3 маленьких узла. Схема «2 узла» — не уменьшенный Prod, а другой класс системы (нет большинства; отказ одного = тупик или split-brain). Уменьшают шарды и размер дисков, не число голосующих.
    + Отсюда требование:
        + сначала спроектировать Prod-инсталляцию
        + потом Dev-инсталляцию, как упрощённый вариант
    + На Prod считать систему высоконагруженной с большим объёмом данных (терабайты). Нагрузка не замерена — не включать «все возможности масштабирования вендора».
        + Зафиксировать минимальную отказоустойчивую топологию (кворум, реплики, роли).
        + Отдельно описать путь роста (добавить брокер, добавить шард) — не включать рост сразу.
        + Ёмкость CPU/RAM/дисков — порядок величины + пометка, что уточняется замером.

    + Политика размещения (вместо жёсткого «stateful = физический сервер»):
        + Есть официальный оператор под наш K8s и данные не требуют сырых дисков → Kubernetes.
        + Вендорский стек / остров (свой инсталлятор, свои версии K8s/Kafka/БД) → как велит вендор, на отдельных VM/кластере.
        + Много локальных дисков / объектное хранилище (кольца дисков) → VM или физический сервер.
        + Боевой запасной путь, если оператора/K8s нет: пакеты на Linux-VM (systemd). Не Docker Compose.
        + Docker Compose — только учебный стенд и явные исключения вендора, не прод и не «запасной прод».

+ Что ожидаю на выходе:
    + К каждому файлу в папке \sample\ создать в папке \sample2\ 2 инструкции:
        + Для Prod-контура
        + Для Dev-контура
    + Каждая инструкция содержит:
        + Схему инстансов и компонентов в mermaid
            + Пример: C:\_ii_\WORK-platform_companents\Out\Платформенная инфра\Kubernetes\Kubernetes.md
            + Схема также должна быть цветной.
            + У схемы должна быть такая же легенда для компонентов (прям точь-в-точь, только пояснение к цвету. Не нужно в легенде описывать назначение каждого элемента и т.д.)
            + На схеме должны быть выделены отдельные инстансы и указаны их атрибуты:
                + Что это:
                    + Под:
                        + K8s / Docker / - ?
                        + Пул нод (не конкретная нода): worker-general, worker-kafka, … Планировщик двигает поды; на схеме не фиксировать «под на ноде 3». Исключение — DaemonSet (Falco, OTel agent и т.п.): «на каждой ноде».
                    + Нода:
                        + Какой пул?
                        + Антиаффинити, если нужно: «не сажать две реплики на одну ноду».
            + На схеме не должно быть потоков, как в примере.
        + Сразу после схемы — пометка: ОС — свойство платформы, не пода. Один стандарт Linux на всех нодах контура; исключение — только если вендор требует иное (отдельной строкой).
        + Сразу после схемы — таблица пулов нод, которые встретились на схеме: имя пула, роль (general / data-localdisk / control-plane / …), кратко зачем выделен.
        + Комментарии к схеме
            + Какой функционал располагается на инстансе
            + Критически важные детали развертывания инстанса
