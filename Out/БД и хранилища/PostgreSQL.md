# PostgreSQL 18.6 — развёртывание и настройка

Версия ПО: **PostgreSQL 18.6** (релизная дата 13 августа 2026; на дату подготовки документа это последний стабильный патч линии **18**).  
Одновременно вышли 17.11, 16.15, 15.19, 14.24 и **19 Beta 3**. В прод **не** берём бету. Релиз 18.6 закрывает **28 CVE** (в том числе несколько с CVSS 8.8, класс «выполнение кода») и 110+ багов; линейка **пропустила 18.5** из‑за регрессии. Оставаться на **18.4** (дефолт оператора, см. ниже) нельзя: это не «почти то же».

Документация линейки: https://www.postgresql.org/docs/18/  
Релиз 18.6: https://www.postgresql.org/about/news/postgresql-186-1711-1615-1519-1424-and-19-beta-3-released-3365/  
Официальный Docker-образ (стенд): `postgres:18.6` (Docker Hub library/postgres; теги `18.6`, `18`, `latest` на эту дату указывают на этот патч).  
Лицензия PostgreSQL — своя (BSD-подобная). Это **не** Postgres Pro Enterprise, **не** EDB, **не** Citus, **не** Patroni как отдельный продукт.

На Kubernetes целевой путь: оператор **CloudNativePG 1.30.0** (релиз 29 июня 2026; Apache-2.0).  
Матрица 1.30.0: Kubernetes **1.36 / 1.35 / 1.34**, PostgreSQL **18–14**, дефолтный образ оператора — **18.4**. Образ кластера **пинить на 18.6** явно (`ghcr.io/cloudnative-pg/postgresql`, тег вида `18.6-…-trixie`, не `latest`).  
Установка оператора: манифест `cnpg-1.30.0.yaml` из ветки `release-1.30`.  
EOL PostgreSQL **14** — **12 ноября 2026**. EOL линии 18 по политике PGDG — **14 ноября 2030**.  
Встроенный Barman Cloud в операторе **deprecated**, снятие обещано в **CNPG 1.31.0**. Для прода — плагин Barman Cloud (CNPG-I), не in-tree.

Этот текст — не мануал «скопируй `docker run postgres`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

PostgreSQL **упоминался** в правилах диалога как типичное платформенное ПО под нагрузку. В исходной архитектуре (Kafka / Camunda / озеро эталона / интеграционное API) PostgreSQL **не назван по имени**. Ниже — как поставить реляционную СУБД на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** шина событий, **не** in-memory кэш и **не** аналитический склад. Это кандидат в **транзакционный источник истины** карточек и справочников — и обязательная metadata-БД для части платформы (Camunda Identity/Web Modeler, Grafana, Superset и т.п.).

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Инстанс / инстанс PostgreSQL** | Один процесс `postgres` (точнее: postmaster + набор backend-процессов) с одним каталогом данных (`PGDATA`). |
| **Кластер PostgreSQL** | Не «Kubernetes-кластер». Это **набор баз на одном PGDATA** (`postgres`, `template1`, ваши БД). Один primary = один такой кластер. |
| **База (`CREATE DATABASE`)** | Логический контейнер схем/таблиц внутри инстанса. Не путать с «кластером» и с «сервером». |
| **Primary (раньше часто master)** | Единственный инстанс, который **принимает запись**. Community PostgreSQL — **не** мультимастер. |
| **Standby / replica / hot standby** | Копия primary по журналу WAL. Hot standby **можно читать**. Писать в неё штатно нельзя. |
| **WAL (Write Ahead Log)** | Журнал «сначала на диск факт изменения, потом сами страницы». Репликация и crash recovery живут им. |
| **Streaming replication** | Standby непрерывно получает WAL по сети с primary. Это **физическая** репликация: копия всего инстанса, не «одной таблицы». |
| **Синхронная репликация** | `COMMIT` на primary **ждёт**, пока указанное число standby подтвердят WAL. Дефолт PostgreSQL: синхронных standby **нет** (`synchronous_standby_names` пустой). |
| **`synchronous_commit`** | Насколько глубоко ждать. `on` (дефолт) + непустой `synchronous_standby_names` = ждать flush WAL на sync-standby. `remote_apply` — ещё и чтобы изменение стало видно на replica (медленнее). `local` / `off` — не ждать replica. |
| **`synchronous_standby_names`** | Кого считать sync. `ANY n (...)` — кворум: любые n из списка. `FIRST n (...)` — приоритет: первые n живых из списка. |
| **Асинхронная репликация** | Primary отвечает клиенту «закоммичено», replica догоняет потом. Падение primary до досылки = **потеря уже подтверждённой** записи. |
| **Failover / switchover** | Смена primary. Switchover — плановый. Failover — аварийный. **В самом PostgreSQL автоfailover нет.** Нужен оператор (CNPG) или Patroni. |
| **Split-brain** | Два инстанса считают себя primary и принимают запись. Потом одну ветку выбрасывают. Это потеря данных, не «потом смержим». |
| **Hot Standby** | Replica принимает `SELECT`, пока догоняет WAL. Читатель может видеть **отставание**. Конфликты replay vs долгий SELECT — отдельная боль (`max_standby_streaming_delay`). |
| **Replication slot** | «Бронирование» WAL на primary для конкретной replica/подписчика. Без слота primary имеет право **удалить** ещё не прочитанный WAL — replica отстанет безвозвратно и её клонируют заново. |
| **Логическая репликация** | Публикация/подписка на уровне таблиц (не побайтовая копия диска). Нужна для выборочного копирования и части апгрейдов. **Не** замена HA. DDL, последовательности, крупные объекты — с оговорками. |
| **`pg_hba.conf`** | Список «с какого адреса, в какую БД, каким методом пускать». Это firewall аутентификации, не NetworkPolicy. |
| **SCRAM-SHA-256** | Как хранить и проверять пароль. Дефолт `password_encryption` с PostgreSQL 14. **MD5 в 18 deprecated**, будет снят в будущем мажоре. |
| **`host` / `hostssl` / `hostnossl`** | Строки `pg_hba`: любой TCP / только TLS / только без TLS. |
| **`ssl`** | Параметр сервера. Историческое имя, имеется в виду **TLS**. Дефолт community: **`off`**. |
| **Суперпользователь (`postgres`)** | Может всё, включая `COPY ... PROGRAM` и чтение файлов ОС. Приложениям **не** выдавать. |
| **Роль / GRANT** | Учётка и права на объекты. Приложение = своя роль с `CONNECT` + DML на свои схемы, без `CREATEDB`/`SUPERUSER`. |
| **RLS (Row Level Security)** | Политика «этой роли видны только такие строки». Это не WAF и не замена отдельной БД на контур. |
| **`shared_buffers`** | Кэш страниц **внутри** PostgreSQL. Дефолт обычно **128MB** (как получится на `initdb`). Для прода этого мало. Это **не** вся RAM машины: остальное — кэш ОС. |
| **`max_connections`** | Потолок одновременных сессий. Дефолт обычно **100**. Каждая сессия — процесс. Раздуть до тысяч «потому что микросервисы» = кончится RAM задолго до QPS. |
| **PgBouncer** | Пул соединений **перед** PostgreSQL: много клиентов делят мало backend-сессий. Режимы: session / transaction / statement. Transaction ломает сессионные фичи (prepared statements в части драйверов, `LISTEN/NOTIFY`, temp tables). |
| **Autovacuum** | Фоновый уборщик мёртвых версий строк (MVCC). Без него таблицы раздуваются, потом кластер упирается в **transaction ID wraparound** и может остановить запись. |
| **PITR** | Point-in-Time Recovery: откат на момент времени из базового бэкапа + архива WAL. Без архива WAL есть только «снимок на вчера». |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. Синхронная репликация целится в RPO≈0 для уже подтверждённого `COMMIT`. Реплика **не** бэкап. |
| **CloudNativePG (CNPG)** | Оператор Kubernetes: CR `Cluster`, поднимает primary+replica, failover, сертификаты, сервисы. |
| **`instances`** | В CR CNPG: сколько подов PostgreSQL. Реплик = `instances - 1`. |
| **Сервисы `-rw` / `-ro` / `-r`** | CNPG: запись (текущий primary) / только replica / любой инстанс. Порт **5432**. Клиенты пишут в **`-rw`**, не в конкретный pod IP. |
| **`dataDurability`** | Ручка CNPG у sync-репликации: `required` (дефолт смысла новой API) — нет живых sync-standby = **запись стоит**; `preferred` — если replica нет, sync временно снимается, запись идёт дальше (окно потери). |
| **Replica cluster (CNPG)** | Другой `Cluster` (часто в **другом Kubernetes**), который непрерывно догоняет источник. Автоfailover **между Kubernetes-кластерами оператор не делает**. |
| **Stretch** | Один логический PostgreSQL-кластер (один primary), инстансы физически в нескольких ЦОДах. |
| **Patroni** | Классический HA-агент для VM: выборы primary через DCS (etcd/consul/…). На Kubernetes в этом файле **не** целевой путь — его роль закрывает CNPG. |
| **Citus / FDW / партиции** | Шарды как отдельный продукт / «таблица на другом сервере» / нарезка одной таблицы. Горизонталь **записи** community PostgreSQL из коробки **не даёт**. |

## Основные элементы системы и зависимости

### Что входит в PostgreSQL 18.6 (это одно ПО из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Primary** | Запись, DDL, источник WAL | **Вертикаль** CPU/RAM/диск. Горизонтали записи нет |
| **Hot standby** | HA и чтение с лагом | Чтение горизонтально (осторожно: лаг и replay-конфликты). Запись всё равно в primary |
| **WAL / archive** | Crash recovery, репликация, PITR | Архив — на объектное хранилище (у вас в платформе есть слой вроде Swift). Это не «ещё одна replica» |
| **Клиенты** | `libpq`, JDBC, драйверы микросервисов, Camunda, Grafana… | Пул **в приложении** + PgBouncer. Не `max_connections=5000` |
| **Расширения** | `pg_stat_statements`, `pgcrypto`, PostGIS, … | Ставятся **в этот** инстанс. Совместимость и обновление — отдельный риск |
| **Утилиты** | `psql`, `pg_dump`/`pg_restore`, `pg_basebackup`, `pg_rewind`, `pg_upgrade` | Операционка, не runtime |

Плюс *рядом*, но это уже другое ПО: **CloudNativePG**, **PgBouncer** (в CNPG — CR `Pooler`), **Barman Cloud plugin**, CSI-диски, объектное хранилище бэкапов, Prometheus postgres-exporter / `PodMonitor`. Их HA проектируется отдельно.

**Patroni и CNPG на один датасет не ставят.** Это два разных способа автоfailover.

### Официальные порты (менять можно, контракт сети лучше не плодить)

| Порт | Назначение |
|---|---|
| **5432/TCP** | Клиенты, репликация, `psql`. У PostgreSQL **нет** отдельного «порта репликации» как cluster bus у Redis. |
| Unix-сокет | Локальные подключения на той же машине/поде. В Docker/K8s приложения почти всегда ходят в TCP. |

UDP нет. TLS — тот же 5432, если `ssl=on` (клиент `sslmode=require` / `verify-full`).

Клиенты:

- Запись: **только primary** (в CNPG — DNS `…-rw`).
- Чтение, если готовы к отставанию: `…-ro`.
- «Любой инстанс» (`…-r`) для записи **нельзя**: replica отклонит DML.

Балансировщик «как у HTTP на все 5432» без разделения rw/ro **ломает** модель так же, как у Kafka: запись попадёт на replica.

### Чего в community PostgreSQL 18 нет (частая путаница)

| Нужно системе | Это не community PostgreSQL 18 | Зачем помнить |
|---|---|---|
| Шина событий, replay, consumer group | Apache Kafka | `LISTEN/NOTIFY` и логическая репликация — не замена вашей шины |
| In-memory кэш с eviction | Redis / Valkey | PostgreSQL можно «прибить» как кэш, но это дорого и не его модель |
| Колоночная аналитика по терабайтам сканов | ClickHouse / склад | PG умеет большие таблицы, но это OLTP-движок. Тяжёлая аналитика на primary убивает OLTP |
| Мультимастер запись в 3 ЦОДах | BDR / Citus MX / проприетарии | Один writer на кластер. Два primary = split-brain |
| Автоfailover «из коробки» | CNPG / Patroni / управляемый сервис | `postgres` сам replica в primary **не** повышает |
| Горизонталь записи (шарды как у Kafka) | Citus, ручной шардинг, несколько БД по доменам | Партиции **внутри** одной БД помогают vacuum и вычищать старое, не добавляют второй writer |
| Озеро файлов/выгрузок ведомств | Object storage (Swift и т.п.) | BYTEA/toast на терабайтах вложений — слабое место |
| ГОСТ TLS / СКЗИ | Не входит | Штатный TLS OpenSSL сборки — не криптография КИИ, если ИБ её выдвинет |
| Официальный порог RTT между ЦОДами | Нет | Sync `COMMIT` не может быть быстрее, чем подтверждение standby. Миллисекунд в доке **нет** |
| Замена бэкапа репликами | Нет | `DROP TABLE` / кривой мигратор / шифровальщик **реплицируются** на все standby |
| Хранение секретов приложений | Vault | Пароли ролей — в Secret/Vault, не в Git и не в `postgres` суперпользователе приложения |

### Зависимости окружения (обязательны)

- **Диск.** Локальный быстрый том (SSD/NVMe) под `PGDATA`. **Не NFS как единственный диск primary** (латентность `fsync`, риск «закоммитили в никуда» при сетевом STO). CNPG прямо рекомендует **application-level** репликацию и **не** рекомендует полагаться на storage-level replication «вместо» standby. Shared-nothing: инстансы на **разных** нодах, **разное** хранилище, лучше разные зоны.
- **RAM.** `shared_buffers` + `work_mem` × сессии + autovacuum + OS cache. Лимит cgroup без запаса → OOM в VACUUM/отчёте, не «в простой SELECT».
- **CPU.** Один primary = потолок записи. Параллелизм SELECT — отдельные воркеры; OLTP-запись часто упирается в WAL и индексы, не в «добавим реплик».
- **Сеть.** Стабильный IP/DNS до **5432** primary и между инстансами (WAL). NAT/случайный NodePort как у веб-приложения ломает replica и слоты. В K8s — сервисы оператора, не «под IP пода в JDBC навсегда».
- **Kubernetes (у вас заявлен 1.36.x).** Stateful нагрузка. Практичный путь: **CNPG 1.30.0**. Совместимость с K8s 1.36 официально в релизе оператора. CSI с `WaitForFirstConsumer`, anti-affinity по `topology.kubernetes.io/zone`. Официальный `postgres:18.6` **не** является образом CNPG (оператор подменяет entrypoint своим instance manager; нужны образы `ghcr.io/cloudnative-pg/postgresql`).
- **Объектное хранилище** под WAL-архив и бэкапы (PITR). Без него «три replica» всё ещё не дают вернуть данные на 15:03 вчера.
- **PKI** для прода: TLS к клиентам и к репликации. CNPG по умолчанию закрывает streaming TLS-сертификатами (`hostssl … cert` для роли `streaming_replica`).
- **Клиенты**, которые переживают смену primary: короткий timeout, reconnect, **не** sticky на pod IP. JDBC/`libpq` на Service `-rw`.

### Как PostgreSQL стыкуется с вашей архитектурой

```
Микросервисы, Camunda job workers, интеграционное API
        │  транзакции, карточки, идемпотентность «в БД», outbox
        ▼
   PostgreSQL 18.6  (OLTP / SoT операционных сущностей)
        ▲
Kafka ── остаётся шиной событий (факт «изменилось»)
Озеро файлов / склад ── сырьё, выгрузки, аналитика, не замена транзакции
Camunda ── состояние процесса в Zeebe; Identity/Modeler — отдельные БД PG
Redis/Valkey ── кэш и короткие локи, не карточка клиента
```

Честные роли в *вашей* картине:

1. **Транзакционный эталон** клиентской карточки / справочника, который сервисы меняют с `COMMIT` и внешними ключами. Это ближе всего к «источнику истины», который руководство называет озером **если** озеро у вас реляционное, а не «файлы в object storage».
2. **Metadata платформы** — отдельные **кластеры или хотя бы отдельные databases**: Camunda Identity/Web Modeler, Grafana, Superset, Backstage. Падение отчёта не должно валить SoT.
3. **Outbox / идемпотентность** рядом с записью в SoT, чтобы событие в Kafka не разъехалось с БД.
4. **PostGIS** — если ГИС (GeoServer) читает контуры; это расширение **этого** или отдельного GIS-кластера, не «ещё ClickHouse».

Нечестные роли:

- «Положим всех клиентов и все ответы 30+ ведомств на годы в одну БД без партиций и TTL архива» — диск и vacuum не бесконечны; «терабайты» без политики хранения съедят primary.
- «Три primary в трёх ЦОДах, пишем во все» — community PostgreSQL так не работает.
- «Реплика = бэкап, архив WAL не нужен» — ошибка операционки.
- «ClickHouse заменит PostgreSQL для карточки, которую правит оператор» — другая модель consistency.

## Краткие вводные

### Зачем вам PostgreSQL в этой архитектуре

Kafka доставляет факт. Кэш отвечает быстро. Camunda ведёт процесс. Интеграционное API ходит в ведомства.

Остаётся вопрос: **где лежит текущая правда** «этот клиент, эти реквизиты, этот статус», которую нельзя потерять при failover кэша и неудобно собирать `SELECT по ИНН` из лога Kafka. Реляционная СУБД с транзакциями, ограничениями и PITR — этот слой.

Если эталон задуман как **файловое озеро** (сырые выгрузки, вложения) — PostgreSQL его не заменяет; он хранит **индекс/карточку**, файлы — в object storage.

### Как устроена отказоустойчивость (идея, не магия)

База — **один writer** плюс копии WAL. Путать «три контейнера в compose» с HA — главная ошибка.

**1) Репликация сама по себе failover не делает**

| Что падает | Что происходит |
|---|---|
| Primary, replica есть, **нет** оператора/Patroni | Replica содержит копию (с лагом, если async). Клиенты на старый адрес **стоят**. Кто-то должен сделать `pg_ctl promote` |
| Replica | Чтение с неё пропадает; запись на primary жива |
| Primary без архива WAL и без слота, replica отстала | Replica может стать бесполезной; нужен новый `pg_basebackup` |
| `DROP DATABASE` / плохая миграция на primary | Успешно уедет на **все** replica |

**2) Синхронная vs асинхронная**

Официально: пока `synchronous_standby_names` пуст, `synchronous_commit=on` ждёт только **локальный** flush. Это дефолт. «Поставили две replica» ≠ RPO=0.

Если включили sync: `COMMIT` ждёт standby. Документация PostgreSQL прямо: транзакция **может не завершиться никогда**, если sync-standby упал и его некому заменить. Это цена RPO=0.

CNPG: sync **выключен, пока не задан** блок `postgresql.synchronous`. Типичный прод для 3 инстансов:

```yaml
postgresql:
  synchronous:
    method: any
    number: 1
    dataDurability: required   # нет живой replica → запись стоит
```

`dataDurability: preferred` — ближе к «система должна работать»: запись продолжится без sync, появится окно потери. Это **явный** выбор, не дефолт новой API.

**3) Оператор (CNPG) внутри одного Kubernetes**

Официально: recommended — Kubernetes на **3+ зоны**, инстансы PG на разных нодах и зонах, local disk, не storage-replication «вместо» replica.

| Что падает | Что происходит |
|---|---|
| Под primary, replica живы, оператор жив | Promote наиболее свежей replica, сервис `-rw` переезжает |
| Зона/ЦОД с primary, две другие живы, это **один** K8s | То же, если replica были в живых зонах и сеть 5432 жива |
| Нет majority / нет живой replica и `dataDurability: required` | Запись стоит (для sync). Это защита, не баг |
| **Два из трёх ЦОДов**, инстансы по одному на ЦОД | Один оставшийся. Для async может стать primary. Для sync `ANY 1` — некого ждать, пока не ослабите durability. Кворум **Kubernetes etcd** при потере двух зон — отдельный отказ (см. документ Kubernetes) |
| Три изолированных Kubernetes | CNPG **не** фелиоверит primary в чужой кластер. Это replica cluster + **ручной/GitOps** switchover |

**4) Replica cluster между Kubernetes (DR)**

CNPG: bootstrap с `pg_basebackup` / snapshot / Barman; догон streaming и/или WAL из object store. Автоfailover **across clusters is not within CloudNativePG's scope**. Для двух площадок вендор прямо рисует active/passive и ручной promote.

**5) Бэкап и PITR**

Реплики не заменяют `pg_dump`/volume snapshot + **непрерывный WAL archive**. Проверяют **restore**, не наличие файла в бакете.

### Как устроено масштабирование

Несколько независимых осей — их нельзя склеить в «добавим replica»:

1. **Больше данных** → диск primary (и каждой replica: полный размер), партиции, архив старого в озеро/склад. Replica **не** уменьшает объём.
2. **Больше чтения** → hot standby + приложения на `-ro` (лаг!). Аналитику лучше **не** на OLTP-primary (у вас есть ClickHouse).
3. **Больше записи** → вертикаль primary, меньше лишних индексов, batch вместо построчной вставки «как в лог», разнести **разные** домены по **разным Cluster** (SoT ≠ Grafana). Второй writer community PG не появится.
4. **Больше соединений** → PgBouncer, не раздувание `max_connections`.
5. **Терабайты** → возможны на одном primary при дисциплине vacuum, партиций, архива. Это не доказательство, что **ваш** профиль влезет: нагрузки нет.

Ориентиры, которые **есть** у вендора, и которые **нельзя** принять за смету вашего прода:

- `shared_buffers` дефолт **~128MB**; «нужно заметно больше минимума» — формулировка runtime-config, без числа «25% RAM» в этой главе.
- `max_connections` дефолт **~100**.
- `ssl` дефолт **off**.
- Sync replication дефолт **выключен**.
- Нагрузки у вас нет — поэтому **нет** цифры «N CPU и M ТБ».

### Безопасность самого PostgreSQL

Модель: сервер слушает тех, кого пустил `listen_addresses` + `pg_hba`. Дефолт `listen_addresses = localhost`. Образы Docker/K8s почти всегда слушают `*`, иначе из пода приложения не подключиться — значит **hba, пароль, TLS и NetworkPolicy обязательны**, иначе 5432 — вход в ПДн.

Компрометация SoT клиентов / ответов ведомств = компрометация **содержимого**, не «только схема». Суперпользователь в приложении = возможность читать файлы и запускать программы из сессии (`COPY PROGRAM` и класс атак вокруг расширений — в 18.6 как раз пачка CVE).

Официально:

- Пароли: SCRAM-SHA-256; MD5 deprecated.
- Канал: TLS (`ssl=on`, в hba `hostssl`). Пароль без TLS на `host` виден снифферу, если метод не SCRAM (SCRAM не шифрует **трафик запросов и строк** — только обмен паролем). Строки карточек по городу между ЦОДами без TLS — отдельное принятие риска ИБ.
- Клиентский сертификат — сильнее пароля; CNPG так закрывает репликацию.
- Не `trust` с не-loopback.
- Приложение — не superuser; отдельная БД; `CONNECT` + права на схему.
- Расширения (`CREATE EXTENSION`) — поверхность атаки; ставить сознательно.
- At-rest: шифрование тома CSI/LUKS. В community нет «галочки encrypt tablespace» как полной замены диску.

«Поднять `docker run -e POSTGRES_HOST_AUTH_METHOD=trust -p 5432:5432 postgres`» — это учебный антипаттерн, не платформа.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть, а не «чуть подкрутить порт».

1. **Берём community PostgreSQL 18.6**, не Postgres Pro, не EDB, не облачный Aurora-совместимый форк. Поведение HA и лицензия у них другие.
2. **Прод крутится в Kubernetes 1.36.x**, инсталлятор — **CloudNativePG 1.30.0**. Образ инстансов — CNPG (`ghcr.io/cloudnative-pg/postgresql`), **пиним 18.6**, не дефолт оператора 18.4. Альтернатива VM+Patroni допустима; правила sync/WAL/hba те же, отличается упаковка.
3. **Три ЦОДа = три зоны отказа.** Если это три зала с общим питанием — stretch даёт ложное чувство безопасности.
4. **Stretch одного `Cluster` на 3 ЦОДа принимается только если** это **один** Kubernetes (или эквивалентная L3-связность подов) и сеть 5432 достаточно быстрая и стабильная. Порога RTT у PostgreSQL **нет**. Пока RTT не измерен — гипотеза.
5. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. Два ЦОДа из трёх при одном инстансе на ЦОД оставляют одну копию; sync `ANY 1` и кворум etcd могут остановить запись/управление.
6. **Нагрузки нет** — поэтому **нет** цифры «N ядер и M терабайт». Есть сигналы (`pg_stat_activity`, replication lag, `checkpoints_timed` vs `req`, bloat, `max_connections`, WAL rate) и рычаги (вертикаль, пул, разнос кластеров, партиции).
7. **Формального SLA / RPO / RTO нет.** Для SoT клиентов в этом файле целевой смысл прода: **RPO≈0 на подтверждённый COMMIT** (sync `ANY 1` + `dataDurability: required`), ценой возможной остановки записи без живой replica. Если приоритет «пишу любой ценой» — это `preferred` или async, и это **другое** обещание руководству.
8. **Корпоративный PKI есть или будет** для клиентского TLS и (если не хватает встроенного CA CNPG) для взаимного доверия. `sslmode=disable` в проде между площадками — принятие риска, не дефолт этого файла.
9. **Идентификация сервисов** — отдельные роли PostgreSQL (и `DatabaseRole` CNPG), least privilege. Люди в прод-БД — через jump/`psql` с аудитом, не учётка приложения.
10. **Шифрование канала — TLS сборки PostgreSQL/OpenSSL.** ГОСТ/СКЗИ не озвучены.
11. **Тестовый стенд изолирован.** На нём допустим один инстанс без TLS на закрытой сети. В прод это не копируем.
12. **Kafka, Camunda, озеро файлов, интеграционное API** — клиенты 5432, не часть этого ПО. Контракт: запись в SoT и публикация в Kafka согласованы (транзакция + outbox), кэш не считается истиной.
13. **«Озеро эталона» не целиком в одной БД.** Операционные карточки — PostgreSQL. Сырые пакеты ведомств, вложения, долгая история — object storage / склад. Иначе смета диска и vacuum не сходится с «огромный объём».
14. **Несколько Cluster, не одна БД на всю платформу.** Минимум отделить SoT от metadata (Camunda Identity/Modeler, Grafana, Superset). Иначе «упал BI» и «vacuum отчёта» бьют по клиентам.
15. **Бэкап в object storage + проверка restore** входят в определение «прод», не в «фазу 2».
16. **Юристы принимают PostgreSQL License и Apache-2.0 CNPG.** Это не SSPL.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили Cluster и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT, jitter, потери на 5432 между ЦОДами** (p50/p95/p99, все пары) | Sync `COMMIT` ≥ времени flush на standby. Высокий/плавающий RTT → таймауты приложений, «БД висит», ложный failover. Stretch станет источником аварий |
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Автоfailover CNPG работает **внутри одного** K8s. Три острова = replica cluster и **ручной** DR, сколько бы replica ни стояло |
| **Что именно кладёте в PostgreSQL** (карточка клиента? сырой XML ведомства? логи Camunda? всё сразу?) | Разный объём, TTL, RLS, пул, sync. «Терабайты» без состава — не смета |
| **Пик соединений** (сервисы × пул Hikari/pgbouncer × воркеры Camunda) | `max_connections` кончится раньше CPU. «Горизонталь подов приложения» без пула убивает primary |
| **Нужна ли запись после падения 1 ЦОДа ценой возможной потери хвоста async** | `dataDurability` required vs preferred. Дефолты CNPG sync и лозунг «работа беспрерывна» **противоречат** друг другу, пока это не выбрано явно |
| **152-ФЗ / срок хранения ПДн** | RLS, отдельные роли, шифрование томов, архив не в том же бакете что публичные бэкапы без ключа |
| **Профиль нагрузки** (транзакций/с, размер строки, чтение/запись, пик интеграций) | Без этого нельзя сказать CPU, `shared_buffers`, диск WAL |
| **Политика хранения** | Без партиций/архива любой OLTP с «терабайтами навсегда» упрётся в vacuum и диск |
| **CSI / local disk vs сетевая СХД** | CNPG: shared-nothing, лучше local. СХД с синхронной репликацией диска **плюс** sync standby — двойная латентность; СХД вместо standby — против рекомендации оператора |
| **Кто владеет схемой** (миграции Flyway/Liquibase vs суперпользователь в CI) | Случайный `DROP` уедет на replica быстрее, чем кто-то нажмёт restore |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **PostgreSQL 18.6** и (для K8s) **CNPG 1.30.0**. Образ пинить, не `postgres:18`.
2. Решить **роль данных** (SoT карточек / metadata платформы / GIS) → из этого отдельный `Cluster`, sync, пул, RLS. Не наоборот.
3. Решить **топологию**: 1 инстанс / 1 primary+replica в одной зоне / stretch 3 зоны / replica cluster в другом K8s.
4. Выставить диск (fsync живой, не NFS «чтобы PVC нашёлся») **до** боевой записи.
5. Включить **аутентификацию и TLS** до боевых клиентов. Не `trust` и не `sslmode=disable` «как в примере».
6. Задать **`shared_buffers` / `max_connections` / пул**. Без этого HA не спасает от OOM и `FATAL: remaining connection slots`.
7. Включить мониторинг: лаг репликации, `pg_stat_replication`, слоты, WAL rate, autovacuum wraparound, бэкап last-success, failover.
8. Прогнать запись/чтение. Убедиться, что строка **видна** и что падение primary на проде оставляет *ту* семантику COMMIT, на которую подписались.
9. Прогнать **контролируемый switchover**. Без этого у вас нет HA, есть надежда.
10. Прогнать **restore** из бэкапа на стенде (PITR). Без этого у вас нет бэкапа, есть файл.
11. Только потом — RLS, отдельные роли на сервис, PgBouncer transaction vs session по факту драйверов.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики создавали таблицы, гоняли миграции, подключали микросервис/Camunda worker. **Не** цель: доказать отказ ЦОДа и ёмкость терабайт.

Официальный минимальный путь:

```text
docker run -d --name pg-dev -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:18.6
```

Проверка: `docker exec -it pg-dev psql -U postgres -c 'SELECT version();'` — в строке должна быть **18.6**.

На Kubernetes: CNPG `Cluster` с `instances: 1`, маленький PVC. Не копировать этот манифест в прод. Bitnami-subchart из чужого Helm (Camunda/Superset) — только чтобы чарт «поднялся», не ваш SoT.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число инстансов | 1 | Нет требования пережить выкат |
| Sync replication | нет | Некому подтверждать |
| Пароль | простой, **только изолированная сеть** | Иначе команда утонет в Vault раньше схемы |
| TLS | нет | Иначе PKI раньше продукта |
| `shared_buffers` | дефолт / сотни МБ | Не цель — ёмкость |
| PgBouncer | можно без | На тесте десяток соединений |
| WAL archive / PITR | можно без на сутки | На препроде включить **тот же** механизм, что в проде |
| Мониторинг | логи + `SELECT 1` | Нет нагрузки |

#### Чего на тесте **не** стоит упрощать

- Версия **18.6** (не «какой postgres есть у devops», не 14 «потому что в чарте Bitnami»).
- **Отдельная БД и роль** на сервис, не всё под `postgres`. Иначе в проде суперпользователь «уже привычен».
- Клиентский код пишет в **hostname сервиса**, не в IP пода. Иначе failover «не влезает» в приложение.
- Миграции идемпотентны; нет ручного `DROP` на проде-подобных данных.
- Если цель прода — чтение с replica: на препроде маленький кластер `instances: 3` и проверка, что приложение **не** пишет в `-ro`.
- Понимание: успешный `INSERT` на одном процессе **не** доказывает failover и **не** доказывает sync через ЦОД.

#### Сильные стороны такой схемы

- Поднимается за минуты, совпадает с официальным Docker-образом.
- Дешево показывает схему карточек и миграции.
- Один инстанс официально нормален для development.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет лага replica, нет поведения sync под RTT.
- `-p 5432:5432` на рабочей станции легко оказывается «торчит в Wi-Fi».
- `POSTGRES_HOST_AUTH_METHOD=trust` из плохих шпаргалок уедет в прод.
- Дефолтные 128MB `shared_buffers` создают ложное чувство «PG и так быстрый».

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (3 инстанса, sync как в проде, TLS, архив WAL, хотя бы один Pooler), даже без боевого трафика.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «терабайты под озеро» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Сначала развилка **по сети Kubernetes**, затем sync.

**Вариант A — stretch: один CNPG `Cluster` на 3 ЦОДа (один Kubernetes, три зоны).**  
Предпочтителен, если это тот stretch, который описан у вас в документе Kubernetes, и 5432 — метро-класс.

- Клиентам один `…-rw`.
- Падение 1 ЦОДа не требует «переключения на другой PostgreSQL», если в живых зонах осталась replica и (для sync) кого ждать.
- Каждый `COMMIT` с sync `ANY 1` идёт через межЦОДовую репликацию → латентность записи привязана к RTT.

CNPG это прямо рекомендует как архитектуру «3 AZ в одном кластере». Shared-nothing: по инстансу в зоне, local disk, taint `node-role.kubernetes.io/postgres`.

**Вариант B — мозг в одном ЦОДе** (primary+2 replica в ЦОД-1, клиенты с ЦОД-2/3 ходят по городу).

Проще кворум K8s и короче sync RTT. Падение ЦОД-1 = нет записи ни у кого, пока не поднимете DR. Спасает replica cluster / restore **с прогоном по времени**.

**Вариант C — три (или два) Kubernetes + CNPG replica cluster.**  
Если K8s изолированы. Официально: оператор **не** делает автоfailover между кластерами. Streaming и/или WAL из object store. Switchover — demote/promote (GitOps). RPO при чисто архивном догоне **> 0** (пока WAL не доехал).

**Пока топология K8s и RTT не зафиксированы, нельзя честно выбрать A.** Дальше A как целевой «3 ЦОДа в одном городе»; B/C — запасные, если замер сети или три острова K8s убьют A.

##### Сильные / слабые стороны stretch (A)

| Сильное | Слабое |
|---|---|
| Один endpoint `-rw`, модель как у разработчиков | Латентность `COMMIT` ≥ RTT до sync-standby |
| Падение 1 ЦОДа может обойтись без ручного promote | Сетевой шторм выглядит как «БД встала» (особенно `dataDurability: required`) |
| Совпадает с рекомендацией CNPG 3 AZ | Не переживает 2 ЦОДа; зависит от живого etcd K8s |
| | Ошибка DDL сразу везде |

##### Сильные / слабые стороны «мозг в одном ЦОДе» (B)

| Сильное | Слабое |
|---|---|
| Sync не зависит от межЦОДового RTT | Падение этого ЦОДа = простой SoT на всех трёх |
| Проще отлаживать failover внутри площадки | Нужен явный DR: replica cluster или PITR **с замером RTO** |
| | Клиентский путь 5432 через город — уже ваша сеть и TLS |

##### Сильные / слабые стороны replica cluster (C)

| Сильное | Слабое |
|---|---|
| ЦОД/K8s независимы | **Нет** автоfailover между кластерами (формулировка CNPG) |
| Можно пережить отказ целого Kubernetes | RPO≠0, если догон только архивом; дубли/рассинхрон ролей при кривом promote |
| | Операционка сложнее, чем «один Cluster» |

##### Слабое место любого stretch без замера RTT

Утверждение «три ЦОДа в одном городе, значит можно размазать sync PostgreSQL» — **непроверенное**. Мерить **5432**, не ping ICMP.

---

#### Если stretch A (рекомендуемый старт, пока один K8s и сеть не опровергли)

Минимум для цели «пережить 1 ЦОД» и RPO≈0 на COMMIT:

- **`instances: 3`**, по одному поду в каждом ЦОДе (topology spread / anti-affinity по зоне).
- **Не** складывать два инстанса в одну зону «чтобы проще».
- Sync:

```yaml
postgresql:
  synchronous:
    method: any
    number: 1
    dataDurability: required
```

- Понимать цену: потеря связи с обеими чужими зонами = **запись стоит**. Если руководство требует «пишем всегда» — либо `preferred` (окно потери), либо это уже не RPO=0.
- Replication slots для HA — включить штатами CNPG, чтобы после failover WAL для оставшихся не подчистился.
- Клиенты знают **Service `-rw`**, не pod name. После failover оператор перекладывает Endpoints.
- Persistence: PVC на каждый инстанс, StorageClass локальный/зональный, `WaitForFirstConsumer`.
- Ноды: taint/label postgres, как в architecture CNPG (кратность трём, по зоне).
- PDB: не эвакуировать сразу primary и единственную sync-replica при drain.
- Ресурсы: requests≈limits по RAM с запасом на autovacuum; CPU throttle → рост лага → ложный failover.

Раскладка:

```
ЦОД1: PostgreSQL (может быть primary)
ЦОД2: hot standby
ЦОД3: hot standby
оператор CNPG: не в одном поде с primary; сам оператор — несколько реплик Deployment
```

После failover primary «переедет». Сеть и `-rw` должны это пережить. Приложение — reconnect.

##### Сильные / слабые стороны 3 инстансов + sync ANY 1

| Сильное | Слабое |
|---|---|
| Официальный рисунок CNPG 3 AZ; RPO≈0 при живой sync-replica | Один writer — потолок |
| Падение 1 ЦОДа: 2 копии, есть кого promote | Падение 2 ЦОДов — одна копия, sync required останавливает запись |
| Чтение можно снять на `-ro` | Читатель видит лаг; replay может отменять долгие SELECT |
| | Клиент со sticky IP = простой после promote |

`number: 2` (ждать **обе** replica) на трёх ЦОДах означает: любой один мёртвый ЦОД (если там была sync-цель) плюс строгий кворум — запись встанет чаще. Для «пережить 1 ЦОД и продолжать писать» обычно **`number: 1`**, не 2.

#### Несколько кластеров PostgreSQL, не один «на всех»

| Cluster | Зачем отдельно |
|---|---|
| **SoT** (карточки, справочники операционные) | Другой RPO, другой объём, другие роли |
| **Camunda Identity / Web Modeler** | Падение моделлера ≠ остановка SoT; в документе Camunda это уже сказано |
| **Grafana / Superset metadata** | То же |
| **GIS/PostGIS** (если контуры огромные) | VACUUM/индексы GiST не должны делить диск с OLTP карточки |

Это не «микросервис = свой postgres в углу без HA». Это **несколько HA-кластеров** с понятным владельцем.

#### Производительность и рост (когда цифры появятся)

| Параметр | Прод-правило | Зачем |
|---|---|---|
| `shared_buffers` | Заметно выше 128MB, ниже RAM пода, оставить долю ОС | Дефолт для прода мал. Точную долю не выдумываем без замера |
| `max_connections` | Малый потолок на сервере + **PgBouncer** | Тысячи backend-процессов съедают RAM |
| Pooler | CNPG `Pooler` перед `-rw` (и отдельно перед `-ro`, если нужно) | Не пускать каждый под приложения отдельным TCP на primary |
| Режим PgBouncer | Начать с **session**, если драйверы/prepared statements не проверены; transaction — только после теста | Иначе «в проде внезапно» ломается JDBC |
| WAL / диск | Отдельный быстрый диск под WAL, если СХД позволяет | Checkpoint и OLTP дерутся за один том |
| `fsync` | **on** (не выключать «для скорости») | Выключить = принять потерю COMMIT при крахе ОС |
| Autovacuum | Включён; следить за wraparound и bloat | На «терабайтах» это ось жизни, не фон |
| Партиции | По времени/диапазону на растущих таблицах | Иначе DELETE/VACUUM вечные |
| Индексы | Только доказанные запросами | Каждый индекс множит WAL и тормозит INSERT |
| Чтение | Тяжёлые отчёты — склад/ClickHouse, не primary SoT | Иначе OLTP и «беспрерывность» проиграют одному дашборду |
| Расширения | `pg_stat_statements` — да. Остальное — по списку | Лишние `.so` = CVE как в 18.6 (`pgcrypto`, `ltree`, …) |

Масштабирование под нагрузку:

1. Замерить TPS, размер WAL/с, p95 `COMMIT`, hit/miss буферов, число сессий.
2. Если CPU/WAL primary упёрлись — вертикаль и/или вынести домен в другой Cluster, не «ещё replica для записи».
3. Если соединения — Pooler.
4. Если диск — партиции + архив в озеро, не бесконечный retention в OLTP.
5. Асинхронный I/O PostgreSQL 18 (`io_method` и связанное) — включать **по замеру** на вашем ядре/диске, не «потому что мажор 18».

#### Безопасность прода

Три слоя, все три:

1. **Сеть** — 5432 только приложениям и инстансам PG. NetworkPolicy. Не LoadBalancer в интернет. Порты instance manager CNPG (status/метрики) — только оператору; в 1.30.0 закрывали GHSA на неаутентифицированный status-порт — NetworkPolicy всё равно нужна на старых соседних кластерах.
2. **Аутентификация** — SCRAM и/или клиентский сертификат. Не `trust`, не MD5 как целевой метод.
3. **Авторизация** — роль на сервис, своя БД/схема, без superuser. RLS, если несколько потребителей ПДн в одной БД.

| Слой | Правило |
|---|---|
| `listen_addresses` | В контейнере `*`, компенсация — hba + NetworkPolicy |
| `pg_hba` | `hostssl` + `scram-sha-256` (или `cert`) с узких CIDR/NS. Не `0.0.0.0/0` |
| TLS | `ssl=on`. Клиенты `verify-full` с CA. CNPG умеет выпускать серверные/клиентские сертификаты; для людей — корпоративный CA |
| Пароли | Secret/Vault; CNPG 1.30 кодирует пароли ролей в SCRAM **до** SQL (CVE-2026-55765), не полагаться на логи `pg_stat_statements` как на сейф |
| Superuser | Только DBA/оператор. Приложение — нет |
| `search_path` | Не оставлять приложение с записью в `public` как superuser: класс атак перегрузки операторов (в 1.30.0 оператор пинит `search_path` у своих коннектов — приложениям то же дисциплина) |
| At-rest | Шифрование PVC. Community не заменяет это настройкой `ssl` |
| Аудит | Логи подключений, `pg_audit`/эквивалент если ИБ потребует; не логировать тела ПДн |
| Обновления | 18.6 закрыл пачку RCE-класса в функциях и contrib. Процесс minor-апдейта — **плановый**, не «когда вспомним» |

##### Сильные / слабые стороны (сеть + роли + TLS)

| Сильное | Слабое |
|---|---|
| Штатные hba/SCRAM/TLS, без Enterprise-лицензии | Ошибка hba = «сервис не коннектится»; нужен процесс выдачи |
| CNPG закрывает репликацию сертификатами из коробки | TLS бьёт по CPU; сертификаты в каждом клиенте |
| Least privilege спасает от одного скомпрометированного сервиса | SQL injection в приложении = доступ в пределах GRANT этой роли |
| | Не ГОСТ; расширения contrib — отдельная поверхность |

Если появится корпоративный IdP — в PostgreSQL 18 есть **OAuth-аутентификация** как опция сервера. Это не дефолт CNPG и не замена ролей на объекты. Людей в SoT по-прежнему не пускают «логином как в Dashboards»; пускают сервисы ролями, людей — через контролируемый jump.

#### Kubernetes-специфика прода

- CR `Cluster` / `Pooler` / `ScheduledBackup` / `DatabaseRole`, **не** Deployment с одним PVC «как у stateless».
- Образ **18.6** в `spec.imageName` (или ImageCatalog), не дефолт 18.4 оператора.
- Бэкап: **Barman Cloud plugin**, не строить процесс на in-tree (снимут в 1.31.0). WAL в тот же контур object storage, что вы уже описывали для платформы.
- Anti-affinity по зоне; не класть primary и обе replica на одну ноду.
- Не ставить PG на overlay с большим jitter без замера. Если pod-сеть между ЦОДами хуже VM — иногда честнее вариант B/C.
- Мониторинг оператора и инстансов: лаг, слоты, статус primary, последняя удача бэкапа. Зелёный под ≠ «WAL доехал».
- Обновление minor: rolling по replica, затем switchover. Major 18→19 — только после GA 19 и `pg_upgrade`/синей-зелёной схемы; **Beta 3 не прод**.

#### Что прогнать, прежде чем назвать это продом

1. `SELECT version()` = 18.6 на всех инстансах.
2. Запись через `-rw`, чтение через `-ro`, попытка записи в `-ro` — отказ.
3. Убить под primary — сервис `-rw` переехал, приложение переподключилось, **число строк** совпало с ожиданием sync (не «почти все»).
4. Изолировать одну зону (если стенд позволяет) — поведение как в таблице выше, не сюрприз.
5. Restore PITR на чистый Cluster.
6. Исчерпание пула соединений (нагрузочный стенд) — ошибка понятная, не лавина процессов на primary.
7. Проверка, что суперпользователь из приложения **не** проходит.

Пока нет замера RTT и профиля TPS, это **правила сборки**, не сертификат «готовы к высокой нагрузке». Готовность к нагрузке появится после цифр, не после третьей replica.
