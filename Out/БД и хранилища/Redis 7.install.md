# Redis Community Edition 7.4.11 — установка и конфигурирование

Связанный документ (глоссарий, HA, безопасность, почему так): `Redis 7.md`.

Этот файл — **как поставить и настроить**. Не копируйте Dev-значения в прод. Stretch одного Sentinel-набора или одного Redis Cluster на несколько ЦОДов **не делаем**: межЦОДовый RTT для gossip/`cluster-node-timeout` и для ping Sentinel неприемлем; порога миллисекунд у Redis **нет**.

Версия: **Redis Community Edition 7.4.11**. Образ: `redis:7.4.11` (не `7.4`, не `7`, не `latest`). Лицензия линии 7.4 — **RSALv2 или SSPLv1** (не BSD). Официального OSS-оператора у Redis Ltd **нет** (их оператор — Enterprise).  
Документация: https://redis.io/docs/latest/operate/oss_and_stack/ · конфиг 7.4: https://github.com/redis/redis/blob/7.4/redis.conf

Redis в этой платформе — **кэш / сессии / идемпотентность / короткие локи**, не источник истины (SoT). Эталон остаётся в озере/СУБД.

---

## Допущения этой инструкции

Их не было в исходном контексте платформы; без них нельзя дать конкретные команды.

1. **Stretch запрещён.** Sentinel-кворум и (если когда-нибудь понадобится) Cluster bus живут **внутри одного ЦОДа** (одного Kubernetes). Между ЦОДами — независимые кэши **или** холодная `replicaof` вне кворума (async, ручной DR). Автоfailover «мастер переехал в чужой ЦОД» **не** цель.
2. Прод — **vanilla Kubernetes 1.36.x + kubeadm** в каждом ЦОДе отдельно (см. `Kubernetes.install.md`). Упаковка: StatefulSet + официальный образ **или** community-оператор (например OT-CONTAINER-KIT) **после** прогона именно 7.4.11 — матрицы «как Strimzi ↔ Kafka» нет.
3. Юристы **принимают RSALv2/SSPL** для закрытого контура. Если нет — этот файл не разрешение ставить 7.4; смотрят 7.2.16 (BSD) или Valkey.
4. Dev — изолированная сеть; пароль в примере не секрет.
5. Нагрузки нет — поэтому **нет** цифры CPU/RAM/`maxmemory` «хватит для прода». Есть минимум, чтобы процесс жил, и рычаги роста.
6. Для 2 ЦОДов: активный Sentinel-набор в ЦОД-1, в ЦОД-2 — независимый Redis **или** async-копия вне кворума. Для 3 ЦОДов: то же + вторая независимая копия или только бэкапы RDB. Третий ЦОД **не** добавляет второго writer на те же ключи.
7. Клиенты умеют (или будут уметь) **Sentinel**. Захардкоженный IP master переживает только standalone.

## Dev: 1 ЦОД, без нагрузки

**Цель:** ключи, TTL, клиент микросервиса/Camunda worker. **Не** цель: отказ площадки и гигабайты RAM.

### Предпосылки

- Docker Engine (стенд разработчика) **или** любой однонодовый Kubernetes.
- Порт 6379 свободен на localhost.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь Dev)

```bash
docker run -d --name redis-dev \
  -p 127.0.0.1:6379:6379 \
  redis:7.4.11
```

Привязка к `127.0.0.1` обязательна: `-p 6379:6379` без адреса часто слушает все интерфейсы. Образы часто bind `*` и снимают protected mode «чтобы завелось».

Проверка:

```bash
docker exec -it redis-dev redis-cli PING
docker exec -it redis-dev redis-cli INFO server | grep redis_version
```

Должно быть `PONG` и версия **7.4.11**. Затем завести ACL-пользователя приложения (не оставлять «весь мир = default» привычкой в прод):

```bash
docker exec -it redis-dev redis-cli ACL SETUSER app \
  on '>dev-app' '~app:*' '+@read' '+@write' '+ping' '+info'
```

Клиент — на `localhost:6379`, пользователь `app`, ключи с префиксом `app:`. Не `FLUSHALL` из приложения.

### Установка (Kubernetes Dev, если стенд уже в K8s)

Один StatefulSet, 1 replica, образ `redis:7.4.11`, порт сервиса не публиковать наружу кластера. PVC маленький или без persistence на сутки. **Не** этот YAML в прод. Community-оператор на Dev не обязателен.

### Конфигурирование Dev

| Параметр | Значение | Зачем |
|---|---|---|
| Один инстанс | да | Некому строить Sentinel |
| Sentinel / Cluster | нет | Иначе команда утонет в discovery/MOVED раньше ключей |
| TLS | нет | Иначе PKI раньше продукта |
| `maxmemory` | 256–512 МБ, если ставите | Не цель — ёмкость; в проде задают **всегда** |
| Persistence | AOF можно выкл. | Потеря ключей при рестарте терпима; на препроде включить **то же**, что в проде |
| `protected-mode no` + bind `*` без пароля | **запрещён** даже на Dev, если порт не loopback | Привычка уедет в прод |

Чего **не** упрощать: версия 7.4.11; префиксы ключей и TTL в коде; клиент ходит на hostname, не на IP контейнера.

### Проверка Dev

1. `INFO server` → 7.4.11.
2. `SET`/`GET` с префиксом приложения.
3. Рестарт контейнера: без volume ключи пропадут — это ожидаемо для Dev без persistence.

### Сильные / слабые стороны Dev

| Сильное | Слабое |
|---|---|
| Минуты, официальный образ | Нет failover, нет лага replica, нет eviction под давлением |
| Совпадает с development-практикой Redis | Успешный `SET` **не** доказывает прод |
| Дешёво гоняет паттерн ключей интеграций | Открытый 6379 на Wi-Fi = дыра |

Препрод: Sentinel 3 + master+2 replica **в одном ЦОДе**, ACL, `maxmemory`, persistence как в проде — даже без боевого трафика.

## Prod: 2 или 3 ЦОДа, без stretch, нагрузка возможна

**Цель:** пережить отказ **машины/пода внутри ЦОДа**; пережить отказ **целого ЦОДа** ценой холодного кэша / RPO>0 и **ручного** promote / прогрева с озера. Цифр ops/s нет — ниже минимум HA внутри площадки, не смета железа.

### Почему не stretch

Репликация Redis **асинхронная** (master не ждёт replica, отвечая клиенту). Sentinel/Cluster считают ноду мёртвой по таймауту ping/gossip. При неприемлемом RTT между ЦОДами stretch даёт ложный failover и разъезд датасетов, а не защиту. Спека Cluster прямо описывает окна потери acknowledged writes. Порога RTT у проекта **нет** — поэтому stretch в этой инструкции не предлагается.

Redis Cluster, растянутый по ЦОДам (1 master на площадку), **не используем**: majority master при падении двух площадок из трёх нет; при плохом RTT — ложные PFAIL.

### Топология

**Внутри активного ЦОДа (ЦОД-1)** — один логический набор (рекомендуемый старт — **Sentinel**, не Cluster):

- **1 master + минимум 2 replica** на **разных нодах** (и разных залах/стойках, если они реально разные домены отказа **этого** ЦОДа);
- **3 процесса Sentinel**, кворум **2**, тоже на разных нодах **этого** ЦОДа. Два Sentinel официально *DON'T DO THIS*;
- клиенты спрашивают Sentinel (порт **26379**), затем пишут на текущий master (**6379**);
- persistence **включена на master и replica** (RDB + AOF `everysec` как компромисс из доки). Авторестарт **пустого** master без диска официально уничтожает replica синхронизацией с пустым;
- PVC локальные/зональные, `WaitForFirstConsumer`, **не NFS** как единственный диск под AOF rewrite;
- образ **7.4.11**.

Cluster внутри ЦОД-1 — только если **доказали**, что один master упирается в CPU/`maxmemory` и ключи хорошо шардируются. Это другой клиентский протокол (MOVED, только DB 0). Не включать «чтобы было как Kafka».

**Между ЦОДами** (вариант B «мозг в одном ЦОДе» / вариант C из `Redis 7.md`):

| Площадок | Что где | Отказ ЦОД-1 |
|---|---|---|
| **2 ЦОДа** | ЦОД-1: Sentinel + master/replica. ЦОД-2: **независимый** Redis (свой кэш, прогрев с озера) **или** одна `replicaof` на master ЦОД-1 **вне** Sentinel (только DR) | Запись/кэш ЦОД-1 стоят. Независимый кэш ЦОД-2 жив, но **холодный** по ключам, которых там не было. `replicaof` сама master **не** выбирает: promote **ручной**. Реплика Redis **async** — хвост записей можно потерять; при кривом promote возможен split-brain |
| **3 ЦОДа** | ЦОД-1: активный. ЦОД-2: независимый Redis или async-копия. ЦОД-3: второй независимый **или** только бэкапы RDB в object storage | То же; третий ЦОД не даёт второго writer на тот же датасет |

Клиенты ЦОД-2/3 в штате: либо ходят на Sentinel ЦОД-1 по городу (**TLS обязателен**), либо на **локальный** независимый Redis (miss → озеро/API). «Пишем во все три ЦОДа один ключ» Community Redis **не умеет** (Active-Active — Enterprise/CRDT).

`replicaof` между ЦОДами — это **не** HA и **не** член кворума. Понимать: master не ждёт эту копию; `WAIT` уменьшает окно, не делает CP. Не добавлять эту replica в Sentinel ЦОД-1 — иначе failover «переедет» через город, то есть stretch.

Несколько **разных** наборов (кэш UI ≠ локи ≠ идемпотентность с `noeviction`) — отдельные HA, не один инстанс «на всех».

### Предпосылки прода

- Kubernetes в каждом ЦОДе (не один stretch-кластер).
- CSI с local/зональным диском.
- NetworkPolicy: 6379 только приложениям и replica; 26379 — Sentinel и Sentinel-клиентам. Не LoadBalancer в интернет.
- Хост: Transparent Huge Pages **выкл.**, `vm.overcommit_memory=1` (latency-гайды Redis, не «на глаз»).
- Секреты ACL — в Secret/Vault, не в Git.
- NAT/Docker port-map для Sentinel официально ломает autodiscovery — в K8s Pod IP / announce, не NodePort «как у веба».

### Установка (Kubernetes, каждый ЦОД где будет Redis)

1. Ноды + local PV + labels зоны **внутри** ЦОДа.
2. StatefulSet данных (1 master + 2 replica) с образом `redis:7.4.11`, PVC на RDB/AOF. Либо CR community-оператора — **пин версии CRD**, прогон 7.4.11 на стенде, образ всё равно официальный `redis:7.4.11`, не `quay.io/opstree/redis` «какой скачается».
3. Три Sentinel (отдельный StatefulSet). `sentinel.conf` должен быть **writable**.
4. ACL и `maxmemory` **до** боевых клиентов. Default user без `FLUSHALL`/`CONFIG`/`DEBUG`/`MODULE`/`EVAL`.
5. TLS на клиентах и на репликации, если клиенты/копия ходят между площадками.

Смысл `sentinel.conf` (не полный файл — сверять с докой Sentinel 7.4):

```text
port 26379
sentinel monitor cache-sot <dns-master-этого-ЦОДа> 6379 2
# down-after-milliseconds — после замера внутри ЦОДа.
# 60000 в учебнике Sentinel — пример, не ваш SLA.
```

Кворум `2` при трёх Sentinel. Клиенты знают **все три** адреса Sentinel, не один.

Replica в ЦОД-2 (если берёте async DR, не независимый кэш):

```bash
redis-cli replicaof <master-цод-1> 6379
```

`replica-read-only yes` (дефолт). Эту ноду **не** включать в `sentinel monitor` ЦОД-1. Promote — runbook, с fencing старого master. Две ветки после кривого promote — потеря/разъезд ключей, не «потом смержим».

### Конфигурирование активного набора (ЦОД-1)

| Параметр | Прод | Зачем |
|---|---|---|
| `maxmemory` | Задан, **ниже** лимита cgroup, запас на replica buffer и `fork` BGSAVE | Дефолт **не задан** — OOM |
| `maxmemory-policy` | Кэш: `allkeys-lru` / `allkeys-lfu`. Локи/idem, которые нельзя выкинуть: `noeviction` + TTL + **отдельный** инстанс | Смешать на одном процессе — слабое место |
| `appendonly` | `yes` | Дефолт `no` |
| `appendfsync` | `everysec` | Официально: можно потерять ~1 с при аварии |
| RDB save | Оставить как бэкап/быстрый старт | RDB удобнее увозить в другой ЦОД, чем сырой AOF |
| `min-replicas-to-write` | `1`, если лучше отказать в записи, чем писать в одиночку | Дефолт — не требовать; снижает доступность при падении replica |
| ACL | Отдельный пользователь на сервис; Lua боевым ролям запретить, пока нет нужды | 7.4.11 закрывает RCE в Lua; `rename-command` deprecated |

`dataDurability` как у PostgreSQL здесь нет: `WAIT 1` в приложении на критичных idem-ключах — осознанная задержка, не сильная согласованность.

### Масштабирование (когда появятся цифры)

1. Замерить рабочий набор, hit/miss, ops/s, p99, CPU `INFO commandstats`, eviction, replication lag.
2. Упёрлись RAM — сначала TTL/не класть эталон, потом `maxmemory`, потом **отдельный** набор по домену ключей. Replica **не** увеличивает объём записи.
3. Упёрлись CPU одного потока и ключи разные — планировать Cluster **внутри ЦОД-1** (другие клиенты) или второй инстанс.
4. Горячий ключ Cluster не спасёт.
5. `io-threads` — по факту сетевого saturating, не «на всякий случай» (в `redis.conf` пример `4`, выключено комментарием).

### Проверка прода (пока это не пройдено — это не прод)

1. `INFO server` = 7.4.11 на всех нодах данных ЦОД-1.
2. Запись через Sentinel-клиент; попытка без ACL — отказ.
3. Убить под master: Sentinel выбрал replica **в том же ЦОДе**, приложение переподключилось.
4. Restore RDB на чистый инстанс **на стенде**.
5. Если есть `replicaof` в ЦОД-2: учение promote **по runbook** (с замером RTO) — хотя бы один раз. Если независимый кэш — учение «ЦОД-1 мёртв, приложение переживает miss».
6. `FLUSHALL` из учётки приложения не проходит.

### Сильные / слабые стороны прод-схемы (мозг в одном ЦОДе + async/независимый DR)

| Сильное | Слабое |
|---|---|
| Gossip/Sentinel не зависят от межЦОДового RTT на кворуме | Падение ЦОД-1 = нет этого Redis, пока прогрев/promote |
| Согласовано с «не stretch» и с моделью кэша (не SoT) | RPO между ЦОДами > 0 (`replicaof` async; независимый кэш холоден) |
| Один writer, понятная модель | Ручной DR; ошибка promote = split-brain |
| | Клиентский 6379 в штате через город — TLS и сеть ваши |

**Не готов к проду**, если: один процесс выдают за HA; все Sentinel в одном поде; `maxmemory` не задан; persistence выкл. на master с авторестартом; `protected-mode no` + bind все без ACL; клиенты не умеют Sentinel; Cluster «на три ЦОДа в уме»; `replicaof` в Sentinel чужого ЦОДа; Redis назначен SoT; образ `latest`; 7.4 без решения по RSALv2/SSPL; Dev-манифест скопирован в бой.
