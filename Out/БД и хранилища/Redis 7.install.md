# Redis Community Edition 7.4.11 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Redis 7.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Redis — кэш, сессии, идемпотентность, короткие локи. Ставите **свою** Community-копию, не облако вендора. Эталон карточек остаётся в озере или СУБД.

Версия в этой инструкции: **7.4.11**. Образ: `redis:7.4.11` (не `7.4`, не `7`, не `latest`). Лицензия линии 7.4 — **RSALv2 или SSPLv1** (не BSD). Если юристы не приняли — этот файл не разрешение ставить 7.4; смотрят 7.2.16 (BSD) или Valkey.

Официального OSS-оператора у Redis Ltd **нет** (их оператор — Enterprise). Упаковка: StatefulSet + официальный образ **или** community-оператор (например OT-CONTAINER-KIT) **после** прогона именно 7.4.11.

Документация: https://redis.io/docs/latest/operate/oss_and_stack/ · конфиг 7.4: https://github.com/redis/redis/blob/7.4/redis.conf

Один Sentinel-набор или один Cluster, размазанный на несколько дата-центров, здесь **не собираем**. Репликация асинхронная; детект отказа живёт ping/gossip. Порога задержки нет. Живой набор — внутри одной площадки. Вторая площадка — независимый кэш или холодная копия вне голосования.

---

## О чём эта инструкция молча договорилась

1. Sentinel-кворум и (если когда-нибудь понадобится) Cluster bus живут **внутри одного дата-центра**. Между площадками — независимые кэши **или** холодная копия вне кворума (ручная авария). Автосмена «master переехал в чужой дата-центр» **не** цель.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`).
3. Юристы **принимают RSALv2/SSPL** для закрытого контура.
4. Учебный стенд — закрытая сеть. Пароль в примере не секрет.
5. Цифр вашей нагрузки нет — нет фразы «хватит N гигабайт».
6. Два дата-центра: активный Sentinel-набор в первом; второй — независимый Redis или async-копия вне кворума. Три дата-центра: то же. Третья площадка **не** добавляет второго писателя на те же ключи.
7. Клиенты умеют (или будут уметь) **Sentinel**. Захардкоженный IP master переживает только одиночку.
8. Кэш UI и локи/идемпотентность с политикой «не вытеснять» — **разные** наборы, не один процесс «на всех».

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** ключи, TTL, клиент микросервиса. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- На localhost свободен порт 6379.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name redis-dev \
  -p 127.0.0.1:6379:6379 \
  redis:7.4.11
```

Привязка к `127.0.0.1` обязательна. Образы часто слушают все интерфейсы и снимают protected mode «чтобы завелось».

Проверка — `PONG` и версия **7.4.11**:

```bash
docker exec -it redis-dev redis-cli PING
docker exec -it redis-dev redis-cli INFO server | grep redis_version
```

Затем заведите ACL-пользователя приложения (не оставлять «весь мир = default» привычкой в бой):

```bash
docker exec -it redis-dev redis-cli ACL SETUSER app \
  on '>dev-app' '~app:*' '+@read' '+@write' '+ping' '+info'
```

Клиент — `localhost:6379`, пользователь `app`, ключи с префиксом `app:`. Не `FLUSHALL` из приложения.

На Kubernetes для учёбы: один StatefulSet, 1 replica, образ `redis:7.4.11`, порт сервиса не публиковать наружу кластера. Том маленький или без persistence на сутки. **Не** этот YAML в бой. Community-оператор на учёбе не обязателен.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Один инстанс | да | Некому строить Sentinel |
| Sentinel / Cluster | нет | Иначе discovery/MOVED раньше ключей |
| TLS | нет, сеть закрыта | Иначе сертификаты раньше продукта |
| `maxmemory` | 256–512 МБ, если ставите | Не цель — ёмкость; в бою задают **всегда** |
| Persistence | AOF можно выкл. | Потеря ключей при рестарте терпима; на препроде включить **то же**, что в бою |
| `protected-mode no` + bind все без пароля | **запрещён**, если порт не loopback | Привычка уедет в бой |

Чего **не** упрощаем: версия **7.4.11**; префиксы ключей и TTL в коде; клиент ходит на имя хоста.

### Как понять, что стенд живой

1. `INFO server` показывает 7.4.11.
2. `SET`/`GET` с префиксом приложения.
3. Рестарт контейнера: без тома ключи пропадут — это ожидаемо для учёбы без persistence.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный образ | Нет смены master, нет лага replica, нет вытеснения под давлением |
| Совпадает с практикой разработки Redis | Успешный `SET` **не** доказывает боевую схему |
| | Открытый 6379 на Wi-Fi = дыра |

Перед боем полезен **препрод**: Sentinel 3 + master+2 replica **в одном** дата-центре, ACL, `maxmemory`, persistence как в бою.

## Бой: один живой дата-центр, второй — запас из снимка

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три Sentinel, master + две replica, persistence на всех). Отказ **всего дата-центра** = этого Redis нет, пока не прогреете кэш с озера или не повысите холодную копию вручную. Хвост асинхронной репликации можно потерять — это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Master **не ждёт** replica, отвечая клиенту. Sentinel и Cluster считают ноду мёртвой по таймауту ping/gossip. При плохой задержке между площадками получите ложную смену master и разъезд датасетов, а не защиту. Спека Cluster прямо описывает окна потери уже подтверждённых записей. Cluster «по одному master на площадку» при падении двух площадок из трёх теряет большинство master. Порога миллисекунд **нет** — поэтому здесь так не делаем.

Не добавлять холодную копию второй площадки в Sentinel первой: иначе смена master «переедет» через город, то есть как раз растягивание, которое здесь не собираем.

### Как расставить в активном дата-центре

Рекомендуемый старт — **Sentinel**, не Cluster:

- **1 master + минимум 2 replica** на **разных нодах** этой площадки (и разных залах/стойках, если они реально разные домены отказа **этого** дата-центра).
- **3 процесса Sentinel**, кворум **2**, тоже на разных нодах **этой** площадки. Два Sentinel официально *DON'T DO THIS*.
- Клиенты спрашивают Sentinel (**26379**), затем пишут на текущий master (**6379**). Знают **все три** адреса Sentinel, не один.
- Persistence **включена на master и replica** (RDB + AOF `everysec` как компромисс из документации). Авторестарт **пустого** master без диска официально уничтожает replica синхронизацией с пустым.
- Том локальный, **не NFS** как единственный диск под сжатие AOF.
- Образ **7.4.11**.
- `down-after-milliseconds` калибровать после замера внутри площадки. Пример из учебника Sentinel **60000** — учебный, не ваш SLA.
- `min-replicas-to-write 1` и разумный лаг — если лучше отказать в записи, чем писать в одиночку. Это **снижает доступность** при падении replica: сознательный выбор. Завод — не требовать replica.
- На критичных ключах идемпотентности внешнего вызова — рассмотреть `WAIT 1` с таймаутом; понимать, что это не сильная согласованность.

Cluster внутри этой площадки — только если **доказали**, что один master упирается в CPU/`maxmemory` и ключи хорошо режутся. Это другой клиентский протокол (MOVED, только база 0). Не включать «чтобы было как Kafka». Минимум Cluster: 3 master + 3 replica, постоянный файл слотов на томе, таймаут ноды **одинаковый** и **заметно больше** задержки сети (завод 15000 мс — только старт). Для «система должна работать» при дырке слотов часто ставят `cluster-require-full-coverage no`; цена: часть ключей недоступна. TLS на cluster bus между машинами — иначе gossip открытым текстом.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: Sentinel + master/replica. Вторая: **независимый** Redis (свой кэш, прогрев с озера) **или** одна холодная копия на master первой **вне** Sentinel | Запись/кэш первой стоят. Независимый кэш второй жив, но **холодный** по ключам, которых там не было. Холодная копия сама master **не** выбирает: повышение **ручное**. Реплика async — хвост можно потерять; при кривом повышении возможен разъезд ключей |
| **Три** | Третья как вторая или только бэкапы RDB в объектное хранилище | То же; третья площадка не даёт второго писателя на тот же датасет |

Клиенты второй площадки в штате: либо ходят на Sentinel первой по городу (**TLS обязателен**), либо на **локальный** независимый Redis (промах → озеро/API). «Пишем во все три площадки один ключ» Community Redis **не умеет** (Active-Active — Enterprise/CRDT).

### Что должно быть до боевой установки

- Kubernetes активной площадки; локальный/зональный диск.
- Сетевая политика: 6379 только приложениям и replica; 26379 — Sentinel и Sentinel-клиентам. Не балансировщик в интернет.
- Хост: Transparent Huge Pages **выкл.**, `vm.overcommit_memory=1`.
- Секреты ACL — в Vault, не в git.
- NAT/проброс портов для Sentinel официально ломает discovery — IP пода / announce, не NodePort «как у веба».

### Порядок установки в активном дата-центре

1. Ноды + локальный том + метки зоны **внутри** площадки.
2. StatefulSet данных (1 master + 2 replica) с образом `redis:7.4.11`, том на RDB/AOF. Либо объект community-оператора — **пин версии**, прогон 7.4.11 на стенде, образ всё равно официальный `redis:7.4.11`, не «какой скачается».
3. Три Sentinel (отдельный StatefulSet). Файл `sentinel.conf` должен быть **записываемый**.
4. ACL и `maxmemory` **до** боевых клиентов. Пользователь default без `FLUSHALL`/`CONFIG`/`DEBUG`/`MODULE`/`EVAL`.
5. TLS на клиентах и на репликации, если клиенты/копия ходят между площадками.

Смысл `sentinel.conf` (не полный файл — сверять с документацией Sentinel 7.4):

```text
port 26379
sentinel monitor cache-sot <dns-master-этой-площадки> 6379 2
# down-after-milliseconds — после замера внутри площадки.
# 60000 в учебнике Sentinel — пример, не ваш SLA.
```

Кворум `2` при трёх Sentinel. Холодная копия на второй площадке:

```bash
redis-cli replicaof <master-первой-площадки> 6379
```

`replica-read-only yes` (завод). Эту ноду **не** включать в `sentinel monitor` первой площадки. Повышение — заранее написанный сценарий, с отключением старого master. Две ветки после кривого повышения — потеря/разъезд ключей, не «потом смержим».

Политика сбоя подов: не снимать сразу большинство Sentinel или две replica. Смена master / drain без failover = простой записи. Лимит CPU слишком жёсткий + throttle = ложный детект «нода мертва».

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| `maxmemory` | Задан, **ниже** лимита контейнера, запас на буфер replica и `fork` снимка | Завод **не задан** — процесс убивают |
| `maxmemory-policy` | Кэш: LRU/LFU. Локи/идемпотентность, которые нельзя выкинуть: не вытеснять + TTL + **отдельный** инстанс | Смешать на одном процессе — слабое место |
| `appendonly` | `yes` | Завод `no` |
| `appendfsync` | `everysec` | Официально: можно потерять ~1 с при аварии. `always` — очень медленно. `no` — в руках ядра, до ~30 с по формулировке документации |
| RDB save | Оставить как бэкап/быстрый старт | RDB удобнее увозить на другую площадку, чем сырой AOF |
| `min-replicas-to-write` | `1`, если лучше отказать в записи, чем писать в одиночку | Завод — не требовать |
| ACL | Отдельный пользователь на сервис; Lua боевым ролям запретить, пока нет нужды | 7.4.11 закрывает выполнение кода в Lua; `rename-command` устарел |
| `replica-read-only` | `yes` (завод) | Случайная запись в replica |
| Горячие/большие ключи | Ловить `redis-cli --bigkeys` / `--memkeys` / `--keystats` (7.4) на стенде | Один огромный hash убивает задержку снимка и сеть репликации |

### Как расти, когда появятся цифры нагрузки

1. Замерить рабочий набор, попадания кэша, операции в секунду, задержку, CPU по командам, вытеснение, лаг репликации.
2. Упёрлись RAM — сначала TTL/не класть эталон, потом `maxmemory`, потом **отдельный** набор по домену ключей. Replica **не** увеличивает объём записи.
3. Упёрлись CPU одного потока и ключи разные — планировать Cluster **внутри этой площадки** (другие клиенты) или второй инстанс.
4. Горячий ключ Cluster не спасёт.
5. `io-threads` — по факту насыщения сети, не «на всякий случай».

### Проверки, без которых это ещё не бой

1. `INFO server` = 7.4.11 на всех нодах данных активной площадки.
2. Запись через Sentinel-клиент; попытка без ACL — отказ.
3. Убили под master: Sentinel выбрал replica **в том же дата-центре**, приложение переподключилось.
4. Восстановили RDB на чистый инстанс **на стенде**.
5. Если есть холодная копия на второй площадке: учение повышения **по сценарию** (время простоя замерить) — хотя бы один раз. Если независимый кэш — учение «первая площадка мертва, приложение переживает промах».
6. `FLUSHALL` из учётки приложения не проходит.

### Что хорошо и что плохо в схеме «набор в одном дата-центре + async/независимый запас»

| Хорошо | Плохо |
|---|---|
| Sentinel не зависит от задержки между городами на кворуме | Падение этой площадки = нет этого Redis, пока прогрев/повышение |
| Согласовано с моделью кэша (не эталон) | Между площадками можно потерять хвост; независимый кэш холоден |
| Один писатель, понятная модель | Ручная авария; ошибка повышения = разъезд ключей |
| | Клиентский 6379 в штате через город — TLS и сеть ваши |

**Не готово к бою**, если: один процесс выдают за отказоустойчивость; все Sentinel в одном поде; `maxmemory` не задан; persistence выкл. на master с авторестартом; protected mode снят и bind все без ACL; клиенты не умеют Sentinel; Cluster «на три дата-центра в уме»; холодная копия в Sentinel чужой площадки; Redis назначен эталоном; образ `latest`; 7.4 без решения по RSALv2/SSPL; учебный манифест уехал в бой.
