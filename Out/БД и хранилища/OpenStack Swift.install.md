# OpenStack Swift 2.37.3 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `OpenStack Swift.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Swift — объектный слой (вложения, снимки, архив интеграций), не эталон клиентских карточек и не Kafka. Ставите **свою** копию с включённым S3 API (`s3api` на тех же proxy).

Версия в этой инструкции: **Swift 2.37.3**, серия OpenStack **2026.1 (Gazpacho)**. Не 2.38.x (unreleased). Не **2.29.2** из инсталлятора GeoData — склеивать платформенный S3 с GeoData «потому что оба Swift» без письма вендора нельзя. Лицензия исходников — **Apache 2.0**.

Официального оператора «как у CloudNativePG» нет. Kolla-Ansible **убрал** роль Swift с 2025.1. OpenStack-Helm на 2026.1 заявляет Kubernetes **≥ 1.33 и ≤ 1.35** — в платформе **1.36.4**, это **не** доказанная комбинация.

Документация: https://docs.openstack.org/swift/2026.1/  
Deployment Guide: https://docs.openstack.org/swift/2026.1/deployment_guide.html  
S3 (`s3api`): https://docs.openstack.org/swift/2026.1/middleware.html

Одно кольцо, размазанное на несколько дата-центров, здесь **не собираем**. Это синхронный PUT и/или rsync по городской сети; порога задержки у проекта нет. Живой кластер — внутри одной площадки. Вторая площадка — независимый кластер (штатный мост — **container sync**) или бэкап объектов и `.builder`.

---

## О чём эта инструкция молча договорилась

1. Один кластер Swift (кольца account/container/object, replica=3, rsync между storage-нодами) живёт **внутри одного дата-центра**. Между площадками — **независимые** кластеры или один кластер + бэкап как авария. Это не «один region на три площадки» и не Global Cluster.
2. Бой-identity — **Keystone** (отдельный отказоустойчивый сервис). tempauth — только стенд.
3. Storage-ноды — машины с **локальным XFS** и стабильным IP в кольце, не `emptyDir` и не NFS как диск object-server. Proxy может быть ближе к Kubernetes.
4. Учебный стенд — закрытая сеть; учётки SAIO не секрет.
5. Цифр вашей нагрузки нет — нет цифры «N дисков и M ТБ». **Не** подставляем степень двойки партиций «с потолка»: в гайде её считают от прогноза максимума дисков (≥ 100 партиций на диск). Здесь только протестированные константы гайда: **replica=3**, пример `min_part_hours=24`.
6. Два дата-центра: кластер в первом; второй — независимый Swift + container sync **или** только бэкап. Три дата-центра: то же. Третья площадка **не** добавляет «ещё одну копию в то же кольцо».
7. S3 Lifecycle / bucket policy / tagging в матрице Swift **нет** — в архитектуру не закладываем.
8. `write_affinity` **не** включаем: документация — для нагрузки «записал и не читаешь сразу из другого региона» (бэкапы). У микросервисов типично GET сразу после PUT.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** PUT/GET объекта, AWS SDK/boto, ловить «lifecycle не поддерживается» на берегу. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Одна Linux-машина/VM (официальный SAIO: ориентир гайда **≥ 2 ГиБ RAM и ≥ 40 ГиБ** места — чтобы **вообще завелось**, не бой).
- На localhost свободен порт 8080.
- Сеть стенда не торчит в интернет.

### Установка (SAIO — официальный путь для учёбы)

Полный плейбук не копируем: https://docs.openstack.org/swift/2026.1/development_saio.html — ветка/серия **2026.1**, пакеты и исходники **2.37.3**. Ниже — то, без чего стенд не считается тем же продуктом.

1. Зависимости (пример Ubuntu из SAIO): `memcached`, `rsync`, `sqlite3`, `xfsprogs`, Python 3, `liberasurecode-dev` и остальное по гайду **этой** серии.
2. XFS. Loopback как в SAIO:

```bash
sudo mkdir -p /srv
sudo truncate -s 1GB /srv/swift-disk
sudo mkfs.xfs /srv/swift-disk
sudo mkdir -p /mnt/sdb1
# fstab: /srv/swift-disk /mnt/sdb1 xfs loop,noatime 0 0
sudo mount -a
```

3. Каталоги `/srv/{1..4}` как в SAIO (лаборатория «несколько процессов на localhost», не боевые порты 6200).
4. rsyncd, memcached, кольца SAIO из гайда, затем proxy **только на loopback**:

```text
bind_ip = 127.0.0.1
bind_port = 8080
```

tempauth в `proxy-server.conf`. `s3api` в конвейере **перед** tempauth, как в sample; для более полной совместимости SAIO включает `s3_acl` / `check_bucket_owner`.

5. Версия процессов — **2.37.3**, не «какой Swift есть в дистрибутиве GeoData».

Проверка Swift API — `curl` на `/auth/v1.0` и `/v1/...` как в SAIO. Проверка S3: endpoint `http://127.0.0.1:8080`, access key вида `account:user`, secret = пароль tempauth.

Альтернатива «чуть ближе к бою»: 3 VM **в одном дата-центре**, replica=3, несколько zone **внутри** площадки — уже видны replicator и кольца. Это всё ещё не модель двух городов.

На Kubernetes для учёбы: один под с SAIO в изолированном namespace, порт не публиковать. **Не** этот манифест в бой.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Одна машина (SAIO) | да | Нет требования пережить обновление |
| Auth | tempauth | Иначе команда утонет в Keystone раньше PUT |
| TLS | HTTP на 127.0.0.1 | Стенд изолирован |
| Encryption at-rest | выкл. | Сначала протокол |
| Zone/region | одна | Не цель — отказ площадки |
| S3 Lifecycle | отсутствует как в бою | Пусть клиент упадёт на тесте |

Чего **не** упрощаем: версия **2.37.3**; лимит **5 ГБ** на один PUT и multipart/SLO; явный ключ объекта (идемпотентный PUT).

### Как понять, что стенд живой

1. PUT/GET по Swift API и по S3 (разные URL и подписи — осознанно).
2. Вызов Lifecycle/bucket policy — ожидаемый отказ матрицы, не «потом в бою заработает».

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный SAIO | Нет отказа площадки, нет Keystone, нет rsync между площадками |
| Дешево показывает враньё AWS SDK vs матрица `s3_compat` | Успешный boto на localhost **не** доказывает бой |
| | tempauth приучает хранить секрет в конфиге |

Перед боем полезен **препрод**: несколько дисков, **разные zone внутри одного дата-центра**, Keystone, TLS, s3api, recon — даже без боевого трафика.

## Бой: один живой дата-центр, второй — запас из снимка

**Зачем:** пережить отказ **диска, ноды или proxy внутри площадки** (три копии в кольце, несколько proxy за балансировщиком). Отказ **всего дата-центра** = этого S3 нет, пока не переключите клиентов на независимый кластер или не восстановите бэкап. Container sync eventual — хвост можно потерять; это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Заводская модель Swift — **один region с низкой задержкой**. Три площадки как три zone одного кольца или три region Global Cluster с `write_affinity` заставляют PUT и/или rsync ходить через город. При неприемлемой задержке это таймауты proxy, рост handoff и «копии ещё не там». Global Cluster **есть** форма растягивания колец — здесь не используем. Цифры миллисекунд документация **не даёт**.

Не копировать `.ring.gz` первой площадки на ноды второй: это и есть попытка растянуть одно кольцо.

### Как расставить в активном дата-центре

Один кластер:

- replica **3** — единственное **протестированное** значение Deployment Guide; меньше 3 на бою = вы сами испытательный стенд;
- zone = залы/стойки/питание **этого** дата-центра (изоляция копий внутри площадки). Не region=чужой дата-центр;
- ≥2 proxy за локальным балансировщиком (HAProxy этой площадки, см. `HAProxy.install.md` если берёте его). Один proxy = точка отказа API при живых дисках;
- object/container/account на локальном XFS, `/srv/node/…` от **root** (`root:root 755`) — иначе при размонтировании rsync может писать в корневой том;
- rsync **внутренняя** сеть; клиентам только 443 → proxy (8080). Порты **6200/6201/6202** и **873** не публичны;
- одинаковые `*.ring.gz` на всех нодах; **`.builder` в бэкапе вне** единственной машины;
- memcached: полный список в `memcache_servers` на каждом proxy;
- Keystone + конвейер s3api **до** боевых бакетов;
- RAID 5/6 под объект **нет**. Надёжность — копии в кольце + auditor, не контроллер RAID;
- квоты аккаунта/контейнера — иначе озеро съест диски;
- один PUT по умолчанию до **5 ГБ**; больше — SLO/multipart;
- клиентам — VIP/DNS на proxy, **path-style** S3 на первый контракт (меньше сюрпризов с TLS/wildcard).

Три кольца минимум: account, container, object (плюс ещё object-кольцо на каждую дополнительную политику хранения). Отправная точка гайда: `create <part_power> 3 24` (replica=3, min_part_hours=24). Степень двойки партиций — от прогноза **максимума** дисков, не от «сейчас купили три HDD». Все изменения устройств — пакетом, потом **один** rebalance. Веса — по реальной ёмкости (ориентир гайда **100.0 × ТБ**). «Все weight=1» на дисках разного размера = одни тома лопнут раньше.

Холодный архив дешевле по месту → **вторая** политика хранения с erasure coding на **новый** контейнер, не ломая default 3×. Политика навешивается при создании контейнера и потом не меняется.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: единственное кольцо (отказ диска/ноды внутри). Вторая: **независимый** Swift (свои кольца, свой проект Keystone) + **container sync** как авария **или** только бэкап объектов и `.builder` | API первой мёртв. Независимый кластер жив со своим (eventual) набором объектов. Без второго кластера — restore с бэкапа, время простоя замерить |
| **Три** | Вторая: независимый + sync. Третья: третий независимый **или** только бэкапы | То же; три кольца = три операционки, не «один бакет на страну» |

Container sync — отдельная глава проекта: https://docs.openstack.org/swift/2026.1/overview_container_sync.html  
Это **не** догон партиций одного кольца. Потеря хвоста > 0, конфликты last-write-wins. Не изобретаем расписание sync — сверять главу проекта.

Клиенты второй площадки в штате: либо S3/Swift первой по городу (TLS), либо **локальный** независимый endpoint (другой бакет/аккаунт, пока sync не догнал).

### Что должно быть до боевой установки

- Выделенные storage-ноды, XFS, xattr, отдельные сети: клиентская / storage (620x) / replication (rsync).
- Keystone с отказоустойчивостью. Без него нет боя S3 (`s3token`). В 2.37.0 отдельно чинили совместимость s3token с Keystone >25.0.0.
- Балансировщик TCP/TLS перед proxy **этой** площадки. VIP proxy в чужом дата-центре = скрытая точка отказа **этого** кластера.
- Kubernetes 1.36.4: proxy как Deployment за Service — нормально (stateless, кольцо только читают). Object-server в кольце по IP пода **без** hostNetwork/стабильного IP — нет. Переезд пода на другую ноду **без** изменения кольца = потеря устройства. Helm OpenStack на 1.36 **не** считать сертифицированным путём.

### Порядок установки в активном дата-центре

Порядок официальный, не «скопируй ring-builder из блога 2016»:

1. Пакеты/образы **Swift 2.37.3** (дистрибутив 2026.1 или своя сборка). Не смешивать серии внутри одного кольца.
2. Диски XFS, точки `/srv/node/<device>`, rsyncd с модулями object/container/account.
3. Собрать **три** кольца. Отправная точка гайда:

```bash
swift-ring-builder account.builder create <part_power> 3 24
swift-ring-builder container.builder create <part_power> 3 24
swift-ring-builder object.builder create <part_power> 3 24
```

`3` — replica, `24` — пример `min_part_hours`. `<part_power>` — **не** выдуман в этой инструкции: по гайду от максимума дисков × ≥100 партиций на диск. Устройства добавлять с zone **внутри этой площадки**, вес ориентир гайда **100.0 × ТБ**. Затем один `rebalance`, раздать `.ring.gz` **всем** proxy и storage. Builder — в защищённый бэкап.

4. Запустить object/container/account, затем **несколько** proxy, memcached.
5. Keystone: `keystoneauth` + для S3 `s3token`. Конвейер боя (смысл, порядок сверять с `proxy-server.conf-sample` **2.37.3**, не с блогом 2016 года): catch_errors / gatekeeper / healthcheck / cache / **authtoken** (`delay_auth_decision = True`) / **s3api** / **s3token** / **keystoneauth** / квоты / **bulk** / **slo** / (keymaster encryption) / proxy-server.
6. TLS на балансировщике. Path-style S3 на первый контракт. Один endpoint S3 на кластер. Не раздавать разработчикам три разных URL «на всякий случай».
7. recon: заполнение дисков, отложенные обновления, время репликации, 5xx proxy.

Второй кластер на второй площадке — **с нуля те же шаги**, другие кольца, другие IP. Затем container sync между контейнерами, которые решили зеркалировать.

At-rest encryption — по решению ИБ; секрет ≥44 символа base64, одинаковый на всех proxy; лучше Barbican. Имена объектов **не** шифруются. GeoData 2.29.2 — отдельный контур, не этот кластер.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| replica | 3 | Единственное протестированное |
| RAID 5/6 под объект | нет | Вендор не рекомендует; надёжность — replica + auditor |
| tempauth | нет | Пароли в конфиге — не identity |
| `s3_acl` | решить сознательно | Завод проекта исторически `False`; часть CVE-2026-71191 завязана на него |
| Квоты | квоты аккаунта / контейнера | Иначе озеро съест диски |
| At-rest encryption | по решению ИБ | Имена объектов **не** шифруются |
| Вход | Только 443 на балансировщике → proxy | 6200–6202, 873 — internal |
| S3-ключи | Отдельные на сервис; минимум прав; ротация | Нет общего ключа «на всех микросервисов» |
| Кольца | Доступ на rebalance — узкий круг; аудит изменений | Ошибка кольца бьёт сильнее падения ноды |
| Патчи | 2.37.3 не «навсегда» | S3-CVE в этой линейке уже были. Обновлять proxy **раньше**, если endpoint торчит |

Не забивать диски вплотную — некуда двигать партиции при перекладке. Мелкие файлы / тяжёлый listing → шардинг контейнеров (отдельная дисциплина), не «как диск Postgres».

### Как расти, когда появятся цифры нагрузки

1. Больше гигабайт → диски в object-кольцо, вес по ТБ, перекладка. Не «увеличить том одного пода».
2. Больше запросов → больше **proxy** (CPU/сеть). TLS часто снимают на балансировщике.
3. Мелкие файлы / тяжёлый listing → шардинг контейнеров.
4. Холодный архив дешевле → **вторая** политика хранения с erasure coding на **новый** контейнер.
5. Не забивать диски вплотную.

### Проверки, без которых это ещё не бой

1. Версия proxy/storage = **2.37.3**.
2. PUT/GET Swift и S3 с ключами сервиса; без ключа — отказ. 6200 с клиентской сети не открыт.
3. Убили один диск и одну storage-ноду **внутри активной площадки**: GET жив, replicator сходится.
4. Падение одного proxy: балансировщик отдаёт на живой.
5. Restore `.builder` + прогон GET на стенде. Если container sync — замерить лаг (это ваша потеря хвоста).
6. Учение «активный дата-центр мёртв»: клиенты второй площадки идут в локальный кластер или ждут restore — то, что обещали, не «как получится».

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + независимый/бэкап запас»

| Хорошо | Плохо |
|---|---|
| Кольцо и rsync не ходят межплощадочно на пути PUT | Падение этой площадки = нет **этого** S3, пока sync/restore |
| Согласовано с запретом растягивать кольцо | Container sync eventual; три кластера = тройные ключи |
| replica=3 внутри площадки — штатный отказ диска/ноды | Ошибка перекладки бьёт весь кластер этой площадки |
| | OpenStack-Helm ≠ ваш Kubernetes 1.36.4 «из коробки» |
| Один кластер — два протокола (Swift и S3) | «S3-совместимый» ≠ AWS; часть SDK отвалится на Lifecycle/policy |
| | Keystone — точка отказа доступа; имена объектов видны даже при at-rest |

**Не готово к бою**, если: SAIO/tempauth; один proxy; replica≠3; NFS/`emptyDir` как диск object-server; кольца разъехались; нет бэкапа `.builder`; 6200 открыт клиентам; одно кольцо на три дата-центра; приложение требует S3 Lifecycle/bucket policy; кластер общий с GeoData 2.29.2; Swift назначен эталоном карточек; учебный конфиг скопирован в бой.
