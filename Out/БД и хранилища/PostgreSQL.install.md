# PostgreSQL 18.6 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `PostgreSQL.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

PostgreSQL — реляционная база для транзакций и карточек. Ставите **свою** community-копию, не Postgres Pro и не EDB.

Версия в этой инструкции: **18.6**. На Kubernetes — оператор **CloudNativePG 1.30.0**, образ инстансов `ghcr.io/cloudnative-pg/postgresql` с тегом линии **18.6** (не завод оператора 18.4, не `latest`).  
Документация: https://www.postgresql.org/docs/18/ · оператор: https://cloudnative-pg.io/documentation/1.30/

Один кластер, размазанный на несколько дата-центров, здесь **не собираем**. Синхронный `COMMIT` не быстрее, чем сброс журнала на запасную машину; порога задержки в документации нет. Автосмена главной между разными Kubernetes у оператора **не в scope**. Живой кластер — внутри одной площадки. Вторая площадка — асинхронная копия-кластер или восстановление из архива.

---

## О чём эта инструкция молча договорилась

1. Один объект `Cluster` живёт **внутри одного дата-центра** (одного Kubernetes). Между площадками — только асинхронная копия-кластер и/или точка восстановления из объектного хранилища.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`).
3. Учебный стенд — закрытая сеть. Пароль в примере не секрет.
4. Цифр вашей нагрузки нет — нет фразы «хватит N ядер». Есть минимум, чтобы процесс жил, и рычаги роста.
5. Бакет для архива WAL в бою **есть или будет**. Копии узлов бэкап не заменяют: команду «удали таблицу» они послушно повторят.
6. Два дата-центра: активный кластер в первом; второй — копия-кластер или только архив. Три дата-центра: то же. Третья площадка **не** добавляет второго писателя.
7. Эталон карточек, метаданные Grafana и Camunda Identity — **разные** кластеры, не одна база «на всех».

---

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** схемы, миграции, подключение микросервиса. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- На localhost свободен порт 5432.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name pg-dev \
  -e POSTGRES_PASSWORD=dev \
  -e POSTGRES_DB=app \
  -p 127.0.0.1:5432:5432 \
  postgres:18.6
```

Привязка к `127.0.0.1` обязательна: `-p 5432:5432` без адреса часто слушает все интерфейсы.

Проверка — в строке должна быть **18.6**:

```bash
docker exec -it pg-dev psql -U postgres -c 'SELECT version();'
```

Затем заведите **не**-суперпользователя:

```bash
docker exec -it pg-dev psql -U postgres -d app -c "
CREATE ROLE app LOGIN PASSWORD 'dev-app';
GRANT CONNECT ON DATABASE app TO app;
GRANT CREATE, USAGE ON SCHEMA public TO app;
"
```

Клиент — `localhost:5432`, база `app`, роль `app`. Не `postgres`. Метод `POSTGRES_HOST_AUTH_METHOD=trust` **запрещён** даже на учебном стенде: привычка уедет в бой.

На Kubernetes для учёбы:

```bash
kubectl apply --server-side -f \
  https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.30/releases/cnpg-1.30.0.yaml
kubectl -n cnpg-system rollout status deployment/cnpg-controller-manager
```

Минимальный кластер (не боевой манифест):

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: pg-dev
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:18.6
  storage:
    size: 10Gi
  bootstrap:
    initdb:
      database: app
      owner: app
```

Сервис записи: `pg-dev-rw:5432`. Образ пинить на 18.6 явно.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Число инстансов | 1 | Некому строить sync |
| TLS | нет, сеть закрыта | Иначе сертификаты раньше схемы |
| `shared_buffers` | завод | Нет нагрузки |
| PgBouncer | не нужен | Десяток соединений |
| Архив WAL | можно без на сутки | На препроде включить **тот же** механизм, что в бою |

Чего **не** упрощаем: версия **18.6**; отдельная база и роль; клиент ходит на имя хоста, не на IP контейнера.

### Как понять, что стенд живой

1. `SELECT version()` возвращает 18.6.
2. Приложение ходит ролью `app`, суперпользователь из приложения — отказ.
3. Контейнер перезапустили с томом — данные на диске на месте.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный образ | Нет смены главной, нет лага копии, нет точки восстановления |
| Совпадает с практикой разработки PostgreSQL | Успешный `INSERT` **не** доказывает боевую схему |
| | Открытый 5432 на Wi-Fi = дыра |

Перед боем полезен **препрод**: 3 инстанса **в одном** дата-центре, sync как в бою, TLS, архив WAL, пул соединений.

## Бой: один живой дата-центр, второй — запас из архива

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три инстанса, `COMMIT` ждёт одну живую копию). Отказ **всего дата-центра** = этой базы нет, пока не повысите копию-кластер на другой площадке или не восстановите архив. При чисто архивном догоне часть свежих данных можно потерять — это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Синхронный `COMMIT` не быстрее, чем сброс WAL на копии. Если задержка между площадками велика, приложения получают таймауты, оператор может ложно сменить главную. Оператор: автосмена **между кластерами Kubernetes не в scope**. Порога миллисекунд у PostgreSQL **нет** — поэтому живой кластер не размазываем.

Ждать **обе** копии на трёх инстансах (`number: 2`) значит: любой один мёртвый узел чаще останавливает запись. Для «пережить одну машину и продолжать писать» обычно ждать **одну** копию, не две.

### Как расставить в активном дата-центре

Один объект `Cluster`:

- `instances: 3` (1 primary + 2 hot standby) на **разных нодах** этой площадки.
- Sync: ждать любую одну копию; без живой sync-копии **запись стоит** (`dataDurability: required`). Если руководство требует «пишем любой ценой» — это `preferred` (окно потери), другое обещание.
- Клиенты пишут в сервис `…-rw`, читают с лагом в `…-ro`.
- Перед `-rw` — пул PgBouncer (объект `Pooler`), начать с режима **session**: режим транзакции ломает prepared statements, `LISTEN/NOTIFY`, временные таблицы в части драйверов.
- Том локальный/зональный, **не NFS** как единственный диск primary.
- Образ **18.6**, не 18.4.
- Слоты репликации включить штатами оператора, чтобы после смены главной WAL для оставшихся не подчистился.
- Политика сбоя подов: не эвакуировать primary и единственную sync-копию одним drain.
- `fsync` **on**. Не выключать «для скорости».

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: кластер. Вторая: **копия-кластер** оператора (поток WAL и/или архив из объектного хранилища) **или** только точка восстановления | Запись стоит, пока не повысите копию / не восстановите. При чисто архивном догоне потеря хвоста **> 0** |
| **Три** | Третья как вторая или только бэкапы | То же. Три независимых кластера ≠ один запрос «по всей стране» без кода над ними |

Клиенты второй площадки в штате ходят в `-rw` первой по городу (**TLS обязателен**) **или** работают только на чтение с локальной копии (лаг, без записи). «Пишем во все три площадки» community PostgreSQL **не умеет**. После кривого повышения возможны две ветки WAL: это потеря данных, не «потом смержим».

Несколько **разных** кластеров на платформе:

| Кластер | Зачем отдельно |
|---|---|
| Эталон (карточки, справочники) | Другой объём, другие роли, другая цена ошибки |
| Camunda Identity / Web Modeler | Падение моделлера ≠ остановка эталона |
| Grafana / Superset metadata | То же |
| GIS/PostGIS (если контуры огромные) | Индексы и vacuum не должны делить диск с OLTP карточки |

Это не «микросервис = свой postgres в углу без отказоустойчивости». Это **несколько** отказоустойчивых кластеров с понятным владельцем.

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемым fsync, один том на один под.
- Объектное хранилище для плагина Barman Cloud (встроенный путь снимут в 1.31.0).
- Сетевая политика: 5432 только приложениям и инстансам PostgreSQL. Порты instance manager оператора — только оператору.
- Секреты ролей — в Vault, не в git.

### Порядок установки в активном дата-центре

```bash
kubectl apply --server-side -f \
  https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.30/releases/cnpg-1.30.0.yaml
```

Оператор — Deployment с несколькими репликами, **не** в одном поде с primary.

Смысл манифеста (не полный объект — сверять с документацией 1.30):

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: pg-sot
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:18.6
  postgresql:
    synchronous:
      method: any
      number: 1
      dataDurability: required
    parameters:
      ssl: "on"
  storage:
    size: 100Gi   # заглушка: реальный размер = данные + WAL + запас; цифр нагрузки нет
```

Обязательно рядом:

1. **Pooler** перед `-rw` (и отдельно перед `-ro`, если нужно). Потолок сессий на сервере держать скромным.
2. Расписание снимков + архив WAL. Проверяют **восстановление**, не наличие файла в бакете.
3. Роли на сервис: без суперпользователя, без права создавать базы. Список доступа: только TLS + SCRAM, не `trust`, не весь интернет.
4. Разнести инстансы по разным нодам. Клиенты: короткий timeout, reconnect, **не** прилипание к IP пода. В бою клиент проверяет сертификат целиком (`sslmode=verify-full`).
5. Копия-кластер на второй площадке — отдельный объект с загрузкой от источника. Повышение — **ручное**.

`shared_buffers` и потолок сессий — **после замера**, не «25% с потолка». В 1.30 оператор кодирует пароли ролей в SCRAM **до** SQL (CVE-2026-55765); логи статистики запросов — не сейф паролей.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| `shared_buffers` | Заметно выше 128 МБ, ниже RAM пода, оставить долю ОС | Завод для боя мал |
| Потолок сессий | Малый на сервере + **PgBouncer** | Тысячи процессов съедают RAM |
| Режим PgBouncer | Начать с **session**; transaction — только после теста драйверов | Иначе «в бою внезапно» ломается JDBC |
| `fsync` | **on** | Выключить = принять потерю COMMIT при крахе ОС |
| Autovacuum | Включён | На больших таблицах это ось жизни |
| Партиции | По времени на растущих таблицах | Иначе DELETE/VACUUM вечные |
| Индексы | Только доказанные запросами | Каждый индекс множит WAL |
| Список доступа | Только TLS + SCRAM с узких сетей | Не весь интернет |
| Superuser | Только администратор. Приложение — нет | В 18.6 пачка CVE класса «выполнение кода» вокруг функций и contrib |
| At-rest | Шифрование тома | Community не заменяет это настройкой `ssl` |

Обновление minor: сначала копии, затем переключение. Major 18→19 — только после стабильного 19; **Beta 3 не бой**.

### Как расти, когда появятся цифры нагрузки

1. Замерить транзакции в секунду, WAL в секунду, задержку `COMMIT`, число сессий, раздувание таблиц.
2. Упёрлись CPU/WAL primary — вертикаль или вынести домен в другой кластер. **Ещё копия не ускоряет запись.**
3. Упёрлись соединения — пул, не потолок сессий в тысячи.
4. Упёрлись диск — партиции + архив старого в озеро, не бесконечное хранение в OLTP.
5. Тяжёлые отчёты — ClickHouse/склад, не primary эталона.

### Проверки, без которых это ещё не бой

1. `SELECT version()` = 18.6 на **всех** инстансах активной площадки. Нет смеси 18.4 и 18.6.
2. Запись в `-rw`, чтение `-ro`, запись в `-ro` — отказ.
3. Убили под primary: `-rw` переехал, приложение переподключилось, число строк совпало с ожиданием sync.
4. Восстановили архив на чистый кластер **на стенде**.
5. Учение «активный дата-центр выключен»: повышение копии-кластера по заранее написанному сценарию (время простоя замерить).
6. Суперпользователь из приложения не проходит.

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + архив»

| Хорошо | Плохо |
|---|---|
| Sync не зависит от задержки между городами | Падение этой площадки = нет записи, пока повышение/восстановление |
| Согласовано с оператором (автосмена внутри одного Kubernetes) | Между площадками можно потерять хвост, если догон только архивом |
| Один писатель, понятная модель для разработчиков | Ручная авария; ошибка повышения = две ветки журнала |
| | Клиентский 5432 в штате идёт через город — TLS и сеть ваши |

**Не готово к бою**, если: один инстанс; образ 18.4/`latest`; нет архива WAL; NFS как диск primary; `trust`/`sslmode=disable` между площадками; клиент на IP пода; учебный манифест уехал в бой; эталон и Grafana в одной базе; ждут, что PostgreSQL заменит Kafka или ClickHouse.
