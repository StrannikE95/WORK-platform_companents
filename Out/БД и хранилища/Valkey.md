# Valkey 9.1.1 — развёртывание и настройка

Версия ПО: **Valkey 9.1.1** (релизная дата 21 июля 2026; на дату подготовки документа это последний стабильный патч линии 9.1).  
Upgrade urgency релиза: **SECURITY**. В 9.1.1 закрыты CVE-2026-56684 (RCE через TLS / `CLIENT KILL` у уже аутентифицированного клиента) и CVE-2026-63639 (RCE через повреждённый stream в RDB). Ставить 9.1.0 «потому что почти то же» нельзя.

Документация: https://valkey.io/  
Образы: `valkey/valkey:9.1.1`, `valkey/valkey:9.1.1-alpine`, `valkey/valkey:9.1.1-trixie`.  
Лицензия: BSD-3 (форк Redis OSS под Linux Foundation). Это **не** Redis Stack / Redis Enterprise и не смена лицензии Redis Ltd. 2024 года.

На Kubernetes у проекта два официальных пути, и их нельзя путать:

| Путь | Что умеет | Готовность к проду |
|---|---|---|
| Helm-чарт **`valkey-io/valkey-helm`**, чарт `valkey` **0.11.0**, `appVersion` **9.1.1** | Standalone **или** primary + replicas. **Не** Cluster. **Не** Sentinel | Да, как упаковка standalone/репликации |
| **`valkey-io/valkey-operator`** (релизы до v0.5.0) | Cluster mode (шарды, слоты, failover) | **Нет.** README оператора: *in active development and **not ready for production use***, API `v1alpha1` может сломаться |

Этот текст — не мануал «скопируй `helm install`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Valkey **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API). Ниже — как поставить in-memory хранилище (кэш, сессии, замки, лимиты) на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** озеро эталона, **не** шина событий и **не** замена PostgreSQL.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **In-memory** | Рабочий набор живёт в **RAM**. Диск (RDB/AOF) — снимок и журнал, не «вторая Cassandra». Терабайты озера в Valkey не помещаются. |
| **Primary (ранее master)** | Узел, который принимает **записи**. В репликации он один на набор данных. |
| **Replica** | Копия primary. Читать можно (если готовы к отставанию). Писать на replica в штатной схеме нельзя. |
| **Асинхронная репликация** | Primary отвечает клиенту **OK**, а потом досылает запись replica. Падение primary до досылки = **потеря уже подтверждённой** записи. Это не баг, это модель. |
| **`WAIT`** | Команда «подожди, пока N replica подтвердят». Снижает шанс потери, **не** даёт строгую консистентность (это прямо сказано в cluster tutorial). |
| **Sentinel** | Отдельные процессы: следят за primary/replica, **выбирают новый primary**, говорят клиентам новый адрес. Нужны, когда **нет** Cluster. |
| **Кворум Sentinel** | Сколько Sentinel должны согласиться, что primary мёртв, чтобы начать failover. Чтобы **выполнить** failover, нужна ещё **majority** всех Sentinel. Два Sentinel вендор показывает как *DON'T DO THIS*. |
| **Valkey Cluster** | Шардирование: данные режутся на **16384 hash slot** по нескольким primary. HA шарда = replica **этого** primary. Sentinel с Cluster **не сочетают**. |
| **Hash slot** | Корзина ключа: `CRC16(key) mod 16384`. Ключ живёт на одном primary. |
| **Hash tag `{…}`** | Кусок ключа в фигурных скобках: `user:{123}:a` и `user:{123}:b` попадут в **один** слот. Нужно для MULTI/Lua на нескольких ключах. |
| **Cluster bus** | Внутренний канал нода↔нода. Порт по умолчанию **клиентский + 10000** (6379 → **16379**). Клиентам туда нельзя. По умолчанию **без** прикладной аутентификации: кто дотянулся до порта, тому кластер верит. |
| **`cluster-node-timeout`** | Сколько миллисекунд нода может не отвечать, прежде чем её сочтут мёртвой. Дефолт в учебнике кластера: **5000**. Primary, который **не видит majority других primary** столько же времени, **перестаёт принимать запросы**. |
| **`cluster-require-full-coverage`** | По умолчанию **yes**: если часть слотов никому не принадлежит, кластер **не принимает записи**. |
| **RDB** | Снимок всего датасета в файл. Быстрый рестарт, удобный бэкап. Между снимками можно потерять **минуты** (зависит от `save`). |
| **AOF** | Журнал каждой записи. Политика `everysec` (дефолт): потерять можно **около 1 секунды**. `always` — очень медленно. |
| **`appendfsync`** | Как часто AOF сбрасывать на диск: `always` / `everysec` / `no`. |
| **Persistence off** | Чистый кэш. Репликация **без** persistence на primary + авторестарт = классический способ **обнулить и primary, и все replica**. Вендор это отдельно запрещает. |
| **`maxmemory` / `maxmemory-policy`** | Потолок RAM и что выкидывать, когда он достигнут. Дефолт политики: **`noeviction`** (новые записи начинают получать ошибку). Для кэша обычно `allkeys-lru` и т.п. — это решение, не дефолт. |
| **ACL** | Пользователи и права на команды/ключи. `requirepass` — совместимость со старым Redis; с `aclfile` / `ACL LOAD` он **игнорируется**. |
| **Protected mode** | Если у `default` нет пароля — слушать только localhost. В Docker/K8s его часто выключают, **подставив bind 0.0.0.0** — тогда без ACL инстанс открыт всей сети пода. |
| **`min-replicas-to-write`** | Primary перестаёт писать, если живых replica с лагом ≤ `min-replicas-max-lag` меньше N. Дефолт **0** (выкл.). Это **не** гарантия, что replica запись приняла, а сужение окна потери. |
| **Failover** | Смена primary. Пока идёт — записи (и иногда чтения шарда) коротко падают. Клиент должен уметь retry и обновлять топологию. |
| **Split-brain / minority** | Клиент остался с меньшинством узлов и ещё пишет в «старый» primary, пока majority не выберет нового. Потом эти записи **выбрасываются**. Окно ≈ `cluster-node-timeout` (Cluster) или `down-after-milliseconds` (Sentinel). |
| **IO threads** | Опция (`io-threads`): часть сетевой работы не на одном ядре. Команды по-прежнему в основном на главном потоке. Больше CPU ≠ линейный QPS без замера. |
| **Stretch** | Один логический Cluster/Sentinel-набор, узлы физически в разных ЦОДах. Общаются по 6379/16379/26379. |

## Основные элементы системы и зависимости

### Что входит в Valkey 9.1.1 (это одно ПО, несколько топологий)

| Топология | Зачем | Как масштабируется запись | Как масштабируется чтение | Автоfailover primary |
|---|---|---|---|---|
| **Standalone** | Тест, один процесс | Вертикаль RAM/CPU | Нет | Нет |
| **Replication** (1 primary + N replica) | Копия данных, чтение с replica | **Нет** (один writer) | Да, replica | **Нет само по себе.** Нужен **Sentinel** (или ручной `REPLICAOF` / Cluster) |
| **Sentinel + replication** | HA без шардов | Нет | Да | Да, если клиент умеет Sentinel и Sentinel ≥ 3 в независимых зонах |
| **Cluster** (минимум 3 primary) | Шарды + HA шарда replica | Да (больше primary) | Да (replica слотов) | Да, внутри Cluster. Sentinel **не** используется |

Плюс рядом, но это уже другое ПО: клиентские библиотеки (должны уметь Sentinel **или** Cluster), Prometheus exporter (`oliver006/redis_exporter` в официальном Helm), Ingress не нужен для Valkey как для UI.

### Официальные порты (менять можно, но это контракт сети)

| Порт | Назначение |
|---|---|
| **6379/TCP** | Клиенты и миграция ключей между нодами Cluster |
| **16379/TCP** | Cluster bus (если клиентский порт 6379). Только ноды кластера |
| **26379/TCP** | Sentinel ↔ Sentinel и клиенты, которые спрашивают «кто сейчас primary» |

Firewall: оба порта Cluster обязательны, иначе кластер «не работает как ожидается» (цитата tutorial). Cluster bus **изолировать** сетью или закрыть **mTLS** (`tls-cluster yes`): вендор прямо пишет, что без этого чужой узел может перехватить слоты.

### Чего в Valkey нет (частая путаница)

| Нужно системе | Это не Valkey | Зачем помнить |
|---|---|---|
| Озеро эталона / клиентские карточки как SoT | PostgreSQL, объектное хранилище, ваше озеро | Данные в RAM + возможная потеря при failover. SoT сюда класть нельзя |
| Шина событий, порядок, replay | Kafka | Pub/Sub в Cluster идёт через bus, это не Kafka |
| Процессный движок | Camunda | Valkey может держать кэш/лок рядом, не BPMN |
| Строгая консистентность (как синхронный Postgres) | Нет. Даже `WAIT` не даёт strong consistency | Не обещать руководству «не потеряем ни одного OK» |
| HA без Sentinel и без Cluster | Нет | Helm replication = копии, **не** смена primary при падении writer |
| Cluster из двух primary | Нет. Минимум **три** primary. Для прода вендор **настоятельно** рекомендует **шесть** узлов (3 primary + 3 replica) | Два ЦОДа «по primary» без третьего — не кворум Cluster |
| Sentinel из двух процессов | *DON'T DO THIS* в официальном гайде | Majority из двух ломается на первой партиции |
| NAT / Docker port-mapping для Cluster и Sentinel | Cluster: *does not support NATted environments*; для Docker — `--net=host`. Sentinel: port remap ломает discovery | В Kubernetes нужны **Pod IP / announce**, не NodePort «как у веб-приложения» |
| Официальный прод-оператор Cluster на K8s | README: **not ready for production** | Не строить платформу на `v1alpha1` |
| Cluster в официальном Helm `valkey` 0.11.0 | *This chart does not and will not support Valkey cluster mode* | Шарды — другой инсталлятор, которого для прода у проекта ещё нет |
| Порог RTT между ЦОДами | Нет миллисекунд | Есть `cluster-node-timeout` (пример 5000 ms) и `down-after-milliseconds` Sentinel (в примере 60000). Это не «можно 80 мс» |
| ГОСТ / СКЗИ | Не заявлено | Штатный TLS — не криптография КИИ |
| Гарантия «терабайты влезут» | Нет | Влезает то, что в **RAM всех primary** (+ запас на fragmentation, replica buffers, fork() при RDB) |

### Зависимости окружения (обязательны)

- **RAM ≥ размер датасета** на каждом primary (и запас: репликация, AOF rewrite, `fork()` на больших снимках может задержать клиентов на миллисекунды–секунды — формулировка persistence-доки).
- **Диск** под RDB/AOF, если persistence включена. SSD предпочтителен не «как у ES», а чтобы `fork`+запись не стопорили. Для replication Helm: persistence **обязательна**.
- **Клиенты**, которые понимают выбранную топологию: обычный TCP на один Service **не** переживает смену primary (Sentinel) и **не** попадает в нужный слот (Cluster; нужен cluster-aware клиент и `-c` у `valkey-cli`).
- **Kubernetes CSI + RWO**, `WaitForFirstConsumer`, если PVC зональные (как у любого StatefulSet). Replica не «переедет» в другой ЦОД со своим диском.
- **Сеть** 6379 между клиентами и primary; 16379 / 26379 только внутри контура узлов.
- **Часы** относительно нормальные: лаг replica считается по ping/ack, не по «терабайтам Kafka».

### Как Valkey стыкуется с вашей архитектурой

```
Микросервисы / интеграционное API / Camunda workers
        │  GET/SET, кэш, сессия, rate-limit, distributed lock
        ▼
   6379 ──► primary  (или cluster-aware клиент → нужный primary слота)
              │  async replication
              ▼
           replica(s)
              ▲
   26379 ── Sentinel (если не Cluster): «кто сейчас primary?»
```

Valkey **не** пишет в озеро и **не** заменяет Kafka. Типичное место: горячий кэш перед эталоном, идемпотентность консьюмера, лимит вызовов к гос-API, сессии UI. Если ключ должен пережить падение ЦОДа **без потери** — его место в БД/озере, а Valkey только ускоряет чтение.

## Краткие вводные

### Зачем вам Valkey в этой архитектуре

У вас много сервисов, интеграции с ожиданием лагов, процессный движок, Kubernetes. Типичные задачи, которые Kafka и озеро **плохо** решают сами:

1. Кэш нормализованного ответа интеграционного API на секунды–минуты (не «вся карточка клиента навсегда»).
2. Rate limit / circuit: не долбить госслужбу с каждого пода.
3. Короткоживущие замки и идемпотентные ключи консьюмера Kafka.
4. Сессии шлюза, если они не должны жить в SQLite пода.

Это слой **ускорения и координации**, не слой истины.

### Как устроена отказоустойчивость (идея, не магия)

Две **несовместимые** модели. Выбрать одну.

**A) Replication + Sentinel (один набор ключей целиком на каждом узле)**

| Что падает | Что происходит |
|---|---|
| Одна replica | Чтение с неё пропадает; запись на primary жива. Primary должен иметь ещё replica, если `min-replicas-to-write ≥ 1` |
| Primary, Sentinel ≥ 3 и majority жива | Failover: replica становится primary. Клиенты **обязаны** спросить Sentinel (или библиотеку). Кто продолжает писать в старый IP — пишет в пустоту/в деградировавший узел |
| Majority Sentinel в меньшинстве партиции | Failover **не** стартует (цитата: *never starts a failover if the majority of Sentinel processes are unable to talk*) |
| Два Sentinel | Официально не схема |
| Primary без persistence + Kubernetes сразу перезапустил под | Replica могут **синхронизироваться с пустым** primary и уничтожить данные. Вендор: persistence на primary **и** replica; иначе **запретить авторестарт**. Sentinel эту гонку **не лечит**, если primary успевает подняться раньше детекта |

**B) Cluster (данные разрезаны по слотам)**

| Что падает | Что происходит |
|---|---|
| Один primary, у него есть replica | Replica становится primary этого диапазона слотов. Остальные шарды живы |
| Primary **и** его единственная replica | Слоты этого диапазона недоступны. При `cluster-require-full-coverage yes` (дефолт) кластер может **отказать в записях вообще** |
| Majority primary недоступна | Кластер недоступен (tutorial: *unavailable when the majority of primaries are unavailable*) |
| Клиент в меньшинстве с одним primary дольше `cluster-node-timeout` | Сначала primary ещё принимает записи, потом останавливается; если за это время majority выбрала нового primary — записи клиента **потеряны** |
| Два ЦОДа из трёх при 3 primary по одному на ЦОД | Жив 1 primary из 3 → majority нет → запись кластера встаёт. Пережить **два** ЦОДа на трёх primary **нельзя** честно |

Дефолтная « fortовая» схема Cluster для прода: **3 primary + 3 replica**. Падение **одного** узла переживается. Падение узла и его replica «вместе» (один ЦОД, если они в одной зоне) — нет.

Репликация **везде асинхронная**. `min-replicas-to-write 1` сужает окно, не закрывает его. `WAIT` в приложении — если готовы платить задержкой.

**Бэкап.** Replica ≠ backup. `FLUSHALL`, кривой ACL, пустой primary после рестарта — replica повторит беду. RDB на сторону (S3/лента) — отдельный процесс.

### Как устроено масштабирование

Три разные оси:

1. **Больше RAM / больше ключей** → вертикаль primary **или** шарды Cluster (больше primary). Озеро «терабайты» сюда не скейлится: вы упрётесь в память **раньше**, чем в диск Kafka.
2. **Больше чтений** → replica (оба режима) + клиенты, которые читают с replica и терпят stale.
3. **Больше записей** → только Cluster (больше primary) **или** несколько **независимых** standalone/Sentinel-наборов (кэш сессий отдельно от rate-limit). Один Sentinel-набор = один writer.

Сигналы: `used_memory`, evicted keys, `connected_replicas`, replication offset/lag, отказ записи при `min-replicas-to-write`, `cluster_state`, очередь клиентов, latency `INFO`.

Официального «N ядер на интеграционный сервис» нет. `io-threads` — опция под замер, не слайд.

Helm 0.11.0 по умолчанию: **нет** persistence на standalone, replica выключены, `minReplicasToWrite: 0`, auth выкл., TLS выкл. Это стенд, не capacity plan.

### Безопасность самого Valkey

Компрометация Valkey = компрометация **сессий, токенов, кэша ответов гос-API, замков**. `FLUSHALL` и `CONFIG` опаснее, чем «просто кэш».

Заводские и Helm-ловушки:

| Тема | Факт |
|---|---|
| Bind в `valkey.conf` | `bind 127.0.0.1 -::1`, `protected-mode yes` |
| Helm без `auth.enabled` | Кто достучался до Service 6379 — тот хозяин, если protected-mode снят под K8s |
| Helm + `auth.enabled` | **Обязателен** пользователь `default` в ACL. Иначе, цитата чарта: *anyone can access the database without credentials* |
| `requirepass` | Совместимость; не мешать с `aclfile` |
| Cluster bus | Без сетевой изоляции / mTLS — захват слотов |
| TLS | В доке Valkey при включённом TLS по умолчанию **mTLS** клиентов. Helm: `tls.requireClientCertificate` дефолт **false** — это уже ослабление относительно доки сервера |
| `rename-command` | Можно спрятать `CONFIG`/`FLUSHALL`; это hardening, не замена ACL |
| 9.1.1 | Без этого патча аутентифицированный TLS-клиент — вектор RCE (CVE-2026-56684) |

«Выставили LoadBalancer 6379 в интернет без ACL» — это не кэш, это открытая память контура.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Self-hosted Valkey 9.1.1**, не облачный Redis/Memorystore/ElastiCache и не Redis Enterprise.
2. **Valkey — кэш и координация, не SoT.** Эталон клиентов остаётся в озере/БД. В Valkey — TTL-данные, которые можно пересчитать.
3. **Прод на Kubernetes**, упаковка не-Cluster: официальный Helm **`valkey` 0.11.0**. Sentinel в чарт **не входит** — его ставят отдельными манифестами/StatefulSet по `sentinel.conf` из дистрибутива, либо принимают, что падение primary = ручной failover / простой записи.
4. **Официальный valkey-operator в прод не берём** (цитата README). Cluster на K8s в этой версии платформы — либо подождать оператора, либо Cluster **на VM/bare metal** по cluster tutorial, либо сознательный риск третьего чарта (Bitnami и т.п. — **не** проект Valkey; в этом файле не целевой путь).
5. **Три ЦОДа = три независимые зоны отказа.** Sentinel официально просит класть 3 процесса на машины, *believed to fail in an independent way* / разные AZ. Cluster: 3 primary лучше не класть все в один ЦОД; replica каждого primary — в **другую** зону.
6. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. На 3 Sentinel / 3 Cluster primary потеря двух площадок снимает majority.
7. **RTT неизвестен** — пока нет замера на 6379/16379/26379, stretch Cluster с `cluster-node-timeout 5000` не утверждаем. Sentinel с `down-after-milliseconds` 60s терпимее к короткой тряске, но это не «можно любой RTT».
8. **Нагрузка и размер горячего кэша неизвестны** — нет цифры «N GiB `maxmemory`». Есть потолок RAM и политика вытеснения.
9. **Клиенты микросервисов умеют (или будут уметь) Sentinel XOR Cluster.** Иначе HA на бумаге, в коде — захардкоженный DNS primary.
10. **Persistence в проде включена** (AOF `everysec` + периодический RDB — рекомендация вендора «если важны данные, как у PostgreSQL по степени заботы»: *use both*). Чистый кэш без диска — только если явно примете потерю и **выключите** авторестарт primary (в K8s это почти нереально: kubelet всегда рестартит). Значит «кэш без диска» на K8s конфликтует с безопасностью репликации.
11. **Тестовый стенд изолирован.** На нём допустимы standalone без пароля *внутри песочницы*.
12. **Camunda / Kafka / озеро / интеграционное API** — клиенты Valkey, не части сервера.
13. **Не используем Docker port-mapping для Cluster/Sentinel.** В K8s — ClusterIP/headless на Pod IP.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «helm install и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **Что именно кладём в Valkey** (TTL-кэш vs «все клиенты») | RAM и потеря при failover. SoT в Valkey = потеря эталона при 1 инциденте |
| **Sentinel или Cluster** | Разные клиенты, порты, модель отказа. Смешать нельзя |
| **RTT и потери между ЦОДами** | Ложные failover vs долгий детект. Цифры вендор не даёт |
| **Один K8s на 3 зоны или три кластера** | PVC зональные; Sentinel majority; stretch bus 16379 |
| **Размер горячего набора и `maxmemory-policy`** | Без потолка OOMKill. С `noeviction` при заполнении **встанет запись** интеграционного API |
| **Клиентские библиотеки** | Без Sentinel/Cluster support failover = простой до правки DNS |
| **ПДн в кэше** | TTL не отменяет 152-ФЗ. Шифрование тома, ACL, сеть |
| **Нужен ли блок записи без replica** (`min-replicas-to-write`) | 0 = пишем в никуда при обрыве репликации. ≥1 = запись встанет, когда replica отвалятся — это надо заложить в UX интеграций |
| **Кто владеет FLUSH/CONFIG** | Один админский ACL на всех поды CI — способ стереть прод |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **9.1.1** (не 9.1.0) и топологию: standalone / replica / replica+Sentinel / Cluster.
2. Оценить **объём горячих ключей** и TTL. Не «терабайты озера».
3. Persistence: для всего, что жалко потерять на рестарте пода — **AOF+RDB**. На replication — **обязательно**.
4. ACL + сеть **до** первого клиента из общего namespace.
5. Прогнать PING, SET/GET, failover (учебный) и убедиться, что **приложение** переключилось, а не только `valkey-cli`.
6. Метрики: память, evict, лаг репликации, `cluster_state` / `SENTINEL CKQUORUM`.
7. Только потом — rate-limit и замки на боевом интеграционном контуре.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель:** увидеть SET/GET, ACL, шум приложения (Camunda worker, кэш API). **Не** цель: доказать переживание ЦОДа и шарды.

**Путь A — Docker одной командой:**

```text
docker run --rm -p 6379:6379 valkey/valkey:9.1.1
```

Для знакомства. Protected-mode/bind в контейнере обычно слушает 0.0.0.0 — **не** публиковать порт за пределы песочницы.

**Путь B — Helm `valkey` 0.11.0 standalone** (ближе к оркестратору):

- чарт 0.11.0, образ **9.1.1**;
- `auth.enabled=true` и пользователь `default` с паролем из Secret, даже на тесте, если сеть не air-gap ноутбука;
- persistence можно выкл., понимая: рестарт пода = пустой кэш.

Режим «6 подов Cluster на Minikube» для знакомства **не нужен**, пока оператор в README запрещён для прода: получите ложное чувство HA и другой операционный контур.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Sentinel / Cluster | нет | Нет требования пережить primary |
| Replica | 0 | Нет нагрузки на чтение |
| PVC | emptyDir | Данные стенда не жалко |
| mTLS / Cluster bus | нет | Нет 16379 |
| `maxmemory` | можно не ставить | Датасет игрушечный |
| `min-replicas-to-write` | 0 | Нет replica |

#### Чего на тесте **не** стоит упрощать

- Тег **9.1.1** (security).
- Хотя бы один SET/GET из **вашего** сервиса, не только `valkey-cli`.
- Понимание: Service `valkey` в Helm — это **writer**. После появления replica запись на `valkey-read` будет ошибкой.
- Не включать replication **без** PVC «на поиграть»: Helm и вендор описывают уничтожение данных.

#### Сильные стороны

- Часы, не недели.
- Совпадает с официальным образом и Helm standalone.
- Дёшево показывает, упрётся ли интеграционный клиент в один RTT до кэша.

#### Слабые стороны

- Нет модели отказа primary.
- Успех GET на стенде **не** доказывает cluster-aware клиент и не доказывает `WAIT`.
- Привычка `auth.enabled=false` уедет в прод.

Препрод: тот же Helm **replication** с PVC + ACL + (если цель HA) три Sentinel, даже без боевого QPS.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «гигабайт под терабайты озера» **нет**. Ниже правила готовности.

#### Шаг 0. Макроархитектура (сделать до установки)

Сначала вопрос: **один writer на весь горячий набор или шарды?**

- Горячий набор **влезает в RAM одной машины** (с запасом 2× на fork/фрагментацию) → **Sentinel + 1 primary + ≥2 replica**. Проще клиенты (многие умеют Sentinel как «Redis Sentinel»).
- Не влезает **или** нужна горизонталь записи → **Cluster 3+3** (и дальше больше primary). Клиенты — только cluster-aware. На K8s официального прод-оператора **нет**: либо Cluster вне «как поды Deployment», либо риск не-GA оператора, либо ждать.

**Вариант A — один Kubernetes, три зоны.**

Sentinel:

- 3 пода Sentinel, topology spread **по зоне**, PVC/emptyDir для `sentinel.conf` (**файл должен быть writable** — иначе Sentinel не стартует).
- Primary + replica: StatefulSet, PVC, **не** все replica в зоне primary.
- Клиенты ходят в Sentinel (26379) за адресом primary, затем на 6379. Не хардкодить DNS primary.
- Quorum в `sentinel monitor` для 3 узлов обычно **2**. Majority для failover тоже 2 из 3. Падение **одного** ЦОДа с одним Sentinel переживается. Падение двух — нет.

Cluster (если выбрали его и приняли инсталлятор):

- 3 primary в **разных** зонах, replica каждого — **не** в той же зоне (иначе один ЦОД убивает шард насовсем).
- `cluster-node-timeout` не ставить «поменьше, чтобы быстрее» пока RTT не измерен: ложный failover + потеря async-записей.
- 16379 только NetworkPolicy между подами Cluster. `tls-cluster yes`.
- Официальный Helm это **не** ставит.

**Вариант B — три Kubernetes.**

Не копировать по независимому Valkey «как Falco DaemonSet». Получите три кэша и три правды сессий.

Рабочие подварианты:

- **B1.** Один Sentinel/Cluster-набор в «домашнем» ЦОДе, клиенты из других ЦОДов ходят по сети. Падение домашнего ЦОДа = нет кэша (приложения должны переживать miss → озеро/API).
- **B2.** Stretch узлов по трём кластерам — та же цена RTT, что у A, плюс сложнее сеть 16379. Без замера не делать.
- **B3.** Три независимых Valkey — только если ключи шардированы приложением (сессии регионально). Обычно хуже.

##### Сильные / слабые (A, Sentinel, 3 зоны)

| Сильное | Слабое |
|---|---|
| Совпадает с гайдом «3 Sentinel / разные AZ» | Один writer: запись не горизонталится |
| Клиенты часто уже умеют Sentinel | Клиент без Sentinel support = ложный HA |
| Пережить 1 ЦОД при размазанных Sentinel | 2 ЦОДа — нет majority |
| Helm умеет replica + `minReplicasToWrite` | Sentinel в официальный чарт **не входит** — это ваш YAML |

##### Сильные / слабые (Cluster 3+3)

| Сильное | Слабое |
|---|---|
| Горизонталь записи, HA шарда | Нет strong consistency; потеря OK при failover |
| Вендорный минимум для «работает как ожидается» | Majority primary; 2 ЦОДа из 3 при 3 primary — смерть записи |
| Не нужен Sentinel | Нужны другие клиенты; MULTI только в одном слоте |
| | Официальный K8s-оператор не для прода; Helm cluster не поддержит |

##### Слабое место stretch без RTT

Нет порога мс. Замерить 6379, 16379, 26379 **до** схемы. Если heartbeat не проходит за `cluster-node-timeout` — Cluster будет «фейлить» живые узлы.

#### Репликация и диск (ядро *не уничтожить данные руками kubelet*)

- Persistence **on** на primary и replica (Helm replication: *mandatory*).
- AOF `everysec` + RDB для бэкапов (вендор: AOF-only не советует).
- Не выключать `save` «для скорости» на primary с replica и авторестартом.
- `min-replicas-to-write 1`, `min-replicas-max-lag 10` (как в примере Helm/conf) — если потеря подтверждённой записи больнее, чем короткий отказ записи. Для кэша с TTL можно оставить 0 **осознанно**.
- PDB на replica (`maxUnavailable: 1` / `minAvailable`), чтобы drain не снял все копии.
- Anti-affinity: primary и хотя бы одна replica не на одном узле/зоне.

**Слабое место:** replica.enabled + emptyDir. Это сценарий «пустой primary после рестарта съел флот».

#### Sentinel (ядро HA *без* шардов)

- Ровно **не меньше 3**, в независимых зонах.
- Не 2.
- Клиенты: discovery через Sentinel, не один ClusterIP primary навсегда (после failover VIP «писателя» должен следовать за ролью, либо клиент сам переспрашивает).
- `SENTINEL CKQUORUM` в мониторинге.
- Auth Sentinel (ACL) **тот же класс секретов**, что у data-узлов; иначе 26379 — пульт failover для злоумышленника.
- Учения: kill primary, проверить, что приложение (не только cli) пишет в новый.

#### Cluster (ядро HA *со* шардами)

- Старт: `--cluster-replicas 1` на 6 узлах (tutorial).
- `appendonly yes` в минимальном примере вендора для узлов Cluster.
- `cluster-require-full-coverage`: для «часть ключей важнее доступности остальных» оставляют yes; для «пусть лучше дырявый кэш» — no (это компромисс доступности, не магия).
- Не открывать 16379 с мира.
- Не Docker NAT.
- После failover клиент **обновляет слот-карту**; иначе пишет не туда.

#### Память и нагрузка

- Выставить `maxmemory` **ниже** cgroup limit (запас на буферы replica, AOF rewrite, fragmentation). Вендор предупреждает: при `maxmemory` на primary с replica нужен запас RAM на буферы.
- Кэш: политика вытеснения явно, не молчаливый `noeviction`.
- Замки/сессии, которые нельзя вытеснить: отдельный инстанс **или** `volatile-*` только на ключах с TTL.
- Не класть озеро. Не класть тела ответов госорганов на недели без оценки RAM.

#### Безопасность прода

1. **Секреты:** ACL, отдельный replication-user (`+psync +replconf +ping` — минимум из Helm README), нет общего `default` с `+@all` у приложений.
2. **Сеть:** 6379 только приложению; 16379/26379 только узлам; NetworkPolicy.
3. **Данные:** TLS к клиентам; для Cluster ещё `tls-cluster` / `tls-replication`; PVC encryption платформы; не тащить ПДн без TTL и правовой оценки.
4. Pin образа **9.1.1** (digest), свой registry.
5. Не LoadBalancer в интернет.
6. Метрики exporter — с auth к Valkey, не анонимный 6379 «для scrape».

Helm production-ish (не Cluster): `auth.enabled`, Secret, `replica.enabled`, PVC size от RAM (диск AOF может быть больше датасета), `minReplicasToWrite` по политике, `tls.enabled` + свой Secret, `metrics.serviceMonitor`, PDB, topologySpread, `initSysctl` не нужен (это не ES).

##### Сильные / слабые выбранной схемы (Helm replica + свои 3 Sentinel + ACL + TLS + pin 9.1.1)

| Сильное | Слабое |
|---|---|
| Официальный сервер и официальный чарт на данные | Sentinel собираете сами |
| BSD, без лицензии DCE как у Sonar | Async: OK клиенту ≠ запись на replica |
| 3 AZ как в гайде Sentinel | 2 ЦОДа убивают failover |
| `min-replicas-to-write` сужает окно потери | Дефолт Helm 0 — легко забыть |
| CVE 9.1.1 закрыты | Забыть пин — снова RCE на TLS |

#### Порядок вывода в прод

1. Решить: кэш с допустимой потерей vs данные, которые нельзя потерять при failover (второе — не только Valkey).
2. Измерить RTT 6379/16379/26379. Выбрать stretch или «мозг в 1–2 ЦОДах + miss в приложении».
3. Оценить RAM горячего набора. Выбрать Sentinel **или** Cluster.
4. Поднять persistence+ACL на препроде. Учение «рестарт primary не обнуляет replica».
5. Поднять 3 Sentinel (или Cluster 3+3 выбранным инсталлятором, **не** GA-оператором, если не принимаете риск).
6. Включить `min-replicas-to-write` по политике.
7. Подключить одно приложение с **правильным** клиентом. Kill primary. Приложение само должно ожить.
8. Нагрузить и смотреть память, лаг, отказы записи.
9. Учение «ЦОД с primary мёртв» и «ЦОД с двумя Sentinel мёртв» (второе — ожидаемый отказ failover).

Без пунктов 4, 7 и 9 у вас нет кэша платформы, есть Deployment с 6379.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Либо **≥3 Sentinel в разных зонах** + replica с PVC, либо **Cluster 3+3** со replica в других зонах; переживание **1** ЦОДа; majority не обещать на 2 ЦОДах; клиент умеет failover; persistence on |
| Производительность / масштаб | Не требуется | `maxmemory` + явная политика; запись горизонталится только Cluster или несколькими наборами; RAM = размер данных, не «терабайты озера» |
| Безопасность | Пароль, если сеть шире localhost | 9.1.1; ACL + не пустой `default`; 16379 закрыт; TLS; нет публичного 6379; replication-user; нет `auth.enabled` без `default` |

**Не готов к проду**, если: standalone на три ЦОДа «для HA»; Helm replica без PVC; два Sentinel; Cluster из двух primary; `valkey-operator` как прод; `latest` / 9.1.0; 6379 с мира без ACL; SoT клиентов в Valkey; клиенты без Sentinel/Cluster; `min-replicas-to-write 0` при обещании «не потеряем записи»; stretch без замера RTT; ждут, что Valkey заменит Kafka/озеро; ждут strong consistency.
