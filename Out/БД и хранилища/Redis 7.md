# Redis Community Edition 7.4.11 — развёртывание и настройка

Версия ПО: **Redis Community Edition 7.4.11** (релизная дата 17 августа 2026; на дату подготовки документа это последний патч линии **7.4**, urgency `SECURITY`).  
Документация OSS/Stack: https://redis.io/docs/latest/operate/oss_and_stack/  
Конфиг-образец (дефолты 7.4): https://github.com/redis/redis/blob/7.4/redis.conf  
Официальный образ: `redis:7.4.11` (Docker Hub library/redis; теги `7.4.11`, `7.4`, `7` на эту дату указывают на этот патч).

Линия **7.2 и старше** — лицензия BSD-3-Clause. Линия **7.4.x** — **RSALv2 или SSPLv1** (это уже не BSD; юридически это не «просто open source как Kafka»). Линия **8.x** на дату документа живая (патч 8.10.1 вышел в тот же день, 17 августа 2026). Этот файл — про **Redis 7**, как запрошено; 8.x сюда не подменяем.

Этот текст — не мануал «скопируй `docker run redis`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Redis **упоминался** в правилах диалога как типичное платформенное ПО под нагрузку. В исходной архитектуре (Kafka / Camunda / озеро эталона / интеграционное API) Redis **не назван**. Ниже — как поставить его на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** замена Kafka, **не** озеро клиентских данных и **не** интеграционная шина к 30+ госслужбам.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Инстанс / нода** | Один процесс `redis-server`. Данные **в RAM**; диск — чтобы пережить рестарт, не чтобы «хранить терабайты как СУБД». |
| **Ключ / значение** | Запись вида `session:abc → …`. Структуры разные: строка, hash, list, set, zset, stream, bitmap… |
| **TTL** | Срок жизни ключа. Истёк — Redis удалит. Для кэша это норма; для «единственной копии клиента» — нет. |
| **Master (primary)** | Нода, которая **принимает запись**. Реплики копируют с неё. |
| **Replica (replica / historically slave)** | Копия master. По умолчанию **только чтение** (`replica-read-only yes`). |
| **Асинхронная репликация** | Master **не ждёт** реплику, отвечая клиенту «записано». Реплика может отстать. Это **дефолт** Redis. |
| **WAIT / WAITAOF** | Команды клиента: «подожди, пока N реплик подтвердят» / «подожди fsync в AOF». Уменьшают окно потери, **не** делают Redis CP-системой с сильной согласованностью. WAITAOF — с **7.2**. |
| **Sentinel** | Отдельные процессы, которые **следят** за одним master+репликами (не Cluster), голосуют, что master мёртв, и **переключают** реплику в master. Клиенты спрашивают Sentinel: «кто сейчас master?». Порт **26379**. |
| **Кворум Sentinel** | Сколько Sentinel должны согласиться, что master недоступен (это *детект*). Сам failover стартует только если есть **большинство процессов Sentinel**. Два Sentinel официально «DON'T DO THIS». |
| **SDOWN / ODOWN** | Subjectively down (один Sentinel так думает) / Objectively down (кворум согласился). Failover — от ODOWN. |
| **Redis Cluster** | Режим шардирования: ключи раскиданы по **16384 слотам**. Несколько master, у каждого свои слоты и обычно свои реплики. Sentinel **не используется**. |
| **Hash slot** | Корзина ключа: `CRC16(key) mod 16384`. Клиент ходит на master, которому слот принадлежит. |
| **Hash tag** `{...}` | Кусок ключа в фигурных скобках: `{user:1}:profile` и `{user:1}:cart` попадут в **один** слот. Без этого мультиключ (`MGET`, транзакция на два ключа) в Cluster часто даёт **CROSSSLOT**. |
| **Cluster bus** | Внутренняя сеть нода↔нода (gossip, failover). Порт по умолчанию **командный + 10000**, то есть **16379**, если клиентам **6379**. Клиенты сюда **не** ходят. |
| **Gossip** | Ноды периодически рассказывают друг другу, кто жив. На этом держится детект отказа Cluster. |
| **NODE_TIMEOUT (`cluster-node-timeout`)** | Сколько миллисекунд нода должна быть недостижима, чтобы её посчитали мёртвой. Дефолт в `redis.conf` **15000**. Должен быть **заметно больше RTT**. Порога «N мс между ЦОДами» у проекта **нет**. |
| **Большинство master** | Failover в Cluster: реплика должна получить голоса **большинства master**. 3 master → нужно 2. Падение двух ЦОДов из трёх при одном master на ЦОД = кворума нет. |
| **cluster-require-full-coverage** | Дефолт **yes**: если часть слотов никому не принадлежит, кластер **отказывается писать** (и часто читать покрытые слоты тоже в error state). `no` — «обслуживаем что осталось». Доступность vs целостность покрытия. |
| **Replica migration** | Если у master не осталось реплик, Cluster может **переселить** лишнюю реплику с другого master. Барьер: `cluster-migration-barrier`. |
| **RDB** | Снимок всего датасета на диск. Быстрый рестарт, компактный файл для бэкапа. Между снимками данные можно потерять (минуты — типичный save point). |
| **AOF** | Журнал записей. С Redis **7.0** — **multi-part AOF** (base + incremental). Политика fsync: `always` / `everysec` (дефолт смысла AOF) / `no`. |
| **appendfsync everysec** | Раз в секунду сбросить AOF на диск. Официально: можно потерять **около 1 секунды** записей при аварии. |
| **BGSAVE / rewrite** | Снимок или сжатие AOF делает **дочерний процесс** после `fork()`. На большом датасете fork даёт паузу latency. Ещё одна причина не класть терабайты в Redis. |
| **maxmemory** | Потолок RAM инстанса. **В дефолтном redis.conf не задан** — процесс будет есть память, пока его не убьёт OOM. В проде задают всегда. |
| **maxmemory-policy** | Что делать, когда потолок достигнут. Дефолт **`noeviction`**: запись получает ошибку, ключи сами не выкидываются. Для кэша обычно `allkeys-lru` / `allkeys-lfu`. |
| **ACL** | Именованные пользователи и права на команды/ключи (с Redis 6). Рекомендуемый способ вместо одного `requirepass` на всех. |
| **requirepass** | Старый «один пароль на инстанс». С `aclfile` несовместим. Пароль в конфиге **открытым текстом**. |
| **Protected mode** | Если слушаем все интерфейсы и **нет** пароля/ACL — с 3.2 Redis отвечает только loopback и ругается остальным. Это страховка от «выставили 6379 в интернет». |
| **TLS** | Шифрование клиента, репликации и (отдельно) cluster bus. В дефолте **выключен** (`tls-port` закомментирован). |
| **io-threads** | С Redis 6: доп. потоки на **сеть**, не на исполнение команд. Команды по-прежнему в основном на **одном** потоке. Масштаб записи одного ключа ≠ «добавить тред». |
| **LOGICAL DB (`SELECT`)** | На standalone по умолчанию **16** логических баз (0…15). В **Redis Cluster работает только DB 0**. Не проектируйте «db=1 для кэша, db=2 для сессий» если цель — Cluster. |
| **redis-cli --cluster** | Утилита создать/добавить ноды Cluster (`create`, `add-node`, `reshard`). |
| **Stretch** | Один логический Sentinel-набор или один Cluster, ноды физически в нескольких ЦОДах. |
| **Active-Active (CRDT)** | Мультимастер запись в нескольких регионах. Это **Redis Software / Redis Cloud**, не Community 7.4. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. |
| **Valkey** | Форк Linux Foundation от Redis 7.2 (BSD). Не этот документ. Имеет смысл только если юристы запретят RSALv2/SSPL. |

## Основные элементы системы и зависимости

### Что входит в Redis 7.4.11 (это одно ПО из нескольких режимов)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Standalone master** | Один процесс, все ключи | Вертикаль RAM/CPU. Потолок — память **одной** машины и один поток команд |
| **Replica** | Копия для чтения и для failover | Чтение горизонтально (осторожно: отставание). Запись всё равно в master |
| **Sentinel** (несколько процессов) | HA **без** шардирования | Нечётное число, минимум **3**, в независимых зонах отказа. Не добавляет ёмкость |
| **Redis Cluster master** | Своя доля из 16384 слотов | Горизонталь: больше master → больше RAM и write-QPS *в сумме*, если ключи равномерны |
| **Redis Cluster replica** | HA слотов | По реплике на master как минимум; раскладка по ЦОДам — руками/антиаффинити, не «магия» |
| **Клиенты** | Библиотеки с поддержкой Sentinel **или** Cluster protocol (MOVED/ASK) | Масштабируются отдельно. Клиент без Cluster-aware **не** замена прокси |
| **Утилиты** | `redis-cli`, `redis-benchmark`, `redis-check-aof`, `redis-check-rdb` | Операционка, не runtime |

Плюс *рядом*, но это уже другое ПО: **redis-exporter** (метрики Prometheus), UI вроде RedisInsight, оператор Kubernetes. Их HA проектируется отдельно.

**Sentinel и Cluster вместе на один датасет не ставят.** Это два разных способа HA. Выбирают один.

### Официальные порты (менять можно, контракт сети лучше не плодить)

| Порт | Назначение |
|---|---|
| **6379/TCP** | Командный протокол (клиенты, репликация, `redis-cli`) |
| **16379/TCP** | Cluster bus (если клиентский 6379 и `cluster-port` не задан: порт+10000) |
| **26379/TCP** | Sentinel |

UDP нет. TLS на тех же ролях — отдельные `tls-port` / `tls-replication` / `tls-cluster` в конфиге.

Клиенты:

- Standalone / replica: на текущий **master** для записи; чтение с replica только если приложение это умеет и переживает stale.
- Sentinel: клиент ходит к **Sentinel** (несколько адресов), спрашивает master, затем к 6379 master. Клиент **обязан** уметь Sentinel.
- Cluster: клиент держит карту слотов, ходит **напрямую** на нужный master. Балансировщик «как у HTTP на все 6379» без cluster-aware ломает модель так же, как у Kafka.

### Чего в Redis Community 7.4 нет (частая путаница)

| Нужно системе | Это не Community Redis 7.4 | Зачем помнить |
|---|---|---|
| Источник истины клиентских данных / «озеро эталона» | СУБД, object storage, warehouse | Redis — in-memory. Терабайты × (1 + реплики) = терабайты **RAM**. Реплика и AOF не делают его SoT |
| Шина событий с партициями, retention, consumer group | Apache Kafka | Pub/Sub Redis — fire-and-forget, нет долгого лога как у Kafka. Streams есть, но это не замена вашей шины |
| Camunda / BPMN | Process engine | В Redis можно кэшировать или лочить шаг, не исполнять процесс |
| Интеграции с госслужбами | Ваше интеграционное API | Сюда — идемпотентность/кэш ответа, не коннект к ведомству |
| Полнотекст / JSON-документы «из коробки» как OpenSearch | Модули RedisJSON / RediSearch, Redis Stack, Redis 8 с модулями, или отдельный поиск | В ванильном `redis:7.4.11` этих модулей **нет**, пока сами не загрузите `.so` (и не примете их лицензию) |
| Мультимастер запись в 3 ЦОДах (Active-Active) | Redis Software / CRDT | Community Cluster = **один** writer на слот |
| Сильная согласованность (как quorum-write в etcd) | Не заявлено | Спека Cluster прямо: окна потери acknowledged writes; `WAIT` это не CP |
| ГОСТ TLS / СКЗИ | Не входит | Штатный TLS OpenSSL/студии сборки — не криптография КИИ, если ИБ её выдвинет |
| Официальный порог RTT между ЦОДами | Нет | `cluster-node-timeout` «должен быть велик относительно RTT». Миллисекунд в доке **нет** |
| Официальный Kubernetes-оператор Community | Нет | Оператор Redis Ltd — **Enterprise**. Community: сторонние операторы/чарты, совместимость **проверять** |
| Замена бэкапа репликами | Нет | Реплика спасает от падения **ноды**. Не спасает от `FLUSHALL`, кривого `DEL`, истечения TTL, шифровальщика |

### Зависимости окружения (обязательны)

- **Процесс и RAM.** Рабочий набор + накладные структуры + буферы реплик + пик AOF rewrite/BGSAVE (copy-on-write после fork) должны влезать в лимит контейнера/машины. Лимит K8s = `maxmemory` без запаса → OOM в самый неудачный момент (снимок).
- **Диск.** Для прода с persistence: локальный быстрый том (SSD) под RDB/AOF, **не NFS** как единственный диск под rewrite (латентность fsync). Даже «кэш» на проде обычно оставляют RDB, чтобы рестарт пода не был холодным стартом всей фермы приложений.
- **Ядро Linux (типичные требования из latency-гайдов Redis, не выдумка «на глаз»):** выключить Transparent Huge Pages (дают хвосты latency); `vm.overcommit_memory=1`, чтобы `fork` для BGSAVE не отказывался. Это хостовые настройки, не «флажок в ConfigMap».
- **Сеть:** стабильный IP/DNS до каждой ноды на **6379**; для Cluster ещё **16379** между **всеми** нодами (полный mesh); для Sentinel — **26379** между Sentinel. NAT/Docker port-mapping Sentinel официально ломает autodiscovery — в доке отдельное предупреждение.
- **Kubernetes (у вас заявлен):** StatefulSet + PVC (RWO) на каждую ноду с persistence; anti-affinity по зонам; NetworkPolicy. Официального OSS-оператора у Redis Ltd **нет**. Практичные community-пути: оператор вроде OT-CONTAINER-KIT (заявляет Redis ≥ 6) или Helm StatefulSet. Образ **пинить `redis:7.4.11`**, не `latest`. Совместимость конкретного релиза оператора с 7.4.11 **прогонять на стенде** — сертификата «как Strimzi 1.2.0 ↔ Kafka 4.3.1» здесь нет.
- **PKI** для прода, если включаете TLS (репликация между ЦОДами без TLS = ключи сессий/токенов по городской сети).
- **Клиентские библиотеки** с нужным режимом (Sentinel vs Cluster) и с таймаутами переключения после failover. «Подключились к одному IP 6379 навсегда» переживает только standalone.

### Как Redis стыкуется с вашей архитектурой

```
Микросервисы, Camunda job workers, интеграционное API
        │  кэш, сессии, идемпотентность, rate-limit, короткие локи
        ▼
   Redis 7.4  (горячее состояние; не SoT)
        ▲
Kafka ── остаётся шиной событий
Озеро эталона ── остаётся истиной клиентских данных
Camunda ── остаётся движком процессов
```

Честные роли в *вашей* картине:

1. **Кэш проекции** справочника/карточки, которую уже отдал интеграционный API или озеро — чтобы не бить озеро на каждый экран.
2. **Идемпотентность** вызова госслужбы: ключ `idem:req-id` с TTL, чтобы повтор Camunda/клиента не удвоил внешний запрос.
3. **Rate-limit / circuit** на выходе интеграционного API (чтобы не уложить чужой контур и свой).
4. **Сессии / одноразовые токены** UI, если они вообще будут в этой системе.
5. **Короткий лок** «этот clientId сейчас обрабатывается» — с пониманием, что Redis-лок не консенсус (сеть моргнула — можно получить два лока). Для денег/юридических шагов это слабое место.

Нечестные роли:

- «Положим клиентов только в Redis, озеро потом» — после eviction, failover с async-репликой или `FLUSHALL` SoT дырявый.
- «Redis Streams вместо Kafka» — другая семантика, другой ops, вы уже выбрали Kafka.
- «Pub/Sub развезём события по 30 интеграциям» — нет persistence как у Kafka; подписчик перезапустился — сообщения нет.

## Краткие вводные

### Зачем вам Redis в этой архитектуре

Kafka доставляет факт. Озеро хранит истину. Camunda ведёт процесс. Интеграционное API ходит наружу и ждёт лаги ведомств.

Остаётся вопрос: **как не ходить в озеро и во внешний мир на каждый чих**, когда нагрузку обещают «высокой», но не измерили. Redis закрывает микролатентность in-memory и простые структуры. Он **не** масштабирует «терабайты эталона» и **не** делает event-sourcing.

Если рабочий набор не влезает в RAM нескольких нод с репликами — это не «добавим Redis Cluster и будет озеро». Это неверный слой.

### Как устроена отказоустойчивость (идея, не магия)

База — **один writer на ключ** плюс **асинхронные копии**. Путать «три контейнера в compose» с HA — главная ошибка.

**1) Репликация сама по себе failover не делает**

| Что падает | Что происходит |
|---|---|
| Master, реплики есть, **нет** Sentinel/Cluster | Реплики содержат копию (с лагом). Клиенты, которые писали в старый IP, **стоят**. Кто-то должен объявить новую master |
| Реплика | Чтение с неё пропадает; запись на master жива |
| Master **без persistence**, процесс авторестартнулся пустым | Официальный failure mode: реплики **синхронизируются с пустым** master и **стирают** свои данные. Persistence на master **и** репликах настоятельно рекомендуется |

**2) Sentinel (один датасет, один master)**

Официально: минимум **3** Sentinel на машинах, которые считаются независимыми по отказу; клиенты с поддержкой Sentinel; периодически **тестировать failover**.

| Что падает | Что происходит |
|---|---|
| Master, кворум Sentinel жив, есть годная реплика | Выборы, реплика → master, клиенты узнают новый адрес через Sentinel |
| Меньшинство Sentinel (нет majority) | Failover **не стартует** — даже если master реально мёртв |
| Два Sentinel из трёх в одном ЦОДе, ЦОД умер | Оставшийся один не проводит failover |
| Сеть между ЦОДами моргнула дольше `down-after-milliseconds` | Риск ложного failover; затем split: старый master мог принять записи, которых нет на новом (async) |

Sentinel **не обещает**, что acknowledged write сохранится: репликация async.

**3) Redis Cluster (шарды + failover слотов)**

Спека: выживает partition, где доступно **большинство master** и есть реплика на каждого недостижимого master. Репликация **async**. «Last failover wins». Окна потери writes — часть дизайна, не баг.

| Что падает | Что происходит |
|---|---|
| Один master из 3, реплика в другой зоне, majority жив | Реплика получает голоса, забирает слоты. Кластер пишет дальше (после секунд на failover; ориентир спеки «обычно 1–2 секунды» **плюс** `NODE_TIMEOUT`) |
| Два ЦОДа из трёх при раскладке 1 master на ЦОД | Majority из 3 нет. Запись останавливается |
| Слоты не покрыты, `cluster-require-full-coverage yes` | Кластер в error: отказ запросов, пока покрытие не восстановится |
| `NODE_TIMEOUT` слишком мал относительно RTT/потерь | Ложные PFAIL/FAIL, лишние failover, потеря async-хвоста |

**4) Persistence**

Реплики не заменяют snapshot/AOF. `FLUSHALL`, ошибка приложения, истёкший TTL, шифровальщик на PVC — реплицируются тоже.

### Как устроено масштабирование

Несколько независимых осей — их нельзя склеить в «добавим реплик»:

1. **Больше данных в RAM** → больше `maxmemory` (вертикаль) или **больше Cluster master** (горизонталь слотов). Реплика **не** увеличивает объём записи.
2. **Больше чтения** → реплики (Sentinel/Cluster replica + `READONLY` в Cluster). Читатель видит **отставание**.
3. **Больше записи** → быстрее CPU одной ноды (команды однопоточны) или **шардирование** Cluster, если разные ключи. Горячий ключ (`client:VIP` на весь мир) Cluster не спасёт.
4. **Сеть** → `io-threads` (не дефолт; в `redis.conf` пример `4`, выключено комментарием). Не путать с «многоядерный Redis как СУБД».
5. **Диск** → не ось ёмкости данных (данные в RAM), ось **как быстро** BGSAVE/AOF не бьют latency.

Ориентиры, которые **есть** у вендора, и которые **нельзя** принять за смету вашего прода:

- Слотов всегда **16384**; «рекомендуемый максимум нод порядка ~1000», не 16384 master.
- Линейность Cluster: спека говорит «как один инстанс × N master» при равномерных ключах и клиенте с persistent connections — это модель, не ваш бенчмарк.
- `maxmemory` в дефолте **нет**. `maxmemory-policy noeviction`.
- AOF в дефолте **выключен** (`appendonly no`); RDB save points в комментариях дефолта: `3600 1`, `300 100`, `60 10000`.
- Нагрузки у вас нет — поэтому **нет** цифры «N гигабайт и M master».

«Терабайты в озере» Redis не наполняют. Наполняет то, что вы **решите туда класть** без TTL и eviction.

### Безопасность самого Redis

Модель из официального security-гайда: Redis рассчитан на **доверенных клиентов в доверенной сети**. Прямой 6379 из интернета — плохая идея. Один `FLUSHALL` сносит датасет. `CONFIG` умеет сменить каталог и имя dump — известный класс атак на запись файла.

Компрометация Redis с сессиями, идемпотентностью интеграций или кэшем ответов госслужб = компрометация **ПДн и содержимого внешних ответов** (даже если «это же кэш»).

Официально:

- Protected mode — если bind-все и без пароля.
- AUTH/пароль **без TLS** не защищает от сниффера: команда AUTH идёт как остальные.
- ACL — рекомендуемый метод с Redis 6.
- `rename-command` **deprecated**, путь — ACL.
- TLS опционален на клиенте, репликации и cluster bus.
- Запускать **не** от root, отдельный пользователь `redis`.
- Lua/`EVAL`: линия 7.4 регулярно закрывает RCE в Lua (в том числе 7.4.11). Боевым учёткам приложений `EVAL`/`SCRIPT` лучше **запретить ACL**, если Lua не нужен.

«Поднять `docker run -p 6379:6379 redis` и выдать порт в сеть» — это новый attack surface, не кэш-платформа. Образы часто слушают `*` и отключают protected mode «чтобы завелось».

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём Redis Community Edition 7.4.11**, не Redis Software (Enterprise), не Redis Cloud, не Redis Stack как отдельный бандл модулей, не Redis 8. Юристы **принимают RSALv2 или SSPLv1** для закрытого контура. Если нет — этот файл не является разрешением ставить 7.4; смотрят 7.2.16 (BSD, другой патч) или Valkey.
2. **Прод крутится в Kubernetes.** Инсталлятор — community operator или Helm StatefulSet с **официальным** образом `redis:7.4.11`. Это не эквивалент «Strimzi официально совместим». Перед продом — прогон именно 7.4.11.
3. **Три ЦОДа = три зоны отказа.** Если это три зала с общим питанием — stretch даёт ложное чувство безопасности.
4. **Stretch принимается только если** сеть 6379/16379/26379 достаточно быстрая и стабильная. Порога RTT у Redis **нет**. Пока RTT не измерен — гипотеза.
5. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. И Sentinel (3 процесса по ЦОДам, majority=2), и Cluster (3 master по ЦОДам, majority=2) два ЦОДа **не** переживают.
6. **Нагрузки нет** — поэтому **нет** цифры «N гигабайт maxmemory». Есть сигналы (`used_memory`, eviction, `rejected_connections`, replication lag, `blocked_clients`, CPU команды) и рычаги (RAM, master'ы Cluster, что кладём, TTL).
7. **Формального SLA / RPO / RTO нет.** Успешный `PING` и живая replica ≠ «ни один idem-ключ не потерян при failover».
8. **Корпоративный PKI есть или будет**, если репликация/клиенты между ЦОДами. Без TLS в проде между площадками — отдельное принятие риска ИБ, не дефолт этого файла.
9. **Идентификация сервисов** — отдельные ACL-пользователи, least privilege (кэш-сервис не делает `FLUSHALL`/`CONFIG`/`DEBUG`/`MODULE`/`EVAL`). Люди в прод-Redis — через jump host / operator, не общая учётка.
10. **Шифрование канала — TLS сборки Redis.** ГОСТ/СКЗИ не озвучены.
11. **Тестовый стенд изолирован.** На нём допустимы standalone без пароля на loopback. В прод это не копируем.
12. **Kafka, Camunda, озеро, интеграционное API** — клиенты 6379, не часть этого ПО. Контракт: ключи с префиксом сервиса, TTL, идемпотентность, Cluster hash tags если Cluster.
13. **Рабочий набор Redis — не терабайты эталона.** Эталон остаётся в озере. Иначе смета RAM не сходится с «огромный объём данных».
14. **Один логический Redis на среду**, не «каждый микросервис свой redis в углу» без причины. Несколько *выделенных* инстансов (кэш vs локи vs сессии) допустимы, если политики eviction/persistence разные — это уже несколько экземпляров, у каждого своя HA.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили StatefulSet и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT, jitter, потери на 6379/16379/26379 между ЦОДами** (p50/p95/p99, все пары) | Gossip и Sentinel ping живут этими каналами. Высокий/плавающий RTT → ложный failover, разъезд датасетов, отказ majority. Stretch станет источником аварий |
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Cluster bus — полный mesh. Нет pod-to-pod между ЦОДами → это **не** один Cluster, а несколько инстансов |
| **Что именно кладёте в Redis** (кэш UI? сессии? локи Camunda? идемпотентность 30+ интеграций? всё сразу?) | Разный `maxmemory-policy`, persistence, TTL, ACL. «Терабайты» без состава — не смета |
| **Размер рабочего набора** | Не влезает в RAM одной ноды с запасом на fork/репликацию → либо Cluster и шардирование, либо Redis вам не тот слой |
| **Нужна ли запись после падения 1 ЦОДа ценой возможной потери хвоста async** | `min-replicas-to-write`, `WAIT`, `cluster-require-full-coverage` — ручки доступность vs осторожность. Дефолты не совпадают с «работа беспрерывна» |
| **Клиенты умеют Sentinel / Cluster** | Иначе failover Redis «успешный», приложение пишет в труп |
| **152-ФЗ / срок хранения ПДн в кэше** | TTL, запрет класть полный паспорт в Redis «на всякий случай», шифрование томов |
| **Лицензия RSALv2/SSPL** | Без решения юристов установка 7.4 в контур может быть запрещена вне зависимости от HA |
| **Нужны ли модули JSON/Search** | Их нет в ванильном 7.4; это другой артефакт и другая атака/ops |
| **StorageClass и fork** | Медленный PVC → AOF everysec врёт по latency; огромный датасет → паузы BGSAVE. Redis «быстрый», пока диск и fork не напомнят |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **7.4.11** (тег образа, не `redis:7`). Юристы — лицензия.
2. Решить **роль данных** (кэш / сессии / локи) → из этого `maxmemory-policy` и persistence. Не наоборот.
3. Решить **топологию**: standalone / Sentinel / Cluster. Не «Cluster потому что звучит продово».
4. Выставить хостовые THP/overcommit **до** первого пода с большим датасетом.
5. Включить **ACL** (и TLS в проде) **до** боевых клиентов. Не оставлять пустой пароль и `protected-mode no` «как в примере».
6. Задать **`maxmemory`** с запасом под репликацию и fork. Без этого HA не спасает от OOM.
7. Включить метрики: `INFO`, `INFO replication`, `INFO memory`, `INFO commandstats`, replication offset, `master_link_status`, Sentinel `SENTINEL masters` / Cluster `CLUSTER INFO`.
8. Прогнать запись/чтение. Убедиться, что ключ **виден** и что падение одной ноды на проде оставляет *ту* семантику, на которую подписались (кэш можно потерять; лок/idem — нет).
9. Прогнать **контролируемый failover** (Sentinel failover / `CLUSTER FAILOVER` на replica). Без этого у вас нет HA, есть надежда.
10. Только потом — тонкий ACL, `WAIT` в критичных местах приложения, отдельные инстансы под разные политики.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики ставили ключи, смотрели TTL, подключали клиент из микросервиса/Camunda worker. **Не** цель: доказать отказ ЦОДа и ёмкость RAM.

Официальный минимальный путь:

```text
docker run -d --name redis-dev -p 6379:6379 redis:7.4.11
```

Проверка: `docker exec -it redis-dev redis-cli PING` → `PONG`.

На Kubernetes: один StatefulSet, 1 replica, маленький PVC или даже без persistence на сутки. Не копировать этот YAML в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число нод | 1 | Нет требования пережить выкат |
| Sentinel / Cluster | нет | Иначе команда утонет в MOVED/Sentinel раньше, чем в ключах |
| Пароль | можно без, **только loopback / изолированная сеть** | Protected mode на дефолтном бинарнике спасает от случайного bind-все; в Docker это часто уже обойдено — сеть всё равно закрыть |
| TLS | нет | Иначе PKI раньше продукта |
| maxmemory | 256–512 МБ | Не цель — ёмкость |
| Persistence | AOF можно выключить | На тесте потеря ключей при рестарте терпима; на препроде включить то, что будет в проде |
| Мониторинг | `PING` + логи | Нет нагрузки |

#### Чего на тесте **не** стоит упрощать

- Версия **7.4.11** (не «какой redis есть у devops»).
- **Префиксы ключей** и TTL в клиентском коде. Иначе в проде «кэш навсегда» съест RAM.
- Если цель прода — Cluster: на препроде нужен **маленький Cluster** (3 master можно без replica). Hash tags и запрет `SELECT 1` надо поймать до боя.
- Если цель прода — Sentinel: клиентская библиотека с Sentinel **на препроде**, не «на проде включим».
- Понимание: успешный `SET/GET` на одном процессе **не** доказывает failover.

#### Сильные стороны такой схемы

- Поднимается за минуты, совпадает с официальным Docker-образом.
- Дешево показывает паттерн ключей интеграций/Camunda.
- Standalone официально нормален для development.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет 16379 между площадками, нет поведения eviction под давлением.
- Docker `-p 6379:6379` на рабочей станции разработчика легко оказывается «торчит в Wi-Fi».
- Привычка без ACL уедет в прод.

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (Sentinel 3 или Cluster 3+3, ACL, `maxmemory`, persistence как в проде), даже без боевого трафика.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «гигабайт под терабайты озера» **нет** — нагрузки нет, и озеро в Redis класть не предполагаем. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Сначала развилка **A/B по сети**, затем развилка **Sentinel vs Cluster** по данным.

**Вариант A — stretch: один логический Redis на 3 ЦОДа.**

Имеет смысл, если mesh 6379/16379 (Cluster) или 26379+репликация (Sentinel) — метро-класс.

**Вариант B — мозг в одном ЦОДе** (все master/Sentinel quorum живут в ЦОД-1, клиенты с ЦОД-2/3 ходят по городу).

Проще кворум. Падение ЦОД-1 = нет Redis ни у кого. Спасает заранее прогнанный restore RDB/AOF на другой площадке (RTO замерить) или холодная replica **вне** кворума (это уже ручной DR, не автоfailover).

**Вариант C — два/три независимых Redis + прогрев кэша с озера.**

Нет общего кворума. После падения площадки кэш **холодный**. Для SoT это нормально (истина в озере). Для сессий — пользователи разлогинятся. Для идемпотентности внешних вызовов — риск повторного запроса в ведомство, пока ключ не восстановится.

**Пока топология K8s и RTT не зафиксированы, нельзя честно выбрать A.** Дальше A как целевой «3 ЦОДа в одном городе»; B/C — запасные.

##### Сильные / слабые стороны stretch (A)

| Сильное | Слабое |
|---|---|
| Клиентам один endpoint/набор Sentinel/карта слотов | Латентность репликации = RTT; запись с `WAIT 1` привязана к чужому ЦОДу |
| Падение 1 ЦОДа может обойтись без «переключения на другой Redis» | Сетевой шторм выглядит как деградация Redis |
| Согласовано с идеей 3 зон | Не переживает 2 ЦОДа; ложный failover при малом timeout |
| | Ошибка `FLUSHALL`/ACL сразу везде |

##### Сильные / слабые стороны «мозг в одном ЦОДе» (B)

| Сильное | Слабое |
|---|---|
| Gossip/Sentinel не зависят от межЦОДового RTT на кворуме | Падение этого ЦОДа = простой Redis на всех трёх |
| Проще отлаживать failover внутри площадки | Нужен явный DR: restore или прогрев с озера **с прогоном по времени** |
| | Клиентский путь 6379 через город — уже ваша сеть |

##### Слабое место любого stretch без замера RTT

Документация требует, чтобы `NODE_TIMEOUT` был велик **по сравнению с RTT**, и не даёт порога. Утверждение «три ЦОДа в одном городе, значит можно размазать Cluster» — **непроверенное**. Мерить те порты, которыми Redis реально ходит, не ping ICMP «на всякий случай».

---

#### Выбор Sentinel vs Cluster (внутри A или B)

| Вопрос | Sentinel | Cluster |
|---|---|---|
| Датасет влезает в RAM **одного** master с запасом? | Да — типичный выбор | Можно, но избыточен |
| Нужен горизонтальный write/RAM больше одной машины? | Нет, только вертикаль | Да, слоты |
| Мультиключ / транзакции / `SELECT` db≠0 | Работает на одном master | Только один слот / только DB 0 |
| Клиенты | Sentinel-aware | Cluster-aware (MOVED) |
| Операционка | Проще логически, Docker+NAT ядовит | Сложнее: слоты, reshard, bus 16379 |
| Масштаб «ещё QPS записи в один горячий ключ» | Не решает | Не решает |

Для кэша/идемпотентности/сессий интеграционного слоя **часто достаточно Sentinel**. Cluster берут, когда **доказали**, что один master упирается в CPU или `maxmemory`, и ключи хорошо шардируются.

Не включать Cluster «чтобы было как Kafka с партициями». У Kafka партиция — единица порядка событий. У Redis слот — единица ключа.

---

#### Если Sentinel (рекомендуемый старт, пока нет доказательства «нужен Cluster»)

Минимум для цели «пережить 1 ЦОД»:

- **3 Sentinel**, по одному в ЦОД. Quorum **2**.
- **1 master + минимум 2 replica**, реплики в **других** ЦОДах относительно master (чтобы падение ЦОДа master не убило все копии). Итого ≥ 3 процесса данных.
- Клиенты знают **все три** адреса Sentinel, не один.
- `down-after-milliseconds`: больше, чем ваш нормальный GC/сетевой блеск, меньше, чем терпимый RTO. Цифру с потолка не ставить — калибровать после замера RTT. Пример из доки `60000` — это учебный, не ваш SLA.
- Persistence **включена на master и репликах** (официальный совет). Авторестарт пустого master без диска — запрещённый паттерн.
- `min-replicas-to-write 1` и разумный `min-replicas-max-lag` — если лучше отказать в записи, чем писать в одиночку. Это **снижает доступность** при падении реплик/ЦОДа: сознательный выбор. Дефолт в конфиге — не требовать реплик.
- Приложение на критичных ключах (идемпотентность внешнего вызова) — рассмотреть `WAIT 1` с таймаутом; понимать, что это не сильная consistency.

Раскладка пример:

```
ЦОД1: Redis (может быть master), Sentinel
ЦОД2: Redis replica,  Sentinel
ЦОД3: Redis replica,  Sentinel
```

После failover master «переедет». Anti-affinity должна позволять master быть в любом ЦОДе, не «всегда ЦОД1 в голове у сети».

##### Сильные / слабые стороны Sentinel на 3 ЦОДах

| Сильное | Слабое |
|---|---|
| Официальный HA без шардирования; 3 Sentinel как в доке | Один writer — потолок RAM/CPU |
| Клиентам понятная модель «спроси Sentinel» | Async: потеря хвоста при failover |
| Падение 1 ЦОДа при quorum=2 переживаемо | Падение 2 ЦОДов — нет majority Sentinel |
| | Клиент без Sentinel-поддержки = простой после смены master |
| | Docker/NAT/port-map официально ломает discovery |

---

#### Если Cluster (когда один master доказанно мал)

Минимум для цели «пережить 1 ЦОД»:

- **3 master + 3 replica** (каждый master имеет реплику в **другом** ЦОДе):

```
ЦОД1: Master A, Replica(C)
ЦОД2: Master B, Replica(A)
ЦОД3: Master C, Replica(B)
```

- `cluster-enabled yes`, уникальный `cluster-config-file` на PVC (nodes.conf). Без постоянного nodes.conf после рестарта пода Cluster «забывает себя».
- `cluster-node-timeout` **одинаковый** на всех; **>> RTT** (дефолт 15000 мс — только старт, не догма). Слишком маленький на городской сети с потерями = ложные failover.
- Replica migration: `cluster-migration-barrier` (дефолтный смысл — не оставлять master совсем без реплик, отдав последнюю). На ровно 1 реплике на master миграция почти не из чего брать — для устойчивости к *двум разнесённым по времени* отказам нод спека предлагает «лишние» реплики. Это RAM сверху.
- `cluster-require-full-coverage`: для «система должна работать» часто ставят `no`, иначе дырка слотов после аварии глушит **весь** кластер. Цена: часть ключей недоступна, приложение должно это пережить. Для кэша обычно приемлемо; для «единственная копия сессии» — нет.
- Клиенты cluster-aware. Hash tags для ключей, которые надо крутить атомарно.
- Reshard при добавлении master — **плановая** операция (`--cluster reshard` / add-node). Новые ноды без reshard стоят пустые (как брокеры Kafka без перекладки партиций).
- Добавлять master **пачками**, чтобы слоты и зоны не перекосились. Точной «пачки по 3» в доке как у Kafka rack нет — но физика зон та же: не складывать все master в один ЦОД.

TLS на cluster bus (`tls-cluster`) в проде между ЦОДами — иначе gossip и failover-команды открытым текстом.

##### Сильные / слабые стороны Cluster на 3 ЦОДах

| Сильное | Слабое |
|---|---|
| Горизонталь RAM и write при равномерных ключах | Полный mesh 16379; чувствителен к RTT |
| Автоfailover слотов при majority | 2 ЦОДа из 3 = стоп; hot key не шардируется |
| Спека прямо описывает окна потери writes | CROSSSLOT ломает наивный код с `MULTI` на два ключа |
| | `SELECT` только 0; операционка reshard |
| | Нет официального OSS-оператора с матрицей совместимости |

#### Persistence, память, производительность (общее для Sentinel и Cluster)

| Параметр | Прод-правило | Зачем |
|---|---|---|
| `maxmemory` | Задан, **ниже** лимита cgroup/RAM, запас на replica output buffer и fork | Иначе OOM killer = «необъяснимый» failover |
| `maxmemory-policy` | Кэш: `allkeys-lru` или `allkeys-lfu`. Сессии/идемпотентность, которые нельзя выкинуть: `noeviction` + алерт на `used_memory` + TTL | Смешать на одном инстансе «кэш можно дропнуть» и «лок нельзя» — слабое место; лучше **два инстанса** |
| `appendonly` | `yes` если потеря секунд при рестарте ноды неприемлема | Дефолт `no` |
| `appendfsync` | `everysec` как компромисс из доки. `always` — очень медленно, очень безопасно | `no` — в руках kernel, до ~30 с по формулировке доки |
| RDB save points | Оставить как бэкап/быстрый старт даже при AOF | RDB удобнее увозить в другой ЦОД/S3, чем сырой AOF |
| Бэкап | Периодически копировать RDB **вне** трёх нод; проверять **restore**, не только наличие файла | Реплика не бэкап |
| `replica-read-only` | `yes` (дефолт) | Случайная запись в реплику |
| Hot keys / big keys | Ловить `redis-cli --bigkeys` / `--memkeys` / `--keystats` (7.4) на стенде с прод-подобными ключами | Один огромный hash убивает latency BGSAVE и сеть репликации |

Масштабирование под нагрузку, когда цифры появятся:

1. Замерить рабочий набор и hit/miss (если кэш).
2. Замерить ops/s, размер значения, CPU `INFO commandstats`, p99 latency.
3. Если CPU упёрся в один поток и ключи разные — планировать Cluster (или второй инстанс по домену ключей).
4. Если RAM упёрлась — сначала TTL/eviction/не класть эталон, потом RAM, потом шарды.
5. `io-threads` включать по факту сетевого saturating, не «на всякий случай».

#### Безопасность прода

Три слоя, все три:

1. **Сеть** — 6379 только приложениям; 16379 только нодам Cluster; 26379 только Sentinel+клиентам Sentinel. NetworkPolicy. Не LoadBalancer в интернет.
2. **Аутентификация** — ACL, не аноним. Не общий пароль `requirepass` на всех сервисах.
3. **Авторизация** — командные категории: приложению кэша не нужны `FLUSHALL`, `KEYS`, `DEBUG`, `CONFIG`, `MODULE`, `EVAL`.

| Слой | Правило |
|---|---|
| Protected mode | Не костыль прода. В проде: явный `bind`, ACL, сеть. `protected-mode no` + bind `*` + без пароля = инцидент |
| TLS | Клиенты и репликация между ЦОДами. Cluster bus — `tls-cluster`. Без TLS AUTH не спасает от сниффера (формулировка security-гайда) |
| ACL | Файл пользователей не в Git; Secret/Vault. Default user в 7.x лучше **выключить** или оставить без опасных команд |
| `rename-command` | Не строить на этом процесс: deprecated в пользу ACL |
| Процесс | Пользователь `redis`, не root |
| At-rest | Шифрование PVC/CSI. В Community нет «галочки encrypt dataset» как замены диску |
| Lua | Боевым ролям запретить, пока нет явной нужды. Патчить 7.4.x оперативно: линия часто закрывает RCE в скриптах |
| Аудит | Логи подключений + отдельный сбор; `hide-user-data-from-log` (7.4) если в логах могут оказаться значения ключей |

##### Сильные / слабые стороны (сеть + ACL + TLS)

| Сильное | Слабое |
|---|---|
| Штатные средства 7.4, без отдельной лицензии Enterprise | ACL-ошибка = «сервис не пишет»; нужен процесс выдачи |
| TLS закрывает репликацию между ЦОДами | TLS бьёт по CPU; сертификаты на каждой ноде и в клиентах |
| Least privilege на `FLUSHALL` спасает от одного скомпрометированного сервиса | Модель «доверенная сеть» всё равно нужна: Redis не WAF |
| | Не ГОСТ; модули/.so — отдельная поверхность |

Если появится корпоративный IdP — Redis Community **не** становится OIDC-сервером. Людей в Redis не пускают «логином как в Dashboards OpenSearch»; пускают сервисы по ACL, людей — через контролируемый jump.

#### Kubernetes-специфика прода

- StatefulSet / CR оператора, **не** Deployment с ephemeral IP как у единственного клиента без Sentinel/Cluster discovery.
- PVC на данные; `emptyDir` для AOF/RDB в проде = каждый рестарт пода как cold start или как пустой master (опасный паттерн репликации).
- Topology spread / anti-affinity: Sentinel не в одном ЦОДе; Cluster master+его replica не на одной ноде и не в одной зоне.
- PDB: не снять сразу majority Sentinel или два master Cluster.
- Ресурсы: request/limit памяти **выше** `maxmemory`. CPU limit слишком жёсткий + throttle = ложный `down-after` / `NODE_TIMEOUT`.
- Не ставить Redis на overlay с большим jitter без замера. Если pod-сеть между ЦОДами хуже VM — ноды иногда лучше на hostNetwork / вне K8s. Решение по замерам.
- Готовые чарты Bitnami: проверять **лицензию образов** и тег. Не тащить `latest`. Community-оператор: пинить версию CRD, читать changelog на failover/PVC.
- `CLUSTER FAILOVER` / Sentinel failover должны переживать rolling upgrade. Drain без failover = простой записи.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами на 6379/16379/26379. Решение A vs B vs C.
2. Зафиксировать состав ключей и политику eviction/TTL. Юристы — лицензия 7.4.
3. Выбрать Sentinel или Cluster. Выделить ноды, PVC, зоны.
4. Поставить 7.4.11, ACL и `maxmemory` **до** боевых клиентов.
5. Включить persistence, снять тестовый RDB, прогнать restore на другой namespace.
6. Подключить клиент **в том режиме**, который выбран (Sentinel/Cluster), с ретраями на failover.
7. Убить под master, убедиться что приложение продолжает (или деградирует так, как задумано для кэша).
8. Нагрузить синтетикой, снять latency/CPU/eviction/lag. По результату — RAM и число master.
9. Прогон «ЦОД недоступен» на препроде: выключить зону, проверить кворум, запись, что идемпотентность/сессии делают то, что обещали бизнесу.
10. Только потом — реальные ключи интеграционного API и Camunda.

Без пункта 9 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Sentinel: 3 Sentinel в 3 зонах, ≥2 replica в чужих зонах **или** Cluster: 3 master + replica в чужих зонах; цель — 1 ЦОД; persistence на master и replica; прогнанный failover и restore |
| Производительность / масштаб | Не требуется | `maxmemory` с запасом; политика eviction по роли данных; SSD под AOF/RDB; горизонталь только Cluster-слотами или отдельным инстансом; не класть эталон |
| Безопасность | Isolated сеть; не торчать 6379 в LAN офиса | ACL least privilege; нет default-открытого 6379; TLS на репликации между ЦОДами; NetworkPolicy; не root; Lua ограничен |

**Не готов к проду**, если: один процесс без Sentinel/Cluster и его выдают за HA; `maxmemory` не задан; persistence выключена на master с авторестартом; `protected-mode no` и bind все без ACL; клиенты не умеют failover; Cluster без PVC на `nodes.conf`; все Sentinel в одном ЦОДе; RTT неизвестен, а схема уже stretch; Redis назначен SoT клиентских данных; образ `redis:latest`; 7.4 поставлен без решения по RSALv2/SSPL.
