# OpenStack Swift 2.37.3 — развёртывание и настройка (S3-совместимый API)

Версия ПО: **Swift 2.37.3**, серия OpenStack **2026.1 (Gazpacho)**.  
Проверено **26 августа 2026**: в [релиз-нотах серии 2026.1](https://docs.openstack.org/releasenotes/swift/2026.1.html) это последний номер линейки. **2.38.x** в [current/unreleased](https://docs.openstack.org/releasenotes/swift/current.html) — это ещё не стабильная серия, в прод не берём.

Документация: https://docs.openstack.org/swift/2026.1/  
Архитектура: https://docs.openstack.org/swift/2026.1/overview_architecture.html  
Развёртывание: https://docs.openstack.org/swift/2026.1/deployment_guide.html  
S3 API (middleware `s3api`): https://docs.openstack.org/swift/2026.1/middleware.html  
Матрица совместимости S3: https://docs.openstack.org/swift/2026.1/s3_compat.html  

Лицензия исходников Swift — **Apache 2.0**. Отдельного license-server нет.

Этот текст — не мануал «скопируй ring-builder и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Swift **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API» как отдельный пункт, но объектное хранилище почти наверняка появится: вложения интеграций, снимки, бэкапы индексов, файлы процессов. Ниже — как поставить **кластер Swift с включённым S3 API** на ту же инфраструктуру (Kubernetes заявлен, 3 ЦОДа). Это **не** замена Kafka, **не** процессный движок и **не** СУБД для эталона клиентских карточек.

Отдельно: в документе по GeoData инсталлятор вендора фиксирует **Swift 2.29.2** и пример колец в **одном** `region`/`zone`. Этот файл — про **платформенный** Swift 2.37.3 как S3-хранилище. Склеивать его с GeoData «потому что оба Swift» без письма вендора нельзя.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Объектное хранилище** | Кладёте файл (объект) по имени в «папку» (контейнер/бакет). Нет SQL, нет строк и индексов «как в Postgres». Читаете и пишете целиком (или кусками multipart). |
| **Account** | Верхний уровень Swift API: пространство имён контейнеров. В связке с Keystone это обычно проект/tenant. |
| **Container** | Аналог S3 **bucket**: пространство имён объектов внутри account. Список объектов живёт **отдельно** от самих файлов (SQLite на container-серверах). |
| **Object** | Сам блоб + метаданные. На диске — файл; метаданные — в **xattr** файловой системы. |
| **Swift API** | Родной REST: `/v1/{account}/{container}/{object}`. Это не S3. |
| **s3api** | Middleware на proxy: принимает запросы «как Amazon S3» и переводит их во внутренности Swift. Это **эмуляция**, не AWS. |
| **s3token** | Middleware: проверяет S3-подпись (access key / secret) через **Keystone**. Нужен, если S3 + Keystone. |
| **tempauth** | Встроенная «учётка в конфиге» для лаборатории (SAIO). Пароли в `proxy-server.conf`. Для прода **не** identity. |
| **Keystone** | Identity OpenStack: пользователи, проекты, роли, каталог сервисов. Для прода S3 обычно берут EC2-credentials из Keystone. |
| **Proxy server** | Единственная «дверь» для клиентов. Смотрит в **ring**, куда послать запрос, стримит данные, не складывает объект целиком на диск proxy (не spool). Stateless: несколько proxy за балансировщиком — штатный HA. |
| **Object / Container / Account server** | Три внутренних сервиса хранения. Клиенту они **не** нужны; proxy ходит к ним сам. |
| **Ring (кольцо)** | Словарь «имя сущности → на каких дисках лежат копии». Отдельные кольца: account, container, и **по одному object-кольцу на storage policy**. Без одинаковых `.ring.gz` на всех нодах кластер врёт. |
| **`.builder`** | Исходник кольца. Его **бэкапят**. Потеряли builder — следующее изменение топологии станет лотереей. |
| **Partition (в кольце)** | Не раздел HDD. Виртуальный кусок пространства имён. Replica раскладываются по партициям. Рекомендация вендора: **≥ 100 партиций на диск**, число партиций = 2^part_power. |
| **Replica** | Сколько копий каждой партиции. В Deployment Guide: **рекомендуется 3** — «это единственное значение, которое тестировали». 3 копии ≈ диск ×3 относительно «один экземпляр файла». |
| **Handoff** | Запасной диск/узел из кольца, куда proxy отправит запись, если primary недоступен. Потом replicator догонит «правильное» место. |
| **Region / Zone** | Иерархия доменов отказа в кольце: region → zone → сервер → диск. Region — обычно «площадка с другой задержкой»; zone — изоляция внутри (зал, ряд, питание, сеть). Оба — **положительные целые**, смысл задаёте вы. |
| **Storage policy** | Именованный класс хранения контейнера (например «3 копии» и отдельно «erasure coding»). Политика задаётся **при создании** контейнера и на жизни контейнера не меняется. |
| **Erasure coding (EC)** | Вместо N полных копий — кодирование с избыточностью (меньше места, больше CPU на proxy при encode/decode). Восстановление — **reconstructor**, не тот же путь, что rsync-репликатор. |
| **Eventual consistency** | Объект после успешного PUT обычно уже читается по имени. **Список** контейнера/аккаунта может отстать: обновление listing могло уйти в очередь updater. |
| **Last write wins** | Конфликт версий объекта на диске решается **временной меткой**. Удаление — это тоже версия (tombstone, файл `.ts`). |
| **Replicator** | Фоновый процесс: догоняет копии (часто через **rsync** для объектов), разносит tombstone. |
| **Updater** | Догоняет отложенные обновления listing контейнера/аккаунта. Окно рассинхрона listing ≈ как часто он бегает и насколько бэкенд был занят. |
| **Auditor** | Ползёт по локальным дискам, ищет битый файл (bit rot), кладёт в quarantine; replicator подтянет живую копию. |
| **SAIO** | Swift All In One: всё на одной машине, официальный путь **разработки/теста**, не прод. |
| **min_part_hours** | Сколько часов нельзя повторно двигать одну и ту же партицию при rebalance. В гайде как ориентир — **24**. |
| **Weight** | Вес диска в кольце (доля партиций). Ориентир гайда: **100.0 × ТБ** ёмкости. |
| **write_affinity / read_affinity** | «Пиши/читай сначала рядом» (свой region/zone). Официальный механизм **global cluster**. Письмо локально ускоряет PUT, но **сразу после записи** копии могут ещё не лежать в чужом ЦОДе. |
| **SLO / DLO** | Большие объекты кусками. По умолчанию один PUT ≤ **5 ГБ**; больше — сегменты + манифест. SLO не зависит от eventual listing; DLO — зависит. Для полной S3-совместимости multipart в pipeline должен быть **slo**. |
| **xattr** | Расширенные атрибуты файла в ФС. Без них object-server не хранит метаданные штатно. Поэтому диск Swift — не «любой NFS на скорую руку». |
| **Memcached** | Кэш **токенов и фактов «контейнер существует»**, не кэш тел объектов. В гайде: обычно на proxy; в `memcache_servers` перечисляют **все** инстансы. |
| ** Barbican / keymaster** | Ключи шифрования at-rest: либо секрет в конфиге (`keymaster`), либо внешний KMS (`kms_keymaster` / `kmip_keymaster`). |
| **swift-recon** | Снятие телеметрии с нод: кольца, время репликации, quarantine, async pending. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. Реплики Swift — не бэкап от «rm контейнера» и не бэкап `.builder`. |

## Основные элементы системы и зависимости

### Что входит в Swift 2.37.3 (это одно ПО из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Proxy** | Публичный API (Swift + при включении s3api — S3), маршрутизация по кольцу, TLS-терминация если не вынесена, EC encode/decode | Горизонтально: больше stateless proxy за LB. Упирается в CPU и сеть, не в диск объектов |
| **Object server** | Файлы на локальных дисках | Горизонтально: диски и ноды в object-кольце + rebalance |
| **Container server** | Listing объектов, счётчики контейнера (SQLite) | Горизонтально; при миллионах объектов в одном контейнере — **sharding** (отдельная операторская дисциплина) |
| **Account server** | Listing контейнеров | Обычно меньше нагрузка, чем object; при необходимости — свои более быстрые диски |
| **Replicator / updater / auditor** (+ reconstructor для EC) | Сходимость копий, listing, целостность | Не «ещё один API». Это фон: ему нужны сеть репликации, I/O и время |
| **Кольца** | Карта размещения | Не масштабируются «подами». Меняются осознанным `rebalance` и выкладкой `.ring.gz` **на все** ноды |

Рядом, но это **другое ПО**: Keystone (прод-identity), Memcached, rsync, балансировщик перед proxy (у вас есть отдельный документ по HAProxy), PKI, опционально Barbican/KMIP, StatsD/Prometheus-exporter как вы решите снимать метрики.

### Официальные порты (менять можно, это должен знать firewall)

В sample-конфигах проекта и в примерах Deployment Guide:

| Порт | Назначение |
|---|---|
| **8080/TCP** | Proxy: клиентский Swift API и (если включили) S3 API |
| **6200/TCP** | Object server (в примере «старого» кольца все диски ноды на одном порту; вариант `servers_per_port` — **свой порт на диск**) |
| **6201/TCP** | Container server |
| **6202/TCP** | Account server |
| **873/TCP** | rsync (репликация объектов; модули задаются в `rsyncd.conf`) |
| **11211/TCP** | Memcached (не Swift, но proxy без него в типичной схеме не аутентифицирует) |

SAIO на одной машине поднимает **несколько** object/container/account на портах вроде 6210/6220/… — это лабораторная схема «много процессов на localhost», не прод-номера.

Клиентам открывают **только proxy** (лучше 443 на LB → 8080). Порты 6200–6202 и rsync — внутренняя сеть хранения. Выдать object-server в интернет = обойти auth proxy.

### Чего в Swift нет (частая путаница)

| Нужно системе | Это не Swift | Зачем помнить |
|---|---|---|
| «Полный AWS S3» | Матрица `s3_compat`: Core PUT/GET/DELETE, multipart, ACL, versioning — **да**. **Нет:** bucket lifecycle (как в AWS), bucket policy, object tagging, notifications, website hosting, billing, inventory, accelerate | Клиенты с Lifecycle-правилами, тегами и bucket policy **сломаются**. Срок жизни объектов — **нативный** object expiration Swift, не S3 Lifecycle API |
| Транзакционный эталон клиентских карточек | PostgreSQL / иное OLTP | Eventual listing, last-write-wins, нет JOIN и ACID на «пачку объектов» |
| Шина событий | Kafka | Swift не гарантирует доставку «всем консьюмерам». Можно положить блоб и **отдельно** опубликовать факт в Kafka |
| Поиск по содержимому озера | OpenSearch / ClickHouse | Swift отдаёт объект по ключу. Listing контейнера — не аналитика |
| Camunda / процессы | Process engine | Swift хранит вложения процесса, не исполняет BPMN |
| Интеграции с госслужбами | Ваше интеграционное API | Сюда складывают вложения/архивы ответов, не ходят в СМЭВ |
| Кворум метаданных как у etcd/Kafka | Нет Raft на объекты | Отказ — это «хватит ли копий и жив ли proxy», не «выбрали ли leader кольца» |
| RAID 5/6 «чтобы диск не умер» | Вендор: RAID **не требуется и не рекомендуется**; паттерн I/O для RAID 5/6 — худший случай | Надёжность — replica в кольце + auditor, не RAID на том же диске |
| Официальный оператор Swift «как у OpenSearch» | У проекта Swift его нет | OpenStack-Helm — **чарт OpenStack**, не ядро Swift. Kolla-Ansible **убрал** роль Swift с 2025.1 |
| Порог RTT между ЦОДами | Нет | Default задуман как **один region** с низкой задержкой. Multi-region — отдельная глава Global Clusters |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS на LB/proxy — не криптография по требованиям КИИ, если ИБ их выдвинет |
| Замена бэкапа тремя копиями | Нет | Replica спасает диск/ноду/зону. Не спасает `DELETE`, кривое кольцо, украденный ключ шифрования, гибель всех трёх ЦОДов |

### Зависимости окружения (обязательны)

- **Linux** с ФС, у которой работают **xattr**. Практический стандарт операторов и SAIO — **XFS**. В SAIO прямо: Swift требует место на XFS, чтобы хранить данные и гонять тесты.
- **Локальные диски** на object/container/account. Deployment Guide: точки монтирования `/srv/node/…` от **root** (`root:root 755`), иначе при размонтировании диска rsync может начать писать в корневой том.
- **rsync** между storage-нодами. Без него object-replicator не сходится штатным путём.
- **Memcached**, доступный всем proxy; в конфиге — полный список. Тела объектов **не** кэшируются. Для tempauth токен **живёт в memcached**: упал memcached — «не пускает». Для Keystone промах кэша обычно означает повторный поход в Keystone (нагрузка на identity), а не мгновенную смерть кластера.
- **Одинаковые кольца** (`*.ring.gz`) на proxy и storage. Расхождение = «пишу не туда» / 404 на живых данных.
- **Сеть минимум двух смыслов:** клиентская до proxy; внутренняя storage (proxy→620x) и replication (rsync). Их смешивать с клиентской — дыра.
- **Identity для прода:** Keystone + `keystoneauth` + для S3 ещё `s3token` (и EC2-credentials). tempauth — стенд.
- **Балансировщик** перед несколькими proxy. Один proxy = SPOF API, даже если диски в трёх ЦОДах живы.
- **Python 3.** В 2.37.1 явно добавлена поддержка **Python 3.14 (GIL enabled)**. Минимальную minor «навсегда» этим документом не фиксируем — смотреть требования пакета/дистрибутива, которым ставите 2.37.3.
- **Kubernetes (у вас заявлен):** официальный Deployment Guide описывает **сервисы на серверах с дисками**, не «StatefulSet из магазина». Чарты OpenStack-Helm для Swift существуют, но матрица проекта на 2026.1: Kubernetes **≥ 1.33 и ≤ 1.35**. У вас в платформе зафиксирован **Kubernetes 1.36.4** — это **не** доказанная комбинация. Кольцо содержит **IP:порт/имя диска**: смена IP пода без обновления кольца ломает кластер.

### Как Swift стыкуется с вашей архитектурой

```
Микросервисы, Camunda, интеграционное API
        │  PUT/GET объекта (лучше: S3 SDK только после проверки матрицы)
        ▼
   HAProxy / Ingress  ──TLS──►  Swift proxy × N   (8080 / 443)
        │                         │  s3api + Keystone (прод)
        │                         ▼
        │                    rings: account / container / object
        │                         │
        │            ┌────────────┼────────────┐
        │            ▼            ▼            ▼
        │      account       container      object
        │      servers       servers        servers   ← диски XFS, rsync
        │
   Kafka  ── по-прежнему шина фактов («файл записан», не сам PDF)

Озеро эталона (карточки клиентов) ──остаётся в СУБД/витрине──►
        в Swift — вложения, выгрузки, снимки, «сырой» архив интеграций
```

Честные роли:

1. **Объектный слой озера** — файлы, выгрузки, вложения ответов госслужб, пакеты, которые жалко держать в Postgres.
2. **Бэкенд для snapshot** других систем (например репозиторий снимков OpenSearch) — если решите, что S3-совместимая точка — этот кластер, и проверите диалект s3api.
3. **Хранилище документов процессов** — если Camunda/сервисы кладут файлы по ключу.

Нечестная роль: «положим всех клиентов JSON-файлами в бакет — это и есть SoT». Listing отстанет, overwrite без транзакции, поиск «по ИНН» вы будете строить **рядом**, не внутри Swift.

## Краткие вводные

### Зачем вам Swift в этой архитектуре

Нужно куда-то класть **большие и долгоживущие блобы** при «терабайтах» и 30+ интеграциях, не раздувая СУБД и не делая Kafka диском. Swift для этого и писался: много дешёвых дисков, 3 копии, переживание отказа диска/ноды за счёт кольца, горизонтальный рост добавлением устройств.

S3 API нужен, потому что экосистема клиентов (AWS SDK, многие бэкапы, часть Java/Python библиотек) говорит на S3. Включаете `s3api` на **том же** proxy. Это не второй кластер.

### Как устроена отказоустойчивость (идея, не магия)

Это **несколько копий в кольце** плюс **несколько stateless proxy**, плюс фоновые replicator/auditor. Путать SAIO «на одной VM» с HA — главная ошибка.

**1) Данные (replica + zone/region)**

| Что падает | Что происходит |
|---|---|
| Один диск при 3 replica, копии на разных устройствах | Чтение с другой копии; replicator/auditor лечит |
| Одна storage-нода, replica разложены по нодам | Тот же принцип. Proxy при PUT идёт на handoff, если primary мёртв |
| Один ЦОД, если **каждая replica партиции в своём ЦОДе** (zone или region = ЦОД, replica=3) | Остаются 2 копии. Чтение живо. Запись: proxy должен набрать успешные записи на живых копиях/handoff |
| Один ЦОД, если две из трёх копий случайно в нём (зоны нарезали «по стойкам», а не по ЦОДам) | Площадка уносит **большинство** копий части данных. Это ошибка карты кольца, не «баг Swift» |
| Все proxy в одном ЦОДе | Диски в других ЦОДах есть, **API нет** |
| Нет бэкапа `.builder` / колец, кольцо пересобрали «с нуля» | Карта мира уничтожена. Файлы на дисках могут остаться, кластер их не найдёт как раньше |
| `DELETE` контейнера / украли ключ S3 | Три копии послушно удалят. Replica ≠ backup |

Deployment Guide: replica **3** — единственное **протестированное** значение. Меньше 3 на проде = вы сами стали испытательным стендом проекта.

Про «кворум записи»: архитектурный обзор описывает, что при недоступности сервера PUT уходит на **handoff**, а не что «etcd выбрал leader». В коде proxy успех клиенту завязан на **большинство** успешных бэкенд-записей (`quorum_size` = replica//2+1, для 3 это **2**). Это нужно понимать как модель API, но **цифру 2 из 3 вендор в Deployment Guide отдельной главой не печает** — печает «ставьте 3 replica».

**2) Proxy**

Падение **одного** proxy при двух и более за LB — клиенты живы. Падение **всех** proxy — кластер глухой, диски целы. Proxy не хранит объекты, но на нём pipeline (auth, s3api, encryption): без него нет входа.

**3) Memcached / Keystone**

Умерли все memcached при **tempauth** — токены не проверить. Умер Keystone при keystoneauth — новые сессии и S3-подпись через s3token не пройти. Это SPOF **доступа**, не SPOF байт на диске.

**4) Репликация между ЦОДами**

Без `write_affinity` PUT идёт к тем устройствам, которые кольцо назвало primary — при 3 ЦОДах как 3 zone/region это **синхронно через город**. Латентность PUT ≈ сеть до чужого ЦОДа.

С `write_affinity` (глава [Global Clusters](https://docs.openstack.org/swift/2026.1/overview_global_cluster.html)): сначала кладут копии **рядом**, replicator развозит «по домам». Быстрее запись, **хуже durabilty в окне до репликации**. Документация прямо: имеет смысл, если **не читаете объект сразу после записи в другом регионе**; типичный пример — бэкапы. Если микросервис в ЦОДе B сразу GET того, что PUT в ЦОДе A — affinity вам навредит (404/WAN GET, пока replicator не догнал). Также: если пишут в один регион быстрее, чем replicator вывозит, распределение портится; тогда affinity **выключают**.

### Как устроено масштабирование

Несколько независимых осей:

1. **Больше гигабайт** → больше **дисков** в object-кольце, вес пропорционален ТБ, затем `rebalance`. Не «увеличить PVC одного пода».
2. **Больше запросов API** → больше **proxy** (CPU/сеть). SSL на proxy ещё дороже CPU — часто TLS снимают на LB.
3. **Больше мелких файлов / тяжёлые listing** → контейнеры, sharding, лимиты listing; не надеяться что object-нода «как диск для Postgres».
4. **Холодный архив дешевле по месту** → вторая **storage policy** с EC, не ломая default 3×. Политика навешивается на **новый** контейнер.
5. **Один объект > 5 ГБ** (дефолт) → SLO/multipart, не «подкрутили max_file_size на терабайт и забыли».

«Терабайты в озере» сами Swift не наполняют. Наполняет то, что вы **решите туда писать**, ×3 при трёх копиях, плюс запас под rebalance (нельзя забивать диски вплотную — некуда двигать партиции).

Ориентиры, которые **есть** у проекта, и которые **нельзя** принять за смету вашего прода:

- ≥ 100 партиций на диск; part_power — степень двойки от «макс. дисков × 100».
- replica = 3 (протестировано).
- «Начните с минимум 5 zone»; можно меньше, но их тесты на отказах лучше с пяти. Это про **изоляцию внутри region**, не приказ «нарежьте 5 ЦОДов».
- `min_part_hours = 24` как пример «хорошего значения».
- Один PUT по умолчанию до 5 ГБ.

### Безопасность самого Swift

Компрометация S3-ключа или неаутентифицированного proxy = доступ к вложениям интеграций, ПДн в выгрузках, снимкам. tempauth-пароль из SAIO и открытый 8080 в интернет — это ключ от бака.

Официально и по практике продукта:

- Клиенты ходят **только на proxy**. Storage-порты и rsync — непубличны.
- Прод-auth: **Keystone**, не tempauth. Для S3 — `s3api` **перед** auth в pipeline; для Keystone рекомендованный пример: `authtoken` → `s3api` → `s3token` → `keystoneauth`, у authtoken `delay_auth_decision = True` (иначе двойной поход в Keystone).
- В pipeline для заявленной S3-совместимости должны быть ещё **bulk** и **slo** (документация middleware).
- At-rest encryption — **опция**: middleware `keymaster` + `encryption` почти в конце pipeline. Шифруется тело объекта, ETag ненулевых объектов, **значения** пользовательских `X-Object-Meta-*`. **Не** шифруются имена account/container/object, имена метаданных, Content-Type, размер, системные метаданные. Документация прямо: это защита от чтения **диска, который унесли**; это **не** защита от того, кто сел на внутреннюю сеть Swift или украл root-секрет. Клиентское шифрование до PUT — единственный способ «plaintext не светился на проводе до proxy».
- Root-секрет keymaster: ≥ **44** символа base64, **одинаковый на всех proxy**. В проде — Barbican/KMIP, не строка `changeme` в git.
- Релизы 2.37.2 / 2.37.3 закрывают свежие дыры S3 и proxy, в том числе CVE-2026-71190 (DoS через `Accept`), CVE-2026-71191 / 71192 (копирование через S3-заголовки), CVE-2026-50221 (SSRF через container-update), CVE-2026-49017 (DoS aws-chunked). **Не** ставить «какой-нибудь Swift 2.29 с GeoData-инсталлятора» как платформенный S3 без отдельного решения по патчам.
- `s3_acl`: дефолт в проекте исторически `False`; часть CVE-2026-71191 завязана на этот дефолт. Для большей S3-совместимости SAIO включает `s3_acl` и `check_bucket_owner`. Выбор надо сделать сознательно и проверить клиентами, не скопировать молча.

«Поднять SAIO и выдать 8080 наружу» — это новый attack surface, не озеро.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём self-hosted Swift 2.37.3 (2026.1)**, не Amazon S3, не MinIO, не Ceph RGW и не Swift 2.29.2 из инсталлятора GeoData. Это разные диалекты API и разные кольца.
2. **S3 API включаем штатным `s3api`** на тех же proxy. Приложения, которым нужен «настоящий AWS», прогоняют матрицу `s3_compat` **до** контракта. Lifecycle/tagging/policy в архитектуре **не** закладываем.
3. **Прод-identity — Keystone** (уже нужен OpenStack-сервисам; для «только Swift» это всё равно отдельный HA-сервис). tempauth — только стенд.
4. **Storage-ноды — выделенные машины (bare metal или VM) с локальным XFS**, не `emptyDir` и не общий NFS как диск object-server. Proxy можно ближе к Kubernetes; object-server — нет, пока не доказан стабильный IP/диск в кольце.
5. **Три ЦОДа = три независимых домена отказа** (питание, сеть, здание). Если это три зала с общим UPS — кольцо с тремя zone даёт ложное спокойствие.
6. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. При replica=3 и раскладке «по одной копии в ЦОД» два мёртвых ЦОДа оставляют одну копию: чтение части данных ещё может работать, устойчивая запись и заявленный HA — нет.
7. **Stretch (один кластер на 3 ЦОДа)** принимается **только если** внутренняя сеть proxy↔object и rsync между площадками достаточно быстрая и стабильная. Порога RTT у проекта **нет**. Пока RTT и потери не измерены — это гипотеза.
8. **Нагрузки нет** — поэтому **нет** цифры «N дисков и M ТБ». Есть сигналы (заполнение дисков, async pending, время replicator, 5xx proxy, латентность PUT) и рычаги (диски, proxy, политики, шардинг контейнеров).
9. **Формального SLA / RPO / RTO нет.** Успешный PUT при 2 из 3 дисков ≠ юридический 24/7 и ≠ «файл уже в двух других ЦОДах», если включён write_affinity.
10. **Корпоративный PKI и секреты есть или будут.** Root-секрет шифрования и S3-ключи не живут в git.
11. **Шифрование канала — TLS на входе proxy/LB.** ГОСТ/СКЗИ не озвучены; vanilla Swift их не закрывает.
12. **Тестовый стенд изолирован.** На нём допустимы SAIO, tempauth, HTTP, один диск. В прод их не копируем.
13. **Kafka, Camunda, озеро-карточки, интеграционное API** — клиенты 8080/S3, не часть этого ПО. Контракт: ключи объектов, идемпотентный PUT, multipart для крупных тел, что делать с listing.
14. **Лицензия Apache 2.0.** Следить нужно за обвязкой (Keystone, образы дистрибутива), не за «лицензией Swift».

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «нарезали кольцо и выдали endpoint разработчикам».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT, потери, полоса** между ЦОДами на **6200–6202 и rsync** (p50/p95/p99, все пары), не ping ICMP | Без affinity каждый PUT ждёт чужие ЦОДы. С affinity — зависит от replicator. Высокий jitter → таймауты proxy, рост handoff, расхождение listing |
| **Один Kubernetes на 3 ЦОДа или три** | Proxy в K8s ещё можно. Object-server с кольцом по IP пода — нет, пока нет hostNetwork/stable IP и локального диска, который **не** переезжает |
| **Совместимость OpenStack-Helm с Kubernetes 1.36.4** | Матрица чартов 2026.1 — до **1.35**. «Поставим Helm на 1.36» — не сертифицированный путь |
| **Что именно кладёте** (вложения? parquet озера? snapshot OpenSearch? всё?) | Разный размер объекта, нужна ли SLO, какой container sharding, какая policy (3× vs EC) |
| **S3 Lifecycle / tagging / bucket policy в требованиях приложений** | В матрице Swift этого **нет**. Либо меняете приложения, либо это не тот продукт |
| **GeoData как клиент этого кластера** | Вендор ждал 2.29.2 и одноzone-пример. Платформенный 2.37.3 + 3 ЦОДа — отдельное согласие |
| **Кто Keystone и какой его HA** | Без identity нет прода S3. Слабый Keystone = «хранилище живо, никто не входит» |
| **Где живёт `.builder` и кто имеет право `rebalance`** | Ошибка кольца бьёт сильнее, чем падение одной ноды |
| **Срок хранения и 152-ФЗ/КИИ** | Имена объектов **не** шифруются at-rest middleware. ПДн в ключе и в listing — вопрос ИБ, не «включили encryption» |
| **Нужен ли write_affinity** | Документация: не для workload «записал и сразу читают из другого региона». У вас микросервисы в трёх ЦОДах — скорее всего **не** бэкапный паттерн |
| **Отдельная сеть репликации** | rsync терабайтов по той же сети, что PUT клиентов, душит API |
| **Квоты** | Без `account_quotas` / container quotas озеро съест диски молча |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **Swift 2.37.3** и способ установки (пакеты дистрибутива / свои образы). Не смешивать major/серии внутри одного кольца.
2. Спланировать **диски XFS**, имена устройств, сети (клиент / storage / replication).
3. Собрать кольца: account, container, object. Сохранить **`.builder`**. Раздать `.ring.gz` всем нодам.
4. Поднять rsync, object/container/account, затем proxy. Memcached — до проверки auth.
5. На стенде — tempauth; на проде — Keystone **до** боевых ключей S3. Включить `s3api` (+ slo, bulk) в pipeline.
6. Выпустить TLS на входе. Storage-сеть не публиковать.
7. Включить **recon** и метрики (хотя бы заполнение дисков, async pending, время репликации, коды proxy).
8. Прогнать PUT/GET по Swift API и по S3 (один и тот же объект глазами двух API — осознанно: это разные URL и разные подписи).
9. Прогнать отказ **одного** диска/ноды: объект читается, replicator сходится.
10. Только потом — encryption at-rest, EC-политика, sharding, write_affinity, если они вообще нужны.

Дальше — два режима.

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики клали и забирали объект, подключали AWS SDK/boto, видели разницу Swift API vs S3, ловили «lifecycle не поддерживается» на берегу. **Не** цель: доказать отказ ЦОДа и ёмкость терабайт.

Официальный минимальный путь — **SAIO** ([development_saio](https://docs.openstack.org/swift/2026.1/development_saio.html)):

- одна машина, XFS (хотя бы loopback-файл, как в гайде), memcached, rsync;
- proxy `127.0.0.1:8080`, tempauth;
- `s3api` в pipeline **перед** tempauth, как в sample; для более полной совместимости в SAIO включают `s3_acl` / `check_bucket_owner`;
- проверка Swift: `curl` на `/auth/v1.0` и `/v1/...` как в SAIO;
- проверка S3: endpoint `http://127.0.0.1:8080`, access key вида `account:user`, secret = пароль tempauth.

Альтернатива «чуть ближе к бою»: 3 VM в одном ЦОДе, replica=3, одна zone — уже видны кольца и replicator, но это всё ещё **не** модель трёх ЦОДов.

На Kubernetes для теста: допустим один под/VM с SAIO **в изолированном namespace**. Не копировать этот манифест в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число машин | 1 (SAIO) | Нет требования пережить выкат |
| Zone/region | одна | Не цель — отказ площадки |
| Auth | tempauth | Иначе команда утонет в Keystone раньше, чем в PUT |
| TLS | HTTP на localhost | Стенд изолирован |
| Encryption at-rest | выкл. или demo-секрет **не из git прода** | Сначала протокол, потом ключи |
| CPU/диски | минимальные XFS | Не цель — ёмкость |
| S3 Lifecycle | отсутствует как в проде | Пусть приложение упадёт на тесте, не в бою |
| Бэкап builder | копия на той же машине | На препроде builder уносят **с машины** |

#### Чего на тесте **не** стоит упрощать

- Версия **2.37.3** (не 2.29.2 «как в GeoData», если это платформенный контур).
- Понимание лимита **5 ГБ** и multipart/SLO.
- Клиентский код с **явным ключом** объекта (идемпотентный PUT). Иначе в проде повтор события из Kafka размножит мусор под разными именами.
- Запомнить: SAIO с tempauth **не** есть «почти прод».
- Не открывать 8080 и 6200 с ноутбука в корпоративную сеть без firewall.

#### Сильные стороны такой схемы

- Совпадает с официальным SAIO; поднимается за часы.
- Дешево показывает, какие вызовы AWS SDK **врёт** матрица.
- Один процесс мышления: кольцо → proxy → диск.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет rsync между площадками, нет Keystone HA.
- Успешный boto на localhost **не** доказывает, что PUT переживёт RTT и что replica разложится по трём zone.
- tempauth приучает хранить секрет в конфиге. В инциденте нужны Keystone и ротация EC2-keys.

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (несколько дисков, **разные zone**, Keystone, TLS, s3api, recon), даже без боевого трафика.

### Прод: 3 ЦОДа, нагрузка

Цифр «дисков под терабайты озера» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Swift плохо переживает **три независимых кольца без процедуры sync** (три правды файла) и плохо переживает **слепой stretch** по медленному rsync.

**Вариант A — один кластер, один region, три zone = три ЦОДа, replica=3.**

Это близко к **дефолтной** модели («один region, низкая задержка»). Кольцо старается разнести replica по zone → по одной копии в ЦОД.

- Proxy **в каждом** ЦОДе (минимум 2 процесса/инстанса на площадку, лучше 2+ машины), клиенты ходят на **местный** LB, при падении площадки — на оставшиеся.
- Storage-ноды во всех трёх ЦОДах, диски в кольце с `r1z1` / `r1z2` / `r1z3` (нумерация ваша).
- **Не** нарезать zone «по стойкам внутри ЦОДа» *вместо* ЦОДа: тогда две replica могут сесть в один ЦОД. Стойки — это уровень **server** в иерархии кольца, либо дополнительные zone **только если** вы проверили `swift-ring-builder` на dispersion и понимаете риск.
- Официальные «минимум 5 zone» при **трёх** ЦОДах закрывают так: 3 zone = ЦОД (обязательная изоляция копии) + достаточное число **серверов/дисков** внутри ЦОДа. Не жертвовать «1 копия = 1 ЦОД» ради цифры 5.
- `write_affinity` по умолчанию **выключен** (пустая настройка = нет предпочтения). Для микросервисов с чтением сразу после записи в другом ЦОДе так и оставить, **если** RTT позволяет. Если RTT убивает PUT — не включать affinity молча: сначала замерить, затем читать главу Global Clusters про деградацию распределения.
- Клиентам — VIP/DNS на proxy, **path-style** S3 на первый контракт (меньше сюрпризов с TLS/wildcard), virtual-hosted — только если сознательно настроили.

**Вариант B — один кластер как Global Cluster: 3 region = 3 ЦОДа.**

Официальный текст Global Clusters писался вокруг **двух** регионов с **тремя zone в каждом**. Три region — допустимое обобщение той же модели affinity, но **не** дословный пример из доки.

- Имеет смысл, если задержка между ЦОДами ближе к «двум городам», чем к «двум стойкам».
- `read_affinity` на proxy площадки: читать своё.
- `write_affinity` — только если workload похож на бэкапы (документация это прямо говорит). Иначе PUT без affinity, ценой латентности.
- Репликатор и полоса **между region** — отдельный бюджет. Если ingest быстрее вывоза — affinity выключают.

**Вариант C — три независимых кластера.**

Штатный мост — **container sync** (отдельная глава проекта), не «один бакет на три endpoint». Это уже три кольца, три Keystone-проекта или сложный IAM, другой RPO. Имеет смысл, если сеть A не позволяет.

**Вариант D — кластер в одном ЦОДе, остальные только клиенты.**

Простые кольца. Падение этого ЦОДа = нет объектного слоя, пока не восстановите с бэкапа. Честно, если RTT/полосы нет и «24/7» ещё не контракт.

**Пока топология сети и RTT не зафиксированы, нельзя честно выбрать A.** Дальше — общее для A как целевого «3 ЦОДа в одном городе»; B — если замеры покажут, что A по латентности PUT неприемлем; C/D — запасные.

##### Сильные / слабые стороны (A, один region, 3 zone)

| Сильное | Слабое |
|---|---|
| Одна карта данных, один бакет, один набор ключей | Каждый синхронный PUT трогает другие ЦОДы |
| Штатная идея Swift «зоны изолируют копии» | 3 zone < «оптимум 5» из гайда — отказ **стойки** внутри ЦОДа кольцо изолирует хуже, чем при 5 zone |
| Переживание 1 ЦОДа при replica=3 | Два ЦОДа сразу — нет |
| Проще, чем три кластера | Ошибка rebalance бьёт все три площадки |

##### Сильные / слабые стороны (B, 3 region + affinity)

| Сильное | Слабое |
|---|---|
| Официальные ручки под геораспределение | Пример в доке — 2 региона; третий вы проектируете сами |
| read_affinity снижает WAN на GET | write_affinity **откладывает** появление копии в чужом ЦОДе; GET сразу после PUT с другой площадки — сюрприз |
| Можно жить с большим RTT на записи | Репликатор не успевает — «всё лежит в одном регионе». Документация: тогда affinity выключить |

##### Сильные / слабые стороны (C, три кластера)

| Сильное | Слабое |
|---|---|
| Падение кольца A не уничтожает кольцо B | Нет прозрачного «одного бакета»; sync eventual |
| Можно не гонять rsync через плохую сеть как путь PUT | Три операционных контура, тройные ключи/политики |

##### Сильные / слабые стороны (D, мозг в одном ЦОДе)

| Сильное | Слабое |
|---|---|
| Кольцо и rsync не ходят межплощадочно | Падение ЦОДа хранения = нет объектов у всех |
| Проще кворум дисков | Нужен очень явный DR: восстановление с бэкапа **с прогоном по времени** |

##### Слабое место любого stretch без замера RTT

Документация **задаёт качественно**: default — один region с **high-bandwidth, low-latency**. Цифры миллисекунд **нет**. Утверждение «три ЦОДа в одном городе, значит можно размазать» — **непроверенное**. Мерить PUT/GET и rsync, не ping.

#### Кольца и ёмкость

- Три кольца минимум: account, container, object (плюс ещё object-кольцо на каждую дополнительную policy).
- `create <part_power> 3 24` как отправная точка (replica=3, min_part_hours=24), part_power — от прогноза **максимума** дисков, не от «сейчас купили три HDD».
- Все изменения устройств — пакетом, потом **один** rebalance. Гайд: так меньше двигается данных.
- Builder-файлы в защищённом бэкапе **вне** трёх ЦОДов или как минимум с кворумом копий. Без builder вы слепы.
- Веса — по реальной ёмкости. «Все weight=1» на дисках разного размера = одни тома лопнут раньше.
- Не RAID5 под объект. Диск умер — кольцо и replicator, не контроллер RAID.

#### Proxy, LB, S3

- Несколько proxy в **каждом** ЦОДе, PDB/anti-affinity по зоне.
- TLS на LB (у вас HAProxy) или на proxy; между LB и proxy — закрытая сеть.
- Pipeline прода (смысл, не копипаста): catch_errors / gatekeeper / healthcheck / cache / **authtoken** / **s3api** / **s3token** / **keystoneauth** / квоты / **bulk** / **slo** / (keymaster encryption) / proxy-server. Точный порядок сверять с `proxy-server.conf-sample` **той же** 2.37.3, не с блогом 2016 года.
- Один endpoint S3 на кластер (или по VIP на ЦОД с одним и тем же кольцом). Не раздавать разработчикам три разных URL «на всякий случай».

#### Kubernetes-специфика прода

- **Object/container/account:** DaemonSet или выделенные ноды, **hostNetwork** (или стабильный IP, который прописан в кольце), локальный volume (hostPath / LVM / raw disk), taint «только Swift». Переезд пода на другую ноду **без** изменения кольца = потеря устройства.
- **Proxy:** Deployment/DaemonSet за Service/HAProxy — нормально: они stateless, кольцо только читают.
- Не класть object-server на overlay-CSI «как Postgres PVC», если том может примонтироваться к другому узлу с другим IP — кольцо этого не поймёт само.
- OpenStack-Helm — опция автоматизации **если** закроете матрицу Kubernetes (у вас 1.36.4 vs ≤1.35 в таблице Helm) и операционную модель колец. Это не снимает XFS, rsync и builder.
- Kolla-Ansible как установщик Swift **не планировать**: поддержка снята с 2025.1.

#### Безопасность прода

| Слой | Правило |
|---|---|
| Вход | Только 443 на LB → proxy. 6200–6202, 873 — internal |
| Auth | Keystone HA; нет tempauth; нет общего ключа «на всех микросервисов» |
| S3 | Отдельные EC2-keys на сервис; least privilege (свой account/container); ротация |
| TLS | Сертификат на endpoint, которым реально пользуются SDK (имя бакета во virtual-host — отдельный SAN/wildcard) |
| At-rest | encryption middleware + секрет вне git; понимать, что **имена не шифруются** |
| Сеть | NetworkPolicy/firewall: proxy→storage, storage↔storage rsync, proxy→Keystone/memcached |
| Кольца | Доступ на `rebalance` — узкий круг; аудит изменений |
| Патчи | 2.37.3 не «навсегда»: S3-CVE в этой линейке уже были. Процесс обновления proxy **раньше** публичного интернета, если endpoint торчит |
| Аудит | proxy-logging (+ метка API swift vs S3 есть в 2.37.0 labeled metrics); отдельно — кто выдал ключ |

##### Сильные / слабые стороны (TLS + Keystone + s3api + encryption)

| Сильное | Слабое |
|---|---|
| Один кластер — два протокола | «S3-совместимый» ≠ AWS; часть SDK отвалится на Lifecycle/policy |
| Keystone уже модель проектов/ролей | Keystone SPOF доступа; s3token зависит от версии Keystone (в 2.37.0 отдельно чинили >25.0.0) |
| At-rest закрывает унесённый диск | Не закрывает админа Swift и внутреннюю сеть; имена объектов видны |
| Нет лицензионного сервера | Операционная сложность колец выше, чем у «одной VM MinIO» |

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами на портах storage и rsync. Решение A vs B vs C/D.
2. Выделить storage-ноды, XFS, нумерацию region/zone (= ЦОД), отдельные сети.
3. Собрать кольца replica=3, сохранить builder, раздать ring.gz.
4. Поднять rsync + storage services + memcached + **несколько** proxy за LB.
5. Включить Keystone-auth и s3api **до** боевых бакетов. Прогнать матрицу нужных S3-вызовов.
6. TLS, закрыть storage-порты, выдать ключи сервисам (не людям в Slack).
7. recon + заполнение дисков + async pending + латентность PUT.
8. Убить один диск и одну storage-ноду на препроде: GET жив, replicator сходится.
9. Условный «ЦОД недоступен»: выключить zone, проверить GET/PUT, что proxy в живых ЦОДах отвечают, что нет массового handoff-шторма.
10. Только потом — боевой поток из Kafka/интеграций. По факту заполнения — добавлять диски **весом**, не «внезапно part_power».

Без пункта 9 у вас нет отказоустойчивости трёх ЦОДов, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | replica=3; zone/region = ЦОД; proxy в каждой площадке; цель — 1 ЦОД; builder в бэкапе; rsync сходится; прогон «зона мертва» |
| Производительность / масштаб | Не требуется | Рост дисками в кольце; рост QPS — proxy; 5 ГБ / SLO; квоты; отдельная сеть репликации; EC только как вторая policy |
| Безопасность | tempauth только в изоляции | Нет tempauth; TLS на входе; storage не публичен; Keystone; раздельные S3-ключи; патч 2.37.3+; at-rest по решению ИБ |

**Не готов к проду**, если: SAIO/tempauth, один proxy, все диски в одной zone при рассказе «у нас 3 ЦОДа», replica≠3, NFS/`emptyDir` как диск object-server, кольца не совпадают на нодах, нет бэкапа `.builder`, 6200 открыт клиентам, RTT неизвестен, а схема уже stretch, приложение требует S3 Lifecycle/bucket policy, кластер общий с GeoData 2.29.2 без вендора, Swift назначен SoT клиентских карточек.
