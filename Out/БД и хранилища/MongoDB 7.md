# MongoDB Community Server 7.0.40 — развёртывание и настройка

Версия ПО: **MongoDB Community Server 7.0.40** (релизная дата 11 августа 2026; на дату подготовки документа это последний **опубликованный** патч линии **7.0**).  
В changelog линии 7.0 уже есть секция 7.0.41, но страница Release Notes 7.0 и теги официального образа на эту дату заканчиваются на **7.0.40**. Ставить «то, что в changelog, но ещё не в Release Notes / не в образе» нельзя.

Документация линейки: https://www.mongodb.com/docs/v7.0/  
Release Notes 7.0: https://www.mongodb.com/docs/v7.0/release-notes/7.0/  
Официальный образ: `mongodb/mongodb-community-server:7.0.40-ubi9-slim` (Docker Hub; тег `7.0-ubi9-slim` на эту дату указывает на тот же патч — в проде пинить **полный** `7.0.40-ubi9-slim`, не `7.0` и не `latest`).

Лицензия сервера: **SSPL** (Server Side Public License). Это не BSD/Apache. Юридически это не «просто open source как Kafka». Kubernetes-оператор MCK — отдельно, Apache 2.0; лицензия **сервера** от этого не меняется.

EOL линии 7.0 (on-prem / Enterprise Advanced и Atlas Dedicated): **31 августа 2027**. На дату документа линия живая. Патчи младше 7.0.40, особенно 7.0.0–7.0.15, содержат закрытые позже Critical Advisories — «любой 7.0» в прод не ставят.

Этот текст — не мануал «скопируй `docker run mongo`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

MongoDB **упоминался** в правилах диалога как типичное платформенное ПО под нагрузку. В исходной архитектуре (Kafka / Camunda / озеро эталона / интеграционное API) MongoDB **не назван** как конкретный слой. Ниже — как поставить Community Server 7.0 на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** замена Kafka, **не** процессный движок и **не** интеграционная шина к 30+ госслужбам.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Документ / коллекция / БД** | Запись JSON-подобного BSON; папка таких записей; пространство имён. Не таблица SQL 1:1: схема гибкая, индексы вы проектируете сами. |
| **BSON** | Бинарный формат документа. Лимит одного документа — **16 МБ**. Больше — GridFS или другое хранилище, не «увеличить лимит». |
| **`mongod`** | Процесс СУБД. «Нода» replica set или шард — это `mongod`. |
| **`mongos`** | Роутер шардированного кластера. Клиенты ходят **сюда**, не на шарды напрямую. Stateless: сам данные не хранит. |
| **Standalone** | Один `mongod` без replica set. Для прода вендор считает это **не** архитектурой. Change streams на standalone **нет**. |
| **Replica set** | Несколько `mongod` с **одним** набором данных: один **primary** (пишет), остальные **secondary** (копируют oplog). Это HA и копии, **не** горизонтальный масштаб записи. |
| **Primary / Secondary** | Кто принимает запись / кто держит копию. Secondary может стать primary на выборах. |
| **Oplog** | Журнал операций replica set (capped collection). Secondary догоняет primary по oplog. Если отстал дальше окна oplog — только **initial sync** (полная копия данных). |
| **Выборы (election)** | Secondary объявляет себя primary, если старый primary не отвечает дольше `electionTimeoutMillis`. Нужно **большинство голосов**. |
| **Кворум / majority** | Большинство **голосующих** членов. 3 члена → 2. Без majority **нет primary** → **нет записи**. |
| **Arbiter** | Голос **без** копии данных. Дешёвый кворум. В тройке PSA даёт известные проблемы с `w: majority`. Вендор: не ставить больше одного arbiter. |
| **PSA / PSS** | Primary–Secondary–Arbiter / Primary–Secondary–Secondary. Для прода с `w: majority` берут **PSS**, не PSA. |
| **Голос / priority** | `votes` — участвует ли в кворуме. `priority` — насколько охотно станет primary. `priority: 0` — никогда не primary (скрытая копия, отчётность, другой ЦОД «только копия»). |
| **Hidden / delayed** | Hidden не светится клиентам как readable. Delayed отстаёт на N секунд — «машина времени» от ошибочного `drop`, не HA. |
| **Write concern (`w`)** | Сколько копий должны подтвердить запись, прежде чем клиент получит OK. `{ w: 1 }` — только primary. `{ w: "majority" }` — большинство data-bearing voting. |
| **`wtimeout`** | Сколько ждать write concern. Без него клиент может ждать **бесконечно**, если majority недоступен. |
| **Read concern** | Насколько «подтверждённую» копию читать. `"local"` — что есть на этом узле. `"majority"` — то, что уже на majority. |
| **Read preference** | На **кого** слать чтение: `primary` (дефолт), `secondary`, `secondaryPreferred`… Secondary может отстать. Вендор прямо: replica set **не** для того, чтобы сваливать чтение на secondary «по умолчанию». |
| **Rollback** | После смены primary записи, которые **не** дошли до majority, на старом primary **откатываются**. `w: 1` это допускает. |
| **Journaling** | WAL на диск. Включено по умолчанию. `w: "majority"` по умолчанию ждёт journal (`writeConcernMajorityJournalDefault: true`). |
| **WiredTiger** | Единственный storage engine Community 7.0 (MMAPv1 давно убран). Данные на диске сжаты (дефолт коллекций — **snappy**), в внутреннем кэше — разжаты. |
| **WiredTiger cache** | RAM движка. Дефолт: **большее из** `50% × (RAM − 1 ГБ)` и **256 МБ**. В контейнере **обязан** быть задан явно: иначе процесс считает RAM **хоста**. |
| **Initial sync** | Новая/отставшая нода копирует **все** данные с донора. Для терабайт — часы/сутки и нагрузка на донора. Это не «рестарт пода». |
| **Шард / sharded cluster** | Данные коллекции разрезаны по **shard key** на несколько replica set. Масштаб **ёмкости и записи**, если ключ удачный. |
| **Shard key** | Поле (или поля), по которому режут коллекцию. Плохой ключ = один горячий шард. С 5.0 есть `reshardCollection`, но это тяжёлая операция, не «поменяли конфиг». |
| **Chunk** | Кусок диапазона shard key на одном шарде. Балансировщик двигает chunk'и. |
| **CSRS (config servers)** | Replica set с **метаданными** шардов (кто какой chunk держит). В проде — **3** члена. Упал CSRS кворум — кластер не маршрутизирует нормально. |
| **Hashed sharding** | Режут по хешу поля. Ровнее пишет (хорошо для монотонного `_id`/времени), хуже диапазонные запросы (часто scatter-gather). |
| **Change stream** | Подписка на изменения коллекции/БД. Нужен replica set или sharded cluster. Это не Kafka: нет долгого retention как у топика, семантика другая. |
| **SCRAM** | Пароль + challenge (дефолтная аутентификация Community). |
| **X.509** | Аутентификация сертификатом (клиенты и/или члены replica set). |
| **Keyfile** | Общий секрет между членами replica set / шардами («мы свои»). Без внутренней аутентификации чужой `mongod` можно добавить в набор, если дотянулся до порта. |
| **RBAC** | Роли: кому какие действия на каких БД. Дефолт: **authorization выключен**. |
| **TLS** | Шифрование канала клиент↔`mongod` и `mongod`↔`mongod`. В дефолте **нет**. |
| **Encryption at rest (WiredTiger native)** | Шифрование файлов движком, часто с KMIP. Это **Enterprise**, не Community. |
| **Аудит** | Журнал «кто что сделал» на сервере. Это **Enterprise**. |
| **LDAP / Kerberos** | Корпоративный вход. Это **Enterprise / Atlas**, не Community 7.0. |
| **MCK** | MongoDB Controllers for Kubernetes — актуальный оператор (слияние Community Operator и Enterprise Operator). |
| **`MongoDBCommunity` CR** | Custom Resource Community: официально тип **только `ReplicaSet`**. Не шарды. |
| **Stretch** | Один replica set / sharded cluster, члены физически в разных ЦОДах. Ходят друг к другу по 27017 (и служебным портам шардов). |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. |
| **SSPL** | Лицензия сервера. Если отдаёте MongoDB **как сервис третьим лицам**, требования жёсткие; закрытый внутренний контур обычно иное, но это решение **юристов**, не админа. |

## Основные элементы системы и зависимости

### Что входит в MongoDB 7.0.40 (это одно ПО, несколько топологий)

| Топология | Зачем | Запись | Чтение | Автоfailover primary |
|---|---|---|---|---|
| **Standalone** | Тест, один процесс | Вертикаль диска/CPU/RAM одной машины | Нет отдельной копии | **Нет** |
| **Replica set PSS** (1 primary + ≥2 data-bearing secondary) | HA и копии. Официальный минимум прода — **3 члена** | **Нет** горизонтали: пишет один primary | Можно secondary, если готовы к отставанию; вендор не рекомендует это как основной паттерн | Да, если majority жив и есть eligible secondary |
| **Replica set PSA** | 2 копии + arbiter | Как PSS, но при падении одной data-ноды `w: majority` **не проходит**, растёт cache pressure | Как PSS | Выборы да; долговечность записи — слабое место |
| **Sharded cluster** | Ёмкость и write-QPS больше одного primary | Да, **если** shard key распределяет нагрузку | Да (mongos + шарды) | HA **внутри каждого** шарда и CSRS — как у replica set. Сам шард key failover не чинит |

Плюс рядом, но это уже другое ПО: драйвер приложения (обязан понимать replica set / mongos), `mongosh`, Database Tools (`mongodump` / `mongorestore` / `mongostat`), экспортёр метрик, UI (Compass — клиент, не кластер). Ops Manager / Cloud Manager / Atlas — коммерческие или облачные контуры, не Community Server.

**Replica set и шарды не взаимозаменяемы.** Реплики не увеличивают объём записи. Шарды без replica set на каждом шарде — не прод (с 3.6 шард **должен** быть replica set).

### Официальные порты (менять можно, контракт сети лучше не плодить)

| Порт | Назначение |
|---|---|
| **27017/TCP** | Клиенты и члены обычного replica set / `mongos` |
| **27018/TCP** | Дефолт `mongod --shardsvr` (член шарда) |
| **27019/TCP** | Дефолт `mongod --configsvr` (config server) |

UDP нет. Между **всеми** членами replica set — полный обмен на их портах (не «клиент ходит только на primary»). У шардов: каждый `mongod`, каждый `mongos` и CSRS должны быть взаимно достижимы. Балансировщик «как у HTTP на все 27017» перед replica set **ломает** модель так же, как у Kafka: клиент должен знать состав набора (`replicaSet=` в URI) и идти на текущий primary.

### Чего в MongoDB Community 7.0 нет (частая путаница)

| Нужно системе | Это не Community 7.0 | Зачем помнить |
|---|---|---|
| Шина событий с партициями, retention, consumer group | Apache Kafka | Change stream — подписка на живые изменения, не замена топика |
| Camunda / BPMN | Process engine | В Mongo можно хранить состояние шага, не исполнять процесс |
| Интеграции с госслужбами | Ваше интеграционное API | Сюда — документы ответа/идемпотентности, не коннект к ведомству |
| Нативная шифровка файлов WiredTiger / KMIP | **Enterprise** | Community: LUKS / CSI encryption / dm-crypt, права на `dbPath` |
| Аудит действий на сервере | **Enterprise** | Community: логи подключений + аудит в приложении / SIEM снаружи |
| LDAP / Kerberos | **Enterprise / Atlas** | Community: SCRAM и X.509 |
| In-Memory storage engine | **Enterprise** | Community — диск + кэш WiredTiger |
| Непрерывный backup с PITR «из коробки» | Ops Manager / Cloud Manager / Atlas | Community: снимки ФС / CSI и `mongodump` (для **небольших** деплоев) |
| Официальный порог RTT между ЦОДами | Нет миллисекунд | Есть `electionTimeoutMillis` (дефолт **10000**) и heartbeat **2 с**. Это не «можно 80 мс» |
| Шардированный кластер через CR `MongoDBCommunity` | Тип CR = **только ReplicaSet** | Шарды Community Server **умеет**; официальный Community-оператор их **не** описывает |
| Сильная multi-master запись в 3 ЦОДах | Нет. Один primary на replica set (и на нешардированную коллекцию) | Два «активных писателя» в двух ЦОДах — не эта СУБД |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS — OpenSSL/библиотека ОС, не криптография КИИ |
| Гарантия «терабайты влезут на три ноды» | Нет | Влезает то, что влезает на **диск primary** (+ те же объёмы на каждой data-копии) и в IOPS. Горизонталь ёмкости — **шарды** |
| Замена бэкапа репликами | Нет | Secondary спасает от падения **ноды**. Не спасает от `dropDatabase`, кривого обновления, шифровальщика на общем бэкап-контуре |

### Зависимости окружения (обязательны)

- **Диск.** Локальный быстрый том (SSD; RAID-10 если аппаратный RAID). XFS для data-bearing **настоятельно** рекомендуется с WiredTiger. NFS формально допустим, если POSIX, но вендор предупреждает: обычно **медленнее**. Не строить прод на NFS «потому что PVC так проще».
- **RAM.** WiredTiger cache + filesystem cache + соединения + агент в sidecar. В Kubernetes **лимит памяти пода ≠ RAM хоста**: задать `storage.wiredTiger.engineConfig.cacheSizeGB` **ниже** лимита cgroup (официальное требование для контейнеров).
- **CPU.** Минимум «два реальных ядра или один многоядерный CPU» на `mongod`/`mongos`. WiredTiger многопоточен; упираться в 1 vCPU на терабайтах — искусственный потолок.
- **Ядро Linux (production notes, не «на глаз»):** выключить Transparent Huge Pages; NUMA — interleave / `numactl --interleave=all`; `vm.swappiness` 0 или 1; readahead тома **8–32**; NTP между узлами (особенно шарды). Это хост/CSI, не только ConfigMap.
- **Сеть:** hostname, не голый IP (с 5.0 узел **только с IP в конфиге replica set не стартует**). Полный mesh 27017 (и 27018/27019 для шардов). Клиенты — replica set URI или список `mongos`, не один вечный IP primary.
- **Kubernetes (у вас заявлен):** StatefulSet + PVC (RWO) на каждый data-bearing `mongod`; anti-affinity по зонам. Актуальный инсталлятор: **MongoDB Controllers for Kubernetes (MCK) 1.10.0** (релизная дата 30 июля 2026). Старый репозиторий Community Operator — EOL (best-effort до ноября 2025): **не** начинать с него. В CR Community пинить `spec.version` **полной** строкой (`7.0.40`), не `7.0`.
- **PKI** для прода: TLS клиентов и кластера; для replica set ещё keyfile или X.509 между членами.
- **Драйверы** с поддержкой replica set / SRV и с retryable writes/reads (в 7.0 это норма драйвера, не «магия сервера»). «Подключились к одному IP 27017 навсегда» переживает только standalone.

### Как MongoDB стыкуется с вашей архитектурой

```
Микросервисы, Camunda job workers, интеграционное API
        │  документы, индексы, транзакции внутри replica set / шарда
        ▼
   MongoDB 7.0  (операционное / документное хранилище)
        │  опционально change stream → продюсер
        ▼
   Kafka ── остаётся шиной событий
Озеро эталона ── источник истины клиентских данных, *если* вы не назначили Mongo этим озером
Camunda ── остаётся движком процессов
```

Честные роли в *вашей* картине (это допущение по роли, не факт из исходного ТЗ):

1. **Операционное хранилище сервиса** — заявки, идемпотентность шага интеграции, проекции для UI, которые **не** обязаны быть эталоном на терабайты.
2. **Кандидат в озеро эталона**, если эталон — документная модель и вы **сознательно** принимаете Mongo как SoT. Тогда к нему требования HA/бэкап/PII как к системе учёта, не как к кэшу.
3. **Change stream → Kafka** — публикация факта «документ изменился». Шина всё равно Kafka: повторная обработка, лаги ведомств, fan-out на 30 интеграций живут там.

Нечестные роли:

- «Положим эталон в Mongo, а Kafka потом» — event-модель руководства так не собирается.
- «Три пода Mongo = масштабирование записи» — это три копии **одного** primary.
- «Читаем с secondary, чтобы ускорить интеграционное API» — stale + вендор против как основного паттерна. Для SoT клиентской карточки опасно без явного read concern и понимания лага.
- «Change stream вместо Kafka» — другой ops, другой retention, вы уже выбрали Kafka.

## Краткие вводные

### Зачем вам MongoDB в этой архитектуре

Kafka доставляет факт. Camunda ведёт процесс. Интеграционное API ходит наружу. Озеро должно быть истиной.

MongoDB закрывает **документную** модель: вложенные структуры, гибкая схема, индексы под запросы, транзакции на replica set (и на шардах — с оговорками стоимости). Он **не** делает event-sourcing и **не** заменяет озеро сам по себе — только если вы его озером назначите.

Если рабочий набор **записи** не влезает в один primary (IOPS, размер данных, hot document) — это не «добавим secondary». Это шардирование **или** другая СУБД/слой. Secondary увеличивает **отказоустойчивость копии**, не пропускную способность записи.

### Как устроена отказоустойчивость (идея, не магия)

База — **один writer на replica set** плюс копии через oplog. Путать «три контейнера в compose» с HA — главная ошибка.

**1) Один `mongod` failover не делает**

| Что падает | Что происходит |
|---|---|
| Процесс / диск standalone | Данные, которые успели в journal, поднимаются с этим диском. Нет второй копии, нет выборов |
| Primary replica set, majority жив, есть eligible secondary | Выборы. Ориентир вендора при дефолтах: медиана до нового primary **обычно не больше ~12 с**, плюс влияние **вашей** сети. Записи `w: 1`, не дошедшие до majority, могут откатиться |
| Нет majority (2 из 3 ЦОДов умерли при раскладке 1-1-1) | Primary нет. Запись **стоит**. Чтение с оставшегося secondary возможно, это уже не полноценный кластер |
| Secondary | Запись на primary жива, пока majority есть. `w: majority` может начать таймаутиться, если не набрать копии |

**2) PSS на 3 ЦОДах (официальный пример)**

Вендор для трёх ЦОДов и **трёх** членов: **по одному члену в ЦОД**. Падение **любого одного** ЦОДа — оставшиеся двое выбирают primary, набор остаётся записываемым.

| Что падает | Что происходит |
|---|---|
| 1 ЦОД | Majority=2 из оставшихся 2. Запись жива. `w: majority` ждёт вторую площадку — латентность = RTT |
| 2 ЦОДа | Majority нет. Запись нет |
| Сеть между ЦОДами моргнула дольше `electionTimeoutMillis` (дефолт 10 с) | Риск ложных выборов; старый primary, оказавшийся в меньшинстве, должен уйти. Хвост `w: 1` — rollback |

**3) Пять членов 2-2-1 (официальный пример на 3 ЦОДа)**

Majority=3. Падение любого **одного** ЦОДа оставляет ≥3 голосов. Плюс: два члена в одном ЦОДе могут закрыть `w: majority` **внутри** площадки primary — меньше зависимости write latency от чужого ЦОДа. Цена: **пять** полных копий данных.

**4) PSA — не ваш прод, пока не доказали обратное**

Официально: если data-bearing нода лежит или отстаёт, `w: majority` в PSA **не выполняется**, majority commit point отстаёт, WiredTiger копит историю, растёт I/O и cache pressure, oplog может разрастаться **выше** лимита, чтобы не срезать commit point. Смягчение вендора: временно `{ votes: 0, priority: 0 }` на больной ноде. Это костыль, не целевая схема.

Неявный default write concern для PSA (2 data + 1 arbiter) — **`{ w: 1 }`**, не majority. То есть «просто поставили тройку с arbiter» **тихо** ослабляет долговечность.

**5) Шардированный кластер**

HA = HA **каждого** replica set (шарды + CSRS) плюс несколько `mongos`. Падение одного шарда ≠ падение всего кластера, но запросы, которым нужен этот шард, падают. CSRS без majority — метаданные. Вендор: в проде CSRS и каждый шард — **3 члена**, и **рекомендует** раскладывать их **минимум на 3 ЦОДа**.

**6) Реплики не бэкап**

`drop`, массовый `update`, истёкший TTL, ransomware на StorageClass — уедут на secondary. Нужен снимок **вне** набора и прогнанный restore.

### Как устроено масштабирование

Несколько независимых осей — их нельзя склеить в «добавим реплик»:

1. **Больше данных на диске** → больше диск/vertical одной ноды **или шарды**. Каждая data-копия ест тот же объём. 10 ТБ × PSS-3 = порядка 10 ТБ **× 3**, плюс oplog, индексы, фрагментация, staging бэкапа.
2. **Больше записи** → быстрее primary (CPU, IOPS, размер рабочего набора в кэше) **или шарды** при удачном shard key. Горячий документ (`client:VIP`) шард не спасёт — он живёт на одном чанке.
3. **Больше чтения** → вертикаль primary; secondary только если явно приняли stale и вендорный совет «не надо». Для read-heavy вендор предлагает **отдельный кластер** (Mongosync и т.п.) — это уже другое ПО.
4. **Индексы.** Запрос без индекса на терабайтах = collection scan = «нагрузка неизвестна» превращается в инцидент. Индекс ест RAM и диск. Это часть сметы, не украшение.
5. **Транзакции и тяжёлый aggregation** — законная фича 7.0 и законный способ уложить primary. Не обещать «как Redis SET» на multi-document transaction через три ЦОДа.

Ориентиры, которые **есть** у вендора, и которые **нельзя** принять за смету вашего прода:

- Replica set: до **50** членов, из них голосующих до **7**. Официальный прод-стандарт — **3**.
- Fault tolerance (голоса): 3→1; 5→2. Четыре члена **не** дают tolerance 2.
- WiredTiger cache: формула выше; **не увеличивать** выше дефолта без причины; в контейнере — **уменьшать** под лимит.
- Дефолт write concern: `w: majority` **если нет arbiter-ловушки**.
- `electionTimeoutMillis` **10000**; heartbeat **2000 мс**.
- Нагрузки у вас нет — поэтому **нет** цифры «N шардов и M гигабайт cache».

«Огромный объём (терабайты)» Mongo **может** хранить. Это не автоматически значит, что **этот** кластер без шардов и без проекта индексов это выдержит.

### Безопасность самого MongoDB

Модель из production notes: по умолчанию **authorization выключен**, `mongod` исходит из **доверенной сети**. Bind по умолчанию — **localhost** (нативный пакет). Образы/Helm часто слушают шире «чтобы завелось». Один `db.dropDatabase()` с сети без пароля — инцидент, не «ещё не настроили».

Компрометация Mongo с клиентскими карточками / ответами госслужб = компрометация **ПДн и содержимого внешних ответов**.

Официальный checklist (Community):

- Включить access control; механизм Community: **SCRAM** (дефолт) или **X.509**.
- Сначала user administrator, потом остальные; least privilege; отдельный пользователь на приложение, не `root` на все сервисы.
- TLS на **всех** соединениях, включая между членами набора.
- Данные на диске: native encryption at rest — **Enterprise**; иначе шифрование тома/ФС + права на файлы (данные, конфиг, keyfile, логи).
- Ограничить сеть; `bindIp` на внутренний интерфейс, не интернет.
- Не root OS; отдельная учётка `mongod`.
- Если не используете server-side JS (`$where`, `$function`, `mapReduce`, `$accumulator`) — `--noscripting`.
- Оставить `net.wireObjectCheck` (дефолт: валидный BSON).
- Антивирус/EDR **исключить** `dbPath` и лог: сканер может испортить файлы и уронить процесс; пользы от скана сжатых (и тем более encrypted-Enterprise) файлов вендор не видит.
- Аудит на сервере — **нет** в Community. Это пробел, если ИБ ждёт «как у СУБД с audit trail».

«Поднять `docker run -p 27017:27017 mongo` и выдать порт в сеть» — это новый attack surface, не платформенная БД.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём MongoDB Community Server 7.0.40**, не Enterprise, не Atlas, не Percona Server for MongoDB, не 8.x. Юристы **принимают SSPL** для закрытого контура. Если нет — этот файл не является разрешением ставить Community 7.0.
2. **Прод крутится в Kubernetes.** Инсталлятор replica set — **MCK 1.10.0** и CR `MongoDBCommunity` с `spec.version: "7.0.40"` и официальным образом `mongodb-community-server`. Совместимость конкретного Helm-тега с 1.10.0 **сверять** (чарты на каталогах могут отставать от GitHub-релиза). Это не эквивалент «Strimzi официально совместим с Kafka 4.3.1» одной строкой в матрице — прогон на стенде обязателен.
3. **Три ЦОДа = три независимые зоны отказа.** Если это три зала с общим питанием/SAN — stretch даёт ложное чувство безопасности.
4. **Stretch принимается только если** mesh 27017 (и при шардах 27018/27019 + `mongos`) достаточно быстрый и стабильный относительно `electionTimeoutMillis`. Порога RTT у MongoDB **нет**. Пока RTT не измерен — гипотеза.
5. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. И 1-1-1, и 2-2-1 два ЦОДа **не** переживают без потери записи (нет majority).
6. **Нагрузки нет** — поэтому **нет** цифры «N шардов». Есть сигнаки (`replSetGetStatus`, лаг oplog, `wiredTiger.cache`, `slowms`, connections) и рычаги (диск, cache, индексы, шарды).
7. **Формального SLA / RPO / RTO нет.** Живой primary и `w: majority` ≠ «ни один документ интеграционного ответа не потерян при dual-DC».
8. **Корпоративный PKI есть или будет** для TLS между ЦОДами. Без TLS в проде между площадками — отдельное принятие риска ИБ.
9. **Идентификация сервисов** — отдельные пользователи RBAC. Camunda worker не имеет `userAdminAnyDatabase`. Люди в прод-Mongo — через jump / оператор, не общая учётка приложения.
10. **Шифрование канала — TLS сборки MongoDB/ОС.** ГОСТ/СКЗИ не озвучены.
11. **Тестовый стенд изолирован.** На нём допустим standalone без auth на loopback. В прод это не копируем.
12. **Kafka, Camunda, озеро, интеграционное API** — клиенты 27017, не часть этого ПО. Контракт: свой database name / user, индексы под запросы, `w: majority` + `wtimeout` на факты, которые нельзя откатить.
13. **MongoDB в этой схеме — не кэш и не Kafka.** Если рабочий набор — горячий кэш TTL, смотрите Redis/Valkey. Если лог событий — Kafka.
14. **Роль «озеро эталона» не закреплена за Mongo.** Если закрепят — бэкап, PII, шарды и запрет secondary как SoT-чтения становятся обязательными, не опциональными.
15. **Шарды на старте не ставим**, пока не доказано, что один PSS не держит объём/запись. Community CR шарды всё равно не умеет: шардирование = отдельное решение по установщику.
16. **Один логический кластер на среду**, не «каждый микросервис свой replica set в углу» без причины. Несколько кластеров допустимы, если разные RPO/PII/нагрузка — это уже несколько экземпляров, у каждого своя HA.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили StatefulSet и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT, jitter, потери на 27017 между ЦОДами** (p50/p95/p99, все пары) | Heartbeat 2 с и выборы ~10 с живут этим каналом. Высокий/плавающий RTT → ложные выборы, rollback `w: 1`, таймауты `w: majority`. Stretch станет источником аварий |
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Replica set — полный mesh. Нет pod-to-pod между ЦОДами → это **не** один набор, а несколько БД |
| **Что именно кладёте в Mongo** (операционка сервисов? эталон клиентов? сырые ответы ведомств? всё сразу?) | Разный бэкап, TTL, индексы, RBAC, 152-ФЗ. «Терабайты» без состава — не смета |
| **Нужна ли запись после падения 1 ЦОДа ценой RTT на каждый `w: majority`** | 1-1-1 всегда ходит за подтверждением в другой ЦОД. 2-2-1 дороже диском. Приоритеты могут оставить primary в одном ЦОДе — но тогда падение **этого** ЦОДа = выборы на чужой площадке с другой latency |
| **Клиенты используют replica set URI / несколько mongos** | Иначе failover Mongo «успешный», приложение пишет в труп |
| **152-ФЗ / срок хранения ПДн** | Индексы и бэкапы тоже ПДн. Community без native at-rest и без аудита — ИБ должна принять компенсирующие меры явно |
| **Лицензия SSPL** | Без решения юристов установка в контур может быть запрещена вне зависимости от HA |
| **Нужны ли шарды** | Community CR их не ставит. Терабайты на одном primary — ставка. Плохой shard key навсегда (почти) режет кластер |
| **StorageClass, IOPS, XFS, THP, cacheSizeGB** | «Mongo быстрый», пока PVC на общем HDD и cache съел лимит пода |
| **Нужен ли серверный аудит / LDAP / encryption at rest движка** | Это Enterprise. Community **не** станет ими после «галочки в Helm» |
| **Окно бэкапа vs размер oplog vs время initial sync** | Терабайты: `mongodump` вендор считает инструментом **небольших** деплоев. Снимок без прогнанного restore — не бэкап |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **7.0.40** (полный тег образа / `spec.version`). Юристы — SSPL.
2. Решить **роль данных** (операционка / эталон / черновик интеграции) → из этого write concern, бэкап, индексы, TTL. Не наоборот.
3. Решить **топологию**: standalone (только тест) / PSS replica set / (позже) шарды. Не «шарды потому что терабайты в слайде».
4. Выставить хостовые THP / NUMA / swappiness / readahead **до** первого пода с боевым объёмом.
5. Включить **authorization + внутренний auth (keyfile/X.509) + TLS** в проде **до** боевых клиентов. Не оставлять `authorization` выключенным «как в примере».
6. Задать **`wiredTigerCacheSizeGB`** под лимит контейнера. Без этого HA не спасает от OOM/eviction storm.
7. Включить метрики: `replSetGetStatus`, лаг, `serverStatus.wiredTiger.cache`, connections, slow queries, диск.
8. Прогнать запись с `{ w: "majority", wtimeout: … }` и чтение. Убедиться, что документ **виден** и что падение одной ноды оставляет *ту* семантику, на которую подписались.
9. Прогнать **контролируемый failover** (`rs.stepDown()`). Без этого у вас нет HA, есть надежда.
10. Снять снимок, прогнать **restore** на другой namespace. Только потом — тонкий RBAC и смежные системы.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики писали документы, смотрели индексы, подключали драйвер из микросервиса/Camunda worker. **Не** цель: доказать отказ ЦОДа и ёмкость терабайт.

Официальный минимальный путь (образ Community, не устаревший `library/mongo` как единственный ориентир):

```text
docker run -d --name mongo-dev -p 127.0.0.1:27017:27017 mongodb/mongodb-community-server:7.0.40-ubi9-slim
```

Проверка: `docker exec -it mongo-dev mongosh --eval "db.runCommand({ ping: 1 })"` → `ok: 1`.

Публиковать `-p 27017:27017` на все интерфейсы рабочей станции **нельзя**: внутри контейнера процесс слушает шире localhost.

На Kubernetes: один StatefulSet / `MongoDBCommunity` с `members: 1` только если команда понимает, что это **не** replica set HA. Для препрода лучше сразу `members: 3` в одной зоне — чтобы драйвер учился URI, а не «в проде включим реплики».

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число нод | 1 | Нет требования пережить выкат |
| Replica set | можно выкл. или 1 член | Иначе команда утонет в URI раньше, чем в документах |
| Пароль | можно без, **только loopback / изолированная сеть** | Нативный bind localhost спасает пакет; Docker это часто уже обошёл — сеть всё равно закрыть |
| TLS | нет | Иначе PKI раньше продукта |
| cacheSizeGB | 256–512 МБ явно | Не цель — ёмкость; в Docker всё равно не считать RAM ноутбука |
| Шарды / mongos | нет | Иначе shard key раньше предметной модели |
| Мониторинг | ping + логи | Нет нагрузки |
| Бэкап | не обязателен | Потеря стенда терпима |

#### Чего на тесте **не** стоит упрощать

- Версия **7.0.40** (не «какой mongo есть у devops», не 8.x «он новее»).
- **Имена полей и индексы** под реальные запросы интеграций. Иначе в проде первый collection scan.
- Лимит документа **16 МБ** — поймать до боя (вложения ответов ведомств легко раздуваются).
- Если цель прода — replica set: на препроде драйвер с `replicaSet=` и `retryWrites`, не «на проде включим».
- Понимание: успешный `insert` на одном процессе **не** доказывает failover и **не** доказывает `w: majority` через ЦОД.

#### Сильные стороны такой схемы

- Поднимается за минуты, совпадает с официальным Community-образом.
- Дешево показывает модель документа и индексы Camunda/интеграций.
- Standalone официально нормален для development.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет heartbeat между площадками, нет поведения cache eviction под давлением, нет initial sync терабайт.
- Docker `-p 27017:27017` на рабочей станции легко оказывается «торчит в Wi-Fi» **без пароля**.
- Привычка без auth уедет в прод: дефолт сервера этому потакает.
- Change stream на чистом standalone недоступен — сюрприз, если прототип «по событию документа» писали на одном процессе без replica set.

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (PSS-3, auth, TLS хотя бы внутри кластера, `w: majority` + `wtimeout`, cacheSizeGB, XFS/CSI как в проде), даже без боевого трафика.

### Прод: 3 ЦОДа, нагрузка

Цифр «гигабайт и шардов под терабайты озера» **нет** — нагрузки нет, и роль озера за Mongo не закреплена. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Сначала развилка **A/B/C по сети**, затем PSS vs шарды по данным.

**Вариант A — stretch: один логический replica set (потом — один sharded cluster) на 3 ЦОДа.**

Имеет смысл, если mesh 27017 — метро-класс. Совпадает с официальным «odd number of data centers» и примером 1-1-1 / 2-2-1.

**Вариант B — мозг в одном ЦОДе** (все voting members живут в ЦОД-1, в ЦОД-2/3 — `priority: 0` скрытые копии или только клиенты).

Кворум не зависит от межЦОДового RTT. Падение ЦОД-1 = нет записи ни у кого. Спасает заранее прогнанный restore / смена конфига voting (это уже **ручной** DR, вендор описывает reconfigure при недоступных членах — это процедура аварии, не автоfailover).

**Вариант C — независимый replica set в каждом ЦОДе** без общего кворума.

Нет единого SoT. Склейка — ваше приложение или Kafka. Для кэша проекций допустимо. Для эталона клиентов — три истины, пока не спроектировали конфликт.

**Пока топология K8s и RTT не зафиксированы, нельзя честно выбрать A.** Дальше A как целевой «3 ЦОДа в одном городе»; B/C — запасные.

##### Сильные / слабые стороны stretch (A)

| Сильное | Слабое |
|---|---|
| Клиентам один URI набора | `w: majority` на 1-1-1 = RTT до чужого ЦОДа на **каждую** такую запись |
| Падение 1 ЦОДа — официально переживается без «переключения на другую БД» | Сетевой шторм выглядит как выборы и деградация Mongo |
| Согласовано с рекомендацией вендора «≥3 ЦОДа для шардов/CSRS» | 2 ЦОДа из 3 = стоп записи; ошибка `drop` сразу везде |
| | Ложный failover при малом `electionTimeoutMillis` относительно сети |

##### Сильные / слабые стороны «мозг в одном ЦОДе» (B)

| Сильное | Слабое |
|---|---|
| Выборы не зависят от межЦОДового RTT на кворуме | Падение этого ЦОДа = простой записи на всех трёх |
| Проще отлаживать failover внутри площадки | Нужен явный DR: restore или ручной reconfigure **с прогоном по времени** |
| | Клиентский путь 27017 через город — уже ваша сеть |

##### Слабое место любого stretch без замера RTT

Документация говорит, что latency **может удлинить** выборы, и не даёт порога миллисекунд. Утверждение «три ЦОДа в одном городе, значит можно размазать PSS» — **непроверенное**. Мерить TCP 27017 (и служебные порты шардов), не ping ICMP «на всякий случай».

---

#### Выбор PSS-3 vs PSS-5 vs шарды (внутри A или B)

| Вопрос | PSS 3 (1-1-1) | PSS 5 (2-2-1) | Шарды (каждый шард = свой PSS) |
|---|---|---|---|
| Пережить 1 ЦОД с записью | Да (офиц. пример) | Да (офиц. пример) | Да, если **каждый** шард и CSRS так разложены |
| Диск | 3 полных копии | 5 полных копий | Копии × число шардов + CSRS (CSRS маленький) |
| `w: majority` без чужого ЦОДа | Обычно нет (нужна 2-я площадка) | Часто да (два члена в ЦОДе primary) | Как у шарда, где живёт документ |
| Запись больше одного primary | Нет | Нет | Да, при удачном shard key |
| Старт на MCK Community | Да, `members: 3` | Да, `members: 5` | **Нет** в `MongoDBCommunity` |

Для неизвестной нагрузки и неизвестного состава данных **стартовая прод-схема — PSS-3 1-1-1**, как стандарт вендора. PSS-5 — если замерили, что majority-RTT 1-1-1 неприемлем, и готовы платить диском. Шарды — когда **доказали**, что один primary упирается в объём или write, и есть кандидат shard key (высокая cardinality, без монотонного hotspot — или hashed).

Не включать шарды «чтобы было как Kafka с партициями». У Kafka партиция — единица порядка событий. У Mongo chunk — единица диапазона shard key.

##### Если PSS (рекомендуемый старт)

Минимум для цели «пережить 1 ЦОД»:

```
ЦОД1: mongod (voting, priority > 0)
ЦОД2: mongod (voting, priority > 0)
ЦОД3: mongod (voting, priority > 0)
```

- Имена — DNS, не IP.
- `w: "majority"` + **ненулевой** `wtimeout` в драйвере на факты, которые нельзя rollback. Дефолт majority при PSS-3 без arbiter совпадает; `wtimeout` дефолтом **не** спасает.
- Не ставить arbiter «чтобы сэкономить диск третьей копии» на проде с терабайтами и PII.
- Anti-affinity: не два voting в одной зоне «случайно», если проектировали 1-1-1.
- Если хотите, чтобы primary **предпочитал** ЦОД1 (клиенты рядом): повысить `priority` там. Помнить: падение ЦОД1 всё равно выборы на ЦОД2/3; не ставить чужим `priority: 0`, если они должны уметь стать primary.
- Oplog: спланировать окно «максимальное время, на которое secondary/бэкап может отстать». Терабайты + маленький oplog = initial sync в худший момент.
- Журналирование включено (дефолт). Не выключать.
- Клиенты знают **все три** (или SRV), `replicaSet=...`. LoadBalancer без понимания primary — антипаттерн.

##### Сильные / слабые стороны PSS-3 на 3 ЦОДах

| Сильное | Слабое |
|---|---|
| Официальный минимум прода и официальный geo-пример | Один writer — потолок |
| Падение 1 ЦОДа переживается | Падение 2 ЦОДов — нет majority |
| `w: majority` защищает от rollback после выборов | Каждая такая запись на 1-1-1 платит RTT |
| Простое ops, MCK Community это умеет | 3× диск; initial sync тяжёлый |

##### Если шарды (когда один primary доказанно мал)

Минимум вендора для прода:

- CSRS: **3** члена, лучше 1-1-1 по ЦОДам.
- Каждый шард: **свой** PSS-3, не standalone.
- ≥1 `mongos` (лучше несколько, рядом с приложениями). Если перед ними прокси — **client affinity** на соединение (официально).
- Полный bidirectional network: `mongos` ↔ CSRS ↔ шарды.
- NTP.
- Шардов для распределения данных вендор: **минимум два** (один шард как «подготовка к шардам» допустим, но не масштабирует).
- Shard key проектировать **до** терабайт данных на коллекции, не после.
- Установщик: не `MongoDBCommunity`. Либо Enterprise/Ops Manager путь, либо ручная раскладка по мануалу шардов, либо другой оператор — это отдельное решение со своей матрицей совместимости с **7.0.40**. Не обещать «включим шарды флажком MCK Community».

##### Сильные / слабые стороны шардов на 3 ЦОДах

| Сильное | Слабое |
|---|---|
| Горизонталь диска и записи при ровном ключе | Ops: CSRS + N наборов + mongos; mesh портов |
| Отказ одного шарда не обязан гасить все коллекции | Scatter-gather на плохом ключе убивает latency |
| Вендор явно рекомендует 3 ЦОДа для CSRS/шардов | Community-оператор не ставит; reshard тяжёлый |
| | Транзакции/join-подобные aggregation дороже |

#### Persistence, память, производительность (общее)

| Параметр | Прод-правило | Зачем |
|---|---|---|
| `cacheSizeGB` | Явно, **меньше** memory limit пода (остаток на FS cache, агент, соединения) | Иначе кэш по RAM хоста → OOM |
| Сжатие | Дефолт snappy; zstd — лучше степень, другой CPU | Терабайты на диске ≠ терабайты в cache (в cache коллекции разжаты) |
| ФС | XFS на dbPath | Вендор: EXT4 + WiredTiger — риск деградации |
| THP | Выкл. | Latency |
| RAID | 10, не 5/6 | Production notes |
| Индексы | Под explainer реальных запросов; не «на все поля» | RAM + запись |
| `slowOp` | Включить профилирование осторожно (сам профилировщик стоит) | Без плана запросов масштаб не из чего считать |
| Бэкап | Снимки тома/CSI **с** journal, предпочтительно со **hidden secondary**; `mongodump --oplog` — для **небольших** деплоев | Реплика не бэкап; dump на терабайтах вендор сам относит к «impact неприемлем → snapshot» |
| Restore | Регулярный прогон | Непроверенный снимок = надежда |
| Antivirus | Exclude dbPath и логи | Иначе порча файлов |

Масштабирование под нагрузку, когда цифры появятся:

1. Замерить размер данных, индексов, working set vs cache, IOPS, p99, лаг replica, `w: majority` latency между ЦОДами.
2. Если CPU/IOPS primary и ключи разные — планировать шарды (и установщик).
3. Если RAM cache thrash — сначала индексы/проекции/не класть лишнее, потом RAM, потом шарды.
4. Если majority latency = RTT — решать 2-2-1 vs принять RTT vs ослабить concern **только** для данных, которые можно rollback (для эталона — нет).

#### Безопасность прода

Три слоя, все три:

1. **Сеть** — 27017 только приложениям и членам набора; 27018/27019 только компонентам шардов. NetworkPolicy. Не LoadBalancer в интернет.
2. **Аутентификация** — SCRAM и/или X.509; keyfile или X.509 **между** `mongod`. Не аноним.
3. **Авторизация** — RBAC least privilege: приложению интеграций не нужны `dropDatabase` / `userAdmin`.

| Слой | Правило |
|---|---|
| Authorization | `enabled` до боевых клиентов. Localhost exception — только процедура создания первого пользователя, не постоянный режим |
| TLS | Клиенты и replication/sharding между ЦОДами. Без TLS пароль SCRAM всё ещё едет по сети |
| Bind | Внутренний интерфейс, не `bindIpAll` «для удобства» |
| Процесс | Пользователь `mongod`, не root |
| At-rest | CSI/LUKS. Не путать с Enterprise encrypted storage engine |
| JS | `--noscripting`, если нет явной нужды |
| Аудит | В Community нет. Компенсация: централизованные логи auth, Wazuh/аналог, аудит в приложении. Если ИБ не принимает — это требование **Enterprise**, его надо эскалировать |
| Секреты | Пароли/keyfile не в Git; Secret/Vault |
| Ротация | Checklist: периодически патчить CVE (7.0.40 закрывает в том числе дефекты планировщика/запросов) и ротировать пользователей |

##### Сильные / слабые стороны (сеть + RBAC + TLS на Community)

| Сильное | Слабое |
|---|---|
| Штатные SCRAM, X.509, TLS, RBAC без Enterprise | Нет серверного аудита и native at-rest |
| Least privilege спасает от одного скомпрометированного сервиса | Модель «доверенная сеть» всё равно нужна |
| | Не ГОСТ; LDAP не встроен |
| | Ошибка RBAC = «сервис не пишет»; нужен процесс выдачи |

Если появится корпоративный IdP — Community 7.0 **не** становится LDAP-сервером. Людей в Mongo не пускают «логином как в AD» без Enterprise/прокси; пускают сервисы по SCRAM/X.509, людей — через контролируемый jump.

#### Kubernetes-специфика прода

- CR `MongoDBCommunity` / StatefulSet, **не** Deployment с ephemeral диском.
- PVC на dbPath; `emptyDir` в проде = каждый рестарт как новая нода (initial sync) или потеря standalone.
- Topology spread: voting members в **разных** зонах по выбранной схеме 1-1-1 или 2-2-1.
- PDB: не снять сразу majority (не эвакуировать 2 из 3 PSS одновременно).
- Ресурсы: memory limit **выше** cache + запас. CPU throttle → ложные выборы (нода «не отвечает» в heartbeat).
- `cacheSizeGB` обязателен в контейнере.
- Не ставить Mongo на overlay с большим jitter без замера. Если pod-сеть между ЦОДами хуже VM — члены иногда лучше вне общего кривого overlay. Решение по замерам.
- Пинить образ `7.0.40-ubi9-slim` и версию оператора. Не `latest`. Не возвращаться на EOL Community Operator.
- Rolling upgrade должен переживать `stepDown` / выборы. Drain primary без stepDown = простой записи.
- sidecar `mongodb-agent` в MCK — отдельный потребитель CPU/RAM в смете пода.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами на 27017 (и портах шардов, если они в плане). Решение A vs B vs C.
2. Зафиксировать состав данных, индексы, write concern. Юристы — SSPL. ИБ — нет аудита/native at-rest.
3. Выбрать PSS-3 / PSS-5. Шарды — только с доказанной причиной и отдельным установщиком.
4. Хостовые THP/NUMA/XFS/CSI. Поставить 7.0.40, auth, TLS, cacheSizeGB **до** боевых клиентов.
5. Снять тестовый снимок, прогнать restore на другой namespace.
6. Подключить клиент **replica set URI**, `w: majority` + `wtimeout` там, где нужен SoT.
7. `rs.stepDown()`, убедиться что приложение продолжает.
8. Нагрузить синтетикой, снять latency/cache eviction/лаг/slow queries. По результату — диск, RAM, решение о шардах.
9. Прогон «ЦОД недоступен» на препроде: выключить зону, проверить кворум, запись, что эталон/интеграции делают то, что обещали бизнесу.
10. Только потом — реальные документы интеграционного API и Camunda.

Без пункта 9 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | PSS ≥3, voting в разных ЦОДах по офиц. схеме 1-1-1 или 2-2-1; цель — 1 ЦОД; прогнанные stepDown, потеря зоны и restore |
| Производительность / масштаб | Не требуется | cacheSizeGB в контейнере; XFS/SSD; индексы под запросы; горизонталь записи только шардами; не путать replica с масштабом |
| Безопасность | Isolated сеть; 27017 не в LAN офиса без auth | Authorization; RBAC least privilege; TLS на клиентах и между ЦОДами; keyfile/X.509 между членами; NetworkPolicy; не root; JS выкл. если не нужен |

**Не готов к проду**, если: один `mongod` выдают за HA; PSA с молчаливым `w: 1`; `authorization` выключен; клиенты без replica set URI; все voting в одном ЦОДе; RTT неизвестен, а схема уже stretch; cacheSizeGB не задан в K8s; бэкап = «есть secondary»; шарды обещаны через `MongoDBCommunity`; образ `latest` / не 7.0.40; Community поставлен без решения по SSPL; Mongo назначен SoT, а чтение идёт на secondary «для скорости» без принятого лага; ждут LDAP/аудит/KMIP от Community.
