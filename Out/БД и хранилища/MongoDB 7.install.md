# MongoDB Community Server 7.0.40 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `MongoDB 7.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

MongoDB — документная база. Ставите **свою** копию Community Server, не облако Atlas и не Enterprise.

Версия в этой инструкции: **7.0.40**. Образ: `mongodb/mongodb-community-server:7.0.40-ubi9-slim` (не `7.0-ubi9-slim`, не `latest`, не устаревший `library/mongo` как единственный ориентир). Лицензия сервера — **SSPL**. Без решения юристов этот файл не разрешение ставить Community 7.0.

На Kubernetes — оператор **MCK 1.10.0** (30 июля 2026), объект **`MongoDBCommunity`**, тип официально **только `ReplicaSet`**. Старый Community Operator — EOL, не начинать с него. Документация линейки: https://www.mongodb.com/docs/v7.0/ · MCK: https://www.mongodb.com/docs/kubernetes/current/

Это **не** замена Kafka и **не** кэш (кэш — Redis/Valkey). Роль озера за Mongo в исходном запросе не закреплена.

Один набор, размазанный на несколько дата-центров, здесь **не собираем**. Выборы главного и пульс между узлами чувствительны к задержке сети; в документации нет цифры «сколько миллисекунд ещё можно». Поэтому живой набор — внутри одной площадки. Вторая площадка — скрытая копия или снимок, не вторая половина того же голосования.

---

## О чём эта инструкция молча договорилась

1. Все **голосующие** члены replica set живут **в одном дата-центре** (одном Kubernetes). Между площадками — скрытая копия без голоса **или** только бэкапы. Автосмена главного в чужой дата-центр **не** цель.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`).
3. Юристы **принимают SSPL** для закрытого контура.
4. Учебный стенд — закрытая сеть. Один процесс без пароля допустим **только там**.
5. Цифр вашей нагрузки нет — нет фразы «хватит N шардов». Шарды на старте **не** ставим: `MongoDBCommunity` их не описывает.
6. Два дата-центра: голосующая тройка в первом; второй — скрытая копия или бэкап. Три дата-центра: то же. Третья площадка **не** добавляет второго писателя.
7. Схему «два диска + arbiter без данных» в бой **не** берём: завод тогда тихо ставит `{ w: 1 }`, и majority-запись ломается при падении одной ноды с данными.
8. Native encryption at rest / аудит / LDAP — **Enterprise**, не Community.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** писать документы, подобрать индексы, подключить драйвер микросервиса. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- На localhost свободен порт 27017.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name mongo-dev \
  -p 127.0.0.1:27017:27017 \
  mongodb/mongodb-community-server:7.0.40-ubi9-slim
```

Привязка к `127.0.0.1` обязательна: внутри контейнера процесс слушает шире localhost. `-p 27017:27017` на все интерфейсы рабочей станции **нельзя**.

Проверка — в ответе должна быть версия **7.0.40**:

```bash
docker exec -it mongo-dev mongosh --eval "db.runCommand({ ping: 1 })"
docker exec -it mongo-dev mongosh --eval "db.version()"
```

`ok: 1` и версия **7.0.40**. Затем заведите **отдельного** пользователя для приложения, не ходите в базу как администратор:

```bash
docker exec -it mongo-dev mongosh --eval '
db.getSiblingDB("app").createUser({
  user: "app",
  pwd: "dev-app",
  roles: [ { role: "readWrite", db: "app" } ]
})
'
```

Клиент — `localhost:27017`, база `app`, роль `app`. Лимит документа **16 МБ** поймать до боя. Change stream на чистой одиночке **нет** — для прототипа «по событию документа» на препроде нужен replica set.

На Kubernetes для учёбы: MCK 1.10.0, затем `MongoDBCommunity` с `members: 1` только если команда понимает: это **не** отказоустойчивость. Для препрода лучше сразу `members: 3` **в одной зоне**.

```bash
kubectl apply -f https://raw.githubusercontent.com/mongodb/mongodb-kubernetes/1.10.0/public/crds.yaml
kubectl apply -f https://raw.githubusercontent.com/mongodb/mongodb-kubernetes/1.10.0/public/mongodb-kubernetes.yaml
```

Либо Helm-репозиторий `https://mongodb.github.io/helm-charts`, чарт `mongodb/mongodb-kubernetes`, пин **1.10.0** (сверить с каталогом чарта, не `latest`).

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Число нод | 1 | Не учимся переживать обновление |
| Replica set | можно без | Иначе URI раньше документов |
| TLS | нет, сеть закрыта | Иначе сертификаты раньше схемы |
| Пароль | можно без, **только loopback** | Завод сервера права выключает — не тащить это в бой |
| `cacheSizeGB` | 256–512 МБ явно, если Kubernetes | Иначе процесс считает RAM **хоста** |
| Шарды / mongos | нет | Иначе ключ шардирования раньше модели |

Чего **не** упрощаем: номер версии **7.0.40**; имена полей и индексы под ваши запросы; клиент ходит на имя хоста, не на сырой IP.

### Как понять, что стенд живой

1. `db.version()` возвращает 7.0.40.
2. Приложение ходит пользователем `app`, не администратором.
3. Контейнер перезапустили с томом — данные на диске на месте.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный Community-образ | Нет выборов, нет `w: majority`, нет полной синхронизации на другую машину |
| Одиночка официально нормальна для разработки | Успешный `insert` **не** доказывает боевую схему |
| | Открытый 27017 без пароля на Wi-Fi = дыра |
| | Change stream на одиночке недоступен |

Перед боем полезен **препрод**: 3 копии с данными **в одном** дата-центре, SCRAM, TLS внутри набора, `w: majority` + `wtimeout`, размер кэша задан явно.

## Бой: один живой дата-центр, второй — запас из снимка

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три голосующих члена, запись подтверждается большинством). Отказ **всего дата-центра, где лежит набор** = записи нет, пока вручную не восстановите снимок на другой площадке или не переключите конфиг голосования. При архивном восстановлении часть свежих данных можно потерять — это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Выборы идут по большинству **голосующих** членов. Пульс — **2 с**, таймаут выборов — **10 с**. Если задержка сети между площадками плавает, начнутся ложные выборы и откат хвоста записей `{ w: 1 }`. Официальные гео-примеры «по одному члену в дата-центр» — как раз растягивание голосования. Порога миллисекунд у MongoDB **нет** — поэтому здесь так не делаем. Схема с arbiter в чужой площадке «чтобы сэкономить диск» ещё хуже: majority-запись ломается, завод тихо ставит `{ w: 1 }`.

### Как расставить в активном дата-центре

Один replica set:

- Три **голосующих** `mongod` с данными на **разных нодах этой** площадки. Это официальный минимум боя, не «хватит терабайтов».
- Клиенты: replica set URI (`replicaSet=...`) или SRV, повтор записи при смене главного. Балансировщик «как HTTP на все 27017» **ломает** модель.
- `{ w: "majority" }` + **ненулевой** `wtimeout` на факты, которые нельзя откатить после смены главного.
- Том локальный, XFS на каталоге данных настоятельно рекомендуется, **не NFS** как основной диск.
- `storage.wiredTiger.engineConfig.cacheSizeGB` **явно**, меньше лимита памяти пода.
- Образ / `spec.version`: **7.0.40**.
- Журналирование включено (завод). Не выключать.
- Oplog: спланировать окно «максимальное время, на которое копия или бэкап может отстать». Маленький oplog на больших данных = полная синхронизация в худший момент.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: голосующая тройка. Вторая: член с `priority: 0` (часто **скрытый**) — копия через oplog **без** голоса **или** только снимок в объектное хранилище | Записи нет, пока restore или ручной пересчёт состава набора (поставщик описывает это как процедуру аварии, не автосмену). Скрытая копия кворум не спасает: голосов на второй площадке нет |
| **Три** | Третья: ещё одна скрытая копия **или** только бэкапы | То же. Третий дата-центр не даёт второго primary |

`MongoDBCommunity` живёт в **одном** Kubernetes: три голосующих пода — в кластере первой площадки. Скрытая копия в чужом Kubernetes — это уже отдельный `mongod` с именем в наборе (обмен на 27017, TLS, keyfile), не «ещё один members: в объекте другого дата-центра». Если обмен между площадками не хотите держать открытым — **только бэкапы**.

Клиенты второй площадки в штате ходят в URI первой по городу (**TLS обязателен**) **или** читают скрытую копию (лаг; поставщик **не** рекомендует это как основной путь; для эталона опасно).

Пять полных копий вместо трёх имеют смысл, только если замерили, что majority-задержка тройки неприемлема, и готовы платить диском. Шарды — когда **доказали**, что один primary упирается в объём или запись, и есть кандидат ключа. Установщик шардов — не `MongoDBCommunity`: либо Enterprise/Ops Manager, либо ручная раскладка, либо другой оператор. Не обещать «включим шарды флажком Community».

Несколько **разных** наборов (операционка сервиса ≠ метаданные Grafana) — отдельные контуры отказоустойчивости.

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемой скоростью, один том на один под. Хост: Transparent Huge Pages выкл., NUMA interleave, `vm.swappiness` 0 или 1.
- Сетевая политика: клиенты → 27017; обмен набора — только член↔член.
- Секреты и keyfile — в Vault, не в git.
- NTP. Имена — DNS, не голый IP.
- Совместимость Helm-тега с MCK 1.10.0 уже прогнана на стенде.

### Порядок установки в активном дата-центре

```bash
kubectl create namespace mongodb
kubectl apply -f https://raw.githubusercontent.com/mongodb/mongodb-kubernetes/1.10.0/public/crds.yaml
kubectl apply -f https://raw.githubusercontent.com/mongodb/mongodb-kubernetes/1.10.0/public/mongodb-kubernetes.yaml
kubectl -n mongodb rollout status deployment/mongodb-kubernetes-operator
```

Оператор — не в одном поде с `mongod`.

Смысл объекта (не полный манифест — сверять спецификацию `MongoDBCommunity` MCK 1.10):

```yaml
apiVersion: mongodbcommunity.mongodb.com/v1
kind: MongoDBCommunity
metadata:
  name: mongo-app
  namespace: mongodb
spec:
  members: 3
  type: ReplicaSet
  version: "7.0.40"
  security:
    authentication:
      modes: ["SCRAM"]
    tls:
      enabled: true
  additionalMongodConfig:
    storage.wiredTiger.engineConfig.cacheSizeGB: 1  # заглушка: меньше лимита пода; не формула хоста
  users:
    - name: app
      db: app
      passwordSecretRef:
        name: mongo-app-password
      roles:
        - name: readWrite
          db: app
      scramCredentialsSecretName: app-scram
```

Обязательно рядом:

1. Пользователь приложения **без** права администрировать пользователей. Сначала администратор, потом остальные.
2. Внутренний секрет: keyfile или X.509 между членами (оператор обычно закрывает — **проверить**, не поверить).
3. `--noscripting`, если нет явной нужды в серверном JavaScript.
4. Политика сбоя подов: не эвакуировать сразу двоих из трёх голосующих.
5. Бэкап: снимок тома **с** журналом, предпочтительно со скрытой копии; `mongodump --oplog` поставщик относит к **небольшим** установкам. Проверяют **восстановление**.
6. Клиенты: проверка TLS, короткий timeout, переподключение. Не IP пода.

Скрытая копия на второй площадке: `priority: 0`, `hidden: true`, `votes: 0`. Это копия для аварии/отчётности, не участник выборов. Сделать её голосующей — **ручной** пересчёт состава.

Антивирус исключить из каталога данных и логов. Сжатие коллекций — завод snappy; zstd — лучше степень, другой CPU.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Права | Включены до боевых клиентов. Localhost-исключение — только создание первого пользователя | Завод права выключает |
| Write concern | `{ w: "majority" }` + ненулевой `wtimeout` | `{ w: 1 }` допускает откат после выборов |
| Arbiter | нет | Тихий `{ w: 1 }` и поломка majority при падении ноды с данными |
| `cacheSizeGB` | Явно, **меньше** лимита памяти пода | Иначе кэш по RAM хоста → процесс убивают |
| ФС каталога данных | XFS | Поставщик: EXT4 + WiredTiger — риск деградации |
| RAID | 10, не 5/6 | Production notes |
| TLS | Клиенты и обмен между узлами | Без TLS пароль SCRAM едет открытым текстом |
| Bind | Внутренний интерфейс | Не все адреса «для удобства» |
| Процесс | Пользователь `mongod`, не root | |
| At-rest | Шифрование тома. Не путать с Enterprise encrypted storage engine | |
| Аудит | В Community нет. Компенсация: логи подключений, SIEM, аудит в приложении | Если ИБ не принимает — эскалировать Enterprise |

Политика сбоя подов: не давать Kubernetes снять сразу majority. Обновление **по одной** ноде. Снять primary без `stepDown` = простой записи. Sidecar агента в MCK — отдельный потребитель CPU/RAM в смете пода.

### Как расти, когда появятся цифры нагрузки

1. Замерить размер данных и индексов, рабочий набор против кэша, IOPS, задержку, лаг копии, соединения.
2. Упёрлись CPU/IOPS primary — вертикаль или шарды (**не** через `MongoDBCommunity`). Копия **не** ускоряет запись.
3. Упёрлись RAM кэша — сначала индексы и проекции, потом RAM.
4. Тяжёлые отчёты — не primary эталона (склад/ClickHouse).
5. Журналирование **не** выключать.

### Проверки, без которых это ещё не бой

1. `db.version()` = 7.0.40 на **всех** членах активной площадки.
2. Запись `w: majority` + `wtimeout`; чтение; запись на копию — не как основной путь.
3. Сменили главного (`rs.stepDown()`): приложение переподключилось, документы на месте.
4. Восстановили снимок на чистый набор **на стенде**.
5. Учение «активный дата-центр выключен»: запись стоит; restore/пересчёт состава на второй площадке прогнали хотя бы раз (время простоя замерить).
6. Права включены; приложение без роли не пишет.

### Что хорошо и что плохо в схеме «набор в одном дата-центре + снимок»

| Хорошо | Плохо |
|---|---|
| Выборы не зависят от задержки между городами | Падение этой площадки = нет записи, пока restore/пересчёт |
| Согласовано с MCK Community (ReplicaSet в одном Kubernetes) | Между площадками можно потерять хвост (скрытая копия догоняет асинхронно; чисто архив — ещё больше) |
| Тройка с данными — официальный минимум боя **внутри** площадки | Ручная авария; нет native at-rest и аудита в Community |
| | Клиентский 27017 через город — TLS и сеть ваши |

**Не готово к бою**, если: один процесс выдают за отказоустойчивость; схема с arbiter; голосующие размазаны по дата-центрам; права выкл.; нет размера кэша в контейнере; клиенты без replica set URI; бэкап = «есть сосед»; шарды обещаны через `MongoDBCommunity`; образ не 7.0.40 / `latest`; SSPL не закрыт юристами; чтение эталона с копии «для скорости» без принятого лага; учебный манифест уехал в бой.
