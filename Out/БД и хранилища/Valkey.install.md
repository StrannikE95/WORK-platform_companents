# Valkey 9.1.1 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Valkey.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Valkey — слой ускорения и координации (кэш, сессии, лимит, локи), не эталон и не замена Kafka/PostgreSQL. Ставите **свою** копию, не облако Redis.

Версия в этой инструкции: **9.1.1** (не 9.1.0: SECURITY, CVE-2026-56684 / CVE-2026-63639). Образы: `valkey/valkey:9.1.1` (также `-alpine`, `-trixie`). Лицензия **BSD-3**.

На Kubernetes: официальный Helm **`valkey-io/valkey-helm`**, чарт `valkey` **0.11.0**, `appVersion` **9.1.1** — одиночка **или** primary+replica. **Не** Cluster. **Не** Sentinel.  
Оператор `valkey-io/valkey-operator` (релизы до v0.5.0): README — *not ready for production use*. В бой **не берём**.

Документация: https://valkey.io/ · Helm: https://valkey.io/valkey-helm/

Один Sentinel-набор или Cluster, размазанный на несколько дата-центров, здесь **не собираем**. Репликация асинхронная; детект отказа живёт heartbeat. Порога задержки нет. Живой набор — внутри одной площадки. Вторая площадка — независимый Valkey или клиенты ходят в «домашний» дата-центр.

---

## О чём эта инструкция молча договорилась

1. Primary, replica и (если ставите) Sentinel-кворум живут **внутри одного дата-центра**. Между площадками — независимые Valkey **или** клиенты ходят в домашний. Растягивание узлов по трём Kubernetes — та же цена задержки.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`).
3. Упаковка не-Cluster: Helm **`valkey` 0.11.0**. Sentinel в чарт **не входит** — отдельные манифесты **или** сознательно принимаете ручную смену primary.
4. Учебный стенд — закрытая сеть. Пароль в примере не секрет.
5. Цифр вашей нагрузки нет — нет цифры `maxmemory` «хватит для боя».
6. Два дата-центра: активный набор в первом; второй — независимый Valkey или только клиенты в первый. Три дата-центра: то же. Третья площадка **не** добавляет второго писателя на те же ключи.
7. Клиенты умеют Sentinel, **если** вы его ставите. Service `valkey` чарта — это писатель; после смены primary без Sentinel DNS сам не «переедет».
8. Persistence в бою **включена**. На Kubernetes «кэш без диска» конфликтует с безопасностью репликации: kubelet рестартит пустой primary, replica синхронизируются с пустым (вендор это запрещает).

---

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** SET/GET, ACL, шум приложения. **Не зачем:** доказывать отказ площадки и шарды.

### Что должно быть до установки

- Docker **или** учебный Kubernetes с Helm 3.
- На localhost свободен порт 6379.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name valkey-dev \
  -p 127.0.0.1:6379:6379 \
  valkey/valkey:9.1.1
```

Привязка к `127.0.0.1` обязательна. В контейнере процесс обычно слушает все интерфейсы.

Проверка — `PONG`; в `INFO` должна быть линия **9.1.1** (Valkey отвечает совместимым полем версии):

```bash
docker exec -it valkey-dev valkey-cli PING
docker exec -it valkey-dev valkey-cli INFO server
```

Затем хотя бы один SET/GET из **вашего** сервиса, не только cli.

На Kubernetes для учёбы:

```bash
helm repo add valkey https://valkey.io/valkey-helm/
helm repo update
helm install valkey-dev valkey/valkey --version 0.11.0 \
  --set image.tag=9.1.1
```

Одиночка, replica выкл., persistence по умолчанию чарта **выкл.** — рестарт пода = пустой кэш. Если сеть шире ноутбука: `auth.enabled=true` и пользователь `default` в ACL (иначе, цитата чарта, *anyone can access the database without credentials*).

Режим «Cluster на Minikube через valkey-operator» для знакомства **не нужен**: оператор не для боя, получите ложное чувство отказоустойчивости.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Sentinel / Cluster | нет | Нет требования пережить primary |
| Replica | 0 | Нет нагрузки на чтение |
| PVC | emptyDir / persistence off | Данные стенда не жалко |
| TLS | нет | Иначе сертификаты раньше продукта |
| `maxmemory` | можно не ставить | Датасет игрушечный |
| `min-replicas-to-write` | 0 | Нет replica |
| `auth.enabled=false` | только loopback | Привычка без ACL уедет в бой — на общем учебном кластере включайте |

Чего **не** упрощаем: тег **9.1.1**; понимание, что Service `valkey` — писатель, на `valkey-read` после появления replica на запись не ходить. Не включать replication **без** тома «на поиграть».

### Как понять, что стенд живой

1. PING / SET / GET с клиента приложения.
2. Рестарт контейнера без тома: ключи пропали — ожидаемо.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный образ и чарт 0.11.0 | Нет модели отказа primary |
| Совпадает с путём проекта (Helm standalone) | Успех GET ≠ Sentinel-клиент и ≠ `WAIT` |
| | Успешный Docker **не** есть готовность боя |

Перед боем полезен **препрод**: тот же Helm **replication** с томом + ACL + (если цель автосмены) три Sentinel **в одном дата-центре**.

## Бой: один живой дата-центр, второй — запас из снимка

**Зачем:** пережить отказ **пода или ноды внутри площадки**; пережить отказ **целого дата-центра** ценой промаха в кэше и ручной аварии. Цифр операций в секунду нет.

### Почему кластер не растягиваем на несколько дата-центров

Репликация **async**: OK клиенту ≠ запись на replica. Sentinel/Cluster живут heartbeat. При плохой задержке — ложная смена primary и потеря хвоста. Cluster: primary, который не видит majority других primary дольше таймаута ноды (в учебнике пример **5000** мс), **перестаёт принимать запросы**. Официальный Helm Cluster **не ставит**; оператор Cluster в бой нельзя. Порога миллисекунд **нет**.

### Как расставить в активном дата-центре

Helm replication + (для автосмены) Sentinel:

- чарт **0.11.0**, образ **9.1.1**;
- replica включены, том **обязателен** (на primary и replica);
- replica на **других нодах**, чем primary (разнести внутри площадки);
- **3 Sentinel** в этом же дата-центре, разные ноды, кворум **2**. Не 2 Sentinel. Файл `sentinel.conf` записываемый;
- клиенты: discovery через Sentinel (26379), затем 6379. Не хардкодить DNS primary навсегда;
- Helm **не** делает смену primary сам: без Sentinel падение писателя = простой записи, пока не `REPLICAOF` руками;
- Persistence: AOF `everysec` + RDB (вендор: если данные важны — *use both*; AOF-only не советует). Не выключать снимки «для скорости» на primary с replica и авторестартом;
- `min-replicas-to-write 1`, `min-replicas-max-lag 10` (как в примере Helm/conf) — если потеря подтверждённой записи больнее, чем короткий отказ записи. Для кэша с TTL можно оставить 0 **осознанно**. Завод Helm **0** — легко забыть;
- политика сбоя подов: не снять все копии одним drain;
- primary и хотя бы одна replica не на одном узле.

Cluster 3+3 **не** ставим этим чартом и **не** ставим valkey-operator. Если когда-нибудь понадобятся шарды — отдельное решение (VM по cluster tutorial **внутри одного дата-центра** или ждать GA оператора), не эта инструкция. В Cluster: `appendonly yes` в минимальном примере вендора; не открывать 16379 с мира; не Docker NAT; после смены primary клиент **обновляет карту слотов**.

Замки/сессии, которые нельзя вытеснять: отдельный инстанс, не смесь с кэшем UI.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: Helm replica + 3 Sentinel. Вторая: **независимый** Valkey (свой кэш) **или** только клиенты в первую | Локальный независимый кэш жив, но холоден. Клиенты «в домашний дата-центр» — кэша нет, пока приложение не переживает промах → озеро/API |
| **Три** | Вторая и третья: независимые Valkey **или** клиенты в первую + бэкапы RDB | То же; три независимых набора = три правды сессий, если ключи не режет приложение регионально |

Не копировать «как DaemonSet в каждый кластер» одни и те же сессии: получите три кэша. Для эталона это нормально (истина в озере). Для сессий UI — разлогин. Для идемпотентности внешнего вызова — риск повтора, пока ключ не восстановится.

### Что должно быть до боевой установки

- Выделенные ноды, локальный диск, не NFS.
- Сетевая политика: 6379 приложениям; 26379 только Sentinel+клиентам Sentinel.
- PKI, если TLS (в доке Valkey при включённом TLS по умолчанию **mTLS** клиентов; Helm `tls.requireClientCertificate` завод **false** — ослабление, в бою решить сознательно).
- Не проброс портов Docker / NAT для Sentinel.

### Порядок установки в активном дата-центре

```bash
helm repo add valkey https://valkey.io/valkey-helm/
helm repo update
helm install valkey valkey/valkey --version 0.11.0 \
  --namespace valkey --create-namespace \
  -f valkey-prod-values.yaml
```

Смысл values (не полный файл — сверять README чарта **0.11.0**):

```yaml
image:
  repository: valkey/valkey
  tag: "9.1.1"
auth:
  enabled: true
  usersExistingSecret: valkey-users
  aclUsers:
    default:
      permissions: "~* &* +@all"   # сузить; не +@all у приложения
    replication-user:
      permissions: "+psync +replconf +ping"
replica:
  enabled: true
  replicas: 2
  replicationUser: replication-user
  persistence:
    size: 10Gi   # заглушка: диск AOF может быть больше датасета; цифр нагрузки нет
  minReplicasToWrite: 1
  minReplicasMaxLag: 10
tls:
  enabled: true
  existingSecret: valkey-tls
podDisruptionBudget:
  enabled: true
  maxUnavailable: 1
```

Затем **отдельно** — 3 Sentinel (манифесты не из этого чарта). `SENTINEL CKQUORUM` в мониторинге. Auth Sentinel — тот же класс секретов, что у узлов данных: иначе 26379 — пульт смены primary для злоумышленника.

На второй/третьей площадке при независимом кэше: тот же чарт **0.11.0** / **9.1.1**, свой Secret, свой endpoint. Разный bootstrap, не один values на всю страну.

Пин образа **9.1.1** (digest), свой registry. Метрики exporter — с auth к Valkey, не анонимный 6379 «для scrape». Не балансировщик в интернет.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| `maxmemory` | Ниже лимита контейнера, запас на буферы replica / сжатие AOF / фрагментацию | Иначе процесс убивают. Вендор: при `maxmemory` на primary с replica нужен запас RAM на буферы |
| `maxmemory-policy` | Кэш: явно LRU/LFU, не молчаливый `noeviction` | При заполнении `noeviction` **встанет запись** |
| Persistence | AOF `everysec` + RDB | Вендор: *use both* |
| ACL | Нет общего `default` с `+@all` у приложений; пользователь репликации минимальный (`+psync +replconf +ping` — минимум из Helm README) | Helm без `default` при `auth.enabled` = дыра |
| `min-replicas-to-write` | По политике (завод Helm **0** — легко забыть) | 0 = пишем при обрыве replica |
| 16379 | Только между нодами Cluster; `tls-cluster yes` | Без этого захват слотов |

### Как расти, когда появятся цифры нагрузки

1. Замерить горячий набор, вытеснение, лаг replica, отказы записи.
2. Больше RAM → вертикаль primary **или** второй независимый набор по домену ключей. Озеро «терабайты» сюда не скейлится.
3. Больше чтения → replica (клиенты терпят отставание).
4. Больше записи → не этот Helm (один писатель). Горизонталь записи — Cluster, которого у GA-установщика нет, или несколько наборов.
5. `io-threads` — опция под замер, не слайд.

### Проверки, без которых это ещё не бой

1. Образ/INFO = **9.1.1** (не 9.1.0).
2. Рестарт primary: replica **не** обнуляются.
3. Убили primary: приложение (не только cli) пишет в новый, **если** Sentinel стоит; без Sentinel — зафиксированный простой.
4. Попытка без ACL — отказ. 6379 не с мира.
5. Учение «активный дата-центр мёртв»: клиенты второй площадки делают промах/локальный кэш так, как обещали бизнесу.

### Что хорошо и что плохо в схеме «Helm replica + Sentinel в одном дата-центре + независимый запас»

| Хорошо | Плохо |
|---|---|
| Официальный сервер и официальный чарт 0.11.0 | Sentinel собираете сами; чарт Cluster не умеет |
| Кворум не зависит от задержки между городами | Падение этой площадки = нет этого кэша |
| BSD, без RSALv2 | Async: OK ≠ запись на replica |
| CVE 9.1.1 закрыты | Забыть пин — снова выполнение кода на TLS |

**Не готово к бою**, если: одиночка на три площадки «для HA»; Helm replica без тома; два Sentinel; `valkey-operator` как бой; Cluster через этот чарт; `latest` / 9.1.0; 6379 с мира без ACL; эталон клиентов в Valkey; клиенты без Sentinel при обещании автосмены; `auth.enabled` без пользователя `default`; растянули вопреки запрету задержки; учебные values уехали в бой.
