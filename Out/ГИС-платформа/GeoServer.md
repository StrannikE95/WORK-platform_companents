# GeoServer 2.24 — развёртывание и настройка

Версия ПО: **GeoServer 2.24.4** (последний патч линии 2.24.x; релиз **18 июня 2024**, вместе с GeoTools 30.4 и GeoWebCache 1.24.4).  
Документация линии: https://docs-archive.geoserver.org/2.24.x/en/user/  
Скачивание релиза: https://geoserver.org/release/2.24.4/  
Официальный контейнер (User Manual 2.24): `docker.osgeo.org/geoserver:2.24.x`. Для прода **не** nightly-тег `2.24.x`, а **конкретный патч** `2.24.4`, если тег есть в реестре OSGeo; иначе — свой образ из **WAR 2.24.4** на Tomcat 9.  
WAR / bin / Windows installer — с той же страницы релиза. Расширения — zip с **той же** minor/patch, что и сервер.

Этот текст — не мануал «скопируй docker run и забудь», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

GeoServer **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить **картографический / OGC-сервер** на ту же инфраструктуру (Kubernetes, 3 ЦОДа). Это **не** озеро эталона, **не** шина событий, **не** Camunda и **не** платформа GeoData (ООО «АйТи Гео», у вас на неё отдельный документ).

**Критично по версии.** По [расписанию релизов проекта](https://github.com/geoserver/geoserver/wiki/Release-Schedule): линия **2.24.x** вышла в stable в сентябре 2023, maintenance — апрель 2024, **EOL — август 2024**. На дату подготовки этого файла (август 2026) линейка **два года без официальных патчей**. 2.24.4 закрывал в том числе **CVE-2024-36401 (RCE, Critical)**. Всё, что нашли **после** июня 2024, в 2.24.x проект **не чинит**. Документ описывает **запрошенную** версию; считать её «готовой к проду с гособменом» без отдельного решения ИБ — нельзя.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **OGC** | Консорциум, который стандартизирует «как говорить про карты и объекты по HTTP». GeoServer — сервер этих протоколов. |
| **WMS** | «Нарисуй мне картинку карты» (PNG/JPEG) по слоям, bbox, стилю. Тяжёлый по CPU/RAM, особенно на растрах. |
| **WFS** | «Отдай объекты» (точки, линии, полигоны) в GML/GeoJSON. Чтение. |
| **WFS-T** | То же + **запись**: клиент может менять объекты в хранилище. В проде часто выключают. |
| **WCS** | «Отдай растр/покрытие» (не картинку для глаз, а сетку значений). |
| **WMTS / TMS / WMS-C** | «Отдай готовый квадратик карты (тайл)». Обычно отдаёт **GeoWebCache**, не «живой» WMS. |
| **WPS** | «Посчитай что-нибудь на сервере» (буфер, пересечение…). Состояние между нодами **не** общее без отдельного расширения. |
| **Слой (layer)** | Опубликованный набор: «здания», «ЗУ», «тепловая карта». Клиент просит слой по имени. |
| **Workspace** | Папка/неймспейс слоёв (чтобы `topp:states` не пересекался с вашим `egrn:parcel`). |
| **DataStore / CoverageStore** | Подключение к данным: PostGIS, Shapefile, GeoTIFF, … Слой смотрит в store, а не «лежит внутри GeoServer». |
| **Каталог (catalog)** | Список workspace / store / layer / стилей. В классическом GeoServer это XML-файлы в **data directory**. |
| **Data directory (`GEOSERVER_DATA_DIR`)** | Каталог на диске: конфиг, security, логи, иногда стили и файловые данные. Без внешнего каталога апгрейд и бэкап ломаются. |
| **GeoWebCache (GWC)** | Встроенный тайловый кэш. Сохраняет уже нарисованные тайлы, чтобы не гонять WMS каждый раз. |
| **`GEOWEBCACHE_CACHE_DIR`** | Где лежат файлы тайлов. Если у каждой ноды свой каталог — кэш **разный**, клиент «мигает». |
| **Capabilities** | XML «что умеет сервис»: список слоёв, SRS, операции. URL в нём должен быть **публичным** (`PROXY_BASE_URL`), иначе клиенты ходят на внутренний `http://pod:8080`. |
| **`PROXY_BASE_URL`** | Базовый URL «как нас видит мир» за reverse proxy (`https://maps.example.ru/geoserver`). |
| **SLD / стиль** | Правила отрисовки (цвет, подпись). Файлы стилей — часть конфига; в кластере их тоже надо синхронизировать. |
| **PostGIS** | Расширение PostgreSQL для геометрии. Типичное **хранилище объектов**, которое GeoServer читает. Это **другое** ПО. |
| **Растр / вектор** | Растр — картинка/сетка (космос, ЦМР). Вектор — объекты с атрибутами. Официально: вектору «больше heap» почти не помогает (стриминг); растру — помогает tile cache в heap. |
| **JAI / JAI-EXT / Marlin** | Библиотеки отрисовки. В 2.24 JAI-EXT **включён по умолчанию**. Marlin — растеризатор линий; на Java 17 в bin-сборке его иногда приходится снимать. |
| **Control-flow** | **Стабильное** расширение: очередь и лимиты параллельных OWS-запросов, чтобы один клиент не убил JVM. |
| **Community-модуль** | Плагин **не** из официального релиза на SourceForge. Экспериментальный, «as is». JAR с **nightly** на релиз **2.24.4** часто **не встанет**. Нужна сборка с git-тега `2.24.4`. |
| **JMS-cluster** | Community: шина ActiveMQ разносит **изменения каталога** Primary → Replica. **Данные слоёв по JMS не едут.** |
| **JDBCConfig / JDBCStore** | Community: каталог (и файлы стилей/иконок) в СУБД, ноды подтягивают изменения без полного рестарта. Цена — нагрузка на БД и на запросы. |
| **GeoServer Cloud** | **Другой** продукт: микросервисы WMS/WFS/REST + брокер + `pgconfig`. Официально его рекомендуют для Kubernetes. Это **не** «GeoServer 2.24 WAR в трёх репликах». |
| **Primary / Replica (JMS)** | Кто имеет право менять конфиг / кто только принимает сообщения. Путать с PostgreSQL primary — ошибка. |
| **`CLUSTER_CONFIG_DIR`** | Если **общий** data dir на несколько JVM — у каждой свой каталог `cluster.properties`. Иначе ноды перетирают настройки кластера. |
| **CSRF** | Защита админки от подделки форм с чужого сайта. За proxy без whitelist ломает UI (`Origin does not correspond to request`). |
| **XXE / entity resolution** | Разбор XML во входных запросах. Без allow-list сервер может сходить на внешние URL (и иногда к файлам) по указке клиента. |
| **Master password** | Отдельный пароль хранилища ключей/шифрования настроек security. В Docker README явно: сменить вместе с `admin`. |
| **`admin` / `geoserver`** | Дефолтный логин админки. Известен всем, кто открывал документацию. |
| **Sticky session** | Балансировщик всегда шлёт одного пользователя на одну ноду. Нужно админке/некоторым WPS, не нужно обычному GetMap. |
| **RWX / RWO** | В Kubernetes: диск, который можно отдать **нескольким** подам сразу / **только одному**. Data dir на RWO + 3 реплики = не стартуют или порчу конфига. |
| **RPO / RTO** | Сколько конфига/тайлов готовы потерять / как быстро поднять карту снова. У GeoServer нет встроенного «кворума как у etcd». |

## Основные элементы системы и зависимости

### Что входит в «экземпляр GeoServer 2.24.4»

Это **одно** Java-приложение (WAR) в контейнере сервлетов. Роли внутри одного процесса:

| Кусок | Зачем | Как масштабируется |
|---|---|---|
| **OGC-сервисы** (WMS/WFS/WCS/WMTS) | Отдают карту и объекты клиентам | Горизонтально: **несколько одинаковых JVM** за балансировщиком, если каталог и данные общие |
| **Web Admin** (`/geoserver/web`) | Люди правят слои и security | Обычно **один** вход на «писателя» конфига; на всех нодах — риск разъезда каталога |
| **REST API** | То же автоматически | Как админка: менять каталог лучше через один узел или через механизм синка |
| **GeoWebCache** | Тайлы | Масштаб чтения — с общего blob (диск/S3). Без общего кэша каждая нода греет своё |
| **Security subsystem** | Пользователи, роли, слой «кто видит слой» | Конфиг в data dir (`security/`). Это не Keycloak из коробки (есть community OIDC/Keycloak) |
| **Расширения** | control-flow, gwc-s3, wps, monitor, … | Ставятся в `WEB-INF/lib` **одинаковым** набором на все ноды |

Рядом, но это **другое** ПО:

- **Apache Tomcat 8.5 / 9** (официальная матрица 2.24) или Jetty из bin-сборки.
- **JRE 11** (протестированный путь). **Java 17** в доке 2.24 — *experimental only*; на Tomcat 9.0.55 «тестировали успешно», bin-сборка требует возни с Marlin.
- **PostgreSQL/PostGIS** — типичный store объектов.
- **Объектное хранилище** (S3-совместимое) — опционально тайлы (`gwc-s3`, **stable**) и COG/GeoTIFF.
- **Ingress / reverse proxy** — TLS снаружи, `PROXY_BASE_URL`.
- **СУБД под JDBCConfig** — только если сознательно берёте community.

### Официальные порты (контракт сети)

В самом GeoServer «свой» порт — это порт контейнера сервлетов.

| Порт | Назначение |
|---|---|
| **8080/TCP** | HTTP приложения в официальном Docker (`/geoserver`). Снаружи обычно **443** на Ingress |
| **8009** и пр. AJP | Не открывать наружу; классический Tomcat-хвост |
| **8443** | Если включили HTTPS **внутри** контейнера (`HTTPS_ENABLED` в *актуальном* README образа — проверять на теге 2.24.4) |

UDP нет. Балансировщик **HTTP(S)** перед нодами — штатная схема кластера из production-доки. Балансировщик «как у Kafka на 9092» здесь не нужен: между нодами GeoServer **нет** своего бинарного кластерного протокола в ядре.

### Чего в GeoServer нет (частая путаница)

| Нужно системе | Это не GeoServer 2.24 | Зачем помнить |
|---|---|---|
| Источник истины контуров/адресов/клиентов | Озеро / PostgreSQL / кадастр | GeoServer **публикует** то, что лежит в store. Упал store — карта пустая при живом UI |
| Шина событий, exactly-once | Kafka | Смена в PostGIS сама в WMS не «событие»; кэш тайлов **устареет**, пока не сбросите GWC |
| BPMN / Camunda | Process engine | GeoServer не исполняет процессы |
| 30+ интеграций с госслужбами | Ваше интеграционное API | Сюда можно отдать **слой** уже нормализованной геометрии, не ходить в СМЭВ |
| Платформа GeoData (IT Geo) | Другой продукт | Свой workflow, своя Cassandra/Kafka. Не «обёртка над GeoServer 2.24» |
| Кворум «пережили ЦОД сами» | etcd / Postgres Patroni / Cassandra | Несколько WAR за LB переживают падение **пода**, не падение **единственного PostGIS** |
| Официальный оператор Kubernetes для WAR 2.24 | Нет | Есть Helm **GeoServer Cloud** (другой дистрибутив) и чужие чарты. Их совместимость с **2.24.4** этим файлом не подтверждена |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS JDK/Ingress — не КриптоПро |
| Гарантия «терабайты влезут» | Нет | Терабайты живут в PostGIS/файлах/объектке. GeoServer держит **рабочий набор** (heap, открытые соединения, тайлы) |
| Замена бэкапа репликами подов | Нет | Три реплики с одним RWX или одним PostGIS: потеряли том/БД — потеряли каталог и/или карту |

### Зависимости окружения (обязательны)

- **Java 11** как опорный runtime линии 2.24. Свой «новейший 21» — за пределами официальной таблицы 2.24.
- **Контейнер сервлетов:** Tomcat **8.5 или 9** (матрица релиза). Tomcat 10+ (Jakarta namespace) — **не** тот WAR.
- **Внешний `GEOSERVER_DATA_DIR`** в проде: дока прямо *highly recommended* (безопасность + апгрейд). В Docker 2.24 точка монтирования примера: `/opt/geoserver_data`.
- **Сеть до store:** JDBC к PostGIS, пути к GeoTIFF, S3. GeoServer без данных — пустая админка.
- **Диск тайлов / data dir:** локальный SSD или объектка. Общий NFS как data dir в кластере — один из официальных приёмов, и одновременно классический источник file-lock и латентности; на 3 ЦОДа без замера это лотерея.
- **Kubernetes (у вас заявлен):** CSI; для **нескольких** реплик с общим data dir нужен **RWX**. RWO PVC на Deployment с `replicas: 3` — ошибка модели. Либо 1 реплика, либо каталог вынесен в БД, либо свой диск на под (тогда нужен синк конфига другим способом).
- **PKI на входе.** Сам GeoServer в примерах слушает HTTP 8080; TLS обычно на Ingress. Cookie сессии: в проде дока просит флаг **`Secure`** (HTTPS).
- **Бэкап:** data dir + security xml + (если есть) БД JDBCConfig + PostGIS. Тайлы GWC можно пересчитать; каталог — нет.

### Как GeoServer стыкуется с вашей архитектурой

```
Озеро эталона / PostGIS (контуры, адреса, объекты)
        │  JDBC / файлы / COG
        ▼
   GeoServer 2.24  (WMS/WFS/WMTS)
        ▲
        │  HTTP(S) 443 → 8080
   Ingress / клиенты UI, ГИС, печать

Микросервисы / Camunda / интеграционное API
        │  (опционально) пишут геометрию в PostGIS
        │  или просят WPS
        ▼
   не заменяют GeoServer и не являются его кластером

Kafka  ──►  не протокол GeoServer
GeoData (IT Geo)  ──►  другой стек, см. отдельный файл
```

Честные роли в *вашей* картине:

1. **Публикация карты** поверх эталонной геометрии (ЗУ, границы, сети) для внутренних UI.
2. **WFS** «отдай GeoJSON/GML» для приложений, которым вектор нужен не картинкой.
3. **WMTS** для тяжёлых подложек (ортофото), чтобы не рисовать WMS на каждый pan.

Нечестная роль: «положим эталон только в Shapefile внутри data dir и размножим три ЦОДа». Файловый store на NFS между ЦОДами и три писателя каталога — это не HA, это гонка.

## Краткие вводные

### Зачем вам GeoServer в этой архитектуре

Kafka двигает факты. Озеро хранит истину. Camunda ведёт процесс. Интеграционное API ходит в ведомства. Остаётся вопрос: **как людям и сервисам показать геометрию** (контур, адрес, охранная зона) стандартными WMS/WFS, не таща терабайты в браузер «как JSON».

GeoServer закрывает OGC-протоколы и стилизацию. Он **горизонтально** держит **чтение**, если за ним общее хранилище. Он **не** делает ваши микросервисы геопространственными — он может быть фасадом над PostGIS.

### Как устроена отказоустойчивость (идея, не магия)

В ядре **нет** выборов лидера и кворума. «Кластер» в production-доке — это **несколько узлов за общим proxy**, одинаковый `PROXY_BASE_URL`, и **одна** правда каталога.

**1) Процесс (JVM / под)**

| Что падает | Что происходит |
|---|---|
| Один под из N за Service/Ingress | Остальные отдают GetMap/GetFeature, если store жив |
| Все поды в одном ЦОДе | Падение площадки = нет карты, даже если PostGIS в других ЦОДах |
| Единственный под | Любой рестарт = простой. Это стенд, не прод |

**2) Каталог (самое тонкое место)**

| Схема | Живой узел | Слабое место |
|---|---|---|
| Один data dir на одном поде | Просто | Потеря PVC = потеря публикации слоёв |
| Общий data dir (NFS/RWX) на все ноды | Все видят одни XML | Блокировки файлов, латентность, «кто последний записал». Рестарт нод после смены конфига — штатная боль доки |
| Писатель один, остальные «запечённый» каталог / копия | Читатели стабильны | Выкат конфига = процедура (REST reload / rolling) |
| JMS Primary/Replica (community) | Конфиг едет сообщениями; **данные слоёв — нет** | Community; multicast по умолчанию **плохо** живёт в Kubernetes; брокер должен быть внешний с failover |
| JDBCConfig+JDBCStore (community) | Каталог в БД | Community; HA теперь у **той** БД; security xml дока/практика часто **локальные** |

Официальная формулировка проблемы: *the challenge is management of changes to the data directory*. Пока это не решено, «три реплики» — три разных сервера с риском трёх каталогов.

**3) Данные слоёв**

JMS-дока прямо: **NO DATA IS SENT THROUGH THE JMS CHANNEL**. PostGIS/файлы/S3 должны быть доступны **каждой** ноде сами. HA PostGIS — отдельный проект.

**4) Тайлы GWC**

Свой каталог на каждом поде = после балансировки клиент получает то старый тайл, то промах. Для прода — **общее** хранилище тайлов (диск RWX или **gwc-s3**, stable). Тайлы не заменяют бэкап каталога.

**5) Админка**

Падение UI ≠ падение GetMap, **если** REST/web не единственный путь и ноды уже сконфигурированы. Один писатель конфига — SPOF **изменения** слоёв, не обязательно SPOF чтения карты.

### Как устроено масштабирование

Несколько независимых осей:

1. **Больше одновременных GetMap** → больше JVM-нод **и** control-flow (иначе OOM). Официальный ориентир модуля: на **локальных** данных пик GetMap около **2 × число ядер** параллельных запросов **на инстанс**. Это не смета вашего прода, это стартовая формула для `ows.wms.getmap`.
2. **Больше «карты как подложки»** → **GWC** (предрасчёт / seed тайлов). Это главный рычаг WMS, не «ещё 64G heap».
3. **Больше объектов WFS** → лимиты GetFeature, индексы PostGIS, не раздувание heap «на всякий случай». Дока: для **вектора** лишняя память скорость почти не растит.
4. **Больше растра** → heap + доля tile cache на Server Config, диск, overview/pyramid, не 200 мелких GeoTIFF без пирамиды.
5. **Каталог на десятки тысяч слоёв** → уже не «XML в data dir комфортно»; в доке для этого фигурирует JDBCConfig (community). Welcome page без `GeoServerHomePage.selectionMode=text` может начать «думать» секундами.

JVM (официальная таблица production/container, **не** ваши цифры нагрузки):

- Пример в таблице: `-Xms128m`, `-Xmx756M` — это **иллюстрация команд**, не размер прода.
- По умолчанию JVM часто берёт **¼ RAM** хоста как max heap — это надо **задать явно** (`-Xms`/`-Xmx` равны по смыслу «без сюрпризов при нагрузке»).
- `-XX:SoftRefLRUPolicyMSPerMB=36000` — дока просит, чтобы кэш SRS/store жил дольше.
- Сборщик: один. Для постоянной нагрузки и кучи **≥ 6 GB** рекомендуют **G1** (`-XX:+UseG1GC`). CMS/ParNew в таблице — наследие; на Java 11+ G1 — разумный дефолт «непрерывной» нагрузки.
- Не включать несколько GC сразу.

Цифр «ядер под терабайты озера» **нет** — нагрузки у вас нет.

### Безопасность самого GeoServer

Компрометация с дефолтным `admin`/`geoserver` = полный каталог слоёв, часто **учётки JDBC** в store, возможность WFS-T если не выключили. Для контура с геометрией клиентов и ответами ведомств это утечка **ПДн и пространственных секретов**.

Официально / релизными фактами:

- Дефолт админки: пользователь **`admin`**, пароль **`geoserver`**. Сменить до любого Ingress наружу.
- Docker README проекта (актуальный текст, примеры на 2.28.x): сменить также **master** password. Для образа 2.24.4 — проверить, что инструкция образа это поддерживает, не копировать 2.28 вслепую.
- 2.24.4 закрывал **CVE-2024-36401 (RCE)** и SSRF в TestWfsPost; линейка после EOL новые CVE **не получает**.
- WFS: для «только чтение» — Service Level **Basic** (без транзакций) + JDBC-учётка store **read-only**. Дока: так снижается даже теоретический SQL injection.
- XML entity: по умолчанию http/https **не ограничены**, `file:` режется. Для прода — `-DENTITY_RESOLUTION_ALLOWLIST=...` (встроенный список w3c/ogc/inspire + proxy base). Галочка *Unrestricted XML External Entity Resolution* **снимает** эти ограничения.
- Не светить env/sysprops на Status/REST: `GEOSERVER_MODULE_SYSTEM_ENVIRONMENT_STATUS_ENABLED` / `_PROPERTY_` в проде **false** или не задавать (в 2.24.4 как раз чинили утечку env — CVE-2024-34696).
- CSRF: не выключать `GEOSERVER_CSRF_DISABLED=true` «чтобы UI заработал за proxy»; задать `GEOSERVER_CSRF_WHITELIST` доменами.
- CORS в примерах Tomcat/Jetty — `allowedOrigins=*`. Для закрытого контура это «любой браузер с любого сайта». Нужен явный origin вашего UI.
- Заголовки: `X-Frame-Options=SAMEORIGIN` по умолчанию; **HSTS выключен** по умолчанию (`geoserver.hsts.shouldSetPolicy`).
- Сессия: `HttpOnly` есть; **`Secure` в проде включить** (web.xml или proxy), если админка только по HTTPS.
- Админку в проде часто **выключают** (`GEOSERVER_CONSOLE_DISABLED=true`) и оставляют REST из внутренней сети.
- Лог: профиль **PRODUCTION**; путь `GEOSERVER_LOG_LOCATION` лучше зафиксировать снаружи, чтобы админка его не уводила.
- Сэмплы: снять `topp:states` и прочий demo.

«Поднять `docker run -p 8080:8080` и выдать в интернет» — это новый WFS/WMS ко всему каталогу, не ГИС-платформа.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём классический GeoServer 2.24.4 (WAR/Docker OSGeo), не GeoServer Cloud и не GeoServer Enterprise (GeoCat).** Cloud — другой деплой (микросервисы, Helm camptocamp). Enterprise — другой вендор и поддержка.
2. **Прод крутится в Kubernetes**, но **официального оператора под WAR 2.24 нет**. Целевой примитив — Deployment/StatefulSet + Ingress + PVC/RWX или вынесенный каталог. Чужие Helm-чарты «geoserver» этим файлом не сертифицируются.
3. **Три ЦОДа = три зоны отказа Kubernetes** (`topology.kubernetes.io/zone`). Если это три зала с одним SAN и одним PostGIS без реплики — схема врёт.
4. **Цель отказа по карте: пережить 1 ЦОД с нодами GeoServer**, при условии что **PostGIS и каталог** этот ЦОД тоже переживают. Пережить гибель единственной БД GeoServer не умеет.
5. **Нагрузки (GetMap/s, размер растра, число слоёв) нет** — поэтому **нет** цифры «N реплик и M heap». Есть control-flow, GWC, лимиты WMS/WFS и сигналы (latency, 429, heap, JDBC).
6. **Формального SLA / RPO / RTO нет.** Живой GetMap ≠ юридический 24/7 и ≠ «тайл обновился сразу после кадастровой сделки».
7. **Основной store — PostGIS** (вектор эталона). Растры — отдельно (файлы/COG/S3), если появятся.
8. **WFS-T в проде выключен**, запись геометрии идёт через ваши сервисы в озеро/БД, не через интернет-WFS.
9. **Идентификация людей** в проде — не общий `admin`. Либо внутренний RBAC GeoServer + отдельные учётки, либо IdP (community-модули OIDC/Keycloak **не** часть стабильного релиза 2.24).
10. **Шифрование канала — TLS на Ingress.** ГОСТ/СКЗИ не озвучены.
11. **Тестовый стенд изолирован.** На нём допустимы demo-слои и дефолтный пароль **только** пока порт не маршрутизируется дальше ноутбука. В прод это не копируем.
12. **Community-модули в проде не считаются «официальным HA»**. Если без них нельзя — это отдельный риск (сборка с тега 2.24.4, нет патчей после EOL).
13. **Лицензия GeoServer — GPL.** Для закрытого контура это про условия распространения модификаций, не про license-server. Юристы — отдельно; здесь только пометка, что это не Apache 2.0 как у Kafka.
14. **Заказчик сознательно остаётся на EOL 2.24.** Иначе целевая поддерживаемая линия на август 2026 — смотреть текущий Stable/Maintenance на https://geoserver.org/download/ (на дату расписания: 3.0 / 2.28), это **другой** документ.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «накрутили replicas: 3».

| Пробел | Почему это ломает решение |
|---|---|
| **EOL 2.24 + ИБ/КИИ** | Два года без патчей на контуре, который смотрит на геометрию и, косвенно, на госинтеграции. Это не «мелочь версии». |
| **Что публикуем** (только внутренние контуры? ортофото? слой с ПДн?) | Разные лимиты WFS, RBAC слоёв, кэш, 152-ФЗ. «Терабайты» без состава — не смета heap. |
| **Где живёт геометрия** (один PostGIS? шардированный? файлы?) | HA карты = HA этого store. GeoServer только читает. |
| **Один Kubernetes на 3 ЦОДа или три** | Общий RWX/NFS и JDBC на 3 площадки требуют сети и locking. Иначе — активная карта в одном ЦОДе + DR. |
| **RTT и IOPS до data dir и до PostGIS между ЦОДами** | Каталог на «общем NFS через город» даёт не HA, а таймауты и битый XML. Порога в доке GeoServer **нет**. |
| **Нужен ли live-синк каталога** или достаточно выката раз в день | От этого зависит: RWX vs «писатель + образ» vs community JDBC/JMS. |
| **Тайлы: пересчитывать или хранить** | Без общего GWC три ноды = три правды картинки. |
| **Кто ходит с браузера в админку** | CSRF whitelist, Console disabled, сеть. Публичный `/web` с `admin`/`geoserver` — инцидент. |
| **Нужен ли WPS** | Состояние jobs между нодами **не** общее без wps-cluster-jdbc/hazelcast (отдельные расширения). |
| **Совместимость образа 2.24.4** | Документация 2.24 показывает тег `2.24.x` (nightly). Наличие и состав тега `2.24.4` в `docker.osgeo.org` надо **проверить в реестре**, не верить README 2026 года про 2.28. |
| **Java 11 vs то, что внутри образа** | Актуальный Dockerfile репозитория docker (2026) для линейки 2.x указывает JDK17. Для **конкретного** 2.24.4 смотреть layers образа. Java 17 в user manual 2.24 — experimental. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **2.24.4** (WAR + те же zip расширений). Не смешивать 2.24.0 и 2.24.4, не ставить community с `2.24.x` nightly на release WAR.
2. Вынести **`GEOSERVER_DATA_DIR`** наружу приложения.
3. Сменить **admin** (и master, если образ/дистрибутив его показывает). Снять demo-слои.
4. Поставить **control-flow** (stable) и лимиты WMS/WFS **до** боевого трафика.
5. Настроить **`PROXY_BASE_URL`** (+ при необходимости headers) **до** раздачи GetCapabilities клиентам.
6. Store: PostGIS с **read-only** учёткой; WFS Basic, если записи через GeoServer нет.
7. Включить метрики: heap, latency GetMap, очередь control-flow, JDBC, размер GWC, 5xx Ingress.
8. Прогнать GetCapabilities / GetMap / GetFeature. Убедиться, что URL в XML — внешние, не `10.x`.
9. Только потом — кластер нод, GWC blob, RBAC слоёв, выключение админки.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики увидели слой из PostGIS, настроили SLD, дернули WMS/WFS, поняли Capabilities. **Не** цель: доказать отказ ЦОДа и ёмкость тайлов.

Официальный быстрый путь (User Manual 2.24, Docker):

```text
docker pull docker.osgeo.org/geoserver:2.24.x
docker run -it -p8080:8080 docker.osgeo.org/geoserver:2.24.x
```

Открыть `http://localhost:8080/geoserver`.  
Дока прямо: тег **2.24.x** в этой главе — **nightly / SNAPSHOT**, *not suitable for a production environment*. На стенде допустимо для «пощупать»; для препрода — **2.24.4**.

Свой каталог (чтобы пережить пересоздание контейнера):

```text
docker run -it -p8080:8080 \
  --mount type=bind,src=/MY/DATADIRECTORY,target=/opt/geoserver_data \
  docker.osgeo.org/geoserver:2.24.x
```

Пустой каталог **заполнится sample data**. Это удобно учиться; в прод sample уносят.

Расширения на старте образа (пример доки): `INSTALL_EXTENSIONS=true`, `STABLE_EXTENSIONS="ysld,h2"` — на стенде можно `control-flow` вместо h2. Плагины должны быть **той же** линии.

На Kubernetes: Deployment **1** реплика, PVC **RWO** под data dir, Service+Ingress в изолированном namespace. Не копировать `replicas: 3` с этого YAML в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число нод | 1 | Нет требования пережить выкат |
| Каталог | локальный диск / один PVC | Не учим NFS locking |
| GWC | локальный каталог | Нет нагрузки «карта на 10k клиентов» |
| PKI | HTTP, self-signed на Ingress | Иначе команда утонет в сертификатах раньше, чем в SLD |
| Пароль | сменить с `geoserver`, сеть изолирована | Дефолт в доке написан открытым текстом — привычка опасна |
| Java/heap | как в образе, 512m–1g | Не цель — ёмкость растра |
| Community cluster | не ставить | Иначе отладка JMS вместо GetMap |
| Snapshot ГИС | достаточно дампа PostGIS + копии data dir | |

#### Чего на тесте **не** стоит упрощать

- Понимание: слой живёт в **store**, не «в GeoServer». Удалите PostGIS — карта умрёт при живом поде.
- **`PROXY_BASE_URL`**, если уже есть Ingress: иначе полдня на «клиент ходит на ClusterIP».
- Версия плагина = версия сервера.
- Запомнить: nightly `2.24.x` **не** есть «почти 2.24.4».

#### Сильные стороны такой схемы

- Совпадает с официальным Docker-quickstart 2.24.
- Дешево показывает SLD и шум GetMap на *вашей* геометрии из озера.
- Один процесс — проще читать логи (`geoserver.log` в data dir).

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет общего кэша, нет доказанной ёмкости.
- Успешная карта на одном поде **не** доказывает, что RWX/JDBCConfig переживут RTT между площадками.
- Дефолтный пароль и demo-слои приучают «так и в проде».
- EOL: даже стенд 2.24 не стоит выставлять в корпоративную сеть без фильтра — RCE в линейке уже были, новые не закроют.

Практическая рекомендация: препрод = **2.24.4** + внешний data dir + control-flow + PostGIS + Ingress с TLS, **две** реплики уже с выбранной схемой каталога (даже без боевого трафика).

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты» **нет**. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

GeoServer плохо переживает **три независимых каталога** и плохо переживает **общий NFS data dir с плохим RTT**.

**Вариант A — один Kubernetes, зоны = ЦОДы, чтение с трёх площадок**

- Deployment GeoServer **≥ 2** (лучше 3+) с topology spread / anti-affinity по зоне.
- Каталог: **не** «три RWO». Либо (A1) JDBCConfig+JDBCStore в HA PostgreSQL (community, риск), либо (A2) один RWX **в пределах задержки, которую вы измерили** (часто это **не** три ЦОДа), либо (A3) **иммутабельный каталог** (ConfigMap/образ/REST) + ноды только читают, изменения — пайплайном.
- Данные слоёв: PostGIS, который сам переживает 1 ЦОД (это документ на PostgreSQL, не этот).
- Тайлы: **gwc-s3** (stable) в объектку, доступную из трёх ЦОДов, или смириться с холодным кэшем после failover.
- Ingress / один внешний URL, `PROXY_BASE_URL`, cookie `Secure`.
- Админка и REST записи — **NetworkPolicy только из bastion**; лучше `GEOSERVER_CONSOLE_DISABLED` на читающих репликах.
- control-flow на **каждой** ноде: он **не** видит кластер. Приоритеты заголовков на двух нодах дока прямо называет слабым местом.

**Вариант B — активный GeoServer в одном ЦОДе, остальные — клиенты и DR**

- Ноды карты в ЦОД-1, клиенты 2 и 3 ходят по городской сети на 443.
- Проще каталог (можно даже 2 пода в одной зоне + PDB).
- Падение ЦОД-1 = нет карты, пока не поднимете DR (тот же data dir + тот же PostGIS replica promote). **RTO надо прогнать**, не нарисовать.
- Честный выбор, пока RTT/RWX/JDBC между ЦОДами не измерены.

**Вариант C — GeoServer Cloud на Helm**

- Официальная страница production/clustering указывает Cloud Native как путь «без рестарта нод» в Kubernetes.
- Это **не 2.24 WAR**. Смешивать в одном документе как «тот же экземпляр» нельзя. Если уйдёте в Cloud — другой файл.

**Пока топология K8s, RTT до PostGIS и способ каталога не зафиксированы, нельзя честно выбрать A.** Дальше — A как целевой «карта с трёх площадок»; B — запасной и часто более честный.

##### Сильные / слабые стороны (A, чтение с 3 ЦОДов)

| Сильное | Слабое |
|---|---|
| Падение одного ЦОДа с подами не гасит GetMap | Каталог и PostGIS всё равно могут быть SPOF |
| Официальная идея «nodes behind load balancer» | RWX на 3 ЦОДа — не то же, что RWX в одном зале |
| GWC на S3 масштабирует подложку | Несогласованный кэш, если S3 «свой» в каждом ЦОДе без общей объектки |
| HPA по CPU/latency возможен | control-flow считает **ноду**, не кластер; HPA без лимитов = OOM |

##### Сильные / слабые стороны (B, мозг карты в одном ЦОДе)

| Сильное | Слабое |
|---|---|
| Каталог не надо синхронизировать через город | Падение ЦОДа карты = нет WMS у всех |
| Меньше community-модулей | Нужен явный DR: восстановление data dir + store **с замером времени** |
| Проще file lock | Клиентский путь 443 через город — ваша сеть, не магия GeoServer |

##### Слабое место любого «общего data dir» без замера

Документация **предлагает** shared filesystem как один из приёмов и **не задаёт** порог задержки. Утверждение «три ЦОДа в одном городе, значит NFS можно» — **непроверенное**. Мерить не ping ICMP, а **open/lock XML + JDBC** с ноды каждого ЦОДа.

#### Каталог: что можно считать продом на стабильных модулях

Опора на **stable**:

1. Несколько нод за LB.
2. `PROXY_BASE_URL` (+ идентификация ноды в GUI — опционально).
3. Смена конфига: либо простой «меняем на одной ноде и **рестартим/reload остальных**» (дока честно пишет про startup time), либо иммутабельный выкат data dir.
4. WPS/Importer — отдельные расширения, если вообще нужны.

Community (JMS, JDBCConfig, hz-cluster) — только с письменным принятием риска: experimental, сборка с тега, **нет** патчей после EOL 2.24. JMS по умолчанию с **embedded multicast** в Kubernetes обычно **не** заводится; нужен внешний брокер и `broker.url` failover. На Primary **нельзя** catalog reload (разашлёт шторм на replica). На pure replica **нельзя** менять конфиг.

Не ставить **два** механизма кластера каталога сразу (известная путаница JMS + JDBCConfig).

#### Данные, кэш, лимиты

- Слои из PostGIS: индексы GIST, не полный table scan на каждый GetMap.
- WMS request limits и WFS max features — **до** интернета.
- `controlflow.properties`: `timeout`, `ows.global`, `ows.wms.getmap`, `ows.gwc`, `user`/`ip`. Пример в доке — на **4 ядра**; ваши числа — с замера, не копия.
- GWC: seed критичных матриц; для кластера — общее хранилище. Расширение **gwc-s3** в списке stable 2.24.
- Лог PRODUCTION, не VERBOSE.

#### JVM и контейнер

- `-Xms` = `-Xmx`, величина с замера (растр vs вектор).
- `-XX:SoftRefLRUPolicyMSPerMB=36000`.
- G1 при большой куче / непрерывной нагрузке.
- Memory limit Kubernetes **выше** heap (native, GWC, JAI). Лимит = `-Xmx` → kill/OOM.
- `serviceStrategy`: в примерах доки **PARTIAL-BUFFER2** как баланс скорости и OGC-ошибок. `SPEED` прячет ошибки, `BUFFER` жрёт RAM.

#### Безопасность прода

| Слой | Правило |
|---|---|
| Версия | Только **2.24.4**, не 2.24.0. Понимать, что это всё равно EOL |
| Учётки | нет `geoserver`; нет общей admin у приложений; JDBC store read-only |
| WFS-T | выключен, если не доказан сценарий записи |
| Сеть | 8080 не в интернет; 443 на Ingress; admin/REST из внутренней сети |
| CSRF | whitelist доменов, не disable |
| CORS | явные origin UI, не `*` на боевом контуре |
| XXE | `ENTITY_RESOLUTION_ALLOWLIST`, unrestricted **выкл** |
| Status page | не включать показ env/sysprops |
| Сессия | `Secure` + HTTPS |
| HSTS | включить на Ingress или `geoserver.hsts.shouldSetPolicy` если TLS доходит до Tomcat |
| Demo | `topp:states` нет; sample data нет |
| Секреты | JDBC пароли не в Git и не в Capabilities; не в образе |
| Аудит | кто менял каталог (REST логи / ваш SIEM). Встроенный «как Wazuh» — нет |

##### Сильные / слабые стороны (LB + N JVM + PostGIS + GWC S3)

| Сильное | Слабое |
|---|---|
| Чтение WMS масштабируется подами | Правда слоёв живёт в каталоге и в БД, не в репликах WAR |
| Stable-путь без community | Выкат конфига с рестартом — простой или сложный пайплайн |
| control-flow и лимиты — официальный прод | Лимиты **на ноду**; кривой HPA обходит справедливость |
| gwc-s3 в stable | Нужна живучая объектка на 3 ЦОДа или кэш «остывает» при failover |
| | EOL: дыры после 2.24.4 не закрываются апстримом |

#### Kubernetes-специфика прода

- **Не** 3 реплики на одном RWO.
- PDB: не снимать все поды зоны сразу при drain.
- Readiness: не «Tomcat принял порт», а **GetMap известного слоя 200** (или хотя бы `/geoserver/web` если админка включена). В актуальном README образа есть `HEALTHCHECK_URL` на логотип — это liveness «процесс жив», не «PostGIS отвечает».
- Rolling update: при общем data dir на NFS — два писателя во время выката. Либо maxUnavailable/maxSurge продумать, либо иммутабельный каталог.
- Не root в проде, если образ умеет `RUN_UNPRIVILEGED` — **проверить на теге 2.24.4** (в README 2026 переменная есть, в user manual 2.24 Docker — нет).
- Шрифты для кириллицы в SLD: в образ 2.24 базовый набор шрифтов бедный; дока Docker (актуальная) монтирует `/opt/additional_fonts`. На 2.24.4 — проверить тот же путь в образе.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Решение ИБ: остаёмся на EOL 2.24.4 или уходим на поддерживаемую линию. Без этого шага остальное — декорация.
2. Замерить RTT/потери: под GeoServer → PostGIS, под → PVC/NFS, под → S3, клиент → Ingress, **все пары ЦОДов**.
3. Выбрать A/B и схему каталога (RWX vs иммутабельный vs community).
4. Собрать **2.24.4** + stable `control-flow` (+ `gwc-s3`, если тайлы). Community — только осознанно, JAR с git-тега `2.24.4`.
5. Вынести data dir, сменить пароли, снять demo, WFS Basic, read-only JDBC, allow-list XXE, PRODUCTION log.
6. Ingress TLS, `PROXY_BASE_URL`, CSRF whitelist, CORS своих UI.
7. Прогнать GetMap/GetFeature/WMTS. Проверить URL в Capabilities.
8. Вторая реплика. Убить под. Карта жива. Сменить стиль на писателе — понять, **когда** вторая нода это увидела (рестарт? сразу? никогда?).
9. Нагрузить хотя бы синтетикой GetMap. Снять heap, queue control-flow, latency. Выставить `ows.wms.getmap` и HPA **после** этого.
10. Прогон «ЦОД недоступен» на препроде: выключить зону с подами; отдельно — зону с PostGIS; отдельно — объектку тайлов. Записать, что именно умерло.

Без пункта 10 у вас нет отказоустойчивости, есть надежда. Без пункта 1 нет безопасности линейки.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | ≥2 ноды в разных зонах **и** живой store+каталог при отказе 1 ЦОДа; цель — 1 площадка; бэкап data dir + PostGIS с прогнанным restore |
| Производительность / масштаб | Не требуется | control-flow; лимиты WMS/WFS; GWC на общем blob; heap с замера (растр ≠ вектор); рост **подов**, не «один гигантский Tomcat» |
| Безопасность | Изоляция; пароль не дефолт, как только есть сеть | 2.24.4 минимум; нет demo; нет WFS-T; read-only JDBC; TLS; CSRF whitelist; XXE allow-list; админка не в интернет; секреты не в git |

**Не готов к проду**, если: тег `2.24.x` nightly, пароль `geoserver`, demo-слои, один под, три реплики на RWO, WFS-T «на всякий случай», JDBC write в эталон, `CORS=*`, CSRF выключен, unrestricted XXE, общий data dir через город без замера, JMS multicast в Kubernetes, community JAR с nightly на release WAR, карта назначена SoT вместо озера, линейка 2.24 принята в КИИ **без** фиксации EOL-риска.
