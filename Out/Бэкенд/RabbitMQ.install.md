# RabbitMQ 4.3.5 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `RabbitMQ.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

RabbitMQ — брокер очередей задач (AMQP). Ставите **свою** копию community-сборки, не коммерческий Tanzu.

Версия в этой инструкции: **4.3.5**. Образ: `rabbitmq:4.3.5-management`. Внутри образа уже есть Erlang **27.x**. Свой Erlang младше 27.0 — нода не стартует. Erlang **28** официально только для **новых** кластеров: на живом 4.3.5 остаёмся на **27.x**.

На Kubernetes — **Cluster Operator v2.22.5**. В описании кластера образ **пинить** `rabbitmq:4.3.5-management`: дефолт оператора на дату соседнего файла — **4.3.4**. Документация: https://www.rabbitmq.com/docs/ · оператор: https://www.rabbitmq.com/kubernetes/operator/operator-overview

Один кластер, размазанный на несколько дата-центров, здесь **не собираем**. Голосование Khepri (метаданные) и quorum queues — распределённая база на Raft, чувствительная к разрыву сети. В документации проекта при p99 **> 100 мс** или потерях пакетов кластер **не рекомендуют**. Поэтому живой кластер — внутри одной площадки. Вторая площадка — отдельный кластер + асинхронный мост (Shovel / Federation) или тёплый запас, не вторая половина того же Raft.

Kafka остаётся шиной событий. RabbitMQ — очереди задач / AMQP, **не** замена Kafka и **не** озеро клиентских данных.

---

## О чём эта инструкция молча договорилась

1. Тройка нод **одного** кластера живёт в **одном** дата-центре. Между площадками — отдельный кластер + Shovel/Federation **или** тёплый запас. Не открывайте между дата-центрами порты Erlang (4369, 25672) и репликации stream (6000–6500), если не строите осознанно другой контур.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`).
3. Учебный стенд — закрытая сеть. Одна нода и AMQP без TLS допустимы **только там**.
4. Цифр вашей нагрузки нет — нет фразы «хватит трёх нод на бой». Сначала увеличивают CPU/RAM/диск одной ноды; новые ноды — нечётными шагами внутри площадки.
5. В контуре **есть** роль AMQP / очередей задач. Если все потоки уже на Kafka — этот брокер можно не ставить.
6. Два дата-центра: активный кластер в первом; второй — независимый кластер + мост **или** тёплый запас (копия схемы, без боевых потребителей). Три дата-центра: то же. Третья площадка **не** третий участник чужого голосования Khepri.
7. Берём community RabbitMQ 4.3.5 (MPL-2.0), не Tanzu.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** публиковать и потреблять, отладить exchange / очередь / binding, контракт confirm/ack. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- На localhost свободны порты 5672 (AMQP) и 15672 (management UI).
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name rmq-dev \
  -e RABBITMQ_DEFAULT_USER=app \
  -e RABBITMQ_DEFAULT_PASS=dev \
  -p 127.0.0.1:5672:5672 \
  -p 127.0.0.1:15672:15672 \
  rabbitmq:4.3.5-management
```

Привязка к `127.0.0.1` обязательна: `-p 5672:5672` без адреса часто слушает все интерфейсы. Порты **4369** (epmd) и **25672** (Erlang distribution) **не** публиковать даже на учебном стенде.

Проверка — в выводе должна быть версия **4.3.5**:

```bash
docker exec -it rmq-dev rabbitmq-diagnostics status
docker exec -it rmq-dev rabbitmqctl version
```

Management UI — `http://127.0.0.1:15672`, пользователь `app`, не `guest` / `guest`.

Клиент AMQP — на `localhost:5672`, vhost `/`, пользователь `app`. Publisher confirms и manual ack в **коде** лучше включить сразу: стенд иначе врёт про бой.

На Kubernetes для учёбы: Cluster Operator **v2.22.5** (манифест с GitHub Releases проекта `rabbitmq/cluster-operator`, файл тега v2.22.5, не `latest`):

```bash
kubectl apply -f <манифест-v2.22.5>
kubectl -n rabbitmq-system rollout status deployment/rabbitmq-cluster-operator
```

Минимальный кластер (этот YAML в бой не копируйте):

```yaml
apiVersion: rabbitmq.com/v1beta1
kind: RabbitmqCluster
metadata:
  name: rmq-dev
spec:
  replicas: 1
  image: rabbitmq:4.3.5-management
  persistence:
    storage: 10Gi
```

Сервис AMQP: `rmq-dev:5672`. Образ пинить на 4.3.5 явно, не дефолт оператора 4.3.4.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Число нод | 1 | Некому строить кворум Khepri |
| TLS | нет, сеть закрыта | Иначе сертификаты раньше routing key |
| Classic queues | допустимы | Некому реплицировать; на препроде — quorum |
| Management 15672 | да, только localhost | Отладка |
| Shovel / Federation | не нужны | Одна площадка |
| `guest` с паролем `guest` | **запрещён** даже на стенде | Привычка уедет в бой |

Чего **не** упрощаем: номер версии **4.3.5**; отдельный пользователь не `guest`; confirms + manual ack в клиенте; имена exchange / очереди / vhost, не «как в туториале»; порты Erlang не публиковать.

### Как понять, что стенд живой

1. `rabbitmqctl version` возвращает 4.3.5, Erlang 27.x.
2. Publish/consume через пользователя `app`; `guest` с сети — отказ.
3. Контейнер перезапустили с томом — durable-очередь на месте. Classic без диска — потеря ожидаема.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный образ | Нет смены лидера, нет Raft, нет моста на другую площадку |
| Одна нода официально нормальна для разработки | Успешный publish **не** доказывает боевую схему |
| | Открытый 5672 на Wi-Fi = дыра |

Перед боем полезен **препрод**: 3 ноды + quorum + TLS — всё **в одном** дата-центре, даже без боевой нагрузки.

## Бой: один живой дата-центр, второй — запас

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три ноды, quorum queues, запись подтверждается большинством реплик). Отказ **всего дата-центра** = этого кластера нет, пока не переключите клиентов на второй независимый кластер (или не догонит асинхронный мост). При обрыве моста часть свежих сообщений можно потерять или получить дважды — это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Khepri выбирает лидера голосованием. Confirm quorum queue не быстрее, чем запись большинства реплик + диск. Если задержка сети между площадками в жёлтой или красной зоне официальной таблицы (см. `RabbitMQ.md`: p99 **> 100 мс** или потери пакетов), Raft даёт ложные выборы лидера и «глухой» Khepri, а не защиту. Даже при «в среднем нормальном» ping разрыв канала между городами для распределённой базы метаданных — штатный риск. Двух площадок для одного Raft **недостаточно**: большинство всегда окажется на одной стороне; её потеря убивает Khepri и quorum queues.

### Как расставить в активном дата-центре

Один кластер:

- **3 ноды** (нечётное; большинство Khepri = 2) на **разных нодах Kubernetes** этой площадки. Anti-affinity обязательна: иначе два из трёх подов окажутся в одном зале.
- `default_queue_type = quorum`. Classic как отказоустойчивость в 4.x **не работает** (mirroring удалён с 4.0).
- `quorum_queue.initial_cluster_size = 3` (или `x-quorum-initial-group-size`). Реплики **внутри** этого дата-центра, не «по городу».
- Клиенты AMQP могут на **любую** ноду; балансировщик перед 5671 допустим.
- PVC на ноду, **Parallel** pod management (не `OrderedReady`: rolling restart официально упирается в deadlock).
- Образ **4.3.5-management**, не 4.3.4 и не `latest`.
- Cookie — один, сгенерирован оркестратором, права файла **600**, не дефолт образа.
- Peer discovery — автоматический (плагин Kubernetes / Operator). Ручной `join_cluster` официально хрупкий для боя.
- `disk_free_limit.absolute` порядка memory watermark, **не** заводские 50 МБ. Считать от **лимита cgroup**.
- `vm_memory_high_watermark.relative` в диапазоне **0.4–0.7** (завод 0.6).
- File descriptors: ориентир чеклиста не меньше **50 тысяч**.
- `net_ticktime` **не понижать** (завод 60 с). Ложные разрывы хуже, чем чуть более медленный детект.
- Внутренний TLS нода↔нода: включить, если трафик нод выходит из доверенного сегмента **этого** дата-центра.

Если на растянутом (или даже локальном) кластере в логах повторяющиеся смены лидера очереди **без** реальных падений нод — тогда (и только тогда) увеличивают `raft.adaptive_failure_detector.poll_interval` (завод 5000 мс). Цена: дольше детект «тихого» обрыва.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: кластер из 3 нод. Вторая: **отдельный** кластер + Shovel/Federation **или** тёплый запас (копия схемы, без боевых потребителей). **Нет** общего Erlang-канала к первой | Нет локальной записи, пока не переключите клиентов. Доставка на вторую площадку асинхронная: **RPO > 0**, возможны дубли. Время простоя замерить |
| **Три** | Третья как вторая | То же. Три независимых кластера ≠ одна quorum queue «по всей стране» одним Raft |

Клиенты микросервисов в штате пишут в **локальный** кластер своей площадки (если она активна для этих очередей) **или** только в первую, а остальные — запас. «Пишем одну quorum queue во все три дата-центра одним Raft» — это stretch, его здесь нет.

Shovel/Federation — **плагины на конкретных нодах**; падение той ноды — отдельный отказ моста, его надо закладывать (не один link «на кластер сам»). Идемпотентность воркера — на вас. Два активных потребителя одной логической задачи на двух кластерах без идемпотентности = двойная работа.

Несколько **разных** кластеров по контурам (задачи интеграционного API ≠ внутренний RPC) — отдельные отказы, не один брокер «на всех». Кластер из десятков нод проект считает поводом **разрезать**, не «добавить ноды».

`pause_minority` / `autoheal` из гайдов 3.x **не применяются**: Mnesia удалена в 4.3. Восстановление — семантика Raft.

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемой скоростью, один том на одну ноду, том **не делится**.
- NetworkPolicy: 5671 клиентам; 4369 / 25672 / 6000–6500 **только** между нодами и jump CLI; epmd не в интернет.
- Erlang cookie — Secret / Vault, не в Git.
- Пользователи и очереди — Definition import / Topology Operator (схема as code), не руками в UI.
- Cluster Operator v2.22.5 уже прогнан с образом **4.3.5** на стенде.

### Порядок установки в активном дата-центре

1. Поставить Cluster Operator **v2.22.5** (манифест конкретного тега, не `latest`). Оператор — Deployment, **не** в одном поде с брокером. Topology Operator — отдельно, если очереди и пользователи декларативно.
2. Описать кластер из 3 нод, образ `rabbitmq:4.3.5-management`. Смысл манифеста (не полный CR — сверять с документацией оператора v2.22.5):

```yaml
apiVersion: rabbitmq.com/v1beta1
kind: RabbitmqCluster
metadata:
  name: rmq-tasks
spec:
  replicas: 3
  image: rabbitmq:4.3.5-management
  persistence:
    storage: 50Gi   # заглушка: реальный размер = очереди + Raft WAL; цифр нагрузки нет
  rabbitmq:
    additionalConfig: |
      default_queue_type = quorum
      vm_memory_high_watermark.relative = 0.6
      disk_free_limit.absolute = 2GB
      anonymous_login_user = none
  # anti-affinity по ноде обязательна; не оставлять 2 из 3 в одном зале
  # peer discovery задаёт Operator — не ручной join_cluster
```

Цифра `2GB` у `disk_free_limit` — не «хватит для боя», а «не оставить заводские 50 МБ». Официальный ориентир: порядка memory watermark.

3. Включить TLS **до** боевых очередей: клиенты 5671, management 15671, при необходимости — между нодами.
4. Удалить `guest`. Не `loopback_users.guest = false`. Завести отдельного администратора и отдельного пользователя на каждое приложение, права на vhost точечно.
5. Политики: delivery-limit (завод 20) + dead-letter; не `-1` «чтобы не мешало» без расчёта диска.
6. Выложить тестовую очередь, прогнать publish / confirm / consume, убить под, убедиться что majority жив и клиенты переподключились. `check_if_node_is_quorum_critical` **до** drain ноды.
7. Мост во второй дата-центр: плагин Shovel **или** Federation, отказоустойчивость самого link, TLS. Переключение продюсеров — **ручной / GitOps**.
8. Только потом — реальные очереди интеграционных воркеров.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Число нод | нечётное, старт **3** | Большинство Khepri и типичный размер quorum group |
| `default_queue_type` | `quorum` | Иначе клиент без `x-queue-type` создаст **classic** без реплик |
| `disk_free_limit` | порядка watermark, не 50 МБ | Не упереться в диск «вдруг» |
| Cookie | свой, не дефолт образа | Иначе ноды не склеятся или склеятся с предсказуемым секретом |
| Пользователь `guest` | удалён | Учебник с паролем `guest` сам просит так не делать |
| ANONYMOUS | выкл | Вход без учётки |
| Клиенты | 5671 + TLS; confirms; durable + persistent; manual ack; prefetch по вместимости воркера; auto-recovery | Без контракта сервер «настроен», а данные теряются |
| `basic.get` в цикле | не использовать | Официально неэффективен |
| Отдельные соединения publish и consume | желательно | Flow control публикации не должен душить ack потребителей |
| Долгие соединения | да | Connect-publish-close на каждое сообщение убивает file descriptors |
| `net_ticktime` | не понижать | На любой «почти WAN» ложные разрывы хуже |

Политика сбоя подов: не давать Kubernetes снять сразу две ноды из трёх. Обновление **по одной** ноде. Перед drain — `rabbitmq-diagnostics check_if_node_is_quorum_critical`.

Мониторинг, без которого бой — надежда: alarms памяти и диска; число соединений / каналов / очередей vs лимиты; unacked и глубина dead-letter; confirm latency; повторяющиеся выборы лидера; алерт «нода не в кластере», «majority lost».

### Как расти, когда появятся цифры нагрузки

1. Замерить сообщ./с, размер, число quorum queues, соединений, confirm latency, alarms памяти/диска.
2. Сначала больше CPU / RAM / диск на существующие ноды, не колокация с СУБД. Ещё нода не ускоряет одну очередь: единица параллелизма — **потребители на этой очереди** + CPU лидера.
3. Добавлять ноды **нечётными** шагами **внутри** дата-центра, затем `rabbitmq-queues grow` / placement. Ориентир проекта «пересмотри топологию» — порядка **5000** quorum queues.
4. Тяжёлые события с долгим логом — Kafka, не «ещё один fan-out exchange».
5. TLS бьёт по CPU — чеклист; «включили и осталась та же скорость» — неверно.

### Проверки, без которых это ещё не бой

1. Версия 4.3.5 / Erlang 27.x на **всех** нодах активной площадки. `cluster_status` — 3 ноды. Нет смеси с 4.3.4.
2. Очередь без `x-queue-type` создаётся **quorum**, не classic.
3. Выключили одну ноду: majority жив, confirm проходит, клиенты переподключились.
4. Publish без ACL / аноним — отказ. `guest` нет. Учебных паролей из документации нет.
5. Shovel/Federation догоняет тестовую очередь во втором дата-центре; замерить лаг (это ваш RPO).
6. Учение «активный дата-центр выключен»: переключение клиентов на вторую площадку **по заранее написанному сценарию**. Порты Erlang между площадками закрыты — и это **ожидаемо**.

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + асинхронный мост»

| Хорошо | Плохо |
|---|---|
| Confirm не зависит от межплощадочной задержки | Падение этой площадки = нет локальной записи, пока не переключите клиентов |
| Голосование Khepri — локальная сеть | RPO между площадками > 0; дубли; идемпотентность на вас |
| Согласовано с официальной таблицей RTT и с запретом stretch | Link Shovel живёт на ноде; отдельный отказ плагина |
| Один кворум на площадку, понятная модель для разработчиков | Два–три кластера: cookie, PKI, definitions — GitOps или разъедутся |

**Не готово к бою**, если: одна нода «как на тесте»; образ 4.3.4 / `latest`; classic queues как отказоустойчивость; mirroring из мануала 3.x; `guest` снаружи; PLAINTEXT на общей сети; emptyDir; `OrderedReady` + `check_running` как единственный probe; один кластер «на три дата-центра в уме»; RabbitMQ объявлен «вместо Kafka»; мост из одного пода без сценария отказа; учебный манифест уехал в бой.
