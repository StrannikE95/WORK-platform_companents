# RabbitMQ 4.3.5 — развёртывание и настройка

Версия ПО: **RabbitMQ 4.3.5** (релизная дата 17 августа 2026; на дату подготовки документа это последний стабильный патч линии **4.3**).  
Документация линейки: https://www.rabbitmq.com/docs/  
Релизы: https://www.rabbitmq.com/release-information  
Образ: `rabbitmq:4.3.5-management` (официальный Docker Hub; теги `4.3.5`, `4.3`, `4`, `latest` на эту дату указывают на этот патч).  
Erlang/OTP: **минимум 27.0**, максимум поддерживаемый — **27.x**. Нода на более старом Erlang **не стартует**. Erlang 28 официально только для **новых** кластеров: rolling-апгрейд Khepri с Erlang 27 → 28 на живом кластере имеет известную проблему mixed-version.

Этот текст — не мануал «скопируй `docker run rabbitmq`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

RabbitMQ **не назван** в исходной архитектуре: шиной событий там заявлена **Kafka**. Ниже — как поставить RabbitMQ на ту же инфраструктуру (Kubernetes, 3 ЦОДа). Это **не** замена Kafka, **не** озеро клиентских данных и **не** интеграционная шина к 30+ госслужбам.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Брокер / нода** | Один процесс `rabbitmq-server` (Erlang VM). Принимает сообщения, хранит очереди, отдаёт потребителям. |
| **Кластер** | Несколько нод с **общими** пользователями, vhost, очередями, exchange, binding. Клиент может подключиться к **любой** ноде (в отличие от Kafka, где клиент ходит к лидеру партиции). |
| **Erlang cookie** | Общий секрет (строка до 255 символов). Ноды и CLI (`rabbitmqctl`) общаются **только** если cookie совпадает. Это не пароль приложения, а «пропуск между нодами». |
| **epmd** | Маленький демон Erlang, помогает нодам найти друг друга. Порт **4369**. |
| **Khepri** | Хранилище **метаданных** кластера (очереди, exchange, пользователи, vhost, права). С 4.3 это **единственное** хранилище: Mnesia удалена. Работает по Raft: нужна **большинство** живых нод. |
| **Raft / кворум** | Протокол «большинство должно согласиться». Для 3 нод большинство = 2. Живых меньше — метаданные и quorum-очереди **не принимают** новые операции. |
| **vhost (virtual host)** | «Квартира» внутри брокера: свои очереди и права. Дефолт — `/`. В одном контуре системы обычно достаточно одного. |
| **Exchange** | Куда публикуют. Сам сообщения не хранит: по правилам (**binding**) раскидывает в очереди. |
| **Queue** | Где сообщения ждут потребителя. Тип задаётся **при создании** (`x-queue-type`) и потом **не меняется политикой**. |
| **Classic queue** | Обычная очередь. С RabbitMQ **4.0** она **не реплицируется**. Живёт на одной ноде. Упала нода — очередь недоступна (durable-сообщения на диске этой ноды). Дефолтный тип, пока его не переопределили. |
| **Quorum queue** | Реплицируемая очередь на Raft. Официально «default choice», когда нужна HA и сохранность. Дефолтный размер группы — **3** члена. |
| **Stream** | Журнал «дописал и читают с offset», ближе к Kafka-топику, чем к классической очереди. Реплицируется. Свой протокол (порты **5552/5551**) плюс AMQP. |
| **Classic mirroring (HA queues)** | Старая репликация classic. **Удалена с 4.0.** В 4.3.5 её нет и включать нечем. |
| **Лидер / follower** | У quorum queue и stream запись идёт через **лидера**. Confirm клиенту — когда **большинство** реплик записало на диск. |
| **Publisher confirm** | Клиент просит брокера сказать «сообщение принято надёжно». Для quorum queue confirm = «большинство реплик сохранило». Без confirm клиент **не знает**, дошло ли. |
| **Consumer ack (manual ack)** | Потребитель говорит «обработал, можно удалять». Без этого (auto-ack) сообщение теряется, если воркер умер на полуслове. |
| **delivery-limit** | Сколько раз сообщение можно отдать потребителю, который его nack/requeue. С 4.0 дефолт **20**; дальше — drop или dead-letter. Яд («poison message»), который вечно крутится, иначе забьёт диск. |
| **DLX / dead-letter** | Exchange, куда уходят отвергнутые/просроченные сообщения. Для разбора, не «магическое сохранение». |
| **Competing consumers** | Несколько потребителей на **одной** очереди делят работу: каждое сообщение — **одному**. Это очередь задач, не «всем читателям своя копия», как consumer group у Kafka на логе. |
| **Binding / routing key** | Правило «из exchange в какую очередь». Direct / topic / fanout / headers — разные способы сопоставить ключ. |
| **AMQP 0-9-1** | Исторический протокол RabbitMQ (каналы, exchange, queue). Большинство Java/.NET/Python-клиентов. |
| **AMQP 1.0** | Международный стандарт. С 4.0 в RabbitMQ **нативно**, без плагина. Требует SASL. |
| **SASL PLAIN / AMQPLAIN / ANONYMOUS / EXTERNAL** | Как клиент представляется. ANONYMOUS в проде выключают. EXTERNAL — клиентский TLS-сертификат. |
| **loopback_users** | Дефолт: пользователь `guest` ходит **только с localhost**. Это не «безопасность прода», это страховка от выставления 5672 в сеть с паролем `guest`. |
| **Federation / Shovel** | Плагины: **копируют сообщения между отдельными кластерами** асинхронно. Нет общего кворума через канал. Нужны, когда stretch-кластер нельзя. |
| **Stretch-кластер** | Один логический кластер, ноды в разных ЦОДах. Raft ходит по межЦОДовой сети. |
| **Peer discovery** | Как ноды находят друг друга при старте (DNS, Kubernetes plugin, список в конфиге). В проде — автоматически, не руками `join_cluster`. |
| **Definition import** | JSON со схемой: vhost, users, permissions, queues, policies. Штатный способ «засеять» кластер при выкатке. |
| **vm_memory_high_watermark** | Порог RAM: выше — брокер **перестаёт принимать** новые сообщения (alarm). Дефолт **0.6** от памяти, которую видит ОС. |
| **disk_free_limit** | Порог свободного диска: ниже — тоже alarm, публикация стопорится. Дефолт **50 МБ** — для туториалов, **не** для прода. |
| **net_ticktime** | Таймер Erlang «жив ли пир». Дефолт **60 с**. На WAN его **не понижают**: ложные разрывы хуже, чем чуть более медленный детект. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. |
| **Cluster Operator / Topology Operator** | Официальные Kubernetes-операторы RabbitMQ (MPL-2.0): кластер нод и декларативные очереди/пользователи. |

## Основные элементы системы и зависимости

### Что входит в RabbitMQ 4.3.5 (это одно ПО из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Нода брокера** | Приём, маршрутизация, хранение | Вертикаль CPU/RAM/диск; горизонталь — **нечётное** число нод (3, 5). Двузначное число нод официально уже дорого по метаданным |
| **Khepri (внутри ноды)** | Метаданные всего кластера | Кворум **всех** нод кластера. Падение большинства = кластер «глухой» даже если очереди на диске |
| **Quorum queue** | HA-очередь задач | Реплики по нодам (обычно 3). Больше очередей ≠ линейно больше throughput; ориентир проекта: пересмотреть топологию, если **> ~5000** quorum queues |
| **Stream** | Журнал с несколькими читателями | Реплики + свой протокол. Не замена вашей Kafka-шины |
| **Classic queue** | Лёгкая нереплицируемая очередь | Одна нода. Для HA в 4.x **не подходит** |
| **Клиенты** | Библиотеки AMQP 0-9-1 / 1.0 / Stream | Масштабируются отдельно. Confirm + manual ack — часть контракта, не «настройка сервера» |
| **Management plugin** | UI и HTTP API (**15672/15671**) | Удобство ops. Падение UI ≠ падение брокера, но API используют Topology Operator и автоматизация |
| **Prometheus plugin** | Метрики | Отдельный listener; HA мониторинга проектируется отдельно |
| **Federation / Shovel** | Мост между **кластерами** | Асинхронно. Сами плагины должны переживать падение ноды, на которой висел link |

Плюс *рядом*, но это уже другое ПО: **Cluster Operator** и **Messaging Topology Operator**, Ingress/балансировщик, IdP (если OAuth 2), диск/CSI, PKI.

### Официальные порты (менять можно, контракт сети лучше не плодить)

| Порт | Назначение | Кто ходит |
|---|---|---|
| **5672/TCP** | AMQP 0-9-1 и AMQP 1.0 без TLS | Клиенты |
| **5671/TCP** | То же поверх TLS | Клиенты в проде |
| **15672/TCP** | HTTP API и management UI | Ops, Topology Operator |
| **15671/TCP** | То же HTTPS | Ops в проде |
| **5552 / 5551/TCP** | Stream protocol / Stream+TLS | Stream-клиенты |
| **4369/TCP** | epmd | Только ноды и CLI, **не** в интернет |
| **25672/TCP** | Erlang distribution (нода↔нода и CLI). По умолчанию AMQP-порт + 20000 | Только ноды и CLI |
| **35672–35682/TCP** | Клиентские порты CLI к distribution | Хосты, с которых запускают `rabbitmqctl` |
| **6000–6500/TCP** | Репликация stream | Между нодами |

Порты 4369 и 25672 **нельзя** выставлять в публичную сеть: cookie + Erlang distribution — это полный административный канал.

Клиенты AMQP могут ходить на **любую** ноду; нода сама прокинет publish к лидеру quorum queue. Балансировщик перед 5671 **допустим** (в отличие от Kafka bootstrap). Цена: лишняя сеть внутри кластера, если попали не на лидера.

### Чего в RabbitMQ 4.3 нет (частая путаница)

| Нужно системе | Это не RabbitMQ 4.3 | Зачем помнить |
|---|---|---|
| Шина событий с долгим логом, партициями, независимыми consumer group, retention «как у Kafka» | **Apache Kafka** (у вас уже в архитектуре) | Exchange+много очередей имитирует fan-out, но ops, replay и объём — другие. Streams есть, это не «поставили Kafka внутри Rabbit» |
| Источник истины клиентских данных | Озеро / СУБД | Очередь — буфер. Сообщение после ack исчезает |
| Camunda 8 / BPMN | Zeebe (отдельный документ) | Camunda **7** умела ходить в Rabbit как job worker transport. Camunda **8 Self-Managed** — свой протокол, не этот брокер |
| Интеграции с госслужбами | Ваше интеграционное API | Сюда — очередь задач воркерам API, не коннект к ведомству |
| Репликация classic queue (mirroring) | Удалена в 4.0 | Политика `ha-mode` из старых мануалов **не работает** |
| Mnesia, `pause_minority` / `autoheal` / `pause_if_all_down` | Удалены в **4.3** вместе с Mnesia | Чеклист «partition handling strategy» из старых гайдов к 4.3.5 **не применяется**. Восстановление — семантика Raft |
| Мультимастер запись одной очереди в 3 ЦОДах без лидера | Нет | Один лидер на quorum queue; confirm ждёт majority |
| ГОСТ TLS / СКЗИ | Не входит | Штатный TLS — стек Erlang/OpenSSL сборки, не криптография КИИ, если ИБ её выдвинет |
| Шифрование тел сообщений **на диске брокера** | Нет, **by design** | Диск/том (LUKS и т.п.) или шифрование **на клиенте** до publish |
| Официальный порог «хватит N нод на терабайты» | Нет | Терабайты в архитектуре — про озеро/хранилище. RabbitMQ так не проектируют как SoT |

### Зависимости окружения (обязательны)

- **Erlang 27.x** в том же образе/пакете, что 4.3.5 (официальный Docker уже содержит). Свой Erlang «сбоку» младше 27.0 — нода не поднимется.
- **Диск.** Khepri, quorum queues и streams рассчитаны **только на durable storage**. Эфемерный диск пода → после рестарта полная синхронизация реплики с лидера (сеть и время). Официально: локальный SSD/NVMe предпочтительнее NAS; NAS допустим, если стабильно низкая латентность I/O и том **не делится** между нодами. Distributed FS (как «общий каталог на всех») — прямой путь к порче данных: ноды не координируют запись в один каталог.
- **RAM.** Минимум прода на ноду по чеклисту проекта: **4 CPU, 4 GiB RAM**, без соседства с другими I/O-тяжёлыми СУБД на тех же ядрах/диске. Ниже — для dev/QA. `vm_memory_high_watermark` считать от **лимита контейнера**, иначе брокер увидит память ноды Kubernetes и сработает слишком поздно (или наоборот).
- **Сеть между нодами:** DNS/hostname каждой ноды резолвится **у всех** членов (в K8s — FQDN, `RABBITMQ_USE_LONGNAME=true`). Cookie одинаковый. Порты 4369, 25672, 6000–6500 открыты **между нодами**, не наружу.
- **Kubernetes (у вас заявлен):** StatefulSet + отдельный PVC на ноду; **Parallel** pod management, не `OrderedReady` (иначе rolling restart кластера официально упирается в deadlock ожидания пира). Readiness probe на полном старте не должен быть `rabbitmq-diagnostics check_running`, пока нода ждёт sync метаданных; для этой фазы годится `rabbitmq-diagnostics ping`. Практичный путь: **RabbitMQ Cluster Operator** (релиз **v2.22.5** от 24 августа 2026; MPL-2.0). Дефолт оператора на дату README — образ **4.3.4**; образ **пинить `rabbitmq:4.3.5-management`** в `spec.image`. Topology Operator — отдельно, для vhost/users/queues as code.
- **Часы.** Кластер без NTP обычно живёт, но management-метрики врут при расхождении. NTP/chrony на нодах — штатная рекомендация.
- **PKI** для прода (клиентский TLS и **inter-node TLS**, если трафик между ЦОДами выходит из доверенного сегмента).

### Как RabbitMQ стыкуется с вашей архитектурой

```
Микросервисы, воркеры интеграционного API, (редко) Camunda job workers
        │  команды, RPC, конкурентная обработка задачи
        ▼
   RabbitMQ 4.3  (очереди задач / буфер; не лог событий и не SoT)
        ▲
Kafka ── остаётся шиной событий (факты «данные изменились»)
Озеро эталона ── остаётся истиной клиентских данных
Camunda 8 ── остаётся движком процессов (Zeebe, не этот брокер)
Интеграционное API ── остаётся единственным выходом к госслужбам
```

Честные роли в *вашей* картине:

1. **Очередь работ** интеграционных воркеров: «сходи в ведомство X за ИНН N» — competing consumers, prefetch, retry, DLX. Пики и лаги внешних API сюда ложатся естественнее, чем в «вечный» лог Kafka.
2. **Request-reply** внутри контура (корреляция, TTL ответа), если сервисы уже говорят AMQP.
3. **Мост к системам, которые умеют только AMQP** (легаси, вендоры, отдельные модули вроде GeoData, у которых в совместимости указан RabbitMQ).

Нечестные роли:

- «Заменим Kafka на Rabbit, раз очереди проще» — другая модель: нет долгого лога на всех читателей, нет партиций как единицы масштаба, метаданные синхронно на **всех** нодах.
- «Положим клиентские карточки в очередь — это же persistence» — после ack данных в брокере нет.
- «Classic durable очередь + три ноды = HA» — в 4.x classic **не зеркалится**. HA = quorum queue или stream.

## Краткие вводные

### Зачем вам RabbitMQ рядом с Kafka

Kafka хорошо везёт **события** (много независимых читателей, replay, объём). RabbitMQ хорошо везёт **задачи**: «сделай один раз, если воркер умер — отдай другому», приоритеты (с 4.3 у quorum queue — 32 уровня), DLX, TTL, RPC.

Если в контуре **нет** AMQP-клиентов и все потоки уже на Kafka — RabbitMQ можно не ставить. Ставить «на всякий случай» значит платить кластером, PKI и дежурством за пустую роль.

### Как устроена отказоустойчивость (идея, не магия)

Долговечность в 4.3 — это **не** «поставили 3 ноды», а:

1. **Khepri**: большинство нод кластера живо, иначе не создать очередь и не сменить права.
2. **Quorum queue / stream**: большинство **реплик этой очереди** живо; publisher **confirm**; consumer **manual ack**.
3. Реплики разложены по **разным ЦОДам** (иначе три ноды в одном зале не переживают площадку).
4. Диск ноды **переживает** рестарт пода.

Confirm без majority **не выдаётся**. Клиент без confirm может решить, что «отправил», а брокер умер до записи.

Classic queue на проде с требованием «упал ЦОД — живём» **не выполняет** это требование.

### Как устроено масштабирование

Это **не** Kafka. Единица параллелизма обработки одной очереди — **потребители на этой очереди**, плюс CPU ноды-лидера.

- Больше нод → больше одновременных TCP-соединений и место для реплик; метаданные всё равно копируются **на каждую** ноду (синхронно). Проект прямо советует не раздувать кластер до десятков нод, а дробить на **отдельные кластеры** по контурам.
- Больше quorum queues → больше Raft-групп, RAM, диска, времени восстановления. Ориентир «пересмотри топологию» — порядка **5000** таких очередей (это не жёсткий лимит кода).
- Тяжёлые сообщения и высокий rate упираются в **диск и сеть**, не в «ещё один exchange».
- Throughput confirm'а на stretch **не может быть быстрее**, чем RTT до ближайшей реплики в другом ЦОДе + fsync.

Нагрузки у вас нет — поэтому ниже **нет** числа «хватит 3 нод на прод» как ёмкости. Есть минимум для кворума и правила роста.

### Память и диск — типичные ошибки

Брокер при пересечении watermark **глушит публикацию**. Это защита, не «зависание непонятно почему».

Дефолт `disk_free_limit` 50 МБ на проде опасен: места «ещё хватает» по мнению брокера, пока том уже на грани. Официальная минимальная планка: **примерно как memory watermark** (пример из чеклиста: watermark 4 ГиБ → `disk_free_limit.absolute = 4G`).

Quorum queues и streams **не обязаны** быстро отдавать место на диске после ack. Правило проекта: диск **перезакладывать**.

### TLS стоит производительности

Чеклист: TLS заметно бьёт по CPU брокера и клиентов. «Включим и останется та же скорость» — неверно.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть, а не «чуть подкрутить порты».

1. **Берём открытый RabbitMQ 4.3.5** (MPL-2.0), не Tanzu/коммерческий дистрибутив с Intra-cluster Compression и прочими надстройками.
2. **Прод в Kubernetes**, путь установки — **Cluster Operator v2.22.5**, образ нод **явно 4.3.5-management**, не дефолт оператора 4.3.4 и не тег `latest`.
3. **Три ЦОДа в одном городе** — три независимых домена отказа. Если это три зала с общим UPS — stretch даёт ложное чувство безопасности.
4. **Stretch (один кластер на 3 ЦОДа)** принимается как целевой **только если** межЦОДовая сеть попадает в официальную таблицу RTT (см. ниже) и без потерь пакетов. **Пока RTT не измерен — это гипотеза.**
5. **Один логический Kubernetes с тремя зонами** *или* три кластера K8s, но ноды одного RabbitMQ должны резолвить друг друга и открыть distribution/stream-порты. Иначе stretch на K8s не взлетит: три отдельных кластера + Federation/Shovel.
6. **Нагрузки нет** — нет числа «сколько сообщений/с» и размера диска. Есть минимум HA (3 ноды) и правила, как потом расти.
7. **Формального SLA / RPO / RTO нет.** При корректных quorum queues, confirm и живой сети потеря **одного** ЦОДа даёт продолжение работы для очередей, у которых majority реплик жив. Это не юридический 24/7.
8. **RabbitMQ не заменяет Kafka.** Если по факту все события уже едут в Kafka, этот кластер нужен только под очереди задач/AMQP. Если руководство хочет «ещё одну шину на всякий» — это отдельное продуктовое решение, не техническая необходимость 4.3.
9. **Корпоративный PKI есть или будет.** Self-signed допустим на тесте; в проде hostname verification не отключаем «чтобы завелось».
10. **Идентификация приложений** на старте — отдельные пользователи с паролем (PLAIN по TLS). Если в контуре уже есть IdP — разумнее OAuth 2 plugin (`rabbit_auth_backend_oauth2`). Выбор ИБ, не единственно верный.
11. **ГОСТ/СКЗИ и 152-ФЗ в части криптографии канала не озвучены.** Vanilla RabbitMQ их не закрывает.
12. **Тестовый стенд** изолирован: на нём допустим AMQP без TLS. Клиентский код лучше сразу писать с publisher confirm и manual ack — иначе тест врёт про прод.
13. **Camunda, озеро, интеграционное API** — клиенты или соседи, не часть этого ПО.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «постановки в прод». Иначе архитектура разъедется.

| Пробел | Почему это ломает решение |
|---|---|
| **Нужен ли RabbitMQ вообще** (есть ли AMQP-клиенты / очереди задач, или всё на Kafka) | Иначе вы разворачиваете второй брокер сообщений без роли, с своим HA и ИБ |
| **p99 и max RTT, потеря пакетов между ЦОДами, все пары, дни а не минуты** | Официальная оценка stretch **завязана на эти цифры** (таблица ниже). Confirm quorum queue **всегда** ≥ RTT до другой реплики + диск. Потери пакетов / RTT > 100 мс → кластер **не** рекомендуют; нужны отдельные кластеры + Shovel/Federation |
| **Профиль нагрузки** (сообщ./с, размер, число очередей, соединений, prefetch, пик vs среднее) | Без этого нет CPU, диска, file descriptors, числа нод «под нагрузку» |
| **Срок хранения в очередях** | RabbitMQ — не озеро. Backlog «на всякий» на терабайты упрётся в диск quorum WAL. Политика TTL/DLX/max-length должна быть явной |
| **Формальные RPO/RTO и «упал ЦОД»** | Stretch из 3 нод переживает **один** ЦОД. Два ЦОДа сразу — кворума Khepri нет |
| **Топология Kubernetes** (один кластер на 3 ЦОДа или три изолированных) | От этого зависит, возможен ли stretch |
| **Требования ИБ: ГОСТ, at-rest, контур КИИ** | Меняют PKI, возможность vanilla TLS, необходимость шифрования томов |
| **Есть ли уже RabbitMQ 3.x с mirrored classic** | В 4.0 mirroring нет. Миграция — отдельный проект (новые quorum queues, не «включил политику ha-mode») |

Официальная таблица RTT для **кластеризации** (документация 4.3, раздел Multiple Data Centers). Это **не** моя оценка «на глаз»:

| p99 RTT между нодами | Оценка проекта RabbitMQ |
|---|---|
| **< 1 мс** | LAN, **рекомендуемая** модель |
| **1–10 мс** | Типичные AZ одного региона; дефолты обычно ок |
| **10–100 мс** | ЦОД/регионы **возможны**; закладывать цену латентности confirm и следить за лишними выборами лидера |
| **> 100 мс или видимые потери пакетов** | Кластер **не рекомендуют**. Отдельные кластеры + **Shovel или Federation** |

Стабильность канала важнее среднего: ровные 50 мс лучше, чем 10 мс с провалами на секунды.

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **4.3.5** и Erlang **27**.
2. Выбрать макросхему: один кластер / stretch / три кластера + Shovel/Federation — **после** замера RTT.
3. Сгенерировать Erlang cookie **автоматизацией** (не «первая нода сама написала файл, мы скопировали»). Права файла **600**.
4. Persistent диск на каждую ноду, hostname стабильный.
5. Поднять ноды, проверить `rabbitmq-diagnostics cluster_status` и кворум Khepri.
6. Удалить `guest`, завести пользователей, выключить ANONYMOUS. В проде — TLS до появления боевых клиентов.
7. Задать `default_queue_type = quorum` (на vhost или node-wide) **до** того, как приложения насоздают classic «по дефолту».
8. Клиентам: publisher confirms, manual ack, durable topology, осмысленный prefetch; не `basic.get` в цикле (polling официально считают неэффективным).
9. Мониторинг: memory/disk alarms, quorum status (`rabbitmq-queues quorum_status`, `check_if_node_is_quorum_critical`), unacked, confirm latency, inter-node buffer, лидеры, которые прыгают без рестартов.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики публиковали и потребляли, отлаживали routing, DLX, контракт confirm/ack. **Не** цель: доказать отказоустойчивость и ёмкость прода.

#### Топология

Минимально достаточно **одной** ноды:

- образ `rabbitmq:4.3.5-management`;
- один PVC или даже эфемерный диск (на тесте потеря данных при `down -v` приемлема);
- AMQP **5672** только в изолированной сети стенда;
- пользователь не `guest` с паролем `guest`, даже на тесте (привычка);
- очереди можно classic: реплицировать некому.

На Kubernetes: Cluster Operator, `replicas: 1`. Этот YAML **не** копировать в прод.

Альтернатива чуть ближе к проду: 3 ноды **в одном** ЦОДе, quorum queues. Отказоустойчивости площадки всё равно нет, но клиенты уже бьются о confirm и failover лидера.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| 1 нода | да | Проект прямо: single-node, когда простота важнее всего (dev, integration, часть QA) |
| Без TLS | да, если сеть закрыта | Иначе команда утонет в сертификатах раньше, чем в routing key |
| Classic queues | допустимы | Некому реплицировать; на препроде уже quorum |
| Management UI 15672 | да | Удобство отладки |
| Мониторинг | минимум | Нет нагрузки |

#### Чего на тесте **не** стоит упрощать в клиентском коде

- Publisher confirms и обработка nack/timeout.
- Manual ack (или осознанный auto-ack только для сообщений, которые не жалко).
- Имена exchange/queue/vhost, а не «как получилось в туториале».
- Идемпотентность воркера: at-least-once после рестарта потребителя — норма.
- Версия клиента, которая умеет AMQP выбранного поколения (0-9-1 vs 1.0).

#### Сильные стороны такой схемы

- Поднимается за часы.
- Дешёвая.
- Совпадает с рекомендацией проекта для development.

#### Слабые стороны (обязательно понимать)

- Падение ноды = простой; при classic — очередь недоступна, пока нода не вернётся с **тем же** диском.
- Стенд **не** ловит: кворум Khepri, split-brain Raft, межЦОдовый confirm, TLS CPU, «попали не на лидера».
- Успешный тест на одной ноде **не** является доказательством готовности прода.

Практическая рекомендация: препрод — **маленькая копия прод-топологии** (3 ноды, quorum, TLS) даже без боевой нагрузки.

---

### Прод: 3 ЦОДа, нагрузка

Цифры «под терабайты» **не** ставятся: нагрузки нет, и терабайты в контексте — про озеро, не про брокер очередей.

#### Шаг 0. Выбор макроархитектуры (сделать до установки)

**Вариант A — stretch (один кластер, по ноде в каждом ЦОДе).**  
Целевой, если RTT в официальной «зелёной/жёлтой» зоне и канал стабильный.

- Клиентам один список узлов / один Service.
- Падение 1 ЦОДа не требует «переключения на другой Rabbit».
- Confirm quorum queue всегда платит межЦОдовый RTT.

**Вариант B — отдельные кластеры на ЦОД (или актив-пассив) + Shovel / Federation.**  
Если p99 > 100 мс, есть потери, или K8s-кластеры не маршрутизируются.

- Локальный confirm быстрый.
- МежЦОДовая доставка **асинхронная**: RPO > 0, возможны дубли, другая операционка.
- Это уже не «один экземпляр», а несколько плюс мост со своим HA.

**Пока RTT не измерен, нельзя честно выбрать A.** Дальше описан **вариант A** как целевой для «3 ЦОДа в одном городе»; B — запасной.

Официально: **двух ЦОДов недостаточно**. Majority всегда окажется на одной площадке; её потеря убивает Khepri и quorum queues. Третья площадка — практический минимум. Это совпадает с тем, что у вас три ЦОДа, и **ломается**, если «третий» — не независимый домен отказа.

##### Сильные / слабые стороны stretch (A)

| Сильное | Слабое |
|---|---|
| Один кластер, простая модель для разработчиков | Латентность confirm ≥ RTT до реплики в другом ЦОДе + диск |
| 3 ноды по 1 на ЦОД переживают потерю **одной** площадки | Сетевой шторм выглядит как деградация/выборы лидера |
| Нет ручного failover приложения | Не переживает потерю **двух** ЦОДов |
| Клиент может ходить на любую ноду | Метаданные (declare queue) тоже платят Raft через ЦОДы |

##### Сильные / слабые стороны Shovel/Federation (B)

| Сильное | Слабое |
|---|---|
| Нет кворума через плохой канал | RPO ≠ 0 |
| Переживает длинный обрыв линка | Дубли, идемпотентность на вас |
| Можно актив-пассив | Link живёт на конкретной ноде; её падение — отдельный failover плагина |

#### Число нод и раскладка по ЦОДам

Нечётное число. **Минимум прода для HA: 3 ноды, по одной в ЦОД.** Это минимум кворума, не ёмкость.

| Схема | Что переживёт | Чего не переживёт |
|---|---|---|
| 3 ноды, 1+1+1 по ЦОДам | 1 ноду или 1 ЦОД | 2 ЦОДа; рестарт ноды в живом ЦОДе, пока другой уже мёртв (остаётся 1 из 3) |
| 5 нод, 2+2+1 | 2 любых ноды; 1 ЦОД целиком | 2 ЦОДа сразу (на оставшейся площадке нет majority из 5) |

Дальше масштабирование: сначала **вертикаль** (CPU/RAM/диск, не колокация с БД), затем добавление нод **нечётными** шагами с переразкладкой реплик. Кластер из десятков нод проект считает поводом **разрезать** систему на несколько кластеров.

На каждой ноде: anti-affinity / topology zone = ЦОД. Иначе Kubernetes положит 2 из 3 подов в один зал.

`quorum_queue.initial_cluster_size = 3` (или `x-quorum-initial-group-size`). Реплики должны оказаться в **разных** ЦОДах; после роста кластера проверять `rabbitmq-queues grow` / placement, не верить, что «само разложилось навсегда».

#### Обязательные настройки (кластер)

| Параметр / практика | Прод-значение | Зачем |
|---|---|---|
| Число нод | нечётное, старт **3** (1 на ЦОД) | Majority Khepri и типичный размер quorum group |
| Cookie | один, сгенерирован оркестратором, не дефолт образа | Иначе ноды не склеятся или склеятся с предсказуемым секретом |
| Peer discovery | автоматический (K8s plugin / Operator) | Ручной `join_cluster` официально считают хрупким для прода |
| `default_queue_type` | `quorum` (vhost и/или node-wide) | Иначе клиент без `x-queue-type` создаст **classic** без реплик |
| `disk_free_limit.absolute` | порядка memory watermark, **не** 50 МБ | Не упереться в диск «вдруг» |
| `vm_memory_high_watermark.relative` | в диапазоне **0.4–0.7** (дефолт 0.6), считать от **cgroup** | Выше 0.7 — только с мониторингом; ОС нужна память под page cache |
| File descriptors | ориентир чеклиста: не меньше **50k**, часто сотни тысяч | Соединения + очереди |
| Durable storage | PVC RWO / local PV, не emptyDir | Иначе полный resync реплик |
| Pod management | **Parallel** | Иначе rolling restart в K8s официально мёртвый |
| NTP | да | Метрики management |

Внутренний TLS нода↔нода: для трафика между ЦОДами проект **рекомендует включить**. `net_ticktime` **не понижать**.

Если на stretch видите в логах повторяющиеся смены лидера очереди **без** реальных падений нод — тогда (и только тогда) увеличивают `raft.adaptive_failure_detector.poll_interval` (дефолт 5000 мс). Цена: дольше детект «тихого» обрыва. Чистые crash/restart ловятся без этого.

#### Безопасность (до боевых клиентов)

1. **Удалить `guest`.** Не «разрешить ему ходить снаружи» (`loopback_users.guest = false`) — это антипаттерн чеклиста.
2. Отдельный администратор с сгенерированным паролем (или OAuth).
3. **Отдельный пользователь на приложение** (интеграционное API, набор микросервисов, воркеры). Fine-grained permissions на vhost/resource.
4. `anonymous_login_user = none`, в `auth_mechanisms` нет **ANONYMOUS**.
5. Клиенты — **5671 + TLS**. Management — **15671**, не торчать 15672 в корпоративный «почти интернет».
6. Peer verification клиентских сертификатов — желательно; минимум — шифрование канала.
7. Порты 4369/25672/stream-replication — NetworkPolicy только между нодами и jump-хостом CLI.
8. Cookie не в git, не в картинке «для удобства».
9. At-rest: шифрование **тома** Kubernetes/хоста и/или payload на клиенте. Брокер тела сообщений сам не шифрует.

Definition import / Topology Operator — чтобы пользователи и очереди не плодились руками в UI и не жили только в голове дежурного.

#### Клиентский контракт (без него сервер «настроен», а данные всё равно теряются)

- Publisher confirms; обработка ситуации «confirm не пришёл».
- Durable queue + persistent messages, если сообщение нельзя потерять при рестарте.
- Manual ack; prefetch по вместимости воркера, не «неограниченный».
- `delivery-limit` (дефолт 20) + DLX на ядовитые сообщения. Не ставить -1 «чтобы не мешало» без расчёта диска.
- Отдельные соединения publish и consume, если возможно (чеклист: flow control публикации не должен душить ack потребителей).
- Долгие соединения, не connect-publish-close на каждое сообщение (connection churn убивает file descriptors).
- Авто-recovery клиента (Java/.NET/Ruby его умеют; иначе — свой цикл переподключения, как в примерах Go/Pika).

#### Мониторинг (без него прод — надежда)

- Alarms памяти и диска.
- Число соединений/каналов/очередей vs лимиты.
- Unacked, DLX depth.
- Confirm latency (на stretch это прямой датчик межЦОДовой сети).
- `rabbitmq-diagnostics check_if_node_is_quorum_critical` **до** drain ноды.
- Повторяющиеся выборы лидера.
- Prometheus plugin + алерт «нода не в кластере», «majority lost».

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами (p50/p95/p99/max, потери, дни). Решение A vs B.
2. Решить, нужен ли брокер рядом с Kafka (роль очередей задач / AMQP).
3. Выделить ноды/зоны, local storage, NetworkPolicy.
4. Поставить Cluster Operator v2.22.5, описать кластер из 3 нод, образ **4.3.5**.
5. TLS (клиент и inter-node), пользователи, удаление guest — **до** боевых очередей.
6. `default_queue_type = quorum`, политики delivery-limit/DLX.
7. Выложить тестовую очередь, прогнать publish/confirm/consume, убить под, убедиться что majority жив и клиенты переподключились.
8. Только потом — реальные очереди интеграционных воркеров.
9. Синтетическая нагрузка: потолок confirm/с, диск, RAM. По результату — вертикаль или 5 нод.
10. Прогон «ЦОД недоступен» на препроде: выключить зону, проверить publish с confirm и consume.

Без пункта 10 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | 3 (или 5) нод; Khepri majority; **quorum queues/streams**, не classic; реплики по ЦОДам; durable диск; переживает 1 ЦОД |
| Производительность / масштаб | Не требуется | Сначала вертикаль; нечётное добавление нод; не десятки нод в одном кластере; confirm latency заложена от RTT; диск перезаложен под WAL |
| Безопасность | AMQP без TLS только в изоляции | TLS 5671/15671; inter-node TLS между ЦОДами; нет guest; нет ANONYMOUS; cookie и 25672 закрыты; отдельный пользователь на приложение |

**Не готов к проду**, если: одна нода «потому что кластер сложный», classic queues как HA, mirroring из мануала 3.x, `guest` снаружи, PLAINTEXT на общей сети, emptyDir, `OrderedReady` + `check_running` как единственный probe, RTT неизвестен, а схема уже stretch, RabbitMQ объявлен «вместо Kafka».
