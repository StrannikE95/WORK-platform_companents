# Apache Kafka 4.3.1 — установка и конфигурирование

Связанный документ (глоссарий, RF/min.ISR, ACL, почему так): `Apache Kafka.md`.

Этот файл — **как поставить и настроить**. Stretch одного кластера брокеров на несколько ЦОДов **не делаем**: `acks=all` не быстрее репликации на копию в другом ЦОДе; при неприемлемом RTT ISR осыпается, запись получает `NOT_ENOUGH_REPLICAS`.

Версии: **Kafka 4.3.1** (только KRaft, ZooKeeper нет), Java на брокерах **≥ 17** (17 / 21 / 25). На Kubernetes — **Strimzi 1.2.0** (матрица: Kafka 4.3.1).  
Образ: `apache/kafka:4.3.1`. Документация: https://kafka.apache.org/43/

---

## Допущения этой инструкции

1. **По кластеру Kafka на ЦОД.** Между ЦОДами — **MirrorMaker 2** (асинхронно). Это несколько экземпляров, не один.
2. Kubernetes в каждом ЦОДе свой (`Kubernetes.install.md`). Брокерам одного кластера нужна прямая L3-связность **внутри** ЦОДа. Overlay с большим jitter — замерить; если хуже VM — hostNetwork или вне K8s (решение по замеру, не по моде).
3. Dev — изолированная сеть, PLAINTEXT допустим. Прод — TLS до появления боевых клиентов.
4. Нагрузки нет — нет числа брокеров «хватит для терабайт». Минимум HA = размещение реплик, не ёмкость.
5. SASL/SCRAM-SHA-512 поверх TLS как практичный старт без Kerberos (выбор ИБ может быть OAUTHBEARER/GSSAPI).
6. Camunda / озеро / интеграционное API — клиенты, не часть этого ПО.

## Dev: 1 ЦОД, без нагрузки

**Цель:** писать/читать события, контракты, воркеры. **Не** цель: отказ ЦОДа.

### Предпосылки

- Docker **или** Dev-Kubernetes.
- Java 17+ только если ставите без Docker (бинарный дистрибутив).

### Установка (Docker combined mode)

Один процесс: и брокер, и контроллер. Apache это разрешает для development, **запрещает** для critical/prod.

Официальный путь bootstrap в 4.1+: динамический кворум, `kafka-storage.sh format --standalone`, затем старт. Образ `apache/kafka:4.3.1` форматирует диск при первом запуске по переменным образа — сверять README **этого тега**, не копировать устаревшие `KAFKA_ZOOKEEPER_CONNECT`.

```bash
docker run -d --name kafka-dev \
  -p 127.0.0.1:9092:9092 \
  apache/kafka:4.3.1
```

Привязка к `127.0.0.1` обязательна. Переменные listener/`advertised` — из README образа 4.3.1: клиент с хоста должен видеть то имя/порт, который брокер рекламирует (частая поломка: внутри контейнера `localhost`, с хоста — нет).

Проверка: создать топик RF=1, produce/consume с той же машины. ZooKeeper **не** ставить.

На Kubernetes Dev: оператор **Strimzi 1.2.0** (пакет с https://strimzi.io/downloads/, не `latest` с main), затем Kafka CR: версия **4.3.1**, 1 брокер, маленький PVC. Combined/один replica — только Dev. **Не** этот CR в прод.

```bash
kubectl create namespace kafka
# манифест оператора 1.2.0 с downloads (имя файла смотреть в релизе, не выдумывать latest)
kubectl apply -n kafka -f <strimzi-cluster-operator-1.2.0.yaml>
```

### Конфигурирование Dev

| Параметр | На тесте | Почему можно |
|---|---|---|
| Combined mode | да | Не нужно отдельно катить контроллеры |
| RF / min.ISR | 1 / 1 | Некому реплицировать |
| PLAINTEXT | да, сеть закрыта | Иначе PKI раньше событий |
| `auto.create.topics.enable` | можно true | Удобство; в прод — false |

Чего **не** упрощать в **клиентском коде**: `acks=all`; явные имена топиков; ключ партиции; версия клиента не древнее брокера на поколение без проверки.

### Проверка Dev

1. Создать топик, записать, прочитать.
2. Рестарт контейнера: при RF=1 незареплицированное теряется — это ожидаемо, не баг стенда.

### Сильные / слабые стороны Dev

| Сильное | Слабое |
|---|---|
| Часы, официальный combined | Любое падение ноды = простой; RF=1 |
| | Не ловит ISR, rebalance, TLS CPU, «клиент не туда» |
| | Успех на одном брокере ≠ готовность прода |

Препрод: 3 брокера + isolated controllers, RF=3, TLS — в **одном** ЦОДе.

## Prod: 2 или 3 ЦОДа, без stretch, нагрузка возможна

### Почему не stretch

Латентность produce с `acks=all` ≥ времени репликации на min.ISR копий. Если копии в другом ЦОДе и RTT плохой — это аварии ISR, не HA.

### Топология

**В каждом ЦОДе — свой кластер** (isolated KRaft):

- контроллеры отдельно от брокеров (`process.roles=controller` **или** `broker`, никогда оба);
- минимум **3 контроллера** в этом ЦОДе (пережить 1 отказ контроллера **внутри** площадки);
- минимум **3 брокера** в этом ЦОДе, `broker.rack` = зал/стойка **этого** ЦОДа (не id чужого ЦОДа);
- топики: `default.replication.factor=3`, `min.insync.replicas=2`, `unclean.leader.election.enable=false`;
- внутренние топики offsets/transactions — RF=3, min.ISR=2;
- `auto.create.topics.enable=false`.

**Между ЦОДами — MirrorMaker 2:**

| Площадок | Схема | Следствие |
|---|---|---|
| **2 ЦОДа** | Актив-пассив: MM2 ЦОД-1 → ЦОД-2 (или актив-актив по **разным** топикам) | RPO > 0; дубли возможны; offsets **не** те же |
| **3 ЦОДа** | Актив в ЦОД-1, MM2 в ЦОД-2 и ЦОД-3 **или** цепочка/звезда по политике | То же; третий кластер не делает «RF=3 между городами» |

MM2 — отдельный компонент с собственным HA (не один под). Именование топиков (`source.topic`) и идемпотентность консьюмеров закладывают **до** боя, не после первого failover.

Клиенты микросервисов в штате пишут в **локальный** bootstrap своего ЦОДа (низкий RTT). Не балансировать HTTP-LB «на все брокеры мира»: клиент ходит к **лидеру партиции**.

Failover площадки: переключить продюсеров на другой кластер — **операционка и контракт топиков**, не автомагия Kafka. Consumer group offsets с исходного кластера **не переносятся один в один**.

### Предпосылки

- Dedicated nodes (taint): не соседствовать с batch, который выбивает page cache.
- Локальный диск под `log.dirs`, не NFS.
- NetworkPolicy: клиентский listener отдельно от controller/replication.
- PKI: сертификаты с SAN=DNS, hostname verification **включён** (с Kafka 2.0 дефолт).

### Установка (Kubernetes, каждый ЦОД)

1. Ноды + local PV + labels зоны **внутри** ЦОДа.
2. Поставить **Strimzi 1.2.0** (тот же пакет, что на Dev, namespace свой на ЦОД). Helm: репозиторий `https://strimzi.io/charts/`, чарт `strimzi-kafka-operator`, `--version` сверить с релизом **1.2.0** на downloads (колонка chart ≠ app version — пинить по app 1.2.0).
3. CR: отдельные **KafkaNodePool** `controller` и `broker`; версия Kafka **4.3.1**.
4. Включить TLS и `StandardAuthorizer` **до** боевых топиков.
5. Проверить RF внутренних топиков (оператор часто создаёт сам — проверить, не поверить).
6. KafkaUser + ACL на каждый сервис (`User:camunda`, `User:integration-api`, …).
7. MM2: `KafkaMirrorMaker2` (Strimzi) между кластерами; сеть — только нужные listener'ы, TLS.

Форматирование дисков KRaft: пустой диск большинства контроллеров может выбрать лидера **без** старых метаданных. Автоformat пустых дисков в 4.x специально убрали; оператор это закрывает, ручная VM-установка — только `kafka-storage.sh` по гайду 4.3.

### Конфигурирование брокера (смысл, не полный server.properties)

| Параметр | Прод | Зачем |
|---|---|---|
| `default.replication.factor` | 3 | Забытый топик не с RF=1 |
| `min.insync.replicas` | 2 | Не подтверждать запись в одну копию |
| `unclean.leader.election.enable` | false | Не терять «уже подтверждённое» |
| `authorizer.class.name` | StandardAuthorizer | Нет ACL → нет доступа (не `allow.everyone.if.no.acl.found`) |
| Listeners | CONTROLLER / inter-broker / CLIENT раздельно | Клиенты не ходят на кворум |
| CLIENT | SASL_SSL | SCRAM без TLS вендор считает опасным |
| JVM heap | ориентир Apache для нагруженного примера LinkedIn: **6 ГиБ** кучи, остальная RAM — page cache | Раздуть кучу = отнять кэш диска |

`min.ISR=3` при RF=3: падение одного брокера **останавливает запись**. Для «система должна работать» при отказе одной машины обычно **min.ISR=2**.

Куча и лимит cgroup: лимит памяти пода **выше** `-Xmx`, иначе Linux нечем кэшировать лог.

PDB + Drain Cleaner/cordon Strimzi: иначе Kubernetes убьёт под с лидерами партиций «вежливо».

### Масштабирование (когда появятся цифры)

1. Замерить MB/s in/out, размер сообщения, число consumer groups (каждое чтение умножает исходящий трафик).
2. Партиции — единица параллелизма; слишком много — давление на контроллер.
3. Добавлять брокеры **внутри ЦОДа** пачками, затем перекладка партиций (Cruise Control / `kafka-reassign-partitions.sh`). Пустые новые брокеры сами данные не заберут.
4. Retention и опционально tiered storage — политика хранения, не «терабайты сами влезут».

### Безопасность (без этого не прод)

1. TLS на всех listener'ах, что выходят за localhost.
2. SASL или mTLS — нет анонимов.
3. ACL least privilege, `super.users` не приложения.
4. Секреты не в Git; пароли SCRAM через admin API / User Operator.
5. `advertised.listeners` — имена, которые резолвят **клиенты** (частая поломка K8s: внутри одно DNS, снаружи другое → разные listener'ы).
6. At-rest: шифрование томов (в OSS Kafka нет галочки «encrypt topics»).
7. Квоты: один зависший консьюмер не должен забить диск/сеть.

### Проверка прода

Внутри ЦОДа:

1. Produce `acks=all`, убить под брокера, ISR и клиенты живы, under-replicated → 0 после догона.
2. Попытка без ACL — отказ.
3. `kafka-metadata-quorum.sh` — кворум контроллеров.
4. Drain одной ноды без потери min.ISR (последовательный выкат, не все брокеры сразу).

Между ЦОДами:

5. MM2 догоняет тестовый топик; замерить лаг (это ваш RPO).
6. Учения: остановить ЦОД-1, переключить клиентов на ЦОД-2 **по runbook**, не «как получится».

### Сильные / слабые стороны (кластер на ЦОД + MM2)

| Сильное | Слабое |
|---|---|
| Локальная запись, не зависит от межЦОДового RTT | RPO ≠ 0, дубли, другие offsets |
| Падение ЦОДа не валит чужой кворум KRaft | Failover ручной; MM2 сам должен быть HA |
| Согласовано с запретом stretch | Операционка сложнее «одного bootstrap на страну» |

**Не готов к проду**, если: combined mode, RF=1, PLAINTEXT на общей сети, один кластер «на три ЦОДа в уме», `allow.everyone.if.no.acl.found=true`, данные на NFS, MM2 из одного пода без SLA.
