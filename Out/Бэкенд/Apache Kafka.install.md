# Apache Kafka 4.3.1 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Apache Kafka.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Apache Kafka — лог событий: сервисы пишут факты, несколько читателей забирают их в своём темпе. Ставите **свою** копию, не Confluent Platform и не облако вендора.

Версия в этой инструкции: **4.3.1** (только KRaft, ZooKeeper нет). Образ: `apache/kafka:4.3.1`. Java на брокерах **≥ 17** (официально 17 / 21 / 25). На Kubernetes — **Strimzi 1.2.0** (матрица: Kafka 4.3.1). Документация: https://kafka.apache.org/43/

Один кластер, размазанный на несколько дата-центров, здесь **не собираем**. Запись с `acks=all` не быстрее репликации на копию в другом дата-центре. Порога задержки у Apache **нет**. Поэтому живой кластер — внутри одной площадки. Вторая площадка — отдельный кластер + MirrorMaker 2 (асинхронно) или восстановление, не вторая половина того же кворума контроллеров.

---

## О чём эта инструкция молча договорилась

1. Тройка контроллеров и брокеры **одного** кластера живут в **одном** дата-центре. Между площадками — отдельный кластер + MirrorMaker 2. Не открывайте между дата-центрами порты репликации и контроллеров, если не строите осознанно другой контур.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`). Брокерам одного кластера нужна прямая связность **внутри** площадки. Overlay с большим jitter — замерить; если хуже обычных виртуальных машин — hostNetwork или вне Kubernetes (решение по замеру, не по моде).
3. Учебный стенд — закрытая сеть. Combined mode и PLAINTEXT допустимы **только там**.
4. Цифр вашей нагрузки нет — нет фразы «хватит N брокеров на терабайты». Сначала увеличивают CPU/RAM/диск; новые брокеры — пачками внутри площадки, затем перекладка партиций.
5. SASL/SCRAM-SHA-512 поверх TLS как практичный старт без Kerberos (выбор ИБ может быть OAUTHBEARER / GSSAPI).
6. Два дата-центра: кластер в первом; второй — свой кластер + MirrorMaker 2 **или** запас из снимка. Три дата-центра: то же. Третья площадка **не** третий контроллер чужого голосования.
7. Camunda / озеро / интеграционное API — клиенты, не часть этого ПО.

---

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** писать и читать события, подобрать ключ партиции, контракты, воркеры. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- Java 17+ только если ставите без Docker (бинарный дистрибутив).
- На localhost свободен порт 9092.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

Один процесс: и брокер, и контроллер. Apache это разрешает для development, **запрещает** для critical / боя.

Официальный путь bootstrap в 4.1+: динамический кворум, `kafka-storage.sh format --standalone`, затем старт. Образ `apache/kafka:4.3.1` форматирует диск при первом запуске по переменным образа — сверять README **этого тега**, не копировать устаревшие `KAFKA_ZOOKEEPER_CONNECT`.

```bash
docker run -d --name kafka-dev \
  -p 127.0.0.1:9092:9092 \
  apache/kafka:4.3.1
```

Привязка к `127.0.0.1` обязательна. Переменные listener / `advertised` — из README образа 4.3.1: клиент с хоста должен видеть то имя/порт, который брокер рекламирует (частая поломка: внутри контейнера `localhost`, с хоста — нет).

Проверка: создать топик с RF=1, записать и прочитать с той же машины. ZooKeeper **не** ставить.

На Kubernetes для учёбы: оператор **Strimzi 1.2.0** (пакет с https://strimzi.io/downloads/, не `latest` с main), затем Kafka CR: версия **4.3.1**, 1 брокер, маленький PVC. Combined / одна replica — только стенд. Этот YAML в бой не копируйте.

```bash
kubectl create namespace kafka
# манифест оператора 1.2.0 с downloads (имя файла смотреть в релизе, не выдумывать latest)
kubectl apply -n kafka -f <strimzi-cluster-operator-1.2.0.yaml>
```

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Combined mode | да | Не нужно отдельно катить контроллеры |
| RF / min.ISR | 1 / 1 | Некому реплицировать |
| PLAINTEXT | да, сеть закрыта | Иначе сертификаты раньше событий |
| `auto.create.topics.enable` | можно true | Удобство; в бой — false |

Чего **не** упрощаем: номер версии **4.3.1**; в **клиентском коде** — `acks=all`, явные имена топиков, ключ партиции; версия клиента не древнее брокера на поколение без проверки; понимание — RF=1 **не копируется** на другую машину.

### Как понять, что стенд живой

1. Топик создан, запись и чтение проходят.
2. Контейнер перезапустили с томом — данные на диске на месте. При RF=1 незареплицированное при убийстве без тома теряется — это ожидаемо, не баг стенда.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный combined | Любое падение ноды = простой; RF=1 |
| Одна нода официально нормальна для разработки | Не ловит ISR, rebalance, TLS CPU, «клиент не туда» |
| | Успех на одном брокере ≠ готовность боя |

Перед боем полезен **препрод**: 3 брокера + isolated controllers, RF=3, TLS — всё **в одном** дата-центре, даже без боевой нагрузки.

---

## Бой: один живой дата-центр, второй — запас из MirrorMaker

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три контроллера, три брокера, RF=3, запись подтверждается двумя копиями). Отказ **всего дата-центра** = этого кластера нет, пока не переключите клиентов на второй независимый кластер (или не догонит MirrorMaker 2). При асинхронной копии часть свежих сообщений можно потерять или получить дважды; offsets **не** те же — это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Латентность produce с `acks=all` ≥ времени репликации на min.ISR копий. Если копии в другом дата-центре и задержка сети плохая — это осыпание ISR и ошибки `NOT_ENOUGH_REPLICAS`, не защита. Документация Apache **не задаёт** порог миллисекунд. «Контроллеры в трёх дата-центрах» при потере двух площадок всё равно снимает большинство голосов.

### Как расставить в активном дата-центре

Один кластер (isolated KRaft):

- Контроллеры отдельно от брокеров (`process.roles=controller` **или** `broker`, никогда оба). Combined mode в бою **запрещён** документацией KRaft.
- Минимум **3 контроллера** в этом дата-центре (пережить 1 отказ контроллера **внутри** площадки). Диск контроллера — отдельный быстрый том под metadata log.
- Минимум **3 брокера** в этом дата-центре. На каждом `broker.rack` = зал / стойка **этой** площадки (не id чужого дата-центра). Иначе Kafka имеет право положить две-три реплики в один зал.
- Топики: `default.replication.factor=3`, `min.insync.replicas=2`, `unclean.leader.election.enable=false`.
- Внутренние топики offsets / transactions — RF=3, min.ISR=2.
- `auto.create.topics.enable=false`.
- Клиенты ходят на CLIENT listener (SASL_SSL), **не** на порт контроллера.
- Один и тот же номер версии **4.3.1** на брокерах **и** на контроллерах.
- Диск: локальный SSD / NVMe, **не сетевая папка**.
- Брокеры — dedicated nodes (taint/toleration): не соседствовать с batch, который выбивает page cache.
- Динамический кворум (KRaft v1, с 4.1): `controller.quorum.bootstrap.servers`. Для новой установки 4.3.1 сразу форматировать как dynamic, не тащить статический `controller.quorum.voters`.
- Форматирование дисков: пустой диск большинства контроллеров может выбрать лидера **без** старых метаданных. Автоformat пустых дисков в 4.x специально убрали; оператор это закрывает, ручная установка на VM — только `kafka-storage.sh` по гайду 4.3.

`min.ISR=3` при RF=3: падение одного брокера **останавливает запись**. Для «система должна работать» при отказе одной машины обычно **min.ISR=2**.

**Слабое место пары RF=3 / min.ISR=2:** не катить по одному брокеру во всех доменах отказа сразу. Выкат **последовательный**. PDB (PodDisruptionBudget), чтобы Kubernetes не снял сразу два брокера одной зоны. У Strimzi есть Drain Cleaner / cordon (в 1.2.0 для Kafka 4.3+ — cordoning при scale-down). Без этого Kubernetes «вежливо» убьёт под с лидерами партиций.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: кластер. Вторая: **нет** прямой репликации партиций и голосования контроллеров к первой. Запас: MirrorMaker 2 (актив-пассив: площадка 1 → площадка 2, или актив-актив по **разным** топикам) | Нет локальной записи, пока не переключите клиентов. RPO > 0; дубли возможны; offsets **не** те же. Время простоя замерить |
| **Три** | Третья как вторая (MM2 в обе запасные **или** цепочка / звезда по политике) | То же. Три независимых кластера ≠ один лог «по всей стране» без прикладного слоя |

Не кладите «все контроллеры в первой площадке, а брокеры в трёх»: падение первой оставит диски, но **без** координации. Это не переживание площадки, а «файлы ещё лежат».

Клиенты микросервисов в штате пишут в **локальный** bootstrap своей площадки. Не балансировать HTTP-LB «на все брокеры мира»: клиент ходит к **лидеру партиции**.

Failover площадки: переключить продюсеров на другой кластер — **операционка и контракт топиков**, не автомагия Kafka. Consumer group offsets с исходного кластера **не переносятся один в один**. Именование топиков MirrorMaker (`source.topic`) и идемпотентность консьюмеров закладывают **до** боя. MirrorMaker 2 — отдельный компонент с собственным отказом (не один под).

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемой скоростью, один том на один под; labels зоны **внутри** площадки.
- NetworkPolicy: клиентский listener отдельно от controller / replication.
- PKI: сертификаты с SAN=DNS, hostname verification **включён**.
- Strimzi 1.2.0 уже прогнан с образом **4.3.1** на стенде.
- Секреты не в Git; пароли SCRAM через admin API / User Operator.

### Порядок установки в активном дата-центре

1. Ноды + local PV + labels зоны **внутри** дата-центра.
2. Поставить **Strimzi 1.2.0** (тот же пакет, что на учебном стенде, namespace свой на площадку). Helm: репозиторий `https://strimzi.io/charts/`, чарт `strimzi-kafka-operator`, `--version` сверить с релизом **1.2.0** на downloads (колонка chart ≠ app version — пинить по app 1.2.0).
3. CR: отдельные **KafkaNodePool** `controller` и `broker`; версия Kafka **4.3.1**.
4. Включить TLS и `StandardAuthorizer` **до** боевых топиков.
5. Проверить RF внутренних топиков (оператор часто создаёт сам — проверить, не поверить).
6. KafkaUser + ACL на каждый сервис (`User:camunda`, `User:integration-api`, …). Least privilege: только свои топики.
7. Выложить тестовый топик, прогнать produce / consume с `acks=all`, убить под брокера, убедиться что ISR и клиенты переживают.
8. MirrorMaker 2: `KafkaMirrorMaker2` (Strimzi) между кластерами; сеть — только нужные listener'ы, TLS.
9. Только потом — реальные топики микросервисов / Camunda / интеграций.
10. Нагрузить (хотя бы синтетикой) и снять потолок. По результату — число брокеров и партиций.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| `default.replication.factor` | 3 | Забытый топик не с RF=1 |
| `min.insync.replicas` | 2 | Не подтверждать запись в одну копию |
| `unclean.leader.election.enable` | false | Не терять «уже подтверждённое» |
| `auto.create.topics.enable` | false | Иначе сервисы плодят топики без RF / ACL |
| `offsets.topic.replication.factor` / `transaction.state.log.replication.factor` | 3 | Иначе падение одного брокера ломает consumer groups и транзакции |
| `transaction.state.log.min.isr` | 2 | Согласовано с min.ISR пользовательских топиков |
| `authorizer.class.name` | StandardAuthorizer | Нет ACL → нет доступа (не `allow.everyone.if.no.acl.found`) |
| Listeners | CONTROLLER / inter-broker / CLIENT раздельно | Клиенты не ходят на кворум |
| CLIENT | SASL_SSL | SCRAM без TLS вендор считает опасным. SASL_PLAINTEXT в бою недопустим |
| JVM heap | ориентир Apache для нагруженного примера LinkedIn: **6 ГиБ** кучи, остальная RAM — page cache | Раздуть кучу = отнять кэш диска. Лимит cgroup **выше** `-Xmx` |
| `advertised.listeners` | имена, которые резолвят **клиенты** | Частая поломка Kubernetes: внутри одно DNS, снаружи другое → разные listener'ы |
| At-rest | шифрование томов | В OSS Kafka нет галочки «encrypt topics» |
| Квоты | задать | Один зависший консьюмер не должен забить диск / сеть |

Продюсеры пользовательских топиков: **`acks=all`**, RF=3, min.ISR=2.

Если появится корпоративный IdP — рассмотреть OAUTHBEARER (в 4.x он есть; в 4.3 дополнительно ужесточены allowed URL для JWKS). Это не «добавить строчку», это жизненный цикл токенов.

### Как расти, когда появятся цифры нагрузки

1. Замерить MB/s in/out, размер сообщения, число consumer groups (каждое чтение умножает исходящий трафик).
2. Выбрать размер партиции по цели задержки и параллелизму воркеров. Слишком много партиций — давление на контроллер.
3. Добавлять брокеры **внутри дата-центра** пачками, затем перекладка партиций (Cruise Control / `kafka-reassign-partitions.sh`). Пустые новые брокеры сами данные не заберут.
4. Retention и опционально tiered storage — политика хранения, не «терабайты сами влезут».
5. Следить за лимитами: сетевая карта, диск, CPU TLS, число партиций на брокер, время восстановления реплики.

### Проверки, без которых это ещё не бой

Внутри активной площадки:

1. `acks=all`, убить под брокера: ISR и клиенты живы, under-replicated → 0 после догона.
2. Попытка без ACL — отказ. Анонимов нет.
3. `kafka-metadata-quorum.sh` — кворум контроллеров. Версия 4.3.1 на **всех** брокерах и контроллерах.
4. Drain одной ноды без потери min.ISR (последовательный выкат, не все брокеры сразу).

Между площадками:

5. MirrorMaker 2 догоняет тестовый топик; замерить лаг (это ваш RPO).
6. Учение «активный дата-центр выключен»: переключение клиентов на вторую площадку **по заранее написанному сценарию**. Порты репликации и контроллеров между площадками закрыты — и это **ожидаемо**.

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + MirrorMaker»

| Хорошо | Плохо |
|---|---|
| Локальная запись, не зависит от межплощадочной задержки | RPO ≠ 0, дубли, другие offsets |
| Голосование контроллеров — локальная сеть | Падение этой площадки = нет локального лога, пока не переключите клиентов |
| Падение площадки не валит чужой кворум KRaft | Failover ручной; MirrorMaker сам должен быть отказоустойчивым |
| Согласовано с запретом stretch | Операционка сложнее «одного bootstrap на страну» |

**Не готово к бою**, если: combined mode; RF=1; PLAINTEXT на общей сети; один кластер «на три дата-центра в уме»; `allow.everyone.if.no.acl.found=true`; данные на NFS; MirrorMaker из одного пода без сценария отказа; учебный манифест уехал в бой; Kafka назначена эталоном карточек клиентов.
