# RabbitMQ 4.3.5 — термины и сокращения

Словарь к файлу `RabbitMQ.md`. Список линейный, не таблица. Сверху — слова, без которых не читаются остальные. Аналогий нет: только что это делает в коде и на диске.

---

**Процесс / нода брокера** — один процесс `rabbitmq-server` (Erlang VM). Принимает сообщения, хранит очереди, отдаёт потребителям.

**Файл / каталог на диске** — durable storage ноды: метаданные Khepri, WAL quorum queues и streams. Эфемерный диск пода → после рестарта полная синхронизация реплики с лидера. Distributed FS как общий каталог на всех нодах — путь к порче данных: ноды не координируют запись в один каталог.

**TCP-порт** — AMQP без TLS **5672**, с TLS **5671**; HTTP API/UI **15672**, HTTPS **15671**; Stream **5552**, Stream+TLS **5551**; epmd **4369**; Erlang distribution **25672** (по умолчанию AMQP-порт + 20000); клиентские порты CLI **35672–35682**; репликация stream **6000–6500**. 4369 и 25672 нельзя выставлять в публичную сеть: cookie + distribution — полный административный канал.

**ЦОД** — независимая площадка. Официально двух ЦОДов недостаточно: majority всегда окажется на одной площадке; её потеря убивает Khepri и quorum queues. Третья площадка — практический минимум.

**RTT** — время туда-обратно. Confirm quorum queue всегда ≥ RTT до другой реплики + диск. Официальная таблица кластеризации 4.3: p99 **< 1 мс** — LAN, рекомендуемая модель; **1–10 мс** — типичные AZ, дефолты обычно ок; **10–100 мс** — ЦОД/регионы возможны, закладывать латентность confirm и следить за лишними выборами лидера; **> 100 мс или видимые потери пакетов** — кластер не рекомендуют, отдельные кластеры + Shovel или Federation. Стабильность канала важнее среднего.

**TLS** — шифрование. Клиенты в проде — **5671**. Management — **15671**. Inter-node TLS между ЦОДами проект рекомендует включить. Штатный стек Erlang/OpenSSL, не ГОСТ/СКЗИ. TLS бьёт по CPU (чеклист).

**HA** — не «поставили 3 ноды», а majority Khepri + majority реплик quorum queue/stream + confirm + manual ack + реплики в разных ЦОДах + диск, который переживает рестарт пода.

**RPO / RTO** — сколько данных готовы потерять / как быстро восстановиться. Формального SLA нет. Потеря одного ЦОДа при живом majority даёт продолжение работы. Два ЦОДа сразу — кворума Khepri нет.

**SoT** — правда карточек клиентов. Очередь — буфер. Сообщение после ack исчезает. Терабайты в архитектуре — про озеро/хранилище, не про брокер.

**Под (Pod)** — единица Kubernetes. Hostname стабильный; в K8s — FQDN, `RABBITMQ_USE_LONGNAME=true`.

**StatefulSet** — отдельный PVC на ноду. Pod management **Parallel**, не `OrderedReady` (иначе rolling restart официально упирается в deadlock ожидания пира).

**PVC / CSI / local PV / NAS** — том ноды. Локальный SSD/NVMe предпочтительнее NAS; NAS допустим при стабильно низкой латентности I/O и если том **не делится** между нодами. emptyDir в проде не годится.

**cgroup** — лимит контейнера. `vm_memory_high_watermark` считать от лимита контейнера, иначе брокер увидит память ноды Kubernetes.

**OOM / alarm** — при пересечении watermark брокер перестаёт принимать новые сообщения. Это защита, не «зависание непонятно почему».

**NetworkPolicy** — 4369, 25672, 6000–6500 только между нодами и jump-хостом CLI. Клиенты — 5671.

**Anti-affinity / topology zone** — зона = ЦОД. Иначе Kubernetes положит 2 из 3 подов в один зал.

**PDB** — не снимать majority при drain. Перед drain: `rabbitmq-diagnostics check_if_node_is_quorum_critical`.

**Helm** — не основной путь в файле. Практичный: **RabbitMQ Cluster Operator**.

**PKI** — клиентский TLS и inter-node TLS. Hostname verification в проде не отключают «чтобы завелось».

**Erlang/OTP** — минимум **27.0**, максимум поддерживаемый — **27.x**. Нода на более старом Erlang не стартует. Erlang 28 официально только для новых кластеров: rolling-апгрейд Khepri с 27 → 28 на живом кластере имеет известную проблему mixed-version. Официальный Docker уже содержит нужный Erlang.

**Erlang cookie** — общий секрет (строка до 255 символов). Ноды и CLI (`rabbitmqctl`) общаются только если cookie совпадает. Это не пароль приложения, а пропуск между нодами. Генерировать автоматизацией, права файла **600**, не дефолт образа, не git.

**epmd** — маленький демон Erlang, помогает нодам найти друг друга. Порт **4369**.

**Khepri** — хранилище метаданных кластера (очереди, exchange, пользователи, vhost, права). С 4.3 это единственное хранилище: Mnesia удалена. Работает по Raft: нужна большинство живых нод. Падение большинства = кластер «глухой», даже если очереди на диске. Метаданные копируются на каждую ноду синхронно.

**Mnesia / `pause_minority` / `autoheal` / `pause_if_all_down`** — удалены в **4.3**. Чеклист «partition handling strategy» из старых гайдов к 4.3.5 не применяется. Восстановление — семантика Raft.

**Raft / кворум** — большинство должно согласиться. Для 3 нод большинство = 2. Живых меньше — метаданные и quorum-очереди не принимают новые операции.

**Кластер** — несколько нод с общими пользователями, vhost, очередями, exchange, binding. Клиент может подключиться к любой ноде (нода сама прокинет publish к лидеру quorum queue). Балансировщик перед 5671 допустим. Цена: лишняя сеть внутри, если попали не на лидера. Двузначное число нод официально уже дорого по метаданным: дробить на отдельные кластеры по контурам.

**vhost (virtual host)** — изолированное пространство внутри брокера: свои очереди и права. Дефолт — `/`. В одном контуре системы обычно достаточно одного.

**Exchange** — куда публикуют. Сам сообщения не хранит: по правилам (binding) раскидывает в очереди.

**Queue** — где сообщения ждут потребителя. Тип задаётся при создании (`x-queue-type`) и потом не меняется политикой.

**Classic queue** — обычная очередь. С RabbitMQ **4.0** она не реплицируется. Живёт на одной ноде. Упала нода — очередь недоступна (durable-сообщения на диске этой ноды). Дефолтный тип, пока его не переопределили. Для HA в 4.x не подходит.

**Quorum queue** — реплицируемая очередь на Raft. Официально «default choice», когда нужна HA и сохранность. Дефолтный размер группы — **3** члена (`quorum_queue.initial_cluster_size` / `x-quorum-initial-group-size`). Ориентир проекта: пересмотреть топологию, если **> ~5000** quorum queues (не жёсткий лимит кода). С 4.3 — 32 уровня приоритета.

**Stream** — журнал «дописал и читают с offset», ближе к Kafka-топику, чем к классической очереди. Реплицируется. Свой протокол (порты **5552/5551**) плюс AMQP. Не замена вашей Kafka-шины.

**Classic mirroring (HA queues) / `ha-mode`** — старая репликация classic. Удалена с 4.0. В 4.3.5 её нет и включать нечем.

**Лидер / follower** — у quorum queue и stream запись идёт через лидера. Confirm клиенту — когда большинство реплик записало на диск.

**Publisher confirm** — клиент просит брокера сказать «сообщение принято надёжно». Для quorum queue confirm = «большинство реплик сохранило». Без confirm клиент не знает, дошло ли. Клиент без confirm может решить, что «отправил», а брокер умер до записи.

**Consumer ack (manual ack)** — потребитель говорит «обработал, можно удалять». Без этого (auto-ack) сообщение теряется, если воркер умер на полуслове. At-least-once после рестарта потребителя — норма: нужна идемпотентность воркера.

**delivery-limit** — сколько раз сообщение можно отдать потребителю, который его nack/requeue. С 4.0 дефолт **20**; дальше — drop или dead-letter. Иначе сообщение, которое вечно отвергают, забьёт диск. Не ставить -1 «чтобы не мешало» без расчёта диска.

**DLX / dead-letter** — exchange, куда уходят отвергнутые/просроченные сообщения. Для разбора, не магическое сохранение.

**Competing consumers** — несколько потребителей на одной очереди делят работу: каждое сообщение одному. Это очередь задач, не «всем читателям своя копия», как consumer group у Kafka на логе. Единица параллелизма одной очереди — потребители плюс CPU ноды-лидера.

**Binding / routing key** — правило «из exchange в какую очередь». Direct / topic / fanout / headers — разные способы сопоставить ключ.

**AMQP 0-9-1** — исторический протокол RabbitMQ (каналы, exchange, queue). Большинство Java/.NET/Python-клиентов.

**AMQP 1.0** — международный стандарт. С 4.0 в RabbitMQ нативно, без плагина. Требует SASL.

**SASL PLAIN / AMQPLAIN / ANONYMOUS / EXTERNAL** — как клиент представляется. ANONYMOUS в проде выключают (`anonymous_login_user = none`, в `auth_mechanisms` нет ANONYMOUS). EXTERNAL — клиентский TLS-сертификат. Прод-старт: отдельные пользователи с паролем (PLAIN по TLS). Если есть IdP — OAuth 2 plugin (`rabbit_auth_backend_oauth2`).

**loopback_users / guest** — дефолт: пользователь `guest` ходит только с localhost. Страховка от выставления 5672 в сеть с паролем `guest`. В проде guest удаляют. `loopback_users.guest = false` (пустить guest снаружи) — антипаттерн чеклиста.

**Federation / Shovel** — плагины: копируют сообщения между отдельными кластерами асинхронно. Нет общего кворума через канал. Нужны, когда stretch-кластер нельзя. RPO > 0, возможны дубли. Link живёт на конкретной ноде; её падение — отдельный failover плагина.

**Stretch-кластер** — один логический кластер, ноды в разных ЦОДах. Raft ходит по межЦОДовой сети. Пока RTT не измерен — гипотеза.

**Peer discovery** — как ноды находят друг друга при старте (DNS, Kubernetes plugin, список в конфиге). В проде — автоматически, не руками `join_cluster` (официально хрупко).

**Definition import** — JSON со схемой: vhost, users, permissions, queues, policies. Штатный способ засеять кластер при выкатке. Topology Operator — то же as code.

**vm_memory_high_watermark** — порог RAM: выше — брокер перестаёт принимать новые сообщения (alarm). Дефолт **0.6** от памяти, которую видит ОС. Прод: диапазон **0.4–0.7**; выше 0.7 — только с мониторингом; ОС нужна память под page cache.

**disk_free_limit** — порог свободного диска: ниже — тоже alarm, публикация стопорится. Дефолт **50 МБ** — для туториалов, не для прода. Официальная минимальная планка: примерно как memory watermark (пример чеклиста: watermark 4 ГиБ → `disk_free_limit.absolute = 4G`). Quorum queues и streams не обязаны быстро отдавать место на диске после ack: диск перезакладывать.

**net_ticktime** — таймер Erlang «жив ли пир». Дефолт **60 с**. На WAN не понижают: ложные разрывы хуже, чем чуть более медленный детект.

**`raft.adaptive_failure_detector.poll_interval`** — интервал детектора Raft (дефолт 5000 мс). Увеличивают только если на stretch в логах повторяющиеся смены лидера очереди без реальных падений нод. Цена: дольше детект «тихого» обрыва. Чистые crash/restart ловятся без этого.

**Cluster Operator / Topology Operator** — официальные Kubernetes-операторы (MPL-2.0): кластер нод и декларативные очереди/пользователи. Cluster Operator **v2.22.5** (24 августа 2026). Дефолт оператора на дату README — образ **4.3.4**; образ пинить `rabbitmq:4.3.5-management` в `spec.image`. Тег `latest` не брать.

**Management plugin** — UI и HTTP API (**15672/15671**). Падение UI ≠ падение брокера, но API используют Topology Operator и автоматизация.

**Prometheus plugin** — метрики, отдельный listener. HA мониторинга отдельно.

**Readiness / `rabbitmq-diagnostics ping` vs `check_running`** — probe на полном старте не должен быть `check_running`, пока нода ждёт sync метаданных; для этой фазы годится `ping`.

**Минимум железа чеклиста** — **4 CPU, 4 GiB RAM** на ноду прода, без соседства с другими I/O-тяжёлыми СУБД на тех же ядрах/диске. Ниже — для dev/QA.

**File descriptors** — ориентир чеклиста: не меньше **50k**, часто сотни тысяч. Соединения + очереди. Connection churn (connect-publish-close на каждое сообщение) убивает дескрипторы.

**NTP / chrony** — кластер без NTP обычно живёт, но management-метрики врут. Штатная рекомендация.

**Durable queue / persistent messages** — очередь и сообщение переживают рестарт ноды, если диск жив. Для classic без реплик — только пока та же нода с тем же диском.

**Prefetch** — сколько не-ack сообщений отдать воркеру. По вместимости воркера, не неограниченный.

**`basic.get` в цикле** — polling. Официально считают неэффективным.

**Flow control** — давление публикации. Чеклист: отдельные соединения publish и consume, если возможно, чтобы публикация не душила ack потребителей.

**Авто-recovery клиента** — Java/.NET/Ruby умеют переподключение; иначе свой цикл, как в примерах Go/Pika.

**`default_queue_type = quorum`** — на vhost или node-wide, до того как приложения насоздают classic «по дефолту». Клиент без `x-queue-type` иначе получит classic без реплик.

**`rabbitmq-queues grow` / placement** — после роста кластера проверить, что реплики quorum queue в разных ЦОДах, не верить, что «само разложилось навсегда».

**`rabbitmq-queues quorum_status` / `cluster_status`** — телеметрия кворума очереди и состава кластера.

**Unacked / DLX depth / confirm latency** — сигналы: неподтверждённые выдачи, глубина dead-letter, задержка confirm (на stretch — датчик межЦОДовой сети). Плюс alarms памяти/диска, inter-node buffer, лидеры, которые прыгают без рестартов.

**At-rest** — брокер тела сообщений сам не шифрует, by design. Диск/том (LUKS) или шифрование на клиенте до publish.

**Tanzu / Intra-cluster Compression** — коммерческие надстройки. Файл про открытый RabbitMQ 4.3.5 (MPL-2.0).

**Camunda 7 vs 8 / Zeebe** — Camunda 7 умела ходить в Rabbit как job worker transport. Camunda 8 Self-Managed — свой протокол, не этот брокер.

**GeoData** — в совместимости указан RabbitMQ: легаси-мост AMQP, не замена Kafka.

**Image `rabbitmq:4.3.5-management`** — официальный образ. Теги `4.3.5`, `4.3`, `4`, `latest` на дату документа указывают на этот патч; в проде пинят полный тег.

**Схема 3 vs 5 нод** — 1+1+1 по ЦОДам: переживёт 1 ноду или 1 ЦОД; не переживёт 2 ЦОДа и рестарт ноды в живом ЦОДе, пока другой уже мёртв (остаётся 1 из 3). 2+2+1: 2 любых ноды или 1 ЦОД целиком; 2 ЦОДа сразу — нет majority из 5.

**QPS / нагрузка** — неизвестны. Нет числа «хватит 3 нод на терабайты». Есть минимум кворума (3 ноды) и сначала вертикаль, затем нечётное добавление нод.

**Соединение / канал (channel)** — TCP-сессия AMQP и несколько независимых потоков команд внутри одного TCP. Долгие соединения, не connect-publish-close на каждое сообщение.

**WAL (quorum / stream)** — журнал на диске реплицируемой очереди. После ack место на диске может освобождаться не сразу.

**TTL сообщения / max-length** — сколько сообщение живёт в очереди и сколько сообщений очередь держит. Backlog «на всякий» на терабайты упрётся в этот журнал. Политика должна быть явной.

**RPC / request-reply** — запрос с корреляцией и TTL ответа внутри контура, если сервисы уже говорят AMQP. Честная роль рядом с Kafka, не замена шины событий.

**LoadBalancer / Service Kubernetes** — перед 5671 допустим (в отличие от Kafka bootstrap). Нода сама прокинет publish к лидеру.

**Vault / Secret** — cookie, пароли, TLS-ключи. Не git и не картинка «для удобства».

**Jump host** — хост, с которого запускают `rabbitmqctl`. Порты CLI 35672–35682 только отсюда и от нод.

**152-ФЗ / at-rest ИБ** — брокер тела не шифрует. Требования ГОСТ и шифрования томов меняют PKI и возможность vanilla TLS.

**Image pin / `latest`** — в проде явный `rabbitmq:4.3.5-management` в `spec.image`, не дефолт оператора 4.3.4 и не `latest`.

Источники формулировок: глоссарий и тело `RabbitMQ.md`. Таблица RTT для stretch взята из документации 4.3, не выдумана. Новых порогов ёмкости здесь нет.
