# Apache Kafka 4.3.1 — развёртывание и настройка

Версия ПО: **Apache Kafka 4.3.1** (релизная дата 25 июня 2026; на дату подготовки документа это последний стабильный патч линии 4.3).  
Документация линейки: https://kafka.apache.org/43/  
Образ: `apache/kafka:4.3.1` (официальный Docker Hub).

Этот текст — не мануал «скопируй и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

---

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Брокер (broker)** | Процесс Kafka, который принимает сообщения, хранит их на диске и отдаёт потребителям. «Сервер очереди». |
| **Контроллер (controller)** | Отдельная роль в Kafka 4.x: хранит метаданные кластера (список топиков, кто лидер партиции, кто жив) и принимает решения. Работает по протоколу Raft. |
| **KRaft** | Режим, в котором метаданные живут внутри Kafka, а не в ZooKeeper. С Kafka 4.0 ZooKeeper **удалён**. 4.3.1 — только KRaft. |
| **Кворум (quorum)** | Большинство голосов. Для 3 контроллеров большинство = 2. Если живых контроллеров меньше большинства, кластер **не выбирает лидера метаданных** и перестаёт принимать изменения (создание топиков, выборы лидеров партиций). |
| **Топик (topic)** | Именованный поток сообщений (например `client.updated`). Аналог «таблицы», но это лог, а не БД. |
| **Партиция (partition)** | Кусок топика. Параллелизм Kafka = число партиций. Один потребитель в классической consumer group читает одну партицию. |
| **Реплика (replica)** | Копия партиции на другом брокере. Нужна, чтобы при падении брокера данные не пропали. |
| **RF / replication.factor** | Сколько копий у каждой партиции. RF=3 значит данные лежат на трёх брокерах. |
| **Лидер (leader)** | Та реплика, в которую пишут продюсеры. Остальные реплики — последователи (followers), они копируют данные с лидера. |
| **ISR (in-sync replicas)** | Реплики, которые не отстали. Только они считаются «достаточно свежими». |
| **min.insync.replicas (min.ISR)** | Минимум живых ISR, без которого запись с `acks=all` **отклоняется**. Это ручка «лучше отказать в записи, чем записать в одну копию». |
| **acks=all** | Продюсер ждёт, пока запись подтвердят все текущие ISR (и при этом ISR не меньше `min.ISR`). Это базовая настройка долговечности. |
| **Rack awareness** | «Осведомлённость о стойке/ЦОДе». Параметр `broker.rack`. Kafka старается разложить реплики по разным стойкам/ЦОДам, а не сложить все три копии в один шкаф. |
| **Продюсер / консьюмер** | Кто пишет / кто читает. Ваши микросервисы, Camunda-воркеры, интеграционный API. |
| **Consumer group** | Группа читателей одного топика: Kafka делит партиции между ними. Если воркеров больше, чем партиций — лишние будут простаивать. |
| **Share group (очереди Kafka)** | Другая модель чтения (KIP-932, production-ready с 4.2): несколько консьюмеров **делят** одну партицию позаписно, как классическая очередь. Нужна не всегда. |
| **Offset** | Номер сообщения в партиции. «Я прочитал до сюда». |
| **Listener** | Сетевой «вход» брокера (порт + протокол). Обычно разные входы: для клиентов, для брокеров между собой, для контроллеров. |
| **SASL** | Протокол аутентификации («кто ты»). Механизмы: SCRAM, Kerberos (GSSAPI), OAUTHBEARER, PLAIN. |
| **TLS / SSL** | Шифрование канала. В конфигурации Kafka исторически пишут `SSL`, имеется в виду TLS. |
| **SASL_SSL** | И аутентификация, и шифрование. Типичный прод-протокол для клиентов. |
| **ACL** | Список «кому что можно»: читать топик, писать, создавать, администрировать. |
| **Authorizer** | Модуль, который эти ACL проверяет. В KRaft — `StandardAuthorizer`, ACL хранятся в метаданных кластера. |
| **bootstrap.servers** | Список 2–3 брокеров, с которых клиент **узнаёт** весь кластер. Это не «все брокеры мира», а точка входа. |
| **Page cache** | Кэш диска в оперативной памяти **ядра Linux**. Kafka кладёт сообщения на диск, а читает горячий хвост лога из этого кэша. Поэтому брокеру нужна свободная RAM **не в куче JVM**. |
| **Strimzi** | Оператор Kubernetes (CNCF) для Kafka. Ставит и сопровождает кластер декларативно. Strimzi 1.2.0 официально поддерживает Kafka 4.3.1. |
| **Stretch-кластер** | Один логический кластер Kafka, брокеры и контроллеры физически стоят в нескольких ЦОДах. |
| **MirrorMaker 2 (MM2)** | Компонент Kafka, который копирует топики **между разными кластерами**. Это уже не один кластер, а репликация «кластер → кластер». |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться после аварии. |
| **Combined mode** | Один процесс и брокер, и контроллер (`process.roles=broker,controller`). Удобно для теста. **Не** для прода. |

## Основные элементы системы и зависимости

### Что входит в Apache Kafka 4.3.1 (это одно ПО)

- **KRaft-контроллеры** — кворум метаданных.
- **Брокеры** — хранение и раздача сообщений.
- **Клиенты** — producer / consumer / admin (библиотеки в приложениях).
- **Kafka Connect** — коннекторы «Kafka ↔ внешние системы» (если решите их использовать).
- **Kafka Streams** — библиотека потоковой обработки *внутри* JVM-приложения, не отдельный сервер.
- **MirrorMaker 2** — репликация между кластерами.
- **Утилиты** — `kafka-storage.sh`, `kafka-topics.sh`, `kafka-acls.sh`, `kafka-metadata-quorum.sh` и т.д.

ZooKeeper **не нужен и не ставится**.

### Чего в Apache Kafka нет (частая путаница)

| Нужно системе | Это не Kafka | Зачем помнить |
|---|---|---|
| Реестр схем сообщений (Avro/JSON Schema/Protobuf) | Confluent Schema Registry, Apicurio и аналоги | Без схем event-модель быстро превращается в хаос несовместимых JSON. |
| UI «посмотреть топики» | AKHQ, Kafdrop, Conduktor и т.п. | Не часть дистрибутива. |
| Автоперекладка партиций при добавлении брокеров | Cruise Control (отдельный проект; в образах Strimzi он есть) | Иначе после scale-out данные остаются на старых брокерах. |
| Шифрование данных **на диске** | LUKS / шифрование томов Kubernetes / hardware | В open-source Kafka нет встроенного at-rest encryption топиков. |
| ГОСТ TLS / СКЗИ | Не входит в Apache Kafka | Если это требование ИБ — отдельно проектировать контур (это критичный пробел, см. ниже). |

### Зависимости окружения (обязательны)

- **Java на брокерах / Connect / утилитах: минимум 17.** Официально для 4.3 полностью поддерживаются Java 17, 21 и 25. Apache рекомендует свежий LTS (на момент документации 4.3 — Java 25) и свежий патч JDK из соображений уязвимостей. Клиенты и Kafka Streams допускают Java 11.
- **ОС и диск:** локальные диски (SSD/NVMe), файловая система с нормальным sequential I/O. **Не NFS / не сетевой NAS как `log.dirs`.** Kafka рассчитана на локальный POSIX-диск и page cache.
- **Сеть:** стабильный IP/DNS до каждого брокера и контроллера; для клиентов — bootstrap и **прямое** соединение до брокера-лидера партиции (балансировщик «как у HTTP» перед всеми брокерами ломает модель).
- **Kubernetes (у вас заявлен):** оркестрация не заменяет диск и сеть. Kafka — stateful. Практичный путь на K8s: **Strimzi 1.2.0** (подтверждена совместимость с 4.3.1).

### Как Kafka стыкуется с вашей архитектурой

```
Микросервисы, Camunda, интеграционное API
        │  produce / consume
        ▼
   Kafka (шина событий)     ← этот документ
        │
        ▼
Озеро эталонных данных, БД, другие сервисы
```

Kafka — **лог событий**, не «источник истины» клиентских данных. Источник истины у вас задуман как озеро/хранилище. Kafka доставляет факт «данные изменились / данные запрошены». Если положить SoT в Kafka, вы получите лог, из которого неудобно делать произвольные выборки «дай клиента по ИНН».

## Краткие вводные

### Зачем вам Kafka в этой архитектуре

Микросервисы на событиях и «30+ интеграций» создают пики, задержки внешних ведомств и необходимость не потерять факт. Kafka даёт:

1. **Буфер** между тем, кто произвёл событие, и тем, кто его обработает (в том числе когда Camunda или интеграционный API временно медленные).
2. **Несколько независимых читателей** одного потока (аудит, озеро данных, процессный движок) без повторной записи в каждый.
3. **Горизонтальное масштабирование чтения/записи** через партиции.

### Как устроена отказоустойчивость (идея, не магия)

Долговечность записи в Kafka — это **не** «fsync на диск», а **репликация на другие брокеры**. Сообщение считается надёжно принятым, когда:

- продюсер использует `acks=all`;
- у топика `min.insync.replicas >= 2`;
- реплики лежат в **разных** доменах отказа (`broker.rack` = ЦОД);
- `unclean.leader.election.enable=false` (значение по умолчанию) — нельзя выбрать лидером отставшую реплику ценой потери уже «подтверждённых» сообщений.

Если отключить это «для скорости», кластер будет быстро писать и молча терять данные при падении брокера.

### Как устроено масштабирование

Единица параллелизма — **партиция**, не «ещё один Kafka». Добавление брокеров увеличивает диск, сеть и CPU, но **не** ускоряет топик, пока партиции не переложены на новые брокеры и пока число партиций достаточно.

Грубая логика (не формула ёмкости — нагрузки у вас нет):

- слишком мало партиций → потолок по throughput и по числу параллельных консьюмеров;
- слишком много партиций → давление на контроллер, дольше восстановление, больше файлов на диске, выше хвосты латентности.

Число партиций выбирают **после** оценки: целевой MB/s, размер сообщения, латентность `acks=all`, число consumer groups. Сейчас этой оценки нет — см. критичные пробелы.

### Память брокера — типичная ошибка

Сообщения **не** живут в куче JVM. Куча нужна под метаданные, сетевые буферы, индексы. Горячие данные читаются из **page cache** ядра.

Официальный пример JVM-аргументов Apache для нагруженного кластера LinkedIn: куча **6 ГБ** (`-Xmx6g -Xms6g`) и G1GC. Остальная RAM машины — кэш диска. Раздуть кучу «как у обычного Java-сервиса» до 32 ГБ — значит отнять память у page cache и замедлить чтение.

Для контроллеров Apache отдельно пишет: для типичного кластера достаточно порядка **5 ГБ RAM и 5 ГБ диска** под metadata log. Это оценка проекта Kafka, не замер вашего кластера.

### TLS стоит производительности

При TLS путь zero-copy `sendfile` для отдачи данных клиенту **не работает** так же, как на plaintext: брокер должен шифровать байты. Это нормальная плата за безопасность, но «включим TLS и останется та же скорость» — неверно. Закладывайте запас по CPU брокеров.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть, а не «чуть подкрутить порты».

1. **Берём Apache Kafka 4.3.1**, не Confluent Platform и не «Kafka API-совместимый» форк. Поведение, лицензия и операторные обвязки у них разные.
2. **Прод крутится в Kubernetes**, и приемлемый способ это делать — **Strimzi 1.2.0** (подтверждена поддержка 4.3.1). Альтернатива — выделенные VM/bare metal; правила по RF/rack/безопасности те же, отличается только установка.
3. **Три ЦОДа в одном городе** рассматриваются как три независимых домена отказа (питание, сеть, площадка). Если это три зала в одном здании с общим UPS — это **не** три ЦОДа, и stretch-схема даёт ложное чувство безопасности.
4. **Stretch-кластер (один кластер на 3 ЦОДа)** принимается как целевой для прода **только если** межЦОДовая сеть достаточно быстрая и стабильная. Порога RTT в документации Apache **нет**. Индустриальная практика (метро/AZ): единицы–низкие десятки миллисекунд; межконтинент так не растягивают. **Пока RTT не измерен — это гипотеза, не решение.**
5. **Один логический Kubernetes с тремя зонами** *или* три кластера K8s, но брокеры одного Kafka всё равно должны иметь прямую L3-связность. Если K8s в ЦОДах изолированы без маршрутизации pod-to-pod — stretch Kafka на K8s **не взлетит**, нужен другой сетевой дизайн или три отдельных Kafka + MM2.
6. **Нагрузки нет** — поэтому ниже **нет** числа брокеров «хватит для прода» и **нет** размера диска. Есть только минимум для отказоустойчивости и правила, как потом расти.
7. **Формального SLA / RPO / RTO нет.** Для stretch при корректных RF/min.ISR и живой сети потеря одного ЦОДа даёт RPO≈0 для уже подтверждённых `acks=all` записей и автоматическое продолжение работы. Это не то же самое, что юридический 24/7.
8. **Корпоративный PKI есть или будет** (CA, выпуск сертификатов с SAN=DNS). Hostname verification в Kafka с 2.0 **включён по умолчанию**; отключать его «чтобы завелось» нельзя считать прод-настройкой.
9. **Идентификация сервисов** — SASL/SCRAM-SHA-512 (логин/пароль в метаданных Kafka) как практичный старт без Kerberos. Если в контуре уже есть IdP (Keycloak и т.п.) — разумнее OAUTHBEARER; если есть доменный Kerberos — GSSAPI. Это выбор ИБ, не «единственно верный».
10. **Шифрование канала — TLS 1.2+** стандартными алгоритмами JDK. Требования ГОСТ/СКЗИ **не озвучены**; если они появятся, vanilla Apache Kafka их не закрывает.
11. **Тестовый стенд** — изолированная сеть, на нём допустим PLAINTEXT. Прод-конфиг безопасности на тест один в один не копируем, но **топики и клиентский код** лучше сразу учить с `acks=all` и явным replication factor, иначе тест врёт.
12. **Camunda, озеро данных, интеграционное API** — клиенты Kafka, не часть этого ПО. Их consumer groups, ключи партиционирования и схемы сообщений проектируются отдельно; от Kafka им нужны bootstrap, сертификаты/учётки и квоты.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** закупки железа и «постановки в прод». Иначе архитектура разъедется.

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потеря пакетов между ЦОДами (p50/p95/p99, в обе стороны, все пары)** | При `acks=all` и реплике в другом ЦОДе латентность записи **не может быть ниже**, чем время репликации на эту копию. Если RTT высокий или «плавает», ISR будут выпадать, записи начнут получать `NOT_ENOUGH_REPLICAS`, клиенты будут ретраить. Stretch станет источником аварий, а не защиты. |
| **Профиль нагрузки** (сообщ./с, MB/s in/out, средний размер, число топиков, партиций, consumer groups, пик vs среднее) | Без этого нельзя сказать ни число брокеров, ни диск, ни «готовы к высокой нагрузке». Kafka масштабируется, но не бесплатно и не линейно от «добавим нод». |
| **Срок хранения и реальный объём** («терабайты» — это 2 или 200? за день или за год?) | Retention (`log.retention.*` или compaction) определяет диск. Без политики хранения любой кластер рано или поздно упрётся в диск. |
| **Формальные RPO/RTO и что значит «упал ЦОД»** | Stretch переживает **один** ЦОД. Два ЦОДа сразу при трёх площадках кворум из 3 или 5 контроллеров, как правило, **не** переживает. Если требование — «живём при потере двух площадок», нужна другая схема (четвёртая площадка / не один кластер). |
| **Топология Kubernetes** (один кластер на 3 ЦОДа или три изолированных) | От этого зависит, возможен ли stretch вообще. |
| **Требования ИБ: ГОСТ, 152-ФЗ, шифрование at-rest, срок хранения ключей, контур КИИ** | Меняют PKI, возможность облачных операторов, необходимость дискового шифрования, аудит. |
| **Есть ли уже Kafka / ZooKeeper-кластер** | На 4.3.1 с ZooKeeper не входят. Миграция только через bridge-релиз **3.9** (последний, где есть переход ZK→KRaft). Для greenfield это неважно. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать версию **4.3.1** и Java (брокеры ≥ 17).
2. Выбрать роли: combined **только** на тесте; в проде `process.roles=controller` **или** `broker`, никогда оба.
3. Сгенерировать `cluster.id`, **отформатировать** диски через `kafka-storage.sh` (в KRaft автоформатирование пустых дисков специально убрали: пустой диск большинства контроллеров может выбрать лидера **без** уже закоммиченных метаданных).
4. Поднять кворум контроллеров, затем брокеры.
5. Выставить дефолты топиков и внутренние топики (`offsets`, `transaction state`).
6. Включить безопасность (на проде — до появления реальных клиентов, не «потом»).
7. Дать клиентам bootstrap **и** правила: `acks=all`, идемпотентный продюсер (в современных клиентах по умолчанию включён), осмысленный ключ партиции.
8. Мониторинг: ISR < RF, under-replicated partitions, request latency, disk, page cache / miss-чтение, лаг консьюмеров, здоровье кворума (`kafka-metadata-quorum.sh`).

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики писали и читали события, отлаживали контракты, поднимали Camunda/сервисы. **Не** цель: доказать отказоустойчивость и ёмкость прода.

#### Топология

Минимально достаточно **одного** процесса в combined mode:

- `process.roles=broker,controller`
- один `node.id`
- один диск
- listener `PLAINTEXT` только на изолированной сети стенда
- топики с `replication.factor=1`, `min.insync.replicas=1`

Альтернатива чуть ближе к проду: 1 контроллер + 1 брокер на одной машине/в одном namespace. Отказоустойчивости всё равно нет.

На Kubernetes: Strimzi в dev-профиле (1 replica, эфемерный или маленький PVC). Не используйте этот YAML как прод.

Официальный путь bootstrap контроллера: `kafka-storage.sh format --standalone` (динамический кворум), затем брокеры с `--no-initial-controllers`. В 4.1+ динамический кворум — рекомендуемый; `controller.quorum.bootstrap.servers` вместо статического `controller.quorum.voters`.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Combined mode | да | Apache прямо разрешает для dev; нельзя отдельно катить контроллеры — на тесте не важно |
| RF / min.ISR | 1 / 1 | Некому реплицировать |
| PLAINTEXT | да, если сеть закрыта | Иначе команда утонет в сертификатах раньше, чем в событиях |
| Автосоздание топиков | можно включить | Удобство; в прод — выключить |
| Мониторинг | минимум (логи + что процесс жив) | Нет нагрузки |

#### Чего на тесте **не** стоит упрощать в клиентском коде

- Продюсер с `acks=all` (на RF=1 это просто «лидер записал»). Иначе в проде внезапно появятся другие гарантии.
- Явные имена топиков, а не «как получится».
- Ключ сообщения (partition key) — от него зависит порядок и «горячие» партиции.
- Версия клиента не древнее брокера на поколение без проверки совместимости.

#### Сильные стороны такой схемы

- Поднимается за часы, не за недели.
- Дешёвая.
- Совпадает с рекомендацией Apache: combined mode для development.

#### Слабые стороны (обязательно понимать)

- **Любое** падение ноды = простой и, при RF=1, потеря незареплицированных данных.
- Стенд **не** ловит проблемы: rebalance, ISR, межЦОДовая латентность, TLS CPU, «клиент достучался не до того брокера».
- Успешный тест на одном брокере **не** является доказательством готовности прода.

Практическая рекомендация: когда появится «препрод», сделать **маленькую копию прод-топологии** (3 брокера, RF=3, TLS) даже без боевой нагрузки — иначе первый сюрприз будет уже на пользователях.

### Прод: 3 ЦОДа, нагрузка

Ниже — правила, которые делают экземпляр пригодным к отказу площадки, росту и закрытому доступу. Цифры брокеров «под терабайты» **не** ставятся: нагрузки нет.

#### Шаг 0. Выбор макроархитектуры (сделать до установки)

**Вариант A — stretch (один кластер на 3 ЦОДа).**  
Предпочтителен, если сеть метро-класса и есть прямая связность брокеров.

- Клиентам один `bootstrap.servers`.
- Падение 1 ЦОДа не требует «переключения на другой Kafka».
- Запись с `acks=all` всегда идёт через межЦОДовую репликацию → латентность записи привязана к RTT.

**Вариант B — три (или два) отдельных кластера + MirrorMaker 2.**  
Если RTT большой, сеть рвётся, или K8s-кластеры не маршрутизируются.

- Локальная запись быстрая.
- МежЦОДовая доставка **асинхронная**: RPO > 0, появятся дубли, offsets не те же самые, операционка сложнее.
- Это уже не «один экземпляр», а несколько, плюс MM2 как отдельный компонент с собственным HA.

**Пока RTT не измерен, нельзя честно выбрать A.** Дальнейший текст описывает **вариант A** как целевой для «3 ЦОДа в одном городе»; вариант B — запасной, если замер сети убьёт A.

##### Сильные / слабые стороны stretch (A)

| Сильное | Слабое |
|---|---|
| Один кластер, простой ментальный модель для разработчиков | Латентность записи ≥ репликации в другой ЦОД |
| При 1 мёртвом ЦОДе и min.ISR=2 запись может продолжаться | Сетевой шторм между ЦОДами выглядит как деградация Kafka |
| Нет перевода offset'ов при failover | Не переживает потерю **двух** ЦОДов |
| Согласовано с rack awareness | Требует, чтобы Kubernetes/сеть это умели |

##### Сильные / слабые стороны MM2 (B)

| Сильное | Слабое |
|---|---|
| ЦОД независим по записи | RPO ≠ 0, eventual consistency между площадками |
| Не зависит от межЦОДового RTT на критическом пути produce | Сложные failover, дубли, именование топиков (`source.topic`) |
| Можно делать актив-пассив | MM2 сам должен быть отказоустойчивым |

#### Контроллеры (кворум)

Правило Apache: чтобы пережить **N** одновременных отказов контроллеров, нужно **2N+1** штук. Combined mode в проде **запрещён** документацией KRaft («not recommended in critical deployment environments»): контроллер нельзя катить отдельно от брокера, он делит GC и диск с нагрузкой клиентов.

| Схема | Что переживёт | Чего не переживёт |
|---|---|---|
| 3 контроллера, по 1 в ЦОД | 1 контроллер или 1 ЦОД | 2 ЦОДа; одновременный рестарт контроллера в живом ЦОДе, пока другой ЦОД уже мёртв |
| 5 контроллеров, например 2+2+1 по ЦОДам | 2 любых контроллера; 1 ЦОД целиком | 2 ЦОДа сразу (на оставшейся площадке обычно нет большинства из 5) |

Для старта прода при трёх площадках **минимум — 3 контроллера (по одному в ЦОД)**. 5 — если готовы платить нодами за более спокойные rolling upgrade.

Динамический кворум (KRaft v1, с 4.1): `controller.quorum.bootstrap.servers`, добавление/удаление контроллеров утилитой `kafka-metadata-quorum.sh`. Для greenfield 4.3.1 сразу форматировать как dynamic, не тащить статический `controller.quorum.voters`.

Listener контроллеров — **отдельный**, не клиентский. Клиенты на него не ходят. В K8s — NetworkPolicy: только брокеры и контроллеры.

Диск контроллера — отдельный быстрый том под metadata log, не общая «куча» с `log.dirs` брокера (в isolated mode это разные процессы и так).

#### Брокеры и раскладка по ЦОДам

**Минимум для HA с RF=3:** не меньше **одного брокера в каждом ЦОДе**, итого ≥ 3. Это минимум **размещения реплик**, не ёмкость.

Дальше масштабирование — **добавлять брокеры равномерно по трём ЦОДам** (3, 6, 9, …), чтобы `broker.rack` мог держать по реплике в каждом ЦОДе.

На каждом брокере:

```
broker.rack=<id ЦОДа>
```

Иначе Kafka имеет право положить две-три реплики в один ЦОД — и «три ЦОДа» на бумаге не спасут.

В Kubernetes: topology zone → `broker.rack` (у Strimzi это штатный rack awareness). Брокеры — **dedicated nodes** (taint/toleration): не соседствовать с batch-джобами, которые выбивают page cache.

Диск брокера:

- local PV / NVMe, не NFS;
- отдельный StorageClass;
- объём = (входящий поток × retention × RF / число брокеров) × запас; **формула пустая, пока нет потока и retention**.
- несколько каталогов `log.dirs` (JBOD) допустимы; RAID «для надёжности» часто вреден: надёжность уже в репликации, RAID-rebuild убивает латентность.

#### Обязательные настройки долговечности (кластер + топики)

Дефолты брокера (чтобы «забытый» топик не родился с RF=1):

| Параметр | Прод-значение | Зачем |
|---|---|---|
| `default.replication.factor` | 3 | Новые топики не живут в одной копии |
| `min.insync.replicas` | 2 | Запись не подтверждается, если жива только одна копия |
| `unclean.leader.election.enable` | `false` (дефолт) | Не выбирать лидером отставшую реплику |
| `auto.create.topics.enable` | `false` | Иначе сервисы плодят топики без RF/ACL |
| `offsets.topic.replication.factor` | 3 | Иначе падение одного брокера ломает consumer groups |
| `transaction.state.log.replication.factor` | 3 | То же для транзакций |
| `transaction.state.log.min.isr` | 2 | Согласовано с min.ISR пользовательских топиков |

Пользовательские топики: **RF=3, min.ISR=2**, продюсеры **`acks=all`**.

Что это даёт при падении **одного** ЦОДа (реплики разложены 1+1+1):

- остаются 2 копии;
- `min.ISR=2` ещё выполняется → **запись жива**;
- чтение живо.

Если поставить `min.ISR=3`, то при падении одного ЦОДа **запись остановится** (выше долговечность «должно быть три живых копии», ниже доступность). Для «система должна работать» обычно берут min.ISR=2.

**Слабое место этой пары RF=3 / min.ISR=2:** если вы одновременно катите по одному брокеру **в каждом** ЦОДе, ISR может просесть ниже 2. Concurrent rolling «все ЦОДы сразу» требует либо большей RF (в документации Confluent для 3 region приводят RF≥4), либо **последовательного** выката по одному ЦОДу. Для vanilla Apache это не отдельный параметр, это дисциплина эксплуатации.

#### Масштабирование под нагрузку (когда цифры появятся)

Порядок, а не гадание:

1. Замерить вход: MB/s, msg/s, размер, пик.
2. Замерить выход: число consumer groups (каждое чтение умножает исходящий трафик).
3. Выбрать размер партиции по цели латентности и параллелизму воркеров.
4. Добавить брокеры **пачками по 3** (по ЦОДу).
5. Переложить партиции (Cruise Control / ручной `kafka-reassign-partitions.sh`). Без этого новые брокеры будут пустыми.
6. Следить за лимитами: сетевая карта, диск write/read, CPU TLS, число партиций на брокер, время восстановления реплики.

«Терабайты» сами по себе не требуют сотен брокеров: если это холодный архив, смотрят **retention** и опционально **tiered storage** (вынос старых сегментов в object storage). Tiered storage в 4.x существует, но это отдельный контур (S3-совместимое хранилище, другая операционка). Не включать «на всякий случай» без политики хранения.

Share groups (очереди) включать точечно: `kafka-features.sh` / `share.version=1`, когда нужен именно конкурентный разбор **записей**, а не порядок внутри ключа. Для event-sourcing клиентских данных обычно остаются классические consumer groups.

#### Безопасность прода (без этого кластер не считается настроенным)

Три слоя, все три:

1. **Шифрование канала (TLS)** — нельзя читать трафик в сети ЦОДа/между ЦОДами.
2. **Аутентификация (SASL или mTLS)** — нельзя подключиться анонимом.
3. **Авторизация (ACL)** — сервис А не читает топики сервиса Б.

Практичная схема слушателей:

| Listener | Кто ходит | Протокол |
|---|---|---|
| `CONTROLLER` | только контроллеры и брокеры | SSL (и доступ закрыт сетью) |
| `REPLICATION` / inter-broker | брокеры между собой | SSL или SASL_SSL |
| `CLIENT` | микросервисы, Camunda, Connect | SASL_SSL |
| Внешний, если вообще нужен | только через отдельный listener | SASL_SSL; лучше не торчать в интернет |

Авторizer на **всех** нодах (брокеры и контроллеры):

```
authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer
```

Поведение по умолчанию: нет ACL на ресурс → **доступ только super.users**. Не включать `allow.everyone.if.no.acl.found=true` в проде.

`super.users` — служебные учётки операторов и брокеров, не приложения.

Клиентская аутентификация (допущение 9): **SASL/SCRAM-SHA-512 поверх TLS**. Официальная документация прямо требует TLS для SCRAM: без него возможен перехват обмена и, при компрометации контроллеров, impersonation. **SASL/PLAIN без TLS в проде недопустим.** SASL_PLAINTEXT — то же самое по сути «пароль открытым текстом в сети».

Сертификаты:

- формат PKCS12 (дефолт современных JDK; JKS устарел);
- SAN=DNS на реальное имя брокера, которое видит клиент;
- **не** обнулять `ssl.endpoint.identification.algorithm`;
- ротация до истечения; отдельный процесс, не «руками раз в три года».

Секреты: не в Git и не в открытом ConfigMap. Kubernetes Secrets + желательно внешний vault. Пароли SCRAM задаются через admin API, не лежат в `server.properties` plaintext-файлом на всех нодах как в старых примерах PLAIN.

Сеть:

- NetworkPolicy / firewall: клиенты только на CLIENT-порт;
- контроллерный порт не публиковать через LoadBalancer «на всякий случай»;
- помнить: клиент ходит **на брокера-лидера**, advertised.listeners должны быть именами, резолвящимися у клиента (частая поломка на K8s: внутри кластера одно имя, снаружи другое — для этого разные listener'ы).

Прочее, без чего «безопасность» дырявая:

- отдельный principal и ACL на каждый сервис (`User:camunda`, `User:integration-api`, …) — least privilege: только свои топики;
- квоты (`quota`) — чтобы один зависший консьюмер не забил диск и сеть;
- аудит подключений и ACL-изменений (логи брокера + централизованный сбор);
- at-rest: шифрование томов;
- не давать разработчикам `ALL` на кластер в проде.

##### Сильные / слабые стороны выбранной ИБ-схемы (TLS + SCRAM + ACL)

| Сильное | Слабое |
|---|---|
| Закрывает сеть, «кто ты», «что можно» штатными средствами Apache | SCRAM — это пароли; нужна ротация и секрет-хранилище |
| StandardAuthorizer хранит ACL в метаданных, без внешней БД | Ошибка в ACL = простой сервиса; нужен процесс выдачи прав |
| Strimzi User Operator умеет заводить пользователей декларативно | TLS бьёт по CPU и zero-copy |
| Не зависит от Kerberos, если его нет | Не ГОСТ; mTLS сложнее в выдаче клиентских сертификатов, но сильнее привязывает identity к PKI |

Если появится корпоративный IdP — рассмотреть OAUTHBEARER (в 4.x он есть; в 4.3 дополнительно ужесточены allowed URL для JWKS). Это не «добавить строчку», это жизненный цикл токенов.

#### Kubernetes-специфика прода

- Отдельные **KafkaNodePool**: `controller` и `broker`.
- PDB (PodDisruptionBudget), чтобы kubelet/кластер не снял сразу два брокера одной зоны.
- Drain: у Strimzi есть Drain Cleaner / cordon (в 1.2.0 для Kafka 4.3+ — cordoning при scale-down). Без этого Kubernetes «вежливо» убьёт под с лидерами партиций.
- Не ставить Kafka на overlay с большим jitter без замера. Если сеть подов между ЦОДами хуже, чем VM-сеть — брокеры иногда лучше держать на hostNetwork или вне K8s. Это решение по замерам, не по моде.
- Ресурсы: лимиты памяти **выше** кучи JVM, чтобы остался page cache. Если лимит = куча, Linux нечем кэшировать лог.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами. Решение A vs B.
2. Выделить ноды и local storage, настроить зоны/`broker.rack`.
3. Поставить Strimzi 1.2.0, описать кластер 4.3.1, isolated controllers.
4. Включить TLS и authorizer **до** создания боевых топиков.
5. Создать внутренние топики с RF=3 (часто оператор делает сам — проверить, не поверить).
6. Завести пользователей и ACL под первые сервисы.
7. Выложить тестовый топик, прогнать produce/consume с `acks=all`, убить под брокера, убедиться что ISR и клиенты переживают.
8. Только потом — реальные топики микросервисов/Camunda/интеграций.
9. Нагрузить (хотя бы синтетикой) и снять потолок. По результату — число брокеров и партиций.
10. Прогон «ЦОД недоступен» на препроде: выключить зону, проверить запись и чтение, кворум контроллеров.

Без пункта 10 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Isolated KRaft 3 или 5; RF=3; min.ISR=2; `broker.rack`; unclean election выкл; переживает 1 ЦОД |
| Производительность / масштаб | Не требуется | Партиции как единица масштаба; брокеры пачками по ЦОДам; куча ~6 ГБ + RAM под page cache; локальные диски; перекладка партиций при scale-out |
| Безопасность | PLAINTEXT только в изоляции | TLS везде; SASL_SSL; StandardAuthorizer; нет ACL → нет доступа; отдельные listener'ы; секреты не в git |

**Не готов к проду**, если: combined mode, RF=1, PLAINTEXT на общей сети, все реплики без rack, `allow.everyone.if.no.acl.found=true`, контроллеры и брокеры на одном процессе, данные на NFS, RTT между ЦОДами неизвестен, а схема уже stretch.
