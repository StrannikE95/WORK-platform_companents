# SafeLine WAF 9.4.0 — развёртывание и настройка

Версия ПО: **SafeLine 9.4.0** (релизная дата 17 августа 2026; на дату подготовки документа это последний стабильный релиз линии 9.x).  
Документация: https://docs.waf.chaitin.com/  
Репозиторий: https://github.com/chaitin/SafeLine  
Образы: `chaitin/safeline-*` (Docker Hub; международная линейка задаётся `REGION=-g`).

Этот текст — не мануал «скопируй и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

---

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **WAF (Web Application Firewall)** | Фильтр **HTTP/HTTPS**-запросов перед вашим приложением. Смотрит не «порт открыт/закрыт» (это обычный firewall), а содержимое веб-запроса: SQL-инъекция, XSS, подозрительный бот и т.п. |
| **Reverse proxy (обратный прокси)** | Клиент стучится не в приложение, а в SafeLine. SafeLine проверяет запрос и, если он «чистый», пересылает его на **upstream** (настоящий сервер). Так устроен SafeLine. |
| **Upstream / origin** | Реальный адрес приложения за WAF (ваш Ingress, Integration API, портал). |
| **Tengine** | Форк Nginx от Alibaba. В SafeLine контейнер `safeline-tengine` принимает трафик 80/443 и отдаёт его на проверку. |
| **Детектор (detector)** | Движок семантического анализа: решает, атака это или нет. Отдельный контейнер `safeline-detector`. |
| **MGT / консоль** | Веб-админка и API управления (`safeline-mgt`), обычно `https://<ip>:9443`. |
| **Семантический анализ** | Детекция не только по «чёрным спискам строк», а по смыслу запроса (инъекция, обход пути и т.д.). Это заявленное ядро SafeLine. |
| **Application (сайт / приложение в консоли)** | Правило «какой домен/порт слушаем → куда форвардим». Не путать с вашим микросервисом в Kubernetes. |
| **Config Auto Sync** | Функция **Pro**: один узел объявляется **master**, остальные — **slave**; конфигурация (сайты, правила) копируется со master на slave. Это **не** общий кластер с общей БД. |
| **Master / slave** | Master — единственное место, где правят правила. Slave принимает копию и обычно **не даёт** менять конфиг локально. Трафик при этом могут принимать **все** узлы. |
| **QPS** | Запросов в секунду к WAF. Единица, в которой SafeLine в FAQ даёт ориентиры по CPU/RAM. |
| **CC / rate limiting** | Ограничение частоты запросов (антифлуд, брутфорс). |
| **Anti-Bot / Challenge** | Капча / слайдер / проверка «ты человек?». |
| **Dynamic Protection** | Шифрование HTML/JS на лету, чтобы ломать готовые бот-скрипты. Включать точечно: ломает часть легитимных клиентов и интеграций. |
| **X-Forwarded-For (XFF)** | Заголовок со «цепочкой» IP клиента, если перед WAF ещё есть балансировщик/CDN. Без правильной настройки WAF видит IP балансировщика, а не атакующего. |
| **PROXY Protocol** | Бинарный префикс от балансировщика с реальным IP клиента. SafeLine умеет его читать (добавлено в линейке 8.x). Нужен, когда HTTP-заголовкам нельзя верить. |
| **Personal / Lite / Pro** | Редакции. Personal — бывшая Community (бесплатная). Lite — платная «домашняя». **Pro** — платная, в ней HA-синхронизация, syslog атак, режимы производительности детектора и ряд других функций. |
| **License server** | Облачный сервер лицензий вендора. Для ключа Pro официально нужна **постоянная** связь с ним. |
| **Host network** | Режим Docker, когда контейнер использует сетевой стек **хоста**, а не изолированный bridge. У `safeline-tengine` именно так: он слушает порты машины напрямую. |
| **Ingress** | Вход HTTP в Kubernetes. SafeLine — **не** Ingress-контроллер; это отдельный reverse proxy перед (или вместо) Ingress. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. Для WAF «данные» — это в первую очередь **конфиг правил** и **логи атак**, не клиентская база. |

## Основные элементы системы и зависимости

### Что входит в один экземпляр SafeLine 9.4.0

Официальный способ поставки — **Docker Compose** на Linux. Один «инстанс» = пачка контейнеров на **одной** машине (публичный `compose.yaml` репозитория):

| Контейнер | Зачем |
|---|---|
| `safeline-pg` | PostgreSQL (в compose на GitHub образ помечен как 15.2; в changelog **9.3.11** отдельно указан апгрейд бандла PostgreSQL **15.2 → 15.18** — брать compose **того релиза**, который ставите, не смешивать). Хранит конфиг, логи, статистику **этого** узла. |
| `safeline-mgt` | Консоль и API. Публикует порт `MGT_PORT` (дефолт 9443) → внутри 1443. Ходит в Postgres по URI с `sslmode=disable`. |
| `safeline-detector` | Детекция атак. Tengine шлёт сюда трафик на `:8000`. |
| `safeline-tengine` | Приём HTTP(S). **`network_mode: host`**. |
| `safeline-luigi` | Обработка логов (контейнер `mario` с 6.10.2 **удалён**, его роль переехала). |
| `safeline-fvm` | Служебный компонент (в compose есть; отдельного описания роли в публичных docs нет — не выдумываем). |
| `safeline-chaos` | Челенджи / динамическая защита (капча и связанная логика). |

ZooKeeper, отдельный Redis, внешний Postgres **в штатной схеме не требуются**. Kafka к SafeLine не подключается.

### Чего в SafeLine нет (частая путаница)

| Нужно системе | Это не SafeLine | Зачем помнить |
|---|---|---|
| Кластер «как у Kafka»: одна БД, реплики партиций, quorum | Нет. Каждый узел — **полный** стек со **своим** Postgres | «Три пода WAF в Deployment» официально не являются кластером |
| Официальный оператор Kubernetes | Нет. Docs описывают Linux + Docker 20.10.14+ и Compose 2.0+ | K8s у вас есть, но SafeLine в него **не встроен** |
| Защита Kafka / Postgres / gRPC Camunda | Нет. Это HTTP reverse proxy | Внутренняя шина событий WAF не видит |
| Исходящие вызовы **от вас к госслужбам** | Обычно нет | WAF стоит на **входе** к вашим HTTP-сервисам, не на исходящих SOAP/REST-клиентах интеграционного API |
| ГОСТ TLS / СКЗИ | Не заявлено | Если требование ИБ — отдельный контур |
| Общий диск логов на 3 ЦОДа | Не входит | Логи живут в локальном Postgres узла; централизация — syslog (Pro) или внешний сборщик |

Сторонний Helm-чарт (`yaencn/safeline-lts-helmchart`) **существует**, но это не основной путь из Install Guide. В README чарта прямо: **у каждого Deployment может быть только 1 replica**; несколько replica «ломают WAF неизвестным образом». LTS-ветка чарта к тому же завязана на LTS SafeLine, а **LTS вендор перестал сопровождать с 9.1.0-LTS (14 августа 2025)**.

### Зависимости окружения (обязательны)

Из официального Install Guide:

- **ОС:** Linux. **macOS/Windows не поддерживаются** ни в одной редакции (FAQ).
- **Архитектура:** x86_64 или arm64. **ARM работает только с лицензией Pro**; Personal на ARM не поддерживается.
- **CPU:** нужен флаг **SSSE3** (проверить `lscpu \| grep ssse3`).
- **Docker ≥ 20.10.14**, **Compose v2 ≥ 2.0.0**.
- **Минимум для запуска:** 1 CPU / 1 ГБ RAM / 5 ГБ диск — это «чтобы контейнеры встали», не прод.
- **Диск инстанса:** конфиг и данные пишутся в `SAFELINE_DIR` (часто `/data/safeline`).
- **Лицензия Pro (для HA и части ИБ-функций):** исходящий доступ контейнера `safeline-mgt` к `safeline.stream.safepoint.cloud:50052`. Официально: ключ требует **стабильного постоянного** соединения с license server.

Ориентиры железа **для одного узла** (FAQ, «recommended configuration», с оговоркой вендора «только справка, тестируйте своё»):

| QPS бизнеса | CPU / RAM (не меньше) |
|---|---|
| &lt; 100 | 2 ядра / 4 ГБ |
| 100–1000 | 4 ядра / 8 ГБ |
| &gt; 1000 | 8 ядер / 16 ГБ |

Цифр «на терабайты озера данных» здесь нет: WAF масштабируется от **HTTP QPS**, не от объёма Kafka/БД.

### Как SafeLine стыкуется с вашей архитектурой

```
Клиенты, браузеры, партнёры, часть входящих HTTP к вам
        │
   внешний балансировщик / DNS   ← не входит в SafeLine
        │
   SafeLine WAF                  ← этот документ
        │  только «чистый» HTTP(S)
        ▼
Integration API, порталы, Ingress, HTTP-микросервисы
        │
   Kafka, Camunda, озеро эталонных данных
```

Правильное место WAF — **периметр HTTP**. Он не заменяет:

- NetworkPolicy / firewall между микросервисами;
- SASL/TLS Kafka;
- авторизацию Camunda и API;
- защиту исходящих интеграций (там нужны mTLS, белые списки, отдельный egress-прокси — другое ПО).

Если повесить SafeLine **за** Ingress без XFF/PROXY Protocol, в логах атак будет IP Ingress, чёрные списки и geo-правила станут бессмысленны.

## Краткие вводные

### Зачем вам WAF в этой архитектуре

Интеграционное API «закрывает собой внешний мир» для **исходящих** опросов ведомств. Снаружи на вас всё равно смотрят:

- сам HTTP API (если он торчит наружу — а 30+ интеграций часто означают и **входящие** колбэки);
- любые веб-консоли (Camunda, админки, портал);
- ошибочно опубликованные сервисы.

WAF — слой «не пустить типичный веб-эксплойт и бота до приложения». Он **не** делает Integration API умнее и **не** нормализует ответы госслужб.

### Как устроена отказоустойчивость (идея, не магия)

SafeLine **не выбирает лидера трафика**. Один Compose-узел упал — этот узел не принимает HTTP.

HA в продукте (с 7.0.0, **Pro**) — это:

1. Несколько **независимых** полных инстансов (у каждого свой диск, свой Postgres, свой Tengine).
2. **Config Auto Sync**: правила живут на master и копируются на slave.
3. **Снаружи** — балансировщик (или DNS), который перестаёт слать трафик на мёртвый узел.

Пока slave уже получил конфиг, падение **master** само по себе не обязано ронять трафик: slave продолжает проксировать. Но **менять правила** вы сможете, только пока жив (и доступен) master — штатной процедуры «выбрать нового master при смерти ЦОДа» в английской документации **нет**.

Синхронизация конфигурации ≠ репликация логов. В changelog 9.4.0 отдельно добавили синхронизацию **forwarding rules**; это намекает, что состав синхронизируемого набора historically неполный. Централизовать логи атак нужно внешне (Pro syslog / SIEM).

### Как устроено масштабирование

Два независимых рычага:

1. **Вертикально** — больше CPU/RAM на узле; в Pro есть «Detection Engine Performance Configuration» (режимы под мощность машины). Personal в материалах вендора описывается как более слабый по утилизации CPU (формулировки вроде «extreme performance» — маркетинговые; опирайтесь на замер QPS).
2. **Горизонтально** — ещё узлы за балансировщиком. Это умножает ёмкость **и** даёт HA. Каждый узел — своя лицензия Pro.

Добавление replica пода в Kubernetes **не** является горизонтальным масштабированием SafeLine (см. Helm warning и host-сеть Tengine).

Апгрейд официально **рестартует сервис и кратко рвёт трафик**. В проде катить по узлам: снять узел с LB → обновить → вернуть. Катить все три ЦОДа сразу = простой периметра.

### Консоль — отдельная поверхность атаки

Порт 9443 — это админка WAF. Если её выставить в интернет, атакуют не сайт, а **щит**. Сброс пароля: `docker exec safeline-mgt resetadmin`. Postgres-пароль в `.env`. Внутри стека Postgres без TLS (`sslmode=disable`) — приемлемо только пока 5432 **не** торчит с хоста.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём SafeLine 9.4.0 международной линейки** (`IMAGE_PREFIX=chaitin`, `REGION=-g`), не китайский зеркальный инсталлятор `waf-ce.chaitin.cn` и не LTS. Вендор прямо предупреждает: континентальный Китай и international-образы по-разному ходят в облако.
2. **Для прода нужна редакция Pro.** Personal не даёт официальный HA Config Auto Sync (changelog 7.0.0: «SafeLine Pro allows HA synchronization…»). Без Pro остаются либо один узел, либо несколько узлов с **ручным** копированием конфига (дрейф правил = дыры).
3. **Официальный runtime прода — Linux VM (или bare metal) + Docker Compose**, а не native Kubernetes Deployment. Kubernetes у вас остаётся для приложений; WAF стоит на выделенных нодах/VM на краю. Community Helm — запасной путь с ограничением 1 replica и без вендорской гарантии.
4. **Три ЦОДа = три независимых домена отказа.** На каждый живой ЦОД — минимум один полный инстанс SafeLine. Stretch «один Postgres WAF на три ЦОДа» **не поддерживается** продуктом.
5. **Перед фермой WAF есть (или будет) внешний балансировщик** L4/L7, умеющий health check и снятие мёртвого бэкенда. SafeLine сам себе failover трафика не делает. В FAQ служебные порты: **65508** health check (не меняется), **65443** custom page (не меняется), **9443** консоль (меняется).
6. **Нагрузки HTTP нет** — поэтому нет числа узлов «хватит для прода». Есть минимум для отказа площадки (по узлу на ЦОД) и правило роста: узлы + CPU по факту QPS.
7. **Исходящий интернет с WAF-узлов до license server допустим** (хотя бы до `safeline.stream.safepoint.cloud:50052`). Если контур КИИ/закрытая сеть **запрещает** это — Pro-лицензия в документированном виде **не работает**; нужен ответ вендора про offline/air-gap, которого в Install Guide нет.
8. **Формального SLA нет.** Схема «3 узла + LB» переживает отказ 1 ЦОДа **по трафику**, если LB и DNS это умеют. Это не юридический 24/7.
9. **WAF защищает входящий HTTP периметра**, не Kafka и не исходящие адаптеры к ведомствам.
10. **Корпоративный PKI есть или будет** для сертификатов сайтов на Tengine (в консоли SSL Cert). Самоподписанный сертификат консоли 9443 для прода недостаточен, если к админке ходят по FQDN.
11. **Тестовый стенд** можно поднять на Personal (x86) в изолированной сети. Прод-конфиг HA/лицензий на тест один в один не копируем, но список Applications и политику «что блокируем» лучше отладить до прода.
12. **Camunda, озеро, Kafka — не часть этого ПО.** Им WAF нужен только если у них есть HTTP, торчащий наружу.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** закупки лицензий и «постановки в прод». Иначе архитектура разъедется.

| Пробел | Почему это ломает решение |
|---|---|
| **Можно ли с WAF-машин ходить в интернет на license server** | Официально ключ Pro требует постоянной связи. IP WAF сменился — сервер лицензий **сам** рвёт сессию. При обрыве вендор пишет, что прокси/детекция/paid features **пока** живут, но это не замена нормальной лицензии и не гарантирует бесконечный offline. Для гос.контура это может быть стоп-фактор на сам продукт. |
| **Какой HTTP реально торчит наружу** (только Integration API? портал? webhooks ведомств? консоли?) | Без карты входящих URL нельзя сказать ни список Applications, ни не сломает ли Anti-Bot машинные интеграции. |
| **Профиль HTTP-нагрузки** (QPS, пик, размер тела, доля TLS, websocket) | FAQ даёт железо «от QPS», у вас QPS нет. «Готовы к высокой нагрузке» без замера — пустая фраза. |
| **Топология Kubernetes и где живёт Ingress** | От этого зависит: WAF перед Ingress, вместо Ingress, или только для выбранных Service. Неправильный слой ломает реальный IP и health checks. |
| **Есть ли уже городской LB / Anycast / DNS failover между 3 ЦОДами** | Без этого три узла WAF — три острова. SafeLine их не склеит. |
| **Требования ИБ: ГОСТ, 152-ФЗ, запрет передачи телеметрии в КНР/облако вендора, контур КИИ** | Вендор — Chaitin (КНР), license/cloud — `safepoint.cloud`. Есть переключатель `Opt in to User Experience Program`. Это отдельное решение ИБ, не «галочка в compose». |
| **Нужен ли air-gap** | Официальный инсталлятор — `curl … manager.sh`. Образы с Docker Hub. Закрытый контур требует зеркала образов **и** ответа по лицензии. |
| **RTT между ЦОДами** | На **проверку запроса** RTT между ЦОДами почти не влияет (проверка локальная). Он влияет на: синхронизацию конфига master→slave, доступ админов к master, и на то, можно ли ставить **один** LB на три ЦОДа. Пока RTT неизвестен — не кладите master «далеко», если консоль должна открываться быстро; для трафика важнее, чтобы клиент попадал в **ближайший живой** узел. |
| **Как повышать slave до master, если умер ЦОД с master** | В публичных EN docs процедуры нет. Без ответа вендора у вас HA трафика, но **SPOF на изменение политики**. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать версию **9.4.0** (`IMAGE_TAG=9.4.0`, не `latest` на проде).
2. Linux x86_64 (если ARM — сразу Pro), SSSE3, Docker/Compose нужных версий.
3. Каталог данных, сильный `POSTGRES_PASSWORD`, уникальный `SUBNET_PREFIX`, если на хосте уже есть Docker-сети.
4. Поднять стек, сменить пароль админа (`resetadmin` — только чтобы **узнать** стартовый, потом сменить и хранить вне Git).
5. **Не** публиковать 9443 и 5432 в интернет.
6. Описать Applications: домен, listen-порт, upstream, TLS.
7. Настроить реальный IP (сокет / заголовок / PROXY Protocol) **до** включения IP-банов.
8. Политика: детектор → allow/deny → rate limit → bot. Сначала observe/логи, потом жёсткий block на боевых интеграциях.
9. Мониторинг: контейнеры, диск `SAFELINE_DIR`, QPS, 5xx «от SafeLine vs от origin» (в Pro это различают), health 65508, синхронизация (если Pro).

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** понять модель reverse proxy, набрать список Applications, проверить, что машинные клиенты (Integration API, health checks ведомств) не ломаются об Anti-Bot и Dynamic Protection. **Не** цель: доказать отказ ЦОДа и ёмкость прода.

#### Топология

Одна VM (2 CPU / 4 ГБ хватит по FAQ для QPS &lt; 100), Docker Compose, Personal на x86 допустим:

- `IMAGE_TAG=9.4.0`
- консоль 9443 только из VPN/jump-хоста
- Tengine слушает 80/443 **хоста** — не ставьте на ту же VM Ingress, который тоже хочет 80/443
- один Application на тестовый HTTP-сервис
- PLAINTEXT до upstream, если стенд изолирован
- без Config Auto Sync

Community Helm в dev-namespace с **1 replica** возможен как эксперимент «впихнуть в K8s», но это уже не официальный путь; не используйте этот YAML как прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Один узел | да | Некому синхронизироваться |
| Personal | да, x86 | HA всё равно нет |
| Балансировщик | не нужен | Один IP |
| Жёсткий block на все правила | нет, сначала лог | Иначе отладите «WAF виноват» две недели |
| Мониторинг | контейнер жив + диск | Нет нагрузки |

#### Чего на тесте **не** стоит упрощать

- Сразу учить приложения ходить **на домен WAF**, не в обход.
- Зафиксировать, как передаётся client IP (пригодится, когда появится LB).
- Не включать Dynamic Protection и Challenge на URL, которые дергают роботы интеграций — это прод-грабли, их надо увидеть на тесте.
- Версию клиента/браузера и HTTP/2 vs 1.1 на тех же путях, что в бою.

#### Сильные стороны такой схемы

- Поднимается за часы официальным `manager.sh` или ручным compose.
- Дешёвая, совпадает с Install Guide.
- Достаточна, чтобы понять, подходит ли продукт интеграционному HTTP вообще.

#### Слабые стороны (обязательно понимать)

- Падение VM = нет WAF и, если DNS указывает только сюда, нет входа на приложения.
- Стенд **не** ловит: рассинхрон master/slave, рестарт при апгрейде, CPU детектора на пике, XFF за городским LB.
- Успешный тест на одном Compose **не** является доказательством готовности трёх ЦОДов.

Практическая рекомендация: препрод = **минимум 2 узла Pro + простой LB**, даже без боевого QPS. Иначе первый сюрприз — «правила на одном ЦОДе другие».

### Прод: 3 ЦОДа, нагрузка

Ниже — правила, которые делают периметр пригодным к отказу площадки, росту и закрытому доступу. Числа узлов «под высокую нагрузку» **не** ставятся: QPS нет.

#### Шаг 0. Выбор макроархитектуры (сделать до установки)

**Вариант A — целевой: 3 независимых инстанса (по одному в ЦОД) + внешний LB + Pro Config Auto Sync.**

```
             клиенты
                │
     LB / DNS (город, 3 бэкенда)
        ┌───────┼───────┐
        ▼       ▼       ▼
     SL-ЦОД1  SL-ЦОД2  SL-ЦОД3     каждый = полный Compose
        │       │       │
        └───────┴───────┘
                │
         ваши HTTP upstream
         (часто — Ingress каждого ЦОДа)
```

- Master — **один**, лучше в ЦОДе, где сидит эксплуатация.
- Slave — остальные; конфиг только с master.
- Трафик — active-active на все здоровые узлы **или** active-passive, если боитесь, что детектор/challenge с липкой сессией плохо переживает балансировку. Sticky session может понадобиться для challenge/auth; это нужно **проверить**, в docs нет жёсткого «всегда sticky».
- Падение 1 ЦОДа: LB вычёркивает бэкенд; два оставшихся продолжают, если на них уже есть синхронизированный конфиг.

**Вариант B — три изолированных WAF без sync (только Personal/ручной YAML).**  
Допустим как временный костыль. Слабое место: через месяц правила разъедутся, «в одном ЦОДе блокируем, в другом нет».

**Вариант C — один WAF на всю систему.**  
Не удовлетворяет «3 ЦОДа» и отказу площадки. Для прода не рассматривать.

**Вариант D — «нативные реплики в Kubernetes».**  
Официально не описан; community Helm запрещает replicas &gt; 1. **Не** целевой.

Пока нет городского LB и решения по лицензионному интернету — нельзя честно включить A в план закупки «просто три VM». Дальнейший текст описывает **вариант A**.

##### Сильные / слабые стороны варианта A

| Сильное | Слабое |
|---|---|
| Переживает отказ 1 ЦОДа по HTTP, если LB живой | Зависит от внешнего LB/DNS — это другое ПО и другой SPOF |
| Масштаб = добавить узел в ЦОД и в пул LB | Каждый узел = лицензия Pro + диск + сопровождение |
| Конфиг правится в одном месте | Master — SPOF на **изменение** политики; процедура failover master в EN docs отсутствует |
| Совпадает с заявленной вендором моделью HA | Синхронизация не заменяет SIEM; логи локальные |
| Апгрейд можно катить по одному ЦОДу | Рестарт узла = краткий вычет ёмкости; без LB drain будет обрыв сессий |

#### Узлы, диск, сеть

**Минимум HA:** 3 узла, по одному в ЦОД. Это минимум **размещения**, не ёмкость.

Дальше рост:

- не хватает CPU детектора на пике → сначала вертикаль (и режим производительности в Pro), потом **ещё узел в том же ЦОДе** в пул LB;
- добавлять узлы лучше **равномерно по ЦОДам**, иначе «весь запас» окажется в одном зале.

На каждом узле:

- выделенная VM; FAQ прямо не рекомендует соседство с бизнесом на одной машине (можно, но нагрузка выше);
- локальный диск под `SAFELINE_DIR` (логи атак раздувают Postgres; политика Clean Data в консоли — обязательна, иначе диск кончится независимо от «терабайт озера»);
- **не NFS как data dir** — этого вендор не описывает; Stateful-паттерн здесь «диск этой VM»;
- Tengine в host-сети: на хосте свободны 80/443 (или те порты, что пропишете в Applications), плюс 65508 и 65443;
- исходящий 50052 до license server; входящий 9443 — только jump/VPN;
- NTP: у Personal для TOTP админки время критично (FAQ); на всех узлах всё равно лучше один NTP.

Связь master↔slave: нужна IP-связность **между WAF-узлами** (внутренний адрес, не публичный — так советуют даже маркетинговые гайды вендорского сообщества). RTT внутри города обычно достаточен для копирования конфига; это не путь `acks=all` Kafka. Если межЦОДовая сеть периодически «отваливается», slave отстанет **правилами**, продолжая пускать трафик по **старой** политике — это тихий риск.

Upstream лучше указывать **локальный** (Ingress/сервис **этого** ЦОДа), а не тащить HTTP через город на чужой ЦОД: иначе при живом WAF и мёртвом «чужом» приложении вы получите лишнюю зависимость.

#### Обязательные настройки «долговечности» периметра

| Настройка | Прод-значение | Зачем |
|---|---|---|
| Версия | pinned `9.4.0`, одинаковая **включая patch** на всех узлах | Sync и лицензии требуют согласованности; это повторяют все описания master-slave |
| Редакция | Pro на **каждом** узле, отдельный ключ | HA-функция платная; один ключ на три машины в docs не обещан |
| Config Auto Sync | 1 master, остальные slave | Иначе три политики |
| Health check LB | на живой HTTP/служебный порт, снять узел при рестарте | Иначе трафик в мёртвый Tengine |
| Апгрейд | по одному узлу, в окно, с бэкапом каталога (официально апгрейд **необратимо** мигрирует данные) | Документация: backup = `docker compose down` + `cp -r` каталога |
| `IMAGE_TAG` | не `latest` | Иначе ЦОДы сами разъедутся по версиям |
| Clean Data | политика хранения логов | Диск и Postgres |

Прогон «ЦОД недоступен»: выключить VM WAF в одном зале, убедиться что:

- LB перестал слать туда клиентов;
- два других узла пускают и **блокируют** тест-атаку одинаково;
- консоль master (если он не в этом зале) жива; если выключили зал master — зафиксировать, **можете ли вы вообще менять правила**.

Без этого прогона у вас нет отказоустойчивости, есть надежда.

#### Масштабирование под нагрузку (когда цифры появятся)

Порядок, а не гадание:

1. Замерить входящий HTTP QPS (пик и плато), долю TLS, размер тела, websocket.
2. Снять CPU `detector` и `tengine` на одном узле в режиме, близком к боевым правилам (пустой WAF врёт).
3. Сверить с таблицей FAQ как **стартовой** оценкой железа, не как гарантией.
4. Включить нужный режим производительности детектора (Pro).
5. Если один узел не держит пик — добавить узлы в пул, не «replicas: 3» в одном Deployment.
6. Следить за диском логов отдельно от CPU.

«Терабайты» озера данных на размер WAF почти не влияют. На размер WAF влияют **access/attack logs**, если их копить месяцами на узле.

#### Безопасность прода (без этого периметр не считается настроенным)

Слои:

1. **Сеть**
   - Tengine: только 80/443 (и нужные listen Applications) с LB/интернета.
   - Консоль 9443: не из интернета; лучше отдельный listener/VPN.
   - Postgres: не публиковать. Внутри compose уже `sslmode=disable` — не расширяйте эту сеть.
   - License: явный egress **только** на нужный хост:порт, не «весь интернет с WAF».
   - Между ЦОДами: sync и админка по внутренней сети.

2. **Идентификация в консоли**
   - Стартовый `admin` + пароль из `resetadmin` сменить.
   - С 9.3.10 есть **read-only** роль — для аудиторов, не для всех `admin`.
   - Не держать консоль на самоподписанном сертификате, если до неё ходят люди (ошибки «кликните Continue» = привычка игнорировать TLS).

3. **TLS на сайтах**
   - Сертификаты приложений в SSL Cert консоли; протокол SSL в UI = TLS.
   - Кастомные cipher — возможность Pro (changelog 6.9.0). Если нужен ГОСТ — vanilla SafeLine это не закрывает.

4. **Правила так, чтобы не убить интеграции**
   - Allowlist служебных IP ведомств **до** жёсткого bot/challenge на тех же URL.
   - Dynamic Protection на JSON API почти наверняка сломает клиентов — включать только на человеческих HTML-страницах.
   - Режим «сначала детектировать и логировать, потом deny» для новых правил.

5. **Реальный IP**
   - За LB: настроить `Get Attack IP From` / PROXY Protocol.
   - Upstream должен получать XFF, если приложениям это нужно (FAQ: SafeLine сам кладёт источник в X-Forwarded-For). Не делать `set_real_ip_from 0.0.0.0/0` на приложении слепо — это уже их конфиг; доверять XFF только от IP WAF.

6. **Секреты и поставка**
   - `.env` не в Git.
   - Прод: не `curl | bash` с сайта вендора в обход зеркала; образы — из вашего registry, digest pinned.
   - Бэкап каталога = бэкап правил и логов узла; шифровать том.

7. **Наблюдаемость ИБ**
   - Pro syslog атак в SIEM (официально с линейки, где это добавили для Professional).
   - Personal в FAQ предлагает fluentd, читающий таблицу Postgres — для прода это костыль, но показывает: логи **в БД узла**.
   - Алертинг (Pro Attack Alert) — не замена SIEM.

8. **Лицензия как зависимость безопасности**
   - Потеря связи с облаком не должна быть сюрпризом: мониторить коннект к `:50052`.
   - Смена IP узла — процедура с риском отвала ключа (официальный License Disconnection).

##### Сильные / слабые стороны выбранной ИБ-схемы

| Сильное | Слабое |
|---|---|
| Reverse proxy закрывает прямой доступ к origin, если DNS/сеть это гарантируют | Один неправильный Application или «обходной» Ingress = WAF в стороне |
| Семантика + rate limit + bot — штатный набор продукта | Ложные срабатывания на интеграциях; нужны allowlist и этап логов |
| Консоль и дата-плоскость разделены портом | 9443 часто забывают, Tengine в host-сети расширяет поверхность хоста |
| Pro sync снижает дрейф политик | Политика и лицензия завязаны на облако вендора |
| Не надо кластеризовать Postgres WAF | Нет at-rest encryption «из коробки»; шифруйте диск сами |

#### Kubernetes-специфика (как жить с фактом «у нас K8s»)

Честная схема:

- Кластер(а) K8s — приложения, Kafka (если решите), Camunda, Integration API.
- SafeLine — **рядом**, на dedicated VM или на worker'ах, где вы сознательно ставите Docker Compose и **не** отдаёте 80/443 Ingress-контроллеру.
- Upstream = внутренние LB/Ingress IP **этого** ЦОДа.
- NetworkPolicy в K8s: origin принимает HTTP **только** с IP WAF-узлов (иначе WAF можно обойти).

Если очень нужно «всё в K8s»: один Helm-release **на узел/ЦОД**, `replicas: 1`, hostNetwork/осторожность с портами, отдельный PVC, **не** HPA. Это хуже официального Compose и всё равно требует внешнего LB и Pro sync. Не продавать руководству как «облачный автоскейл WAF».

#### Порядок вывода в прод (этапы, не команда за командой)

1. Закрыть таблицу пробелов: интернет до лицензий, карта входящего HTTP, есть ли городской LB, ИБ по вендору из КНР.
2. Замерить или хотя бы оценить QPS; выбрать размер VM по FAQ как старт.
3. Поднять **один** узел 9.4.0 Pro на препроде, описать Applications, проверить интеграции без challenge.
4. Настроить реальный IP за тестовым LB.
5. Поднять второй узел, включить Config Auto Sync, убедиться что сайт и правила появились на slave (в т.ч. forwarding rules — это чинили/добавляли вплоть до 9.4.0).
6. Повесить LB на оба, убить один узел, проверить трафик и блокировку тест-атаки.
7. Третий ЦОД — тот же шаблон.
8. Только потом — боевые DNS.
9. Нагрузить синтетикой с **включёнными** правилами. По результату — CPU и число узлов.
10. Прогон «ЦОД master недоступен»: что с трафиком **и** что с возможностью менять правила.
11. Катить апгрейды только rolling + бэкап каталога; помнить миграцию конфигов при прыжке через старые мажоры (для 9.4.0 смотреть changelog, особенно порог 9.2.7).

Без пунктов 6 и 10 у вас нет отказоустойчивости.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | 3 полных узла Compose; Pro Config Auto Sync; внешний LB с health check; переживает 1 ЦОД **по трафику**; master не в единственном экземпляре «на бумаге», пока нет процедуры его замены |
| Производительность / масштаб | Не требуется | Железо от QPS (таблица FAQ + свой замер); горизонталь = новые узлы, не replicas Deployment; режим производительности Pro; диск под логи |
| Безопасность | Консоль не в интернет; тестовые правила | TLS сайтов; 9443 закрыт; Postgres не опубликован; реальный IP; least privilege в консоли; pin версии; egress только на license host; логи в SIEM; origin не доступен в обход WAF |

**Не готов к проду**, если: один Compose на три ЦОДа, Personal как «кластер», `replicas: 3` в Kubernetes, `IMAGE_TAG=latest`, консоль 9443 с мира, нет LB, license server заблокирован файрволом «по политике» без альтернативы от вендора, Dynamic Protection на machine-to-machine API, origin всё ещё публикуется напрямую, RTO/RPO и прогон отказа ЦОДа не делались.
