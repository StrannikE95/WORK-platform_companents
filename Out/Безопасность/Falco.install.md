# Falco 0.44.1 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Falco.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Falco — агент на Linux-ноде: читает системные вызовы и пишет тревогу. Сам атаку не останавливает. Ставите **свою** копию open-source, не коммерческий «совместимый» агент.

Версия в этой инструкции: **0.44.1**. Образ: `falcosecurity/falco:0.44.1`.  
На Kubernetes **1.29+**: **Falco Operator v0.4.1**, Helm-чарт **`falcosecurity/falco-operator` 0.3.0**. Альтернатива: Helm **`falcosecurity/falco` 9.1.0** (тоже 0.44.1) — если кластер старше 1.29.  
Документация: https://falco.org/docs/

Растягивать «кластер Falco» между дата-центрами **нечего**: это не Raft и не общая база. Два или три независимых Kubernetes = Falco **в каждом**. Глобального агента «на страну» нет. Сводить нужно **алерты** (SIEM / NATS через Falcosidekick), не процессы на нодах. Сам Falco 0.44 шлёт stdout/файл/syslog/HTTP; встроенного NATS/Kafka-продюсера нет (gRPC-выход в 0.44 удалён).

---

## О чём эта инструкция молча договорилась

1. **По контуру Falco на Kubernetes-кластер.** Два зала = две установки. Три = три. Общего кворума нет.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`, если есть). Если там 1.36 — Operator v0.4.1 допустим (≥ 1.29).
3. Драйвер боя — **`modern_ebpf`**. Ядра с BTF и ring buffer (обычно Linux ≥ 5.8). Модуль ядра — только пул, где eBPF физически не встаёт (полные привилегии).
4. Учебный стенд — закрытая сеть; HTTP до Sidekick на тесте допустим.
5. Цифр нагрузки нет — нет millicores «хватит агенту на брокер». Есть счётчики дропов и рычаги буферов/правил.
6. Приёмник алертов **будет**: SIEM (Wazuh) и/или NATS через Falcosidekick. UI Sidekick **не** замена SIEM.
7. Автоответ «убить под» (Talon) в этом файле **не включается**.
8. Из развилки «один Kubernetes на три зоны vs три кластера» здесь берём **контур на каждый кластер** (как независимые Kubernetes). Вариант «один DaemonSet на три зала одного кластера» имел бы смысл только при одном Kubernetes на три площадки — его эта инструкция не предполагает.

---

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** увидеть алерт штатных правил на ваших образах, отладить доставку. **Не зачем:** доказать детект на Kafka-ноде под нагрузкой.

### Что должно быть до установки

- Учебный Kubernetes, Linux-ноды (Windows Falco не покрывает).
- BTF/ringbuf на ядре стенда — иначе modern eBPF не встанет, и вы отладите не тот драйвер.
- Registry до образа **0.44.1** и OCI-правил (или зеркало).

Deployment с `replicas: 2` для съёма вызовов ядра **не использовать**.

### Установка (Operator — основной путь при Kubernetes ≥ 1.29)

```bash
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm repo update
kubectl create namespace falco
helm install falco-operator falcosecurity/falco-operator \
  --version 0.3.0 -n falco
```

Затем объект Falco: DaemonSet, **`engine.kind: modern_ebpf`**, плагин контейнера, официальный набор правил. Образ агента явно **0.44.1**, не `latest`. На тесте тег ruleset можно ослабить; в бой — pin.

Альтернатива без оператора:

```bash
helm install falco falcosecurity/falco --version 9.1.0 -n falco \
  --set image.tag=0.44.1
```

Сверять values чарта 9.1.0: драйвер modern eBPF, режим daemonset, не Deployment.

Quickstart-манифест оператора поднимает Falco + Sidekick + UI + Redis + сборщик метаданных. Для знакомства удобно. **Это не бой** (HTTP, `latest`, UI).

Опционально на тесте: Falcosidekick **1** реплика, HTTP только в закрытой сети. Хотя бы один выход кроме просмотра логов пода.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| TLS до Sidekick | нет, если сеть закрыта | Иначе PKI раньше правил |
| Реплики Sidekick | 1 | Нет требования пережить выкат |
| Свои исключения | минимум | Сначала увидеть шум Java/Kafka |
| Лимит CPU | мягкий / без жёсткого throttle | Не получить дропы из cgroup |
| Control-plane | можно не сразу | На тесте часто одна нода |

Чего **не** упрощаем: драйвер **`modern_ebpf`**; метрики дропов включены (счётчики ядра, действия при дропах: журнал + алерт, не ignore); плагин контейнера **до** набора правил (иначе поля контейнера мертвы); версия **0.44.1**.

### Как понять, что стенд живой

1. Поды DaemonSet Running, драйвер modern eBPF, версия **0.44.1**.
2. `kubectl exec` в тестовый под с `sh` → ожидаемый алерт дошёл до stdout **и** до Sidekick/лога.
3. Рестарт пода Falco: нода слепая, пока не встанет — ожидаемо.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный quickstart оператора | Нет TLS, нет покрытия tainted-нод, нет ёмкости буферов |
| Шум правил на *ваших* образах дёшево | Детект exec на простой ноде ≠ брокер под нагрузкой |
| | UI приучает «смотреть в Falco», а не в SIEM |

Перед боем полезен **препрод**: DaemonSet на все tainted-ноды, TLS, 2 Sidekick, pin 0.44.1, свои исключения — в **одном** дата-центре.

## Бой: контур на каждый кластер, алерты в общий SIEM

**Зачем:** на **каждой** живой Linux-ноде с нагрузкой есть агент; падение дата-центра слепит **только** его ноды; алерты с живых площадок доходят в SIEM/NATS. Цифр событий в секунду нет.

Если бы у вас был **один** Kubernetes на три зоны, хватило бы одного оператора и одного DaemonSet: kubelet сам держит под на каждой ноде каждой зоны, а Sidekick размазать anti-affinity по зонам. Этого Kubernetes здесь нет — поэтому три независимых контура проще и честнее, чем выдуманный общий агент.

### Почему не stretch

Нечего растягивать. Системные вызовы снимаются с **этого** ядра. «Один Falco на три зала» означало бы один Kubernetes. Сводить нужно алерты, не агенты.

Не ставить один Sidekick «в домашнем зале на всех»: смерть этого зала + HTTP с чужих нод через город — лишняя связность. Sidekick **локальный** кластеру; дальше SIEM/NATS, которые умеют принимать с нескольких источников.

Метки кластера / hostname зала в алерте закладывают **до** боя, иначе дежурные увидят три потока без площадки.

### Как расставить

В **каждом** Kubernetes — свой контур:

- Operator + DaemonSet Falco **0.44.1** + Falcosidekick (не меньше 2 реплик в **этом** зале);
- алерты наружу в **общий** SIEM и/или NATS.

| Сколько площадок | Что где | Если умер зал 1 |
|---|---|---|
| **Две** | Falco в обоих кластерах; Sidekick каждого смотрит в общий приёмник | Детект и нагрузка зала 1 мертвы вместе. Зал 2 шлёт алерты как раньше |
| **Три** | Третий такой же контур | То же; третий агент не «выбирает лидера» за мёртвый зал |

Три копии правил легко разъедутся — GitOps один overlay **плюс** идентификатор кластера в алерте. Легче забыть включить Falco в новом кластере: это часть приёмки площадки, не «потом».

### Что должно быть до боевой установки (на каждой площадке)

- Ядро: BTF, ringbuf, JIT. Снять **во всех пулах** до установки.
- CRI-сокеты на ноде для плагина контейнера.
- Зеркало образа **0.44.1** и OCI-артефактов правил.
- PKI: HTTPS Falco → Sidekick с **валидным** сертификатом. Документация: self-signed / invalid для HTTP-выхода **не поддерживаются**.
- Куда слать: Wazuh и/или NATS. URL и токен не класть в git открытым текстом.
- Taints: control-plane, dedicated Kafka, Camunda, интеграция — без tolerations это **слепые** самые важные ноды.

### Порядок установки (повторить в каждом кластере)

1. Снять версии Kubernetes и ядер во всех пулах.
2. Helm **falco-operator 0.3.0** → Operator **v0.4.1**. Deployment оператора **не меньше 2** + PDB. Краткий простой оператора уже запущенный DaemonSet обычно переживает; выкат правил — нет.
3. Объект Falco: только **DaemonSet**, `engine.kind: modern_ebpf`, образ **0.44.1** (userspace 0.44 несовместим с драйвером 0.43).
4. Порядок артефактов (дока оператора): плагин контейнера (pin тега) → плагин метаданных Kubernetes + сборщик → набор правил **зафиксированный** тег → свой overlay исключений под Kafka/JVM/Camunda и отдельные правила высокого приоритета под интеграционный контур (неожиданный исходящий не на список ведомств, shell в образе API, запись в ключи TLS).
5. Не удалять объект Falco раньше правил/плагинов/конфига — finalizer sidecar повиснет.
6. Метрики + действия при дропах: журнал + алерт. Не ignore. Не «завершить процесс» как норма (гарантированная слепота до рестарта).
7. Выходы **до** объявления «мы под мониторингом»:
   - stdout/syslog → сбор логов ноды (переживает смерть Sidekick);
   - HTTP HTTPS → локальный Falcosidekick, JSON включён.
8. Falcosidekick **не меньше 2**, PDB «хотя бы один жив», anti-affinity в **этом** зале. TLS-сервер включён, лучше взаимный TLS. Не LoadBalancer в интернет. Quickstart `http://sidekick:2801` в бой **не** копировать.
9. Маршруты Sidekick: SIEM (Wazuh; это не часть дистрибутива Wazuh) и/или NATS. Опционально отдельный топик Kafka — не бизнес-топики, TLS+ACL. UI наружу не публиковать; если UI нужен — единый вход, не basic из демо.
10. NetworkPolicy: поды Falco только на Sidekick; Sidekick только на SIEM/NATS.
11. GitOps на правила/конфиг. Ревью ClusterRole оператора при апгрейде чарта — не раздувать до cluster-admin сверх того, что ставит чарт.
12. `priorityClassName` высокий: не вытеснять агента как BestEffort. Rolling DaemonSet: `maxUnavailable` низкий (часто 1). Во время выката часть нод слепая.
13. Сборщик метаданных в quickstart — 1 реплика: точка отказа **обогащения**, не съёма. Мониторить.
14. Неделя шума на препроде → исключения → **потом** дежурство. Нагрузить соседством с тестовым Kafka и снять дропы.

Least privilege modern eBPF: `CAP_BPF`, `CAP_PERFMON`, `CAP_SYS_RESOURCE`, `CAP_SYS_PTRACE` (на ядрах без дробных cap — ещё `CAP_SYS_ADMIN`). Не `privileged: true` «на всякий случай». hostPath — минимум: `/proc`, runtime sockets. Read-only корень файловой системы пода — где возможно.

Образы только по digest или неизменяемому тегу 0.44.1.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Режим | DaemonSet на **всех** Linux-нодах с нагрузкой | Deployment не видит чужие ядра |
| Драйвер | modern eBPF | Без сборки модуля; legacy eBPF в 0.44 удалён |
| Правила | pin OCI + overlay | `latest` разъедет 2–3 кластера |
| HTTP | https, валидный сертификат | Self-signed Falco не примет |
| Дропы | журнал+алерт, не ignore | Слепая зона должна быть видна |
| Лимит CPU | не 50m «чтобы не мешал» | Throttle → дропы → ложь |
| Таймаут HTTP-выхода | подобрать замером | Малый — потеря писем; большой — обратное давление на разбор вызовов |

Не монтировать в под больше путей хоста, чем нужно. BPF JIT включён на нодах.

### Как расти, когда появятся цифры нагрузки

Единица масштаба — **нода**. Добавили worker → DaemonSet сам поставил агента. Второй процесс Falco на той же ноде удваивает работу ядра.

1. Смотреть число дропов, частоту событий, CPU пода.
2. Дропы: сначала сузить правила и набор вызовов (официальный рычаг минимума для движка состояния), потом буферы.
3. Troubleshooting modern eBPF (с оговоркой авторов): эксперимент пресет буфера 6–7, несколько CPU на буфер 4–6 на крупных машинах. Больше буфер = больше RAM × число буферов. Не гарантия.
4. Ориентир той же страницы: порядка меньше ~1–1.5 тысячи событий/с на ядро обычно терпимо, больше ~3 тысяч/с часто тяжело — **не** смета вашего кластера.
5. Шумные пулы (Kafka) — отдельные замеры. Документация признаёт: на очень шумных машинах дропы могут быть неустранимы. Тогда не врать SLA.
6. Не второй syscall-агент «для надёжности» на те же точки ядра.

### Проверки, без которых это ещё не бой

На **каждом** кластере:

1. Версия **0.44.1**, modern eBPF, плагин контейнера, DaemonSet на tainted-нодах (Kafka/Camunda тоже).
2. Контролируемый exec / генератор событий → алерт в SIEM **и/или** NATS, не только в логах пода.
3. Метрики дропов живые; ignore нет.
4. HTTPS Sidekick; с мира UI/порт приёма — отказ.
5. Убить один под Sidekick: второй принимает; syslog/stdout всё ещё пишет.

Межзаловый прогон: выключить кластер зала 1 — алерты зала 2 (и зала 3) идут. Нет «переключения Falco».

Учение «зона недоступна»: ноды живых залов всё ещё шлют; Sidekick не единственная точка в мёртвой зоне.

Неделя шума на препроде → исключения → **потом** дежурство. Без этого либо игнор, либо душат легитимный exec.

### Что хорошо и что плохо в схеме «контур на кластер + SIEM/NATS»

| Хорошо | Плохо |
|---|---|
| Детект не зависит от задержки между городами | 2–3 выката правил; легко забыть новый кластер |
| Радиус взрыва = зал: чужие ноды мониторятся как раньше | Без общего SIEM/NATS — три правды |
| Согласовано с независимыми Kubernetes | Sidekick и сеть алертов — отдельный путь отказа |
| modern eBPF без модуля ядра на ядрах ≥ 5.8 | Агент видит всю ноду; компрометация = наблюдаемость |
| Два канала алертов переживают смерть Sidekick | TLS с запретом self-signed требует нормальный PKI |
| | Ошибка в overlay сразу на всех нодах этого кластера |

**Не готово к бою**, если: Deployment вместо DaemonSet для вызовов ядра; поставили только в одном зале; нет плагина контейнера; тег `latest`; открытый HTTP Sidekick на общей сети; нет tolerations на Kafka; дропы в режиме ignore; единственный выход — UI; ждут, что Falco *остановит* атаку; ядро без BTF при modern eBPF «надеемся»; выдумали глобальный кластер Falco вместо SIEM/NATS; учебный quickstart уехал в бой.
