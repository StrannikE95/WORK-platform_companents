# SafeLine WAF 9.4.0 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `SafeLine WAF.md`.  
Словарь: `SafeLine WAF.info.md`. Схема стыковки: `SafeLine WAF.shema.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

**Допущение этой инструкции:** учебный контур — одна Linux-машина в закрытой сети, редакция **Personal**, архитектура **x86_64**. Бой — отдельный раздел в конце, не «чуть подкрученный» стенд.

---

## Что вы ставите

SafeLine — фильтр HTTP/HTTPS перед приложением (обратный прокси). Клиент стучится в SafeLine; тот проверяет запрос и, если он чистый, пересылает его на настоящий сервер (**upstream**). Это **не** Ingress-контроллер Kubernetes и **не** замена NetworkPolicy между микросервисами.

Версия в этой инструкции: **9.4.0** (changelog: 17 августа 2026). Образы: **`chaitin/safeline-*`**, международная линейка **`REGION=-g`**, `IMAGE_PREFIX=chaitin`, `IMAGE_TAG=9.4.0` (не `latest`, не китайский инсталлятор `waf-ce.chaitin.cn`, не LTS — вендор LTS не сопровождает с 9.1.0-LTS).

Официальный путь: **Linux + Docker Compose** (Docker ≥ 20.10.14, Compose v2 ≥ 2.0.0). Документация установки: https://docs.waf.chaitin.com/en/GetStarted/Deploy

**Docker** — программа, которая запускает готовый **образ** (упакованная программа с зависимостями) как **контейнер** (запущенная копия образа). **Docker Compose** — программа, которая по файлу `compose.yaml` поднимает сразу несколько контейнеров как один стек.

Общую базу WAF на несколько дата-центров здесь **не собираем**: у каждого узла **свой** PostgreSQL. Продукт такой схемы не описывает.

## О чём эта инструкция молча договорилась

1. **Один Compose-узел = полный стек внутри одной площадки.** Между залами — не общая БД и не общие сессии.
2. Приложения — в Kubernetes каждого дата-центра (см. `Kubernetes.install.md`, если есть). WAF стоит **рядом**, на выделенной Linux VM (или на worker, где сознательно Compose и **не** Ingress на 80/443).
3. Учебный стенд — закрытая сеть, Personal на **x86_64**. ARM в Personal вендор не поддерживает; ARM = Pro.
4. Цифр HTTP-нагрузки нет — нет числа узлов «хватит для боя». FAQ даёт CPU/RAM от запросов в секунду как справку, не гарантию.
5. Перед фермой в бою есть (или будет) **внешний балансировщик или DNS** с health check. SafeLine сам failover трафика не делает.
6. Два дата-центра: по полному инстансу в каждом, перед Ingress **этого** зала. Три: то же на третьей площадке. Один WAF «на всю систему» отказ зала не переживает.
7. Синхронизация master/slave — **Pro** (с 7.0.0). Personal: ручное копирование, иначе через месяц в одном зале блокируем, в другом нет.
8. Вариант «нативные реплики в Kubernetes» официально не описан; сторонний Helm запрещает replicas больше 1. В бой не берём.

## Куда ставить и сколько ресурсов (учебный контур)

**Куда.** Одна выделенная **Linux-машина x86_64** (виртуальная машина или железо) **рядом** с учебным Kubernetes, не внутри него как Ingress. На этой машине будет Docker Compose. Tengine (форк Nginx, контейнер `safeline-tengine`) работает в **host-сети**: слушает порты **самой машины**, не изолированной сети Docker. Поэтому на этой VM нельзя держать Ingress или другой процесс, которому тоже нужны **80 и 443**.

macOS и Windows вендор **не поддерживает** ни в одной редакции. ARM на учебном Personal **не ставим**.

**Сколько железа.** Вендор разделяет «минимум, чтобы контейнеры встали» и «рекомендация от запросов в секунду». Путать их нельзя.

| Зачем цифра | CPU | RAM | Диск | Откуда |
|---|---|---|---|---|
| Минимум, чтобы процесс поднялся | 1 ядро | 1 ГБ | 5 ГБ | страница Deploy |
| Учебный контур, ориентир «меньше 100 запросов/с» | **2 ядра** | **4 ГБ** | каталог `/data/safeline` на **локальном** диске | FAQ, recommended configuration |
| Бой | не эта таблица | не эта таблица | политика очистки логов | нет вашей нагрузки → нет сметы |

Для учебного контура берите **2 CPU / 4 ГБ / не меньше 5 ГБ свободных** на каталог данных. Это не «хватит для боя» и не гарантия: FAQ прямо пишет, что цифры — справка, тестируйте своё.

**Сильная сторона:** совпадает с официальным Install Guide, поднимается на одной VM.  
**Слабая сторона:** падение этой VM = нет WAF и, если DNS указывает только сюда, нет HTTP-входа. Успех одного Compose **не** доказывает отказ зала и CPU детектора на пике.

**Критично, даже если не спрашивали:** порты **9443** (консоль) и **5432** (Postgres узла) в интернет не публиковать. Каталог данных — локальный диск, не NFS (вендор NFS не описывает). Не ставить `IMAGE_TAG=latest`. Один Compose — не кластер.

Community Helm (`replicas: 1`) — эксперимент «впихнуть в Kubernetes», **не** официальный Install Guide. В учебный контур этой инструкции не входит.

## Установка для новичка

Команды ниже — **на Linux-машине стенда**, не в PowerShell на Windows. Нужны права **root** (так в Install Guide для автоматической установки; ручной путь тоже ставит системный Docker).

Официальная страница шагов: https://docs.waf.chaitin.com/en/GetStarted/Deploy

Вендор рекомендует скрипт `manager.sh`. Скрипт ставит линейку **`latest`**. В этой инструкции фиксируем **9.4.0**, поэтому идём **ручным** путём с того же гайда: каталог → `compose.yaml` → свой `.env` → `docker compose up -d`.

### Что должно быть до установки

Есть:

- Linux x86_64, флаг CPU **SSSE3**.
- Закрытая сеть; вход на машину с jump-хоста или VPN.
- Свободны на хосте порты **80**, **443**, консоль **9443**, служебные **65508** (health check, не меняется) и **65443** (своя страница ошибки, не меняется).
- Не меньше 5 ГБ на каталог данных.

Нет (и не должно появиться на этой VM):

- Ingress или nginx, который тоже хочет 80/443.
- Публикация 9443 и 5432 в интернет.
- ARM без лицензии Pro.
- Файла `.env` в git.

### Этап 1. Проверяем, что машина подходит

**Что делаем:** убеждаемся, что это Linux x86_64 с SSSE3 и хватает места. Без SSSE3 официальный путь не тот.

```bash
uname -m
lscpu | grep ssse3
cat /proc/cpuinfo | grep "processor"
free -h
df -h
```

Успех: `uname -m` печатает `x86_64`; в выводе `lscpu` есть `ssse3`; свободно ≥ 5 ГБ. Команды сверки — с той же страницы Deploy.

### Этап 2. Ставим Docker и Compose, если их ещё нет

**Что делаем:** ставим Docker (программа, которая запускает образы) и плагин Compose v2. Если Docker уже есть — этот шаг пропускаем, только проверяем версии.

```bash
curl -sSL "https://get.docker.com/" | bash
docker version
docker compose version
```

Успех: Docker **≥ 20.10.14**, Compose **≥ 2.0.0** (это `docker compose`, два слова — плагин v2, не старый `docker-compose`). Если видите `Cannot connect to the Docker daemon` — демон не запущен; FAQ предлагает `systemctl restart docker` или проверку, что Docker установлен.

На закрытом контуре `get.docker.com` может быть недоступен — тогда Docker ставят из **вашего** зеркала пакетов. Суть та же: те же минимальные версии.

### Этап 3. Каталог данных

**Что делаем:** создаём каталог, куда SafeLine запишет конфиг, свою PostgreSQL и логи **этого** узла. Вендор по умолчанию использует `/data/safeline`, не меньше 5 ГБ.

```bash
mkdir -p /data/safeline
cd /data/safeline
```

Успех: `pwd` показывает `/data/safeline`. Этот каталог — не NFS.

### Этап 4. Файл Compose того релиза, который ставите

**Что делаем:** скачиваем официальный `compose.yaml` — описание стека контейнеров. Tengine в этом файле с `network_mode: host` (сеть хоста).

```bash
cd /data/safeline
wget "https://waf.chaitin.com/release/latest/compose.yaml"
```

Успех: файл `compose.yaml` лежит в `/data/safeline`. Не смешивайте compose разных тегов: в changelog **9.3.11** бандл Postgres **15.2 → 15.18**. Публичный `compose.yaml` ветки `main` на GitHub может отставать по тегу Postgres — ориентир для имён сервисов и host-сети, не замена файла **того** релиза, который ставите.

### Этап 5. Файл `.env` — версия, порты, пароль базы

**Что делаем:** создаём скрытый файл переменных рядом с `compose.yaml`. Compose подставляет их в имена образов и пароль Postgres. Файл **не** в git: в нём секрет базы.

```bash
cd /data/safeline
touch .env
```

Запишите в `.env` (не копируйте `IMAGE_TAG=latest` из примера вендора):

```bash
SAFELINE_DIR=/data/safeline
IMAGE_TAG=9.4.0
MGT_PORT=9443
POSTGRES_PASSWORD=ЗАМЕНИТЕ_СВОИМ_ПАРОЛЕМ
SUBNET_PREFIX=172.22.222
IMAGE_PREFIX=chaitin
ARCH_SUFFIX=
RELEASE=
REGION=-g
MGT_PROXY=0
```

Что значат строки:

| Переменная | Зачем |
|---|---|
| `SAFELINE_DIR` | Каталог данных на диске |
| `IMAGE_TAG` | Версия образов. Здесь **9.4.0**, не `latest` |
| `MGT_PORT` | Порт консоли на хосте (внутри контейнера 1443) |
| `POSTGRES_PASSWORD` | Пароль встроенной PostgreSQL узла. Свой, длинный |
| `SUBNET_PREFIX` | Префикс внутренней Docker-сети стека. Если на хосте уже есть сеть с тем же адресом — смените (FAQ: ошибка `Pool overlaps`) |
| `IMAGE_PREFIX` | Реестр образов: `chaitin` |
| `ARCH_SUFFIX` | Пусто на x86_64. На ARM было бы `-arm`, но ARM = Pro |
| `RELEASE` | Пусто. Не `-lts` |
| `REGION` | `-g` — международная линейка |
| `MGT_PROXY` | Сколько прокси перед консолью. На стенде **0** |

Успех: `grep IMAGE_TAG /data/safeline/.env` печатает `9.4.0`; `REGION=-g`; пароль не плейсхолдер из примера.

### Этап 6. Поднимаем стек

**Что делаем:** Compose скачивает образы и запускает контейнеры. Может занять несколько минут (так пишет вендор).

```bash
cd /data/safeline
docker compose up -d
```

Успех: команда завершилась без ошибки. Смотрим, что контейнеры живы:

```bash
docker ps
```

Ожидаются в том числе: `safeline-tengine`, `safeline-detector`, `safeline-mgt`, `safeline-pg` (плюс `safeline-luigi`, `safeline-chaos`, `safeline-fvm` в актуальном compose). В колонке образа у сервисов с `IMAGE_TAG` — **9.4.0**, не `latest`.

Если `safeline-tengine` пишет `Address already in use` — занят порт хоста (часто 80/443/9443/65508/65443). Разбирают конфликт, а не «ещё один Ingress рядом». Если `failed to create network safeline-ce` — FAQ: `systemctl restart docker` и повтор.

### Этап 7. Стенд живой — что проверить до браузера

```bash
docker ps
docker logs --tail 50 safeline-mgt
docker logs --tail 50 safeline-tengine
```

Успех: контейнеры `Up` / healthy; в логах нет циклического рестарта. Рестарт VM: пока DNS указывает только сюда, входа нет — на одном узле это **ожидаемо**.

Чего этот стенд **ещё не доказывает:** отказ зала, рассинхрон правил на двух узлах, апгрейд с обрывом трафика, CPU детектора на пике, реальный IP клиента за городским балансировщиком, выборы лидера (их в продукте нет).

## Первый запуск — URL, порт, учётка, смена пароля

**URL и порт.** Консоль: `https://<ip-машины-стенда>:9443/`  
Порт **9443** задаётся `MGT_PORT`. Открывайте **с jump-хоста или VPN**, не выставляйте 9443 в интернет: это админка щита, не сайт. Сертификат консоли самоподписанный: healthcheck в compose идёт через `curl -k`. Браузер покажет предупреждение — на учебном стенде это ожидаемо; в бой самоподписанный 9443 для людей на FQDN — плохая норма.

Страница входа: https://docs.waf.chaitin.com/en/GetStarted/Deploy#use-web-ui

**Учётка.** Стартового пароля «из коробки на экране» нет. Его печатает команда сброса на машине, где крутится стек:

```bash
docker exec safeline-mgt resetadmin
```

Ожидаемый вывод (с https://docs.waf.chaitin.com/en/GetStarted/Deploy#get-administrator-account):

```text
[SafeLine] Initial username：admin
[SafeLine] Initial password：**********
[SafeLine] Done
```

Логин: пользователь **`admin`**, пароль — из этой печати. Вендор пишет: «Please must remember this content».

**Смена пароля.** После входа **сразу смените** пароль администратора в консоли. Учебный пароль из `resetadmin` в бой не копируют. Хранить новый пароль вне git (сейф / Vault), не в чате и не в `.env` рядом с compose в репозитории.

Если забыли пароль — снова `docker exec safeline-mgt resetadmin` (FAQ: Login Issues).

**Personal и TOTP.** В Personal консоль может потребовать одноразовый код (TOTP — пароль, который живёт 30 секунд на телефоне). Часы сервера и телефона должны совпадать (NTP). Если код «не тот»: FAQ — время и часовой пояс; перепривязка: `docker exec safeline-mgt resettotp`.

Роль «только чтение» для аудиторов есть с **9.3.10** — на учебном стенде не обязательна; в бою заведите отдельно, не ходите все под `admin`.

## Подключение к своей системе

Приложения **не** ходят в SafeLine как в библиотеку и **не** открывают к нему JDBC/gRPC. Люди и партнёры открывают **домен, который слушает WAF**; WAF проверяет HTTP и проксирует на origin.

Официальная модель и поля сайта: https://docs.waf.chaitin.com/en/GetStarted/AddApplication

### Протокол

| Что | Как |
|---|---|
| Вход пользователей | **HTTP и HTTPS** (порты listen сайта, обычно **80** и **443** на хосте WAF) |
| Консоль | HTTPS **9443** — только админы с VPN |
| До origin | HTTP или HTTPS, как настроите **Upstream**. На закрытом стенде допустим открытый текст до локального Ingress |
| Health для будущего балансировщика | порт **65508**, не меняется (на одном учебном узле балансировщик не нужен) |
| Лицензия Pro | исходящий **:50052** на `safeline.stream.safepoint.cloud`. На учебном Personal **не требуется**. Offline в Install Guide нет |

### Кто клиент

- Браузер человека и HTTP-клиент партнёра — на **домен WAF**, не в обход на Ingress.
- Машинные интеграции (колбэки, health ведомств) — на **тот же** домен, в allowlist **до** капчи на этих URL.
- Syslog атак в SIEM — функция **Pro**, не Personal.
- Kafka, Camunda, Postgres эталона в SafeLine **не подключаются**.

### Что класть в секрет (не в git)

| Секрет | Где живёт | Куда не класть |
|---|---|---|
| `POSTGRES_PASSWORD` | файл `/data/safeline/.env` | git, чат, образ |
| Пароль `admin` после смены | сейф / Vault | git, `.env` в репозитории |
| Ключ лицензии Pro (если появится) | консоль + сейф | git |
| Сертификаты сайтов на tengine | консоль «SSL Cert» / корпоративный PKI | публичный репозиторий ключа |

В git можно описание процедуры и **безсекретовый** фрагмент `.env` (имена переменных). Сам `.env` с паролем — нет.

### Как повесить первый учебный сайт

1. В консоли: **Applications → Add Application**.
2. **Domain** — имя (или IP) вашего приложения, как его видит клиент, например учебный `app.example.test`.
3. **Port** — что слушает SafeLine, обычно `80` или `443`. Для HTTPS включите опцию SSL и задайте сертификат.
4. **Upstream** — реальный адрес origin: Ingress **этого** зала (учебный Service/Ingress), не HTTP через город на чужой дата-центр.
5. Резолв имени: домен должен указывать на **IP машины SafeLine**, не на origin напрямую. Иначе клиент обойдёт щит, а счётчик «Today's visits» в консоли не вырастет.

Проверка с машины клиента или jump-хоста (подставьте свои имя, IP и порт listen):

```bash
curl -v -H "Host: <домен>" http://<ip-safeline>:<listen-порт>
```

Успех по FAQ: ответ origin пришёл **и** счётчик посещений сайта в консоли вырос на 1. Если видите `502 Bad Gateway tengine` — WAF не достучался до upstream (неверный адрес или сеть).

Политика на стенде: сначала **журнал**, потом блокировка. Капчу и динамическую защиту **не** включать на URL роботов и JSON API — ломает машинных клиентов. Реальный IP клиента за балансировщиком (`Applications → Advanced → Get Attack IP From`) настраивают **до** банов по IP; на одном учебном узле без балансировщика WAF берёт IP из сокета.

Тестовые атаки из гайда Add Application (SQL-инъекция, XSS и т.д.) гоняйте **через домен WAF**. Если в журнале пусто — запрос, скорее всего, ушёл на origin в обход.

### Чем продукт не является

| Сосед / ожидание | Чем отличается |
|---|---|
| Ingress / NetworkPolicy | WAF их не заменяет. Origin в Kubernetes в бою принимает HTTP **только** с IP WAF |
| HAProxy | Балансировка и VIP; WAF — фильтр содержимого HTTP |
| Spring Cloud Gateway | Ваш Java-шлюз **внутри** платформы; SafeLine — на входе HTTP снаружи |
| Защита Kafka / gRPC / Postgres | Не видит шину и не читает тело не-HTTP |
| Исходящие вызовы к ведомствам | Стоит на **входящем** HTTP; исходящее интеграционное API им не является |
| Кластер с общей БД | У каждого узла свой Postgres. Personal ≠ кластер |
| Библиотека в коде приложения | Клиенты ходят на домен WAF, код приложения SafeLine не импортирует |

На учебном стенде прямой обход origin ещё возможен — так и задумано для отладки. В бою это дыра.

## Бой: узел на каждую площадку, балансировщик снаружи

Учебный запуск сюда **не** копируют. **Зачем бой:** пережить отказ **узла или целого зала по HTTP-трафику**, если балансировщик снимает мёртвый бэкенд. Конфиг правил одной базой не растягивать. Цифр запросов в секунду нет.

Целевой вариант: **по независимому инстансу в каждом живом дата-центре + внешний балансировщик + Pro Config Auto Sync**. Один WAF на всю систему отказ зала не переживает. Три изолированных WAF без sync — временный костыль (правила разъедутся). «Реплики в Kubernetes» — не цель.

Трафик — на все здоровые узлы **или** active-passive, если капча/сессия плохо переживает балансировку. Липкость сессии может понадобиться; в документации нет жёсткого «всегда sticky» — это надо **проверить**.

### Почему базу не растягиваем на несколько дата-центров

Postgres узла хранит конфиг, логи и статистику **этого** узла. Общего Raft нет. Тащить одну БД WAF через город — схема, которой продукт не описывает. Tengine и detector проверяют запрос **локально**.

Если сеть между залами периодически отваливается, slave отстанет **правилами**, продолжая пускать трафик по **старой** политике — тихий риск.

### Как расставить машины

**В каждом живом дата-центре — свой полный инстанс** перед Ingress **этого** зала:

- выделенная VM; FAQ не рекомендует соседство с бизнесом на одной машине;
- локальный диск каталога данных, **не NFS**;
- политика очистки логов — иначе Postgres съест диск независимо от озера;
- свободны 80/443, 65508, 65443; консоль 9443 — jump/VPN; Postgres **не** публиковать;
- исходящий **:50052** на сервер лицензий (Pro);
- upstream — **локальный** Ingress/сервис этого зала, не HTTP через город;
- origin в Kubernetes принимает HTTP **только** с IP WAF-узлов (NetworkPolicy). Иначе щит обходят.

Master — **один**, лучше в зале, где сидит эксплуатация. Slave — остальные; конфиг только с master. Связь master↔slave — внутренние адреса WAF-узлов, не публичные.

**Между площадками:**

| Сколько площадок | Что где | Если умер зал 1 |
|---|---|---|
| **Две** | По узлу (или пулу узлов) в каждом; каждый перед своим Ingress | Трафика зала 1 нет, пока балансировщик/DNS не увёл на зал 2. Конфиг зала 1 сам не «переезжает» |
| **Три** | Третий такой же узел | То же; третий узел не склеивает Postgres |

**Синхронизация правил (не БД, не сессии):**

| Редакция | Как | Следствие |
|---|---|---|
| **Pro** | Один master, остальные slave; трафик могут принимать все | Падение master не обязано ронять HTTP, если slave уже получил конфиг. Менять правила — пока жив master. Процедуры «выбрать нового master» в EN docs **нет** |
| **Personal** | Ручной экспорт/YAML на каждом узле | Дрейф = в одном зале блокируем, в другом нет |

Горизонталь внутри зала при нехватке CPU: **ещё один полный узел** в пул балансировщика этой площадки, не `replicas: 3`. Каждый Pro-узел — свой ключ.

Health балансировщика — на живой HTTP или **65508**, узел снимать на время рестарта. Апгрейд официально **рвёт** трафик узла. Версия **включая патч** одинаковая на всех узлах: sync и лицензии требуют согласованности.

Если очень нужно «всё в Kubernetes»: один Helm-release **на узел/зал**, `replicas: 1`, hostNetwork и осторожность с портами, отдельный диск, **не** HPA. Это хуже официального Compose и всё равно требует внешнего балансировщика и Pro-sync. Не продавать как «облачный автоскейл WAF».

### Что должно быть до боевой установки

- Linux VM на площадку, SSSE3, Docker/Compose.
- Зеркало образов в **вашем** registry по digest, если закрытый контур. В бою не `curl | bash` с сайта вендора в обход зеркала.
- Корпоративный PKI для сертификатов сайтов. Самоподписанный 9443 для людей на FQDN — плохая норма.
- Решение ИБ по вендору из КНР, телеметрии и постоянному интернету до `:50052`. Если контур это запрещает — документированный Pro не работает; offline в Install Guide нет.
- Карта входящего HTTP (API, портал, колбэки, консоли) — без неё нельзя список сайтов и allowlist.
- Городской или площадочный балансировщик с health check.

### Порядок установки (повторить в каждом дата-центре)

1. Закрыть пробелы: интернет до лицензий, карта HTTP, есть ли балансировщик, ИБ по вендору.
2. Оценить запросы в секунду хотя бы грубо; размер VM по FAQ как старт.
3. VM, каталог данных, сильный пароль Postgres, `.env`: `IMAGE_TAG=9.4.0`, `REGION=-g`.
4. Поднять стек → `resetadmin` → сменить admin → роль только на чтение для аудиторов (есть с 9.3.10).
5. Сайты: домен, listen, upstream **этого** зала, TLS.
6. Реальный IP **до** банов: откуда брать IP атаки / PROXY Protocol за балансировщиком. SafeLine сам кладёт источник в X-Forwarded-For; приложению доверять заголовок только от IP WAF, не с любого адреса.
7. Политика: сначала журнал, потом блокировка на боевых интеграциях. Allowlist IP ведомств **до** капчи на тех же URL. Динамическая защита на JSON API почти наверняка сломает клиентов — только на человеческих HTML-страницах.
8. Pro: включить Config Auto Sync (master в зале эксплуатации). Проверить, что на slave появились сайты и правила форвардинга (состав sync дорабатывали вплоть до 9.4.0).
9. Personal: процедура копирования YAML — часть установки, не «потом».
10. Syslog атак в SIEM (Pro). Логи в БД узла сами в три зала не сливаются. Personal в FAQ предлагает fluentd из таблицы Postgres — для боя это костыль, но показывает: логи **в базе узла**. Алертинг Pro — не замена SIEM.
11. Мониторинг: контейнеры, диск, запросы/с, 5xx «SafeLine vs origin», health 65508, коннект :50052, смена IP узла как процедура с риском отвала ключа.
12. Только потом — боевые DNS.
13. Нагрузить синтетикой с **включёнными** правилами. По результату — CPU и число узлов.
14. Прогон «зал master недоступен»: что с трафиком **и** что с возможностью менять правила.

Апгрейд: снять узел с балансировщика → бэкап каталога (`compose down` + копия, миграция **необратима**) → обновить одинаковым патчем **9.4.0** на всех → вернуть. Прыжок через старые мажоры — смотреть changelog, особенно порог 9.2.7. Катить все залы сразу = простой периметра.

Шифрование тома каталога — ваше: в продукте at-rest «из коробки» нет.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Версия | pinned 9.4.0 на **всех** узлах | Sync и лицензии требуют согласованности |
| БД/сессии | только локальный Postgres узла | Нет растяжки |
| Upstream | Ingress этого зала | Нет лишней межзаловой зависимости |
| 9443 | не из интернета | Админка щита = поверхность атаки |
| IMAGE_TAG | не `latest` | Иначе залы разъедутся |
| Host 80/443 | только tengine, не ещё и Ingress | Конфликт портов |
| Лицензия | Pro на **каждом** узле, отдельный ключ | HA-функция платная |

Исходящий с WAF — **только** на хост лицензий, не весь интернет.

### Как расти, когда появятся цифры нагрузки

1. Замерить входящий HTTP (пик и плато), долю TLS, размер тела, websocket.
2. Снять CPU detector и tengine при **включённых** правилах (пустой WAF врёт).
3. Сверить с FAQ: меньше 100 запросов/с → 2 ядра / 4 ГБ; 100–1000 → 4/8; больше 1000 → 8/16 — как **старт**, не гарантия.
4. Pro: режим производительности детектора.
5. Не хватает пика — ещё узел **в том же зале** в пул, равномерно по площадкам.
6. Диск логов — отдельно от CPU.

### Проверки, без которых это ещё не бой

1. Тег **9.4.0**, `REGION=-g` на всех узлах.
2. Запрос в зал N идёт через WAF зала N на **локальный** origin; origin с мира без WAF — отказ.
3. Выключить VM WAF зала 1: балансировщик туда не шлёт; живые узлы **одинаково** пускают и блокируют тест-атаку (sync Pro или свежий ручной YAML).
4. Учение «зал master недоступен»: трафик vs возможность **менять** правила — зафиксировать письменно.
5. Капча и динамическая защита не ломают машинные интеграции.
6. 9443 с мира — отказ. Postgres с хоста мир не слушает.
7. Смена IP узла и обрыв :50052 — не сюрприз: мониторинг есть.

### Что хорошо и что плохо в схеме «узел на зал + sync/YAML»

| Хорошо | Плохо |
|---|---|
| Детект локальный, БД не зависит от задержки между городами | Зависит от внешнего балансировщика/DNS — другое ПО и другая точка отказа |
| Отказ 1 зала не валит чужой tengine | Personal: дрейф правил; Pro: master = точка отказа на изменение политики |
| Согласовано с запретом общей БД | Лицензия Pro завязана на облако вендора |
| Origin только с IP WAF | Один обходной Ingress = WAF в стороне |
| Апгрейд можно катить по одному залу | Рестарт узла = краткий вычет ёмкости; без drain будут обрывы сессий |
| | Нет процедуры смены master в EN docs |

**Не готово к бою**, если: один Compose на 2–3 зала; общая БД WAF «на три площадки»; Personal как «кластер» без процедуры YAML; `replicas: 3` в Kubernetes; `IMAGE_TAG=latest`; консоль 9443 с мира; нет балансировщика; сервер лицензий заблокирован без альтернативы вендора; динамическая защита на машинном API; origin опубликован напрямую; ждут замену NetworkPolicy; прогон отказа зала и master не делали.
