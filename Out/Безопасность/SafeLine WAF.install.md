# SafeLine WAF 9.4.0 — установка и конфигурирование

Связанный документ (глоссарий, tengine/detector, Personal vs Pro, Config Auto Sync, почему так): `SafeLine WAF.md`.

Этот файл — **как поставить и настроить**. Не копируйте Dev-значения в прод. Stretch Postgres/сессий SafeLine на несколько ЦОДов **не делаем**: у каждого узла **свой** `safeline-pg`; общей БД на 2–3 площадки продукт не даёт, а ping для «одной БД WAF на страну» запрещён. SafeLine — **reverse proxy WAF** (HTTP/HTTPS). Это **не** Ingress-контроллер и **не** замена NetworkPolicy.

Версия: **SafeLine 9.4.0**. Образы: **`chaitin/safeline-*`**, международная линейка **`REGION=-g`**, `IMAGE_PREFIX=chaitin`, `IMAGE_TAG=9.4.0` (не `latest`, не китайский инсталлятор `waf-ce.chaitin.cn`, не LTS — вендор LTS не сопровождает с 9.1.0-LTS).  
Официальный runtime: **Linux + Docker Compose** (Docker ≥ 20.10.14, Compose v2 ≥ 2.0.0). Документация: https://docs.waf.chaitin.com/ · Deploy: https://docs.waf.chaitin.com/en/GetStarted/Deploy

---

## Допущения этой инструкции

Их не было в исходном контексте платформы; без них нельзя дать конкретные команды.

1. **Stretch запрещён.** Один Compose-узел = полный стек (tengine + detector + mgt + **свой** Postgres) **внутри одного ЦОДа**. Между ЦОДами — независимые инстансы, не общая БД.
2. Прод-приложения — в Kubernetes каждого ЦОДа (см. `Kubernetes.install.md`). WAF стоит **рядом**, на выделенной Linux VM (или worker, где сознательно Compose и **не** Ingress на 80/443).
3. Dev — изолированная сеть, Personal на **x86_64** допустим (ARM в Personal вендор не поддерживает; ARM = Pro).
4. Нагрузки HTTP нет — нет числа узлов «хватит для прода». FAQ даёт CPU/RAM **от QPS** как справку, не гарантию.
5. Перед фермой в проде есть (или будет) **внешний LB/DNS** с health check. SafeLine сам failover трафика не делает.
6. Для 2 ЦОДов: по полному инстансу в каждом, перед Ingress **этого** ЦОДа. Для 3 ЦОДов: то же на третьей площадке. Один WAF «на всю систему» отказ площадки не переживает.
7. **Config Auto Sync (master/slave) — Pro** (с 7.0.0). Personal: ручное копирование конфига/YAML, иначе через месяц правила разъедутся.

## Dev: 1 ЦОД, без нагрузки

**Цель:** модель reverse proxy, список Applications, не сломать машинные клиенты Anti-Bot/Dynamic Protection. **Не** цель: отказ ЦОДа и CPU детектора на пике.

### Предпосылки

- Linux x86_64, флаг **SSSE3** (`lscpu | grep ssse3`).
- Docker ≥ 20.10.14, Compose v2.
- Свободны 80/443 хоста (tengine в **`network_mode: host`**) и консоль **9443**. Не ставить на ту же VM Ingress, который тоже хочет 80/443.
- Минимум «чтобы встало»: 1 CPU / 1 ГБ / 5 ГБ — не прод. Для QPS < 100 FAQ: 2 CPU / 4 ГБ.
- Сеть стенда закрыта. **9443 и 5432 не в интернет.**

### Установка (Docker Compose — основной путь Dev)

Зафиксировать в `.env` (файл **не** в git):

```bash
IMAGE_PREFIX=chaitin
REGION=-g
IMAGE_TAG=9.4.0
SAFELINE_DIR=/data/safeline
MGT_PORT=9443
# POSTGRES_PASSWORD — свой, не дефолт
# SUBNET_PREFIX — уникальный, если на хосте уже есть Docker-сети
```

Официальный инсталлятор — `manager.sh` с сайта вендора **или** compose репозитория **того релиза**, который ставите (в changelog 9.3.11 бандл Postgres **15.2 → 15.18**; не смешивать compose разных тегов). На закрытом стенде — зеркало образов `chaitin/safeline-*:9.4.0`.

После подъёма:

```bash
docker exec safeline-mgt resetadmin
```

`resetadmin` — узнать стартовый пароль, затем **сменить**. Хранить вне git.

Проверка: консоль `https://<ip>:9443` с jump/VPN; контейнеры `safeline-tengine`, `safeline-detector`, `safeline-mgt`, `safeline-pg` живы; один Application на тестовый HTTP → запрос доходит до upstream.

Community Helm (`replicas: 1`) — эксперимент «впихнуть в K8s», **не** официальный Install Guide и не YAML прода. В README стороннего чарта несколько replica «ломают WAF неизвестным образом».

### Конфигурирование Dev

| Параметр | На тесте | Почему можно |
|---|---|---|
| Один узел Personal | да | Некому синхронизироваться |
| Балансировщик | не нужен | Один IP |
| TLS до upstream | PLAIN, если сеть закрыта | Иначе PKI раньше списка сайтов |
| Жёсткий block всех правил | нет, сначала лог | Иначе две недели «WAF виноват» |
| Config Auto Sync | нет | Один узел |

Чего **не** упрощать: приложения ходят **на домен WAF**, не в обход; сразу решить, как передаётся client IP (сокет / XFF / PROXY Protocol) — пригодится с LB; **не** включать Dynamic Protection и Challenge на URL роботов интеграций; версия **9.4.0**.

### Проверка Dev

1. Образ/тег **9.4.0**, `REGION=-g`.
2. Тестовый запрос через WAF → 200 от origin; прямой обход origin с стенда ещё возможен — на тесте ок, в проде это дыра.
3. Рестарт VM: пока DNS указывает только сюда, входа нет — ожидаемо.

### Сильные / слабые стороны Dev

| Сильное | Слабое |
|---|---|
| Часы, официальный Compose | Падение VM = нет WAF и, если DNS сюда, нет HTTP входа |
| Дешево понять, жив ли продукт с интеграционным HTTP | Не ловит рассинхрон узлов, апгрейд с обрывом, XFF за городским LB |
| | Успех одного Compose ≠ готовность 2–3 ЦОДов |

Препрод: **минимум 2 узла** (Pro + sync **или** Personal + ручной YAML, который вы реально копируете) + простой LB — в **одном** ЦОДе уже полезно, иначе первый сюрприз «правила разные».

## Prod: 2 или 3 ЦОДа, без stretch, нагрузка возможна

**Цель:** пережить отказ **узла/ЦОДа по HTTP-трафику**, если LB снимает мёртвый бэкенд; конфиг правил не растягивать одной БД. Цифр QPS нет.

### Почему не stretch

`safeline-pg` хранит конфиг, логи и статистику **этого** узла. Общего Raft/реплики Postgres между ЦОДами нет. Тащить одну БД WAF через город — и запрещённый stretch, и схема, которой продукт не описывает. Tengine+detector проверяют запрос **локально**; межЦОДовый RTT на детект почти не влияет.

### Топология

**В каждом живом ЦОДе — свой полный инстанс** перед Ingress **этого** ЦОДа:

```
клиенты → LB/DNS площадки или города
             ▼
     SafeLine ЦОД-N  (Compose: tengine + detector + mgt + свой pg)
             ▼
     Ingress / HTTP origin **этого** ЦОДа
```

Upstream — **локальный**. Не форвардить HTTP через город на чужой Ingress: живой WAF + мёртвое «чужое» приложение = лишняя зависимость.

| Площадок | Что где | Отказ ЦОД-1 |
|---|---|---|
| **2 ЦОДа** | По узлу (или пулу узлов) в ЦОД-1 и ЦОД-2; каждый перед своим Ingress | Трафик ЦОД-1 нет, пока LB/DNS не увёл на ЦОД-2. Конфиг ЦОД-1 не «переезжает сам» |
| **3 ЦОДа** | Третий такой же узел в ЦОД-3 | То же; третий узел не склеивает Postgres |

**Синхронизация правил (не БД, не сессии):**

| Редакция | Как | Следствие |
|---|---|---|
| **Pro** | Config Auto Sync: **один** master, остальные slave; трафик могут принимать все | Падение master не обязано ронять HTTP, если slave уже получил конфиг. Менять правила — пока жив master. Процедуры «выбрать нового master» в EN docs **нет** |
| **Personal** | Ручной экспорт/YAML/повторить Applications на каждом узле | Дрейф = в одном ЦОДе блокируем, в другом нет. Допустимо как временный костыль, не как «кластер» |

Горизонталь внутри ЦОДа при нехватке CPU: **ещё один полный узел** в пул LB этой площадки, не `replicas: 3` в Deployment. Каждый Pro-узел — свой ключ (один ключ на три машины docs не обещает).

Tengine слушает 80/443 хоста; служебные порты FAQ: **65508** health (не меняется), **65443** custom page, **9443** консоль (меняется). Health LB — на живой HTTP/65508, узел снимать на время рестарта (апгрейд официально **рвёт** трафик узла).

### Предпосылки прода

- Linux VM на площадку; FAQ не рекомендует соседство с бизнесом на одной машине.
- Локальный диск `SAFELINE_DIR`. **Не NFS.** Политика Clean Data — иначе Postgres логов съест диск независимо от озера.
- Свободны 80/443, 65508, 65443. Консоль 9443 — jump/VPN. Postgres **не** публиковать (`sslmode=disable` внутри стека — не расширять эту сеть).
- Origin в Kubernetes принимает HTTP **только** с IP WAF-узлов (NetworkPolicy). Иначе WAF обходятся. WAF **не** заменяет NetworkPolicy между микросервисами, SASL Kafka, авторизацию API.
- Pro: исходящий **`safeline.stream.safepoint.cloud:50052`** постоянный. Если контур это запрещает — документированный Pro **не работает**; offline-схемы в Install Guide нет. Смена IP узла может оборвать лицензию.
- Корпоративный PKI для сертификатов сайтов на tengine. Самоподписанный 9443 для людей на FQDN — плохая норма.

### Установка (повторить в каждом ЦОДе)

1. VM, SSSE3, Docker/Compose, каталог данных, сильный `POSTGRES_PASSWORD`.
2. `.env`: `IMAGE_TAG=9.4.0`, `REGION=-g`, образы из **вашего** registry по digest.
3. Поднять стек → `resetadmin` → сменить admin → read-only роль для аудиторов (есть с 9.3.10).
4. Applications: домен, listen, upstream **этого** ЦОДа, TLS.
5. Реальный IP **до** IP-банов: `Get Attack IP From` / PROXY Protocol за LB. SafeLine сам кладёт источник в XFF; приложению доверять XFF только от IP WAF, не `0.0.0.0/0`.
6. Политика: сначала observe/лог, потом deny на боевых интеграциях. Allowlist IP ведомств **до** challenge на тех же URL. Dynamic Protection на JSON API почти наверняка сломает клиентов.
7. Pro: включить Config Auto Sync (master в ЦОДе эксплуатации). Проверить, что на slave появились сайты и forwarding rules (состав sync дорабатывали вплоть до 9.4.0).
8. Personal: процедура копирования YAML/конфига — часть установки, не «потом».
9. Syslog атак в SIEM (Pro). Логи в БД узла сами в три ЦОДа не сливаются.
10. Мониторинг: контейнеры, диск, QPS, 5xx «SafeLine vs origin» (различают в Pro), health 65508, коннект :50052.

Апгрейд: снять узел с LB → бэкап каталога (`compose down` + `cp -r`, миграция **необратима**) → обновить **9.4.0** одинаковым патчем на всех → вернуть. Катить все ЦОДы сразу = простой периметра.

### Конфигурирование (смысл)

| Параметр | Прод | Зачем |
|---|---|---|
| Версия | pinned 9.4.0 на **всех** узлах | Sync и лицензии требуют согласованности |
| БД/сессии | только локальный pg узла | Нет stretch |
| Upstream | Ingress этого ЦОДа | Нет лишней межЦОДовой Hop |
| 9443 | не из интернета | Админка щита = поверхность атаки |
| IMAGE_TAG | не `latest` | Иначе ЦОДы разъедутся |
| Host 80/443 | только tengine, не ещё и Ingress | Конфликт портов |

### Масштабирование (когда появятся цифры)

1. Замерить HTTP QPS (пик/плато), долю TLS, размер тела, websocket.
2. Снять CPU `detector` и `tengine` при **включённых** правилах (пустой WAF врёт).
3. Сверить с FAQ: <100 QPS → 2/4 ГиБ; 100–1000 → 4/8; >1000 → 8/16 — как **старт**, не гарантия.
4. Pro: режим производительности детектора.
5. Не хватает пика — ещё узел **в том же ЦОДе** в пул LB, равномерно по площадкам.
6. Диск логов — отдельно от CPU.

### Проверка прода (пока это не пройдено — это не прод)

1. Тег **9.4.0**, `REGION=-g` на всех узлах.
2. Запрос в ЦОД-N идёт через WAF ЦОД-N на **локальный** origin; origin с мира без WAF — отказ (NetworkPolicy/firewall).
3. Выключить VM WAF ЦОД-1: LB не шлёт туда; живые узлы **одинаково** пускают и блокируют тест-атаку (sync Pro или свежий ручной YAML).
4. Учение «ЦОД master недоступен» (Pro): трафик vs возможность **менять** правила — зафиксировать.
5. Challenge/Dynamic Protection не ломают машинные интеграции.
6. 9443 с мира — отказ. Postgres с хоста не слушает мир.

### Сильные / слабые стороны прод-схемы (узел на ЦОД + sync/YAML)

| Сильное | Слабое |
|---|---|
| Детект локальный, БД не зависит от межЦОДового RTT | Зависит от внешнего LB/DNS |
| Отказ 1 ЦОДа не валит чужой Tengine | Personal: дрейф правил; Pro: master = SPOF на изменение политики |
| Согласовано с запретом stretch | Лицензия Pro завязана на облако вендора |
| Origin только с IP WAF | Один обходной Ingress = WAF в стороне |

**Не готов к проду**, если: один Compose на 2–3 ЦОДа; общая БД WAF «на три площадки»; Personal как «кластер» без процедуры YAML; `replicas: 3` в Kubernetes; `IMAGE_TAG=latest`; консоль 9443 с мира; нет LB; license server заблокирован без альтернативы вендора; Dynamic Protection на M2M API; origin опубликован напрямую; ждут замену NetworkPolicy.
