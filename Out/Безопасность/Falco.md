# Falco 0.44.1 — развёртывание и настройка

Версия ПО: **Falco 0.44.1** (релизная дата 11 июня 2026; на дату подготовки документа это последний стабильный патч линии 0.44).  
Документация: https://falco.org/docs/  
Образ: `falcosecurity/falco:0.44.1` (Docker Hub и `public.ecr.aws/falcosecurity/falco:0.44.1`).  
На Kubernetes официально рекомендуемый способ: **Falco Operator v0.4.1** (с v0.4.0 в матрице версий оператора default Falco = 0.44.1). Helm-чарт оператора на этой линии — `falcosecurity/falco-operator` **0.3.0**. Альтернатива, всё ещё полностью поддерживаемая: Helm-чарт `falcosecurity/falco` **9.1.0** (тоже ставит Falco 0.44.1).

Этот текст — не мануал «скопируй и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Falco **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API). Ниже — как поставить runtime-детектор на ту же Kubernetes-платформу. Это не замена сетевых политик, RBAC, WAF и не «кнопка безопасность включена».

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Runtime security** | Защита «пока уже работает»: смотрим, что процесс *делает* (запустил shell, открыл `/etc/shadow`, вышел в сеть), а не только то, какой у него образ. |
| **Syscall (системный вызов)** | Обращение программы к ядру Linux: открыть файл, создать процесс, соединиться по сети. Falco читает этот поток. |
| **Драйвер (driver / engine)** | Кусок, который в ядре (или рядом с ним) снимает syscalls и отдаёт их процессу `falco`. В 0.44 осталось два: **modern eBPF** и **kernel module**. |
| **modern eBPF (modern_ebpf)** | Драйвер по умолчанию. Программа eBPF, встроенная в бинарник Falco, без сборки модуля под каждый kernel. Нужны возможности ядра: BPF ring buffer и BTF (обычно Linux **≥ 5.8**, на части дистрибутивов могли бэкпортировать раньше). |
| **CO-RE** | «Compile Once, Run Everywhere»: eBPF-программа подстраивается под конкретное ядро по BTF, без исходников ядра на ноде. |
| **BTF** | Таблица типов ядра. Без неё modern eBPF не встанет. |
| **Kernel module (kmod)** | Классический модуль ядра. Работает на более старых ядрах (≥ 3.10), но требует **полных привилегий** и загрузки модуля на каждую ноду (часто через `falco-driver-loader`). |
| **Legacy eBPF** | Старый eBPF-проб. **Удалён в 0.44.** Оставлять его в конфиге нельзя. |
| **Правило (rule)** | Условие «если произошло X — подними тревогу» на YAML. Набор условий + текст алерта + приоритет. |
| **Макрос / список (macro / list)** | Переиспользуемые куски условий и списки имён (шеллы, бинарники). Чтобы не копировать одно и то же в каждое правило. |
| **Приоритет** | Громкость правила: `emergency` … `debug`. Нужен, чтобы SIEM и дежурные не тонули в шуме. |
| **Алерт (alert / output)** | Сообщение «правило сработало». Falco сам **не убивает** под и **не блокирует** syscall. |
| **Дроп событий (syscall event drop)** | Ядро не смогло записать syscall в буфер — Falco его **не увидел**. Это слепая зона, не «оптимизация». |
| **buf_size_preset** | Размер кольцевого буфера между ядром и Falco. Больше буфер → меньше дропов и больше RAM. |
| **cpus_for_each_buffer** | Только modern eBPF: сколько CPU делят один буфер. `1` = буфер на каждое ядро (больше памяти, меньше конкуренции). |
| **base_syscalls** | Какие syscalls вообще снимать. Чем шире набор и чем больше правил — тем выше нагрузка. |
| **Plugin** | Расширение: новые поля или даже другой источник событий (не только ядро). Для Kubernetes почти всегда нужны **container** и часто **k8smeta**. |
| **container plugin** | Достаёт метаданные контейнера (образ, id) через сокеты containerd/CRI-O/Docker. Без него штатные правила с `container.*` не работают. |
| **k8smeta + k8s-metacollector** | Плагин + отдельный сборщик: в алерт попадают pod/namespace/deployment, а не только «какой-то контейнер на ноде». |
| **DaemonSet** | Контроллер Kubernetes: «по одному поду на каждую ноду». Для syscall-мониторинга это **единственный** правильный режим. |
| **Deployment mode** | Falco как обычный Deployment (N реплик). Для съёма syscalls со всех нод **не подходит**. Имеет смысл для плагинных источников (например Kubernetes audit), не для ядра каждой машины. |
| **Falcosidekick** | Отдельный сервис экосистемы: принимает алерты Falco по HTTP и раздаёт в 70+ мест (SIEM, webhook, Kafka, Slack, …). |
| **Falcoctl** | Утилита: ставить/обновлять правила и плагины (артефакты). В Operator это делает sidecar Artifact Operator. |
| **OCI-артефакт правил** | Правила как образ в registry (`ghcr.io/falcosecurity/rules/falco-rules`), а не файл, зашитый в Docker-образ Falco. |
| **least privilege (capabilities)** | Не `privileged: true` на весь под, а набор Linux capabilities. Для modern eBPF официальный минимум: `CAP_BPF`, `CAP_PERFMON`, `CAP_SYS_RESOURCE`, `CAP_SYS_PTRACE` (на ядрах без дробных cap — ещё `CAP_SYS_ADMIN`). |
| **hostPath / HOST_ROOT** | Монтирование `/proc`, сокетов runtime с ноды в под Falco. Без этого нет нормального контекста процессов и контейнеров. |
| **output_timeout** | Сколько Falco ждёт, пока канал алерта (HTTP и т.д.) примет событие. Если приёмник лежит — это влияет на backpressure и дропы, не только на «потеряли письмо». |
| **Falco Talon** | **Другой** проект экосистемы: движок *реакции* (убить под, повесить NetworkPolicy). В дистрибутив Falco 0.44.1 **не входит**. |
| **SIEM** | Система, куда складывают security-события и где по ним дежурят люди/плейбуки. Falco без приёмника — это логи на ноде. |
| **Слепая зона (blind spot)** | Нода/ЦОД, где Falco не бежит или дропает события: атака там не детектируется. |

## Основные элементы системы и зависимости

### Что входит в Falco 0.44.1 (это одно ПО)

- **Userspace `falco`** — читает события, применяет правила, шлёт алерты.
- **Драйвер** — modern eBPF (по умолчанию) или kernel module.
- **Конфиг `falco.yaml`** — драйвер, выходы, буферы, метрики, плагины.
- **Правила** — YAML (файлы или OCI-артефакты).
- **falcoctl** — ставится вместе с Falco; на K8s его работу часто забирает оператор.

### Экосистема (отдельные компоненты, без них прод обычно неполный)

| Компонент | Зачем | Это не «сам Falco» |
|---|---|---|
| **Falco Operator** | CRD `Falco` / `Rulesfile` / `Plugin` / `Config` / `Component`; рекомендуемый путь на K8s | Отдельный репозиторий `falcosecurity/falco-operator` |
| **Artifact Operator** | Sidecar в поде Falco: доставляет правила и плагины | Требует Kubernetes **1.29+** (native sidecars) |
| **Falcosidekick** | Маршрутизация алертов | Отдельный Deployment; у Falco из коробки только stdout/file/syslog/программа/HTTP |
| **k8s-metacollector + k8smeta** | Kubernetes-контекст в алертах | Отдельный сервис + плагин |
| **Falcosidekick UI + Redis** | Веб-просмотр алертов | Удобство, не контур детектирования. Redis — ещё одна зависимость |
| **Falco Talon** | Автоответ на алерт | Отдельное решение; включать только с ИБ-процессом |

### Чего в Falco нет (частая путаница)

| Нужно системе | Это не Falco | Зачем помнить |
|---|---|---|
| Запретить syscall / не пустить пакет | seccomp, NetworkPolicy, WAF, firewall | Falco **детектирует и алертит**. Цитата документации проекта: monitoring and detection agent. |
| Закрыть образ до запуска (скан CVE) | Trivy, Grype, политика admission | Другой слой (supply chain), другое время жизни. |
| Kubernetes Audit «кто вызвал API» | API server audit → плагин `k8saudit` (отдельный источник) | Штатный DaemonSet смотрит **ядро ноды**, не audit.log apiserver. |
| Шифрование at-rest / ГОСТ TLS | Не входит | Канал алертов — обычный HTTP или TLS с валидным сертификатом (self-signed Falco **не** принимает). |
| Единый кластер «на 3 ЦОДа» с кворумом | Нет такого | Falco — **агент на ноде**. Падение ЦОДа не «выбирает нового лидера Falco»; ноды мёртвого ЦОДа просто не мониторятся. |
| Гарантия 0 дропов при любой нагрузке | Не обещается | Официальный troubleshooting прямо говорит: на очень шумных машинах дропы могут быть неустранимы. |

### Зависимости окружения (обязательны)

- **ОС нод: Linux**, архитектуры **x86_64 или ARM64**. Windows-ноды Falco не покрывает.
- **Для modern eBPF:** BTF + BPF ring buffer; для производительности — `CONFIG_BPF_JIT` и `net.core.bpf_jit_enable=1` (официальная страница пакетов).
- **Для kmod:** возможность грузить модуль ядра, часто kernel headers / prebuilt module, **full privileges**.
- **Kubernetes:** оркестрация подов Falco. Operator: **1.29+**. Чарт `falco` 9.1.0 — если кластер старше (проверять values чарта, не этот документ).
- **CRI-сокеты на ноде** (containerd / CRI-O / Docker) — для container plugin.
- **Исходящая сеть** с нод до приёмника алертов (Falcosidekick / syslog / SIEM). Без неё детект есть, реакции и учёта нет.
- **Registry** для образов и OCI-правил (`ghcr.io` или внутреннее зеркало). В закрытом контуре без зеркала поды не стартанут.

### Как Falco стыкуется с вашей архитектурой

```
Ноды Kubernetes (микросервисы, Kafka, Camunda, интеграционный API)
        │  syscalls
        ▼
   Falco DaemonSet (этот документ)
        │  JSON-алерты (stdout + HTTP)
        ▼
   Falcosidekick ──► SIEM / webhook дежурных
                 └─► опционально отдельный топик Kafka (не бизнес-события)
```

Falco **не** участвует в event-sourcing и **не** является источником истины клиентских данных. Он смотрит, не делает ли рантайм ноды того, чего правила считают опасным (shell в контейнере, запись в `/etc`, неожиданный исходящий коннект, смена namespace и т.д. — это примеры штатного ruleset, не ваш уникальный профиль угроз).

## Краткие вводные

### Зачем вам Falco в этой архитектуре

У вас Kubernetes, много сервисов, Kafka, процессный движок, интеграции с госслужбами. Типичные дыры, которые admission-контроллер и сканер образов **не** закрывают:

1. Скомпрометированный контейнер, который уже запущен (RCE, украденные учётные данные воркера).
2. Отладка «на живую»: `kubectl exec` → `bash` в проде.
3. Процесс полез не туда в файловой системе или открыл лишний сокет.

Falco как раз про это: поток syscalls + правила → алерт с контекстом контейнера/пода.

### Как устроена отказоустойчивость (идея, не магия)

Это **не** Kafka. Нет реплик партиций и нет кворума.

| Что падает | Что происходит |
|---|---|
| Под Falco на ноде | Эта нода **слепая**, пока под не перезапустится. Нагрузка приложений на ноде жива. |
| Нода целиком | И нагрузка, и Falco мертвы вместе. Это нормально. |
| Falcosidekick | Детект на нодах продолжается; HTTP-алерты могут копиться/отваливаться по `output_timeout`. Если настроен ещё stdout/syslog в агент логов — след не обязан пропасть. |
| Один ЦОД из трёх | Ноды двух других ЦОДов мониторятся независимо. «Переключения на другой Falco» нет и не нужно. |
| Оператор | Уже запущенные DaemonSet'ы обычно продолжают работать; ломается выкат правил/конфига. |

Следствие: HA Falco = **под на каждой рабочей ноде** (включая tainted: control-plane, dedicated Kafka) + **живой канал алертов** минимум в двух экземплярах + запасной канал (логи ноды).

### Как устроено масштабирование

Единица масштаба — **нода**, не «ещё один Falco-кластер».

- Добавили ноды в Kubernetes → DaemonSet сам поставил ещё один агент.
- «Терабайты в озере данных» на Falco почти не влияют. Влияет **частота syscalls на ноде** (Kafka с большим сетевым/дисковым I/O, Java с частым fork/exec — шумные соседи).
- Узкое место официально: userspace Falco обрабатывает основной поток **однопоточно**; слишком широкие правила и лишние плагины создают backpressure → дропы в ядре.
- Горизонтально «размазать один агент на три ноды» нельзя: каждый агент видит только своё ядро.

Официальный troubleshooting (с их же оговоркой «take with a grain of salt»): ориентиры **на одно CPU** по `scap.evts_rate_sec / falco.host_num_cpus` — порядка **< ~1–1.5k events/s** обычно терпимо, **> ~3k/s** уже часто тяжело. Это не расчёт ёмкости вашего кластера.

### Безопасность самого Falco

Агент с доступом к syscalls всей ноды — **привилегированный наблюдатель**. Если его взломают или ошибочно отдадут `kubectl logs`/webhook наружу, это утечка фактов о процессах и, при широких правилах, о путях/командных строках.

Поэтому «включить Falco с quickstart.yaml и UI в интернет» — это не прод, это новый attack surface.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём open-source Falco 0.44.1**, не Sysdig Shield / коммерческий «Falco-совместимый» агент. Правила, лицензия и оператор у них другие.
2. **Прод крутится в Kubernetes.** Целевой путь — **Falco Operator v0.4.1**. Если Kubernetes **< 1.29**, Operator (native sidecar Artifact Operator) **не** тот путь; тогда Helm `falco` 9.1.0. Версия вашего K8s в контексте не названа.
3. **Драйвер прода — `modern_ebpf`.** Ядра нод достаточно новые (BTF + ringbuf). Если в парке есть древние ядра без этих фич — для *этих* нод только kmod (другие привилегии, другой operational burden). Смешивать «тихо» нельзя: это должно быть явное решение по пулу нод.
4. **Три ЦОДа = три домена отказа для нод**, но Falco не stretch-кластер. Схема следует топологии Kubernetes: один кластер на 3 зоны **или** три изолированных кластера (это не сказано — см. пробелы).
5. **Нагрузка неизвестна** — поэтому **нет** цифры CPU/RAM «хватит агенту». Есть сигналы (`scap.n_drops`, `scap.evts_drop_rate_sec`) и рычаги (буферы, правила, `base_syscalls`).
6. **Формального SLA на детектирование нет.** «Система работает 24/7» ≠ «Falco не пропустил syscall». Дропы при пике Kafka на ноде — штатный риск, его надо мерить, а не отрицать.
7. **Приёмник алертов будет** (SIEM / SOC-очередь / on-call webhook). Без него экземпляр «настроенным» не считается. Falcosidekick UI **не** замена SIEM.
8. **Корпоративный PKI есть или будет.** HTTPS от Falco к Sidekick и от Sidekick к SIEM — с **валидными** сертификатами. Документация Falco: self-signed / invalid cert для `http_output` **не поддерживаются**.
9. **Штатный ruleset — старт, не финиш.** Официальные правила (линейка `falco-rules`, в составе 0.44.0 упоминается 5.1.0) дадут шум на Java/Kafka/Camunda (exec, сеть, запись во временные файлы). Нужен процесс исключений. Без него либо все игнорируют алерты, либо душат легитимную работу.
10. **Реакция (kill pod) не включается в этом документе.** Talon/OPA/ручной SOC — отдельное решение ИБ. Иначе первый ложный `exec` в контейнере интеграции положит процесс гос-обмена.
11. **Тестовый стенд изолирован.** На нём допустим HTTP до Sidekick и default rules. Прод-TLS и свои исключения на тест один в один не копируем, но **каналы вывода и метрики дропов** лучше включить сразу, иначе тест не показывает слепые зоны.
12. **Camunda, Kafka, озеро, интеграционное API** — *нагрузка и поверхность атаки* на тех же нодах, не часть Falco. Их ноды обязаны попасть в DaemonSet (tolerations!).

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили DaemonSet и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **Версия Kubernetes** | Operator v0.4.x официально требует **1.29+**. Ниже — другой инсталлятор. |
| **Версия и BTF ядер нод** (все пулы, все ЦОДы) | Без ringbuf/BTF modern eBPF не встанет. Откат на kmod меняет привилегии и процесс выката ядра. |
| **Один K8s на 3 ЦОДа или три кластера** | От этого зависит, один Operator или три независимых контура и как алерты сходятся в один SOC. |
| **Taints/пулы нод** (Kafka dedicated, control-plane, GPU, Windows) | DaemonSet без tolerations = **слепые самые важные ноды**. Windows = постоянная слепая зона. |
| **Куда девать алерты** (SIEM, Kafka-топик, почта, никуда) | Без приёмника и on-call Falco не закрывает «безопасность», только генерирует JSON. |
| **Профиль syscalls / шум нод** | Нет замера `scap.evts_rate_sec` и дропов → нельзя сказать, выдержит ли агент соседство с Kafka. |
| **Требования ИБ: ГОСТ, 152-ФЗ, КИИ, срок хранения алертов, запрет privileged** | Меняют TLS, возможность eBPF, куда можно слать cmdline процессов (персональные данные в аргументах!), at-rest логов. |
| **Политика `kubectl exec` / debug в проде** | Штатные правила на shell в контейнере либо будут орать постоянно, либо их выключат «чтобы не мешали». Это решение процесса, не YAML. |
| **Есть ли уже другой runtime-агент** (Sysdig, CrowdStrike, auditd) | Два хука на одни tracepoints усиливают overhead и спорят за буферы. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **Falco 0.44.1** и способ установки (Operator v0.4.1 *или* Helm `falco` 9.1.0).
2. Проверить ядро: BTF, ringbuf, BPF JIT.
3. Поставить агент как **DaemonSet**, драйвер **`modern_ebpf`**.
4. Сначала **container plugin**, потом ruleset (официальный порядок Operator: без плагина поля `container.*` в правилах мертвы). Для осмысленных алертов в K8s — ещё k8smeta + metacollector.
5. Включить **метрики** (`kernel_event_counters_enabled`) и действия на дропы (`syscall_event_drops`: как минимум `log` + `alert`, не молчаливый `ignore`).
6. Настроить выходы алертов **до** объявления «мы под мониторингом».
7. Прогнать контролируемую атаку (официальный event-generator / свой exec в тестовом поде) и убедиться, что алерт **доехал** до приёмника.
8. Только потом — сужение правил под ваши сервисы.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** увидеть алерты, понять шум штатных правил на ваших образах, отладить доставку в мессенджер/лог. **Не** цель: доказать, что прод не пропустит атаку на Kafka-ноде под нагрузкой.

#### Топология

Минимально достаточно:

- namespace `falco`;
- Operator (если K8s ≥ 1.29) **или** Helm `falco` 9.1.0;
- один `Falco` CR / один DaemonSet, `engine.kind=modern_ebpf`;
- Plugin `container`;
- Rulesfile официальный `falco-rules` (на тесте тег можно `latest`, в прод — **pin**);
- опционально Falcosidekick **1 реплика** + UI, HTTP без TLS **только в изолированной сети**.

Quickstart-манифест оператора (`quickstart.yaml`) поднимает сразу Falco + плагины + Sidekick + UI + Redis + metacollector. Для знакомства удобно. **Это не прод-манифест** (HTTP на Sidekick, `latest` теги, UI, Redis).

Режим Deployment с `replicas: 2` на тесте для syscall-мониторинга **не использовать**: создаст ложное чувство HA и не покроет ноды.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| TLS до Sidekick | нет, если сеть закрыта | Иначе команда утонет в PKI раньше, чем в правилах |
| Реплики Sidekick | 1 | Нет требования пережить выкат |
| Свои exceptions | минимум | Сначала увидеть реальный шум |
| CPU/memory limits | мягкие/без жёсткого throttle | На тесте важнее не получить дропы из-за cgroup throttle |
| Покрытие control-plane | можно не сразу | На тесте часто одна нода |

#### Чего на тесте **не** стоит упрощать

- Драйвер тот же (`modern_ebpf`), что планируете в прод.
- Метрики дропов включены.
- Хотя бы один выход кроме «под смотрит человек в `kubectl logs`» — иначе в проде внезапно окажется, что HTTP никто не принимал.
- Проверка: под с `sleep` + `kubectl exec sh` даёт ожидаемый алерт.

#### Сильные стороны такой схемы

- Поднимается за часы.
- Совпадает с официальным quickstart Operator.
- Показывает шум правил на *ваших* Java/Node образах дешево.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет TLS, нет доказанной ёмкости буферов.
- Успешный детект exec на простой ноде **не** доказывает детект на нагруженном брокерном узле.
- UI + Redis на тесте приучают «ходить смотреть в Falco UI»; в инциденте нужен SIEM/on-call, не дашборд в namespace `falco`.

Практическая рекомендация: препрод = маленький **прод-профиль** (DaemonSet на все tainted-ноды, TLS, 2 Sidekick, pin версий, свои exceptions), даже без боевого трафика.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер на агент под терабайты» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Falco не выбирает stretch vs MirrorMaker. Он следует Kubernetes.

**Вариант A — один Kubernetes на 3 ЦОДа (зоны).**

- Один Operator, один `Falco` DaemonSet: kubelet сам держит под на каждой ноде каждой зоны.
- Falcosidekick: **≥ 2 реплики** (в примерах оператора для Sidekick указано `replicas: 2`) + **topology spread / anti-affinity по зоне**, лучше не меньше одной живой реплики в каждом ЦОДе, если хотите пережить падение площадки *на пути алертов*.
- Детект на живых нодах не зависит от RTT между ЦОДами. RTT важен только доставке алертов и работе metacollector/API.

**Вариант B — три изолированных Kubernetes.**

- Три независимых контура Falco (три Operator, три DaemonSet). Это **нормально и даже проще**.
- Свести алерты в **один** SIEM/топик (три Sidekick смотрят наружу, не три UI).
- Падение ЦОДа = нет и нагрузки, и детекта этой площадки. Нет «переключения Falco».

**Пока топология K8s не зафиксирована, нельзя честно выбрать A или B.** Дальше описывается общее для обоих; расхождение — только в числе операторов и в том, где живут реплики Sidekick.

##### Сильные / слабые стороны (A, один кластер)

| Сильное | Слабое |
|---|---|
| Один ruleset, один выкат | Сетевой раздел между ЦОДами: агенты живы, HTTP до Sidekick в другой зоне может отвалиться |
| DaemonSet покрывает зоны сам | Ошибка в ClusterRole/правиле сразу на всех площадках |
| Проще операционка | Sidekick и metacollector становятся общими SPOF, если не размазаны по зонам |

##### Сильные / слабые стороны (B, три кластера)

| Сильное | Слабое |
|---|---|
| Изоляция выката и отказа | Три копии правил; легко разъехаться |
| Алерты можно слать локально, без межЦОДового RTT на критическом пути | Нужен общий SOC, иначе три «правды» |
| Не зависит от pod-to-pod между ЦОДами | Легче забыть включить Falco в новом кластере |

#### Агент на нодах (ядро отказоустойчивости детекта)

- Только **DaemonSet**, не Deployment.
- **Tolerations на все taints**, где крутится нагрузка: control-plane (если там kubelet с подами), dedicated Kafka, Camunda, интеграционные ноды. Иначе HA платформы и HA Falco расходятся.
- `priorityClassName` высокий (как у node-critical / выше обычных приложений): при давлении памяти убивать бизнес-под, оставляя слепую ноду — плохой обмен, но ещё хуже вытеснить Falco «как BestEffort». Выбор class — решение эксплуатации; смысл: агент не должен быть первым кандидатом на evict.
- Rolling update DaemonSet: `maxUnavailable` держать низким (часто 1 или малый процент). Во время выката часть нод слепая — это окно атаки.
- PDB для DaemonSet в классическом виде почти бесполезен (по одному поду на ноду). Дисциплина — в `updateStrategy` и в том, чтобы не drain'ить сразу все ноды зоны без понимания окна слепоты.

#### Драйвер и привилегии

Прод-default:

```
engine.kind: modern_ebpf
```

- Не privileged «на всякий случай», если ядро умеет BPF capabilities — **least privilege** по официальному списку (`CAP_BPF`, `CAP_PERFMON`, `CAP_SYS_RESOURCE`, `CAP_SYS_PTRACE`; иначе `CAP_SYS_ADMIN`).
- kmod в проде — только для нод, где modern eBPF физически не встаёт. kmod **не умеет** least-privilege mode (официальная таблица: full privileges).
- Не монтировать в под больше hostPath, чем нужно (`/proc`, runtime sockets, при kmod — пути загрузки модуля).
- BPF JIT включён на нодах.

**Слабое место:** даже least-privilege Falco видит командный строки и пути по всей ноде. RBAC на namespace `falco`, отсутствие лишних Ingress на UI, NetworkPolicy «Falco → только Sidekick», Sidekick → только SIEM.

#### Правила и плагины (без этого детект либо мёртв, либо врёт)

Обязательный порядок (как в документации Operator):

1. Plugin **container** (pin тега образа плагина, не `latest` в проде).
2. Для K8s-контекста: **k8smeta** + Component **metacollector**.
3. Rulesfile официальный, **зафиксированный тег**.
4. Свои overlay-правила: exceptions под Kafka/JVM/Camunda, отдельные high-priority правила под интеграционный контур (неожиданный исходящий коннект не на список ведомств, shell в образе API, запись в TLS-ключи).

Выкат правил — через `Rulesfile` CR / артефакты, не «ssh и vi на ноде». Иначе три ЦОДа разъедутся.

**Слабое место штатных правил:** они про «необычно для generic container», не про вашу предметку. Без своего слоя либо шум, либо дыры.

Официальный metacollector в quickstart оператора — `replicas: 1`. Это **SPOF для обогащения** k8s-полями, не для съёма syscalls. Детект ядра живёт без него, но алерты деградируют до «контейнер на hostname». Заложить мониторинг доступности collector; не считать его равным по критичности Kafka, но и не оставлять без алерта.

#### Выходы алертов и HA пути «увидели → узнали»

Минимум два независимых канала:

| Канал | Роль |
|---|---|
| **stdout / syslog** → ваш сбор логов с ноды (он уже должен переживать 1 ЦОД, если платформа живая) | Переживает смерть Sidekick |
| **http_output** → Falcosidekick (JSON) | Маршрутизация в SIEM, webhook, опционально Kafka |

Прод-HTTP:

- `json_output: true`;
- `http_output.url` = **https://** Sidekick с валидным сертификатом (не self-signed);
- на Sidekick: `tlsserver.deploy=true`, проверка клиентских сертификатов по возможности (mTLS есть в Falcosidekick);
- NetworkPolicy: поды Falco только на порт Sidekick; Sidekick не LoadBalancer в интернет.
- Sidekick **≥ 2**, PDB `minAvailable: 1`, размазать по зонам/ЦОДам.
- Quickstart-пример оператора с `url: http://sidekick:2801` — **не копировать в прод**.

Опционально: выход Falcosidekick в **отдельный** топик вашей Kafka (TLS + ACL, не бизнес-топики). Это стык с event-шиной, не замена SIEM. Сам Falco 0.44 **не имеет** встроенного Kafka producer; gRPC output в 0.44 **удалён** — старые схемы «читаем Falco по gRPC» надо ломать и переводить на HTTP/Sidekick.

`output_timeout`: слишком маленький — потеря алертов при лаге; слишком большой — Falco тормозит разбор syscalls → дропы. Значение подбирать замером, не гаданием. В примере оператора фигурирует `2000` (мс) как иллюстрация Config CR, не как закон.

#### Производительность под нагрузку (когда цифры появятся)

Порядок, не гадание:

1. Включить metrics snapshot / Prometheus scrape (официальный блок Metrics). Смотреть `scap.n_drops`, `scap.evts_drop_rate_sec`, `falco.evts_rate_sec`, CPU пода.
2. Если дропы: сначала **сузить правила и syscalls** (`base_syscalls` + `repair: true` как официальный рычаг минимума для state engine), потом увеличивать буферы.
3. Для modern eBPF официальный troubleshooting предлагает *эксперимент*: `modern_ebpf.buf_size_preset` **6 или 7** и `cpus_for_each_buffer` **4 или 6** на крупных машинах. Это не гарантия, это стартовая ручка. Больше буфер = больше RAM на каждой ноде (× число буферов).
4. Не ставить на одну ноду второй syscall-агент «для надёжности».
5. Не ждать, что добавление реплик Falco на той же ноде поможет: второй процесс удвоит работу ядра, не разделит её.
6. Шумные пулы (брокеры Kafka) — отдельные замеры. Если дропы неустранимы на 128 CPU при >3k events/s на ядро — это ограничение, которое документация признаёт; тогда либо слабее охват syscalls, либо смириться с % дропов на *этом* пуле и не врать себе в SLA.

`syscall_event_drops.actions`: в проде **не** оставлять пустым/`ignore`. Практичный набор: `log` + `alert`. Действие `exit` превращает перегруз в **гарантированную** слепоту до рестарта пода — обычно хуже, чем алерт «мы слепнем».

#### Безопасность прода (без этого кластер не считается настроенным)

Три слоя:

1. **Сам агент не дырявый** — least privilege, нет privileged без нужды, нет публичного UI, pin образов, внутренний registry, read-only rootfs где возможно.
2. **Канал алертов закрыт** — TLS (валидный cert), лучше mTLS, ACL на топик Kafka если используете, секреты не в Git.
3. **Правила и данные** — cmdline может содержать ПДн/секреты; политика хранения алертов и маскирование — вопрос 152-ФЗ, не «включим JSON». Least privilege на то, кто читает логи Falco.

Плюс:

- отдельный namespace, RBAC: разработчикам приложений не нужен `get secrets` в `falco`;
- не давать `cluster-admin` сервисному аккаунту оператора сверх того, что ставит чарт (чарт ставит ClusterRole — ревьють дифф при апгрейде);
- аудит изменений `Rulesfile`/`Config` (GitOps);
- ротация сертификатов Sidekick;
- не публиковать Falcosidekick UI наружу; если UI нужен — SSO, не basic из демо.

##### Сильные / слабые стороны выбранной ИБ-схемы (DaemonSet eBPF + HTTPS Sidekick + правила overlay)

| Сильное | Слабое |
|---|---|
| Штатный CNCF-путь, modern eBPF без сборки kmod | Агент всё равно видит всю ноду; компрометация агента = компрометация наблюдаемости |
| Capabilities вместо полного privileged на ядрах ≥ 5.8 | На старых ядрах откат на kmod = полный privilege |
| Два канала алертов переживают смерть Sidekick | TLS с запретом self-signed требует нормальный PKI |
| Правила декларативно через Operator | Ошибка в overlay может заглушить детект или заспамить SOC |
| Не ГОСТ | Если ИБ потребует СКЗИ на канал — vanilla Falco `http_output` это не закроет |

#### Kubernetes-специфика прода

- Operator: **≥ 2 реплики** Deployment + PDB; иначе выкат оператора = риск застрявших CR. На работу уже запущенного Falco краткий простой оператора обычно не влияет.
- Не удалять `Falco` CR раньше артефактов: документация оператора — сначала `Rulesfile`/`Plugin`/`Config`, иначе finalizer sidecar повиснет.
- Ресурсы: requests по замеру; **limit CPU слишком жёсткий → дропы**. Memory limit с запасом под буферы eBPF и таблицы процессов.
- Не ставить Falco в Guaranteed с лимитом CPU в 50m «чтобы не мешал» — он начнёт лгать.
- Образы только по digest или неизменяемому тегу 0.44.1; драйвер userspace и kernel **одной** линии (0.44 userspace несовместим с драйвером 0.43 — breaking change 0.44.0).

#### Порядок вывода в прод (этапы, не команда за командой)

1. Снять версии K8s и ядер (BTF/ringbuf) **во всех ЦОДах и пулах**.
2. Решить A vs B (один кластер / три).
3. Поднять Operator v0.4.1 (или Helm 9.1.0), pin Falco 0.44.1.
4. DaemonSet + modern_ebpf + container plugin + k8smeta, ещё **без** боевого шума в SOC (выход в staging-канал).
5. Включить метрики и syscall_event_drops.
6. Прогнать event-generator / контролируемый exec. Проверить доставку.
7. Включить TLS Sidekick, 2+ реплики, NetworkPolicy, второй канал (логи).
8. Собрать неделю шума на препроде, написать exceptions, **потом** цеплять on-call.
9. Нагрузить препрод (хотя бы соседство с тестовым Kafka) и снять дропы. Поджечь буферы/правила.
10. Учение «ЦОД/зона недоступна»: ноды живых зон всё ещё шлют алерты; Sidekick не единственная точка в мёртвой зоне.

Без пунктов 8–10 у вас нет runtime security, есть DaemonSet.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | DaemonSet на **всех** Linux-нодах с нагрузкой; tolerations; низкий maxUnavailable; Sidekick ≥2 в разных зонах/кластерах; запасной канал логов; переживание 1 ЦОДа на *живых* нодах, не «кворум Falco» |
| Производительность / масштаб | Не требуется | Масштаб = число нод; метрики дропов; буферы и `base_syscalls` по замеру; не второй агент на ноду; шумные пулы мерять отдельно |
| Безопасность | HTTP только в изоляции | modern_ebpf least privilege; pin 0.44.1; HTTPS с валидным cert; нет публичного UI; overlay правил; секреты не в git; NetworkPolicy |

**Не готов к проду**, если: Deployment вместо DaemonSet для syscalls; нет container plugin; `latest` в проде; PLAIN HTTP Sidekick на общей сети; нет tolerations на Kafka-ноды; `syscall_event_drops: ignore`; единственный выход — UI; Operator на K8s &lt; 1.29 «как в гайде»; ядро без BTF, а в конфиге modern_ebpf «надеемся»; ждут, что Falco *остановит* атаку.
