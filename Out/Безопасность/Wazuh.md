# Wazuh 4.14.7 — развёртывание и настройка

Версия ПО: **Wazuh 4.14.7** (релизная дата 29 июля 2026; на дату подготовки документа это последний стабильный патч линии 4.14).  
Документация: https://documentation.wazuh.com/current/  
Образы: `wazuh/wazuh-manager:4.14.7`, `wazuh/wazuh-indexer:4.14.7`, `wazuh/wazuh-dashboard:4.14.7`, `wazuh/wazuh-agent:4.14.7`.  
На Kubernetes официальный путь: репозиторий `wazuh/wazuh-kubernetes`, тег **`v4.14.7`**, установка через Kustomize (`envs/eks/` или `envs/local-env/`). Отдельного Helm-оператора у вендора в этом гайде нет.

Этот текст — не мануал «скопируй и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Wazuh **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API). Ниже — как поставить SIEM/XDR-платформу на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это не замена WAF, NetworkPolicy, Falco и не «кнопка безопасность включена».

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **SIEM** | Система, куда складывают security-события, ищут по ним и дежурят. В Wazuh эту роль закрывают **server + indexer + dashboard**. |
| **XDR** | Маркетинговая рамка вендора: не только логи, но ещё FIM, SCA, уязвимости, реакция на хосте. Не путать с «серебряной пулей». |
| **Wazuh agent** | Программа на наблюдаемой машине (или в поде). Собирает логи, следит за файлами, шлёт события на server по зашифрованному каналу. |
| **Wazuh server (manager)** | Мозг анализа: декодирует события, применяет правила, управляет агентами. Может быть кластером **один master + N worker**. |
| **Master (server cluster)** | Единственный управляющий узел server-кластера: регистрация агентов (`authd`), эталон правил/ключей, API управления. **Второй master штатно нельзя.** |
| **Worker (server cluster)** | Узел, который принимает события агентов и анализирует их. Масштаб анализа = число worker'ов + балансировщик. |
| **Enrollment / authd** | Первичная регистрация агента: агент получает уникальный ключ. Слушает порт **1515**, живёт на **master**. |
| **Agent connection** | Постоянный канал событий уже зарегистрированного агента. По умолчанию **TCP 1514**. |
| **Cluster key** | Общий секрет 32 символа: им шифруется общение master↔worker по порту **1516**. Это корневой секрет кластера, не «просто строка в YAML». |
| **Wazuh indexer** | Поисковый движок на базе OpenSearch: хранит и ищет алерты. Отдельный кластер, не путать с server-кластером. |
| **Cluster-manager (indexer)** | Узел indexer, который ведёт состояние кластера (кто какие шарды держит). Выбирается голосованием среди *eligible* узлов. |
| **Shard / replica** | Индекс режут на куски (**primary shards**) и делают копии (**replicas**). Без replica падение узла = дырка в индексе. Число primary задаётся **при создании** индекса; потом только re-index. |
| **Filebeat** | Программа на каждом Wazuh server: читает JSON-алерты и по TLS отдаёт их в indexer на **9200**. |
| **Wazuh dashboard** | Веб-UI. Ходит в indexer (поиск) и в API master (агенты, конфиг). По официальному K8s-гайду **stateless** (Deployment). |
| **All-in-one** | Server + indexer + dashboard на **одной** машине. Лаборатория / маленький стенд, не прод на 3 ЦОДа. |
| **FIM (File Integrity Monitoring)** | Слежение: файл создали/изменили/удалили, кто и когда. На шумных каталогах Kafka/Java даёт лавину. |
| **SCA** | Проверка «настроен ли хост по CIS-бенчмарку». Не детект атаки в момент T, а оценка конфигурации. |
| **Active Response** | Автоответ агента: блокировать IP, убить процесс, удалить файл. Без процесса ИБ это способ уронить интеграцию с госслужбой. |
| **ISM** | Политики жизни индексов: через N дней удалить/сжать. Без этого диск indexer съест «терабайты» сам. |
| **APS** | Alerts per second — ориентир вендора для оценки диска, не ваш замер. |
| **Load balancer** | TCP-балансировщик перед 1514/1515. Официальная рекомендация для агентов: агент знает один адрес, а не список всех worker'ов. |
| **HAProxy helper** | Опция на **master**: сам двигает бэкенды HAProxy, когда worker'ы появляются/пропадают. HAProxy при этом — **отдельное** ПО. |
| **CTI** | Публичный сервис угроз Wazuh (уязвимости/CVE). Модуль Vulnerability Detection на него завязан. |
| **PVC / RWO** | Диск пода в Kubernetes, который можно отдать только одному поду. Manager и indexer без постоянного диска теряют данные при рестарте. |
| **vm.max_map_count** | Лимит ядра Linux на число mmap. Indexer официально требует **≥ 262144**, иначе падает. |
| **Yellow / red cluster** | Состояние indexer: yellow = не все replica на месте, поиск ещё идёт; red = не хватает primary — часть данных недоступна. |

## Основные элементы системы и зависимости

### Что входит в Wazuh 4.14.7 (это одно ПО из четырёх ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Agent** | Сбор с endpoint | По числу машин/нод (DaemonSet или пакет на VM) |
| **Server (manager)** | Анализ, правила, управление агентами | Горизонтально: **worker'ы**. Master всегда **один** |
| **Indexer** | Хранение и поиск алертов | Горизонтально: ноды OpenSearch + шарды/реплики |
| **Dashboard** | UI | Несколько реплик Deployment на тот же indexer; официальный манифест ставит **1** |

Плюс на каждом server: **Filebeat** (в образе manager). Без него алерты есть в файлах manager, но dashboard их не увидит.

### Официальные порты (менять можно, но это контракт сети)

| Компонент | Порт | Назначение |
|---|---|---|
| Server | **1514/TCP** | События агентов (UDP 1514 по умолчанию выключен) |
| Server | **1515/TCP** | Регистрация агентов (`authd`, master) |
| Server | **1516/TCP** | Синхронизация server-кластера. Документация конфигурации: сегмент только для узлов кластера |
| Server | **55000/TCP** | REST API |
| Server | 514 UDP/TCP | Syslog collector (по умолчанию **выключен**) |
| Indexer | **9200/TCP** | REST API (Filebeat, dashboard) |
| Indexer | **9300–9400/TCP** | Общение нод indexer |
| Dashboard | **443** (в K8s-манифесте контейнер слушает **5601**) | UI |

Канал агент↔server по умолчанию: **AES** (блок 128 бит, ключ 256 бит). Blowfish — опция. Filebeat→indexer и dashboard→API — **TLS + логин/пароль**.

### Чего в Wazuh нет (частая путаница)

| Нужно системе | Это не Wazuh | Зачем помнить |
|---|---|---|
| Два активных master server | Нет. Цитата справочника `ossec.conf`: *The current cluster only allows one master node* | Падение ЦОДа с master — это падение **управления и enrollment**, не «выберется другой master» |
| Кворум server-кластера как у Kafka/etcd | Нет. Worker'ы сами инициируют связь с master | Это не Raft. Не проектировать «3 master в 3 ЦОДах» |
| Замена Falco / WAF / NetworkPolicy | Нет | Wazuh смотрит логи, файлы, конфиг, инвентарь. Syscall-поток ядра — у Falco. HTTP-атаки на входе — у WAF |
| Шина бизнес-событий / Camunda / озеро эталона | Нет | Алерты можно *опционально* куда-то ещё слать, но Wazuh не источник истины клиентских данных |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный AES/TLS — не криптография по требованиям КИИ, если ИБ их выдвинет |
| Официальный порог RTT между ЦОДами | Нет | Indexer **умеет** zone awareness для «geographically dispersed zones», но миллисекунд в доке нет |
| Гарантия «терабайты алертов влезут» | Нет | Диск считают от APS × агенты × срок хранения. Нагрузки у вас нет |

### Зависимости окружения (обязательны)

- **ОС центральных компонентов:** 64-bit Linux, x86_64 или ARM64. Вендор перечисляет Amazon Linux 2/2023, CentOS Stream 10, RHEL 7–10, Ubuntu 16.04–24.04. Windows как host для indexer/server **не** в этом списке.
- **Агент:** Linux, Windows, macOS, Solaris, AIX, HP-UX. На Kubernetes — отдельный DaemonSet/sidecar из того же гайда.
- **Kubernetes (если идёте официальным overlay):** работающий кластер; **CSI** для PersistentVolume (для EKS 1.23+ вендор отдельно требует IAM-роль EBS CSI). Минимум ресурсов *чтобы поды стартанули*: **2 CPU / 3 Gi RAM / 2 Gi storage** — это не прод.
- **Диски RWO** под manager и indexer. Shared NFS «один том на три indexer» в манифестах **нет**.
- **`vm.max_map_count ≥ 262144`** на нодах, где живёт indexer (в K8s-манифесте это privileged initContainer `sysctl`).
- **Исходящая сеть до Wazuh CTI**, если включаете Vulnerability Detection. В закрытом контуре модуль либо не работает как в гайде, либо нужна отдельная схема контента — её этот документ не выдумывает.
- **Балансировщик TCP** перед 1514 (и обычно 1515) в проде. Это не часть образа Wazuh.
- **PKI.** Скрипт `generate_certs.sh` в `wazuh-kubernetes` делает **self-signed**. Для API вендор прямо советует свой доверенный сертификат.

### Как Wazuh стыкуется с вашей архитектурой

```
Ноды / VM (микросервисы, Kafka, Camunda, интеграционный API, Linux/Windows)
        │  агент (логи, FIM, SCA, инвентарь)  или syslog без агента
        ▼
   TCP 1514 ──► Load balancer ──► Wazuh server workers
   TCP 1515 ──► (enrollment)  ──► Wazuh server master   (один)
        │
        │  Filebeat, TLS :9200
        ▼
   Wazuh indexer cluster (алерты, поиск)
        ▲
        │  UI / API
   Wazuh dashboard
```

Wazuh **не** участвует в event-sourcing и **не** ходит в госслужбы вместо интеграционного API. Он наблюдает хосты и (по желанию) принимает syslog с сетевых коробок. Пересечение с уже описанным Falco: оба могут кричать про «shell в контейнере» / аномалии на ноде — это два слоя, не дубль «поставили одно — второе не нужно».

## Краткие вводные

### Зачем вам Wazuh в этой архитектуре

У вас Kubernetes, много сервисов, Kafka, процессный движок, интеграции с госслужбами, ожидание непрерывной работы. Типичные дыры, которые WAF и Falco **не** закрывают сами:

1. «Что случилось на Windows-бастионе / на VM вне K8s / в логах приложения» — единый разбор в одном UI.
2. Целостность конфигов и ключей на диске (FIM), а не только syscall в момент записи.
3. «Нода уехала от CIS» (SCA), уязвимые пакеты, инвентарь.
4. Долгое хранение и поиск алертов (это как раз indexer). Falco без SIEM — JSON на ноде.

Wazuh как раз про это: агент → правила на server → индекс → дашборды/API.

### Как устроена отказоустойчивость (идея, не магия)

Это **два разных кластера** плюс агенты. Путать их — главная ошибка.

**1) Server-кластер (master/worker)**

| Что падает | Что происходит по ролям из документации |
|---|---|
| Один **worker** | Агенты, которые смотрели только на него, отвалятся, пока не переключатся (LB или список серверов в `ossec.conf`). Остальные worker'ы живы. Связь других worker↔master не обязана пострадать: worker сам инициирует соединение. |
| **Master** | Enrollment (`authd`) и управление, завязанные на этот узел, встают. Синхронизация правил/ключей на worker'ы останавливается. Анализ событий — **роль worker**; вендор **не** публикует SLA вида «N часов анализа без master». Это надо подтверждать учением, не слайдом. |
| Весь ЦОД с master | То же + нет API, на который смотрит dashboard (`WAZUH_API_URL` в официальном Deployment указывает на `wazuh-manager-master-0`). UI может открыться к indexer, а управление агентами — нет. |
| Нет LB, агент знает один IP | Падение этого IP = слепые агенты, даже если в кластере ещё есть worker'ы. |

Следствие: HA **приёма событий** = несколько worker + балансировщик (или failover-список на агенте). HA **управления** = живой единственный master (и план, что делать, когда его ЦОД мёртв). Автовыбора нового master **нет**.

**2) Indexer-кластер (OpenSearch)**

| Что падает | Что происходит |
|---|---|
| Одна data-нода при `number_of_replicas: 1` и шардах на разных узлах | Полный индекс ещё доступен (официальный пример на 3 узлах). |
| Одна нода при **0 replica** (дефолт шаблона!) | Неполный индекс. Это **не HA**. |
| Потеря кворума cluster-manager (например 2 из 3 площадок сразу, если eligible-узлы размазаны по одному на ЦОД) | Кластер не выбирает manager — запись/стабильность под вопросом. Пережить **два** ЦОДа на трёх нодах нельзя честно. |
| Filebeat не достучался до 9200 | Анализ на server идёт, поиск в UI отстаёт или дырявится. |

Официально: multi-node indexer — «когда нужны HA и нагрузка». Zone awareness — чтобы replica жила в **другой** зоне, чем primary.

**3) Агент**

Агент падает вместе с нодой — это нормально. Пока нода жива, а путь до 1514 мёртв — на ноде копится очередь (flow control в описании агента), но бесконечный буфер вендор не обещает.

### Как устроено масштабирование

Три независимые оси (официальный текст: server и indexer кластеризуются отдельно):

1. **Больше агентов / больше событий** → больше **worker** + следить за `events_dropped` (`wazuh-analysisd.state`) и `discarded_count` (`wazuh-remoted.state`). Оба должны быть **0**. Иначе — ресурсы или ещё worker.
2. **Больше хранения и поиска** → больше **indexer** (RAM/диск/ноды) + шардная схема + ISM. JVM heap: половина RAM узла, **Xms = Xmx**, в примере вендора 8 ГБ RAM → 4g. Не раздувать «на глаз»: лимит в K8s 2 Gi при `-Xms1g` из overlay — это стенд.
3. **Больше нод Kubernetes** → DaemonSet агентов растёт сам. На центральные компоненты это давит **потоком событий**, не «числом подов бизнес-приложений» напрямую.

«Терабайты в озере данных» сами по себе Wazuh не наполняют. Наполняют: включённые **archives** (все события, не только алерты), широкий FIM, auditd на брокерах Kafka, срок хранения без ISM.

Ориентиры диска **на одного агента за 90 дней** (таблица вендора, не ваш Kafka):

| Что мониторят | APS (оценка вендора) | Indexer | Server |
|---|---|---|---|
| Сервер | 0.25 | 3.7 ГБ | 0.1 ГБ |
| Рабочая станция | 0.1 | 1.5 ГБ | 0.04 ГБ |
| Сетевое устройство | 0.5 | 7.4 ГБ | 0.2 ГБ |

Пример из той же страницы: 80 станций + 10 серверов + 10 сетевых ≈ **231 ГБ** на indexer за 90 дней. Для «огромного объёма» и неизвестной нагрузки это **не** смета, это единица пересчёта, когда появятся APS.

Quickstart all-in-one (до ~100 агентов, 90 дней в индексе):

| Агенты | CPU | RAM | Диск |
|---|---|---|---|
| 1–25 | 4 vCPU | 8 GiB | 50 GB |
| 25–50 | 8 vCPU | 8 GiB | 100 GB |
| 50–100 | 8 vCPU | 8 GiB | 200 GB |

Распределённая установка, **рекомендации на узел** (не «на весь прод»):

| Компонент | Минимум | Рекомендовано |
|---|---|---|
| Wazuh server | 2 ГБ RAM / 2 CPU | **4 ГБ / 8 CPU** |
| Wazuh indexer | 4 ГБ RAM / 2 CPU | **16 ГБ / 8 CPU** |

Kustomize `envs/eks` для indexer ставит **500m–1 CPU и 1–2 Gi RAM, 10 Gi PVC** — это патч «чтобы стартануло на EKS», **не** таблица ёмкости. Путать с recommended hardware нельзя.

### Безопасность самого Wazuh

Компрометация manager/indexer = компрометация **карты вашей инфраструктуры**, командных строк, путей, иногда содержимого файлов из FIM. Кластерный ключ и пароль `authd` равносильны возможности принять чужой агент или войти в синхронизацию узлов.

Официальный overlay Kubernetes кладёт в Git-репозиторий **известные** секреты. Их нельзя оставлять в проде:

| Secret | Значение в `v4.14.7` (публичный манифест) |
|---|---|
| `wazuh-authd-pass` | `password` |
| `indexer-cred` | `admin` / `SecretPassword` |
| `dashboard-cred` | `kibanaserver` / `kibanaserver` |
| `wazuh-api-cred` | `wazuh-wui` / `MyS3cr37P450r.*-` |
| `wazuh-cluster-key` | `123a45bc67def891gh23i45jk67l8mn9` (ровно 32 символа) |

Документация K8s буквально говорит: default enrollment password — `password`, лежит в `/var/ossec/etc/authd.pass`. Документация API: сменить дефолтные пароли и **не** оставлять self-signed, если можно иначе.

«Включить Wazuh с `kubectl apply -k` и отдать dashboard в интернет» — это новый attack surface, не контур ИБ.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём self-hosted open-source Wazuh 4.14.7**, не Wazuh Cloud. Облако вендора в вашей схеме с тремя своими ЦОДами не предполагалось.
2. **Прод крутится в Kubernetes**, целевой инсталлятор центральных компонентов — **`wazuh-kubernetes` v4.14.7**. Агенты — пакет на VM **и/или** DaemonSet из того же гайда. Если решите ставить server/indexer «голым» Linux рядом с K8s — правила HA те же, меняется только оркестрация дисков.
3. **Три ЦОДа = три зоны отказа.** Wazuh не делает stretch «из коробки лучше, чем позволяет сеть». Пока RTT неизвестен, честный прод-вариант — либо один логический indexer+server кластер с **замеренным** RTT, либо не растягивать indexer на все три площадки вслепую.
4. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. На трёх cluster-manager нодах (по одной на ЦОД) потеря двух площадок снимает кворум. Вендор это отдельным SLA не обещает — это следует из модели кворума, которую он сам описывает (выборы cluster-manager).
5. **Нагрузка неизвестна** — поэтому **нет** цифры «N worker и M терабайт PVC». Есть сигналы (`events_dropped`, `discarded_count`, состояние indexer yellow/red, heap, диск) и рычаги (worker'ы, железо indexer, правила, FIM, ISM).
6. **Формального SLA на детект нет.** «Система 24/7» ≠ «ни один лог не потерян при пике Kafka». Очереди агента и дропы analysisd — штатный риск, его надо мерить.
7. **SOC/приёмник людей будет.** Dashboard без дежурства и без политики хранения — это поисковик, не безопасность. Wazuh здесь *может быть* SIEM; Falcosidekick в него можно целить отдельно, это не часть дистрибутива Wazuh.
8. **Корпоративный PKI есть или будет.** Self-signed из `generate_certs.sh` — для теста. Прод: свои cert для dashboard, API, indexer, Filebeat.
9. **Штатный ruleset и CIS SCA — старт, не финиш.** На Java/Kafka/Camunda будет шум (перезапись файлов, exec, сеть). Нужен процесс исключений. Active Response в этом документе **не включается** по умолчанию (тот же риск, что у Falco Talon: ложный позитив на интеграционном контуре).
10. **Vulnerability Detection в закрытом контуре может быть выключен**, пока нет решения по CTI. Не обещать руководству «сканер CVE из коробки» без исходящего доступа.
11. **Тестовый стенд изолирован.** На нём допустимы all-in-one / `local-env` (1 indexer, 1 worker) и дефолтные пароли *внутри песочницы*. В прод их не копируем.
12. **Camunda, Kafka, озеро, интеграционное API** — источники логов и поверхность FIM, не часть Wazuh. Их ноды обязаны иметь агента (или syslog), иначе SIEM слепой ровно там, где деньги и гособмен.
13. **Лицензия.** Центральные компоненты — GPLv2 / Apache 2.0 по quickstart. Отдельного license-server как у SafeLine **нет** — это плюс для закрытого контура.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили Kustomize и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потеря пакетов между ЦОДами** | Indexer-кластер чувствителен к задержке cluster state. Wazuh даёт zone awareness, **не** даёт «можно при 80 мс». Без замера stretch на 3 площадки — лотерея yellow/split. |
| **Один K8s на 3 ЦОДа или три кластера** | От этого зависит, один StatefulSet indexer или три независимых SIEM (три правды — плохо для SOC). |
| **Где живёт единственный master** | Нельзя «по одному master на ЦОД». Нужно явно: в каком ЦОДе master, как агенты и dashboard переживают его смерть. |
| **Число агентов и APS** (K8s-ноды, Kafka, Windows, syslog с сетевых) | Без этого нельзя выбрать диск indexer, число worker, heap. Таблица 3.7 ГБ/сервер — не Kafka с audit. |
| **Срок хранения алертов и 152-ФЗ/КИИ** | ISM, шифрование томов, что писать в FIM (ПДн в файлах!), куда можно выносить cmdline. |
| **Куда смотрит dashboard** (только внутренняя сеть? SSO?) | Публичный 443 с `admin`/`SecretPassword` — инцидент, не «пилот». |
| **Есть ли уже Falco / другой HIDS / auditd** | Два агента на одной ноде — двойной overhead и двойной шум. Нужна матрица: кто за syscall, кто за логи/FIM. |
| **Политика `kubectl exec` / debug в проде** | Правила и SCA либо орют, либо их выключат. Это процесс, не YAML. |
| **StorageClass: локальный SSD vs сеть** | Indexer — I/O машина. Медленный диск = очередь Filebeat = дырки в SIEM при живом анализе. |
| **Исход в интернет (CTI, packages.wazuh.com)** | Закрытый контур: зеркало образов/пакетов, иначе поды не стартанут; VD без CTI — отдельное решение. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **Wazuh 4.14.7** и способ: all-in-one **или** `wazuh-kubernetes` v4.14.7 **или** пакеты на VM. Не смешивать 4.13 indexer с 4.14 manager «на глаз».
2. Сначала **indexer**, потом **server**, потом **dashboard** (порядок installation guide). В Kustomize это один `kubectl apply -k`, но логическая зависимость та же.
3. Выпустить **свои** секреты и сертификаты **до** первого агента в проде. Не применять Git-дефолты.
4. Включить метрики здоровья: `events_dropped` / `discarded_count` = 0; indexer `_cluster/health`; диск и heap.
5. Настроить **шаблоны индексов** (replicas!) и **ISM** **до** боевого потока. Дефолт вендора: *three primary shards and no replicas*. Для кластера из 3 нод это прямое противоречие HA.
6. Поставить агентов (или syslog) и прогнать контролируемое событие (изменение файла из FIM / известный лог). Убедиться, что алерт **доехал до индекса** и виден в dashboard.
7. Только потом — сужение правил, FIM-путей, SCA, интеграции с on-call.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** увидеть агента, алерт, шум штатных правил на ваших образах, понять UI. **Не** цель: доказать, что прод переживёт падение ЦОДа и поток логов Kafka.

Два официальных минимальных пути (выберите один, не оба сразу):

**Путь A — all-in-one Linux** (быстрее понять продукт):

```text
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh && sudo bash ./wazuh-install.sh -a
```

Это server+indexer+dashboard на одном хосте. Вендор: обычно хватает **до ~100 endpoints** и 90 дней индекса. После установки — **отключить репозиторий пакетов**, чтобы случайный `yum update` не разъехал версии (рекомендация quickstart).

**Путь B — Kubernetes `envs/local-env`** (ближе к вашему прод-оркестратору):

- namespace `wazuh`;
- indexer **1** реплика (патч `local-env/indexer-resources.yaml`);
- master 1 + worker **1** (патч `wazuh-resources.yaml`);
- dashboard 1;
- StorageClass под ваш кластер;
- сертификаты скриптом репозитория.

Официальный прогон `get statefulsets` на полном (не local) overlay показывает indexer 3 / master 1 / worker 2 — это уже не «тест без нагрузки», если копировать слепо на ноутбук.

Режим «три indexer на Minikube» для знакомства **не нужен**: создаст ложное чувство HA и сгорит по RAM.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Replica indexer | 0 (и 1 узел) | Иначе yellow на одном поде. Вендор: на single-node replicas **ставить 0** |
| Worker'ы | 1 | Нет требования пережить выкат |
| PKI | self-signed | Иначе команда утонет в сертификатах раньше, чем в правилах |
| Пароли overlay | можно оставить дефолт **только в изолированной сети** | На тесте важнее контур данных, чем парольная политика — но в чек-лист прода их не переносить |
| FIM/SCA | минимум путей | Сначала увидеть реальный шум |
| CTI / VD | можно выключить | Часто нет интернета со стенда |
| CPU/memory limits | как в `local-env` | Не цель — ёмкость |

#### Чего на тесте **не** стоит упрощать

- Версия **4.14.7** на всех четырёх ролях (агент не старше/младше manager без чтения upgrade guide).
- Хотя бы один агент, который шлёт не «пусто». Проверка: файл из FIM или лог приложения → документ в `wazuh-alerts-*`.
- Понимание, что **archives** (все события) на тесте включать «из любопытства» опасно: диск и шум, привычка, которую утащат в прод.
- Запомнить: `ossec.conf` master **не** синхронизируется на worker автоматически. Даже на тесте с 1 worker это ловушка, когда начнёте второй узел.

#### Сильные стороны такой схемы

- Поднимается за часы (all-in-one — быстрее).
- Совпадает с официальным quickstart / local-env.
- Дешево показывает шум правил на *ваших* Java/Kafka логах.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет доказанной ёмкости indexer, нет LB.
- Успешный алерт на простой ноде **не** доказывает, что analysisd не будет дропать события с брокерного узла.
- Дефолтные пароли и LoadBalancer в примере K8s приучают «открыть и зайти». В инциденте нужен закрытый UI и RBAC, не `admin`/`SecretPassword`.

Практическая рекомендация: препрод = маленький **прод-профиль** (3 indexer, 1 master + ≥2 worker, свои секреты, replica шардов ≥ 1, ISM, агент на tainted-нодах), даже без боевого трафика.

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер на worker под терабайты озера» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Wazuh не выбирает за вас «один Kubernetes или три». Он плохо переживает **три независимых SIEM** (три индекса, три набора агентов, три правды для SOC) и плохо переживает **слепой stretch** indexer.

**Вариант A — один Kubernetes на 3 ЦОДа (зоны), один Wazuh.**

- Один overlay: indexer StatefulSet **3** (как в базовом манифесте; дальше можно больше data-нод, но **нечётное** число cluster-manager).
- Topology spread / anti-affinity: **не класть все replica indexer в один ЦОД**.
- Server: **1 master** (явно прибить к зоне/ЦОДу с лучшей связностью и процедурой восстановления) + **worker'ы ≥ 2**, лучше с размазыванием по зонам.
- Перед 1514 (и 1515, если enrollment идёт через тот же VIP) — **TCP LB** в каждой зоне или городской LB. Официальная рекомендация: агенты смотрят в LB, не в список подов.
- Dashboard: официально stateless → в проде **≥ 2** реплики Deployment + anti-affinity, хотя вендорский YAML даёт `replicas: 1`. Один под UI — SPOF **просмотра**, не детекта.

**Вариант B — три изолированных Kubernetes.**

Центральные компоненты Wazuh **не стоит** копировать «по кластеру как DaemonSet Falco». Falco — агент на ноде. Wazuh server/indexer — **общая** система.

Рабочие подварианты B:

- **B1.** Агенты во всех трёх кластерах → **один** server+indexer (в одном кластере или на VM рядом). Нужен сетевой путь 1514/1515/55000 и, если indexer в другом кластере, 9200 только из Filebeat, не с мира.
- **B2.** Три полных Wazuh — только если SOC готов склеивать три индекса. Обычно это хуже.

**Пока топология K8s не зафиксирована, нельзя честно выбрать A или B1.** Дальше — общее; расхождение в том, где стоят StatefulSet'ы и как агент находит VIP.

##### Сильные / слабые стороны (A, один кластер на 3 зоны)

| Сильное | Слабое |
|---|---|
| Один ruleset, один индекс, один SOC | RTT между ЦОДами бьёт по indexer cluster state |
| Worker'ы и шарды можно размазать зонами | Ошибка в правилах/секрете сразу везде |
| Официальный K8s overlay почти про это | Master всё равно один: зона master — слабое место управления |
| Zone awareness в доке indexer прямо про несколько зон | Forced awareness при нехватке диска оставляет кластер yellow, пока мёртвая зона не встала |

##### Сильные / слабые стороны (B1, агенты везде, мозг в одном месте)

| Сильное | Слабое |
|---|---|
| Indexer не обязан ходить по 9300 между ЦОДами | Путь агентов до 1514 пересекает ЦОДы: RTT и разрыв канала |
| Проще кворум indexer (все ноды «дома») | Падение ЦОДа с мозгом = нет SIEM для всех трёх площадок |
| Меньше сюрпризов OpenSearch | Нужен очень явный DR: как поднять master/indexer на другой площадке **с дисками** |

##### Слабое место любого stretch без замера RTT

Документация Wazuh **не задаёт** порог задержки. Утверждение «3 ЦОДа в одном городе, значит indexer можно размазать» — **непроверенное**. Городская сеть бывает и 0.5 мс, и «через кривой firewall 40 мс с потерями». Это надо измерить на портах **9300** (indexer) и **1516** (server cluster) до закупки схемы.

#### Indexer (ядро отказоустойчивости *данных* SIEM)

Минимум для «пережить 1 узел / 1 зону»:

- **≥ 3** ноды, все по умолчанию master-eligible+data, как в манифесте `replicas: 3` (комментарий вендора: *3 master nodes*).
- Шаблон индексов `wazuh-alerts-4.x-*`: **не** дефолтные 3 primary / **0 replica**. Для 3 нод вендор сам формулирует правило: число primary ≈ число нод; для HA — **хотя бы 1 replica**. Пример в доке: 0 replica → при падении узла индекс из 2 шардов; 1 replica → полный индекс; 2 replica → живут даже 2 упавших узла ценой диска.
- **Zone awareness** (`node.attr.zone` + `cluster.routing.allocation.awareness.attributes: zone`), если ноды реально в разных ЦОДах. Forced awareness — только если понимаете yellow при отказе зоны (официальная оговорка).
- При трёх зонах вендор советует **добавлять data-ноды сбалансировано** («if you have three zones, add a data node for each zone»).
- JVM: `Xms=Xmx`, ориентир **половина RAM**, memory lock в Linux-гайде (`bootstrap.memory_lock`); в официальном K8s overlay `bootstrap.memory_lock` как раз **false** и heap **1g** — для прода это надо пересмотреть вместе с requests/limits, а не копировать 2Gi.
- `vm.max_map_count=262144` на **каждой** ноде indexer (и после ребута).
- PVC размер — от APS × retention, не 500Mi из базового YAML и не 10Gi из EKS-патча «как есть».
- ISM: вендорский пример retention **90d** для алертов. Ваш срок хранения — решение ИБ; без политики диск вырастет независимо от «терабайт озера».
- **Не включать archives** в прод, пока нет отдельной ёмкости и причины «хранить всё, включая не-алерты».

**Слабое место:** дефолтный шаблон без replica + overlay с 10Gi — выглядит как кластер, ведёт себя как один диск с тройной точкой отказа по данным.

#### Server-кластер (ядро отказоустойчивости *анализа*)

- Ровно **один** master. В `<nodes>` списка master'ов официально должен быть **один** элемент; остальные игнорируются.
- Worker'ы: старт как в полном K8s overlay — **2**; дальше — по `events_dropped` / `discarded_count`.
- `ossec.conf` на worker **копировать руками** (или своим GitOps) после изменений на master. Синхронизируются ключи агентов, кастомные rules/decoders, CDB, SCA, группы — **не** весь `ossec.conf`.
- Порт **1516** только между узлами server. Справочник конфигурации кластера: изоляция 1516 — требование модели безопасности, не опция. Cluster key — как root.
- Агенты: **LB + leastconn** (HAProxy в гайде) или список `<server>` failover. Рекомендация вендора — LB, чтобы новый worker не требовал правки всех агентов. HAProxy helper — опция **на master**, сам HAProxy всё равно нужен.
- Enrollment (1515) лучше не торчать в интернет: пароль из overlay известен всему GitHub. В проде — длинный `authd.pass` или (лучше) enrollment с проверкой сертификата агента (`ssl_agent_ca`); дефолт `<use_password>no</use_password>` в эталонном `ossec.conf`, а K8s overlay как раз сажает пароль `password`.
- `priority`/ресурсы worker: жёсткий CPU throttle → дропы analysisd. Те же грабли, что у Falco с cgroup.

Падение master: закладывайте runbook. Официально новый master **сам не выбирается**. Восстановление = поднять тот же StatefulSet с PVC (или процедура смены роли, которой нет в этом тексте, потому что вендор не даёт «click failover»). Не обещать руководству «как у etcd».

#### Агенты на Kubernetes и рядом

- Для нод кластера — **DaemonSet** из документации 4.14.7, с enrollment на 1515 и событиями на VIP 1514. Имя агента = `spec.nodeName`, чтобы ноды не сливались в одного агента.
- Docker-документация честно пишет: агент **в контейнере без доступа к хосту хост не мониторит**. DaemonSet без hostPath/`/var/log`, `/proc` и т.п. — декорация. Это не «поставили YAML — покрыли Kafka».
- Windows-ноды / VM вне K8s — пакет агента, не DaemonSet.
- **Tolerations** на Kafka/Camunda/control-plane — иначе слепые самые важные машины (как у Falco).
- FIM: не вешать на data-dir брокера и транзакционные логи «всё подряд». Иначе APS взорвётся, а смысл утонет.
- Active Response по умолчанию **выкл** для интеграционного контура.

Официальный Docker-агент (`wazuh/wazuh-agent:4.14.7`) годится для syslog-коллектора, не как замена host IDS.

#### Dashboard и доступ людей

- Не LoadBalancer из примера в интернет.
- Свои сертификаты; first-login warning про untrusted CA на тесте — в проде недопустим как норма.
- Сменить `wazuh` / `wazuh-wui` / `admin` (документация API: смена `wazuh-wui` ломает связь dashboard, надо обновить конфиг UI).
- RBAC API: least privilege, не все с правами администратора. Режим *white* (deny by default) существует в модели RBAC — включать только когда роли описаны, иначе сломаете эксплуатацию.
- SSO — если есть корпоративный IdP; в 4.14 это отдельная настройка dashboard/indexer, не «галочка в apply -k». Без SSO хотя бы уникальные пароли и аудит входа.

#### Безопасность прода (без этого кластер не считается настроенным)

Три слоя:

1. **Секреты и идентичность** — все пять overlay-секретов заменены; cluster key 32 символа с энтропией; authd не `password`; образы по тегу **4.14.7** (лучше digest) из **вашего** registry.
2. **Сеть** — 9200, 9300, 1516, 55000 не с мира; 1514/1515 только от агентов/LB; NetworkPolicy; 1516 в отдельном сегменте.
3. **Данные** — TLS везде по цепочке Filebeat/indexer/dashboard/API; диски PVC шифровать средствами платформы (в самом Wazuh at-rest encryption «ГОСТ-кнопки» нет); политика: что FIM и логи приложений могут содержать ПДн.

Плюс:

- после установки **выключить** автообновление репозитория Wazuh (официальный совет: случайный апгрейд ломает контур);
- GitOps на rules/decoders, выкат только через master;
- бэкап PVC indexer **и** `/var/ossec` master (ключи агентов!). Потеря ключей = пере-enrollment флота;
- не публиковать indexer API «для удобства Grafana» без отдельного read-only и TLS;
- ревью ClusterRole/привилегий initContainer `sysctl` (privileged) — это осознанный долг K8s-схемы вендора.

##### Сильные / слабые стороны выбранной ИБ-схемы (K8s overlay 4.14.7 + LB + свои секреты + replica шардов)

| Сильное | Слабое |
|---|---|
| Один вендорский стек SIEM+агент, GPL, без облачной лицензии | Известные дефолтные пароли в публичном репо — цена ошибки «как в гайде» |
| Индексатор умеет зоны и replica | Server master — единая точка управления; 1516/cluster key = полный доступ к кластеру |
| Агент мультиплатформенный (в отличие от Falco) | Агент в K8s легко поставить «для галочки» без host visibility |
| Filebeat→indexer уже TLS | Self-signed скрипт; API по умолчанию сам генерит self-signed |
| Горизонталь worker + горизонталь indexer разделены | Два кластера надо эксплуатировать как два продукта (OpenSearch + OSSEC-потомок) |
| Не ГОСТ | Если ИБ потребует СКЗИ — vanilla AES/TLS это не закроет |

#### Kubernetes-специфика прода

- Тег репозитория **`v4.14.7`**, не `main` (на `main` уже мелькают образы другой линейки).
- Manager и indexer — **только StatefulSet + PVC**. Deployment для них = потеря идентичности и диска.
- Dashboard — Deployment, можно поднять реплики; это не кластер с кворумом.
- Минимум **двух worker-нод K8s** в гайдах часто всплывает из-за podAntiAffinity — иначе поды indexer/manager не разъедутся.
- CSI обязателен. Без динамических PVC overlay не о том.
- Ресурсы EKS-патчей **не копировать в прод как capacity plan**. Сверять с таблицей recommended hardware и со своими APS.
- Rolling update StatefulSet indexer: по одному поду. Пока под вниз — полагаетесь на replica шардов. Без replica выкат = деградация поиска.
- PDB: для StatefulSet имеет смысл `minAvailable` так, чтобы не убить сразу 2 из 3 indexer.
- Агенты: отдельный манифест DaemonSet, его **нет** внутри базового `envs/eks` «центра». Центральный стек ≠ покрытие нод.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Indexer ≥3, **replica ≥ 1**, zone awareness если ноды в разных ЦОДах; server 1 master + ≥2 worker + LB на 1514; переживание **1** ЦОДа по данным и приёму событий; отдельный runbook на смерть master (второго master нет); dashboard не единственная точка «узнали» (есть API/поиск indexer и on-call) |
| Производительность / масштаб | Не требуется | Worker'ы по `events_dropped=0`; indexer по heap/диску/APS; ISM; не archives «на всякий случай»; ресурсы не из 2Gi EKS-патча; шумные пулы (Kafka) мерять отдельно |
| Безопасность | Дефолт паролей только в изоляции; UI не с мира | Смена всех overlay-секретов; PKI; 1516/9200/55000 закрыты; pin 4.14.7; RBAC; FIM не пылесосит ПДн без политики; без публичного dashboard; репозиторий пакетов выключен после установки |

**Не готов к проду**, если: all-in-one на три ЦОДа; один indexer без replica; дефолт `password` / `SecretPassword` / cluster key из Git; master «для HA» в трёх экземплярах; агенты без LB и без failover; DaemonSet агента без видимости хоста; `latest`; dashboard из LoadBalancer в интернет; нет ISM при «терабайтах»; ждут, что Wazuh *остановит* атаку как WAF; ждут, что Wazuh заменит Falco; RTT не мерили, а indexer растянули на 3 ЦОДа; учение отказа master/зоны не делали.
