# Falco 0.44.1 — термины и сокращения

Словарь к файлу `Falco.md`. Список линейный, не таблица. Сверху — слова, без которых не читаются остальные. Аналогий нет: только что это делает в коде и на диске.

---

**Процесс** — запущенная программа в ОС: память, потоки, открытые файлы. Userspace Falco — процесс `falco`: читает события от драйвера, применяет правила, пишет алерты. Агент с доступом к обращениям программ в ядро на всей ноде видит аргументы командной строки и пути; компрометация агента = компрометация наблюдаемости.

**Файл / каталог на диске** — конфиг `falco.yaml` (драйвер, выходы, буферы, плагины, метрики), файлы правил YAML либо пакеты правил в registry (OCI). Хостовые `/proc` и сокеты runtime контейнеров монтируют в под с ноды.

**HTTP** — запросы с методом и телом. Алерты в прод часто уходят JSON POST на отдельный приёмник (`http_output`, Falcosidekick). Самоподписанный / невалидный сертификат для `http_output` Falco **не принимает**. Выход по gRPC в 0.44 **удалён**.

**TCP-порт** — сокет приёмника алертов (в примерах оператора у приёмника фигурирует 2801). Съём обращений в ядро идёт на ноде локально, без клиентского порта «Falco API».

**TLS / HTTPS** — шифрование HTTP. Канал Falco→приёмник и приёмник→хранилище событий — с **валидным** сертификатом корпоративного PKI. TLS с сертификатом с обеих сторон (mTLS) есть в Falcosidekick. ГОСТ / СКЗИ в штатном `http_output` нет.

**Секрет** — токен, ключ, пароль в аргументах процесса или в файле. Алерт Falco может их процитировать; кто читает логи агента — вопрос RBAC и срока хранения, не «JSON как есть».

**ЦОД** — отдельная площадка. Falco не выбирает лидера между ЦОДами: ноды мёртвого ЦОДа просто не мониторятся. Съём на живых нодах от задержки сети между площадками не зависит.

**RTT** — время туда-обратно. На съём обращений в ядро почти не влияет. Влияет на доставку HTTP-алертов и на сборщик метаданных Kubernetes. Порога в миллисекундах у Falco нет.

**Ядро Linux (kernel)** — код ОС, который выполняет запросы программ: открыть файл, создать процесс, открыть сокет. Falco 0.44 снимает этот поток драйвером. Windows-ноды не покрывает. Архитектуры агента: x86_64, ARM64.

**Syscall (системный вызов)** — вход процесса в ядро: `open` файла, `execve` процесса, `connect` сокета. Falco читает этот поток. Запретить syscall он не может (это seccomp).

**Runtime security** — смотреть, что процесс **уже делает** на живой ноде, не только CVE образа до запуска. Admission и сканер образов (Trivy, Grype) — другой слой и другое время.

**Драйвер (driver / engine)** — код, который снимает syscall и отдаёт их `falco`. В 0.44 осталось два: **modern eBPF** и **kernel module**. Поле конфига: `engine.kind`. Userspace 0.44 **несовместим** с драйвером 0.43 (breaking change 0.44.0).

**eBPF** — программы, которые ядро проверяет (verifier) и выполняет через JIT, без загрузки произвольного `.ko`. Falco кладёт туда щуп на обращения в ядро и пишет события в кольцевой буфер.

**modern eBPF (`modern_ebpf`)** — драйвер по умолчанию. Программа встроена в бинарник Falco, без сборки `.ko` под каждое ядро. Нужны BPF ring buffer и **BTF** (обычно Linux **≥ 5.8**, часть дистрибутивов бэкпортировала раньше). Для производительности: `CONFIG_BPF_JIT` и `net.core.bpf_jit_enable=1`.

**CO-RE** — eBPF-бинарник подстраивается под конкретное ядро по BTF, без исходников ядра на ноде.

**BTF** — таблица типов ядра в `/sys` (и vmlinux). Без BTF modern eBPF не встанет.

**BPF ring buffer** — кольцевая очередь в ядре: syscall-события → userspace Falco. Если ядро не успело записать — **дроп**.

**Kernel module (kmod)** — классический `.ko` в ядре. Работает на более старых ядрах (≥ 3.10), требует **полных привилегий** и загрузки модуля на каждую ноду (часто `falco-driver-loader`). Least-privilege mode kmod **не умеет**. Только для нод, где modern eBPF физически не встаёт.

**Legacy eBPF** — старый eBPF-проб. **Удалён в 0.44.** Оставлять в конфиге нельзя. gVisor-источник в 0.44 тоже убран.

**Tracepoint** — точка в ядре, куда вешают щуп. Два syscall-агента на одни tracepoints усиливают overhead и спорят за буферы.

**Правило (rule)** — YAML: условие на поля события + текст алерта + приоритет. Штатный набор (`falco-rules`, в составе 0.44.0 упоминается 5.1.0) — старт; под Java/Kafka/Camunda нужен overlay исключений.

**Макрос / список (macro / list)** — именованный кусок условия или список бинарников/шеллов, чтобы не копировать в каждое правило.

**Приоритет** — `emergency` … `debug`. Чтобы SIEM и дежурные не тонули в шуме.

**Алерт (alert / output)** — сообщение «правило сработало» (часто JSON). Falco сам **не** убивает под и **не** блокирует syscall. Цитата проекта: monitoring and detection agent.

**Дроп событий (syscall event drop)** — ядро не записало syscall в буфер — Falco его **не увидел**. Слепая зона, не оптимизация. На очень шумных машинах документация допускает неустранимые дропы. Метрики: `scap.n_drops`, `scap.evts_drop_rate_sec`, `falco.evts_rate_sec`. Ориентир troubleshooting (с оговоркой авторов) на одно CPU: `scap.evts_rate_sec / falco.host_num_cpus` обычно терпимо **< ~1–1.5k/s**, часто тяжело **> ~3k/s** — не смета вашего кластера.

**`syscall_event_drops`** — что делать при дропах: минимум `log` + `alert`, не молчаливый `ignore`. Действие `exit` убивает процесс Falco → гарантированная слепота до рестарта пода.

**`kernel_event_counters_enabled`** — включить счётчики событий/дропов для scrape.

**`buf_size_preset`** — размер кольцевого буфера ядро↔Falco. Больше → меньше дропов и больше RAM. Troubleshooting для modern eBPF предлагает эксперимент **6 или 7** на крупных машинах — ручка, не гарантия.

**`cpus_for_each_buffer`** — только modern eBPF: сколько CPU делят один буфер. `1` = буфер на каждое ядро (больше памяти, меньше конкуренции). Эксперимент на крупных машинах: **4 или 6**.

**`base_syscalls`** — какие syscall вообще снимать. Шире набор + больше правил = выше нагрузка. `repair: true` — официальный рычаг минимума syscall для state engine. Сужать правила и syscall **раньше**, чем раздувать буферы.

**Userspace однопоточный** — основной разбор событий в процессе `falco` идёт одним потоком. Широкие правила и лишние плагины создают backpressure → дропы в ядре. Второй процесс Falco на той же ноде удвоит работу ядра, не разделит её.

**Plugin** — расширение: новые поля или другой источник событий (не ядро). Для Kubernetes почти всегда **container**, часто **k8smeta**. Порядок Operator: сначала плагин, потом ruleset — иначе поля `container.*` в правилах мертвы.

**container plugin** — метаданные контейнера (образ, id) через сокеты **containerd / CRI-O / Docker**. Без него штатные правила с `container.*` не работают.

**CRI-сокет** — Unix-сокет runtime на ноде. Без mount в под Falco не видит, какой контейнер сделал syscall.

**k8smeta + k8s-metacollector** — плагин + отдельный Deployment: в алерт попадают pod/namespace/deployment, не только «контейнер на hostname». Детект ядра жив без collector; enrichment деградирует. В quickstart оператора collector **replicas: 1** — SPOF для полей Kubernetes, не для съёма syscall.

**k8saudit** — плагин: события audit.log API-сервера Kubernetes («кто вызвал API»). Штатный DaemonSet смотрит **ядро ноды**, не этот лог. Источник другой, часто другой режим запуска.

**DaemonSet** — по одному поду на каждую ноду. Для syscall-мониторинга это **единственный** правильный режим. Добавили ноды — kubelet сам поставил ещё один агент. «Размазать один агент на три ноды» нельзя: каждый видит только своё ядро.

**Deployment mode** — N реплик обычного Deployment. Для съёма syscall со всех нод **не подходит**. Имеет смысл для плагинных источников (например k8saudit), не для ядра каждой машины. `replicas: 2` на тесте для syscall создаёт ложное чувство HA.

**Tolerations / taints** — без tolerations DaemonSet не встанет на dedicated Kafka, Camunda, control-plane. Эти ноды — постоянная слепая зона. Windows — тоже постоянная слепая зона.

**`priorityClassName`** — приоритет вытеснения. Агент не должен быть первым кандидатом на evict как BestEffort; конкретный class — решение эксплуатации.

**`updateStrategy.maxUnavailable`** — сколько подов DaemonSet можно снять сразу при выкате. Часто 1: на это время нода слепая.

**PDB (PodDisruptionBudget)** — лимит плановых снятий. Для DaemonSet (один под на ноду) классический PDB почти бесполезен; дисциплина в `updateStrategy` и в том, чтобы не drain'ить сразу всю зону.

**hostPath / `HOST_ROOT`** — монтирование `/proc`, сокетов runtime (при kmod — путей загрузки модуля) с ноды в под. Без этого нет контекста процессов и контейнеров. Не монтировать лишнего.

**Least privilege (capabilities)** — не `privileged: true` на весь под, а набор Linux capabilities. Для modern eBPF официальный минимум: `CAP_BPF`, `CAP_PERFMON`, `CAP_SYS_RESOURCE`, `CAP_SYS_PTRACE`; на ядрах без дробных cap ещё `CAP_SYS_ADMIN`.

**cgroup** — лимит CPU/RAM контейнера. Слишком жёсткий CPU limit → дропы (агент лжёт). Memory limit — с запасом под буферы eBPF и таблицы процессов. Guaranteed с 50m CPU «чтобы не мешал» — тот же эффект.

**Falco Operator** — контроллер с CRD `Falco`, `Rulesfile`, `Plugin`, `Config`, `Component`. Рекомендуемый путь на Kubernetes: **v0.4.1** (с v0.4.0 default Falco = **0.44.1**). Чарт оператора на линии — `falcosecurity/falco-operator` **0.3.0**. Требует Kubernetes **1.29+** (native sidecars). Уже запущенный DaemonSet при простое оператора обычно продолжает снимать syscall; ломается выкат правил/конфига. Оператор в проде: **≥ 2** реплики + PDB. Не удалять `Falco` CR раньше артефактов: finalizer sidecar повиснет.

**Artifact Operator** — sidecar в поде Falco: качает правила и плагины. Native sidecars = K8s 1.29+.

**Helm `falco` 9.1.0** — альтернатива оператору, тоже ставит Falco 0.44.1. Если кластер старше 1.29 — этот путь, не Operator.

**Falcoctl** — CLI: ставить/обновлять правила и плагины. На K8s работу часто забирает Artifact Operator.

**OCI-артефакт правил** — правила как образ в registry (`ghcr.io/falcosecurity/rules/falco-rules`), не файл, зашитый в Docker-образ Falco. В проде тег **pin**, не `latest`. Закрытый контур — зеркало registry.

**Image digest / `0.44.1`** — пин образа. `latest` в проде нельзя. Quickstart оператора с `latest` и HTTP — не прод-манифест.

**Falcosidekick** — отдельный Deployment экосистемы: принимает алерты Falco по HTTP и раздаёт в 70+ мест (SIEM, webhook, Slack, опционально топик Kafka). У Falco из коробки: stdout, file, syslog, программа, HTTP. Сам Falco 0.44 **не** имеет встроенного Kafka producer. В примерах оператора Sidekick `replicas: 2`. PDB `minAvailable: 1`, размазать по зонам. URL `http://sidekick:2801` из quickstart в прод не копируют. Не LoadBalancer в интернет.

**Falcosidekick UI + Redis** — веб-просмотр алертов. Удобство, не контур детекта. Redis — ещё одна зависимость. UI наружу не публикуют; если нужен — SSO, не basic из демо.

**`output_timeout`** — сколько миллисекунд Falco ждёт, пока канал алерта примет событие. Маленький — потеря алертов при лаге приёмника; большой — тормозит разбор syscall → дропы. В примере Config CR оператора фигурирует `2000` мс — иллюстрация, не закон.

**`json_output: true`** — алерт в JSON, как ждёт Sidekick.

**Два канала алертов** — stdout/syslog в уже существующий сбор логов ноды (переживает смерть Sidekick) **и** HTTPS на Sidekick. Без приёмника и on-call экземпляр не считается настроенным.

**SIEM** — система, куда складывают security-события и где дежурят. Falco без приёмника — JSON на ноде / в `kubectl logs`. UI Sidekick SIEM не заменяет.

**SOC / on-call / webhook** — люди и канал «проснулись». Неделя шума на препроде → exceptions → потом on-call.

**Falco Talon** — **другой** проект: реакция (убить под, повесить NetworkPolicy). В дистрибутив Falco 0.44.1 **не входит**. В исходном файле kill pod не включают: ложный `exec` в контейнере интеграции роняет обмен.

**seccomp / NetworkPolicy / WAF / firewall** — запрет syscall, TCP в кластере, разбор HTTP на входе, фильтр портов. Falco их не заменяет.

**Слепая зона (blind spot)** — нода/ЦОД, где пода Falco нет, он вытеснен, или дропает события: атака там не детектируется. Выкат DaemonSet и drain зоны — окно слепоты.

**HA** — под на **каждой** Linux-ноде с нагрузкой (включая tainted) + живой канал алертов минимум в двух экземплярах Sidekick + запасной канал логов. Нет кворума и нет «переключения на другой Falco». Падение оператора ≠ падение детекта на уже бегущих агентах.

**SPOF** — единственный Sidekick в одной зоне; единственный metacollector для k8s-полей; единственный выход — UI.

**NetworkPolicy** — поды Falco только на порт Sidekick; Sidekick только в SIEM. Лишний Ingress на UI — поверхность атаки.

**RBAC / ClusterRole** — кто читает логи Falco и правит CR. Разработчикам приложений не нужен `get secrets` в namespace `falco`. Чарт оператора ставит ClusterRole — ревью диффа при апгрейде, не `cluster-admin` сверх чарта.

**GitOps** — выкат `Rulesfile`/`Config` через git, не `vi` на ноде. Иначе три ЦОДа разъедутся.

**cmdline / ПДн / 152-ФЗ / КИИ** — аргументы процесса в алерте могут содержать персональные данные и секреты. Политика хранения и маскирования — ИБ, не «включим JSON».

**event-generator** — официальный способ прогнать контролируемое событие (или свой `kubectl exec sh` в тестовом поде) и проверить, что алерт **доехал** до приёмника.

**`kubectl exec`** — API Kubernetes запускает процесс в контейнере. Штатные правила на shell в контейнере будут орать, если debug в проде норма. Это процесс, не YAML.

**Overlay-правила / exceptions** — свои YAML поверх `falco-rules`: заглушить легитимный exec/сеть Kafka/JVM и отдельно high-priority на интеграционный контур (исходящий не на список ведомств, shell в образе API, запись в TLS-ключи). Ошибка overlay глушит детект или спамит SOC.

**Kafka (топик алертов)** — опциональный выход Sidekick, TLS + ACL, не бизнес-топики. Соседство брокера с агентом на ноде — шум syscall (сеть/диск/fork); «терабайты озера» сами по себе Falco не наполняют.

Источники формулировок: глоссарий и тело `Falco.md`. Новых порогов RTT и размеров диска здесь нет.
