# HashiCorp Vault 2.0.4 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `HashiCorp Vault.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Vault — хранилище секретов и ключей. Ставите **свою** копию Community, не облако вендора и не Enterprise (лицензии в контексте не было).

Версия в этой инструкции: **2.0.4**. Образ: `hashicorp/vault:2.0.4` (зафиксировать digest, не `latest`).  
На Kubernetes — Helm-чарт **hashicorp/vault 0.34.1**. Документация: https://developer.hashicorp.com/vault/docs/

Хранилище — только встроенный Raft. Consul как бэкенд не ставим: это был бы ещё один кластер.

Один Raft, размазанный на несколько дата-центров, здесь **не собираем**. HashiCorp для зон пишет задержку **меньше 8 мс**, но голосование Raft между площадками в этой инструкции запрещено независимо от замера: порты **8200/8201** между дата-центрами не открываем как «один кластер». Community **не** умеет репликацию кластера на другой зал. Три независимых Vault — это три источника правды секретов, не «единые ключи». Поэтому живой кластер — внутри одной площадки. Другие площадки держат **снимки** и восстанавливаются вручную.

---

## О чём эта инструкция молча договорилась

1. **Один живой мозг в одном дата-центре.** Пять (минимум три) голосующих узлов Raft живут **в одной площадке**. Между площадками — только шифрованные снимки, не вторая половина того же кворума. Это тот вариант из исходной развилки, который не зависит от задержки между городами и не требует лицензии Enterprise.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`, если есть). Серверы Vault — только в домашнем.
3. Учебный стенд — закрытая сеть. Shamir и даже HTTP без TLS допустимы **только там**. Доли в git не кладём даже на тесте.
4. Цифр вашей нагрузки нет — нет фразы «хватит N ядер». Ориентир HashiCorp small: 2–4 CPU, 8–16 ГиБ, диск от 100 ГБ — старт, не расчёт запросов в секунду.
5. Два дата-центра: кластер в первом; второй — снимки. Три дата-центра: то же плюс копия снимка в третьем. Третья площадка **не** даёт второго писателя и не даёт репликацию чтений.
6. Растяжка 5 узлов как 2-2-1 по трём залам и путь Enterprise (локальные чтения + тёплая копия) в этой инструкции **не** включаются: для первого нет разрешённого Raft между площадками, для второго нет лицензии. Если лицензия появится — это другой образ и другая операционка, не «галка в values».
7. Терабайты озера в KV не кладём. Автоответ «убить под» к Vault не относится.

---

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** вход приложений (JWT Kubernetes или AppRole), запись ключ-значение, увидеть печать и смену лидера. **Не зачем:** доказывать отказ зала и пик sidecar при массовом рестарте.

### Что должно быть до установки

- Учебный Kubernetes (или kind: понимание, что «не сажать два пода на одну ноду» на одной машине не докажет устойчивость).
- Helm 3.6+.
- Свободное пространство имён; порты 8200/8201 внутри кластера.
- Сеть стенда не торчит в интернет.

Дефолт чарта — **один сервер и файловый бэкенд**. HashiCorp помечает это как предупреждение безопасности. Для «потыкать команду» сгодится. Для «как будем жить в бою» — **нет**. Режим `vault server -dev` в эту инструкцию не входит.

### Установка (Helm HA Raft — основной путь для учёбы)

```bash
helm repo add hashicorp https://helm.releases.hashicorp.com
helm repo update
kubectl create namespace vault
```

Смысл values (не полный боевой файл — сверять с документацией чарта 0.34.1):

```yaml
server:
  image:
    repository: hashicorp/vault
    tag: "2.0.4"
  ha:
    enabled: true
    replicas: 3
    raft:
      enabled: true
      setNodeId: true
injector:
  replicas: 1
```

```bash
helm install vault hashicorp/vault --version 0.34.1 -n vault \
  -f ./vault-ha.yaml
kubectl -n vault rollout status statefulset/vault
```

Файл values — локальная копия блока выше. Тег **2.0.4** в values обязателен: не полагаться на «чарт сам подтянет».

Когда все три пода в `Running`, но ещё запечатаны — `init` **один раз** на первом поде (обычно `vault-0`):

```bash
kubectl -n vault exec -it vault-0 -- vault operator init
```

Доли Shamir и root-токен — людям в сейф, **не** в git, не в общий чат, не в ConfigMap. Затем распечатать **каждый** под (порог K из N долей на каждый рестарт). Присоединение остальных в чарте обычно через повтор join.

Проверка:

```bash
kubectl -n vault exec -it vault-0 -- vault status
```

В выводе: линия **2.0.4**, HA включён, хранилище **raft**, не file. На большинстве узлов распечатано.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| 3 голосующих | да | Увидеть смену лидера; не standalone |
| Shamir | да | Не строить KMS ради песочницы |
| TLS на 8200 | можно отложить **только** в закрытой сети | Иначе PKI раньше политик |
| Injector | 1 реплика | Sidecar на тестовом поде |
| Оператор секретов в Kubernetes | можно не ставить | Сначала API + одна политика + KV |
| Журнал | хотя бы файл | Увидеть, что секрет в логе хеширован |

Чего **не** упрощаем: образ **2.0.4**; `init` один раз; доли не в git; вход Kubernetes с ролью на сервисный аккаунт тестового пода; не класть озеро клиентов в KV.

### Как понять, что стенд живой

1. Статус: 2.0.4, Raft, распечатан.
2. Приложение пишет и читает KV по политике своей роли; root из приложения — отказ (после настройки входа root лучше отозвать и на тесте).
3. Убили под-лидер: кластер выбирает активного, проверка здоровья сходится. Успех трёх подов **не** доказывает бой.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный пример HA-with-raft | Нет автоматической распечатки, нет отказа зала, нет ёмкости |
| Команда видит печать и большинство голосов до боя с KMS | Успешное чтение KV **не** доказывает боевую схему |
| | UI под root приучает кликать секреты |

Перед боем полезен **препрод**: TLS, 3–5 Raft, автоматическая распечатка **или** отрепетированный Shamir, два журнала, задание снимка — в **одном** дата-центре.

---

## Бой: один живой дата-центр, второй — запас из снимка

**Зачем:** пережить отказ **машины или пода внутри домашней площадки** (пять голосующих, пережить два узла; минимум три — пережить один). Отказ **всего дата-центра** = Vault нет, пока не поднимете 3–5 новых узлов на другой площадке, не распечатаете и не восстановите снимок. Часть секретов после последнего снимка можно потерять — интервал и время подъёма нужно замерить и **записать в ожидания руководства**, не прятать за «у нас три дата-центра приложений».

### Почему кластер не растягиваем на несколько дата-центров

Запись в Raft не быстрее, чем подтверждение большинством. HashiCorp для зон требует задержку **меньше 8 мс**. Голосование через город при запрете этих портов — таймауты и ложные выборы, не защита. Пять узлов как 2-2-1 по трём залам переживают **один** зал только если сеть голосования жива; два мёртвых зала из трёх всё равно снимают большинство.

Три Community-кластера «по залу» **без** репликации вендора — три источника правды: политики и секреты разъедутся, единого отзыва не будет. Репликация чтений и тёплая копия есть только в Enterprise: другие образы, другие потоки, это не включается галкой.

### Как расставить в активном дата-центре

Один кластер Community:

- **5** голосующих (официальный идеальный размер, пережить **2** узла внутри площадки). Минимум **3**, если явно принимаете «пережить один узел». Чётные 2/4/6 как цель не использовать: большинство не лучше, сложность лишняя.
- Нечётное число. Anti-affinity: **отдельная нода на каждый под** (5 серверов → не меньше 5 нод пула). Swap на нодах **выключен** (проверить).
- Диск данных + отдельно диск журнала, локальный/зонный, **не NFS**. Под после пересоздания должен найти **свой** том.
- Один лидер; запасные пересылают запросы (Community не обслуживает чтения сама на запасном).
- Клиенты всех площадок в штате ходят на этот кластер по TLS.
- Injector **не меньше двух** реплик webhook (иначе выкат Injector = нельзя создать новые поды с аннотациями).
- Обновление **последовательно**, сохраняя большинство. Не «все сразу». Новые узлы не добавлять пачкой: Autopilot сначала догоняет без голоса. Вычистку мёртвых серверов включить *после* init, иначе мёртвые поды остаются в списке пиров.

**Между площадками — только снимки, не Raft:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: 5 (мин. 3) Raft. Вторая: шифрованные снимки (объектное хранилище / лента), **не** второй кластер-источник правды | Vault нет, пока поднять узлы + распечатать + восстановить снимок. Потеря данных после последнего снимка > 0 |
| **Три** | То же + копия снимка в третьей | То же; третья площадка не даёт второго писателя |

Helm без переопределений (один сервер + файл) в бой **не** идёт.

### Что должно быть до боевой установки

- Kubernetes домашней площадки; класс диска локальный/зонный; объектное хранилище для снимков **есть или будет** и переживает гибель этой площадки.
- PKI для TLS на 8200. Проверка балансировщика: **`/v1/sys/health`**, не «порт открыт». TLS до конца; обрывать TLS на Ingress и дальше открытым текстом HashiCorp для боя не рекомендует.
- NetworkPolicy: клиенты → 8200; узлы Vault ↔ 8200/8201; исходящие только куда надо (KMS, СУБД движка database, каталог пользователей, syslog).
- Решение по распечатке **до** init (таблица ниже).
- Секреты и доли — не в Git.

### Порядок установки в активном дата-центре

1. Пул нод (swap выкл) + класс диска + PKI + способ распечатки.
2. Helm **hashicorp/vault 0.34.1**, образ **`hashicorp/vault:2.0.4`**.
3. Values: HA + Raft, `replicas: 5` (или 3 с принятым риском), диски данных и журнала, TLS, Injector не меньше 2.
4. Дождаться Running → `vault operator init` **один раз**.
5. Раздать доли Shamir **или** ключи восстановления (при автоматической распечатке). Включить вход Kubernetes + политики админов → **отозвать root**.
6. Присоединение через retry_join / Autopilot. Вычистку мёртвых — после init.
7. Два устройства журнала сразу после init, **до** боевых секретов (по умолчанию журнал выключен).
8. Задание/`vault operator raft snapshot save` → шифрованное хранилище в других дата-центрах. Восстановление прогнать на стенде. Автоснимки вендора — **Enterprise**.
9. Одна боевая роль на препрод-поде; проверка Injector. Только потом — Camunda, Kafka, интеграции и ротация паролей БД.

`disable_mlock=true` при Raft — норма чарта; capability IPC_LOCK на дефолтный образ вслепую не вешать (на бинарнике её может не быть, admission отвергнет под).

### Распечатка

Без автоматической распечатки Kubernetes **не** считается готовым к бою: переезд пода = запечатан, пока люди не внесут доли **на каждый** под.

| Механизм | Редакция | Когда |
|---|---|---|
| Облачный KMS | Community и Enterprise | Есть KMS и сеть до него. Учётки не в файле конфигурации открытым текстом |
| HSM PKCS#11 | **Только Enterprise** | Требование средства криптозащиты |
| Transit (другой Vault) | Оба | Свои залы без HSM: маленький кластер только для распечатки. Shamir переезжает туда; его тоже надо уметь открывать |
| Shamir | Оба | Только круглосуточная процедура и разные люди с долями. На бою Kubernetes — слабое место |

Init один раз. Доли и ключи восстановления **не в git**. Все доли в одном сейфе одного админа = один человек = весь контур.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Голосующие | 5 (мин. 3) в **одном** дата-центре | Большинство не зависит от задержки между городами |
| Listener | TLS, не открытый текст на общей сети | Hardening HashiCorp |
| Журнал | не меньше 2 (файл на отдельном томе + syslog/сокет в SIEM) | Некуда писать ни на одно → Vault отказывается обслуживать |
| UI | выкл или только сеть администраторов | Не интернет |
| TTL токенов | короткие | Отзыв при компрометации пода |
| Политики | минимум прав, без широких `*` | Иначе источник ключей = дыра |
| Injector | не меньше 2 | Иначе выкат webhook ломает создание аннотированных подов |
| Оператор секретов в Kubernetes | только вместе с шифрованием etcd | Иначе обошли Vault через API Kubernetes |
| Пользователь в контейнере | не root (официальный образ — пользователь `vault`) | Hardening |

Клиенты (микросервисы, Camunda, интеграционное API) переживают короткую ошибку при смене лидера — повторы в **коде**, не в Helm.

### Как расти, когда появятся цифры нагрузки

1. Замерить входы в секунду, KV, transit, пик Injector при массовом рестарте подов.
2. Упёрлись в лидера — вертикаль (IOPS диска, RAM по small/large). **Ещё голосующие запись не ускоряют.**
3. Чтения в другом дата-центре без езды на лидера — только Enterprise; в этой схеме клиенты едут в домашний зал.
4. Терабайты озера на CPU Vault не давят, пока вы не гоняете их через transit побайтово без кэша в приложении.
5. Ограничение частоты на стороне Vault — защита от своих же клиентов, не замена ёмкости; часть лимитов — Enterprise.

### Проверки, без которых это ещё не бой

1. Версия **2.0.4** на всех голосующих; хранилище raft; TLS. Нет смеси редакций и тегов.
2. Убить лидера: выборы, клиенты живы после повтора запроса.
3. Увести одну ноду: большинство живо, том «свой».
4. Диск журнала 100% на стенде — понять, что API встаёт; мониторинг места обязателен.
5. Восстановить снимок на **чистый** кластер в другом дата-центре хотя бы раз (замер времени).
6. Root из приложения не проходит; доли не в репозитории; суперширокая политика `*` сервисам не выдана.
7. Учение «домашний дата-центр выключен»: подъём по заранее написанному сценарию. Порты Raft между площадками закрыты — и это **ожидаемо**.

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + снимок»

| Хорошо | Плохо |
|---|---|
| Голосование Raft — локальная сеть, нет зависимости от 8 мс между городами | Падение этой площадки = нет секретов ни у кого, пока не восстановите снимок |
| Один источник правды; согласовано с Community (нет репликации кластеров) | Потеря после последнего снимка > 0; время подъёма = ручная распечатка |
| Проще сеть, чем 2-2-1 | Легко забыть, что «три зала приложений» ≠ «три зала Vault» |
| | Клиенты чужих площадок в штате идут через город — TLS и сеть ваши |
| | Нет вендорского DR на потерю города |

**Не готово к бою**, если: дефолтный один сервер и файл; тег `latest`; один узел Raft; растяжка «потому что в доке 8 мс»; три независимых Community как один источник правды; Shamir без сценария на Kubernetes; один журнал на диске ОС; нет снимков вне кластера; открытый listener; root живёт «на всякий случай»; доли в git; учебные values уехали в бой; озеро клиентов в KV; ждут, что 5 подов ускорят запись.
