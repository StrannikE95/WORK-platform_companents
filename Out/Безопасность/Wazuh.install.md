# Wazuh 4.14.7 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Wazuh.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Wazuh — платформа, куда складывают события безопасности с машин и ищут по ним. Ставите **свою** копию, не облако вендора.

Версия в этой инструкции: **4.14.7**. Образы:

- `wazuh/wazuh-manager:4.14.7` — разбор событий и управление агентами (в образе ещё Filebeat, который отдаёт алерты в поиск);
- `wazuh/wazuh-indexer:4.14.7` — хранение и поиск алертов (движок на базе OpenSearch **этого** продукта, не платформенный OpenSearch);
- `wazuh/wazuh-dashboard:4.14.7` — веб-интерфейс;
- `wazuh/wazuh-agent:4.14.7` — программа на наблюдаемой машине.

На Kubernetes — репозиторий **`wazuh/wazuh-kubernetes`**, тег **`v4.14.7`**, Kustomize. Отдельного Helm-оператора у вендора в этом гайде нет. Документация: https://documentation.wazuh.com/current/

Один кластер indexer и разговор master↔worker, размазанные на несколько дата-центров, здесь **не собираем**. Состояние indexer идёт по порту **9300**, синхронизация server — по **1516**. В документации нет цифры «сколько миллисекунд ещё можно». Поэтому живой «мозг» (indexer + master + worker + dashboard) — внутри одной площадки. Другие площадки шлют события **агентами** на адрес этой площадки. Третья площадка не даёт второго master: его штатно нельзя.

---

## О чём эта инструкция молча договорилась

1. **Один живой мозг в одном дата-центре.** Indexer, единственный master, worker'ы и dashboard живут **в одной площадке**. Второй и третий дата-центры — агенты (и бэкап дисков), а не вторая половина того же кластера поиска. Три полных Wazuh без склейки событий = три разных SIEM (три индекса, три правды для дежурных). Так единый разбор не закрыть.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`, если есть). Мозг Wazuh — в домашнем.
3. Учебный стенд — закрытая сеть. All-in-one или `local-env` допустимы **только там**. Пароли из публичного манифеста известны всему GitHub — на тесте можно оставить **только** в песочнице.
4. Цифр вашей нагрузки нет — нет фразы «хватит N worker и M терабайт диска». Есть сигналы (отброшенные события, куча Java, диск) и рычаги.
5. Два дата-центра: мозг в первом, агенты второго смотрят на адрес первого. Три дата-центра: то же плюс агенты третьего. Если у второй площадки нет сети до 1514 — это уже **второй** SIEM, события сами не сольются.
6. Wazuh **не** заменяет WAF, Falco и NetworkPolicy. Агент в контейнере без каталогов хоста хост не видит.
7. Поиск уязвимостей через облако вендора в первом контуре можно выключить. Active Response на интеграционном контуре **выключен**.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** увидеть цепочку «агент → алерт → документ в индексе → экран» и понять шум штатных правил на ваших образах. **Не зачем:** доказывать отказ дата-центра и поток auditd с Kafka.

### Что должно быть до установки

- Linux x86_64 или ARM64 **или** учебный Kubernetes с постоянными дисками.
- Порты 1514, 1515, 443/5601 не торчат в интернет.
- Сеть стенда закрыта.

Два официальных пути — **выберите один**, не оба сразу.

### Установка (путь A — всё на одной машине)

Быстрее понять продукт. Server + indexer + dashboard на **одной** машине. Вендор: обычно до ~100 точек и 90 дней индекса — это не ваш бой.

```bash
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
sudo bash ./wazuh-install.sh -a
```

После установки **отключить репозиторий пакетов**, чтобы случайное обновление системы не разъехало версии. Пакеты линии **4.14.7**.

Открывайте интерфейс с jump-хоста, не выставляйте балансировщик в интернет.

### Установка (путь B — Kubernetes `envs/local-env`)

Ближе к боевому оркестратору. Полный overlay «indexer 3 / worker 2» на ноутбук не копируйте: это уже не «тест без нагрузки».

```bash
git clone -b v4.14.7 --depth 1 https://github.com/wazuh/wazuh-kubernetes.git
cd wazuh-kubernetes
# сертификаты скриптом репозитория (самоподписанные — только стенд)
kubectl apply -k envs/local-env
```

Ожидаемо: indexer **1**, master **1**, worker **1**, dashboard **1**. Класс диска — ваш. Образы проверить: тег **4.14.7**, не `main`.

Порядок зависимости тот же, что в руководстве по установке, даже если Kustomize применяет всё пакетом: **indexer → server → dashboard**. Пока indexer не принимает 9200, Filebeat на manager некуда писать.

На Kubernetes для учёбы один indexer без копий шардов нормален. Этот YAML в бой не копируйте.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Копии шардов indexer | 0 при одном узле | Иначе «жёлтый» кластер. Вендор: на одном узле копии ставить 0 |
| Worker | 1 | Некому балансировать |
| Сертификаты | самоподписанные | Иначе PKI раньше правил |
| Пароли overlay | завод **только в изоляции** | В чек-лист боя не переносить |
| FIM / проверки конфигурации | минимум путей | Сначала увидеть шум |
| Поиск уязвимостей | можно выкл | Часто нет интернета со стенда |
| Архивы всех событий | не включать из любопытства | Диск и привычка в бой |

Чего **не** упрощаем: номер **4.14.7** на всех четырёх ролях; хотя бы один агент, который шлёт не пусто; понимание — файл настроек master **не** копируется на worker сам; веб и базу поиска не открывать в интернет.

Агент: пакет на машину **или** DaemonSet из гайда 4.14.7. Агент в контейнере **без** `/var/log` и `/proc` хоста — декорация.

### Как понять, что стенд живой

1. Версии manager, indexer, dashboard, agent = **4.14.7**.
2. Изменили файл из списка слежения (или пришёл известный лог) — документ появился в индексе `wazuh-alerts-*` и виден на экране.
3. Перезапустили единственный indexer: поиск дырявится. На одном узле без копий так и должно быть.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный quickstart / local-env | Нет балансировщика, нет копий шардов, нет отказа площадки |
| Дешево показывает шум на *ваших* логах | Успешный алерт на простой ноде ≠ анализ под нагрузкой брокера |
| | Заводской пароль `password` приучает открыть экран «как в гайде» |

Перед боем полезен **препрод**: 3 indexer, 1 master + не меньше 2 worker, свои секреты, копии шардов не меньше 1, политика жизни индексов, агент на нодах с taint — всё **в одном** дата-центре.

## Бой: один живой дата-центр, второй — запас из снимка и агентов

**Зачем:** пережить отказ **одной машины внутри домашней площадки** (три indexer с копиями шардов, два worker, балансировщик). Отказ **всего дата-центра, где лежит мозг** = SIEM нет ни у кого, пока не восстановите диски indexer и каталог master (ключи агентов) на другой площадке. Агенты чужих площадок при живом мозге продолжают слать события; при мёртвом мозге копят очередь — бесконечный буфер вендор не обещает. Цифр событий в секунду нет.

### Почему кластер не растягиваем на несколько дата-центров

Indexer постоянно гоняет состояние кластера по **9300**. Server-кластер синхронизируется по **1516**. Если городской файрвол режет эти порты — кластер не соберётся. Если задержка сети большая — «жёлтый» поиск и ложные разъезды, не устойчивость. Документация **не задаёт** порог. «Три indexer в трёх дата-центрах» при потере двух площадок всё равно снимает большинство узлов, которые выбирают ведущего.

Один Kubernetes на три площадки в этой инструкции тоже не предполагается. Размазать StatefulSet «как зоны облака» здесь нельзя честно.

Falco — агент на каждой ноде, его нормально ставить в каждом кластере. Wazuh server/indexer — **общая** система. Копировать мозг «по кластеру как Falco» без склейки событий = три SIEM.

Из исходной боевой развилки вендора здесь выбран честный вариант при неизвестной задержке: **агенты везде, мозг в одном месте**. Вариант «один indexer на три площадки» откладывается, пока не измерите 9300/1516. Вариант «три полных Wazuh» — только если дежурные готовы склеивать три индекса; обычно это хуже.

### Как расставить машины

**В активном дата-центре:**

- **Indexer:** не меньше **трёх** нод StatefulSet, все в этой площадке. Шаблон индексов `wazuh-alerts-4.x-*`: **не** заводские три основных куска и **ноль копий**. Для устойчивости — **хотя бы одна копия** шарда. Вендор формулирует: число основных кусков примерно как число нод; 0 копий → при падении узла индекс дырявый; 1 копия → полный индекс; 2 копии → живут даже два упавших узла ценой диска.
- Куча Java: `Xms = Xmx`, ориентир **половина RAM**. В официальном overlay Kubernetes блокировка памяти выключена и куча **1g** при лимите 2 ГиБ — для боя это пересмотреть вместе с requests/limits, не копировать. На каждой ноде indexer: `vm.max_map_count=262144` и после ребута.
- Размер диска — от ваших событий в секунду × срок хранения, не 500 МиБ из базового YAML и не 10 ГиБ из патча «чтобы стартануло». Политика жизни индексов: в примере вендора **90 дней** для алертов; ваш срок — решение ИБ. **Не включать архивы всех событий**, пока нет отдельной ёмкости.
- Диск: **RWO**, не NFS «один том на троих».
- **Server:** ровно **один** master + **не меньше двух** worker (как полный overlay). В списке master официально должен быть **один** элемент; остальные игнорируются. Второго master штатно нет: падение этой площадки = нет регистрации агентов и API, пока не поднимете тот же StatefulSet с диском. Сценарий восстановления записать заранее, не обещать «как etcd».
- Файл настроек на worker **копировать самим** (GitOps) после правок на master. Сами едут ключи агентов, свои правила и декодеры, словари, проверки конфигурации, группы — **не** весь файл настроек.
- Порт **1516** только между узлами server. Ключ кластера — как пароль от всего server-кластера: 32 символа с энтропией, не строка из Git.
- Перед **1514** (и обычно **1515**) — **TCP-балансировщик** этой площадки, лучше leastconn. Агенты знают один адрес, не список подов. Помощник HAProxy на master — опция; сам HAProxy всё равно отдельное ПО.
- Регистрация агентов: длинный пароль, лучше проверка сертификата агента; 1515 не в интернет. Завод в эталоне — «пароль не использовать»; overlay Kubernetes как раз сажает `password`.
- **Dashboard:** официально без своего склада. В бою **не меньше двух** реплик Deployment (вендорский YAML даёт 1 — точка отказа просмотра, не детекта). Только внутренняя сеть, не LoadBalancer из примера в интернет.
- Filebeat в образе manager пишет **в этот же** indexer на 9200, не в платформенный поиск логов приложений.
- Жёсткий лимит CPU на worker → анализ начинает отбрасывать события. Не душить «чтобы не мешал».

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: весь мозг. Вторая: агенты (DaemonSet или пакет) на адрес 1514/1515 первой. **Нет** 9300 и 1516 между площадками | SIEM нет для обеих площадок, пока не восстановите мозг с дисков. Агенты второй копят очередь. Время простоя замерить. Копия шарда **не** заменяет бэкап: команду «удали индекс» копия послушно повторит |
| **Три** | Третья: ещё агенты на тот же адрес | То же. Третья площадка не даёт второго master. Три независимых полных Wazuh ≠ один разбор |

Если вторая площадка изолирована и 1514 до первой нет — ставите локальный manager+indexer. Это **второй** SIEM: события сами не сольются. Дежурные должны это принять явно.

Клиенты dashboard — только внутренняя сеть.

Не кладите «все indexer в первой площадке, а master во второй»: dashboard в официальном Deployment смотрит API на master по имени; разъезд ролей через город без замера — отдельный неподтверждённый контур.

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемой скоростью, один том на один под. Минимум двух рабочих нод Kubernetes часто всплывает из-за правила «поды indexer не сажать на одну машину».
- Свои сертификаты (скрипт репозитория — самоподписанные для теста). Свои секреты **до** первого агента. Overlay v4.14.7 кладёт в git известные значения — перечень в `Wazuh.md`.
- Сетевая политика: 9200, 9300, 1516, 55000 не с мира; 1514/1515 только от агентов и балансировщика; 1516 только между узлами server.
- Зеркало образов `wazuh/*:4.14.7` (лучше digest), если закрытый контур.
- Бэкап дисков indexer **и** каталога `/var/ossec` master (ключи агентов). Потеря ключей = заново регистрировать весь флот.
- NTP на всех машинах.
- Понимание: привилегированный init-контейнер, который ставит `vm.max_map_count`, — осознанный долг схемы вендора, его ревьюит ИБ.

### Порядок установки в активном дата-центре

Это этапы, не замена руководства вашей сборки 4.14.7:

1. Снять оценку: сколько Linux/Windows/нод Kubernetes, какие логи, FIM или нет, 90 дней или нет. Зафиксировать: мозг здесь, агенты на других площадках смотрят сюда.
2. Клонировать репозиторий **тегом `v4.14.7`**, не `main` (на `main` уже мелькают образы другой линейки).
3. Заменить все секреты, свои сертификаты, класс диска, ресурсы **не** из патча 1–2 ГиБ / 10 ГиБ.
4. Поднять overlay (логический порядок **indexer → server → dashboard**). Дождаться, что indexer зелёный, *до* боевого Filebeat.
5. Шаблон индексов: копия шарда не меньше 1. Политика жизни индексов **до** боевого потока.
6. Ключ кластера 32 символа; регистрация агентов не `password`; 1515 не в интернет.
7. Балансировщик на 1514. Проверить, что 1516 ниоткуда кроме узлов server.
8. Dashboard не меньше одной реплики (лучше две) только во внутренней сети. Сменить заводские учётки; смена `wazuh-wui` ломает связь экрана — обновить конфиг UI. Роли API: не все администраторы.
9. Агенты: DaemonSet 4.14.7 на **каждом** Linux-кластере, имя агента = имя ноды, **tolerations** на Kafka / Camunda / control-plane. Windows и обычные VM — пакет. FIM не вешать на каталог данных брокера «всё подряд». Официальный Docker-агент годится как syslog-коллектор, не как замена наблюдения за хостом.
10. Active Response **выкл** на интеграционном контуре. Поиск уязвимостей — только если есть исходящий доступ к CTI.
11. После установки — выключить автообновление репозитория Wazuh.
12. GitOps на свои правила; выкат только через master.
13. Не публиковать API indexer «для удобства Grafana» без отдельной учётки только на чтение и TLS.

Если в договоре когда-нибудь дадут другой установщик — следуйте **ему**. Иначе честный план: мозг Wazuh на этой схеме Kubernetes/VM, в чужих кластерах только агенты.

Обновление indexer: по одному поду. Пока под вниз — полагаетесь на копии шардов. Без копий выкат = деградация поиска. Имеет смысл не давать Kubernetes снять сразу два из трёх indexer.

### Правила конфигурации боя

| Слой | Правило |
|---|---|
| Сеть | 443 dashboard — из сети единого входа; 1514/1515 — от агентов; 9200/9300/1516/55000 — не из пользовательской сети |
| Indexer | Копии шардов не меньше 1; политика жизни индексов; архивы выкл, пока нет отдельной ёмкости |
| Server | Ровно один master в домашней площадке; worker не меньше 2, дальше по нулю отброшенных событий |
| Агенты | Один адрес балансировщика; видимость хоста в Kubernetes; не пылесосить персональные данные без политики |
| Секреты | Все пять overlay-секретов свои; образы по тегу **4.14.7** из **вашего** registry |
| Данные | TLS по цепочке Filebeat / indexer / dashboard / API; тома шифровать средствами платформы (в самом Wazuh кнопки «шифровать диск» нет) |

Порты и имена в overlay **сверить** с тегом v4.14.7 вашей копии репозитория.

### Как расти, когда появятся цифры нагрузки

1. Замерить события в секунду, отброшенные события, кучу Java, диск, жёлтый/красный поиск.
2. Больше событий → worker'ы, не «ещё один master».
3. Больше хранения и поиска → ноды indexer и политика индексов, не безразмерный диск.
4. Больше нод Kubernetes → DaemonSet агентов растёт сам; на мозг давит **поток**, не число микросервисов.
5. Шумные пулы (Kafka + auditd + широкий FIM) мерить отдельно.
6. Фраза вендора про all-in-one «до 100 агентов» и таблица 3.7 ГБ/сервер — ориентир, не список закупки.

### Проверки, без которых это ещё не бой

1. Все роли **4.14.7**; здоровье indexer зелёное; копии шардов на месте. Нет смеси 4.13 и 4.14.
2. Алерт с агента домашней площадки и с агента второй площадки доехал в **один** индекс.
3. Выключили один worker — агенты через балансировщик на живых; отброшенные события после догона снова 0.
4. Выключили одну ноду indexer — индекс полный, не красный.
5. Учение «площадка master мертва»: что с регистрацией, API, экраном; сколько анализа осталось на worker. Второго master нет — сценарий подъёма с диска, не «сам выберется».
6. Попытка с заводским `password` overlay — отказ. Экран с мира — отказ.
7. Выкат indexer по одному поду: без копий шардов поиск деградирует — и это должно быть понято **до** боя.
8. Снесли учебный индекс командой — копии шардов повторили удаление; выручил **бэкап**, не реплика.

### Что хорошо и что плохо в схеме «мозг в одном дата-центре»

| Хорошо | Плохо |
|---|---|
| Состояние indexer и порт 1516 не зависят от задержки между городами | Падение этой площадки = нет SIEM ни у кого, пока не восстановите диски |
| Один набор правил, один индекс, одни дежурные | Путь агентов чужих площадок до 1514 пересекает город |
| Согласовано с запретом растяжки и с «не три SIEM» | Master — единая точка управления; автоматического переключения нет |
| Агент есть и на Windows, в отличие от Falco | DaemonSet без видимости хоста = галочка, не покрытие |
| | Ресурсы из патча «чтобы стартануло» легко уехать в бой как «официальный минимум» |

**Не готово к бою**, если: одна машина «как на тесте» на две-три площадки; один indexer без копий шардов; секреты overlay из git; три независимых Wazuh без склейки «как будто одни дежурные»; растяжка indexer по 9300 между дата-центрами; два master «для устойчивости»; агенты без балансировщика; агент без видимости хоста; тег `latest`; dashboard в интернет; нет политики индексов; indexer = платформенный OpenSearch; ждут, что Wazuh заменит WAF, Falco или NetworkPolicy; бэкап ключей агентов ни разу не восстанавливали.
