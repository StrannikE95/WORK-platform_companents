# Camunda 8.9 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Camunda 8.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Camunda 8 — движок долгих процессов: схема исполняется на кластере брокеров, ваши программы только берут работу и возвращают короткий результат. Ставите **свою** копию Self-Managed, не облако поставщика.

Версия в этой инструкции: **Camunda 8.9**. На Kubernetes — Helm-чарт **`camunda-platform` 14.8.5**, образ Orchestration Cluster **`camunda/camunda:8.9.17`**. Соседние образы той же строки матрицы: Connectors 8.9.8, Optimize 8.9.17, Management Identity 8.9.8, Web Modeler 8.9.7, Console 8.9.88.

Матрица: https://helm.camunda.io/camunda-platform/version-matrix/camunda-8.9/  
Документация: https://docs.camunda.io/

**8.10** на дату соседнего файла — Alpha; в бой не брать. Переход на 8.9 — только с 8.8.x. С 8.6 production Self-Managed **требует лицензию** (`CAMUNDA_LICENSE_KEY`). Без ключа на экране может быть плашка Non-Production — это не разрешение для боя.

Обычный путь боя — Helm на Kubernetes. Учебный путь — Camunda 8 Run или Docker Compose: поставщик прямо пишет, что это не production. Windows/macOS как хост — только учёба. Образы брокеров — Linux amd64/arm64.

Вторичное хранилище (чтобы Operate видел процессы) в бою — **OpenSearch 3.8.0** (ветка 3.6+ для 8.9). С 8.9 без явного `orchestration.data.secondaryStorage.type` чарт **не ставится**. Смена семейства потом — не замена на месте.

Один кластер брокеров, размазанный на несколько дата-центров, здесь **не собираем**. Запись коммитится, когда большинство копий партиции подтвердило по порту **26502**; в документации нет цифры «сколько миллисекунд ещё можно» для трёх площадок. Поэтому живой кластер — внутри одной площадки. Вторая площадка — снимок и восстановление, не вторая половина того же Raft.

Официальная схема dual-region (две площадки, 8 брокеров, RF=4, ручной failover, RPO 0) — тоже Raft между городами, и OpenSearch там **не поддерживается**. В этой инструкции её не ставим.

---

## О чём эта инструкция молча договорилась

1. Тройка брокеров, кворум Raft и OpenSearch **одного** кластера живут в **одном** дата-центре. Между площадками — восстановление из снимка, не голосование 26502. Не открывайте между дата-центрами порты 26501/26502, если не строите осознанно другой контур.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`). Совместимость чарта 14.8.5 с вашей версией Kubernetes проверить CSI/PDB на момент установки.
3. Учебный стенд — закрытая сеть. Camunda 8 Run, H2 и Compose допустимы **только там**.
4. Цифр вашей нагрузки нет — нет фразы «хватит N партиций». Стартовая тройка брокеров/партиций/копий в бою: **3 / 3 / 3**, пока свой замер не скажет иначе.
5. Бакет для снимков движка и индексов OpenSearch в бою **есть или будет**. Копии партиций бэкап не заменяют: команду «удали том» они не откатят.
6. Два дата-центра: кластер в первом; второй — восстановление из снимка. Три дата-центра: то же. Третья площадка — **не** третий брокер чужого голосования.
7. Интеграции с ведомствами — только через ваше интеграционное API. Коннекторы Camunda туда не плодим. В переменных процесса — идентификаторы и статусы, не досье (потолок порядка **~3 МБ** на экземпляр — эвристика поставщика).
8. Optimize в первом боевом контуре выключен (ориентир поставщика: ×3–4 к нагрузке поиска). Bitnami Elasticsearch/PostgreSQL из чарта в бою выключены.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** нарисовать схему, задеплоить, написать воркер, увидеть экземпляр в Operate. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- Java воркера совместима с 8.9 (брокеры: OpenJDK 21–25).
- Сеть стенда не торчит в интернет.
- Не смешивать привычку «C8 Run = почти бой» с Helm.

### Установка (Camunda 8 Run / Compose — основной путь для учёбы)

Возьмите **Camunda 8 Run** или Docker Compose из developer quickstart: Orchestration Cluster + Connectors, вторичное хранилище по умолчанию **H2**. Поставщик: **не для production**.

Клиенты (воркеры, экраны) ходят на gateway **8080** (REST) и **26500** (gRPC). Порты **26501** и **26502** — внутренние (команды и Raft); на учебном стенде не публиковать их на все интерфейсы. **9600** — служебные метрики, не в интернет.

После старта: задеплоить процесс с одной сервисной задачей, живой воркер **снаружи** движка, экземпляр доходит до конца. В переменную кладите идентификатор, не XML досье.

### Установка (Kubernetes — если стенд уже в кластере)

Чарт **14.8.5**, урезанные values. Явно задать тип вторичного хранилища **до** установки:

```yaml
orchestration:
  clusterSize: 1
  replicationFactor: 1
  partitionCount: 1
  data:
    secondaryStorage:
      type: elasticsearch   # или opensearch / rdbms
```

H2 в Helm-бою нет; на учёбе допустим маленький OpenSearch в соседнем namespace **или** сознательный H2 только в C8 Run. **Не** этот values в бой.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Брокеры / копии / партиции | 1 / 1 / 1 | Не учимся переживать падение машины |
| Вторичное хранилище | H2 (C8 Run) или маленький OpenSearch | H2 не учит экспорт — на препроде OpenSearch обязателен |
| Вход | basic | Иначе IdP раньше воркера |
| Лицензия | Non-Production | Стенд не бой |
| Optimize / Web Modeler | выкл | Не нужны, чтобы понять воркер |
| Переменные процесса | id/статус, не досье | Иначе в бою раздует партиции |

Чего **не** упрощаем: версия **8.9.x** и клиент воркера под 8.9; воркеры **снаружи** JVM движка; веб и 8080 не открывать в интернет «навсегда».

### Как понять, что стенд живой

1. Версия 8.9.x. Процесс виден в Operate (если не H2 без экспорта — хотя бы работа дошла до конца).
2. Рестарт единственного брокера при одной копии: незареплицированное теряется — так и должно быть на тесте.
3. Не копировать values C8 Run в GitOps боя.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный C8 Run / Compose | Нет Raft между машинами, нет экспорта в OpenSearch 3.8.0 |
| Учит внешних воркеров, не встроенный listener в той же JVM | Успех на H2 **не** доказывает backpressure при падении OpenSearch |
| | Basic `demo` приучает вход без IdP |

Перед боем полезен **препрод**: 3 брокера, RF=3, свой OpenSearch, OIDC stage, backup API — всё **в одном** дата-центре, даже без боевых процессов.

## Бой: один живой дата-центр, второй — запас из снимка

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три брокера, три копии каждой партиции, запись подтверждается большинством). Отказ **всего дата-центра, где лежит кластер** = оркестрации нет, пока не восстановите снимок на другой площадке. При восстановлении часть свежих данных можно потерять — это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Запись коммитится, когда большинство копий партиции подтвердило. Порт **26502** между городами при неизвестной задержке → медленные процессы, ложный отказ брокера, постоянный backpressure. Порога задержки для **трёх** площадок у поставщика **нет**. Dual-region: ориентир **≤ 100 мс**, минимум 8 брокеров, RF=4, при потере региона обработка **встаёт** до процедуры, вторичное хранилище **только Elasticsearch**. Это форма того же Raft между площадками — в этой инструкции **не ставится**. Плюс выбранный OpenSearch 3.8.0 dual-region не поддерживает.

### Как расставить машины

**В активном дата-центре** — один Orchestration Cluster:

- `clusterSize: 3`, `replicationFactor: 3`, `partitionCount` кратно 3 (старт часто **3**, не 1). Тройка на всех брокерах **одинаковая**. RF не больше числа брокеров.
- Брокеры на **разных нодах** этой площадки (anti-affinity / topology spread **зала**, не идентификатор чужого дата-центра).
- Gateway: несколько реплик входа (с 8.8 часто встроен; масштабируют репликами). Клиенты на **8080 / 26500**, не на 26501/26502. Список контактов — **все** брокеры.
- Вторичное хранилище: отдельный **OpenSearch 3.8.0**, `orchestration.data.secondaryStorage.type: opensearch`. Не бизнес-поиск, не Wazuh. Один кластер поиска на Operate, Tasklist и Admin.
- Том **RWO** на каждого брокера, SSD, поставщик: **≥ 1000 IOPS**, HDD не поддерживается. `emptyDir` запрещён. NFS — только POSIX и один писатель.
- PostgreSQL для Identity/Modeler — внешний кластер **в этом дата-центре** (`PostgreSQL.install.md`), не Bitnami-subchart.
- Connectors и загрузка — не на тех же ядрах, что вход, если нагрузка серьёзная.
- Optimize в первом бою **выкл**.
- Два namespace как в production-гайде: `orchestration` (кластер, connectors) и при необходимости `management-and-modeling` (Identity, Console, Web Modeler).
- PDB: не дать Kubernetes снять сразу два брокера из трёх. Выкат — rolling по одному брокеру, ждать здоровые партиции.
- Helm `values-tls.yaml` закрывает TLS **к** OpenSearch/PostgreSQL/OIDC. **Не** закрывает весь gRPC между подами: для 26501/26502 поставщик отсылает на service mesh. NetworkPolicy обязателен в любом случае.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: весь кластер RF=3. Вторая: объектное хранилище бэкапов движка + снимок OpenSearch; **не** участник голосования 26502 первой площадки | Оркестрация стоит, пока не восстановите снимок в свой Kubernetes. RPO = период backup. RTO **мерить**. Копия партиции **не** заменяет бэкап |
| **Три** | Третья: ещё одна копия бэкапа или второй стенд восстановления | То же. Три независимых движка «для надёжности» — это три разных правды процессов, так не делают |

Клиенты с других площадок в штате ходят на gateway первой (TLS, gRPC-aware балансировщик на 26500). «Пишем Raft во все дата-центры» **не делаем**.

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемым IOPS, один том на один брокер.
- Лицензия Enterprise Self-Managed. OIDC, не `demo:demo`.
- OpenSearch 3.8.0 для Camunda **до** `helm install`.
- Бакет: (1) репозиторий снимков OpenSearch, (2) хранилище **partition backup** движка. Снимок диска брокера **не** согласованный бэкап. Бакет должен **переживать** гибель этой площадки.
- Helm CLI **v3** (матрица 14.8.x: Helm 3.20.x). Helm v4 — требование 8.10.
- Сетевая политика: клиенты → 8080/26500; 26501/26502 — только брокеры и gateway; 9600 — мониторинг и бэкап.
- NTP на всех нодах.

### Порядок установки в активном дата-центре

Это этапы, не замена руководства вашей сборки 8.9:

1. ОС нод, настройки ядра и дисков, NTP. Sysctl и StorageClass с предсказуемым IOPS.
2. Поднять OpenSearch 3.8.0 **для Camunda** (отдельный кластер).
3. Поставить чарт:

```bash
helm repo add camunda https://helm.camunda.io
helm install camunda camunda/camunda-platform --version 14.8.5 \
  -f values-prod.yaml
```

В `values-prod.yaml` обязательно (смысл, сверять с документацией 8.9):

- `orchestration.data.secondaryStorage.type: opensearch` плюс URL и учётки вашего OpenSearch 3.8.0;
- `clusterSize` / `partitionCount` / `replicationFactor`: **3 / 3 / 3**, пока замер не скажет иначе;
- `elasticsearch.enabled: false`; свой OpenSearch;
- `global.license.secret`; вход — OIDC, не basic.

4. Включить TLS до OpenSearch и Ingress **до** боевых процессов.
5. Выключить опасные заводские значения: нет `demo`, 26502 не слушает периметр, Keycloak/OIDC на корпоративный IdP.
6. Задеплоить пустой процесс с одной сервисной задачей и живым воркером. Проверка: экземпляр доходит до конца и виден в Operate.
7. Подключить первый реальный процесс: озеро по идентификатору, интеграционное API, Kafka. **Не** коннекторы в ведомства. В переменную — `requestId` / статус, тело ответа — в озеро.
8. Бэкап через API компонентов с **одним** идентификатором (движок + индексы экспорта). Восстановление — на другой namespace **и** на кластер второй площадки. Без прогона восстановления нет запасного контура.
9. Метрики `:9600/metrics`, лаг экспорта, алерты: потеря кворума, диск брокера, экспортёр, OpenSearch yellow/red, воркеры 0 реплик, лицензия.

После старта новые брокеры **присоединяются** процедурой scaling, а не поднимают второй кластер с тем же именем.

### Правила конфигурации боя

| Слой | Правило |
|---|---|
| Сеть | 8080/26500 — из сети единого входа; 26501/26502 — только брокеры и gateway; 9600 — только мониторинг и бэкап |
| Воркеры | Deployment ≥2 на каждый тип работы; таймаут работы **больше** типичного времени интеграционного API (ведомства с лагами в дни). Иначе движок отдаст работу другому воркеру — двойной вызов. Повтор без побочного эффекта — на стороне API |
| Kafka | Воркер **или** inbound connector читает топик и стартует/продолжает процесс. Не дублировать «и коннектор, и свой consumer» без ключа экземпляра |
| Переменные | Килобайты, идентификаторы. Потолок порядка ~3 МБ на экземпляр — не озеро |
| Connectors в ведомства | Нет. Воркер → ваше интеграционное API |
| Dual-region values | Не применять |
| 26502 в чужой дата-центр | Нет |
| Bitnami ES/PG | Выкл |
| Индексы OpenSearch | Учётки экспорта — минимум прав, не `admin` кластера. Срок хранения считать от событий процесса, не от терабайт озера |
| Права | OIDC; authorizations на процессы и задачи; Admin кластера и Management Identity — разные контуры, оба на корпоративный IdP |
| Секреты | Лицензия, OIDC, коннекторы — Vault/Secret, не Git и не схема процесса |
| Диск | Шифрование томов брокеров средствами платформы |
| Схемы в Git | Не класть секреты в BPMN; ревью моделей как код |

Балансировщик на 26500: L4 или gRPC-aware, не обычный HTTP round-robin. Лидерство партиций может сползти на одну ноду; для выравнивания есть Rebalancing API — best effort, не «всегда идеально».

### Как расти, когда появятся цифры нагрузки

1. Параллелизм ≈ партиции; добавлять брокеров процедурой scaling, не второй кластер с тем же именем.
2. Больше входа → реплики gateway, **если** партиции уже тянут.
3. Operate упирается в OpenSearch, не в «ещё брокер».
4. Медленный том брокера = «движок тупит» при живом кворуме. Не подменять SSD сетевой папкой на троих писателях.
5. Воркеры — HPA по **своим** метрикам (длина работы, не CPU брокера).
6. Ориентир поставщика «20× средней нагрузки» и «~3,5 ядра на брокер» — не смета закупки.

### Проверки, без которых это ещё не бой

1. Образ `camunda/camunda:8.9.17`, чарт 14.8.5; тип вторичного хранилища = opensearch на **всех** брокерах активной площадки.
2. Процесс доходит до конца, виден в Operate. Выключили один брокер — экземпляр продолжается. Клиенты ходят через gateway, не на зашитый адрес брокера.
3. Остановить OpenSearch на минуты: понять backpressure (это защита, не «баг медленности»).
4. Восстановили снимок в чистый namespace на стенде и на вторую площадку (замер RTO).
5. Нет `demo`; 26502 не слушает периметр; лицензия не Non-Production; dual-region **не** включён.
6. Учение «активный дата-центр выключен»: подъём запаса по заранее написанному сценарию. Учение «воркеры нулевые»: процессы стоят на работах — так и должно быть.

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + снимок»

| Хорошо | Плохо |
|---|---|
| Голосование Raft и диск брокера — локальная сеть | Падение этой площадки = нет оркестрации, пока не восстановите снимок |
| OpenSearch 3.8.0 остаётся вторичным хранилищем | RPO/RTO = частота backup, надо мерить; при восстановлении можно потерять хвост |
| Не зависит от неизвестной задержки между городами | Клиенты с других площадок ходят на gateway через город |
| Согласовано с запретом stretch и с dual-region≠OpenSearch | Dual-region RPO 0 сознательно не берём |

**Не готово к бою**, если: C8 Run / H2; одна копия партиции; брокеры без anti-affinity внутри площадки; stretch или dual-region; нет `secondaryStorage.type`; Camunda пишет в OpenSearch поиска или Wazuh; нет лицензии; нет прогнанного восстановления; терабайты в переменных; коннекторы в обход интеграционного API; самодельный Compose выдан за официальный бой.
