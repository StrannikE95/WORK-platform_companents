# Kubernetes 1.36.4 — развёртывание и настройка

Версия ПО: **Kubernetes 1.36.4** (патч-релиз линии 1.36; тег GitHub опубликован 20 августа 2026).  
Проверено **26 августа 2026**: на GitHub это последний стабильный патч поддерживаемой линии 1.36. Тега **v1.37.0** ещё нет (есть pre-release `v1.37.0-rc.1`). Страница https://kubernetes.io/releases/ на этот момент отставала (показывала 1.36.2) — ориентир по патчу брать из [релизов GitHub](https://github.com/kubernetes/kubernetes/releases), не из кэша маркетинговой страницы.

Документация: https://kubernetes.io/docs/home/  
Релизы и поддержка: https://kubernetes.io/releases/  
Установка HA (официальный путь проекта): kubeadm — https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/high-availability/

Релиз 1.37.0 в календаре SIG Release стоит на 26 августа 2026. В прод **не** берём RC и **не** прыгаем на 1.37 в день GA: сначала патч текущей minor, затем плановый minor без skip. Пока GA-тега нет — целевая версия **1.36.4**.

Этот текст — не мануал «скопируй kubeadm init», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Кластер** | Набор машин, которыми управляет один control plane. «Один Kubernetes» = один кластер. Три независимых Kubernetes — это **три** кластера. |
| **Нода (node)** | Машина (физическая или VM), на которой крутится kubelet. Бывает control-plane и worker. |
| **Pod** | Минимальная единица запуска: один или несколько контейнеров, которые всегда вместе, с общим network namespace. Поды **смертны**: Kubernetes имеет право их убить и создать заново на другой ноде. |
| **Контейнер** | Изолированный процесс (обычно OCI-образ). Сам Kubernetes контейнеры не запускает — это делает **runtime** (containerd / CRI-O). |
| **Control plane** | «Мозг» кластера: API, планировщик, контроллеры, etcd. Без него **уже запущенные** поды обычно продолжают работать, но нельзя деплоить, масштабировать и переносить упавшие поды. |
| **kube-apiserver** | Единственная «дверь» в кластер. Всё управление идёт через его HTTP API (обычно порт 6443, TLS). |
| **etcd** | Распределённое key-value хранилище **состояния кластера** (какие Deployment'ы есть, какие поды должны быть, Secrets). Это **не** озеро данных и не Kafka. |
| **Кворум (quorum)** | Большинство голосов etcd. Для 3 членов большинство = 2. Если живых меньше большинства, etcd **перестаёт принимать запись**. Кластер «глухой» для изменений. |
| **Raft** | Протокол согласия, на котором etcd выбирает лидера и реплицирует запись. Каждая успешная запись должна быть подтверждена большинством. |
| **Stacked etcd** | etcd живёт **на тех же** машинах, что и API-сервер. Проще, меньше железа. Падение ноды бьёт сразу по API и по голосу etcd. Дефолт kubeadm. |
| **External etcd** | etcd на **отдельных** машинах. Дороже (минимум ещё 3 хоста), зато отказ API-сервера не снимает голос etcd. |
| **kube-scheduler** | Решает, на какую ноду положить новый под (ресурсы, зоны, taint/toleration, affinity). |
| **kube-controller-manager** | Набор контроллеров: «хотели 3 реплики — сейчас 2 — создать ещё одну». |
| **kubelet** | Агент на каждой ноде: следит, чтобы назначенные поды реально бежали. |
| **kube-proxy** | Реализует Service на ноде (обычно iptables/ipvs или его заменяет CNI вроде Cilium). |
| **Service** | Стабильный виртуальный IP/DNS на набор подов. Поды умирают и меняют IP — Service остаётся. |
| **Ingress / Gateway API** | Вход HTTP(S) снаружи. **Не** часть ядра Kubernetes: нужен отдельный контроллер. Gateway API — более новый стандарт, Ingress — старый, всё ещё живой. |
| **CNI (Container Network Interface)** | Плагин сети подов. Без него кластер после kubeadm **не умеет** нормально запускать поды. Kubernetes сеть «из коробки» не даёт. |
| **CSI (Container Storage Interface)** | Плагин дисков. PersistentVolume без CSI-драйвера (или in-tree, которых почти не осталось) не появится. |
| **PersistentVolume (PV) / PVC** | Диск для пода, который переживает перезапуск пода. **Не** переживает потерю ноды, если том локальный и репликации нет. |
| **StorageClass** | «Какой диск дать»: быстрый локальный NVMe, сетевой, с репликацией, в какой зоне. |
| **WaitForFirstConsumer** | Режим привязки тома: диск создаётся **после** выбора ноды. Нужен, чтобы том не оказался в ЦОДе A, а под — в ЦОДе B. |
| **Namespace** | Логическая папка в одном кластере (права, квоты, NetworkPolicy). Это **не** изоляция уровня ЦОДа и не отдельный Kubernetes. |
| **RBAC** | Кто какие API-вызовы может делать (`get pods`, `create secrets`, …). Сервисный аккаунт приложения — не человек. |
| **ServiceAccount** | Учётка пода для обращения к API. Токен монтируется в под. |
| **Pod Security Admission (PSA)** | Встроенный фильтр: какие поды вообще можно создать. Три профиля: Privileged / Baseline / Restricted. |
| **NetworkPolicy** | Firewall между подами. **Работает только если CNI это умеет.** Объект в API без поддержки CNI — декорация. |
| **Taint / Toleration** | «На эту ноду обычные поды не пускать» / «этому поду можно». Control plane по умолчанию tainted. |
| **Affinity / topologySpreadConstraints** | Правила «положи рядом» / «размажь по зонам». Без них все реплики могут сесть в один ЦОД. |
| **topology.kubernetes.io/zone** | Стандартный ярлык зоны (у вас — id ЦОДа). Scheduler и CSI на него опираются. |
| **PDB (PodDisruptionBudget)** | «Не убивай сразу две реплики при drain». Защита от **добровольных** снятий (обновление ноды), не от падения ЦОДа. |
| **HPA** | Horizontal Pod Autoscaler: больше/меньше подов по метрикам. Нужен источник метрик (обычно Metrics Server — **не** часть kubeadm). |
| **Cluster Autoscaler / Cluster API** | Добавление **нод**, не подов. Отдельные проекты. Без возможности заказать VM «из воздуха» autoscaler бесполезен. |
| **ControlPlaneEndpoint** | DNS/IP балансировщика **перед** несколькими kube-apiserver. Без него HA control plane по kubeadm не собирают. |
| **Skew (version skew)** | Насколько версии компонентов могут отличаться. kubelet **нельзя** новее apiserver; можно отстать до 3 minor. |
| **CRI** | Container Runtime Interface. Docker-shim давно убран. Нужен containerd или CRI-O. |
| **Stretch-кластер** | Один Kubernetes, ноды физически в нескольких ЦОДах, **один** etcd-кворум растянут между ними. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. Для etcd это состояние кластера; данные Kafka/БД — **другой** RPO. |

## Основные элементы системы и зависимости

### Что входит в Kubernetes 1.36.4 (это одно ПО)

- **kube-apiserver, kube-scheduler, kube-controller-manager** — control plane.
- **etcd** — хранилище состояния; kubeadm ставит его сам (stacked) или вы подключаете external. Линия kubeadm 1.36 использует etcd **3.6.x**; точный патч образа на момент установки смотреть командой `kubeadm config images list`, не запоминать «навсегда».
- **kubelet, kube-proxy** — на каждой ноде.
- **kubectl** — клиент (ставится отдельно, на машины администраторов).
- **Встроенные API:** Pod, Deployment, StatefulSet, DaemonSet, Job, Service, ConfigMap, Secret, RBAC, NetworkPolicy, PDB, HPA, StorageClass, PSA и т.д.
- **Сертификаты кластера** (CA, apiserver, etcd, kubelet) — kubeadm генерирует PKI.

CoreDNS в типичной установке kubeadm тоже поднимается, но это **аддон**, не «ядро языка Kubernetes». Без DNS сервисы по имени не резолвятся.

### Чего в Kubernetes нет (частая путаница)

| Нужно системе | Это не Kubernetes | Зачем помнить |
|---|---|---|
| Сеть между подами, NetworkPolicy «по-настоящему» | CNI: Cilium, Calico, … | Без CNI кластер нерабочий; без CNI с NetworkPolicy объекты политики ничего не режут. |
| Диски для Kafka/Postgres/озера | CSI-драйвер + StorageClass | Kubernetes только **заказывает** том. Репликация диска — задача СХД/CSI, не kube-scheduler. |
| Внешний IP для Service `LoadBalancer` | MetalLB, BGP к вашим маршрутизаторам, внешний ADC | На железе в ЦОДе «просто LoadBalancer» не появится. |
| HTTP-вход | Ingress-контроллер или Gateway-контроллер | В API есть объекты, исполнителя нет. |
| Метрики для HPA | Metrics Server и/или Prometheus Adapter | Без них HPA не из чего считать. |
| GitOps, единый деплой на 3 кластера | Argo CD / Flux и т.п. | Сам Kubernetes не синхронизирует три control plane. |
| Реестр образов | Harbor / Quay / корпоративный registry | Ноды должны **откуда-то** тянуть образы; `registry.k8s.io` из закрытого контура может быть недоступен. |
| ГОСТ TLS / СКЗИ | Не входит | Если требование ИБ — отдельный контур (критичный пробел, см. ниже). |
| Озеро данных, Kafka, Camunda | Клиенты платформы | Они **бегут на** Kubernetes, но отказоустойчивость их данных — в их RF/репликах, не в «у нас три ноды Kubernetes». |

### Зависимости окружения (обязательны)

- **ОС:** Linux на нодах (Windows-ноды в этой архитектуре не рассматриваем — см. допущения).
- **CRI:** containerd или CRI-O, уже работает **до** `kubeadm init`.
- **Полная IP-связность** всех нод кластера между собой (явное требование HA-гайда kubeadm). Для stretch — это связность **между ЦОДами**.
- **Балансировщик TCP** на порт apiserver (6443) для HA: health check — TCP до 6443. Сам балансировщик должен переживать отказ одной машины/одного ЦОДа, иначе control plane «высокодоступный» только на бумаге.
- **Диск etcd:** локальный SSD/NVMe, низкий хвост fsync. **Не NFS.** etcd пишет в Raft-лог каждый коммит; медленный диск = ложные выборы лидера.
- **Время:** синхронизация часов (NTP/chrony). Рассинхрон ломает TLS и путает таймауты Raft.
- **Образы:** доступ к `registry.k8s.io` **или** заранее пролитые образы на ноды / зеркало.

### Как Kubernetes стыкуется с вашей архитектурой

```
3 ЦОДа, железо / VM
        │
        ▼
   Kubernetes          ← этот документ (оркестрация)
        │  запускает и чинит поды
        ▼
Kafka, Camunda, интеграционное API, озеро данных, Postgres/…
```

Kubernetes **не** источник истины клиентских данных и **не** шина событий. Он держит в etcd только «как должна выглядеть система». Терабайты живут в томах и в Kafka/БД. Если etcd раздуть прикладными данными — control plane умрёт раньше, чем кончится место на озере.

## Краткие вводные

### Зачем вам Kubernetes в этой архитектуре

Вам нужно одинаково запускать много сервисов (микросервисы, Camunda, интеграционный слой), переживать падение машин и наращивать мощность. Kubernetes даёт:

1. **Желаемое состояние:** «хочу 5 реплик этого сервиса» — контроллер сам догонит факт.
2. **Площадку для масштаба:** больше подов (HPA) и больше нод (докупка машин / autoscaler).
3. **Единые рычаги безопасности:** RBAC, PSA, NetworkPolicy, Secrets — если их **включить и соблюдать**. Из коробки после kubeadm этого недостаточно для прода.

### Как устроена отказоустойчивость (идея, не магия)

Есть **два разных слоя**, их постоянно путают.

**Слой A — control plane (etcd + API).**  
Живёт, пока жив кворум etcd. Правило то же, что у Kafka-контроллеров: чтобы пережить N одновременных отказов членов, нужно 2N+1. Три etcd → переживёте **одного** члена. Пять → двоих.

Официальная документация etcd прямо говорит: **члены etcd по возможности держать в одном ЦОДе**, чтобы не платить задержкой и риском partition. Это **конфликт** с желанием «один кластер на три ЦОДа». Конфликт нельзя «закрыть настройкой»; его надо выбрать (см. шаг 0 в проде).

**Слой B — ваши приложения.**  
Реплики подов + PDB + разложение по зонам + **репликация самих данных** (RF Kafka, реплики Postgres, CSI). Kubernetes перезапустит под. Он **не** восстановит данные, если единственная копия лежала на умершем диске.

Падение control plane **не** равно падению бизнеса в ту же секунду: kubelet продолжает держать уже запущенные поды. Но новые деплои, failover подов с умершей ноды, смена Service/сертификатов — встанут. Если за время «глухого» API умрёт ещё и worker — эти поды никто не поднимет.

### Как устроено масштабирование

Две оси, не одна:

| Ось | Что добавляете | Что это даёт | Потолок |
|---|---|---|---|
| Поды (HPA / replica) | процессы приложения | CPU/RAM сервиса | сколько влезает на текущие ноды; для stateful — ещё и партиции/шарды приложения |
| Ноды | машины | суммарные CPU, RAM, диск, сеть кластера | закупки железа, сеть, лимиты etcd и API |

«Терабайты» почти наверняка лежат **не в etcd**. Квота etcd по умолчанию **2 ГиБ**, рекомендуемый максимум для обычных сред — **8 ГиБ** (выше — предупреждение при старте). Это размер **метаданных кластера**, не озера. Раздутый etcd (тысячи огромных ConfigMap/Secret, слишком много объектов) убивает API раньше, чем закончится СХД.

### Секреты по умолчанию не секретны на диске

Официальная документация: без `--encryption-provider-config` API-сервер кладёт ресурсы в etcd **открытым текстом**. Secret в etcd — это не «зашифровано Kubernetes'ом»; это base64 в API и plaintext в etcd. Кто снял снимок диска etcd — читает пароли Kafka, токены гос-API, ключи.

Шифрование канала (TLS к API) от этого **не** спасает.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть, а не «чуть подкрутить CIDR».

1. **Берём vanilla Kubernetes 1.36.4 + kubeadm** как документированный проектом путь HA. Дистрибутивы (RKE2, Talos, OpenShift и т.д.) **не отменяют** правила кворума etcd, зон и RBAC; они меняют установку и обвязку. Если выберете дистрибутив — те же топологические правила, другой плейбук.
2. **Прод on-prem в ваших трёх ЦОДах**, не managed EKS/AKS/GKE. Облачный LoadBalancer и динамические PV «из гайда kubeadm» там прямо помечены как не про этот сценарий.
3. **Три ЦОДа в одном городе** — три независимых домена отказа (питание, сеть, площадка). Если это три зала с общим UPS — «три ЦОДа» ложные, и раскладка etcd 1+1+1 не даёт заявленной защиты.
4. **ОС нод — Linux.** Смешанные Windows-ноды не закладываем.
5. **CRI — containerd** (CRI-O допустим; на правила HA это не влияет).
6. **CNI будет выбран отдельно** и **обязан** реализовывать NetworkPolicy. Конкретный продукт (Cilium vs Calico vs …) — решение сети/ИБ, не «единственно верный». Без этого решения нельзя честно обещать изоляцию интеграционного контура от остального.
7. **Stretch одного Kubernetes на 3 ЦОДа** принимается **только если** сеть между членами etcd достаточно быстрая и стабильная. Порога RTT в документации **проекта Kubernetes нет**. Документация **etcd**: по возможности один ЦОД; для нескольких ЦОДов — тюнинг heartbeat/election timeout. Дефолты etcd: heartbeat **100 ms**, election timeout **1000 ms**; election timeout должен быть **не меньше 10× RTT**. Пока RTT и потери пакетов не измерены — stretch **гипотеза**, не решение.
8. **Нагрузки нет** — поэтому **нет** числа worker-нод «хватит для прода» и **нет** размера дисков приложений. Есть минимум для control plane и правила роста.
9. **Формального SLA / RPO / RTO нет.** «Работа беспрерывная» не равно юридический 24/7. Потеря **двух** ЦОДов при трёх членах etcd кворум, как правило, убивает.
10. **Корпоративный PKI / KMS** для ключей шифрования Secrets либо будет, либо на старте — локальный `aesgcm` с ключом, который сам должен храниться не в Git. KMSv2 — рекомендованный Kubernetes путь, если KMS есть. KMSv1 с 1.28 deprecated, с 1.29 выключен по умолчанию.
11. **Тестовый стенд** — изолированная сеть; там допустим один control plane. Прод-RBAC и PSA на тест один в один не копируем в первый день, но **манифесты приложений** лучше сразу писать без `privileged` и без hostNetwork — иначе тест врёт.
12. **Kafka, Camunda, озеро, интеграционное API** — workload. Их RF, PVC и сетевые политики проектируются в их документах. От Kubernetes им нужны: зоны, StorageClass, ресурсы, PDB, NetworkPolicy, ServiceAccount с least privilege.
13. **Решение по Kafka stretch vs MirrorMaker** (файл `Apache Kafka.md`) **зависит** от того, один у вас Kubernetes или три. Это не ортогональные выборы.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** закупки «кластера на три площадки». Иначе архитектура разъедется.

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потери между ЦОДами (p50/p95/p99, все пары, в обе стороны)** | Запись в etcd не быстрее, чем репликация на большинство. Если RTT «плавает» или пакеты теряются, начнутся выборы лидера, API будет таймаутиться, **весь** кластер станет нестабильным — не только «сеть чуть тормозит». |
| **Топология: один Kubernetes или три** | Stretch vs независимые кластеры — разные RPO/RTO, разный GitOps, разная схема Kafka. «Мы используем Kubernetes» этого выбора не содержит. |
| **Как устроена L3 между ЦОДами и нужны ли overlay (VXLAN/Geneve)** | Overlay между ЦОДами добавляет латентность и проблемы MTU. Для Kafka (прямые соединения брокер–брокер) плохая подложка может сделать stretch Kafka невозможным даже при «живом» Kubernetes. |
| **Профиль нагрузки** (число сервисов, подов, QPS к API, частота деплоев, размер образов) | Без этого нельзя сказать ни число нод, ни «готовы к высокой нагрузке». Рост нод увеличивает давление на etcd и apiserver. |
| **Где живут терабайты** (объектное хранилище, PVC, Kafka log.dirs) | Если кто-то предложит «сложить в etcd / в ConfigMap» — это путь к деградации control plane. Политика: в etcd только метаданные. |
| **Формальные RPO/RTO и что значит «упал ЦОД»** | Stretch etcd переживает **один** ЦОД при 3 членах. Два ЦОДа — нет. Три независимых кластера переживают смерть площадки **как площадки**, но приложение должно уметь работать на оставшихся (данные + трафик). |
| **Балансировщик перед apiserver** (кто, anycast?, переживает ли он ЦОД) | SPOF control plane часто оказывается не etcd, а один HAProxy в одном шкафу. |
| **Требования ИБ: ГОСТ, 152-ФЗ, КИИ, сканирование образов, срок ключей** | Меняют PKI, допустимость образов с Docker Hub, необходимость KMS/HSM, аудит. |
| **Реестр образов и выход в интернет с нод** | Закрытый контур без зеркала = кластер не встанет и не обновится. |
| **Кто оперирует кластером 24/7** (дежурства, drain, сертификаты kubeadm живут 1 год по умолчанию) | Истёкший сертификат apiserver — вполне себе полный простой управления. Это операционка, не «Kubernetes сам». |

---

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **1.36.4** и не прыгать через minor при апгрейде (проект **запрещает** skip minor даже на одном apiserver).
2. Поставить CRI, выключить или корректно настроить swap по текущим требованиям kubeadm/kubelet.
3. Поднять etcd-кворум и control plane (тест — 1 узел; прод — 3 или 5).
4. Поставить **CNI**, затем CSI, CoreDNS проверить.
5. Выставить зоны (`topology.kubernetes.io/zone`), taint'ы пулов нод.
6. Включить безопасность **до** боевых namespace'ов приложений (RBAC, PSA, encryption at rest, audit, NetworkPolicy default-deny).
7. Отдать разработчикам не cluster-admin, а namespace + лимиты.
8. Мониторинг: здоровье etcd (лидер, fsync, peer RTT p99), apiserver latency, disk etcd, число объектов, сертификаты, not-ready ноды, PDB vs eviction.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы команда деплоила сервисы, отлаживала манифесты, подключалась к Kafka/Camunda. **Не** цель: доказать отказоустойчивость трёх ЦОДов.

#### Топология

Минимально достаточно **одного** control plane + etcd на той же машине (stacked, один член — кворума «пережить отказ» нет):

- 1 VM/хост или kind/k3d/minikube — если цель только API и поды;
- либо kubeadm: 1 control-plane и 1–2 worker, один ЦОД;
- CNI любой простой для dev;
- Storage: hostPath / local-path-provisioner;
- PSA: `baseline` на dev-namespace уже полезен, `privileged` только для системных аддонов.

Официальный минимум kubeadm (чтобы **вообще завелось**, не прод): порядка 2 CPU и 2 ГиБ RAM на машину, уникальные hostname/MAC/product_uuid. Это не сайзинг прода.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Один etcd | да | Некому строить кворум |
| Без ControlPlaneEndpoint-LB | да | Один apiserver |
| Encryption at rest | можно отложить | Изолированный стенд; в проде — нет |
| LoadBalancer / MetalLB | опционально | NodePort хватит |
| Мониторинг | минимум | Нет нагрузки |

#### Чего на тесте **не** стоит упрощать в манифестах приложений

- `resources.requests` (иначе в проде scheduler и HPA живут в другом мире).
- Запрет `privileged` / hostNetwork без нужды.
- Явные зоны не обязательны на одной стойке, но **StatefulSet + volumeClaimTemplates** лучше сразу, если в проде будет CSI.
- Не класть секреты в Git «потому что тест».

#### Сильные стороны такой схемы

- Поднимается за часы.
- Дешёвая.
- Совпадает с практикой проекта: однонодовый кластер для разработки допустим.

#### Слабые стороны (обязательно понимать)

- Падение единственной ноды = простой всего.
- Стенд **не** ловит: etcd elections, topologySpread, CSI WaitForFirstConsumer, латентность CNI между ЦОДами, истечение сертификатов на трёх API.
- Успешный тест на kind **не** является доказательством готовности прода.

Практическая рекомендация: препрод — **маленькая копия прод-топологии control plane** (3 stacked или 3+3 external) даже без боевой нагрузки, в одном ЦОДе. Иначе первый сюрприз — кворум и сертификаты на пользователях.

---

### Прод: 3 ЦОДа, нагрузка

Ниже — правила. Число worker-нод «под терабайты» **не** ставится: нагрузки нет.

#### Шаг 0. Выбор макроархитектуры (сделать до установки)

Три правдивых варианта. Четвёртый («etcd в одном ЦОДе, воркеры во всех трёх, и мы переживём смерть ЦОДа с etcd как управляемый кластер») — **не** HA control plane.

**Вариант A — stretch: один кластер, ноды во всех трёх ЦОДах, etcd 1+1+1 (или 2+2+1).**

- Разработчикам один kubeconfig, один API.
- Падение 1 ЦОДа: при 3 etcd кворум из 2 жив → API жив, scheduler может поднимать поды на оставшихся нодах (**если** образы и PVC там есть).
- Каждая запись в API платит за межЦОДовый Raft.
- Сетевой partition «1 ЦОД vs 2» изолирует меньшинство: локальный API в меньшинстве не запишет в etcd.
- Официальная рекомендация etcd «держитесь одного ЦОДа» здесь **сознательно нарушается** ради домена отказа.

**Вариант B — три независимых кластера (по одному в ЦОДе).** etcd каждого кластера **не** растянут.

- Соответствует «etcd в одном ЦОДе».
- Падение ЦОДа убивает **только** его кластер. Остальные API живы.
- Нет единого «kubectl на всю страну»: нужен GitOps (или аналог) и схема трафика/данных между площадками.
- Stretch-Kafka из соседнего документа потребует связности брокеров **поверх** трёх кластеров (маршрутизация pod CIDR, отдельная сеть брокеров, или Kafka вне Kubernetes).

**Пока RTT не измерен, нельзя честно выбрать A.**  
Дальше как **консервативный прод при неизвестной сети** описан **вариант B** (он не спорит с документацией etcd). Вариант A — целевой только после замера, если сеть метро-класса и вы принимаете связанный blast radius одного etcd.

##### Сильные / слабые стороны stretch (A)

| Сильное | Слабое |
|---|---|
| Один API, проще ментальная модель | etcd чувствителен к RTT и jitter; официально «лучше один ЦОД» |
| Scheduler сам уносит поды с мёртвой зоны (если есть ёмкость и диски) | Один плохой апгрейд/баг control plane бьёт все три ЦОДа |
| Удобно для stretch-Kafka внутри кластера | Нужен **межЦОДовый** HA-балансировщик apiserver |
| | Не переживает потерю двух ЦОДов (при 3 etcd) |

##### Сильные / слабые стороны трёх кластеров (B)

| Сильное | Слабое |
|---|---|
| etcd локальный, предсказуемый | Три upgrade, три PKI, три набора аддонов |
| Blast radius ограничен ЦОДом | Приложение само должно быть активно в нескольких ЦОДах |
| Согласовано с гайдом etcd | Stretch-Kafka сложнее по сети |
| Локальный LB apiserver проще | Без GitOps конфиги разъедутся за месяц |

##### Сильные / слабые стороны «все etcd в одном ЦОДе, воркеры везде» (не рекомендуется под вашу цель)

| Сильное | Слабое |
|---|---|
| etcd счастлив по латентности | Смерть ЦОДа с etcd = нельзя управлять кластером; рестарт подов на живых площадках не произойдёт |
| Дешевле по железу control plane | Создаёт иллюзию «у нас ноды в трёх ЦОДах, значит HA» |

#### Control plane и etcd

kubeadm требует для HA: **нечётное** число control plane (помогает выбору лидера при отказе зоны) и для external etcd — **нечётное** число членов отдельно.

| Схема | Минимум хостов | Что переживёт | Чего не переживёт |
|---|---|---|---|
| Stacked 3 (по 1 в ЦОД) — только вариант A | 3 CP | 1 ноду CP или 1 ЦОД | 2 ЦОДа; одновременный рестарт CP в живом ЦОДе, пока другой уже мёртв |
| External 3+3 — вариант A | 3 CP + 3 etcd | Отказ CP **или** etcd-машины порознь легче, чем stacked | Дороже; сеть CP↔etcd тоже критична |
| Stacked 3 **внутри каждого** ЦОДа — вариант B | 9 CP на три кластера | Смерть чужого ЦОДа | Смерть своего ЦОДа (этот кластер мёртв) — так и задумано |

Для **одного** кластера в проде stacked 3 — допустимый старт (это дефолт kubeadm и документированный минимум HA). External etcd — когда готовы платить машинами за развязку IO: документация kubeadm прямо пишет, что stacked связывает судьбу API и etcd на одной ноде.

Правила etcd в проде (официальные hardware guidelines — **отправная точка**, не замер вашего кластера):

- выделенные машины или хотя бы выделенный диск + отсутствие соседей, которые бьют fsync;
- SSD; для нагруженных контуров ориентир **500 sequential IOPS**; типичная память **8 ГиБ** (тяжелее — 16–64);
- 1 GbE достаточно «для обычных» деплоев, 10 GbE ускоряет восстановление члена;
- не RAID1 «для надёжности» вместо кворума: etcd уже реплицирует; RAID-rebuild вреден для латентности (как у Kafka).

Квота БД: дефолт 2 ГиБ, предлагаемый потолок обычной среды 8 ГиБ. Компакция и дефрагментация — регулярная операция, не «когда диск красный».

#### Балансировщик kube-apiserver

HA-гайд kubeadm: сначала LB, DNS-имя = `ControlPlaneEndpoint`, проверка — TCP :6443.

В варианте A LB должен пережить отказ ЦОДа (anycast / DNS с health check / пара балансировщиков в разных ЦОДах). Один VIP в одном ЦОДе = скрытый SPOF.

В варианте B достаточно локального HA внутри ЦОДа (keepalived/haproxy на двух машинах той же площадки).

Клиенты (kubectl, контроллеры, kubelet) ходят **на endpoint**, не на «первый master».

#### Worker-ноды, зоны, масштабирование нагрузки

На каждой ноде:

```
topology.kubernetes.io/zone=<id ЦОДа>
```

Иначе scheduler не знает ЦОДы. Реплики Deployment без `topologySpreadConstraints` имеют право сесть в один зал.

Пулы нод (taint + dedicated):

- `control-plane` — только control plane (kubeadm так и делает);
- `platform` — Kafka, etcd-не-кластерный, тяжёлые БД (как в документе Kafka: не делить page cache с batch);
- `general` — микросервисы, Camunda workers;
- при необходимости `ingress` / `integration-dmz`.

Масштаб **когда появятся цифры**:

1. Замерить CPU/RAM/сеть сервисов и QPS к apiserver.
2. Выставить requests ≈ факт, limits по политике (без requests — BestEffort, их выкинут первыми).
3. HPA на статeless. Для Kafka/БД HPA «просто добавь под» **не** увеличивает партиции и не создаёт реплики данных.
4. Добавлять worker-ноды **равномерно по ЦОДам** (в A — внутри одного кластера; в B — в каждом кластере по потребности).
5. Следить за etcd size и latency API: «ещё 200 нод» может упереться в control plane, не в CPU воркеров.

Числа нод из таблиц etcd (50 / 250 / 1000) — **примеры нагрузки на сам etcd** в документации etcd, не расчёт вашей системы.

#### Хранилище

- Для etcd и для Kafka `log.dirs` — **локальный** диск, не NFS.
- Для приложений — StorageClass с **WaitForFirstConsumer** и привязкой к зоне, иначе PVC в ЦОДе A, под в B.
- Репликация тома между ЦОДами — свойство **СХД/CSI**, его нужно требовать отдельно. Kubernetes его не включает флажком.

#### Безопасность прода (без этого кластер не считается настроенным)

Слои, все нужны:

1. **Сеть до API** — только с jump/VPN/bastion, не 6443 в интернет.
2. **TLS** — kubeadm включает для API и etcd; не выключать проверку сертификатов «чтобы завелось».
3. **Аутентификация людей** — OIDC к корпоративному IdP (или клиентские сертификаты). Файл `admin.conf` с cluster-admin — не рабочий процесс на 50 человек.
4. **RBAC** — каждому сервису свой ServiceAccount, только свои namespace/ресурсы. Не `cluster-admin` приложениям.
5. **PSA** — для прикладных namespace `restricted` или как минимум `baseline`; `privileged` только kube-system и оговорённым операторам (CSI, CNI).
6. **NetworkPolicy** — default-deny в namespace, затем разрешить DNS, свои зависимости, интеграционный API — отдельно (он смотрит в госсеть).
7. **Encryption at rest** для Secrets (минимум) через `EncryptionConfiguration` **до** появления боевых секретов, затем `replace` существующих Secret, чтобы перешифровать.
8. **Audit log** apiserver — кто читал Secret и менял RBAC.
9. **Образы** — только свой registry; в проде не `:latest`; по возможности подпись/скан (это уже политика ИБ, не ядро Kubernetes).

Шифрование Secrets:

| Способ | Когда | Слабое место |
|---|---|---|
| **KMSv2** (рекомендация Kubernetes 1.36) | Есть KMS/HSM/Vault-plugin | Зависимость: если KMS недоступен, API может не расшифровать |
| **aesgcm** локальным ключом | Нет KMS на старте | Ключ на диске control plane; нужна ротация и защита файла |
| **identity** (дефолт) | Никогда в проде | plaintext в etcd |

KMSv1 не использовать: deprecated с 1.28, disabled by default с 1.29.

Прочее, без чего «безопасность» дырявая:

- ротация сертификатов кластера (у kubeadm по умолчанию **1 год** — заложить процедуру, не вспоминать в день X);
- секреты не в Git, не в открытом ConfigMap;
- ограничить anonymous-доступ (не оставлять «мир может list'ить»);
- не публиковать Kubernetes Dashboard с token-admin;
- отдельные kubeconfig на CI с узким RBAC, не тот же, что у человека-админа.

##### Сильные / слабые стороны выбранной ИБ-схемы (TLS + OIDC + RBAC + PSA + NetworkPolicy + encryption)

| Сильное | Слабое |
|---|---|
| Закрывает вход, «кто ты», «что можно поду», «что можно по сети», Secrets в etcd | NetworkPolicy мёртв без правильного CNI |
| PSA встроен, без внешнего PSP (PSP давно убрали) | `restricted` ломает «как привыкли» образы (root, capabilities) — это плата |
| KMSv2 — штатный сильный вариант | Нужен живой KMS; aesgcm проще, но ключ рядом с etcd |
| Не зависит от конкретного вендора дистрибутива | Не ГОСТ; admission-webhook'и (OPA/Kyverno) — отдельное ПО и свой HA |

#### Kubernetes-специфика прода (и A, и B)

- PDB на каждую критичную нагрузку с >1 репликой.
- Drain нод **по одной зоне/ЦОДу**, не параллельно все три.
- Не ставить etcd/Kafka на overlay с большим jitter без замера.
- Лимиты памяти подов должны оставлять ноде память на kubelet и page cache (для Kafka это разобрано в его файле).
- Бэкап etcd (снимок) **регулярно**, проверка восстановления на стенде. Без этого отказ кворума = сбор кластера заново.
- Апгрейд: сначала патч текущей minor, потом 1.36 → следующая minor **без прыжка**. Порядок: apiserver → controller-manager/scheduler → kubelet (с drain). kubelet новее API — нельзя.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами. Решение A vs B. Согласовать с решением по Kafka.
2. Спроектировать LB apiserver, зоны, пулы нод, CNI (overlay vs native routing), CSI.
3. Поднять control plane 1.36.4 (на препроде — полная схема кворума).
4. Включить encryption at rest, audit, PSA, заготовки NetworkPolicy **до** боевых приложений.
5. Поднять мониторинг etcd/API. Прогнать отказ одной CP-ноды.
6. Выкатить платформу (Kafka и т.д.) с topologySpread и правильными StorageClass.
7. Нагрузить (хотя бы синтетикой) API и etcd, не только бизнес-QPS.
8. Прогон «ЦОД недоступен» на препроде: выключить зону/кластер, проверить и управление, и приложения.

Без пункта 8 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Либо 3 независимых кластера, либо stretch с etcd 3/5 и измеренным RTT; LB apiserver не SPOF одной площадки; бэкап etcd; переживание 1 ЦОДа **проверено** |
| Производительность / масштаб | Не требуется | Рост подов и нод раздельно; requests; HPA для stateless; etcd не склад терабайт; локальные диски для etcd; зоны и topologySpread |
| Безопасность | Изолированная сеть | API не в интернете; OIDC/RBAC least privilege; PSA; NetworkPolicy с рабочим CNI; encryption at rest; audit; свой registry |

**Не готов к проду**, если: один etcd «на всех трёх ЦОДах в уме», PLAIN Secrets в etcd, CNI без NetworkPolicy при обещании изоляции, все реплики без zone labels, cluster-admin у приложений, NFS под etcd, сертификаты без процедуры ротации, RTT неизвестен, а схема уже stretch.

Утверждения про конкретный миллисекундный порог RTT «для здорового etcd» в документации **проекта Kubernetes отсутствуют**. Цифра «< 50 ms», встречающаяся у вендоров (например OpenShift/OKD), **не** выдаётся здесь за стандарт Kubernetes и не используется как критерий выбора A/B.

Дефолты heartbeat/election etcd и правило «≥ 10× RTT» — из документации etcd; подставлять в них ваш замер можно только после того, как замер появится.
