# Grafana 13.2.0 — развёртывание и настройка

Версия ПО: **Grafana 13.2.0** (релизная дата 18 августа 2026; на дату подготовки документа это последний стабильный релиз линии 13.2).  
Документация: https://grafana.com/docs/grafana/latest/  
Образ OSS: `grafana/grafana:13.2.0`. Образ Enterprise (тот же функционал OSS + возможность включить коммерческие плагины лицензией): `grafana/grafana-enterprise:13.2.0`.  
На Kubernetes официальный путь сообщества: Helm-чарт **`grafana-community/grafana` 12.11.2** (опубликован 23 августа 2026, `appVersion` **13.2.0**). Репозиторий: `https://grafana-community.github.io/helm-charts`, OCI: `oci://ghcr.io/grafana-community/helm-charts/grafana`. Kubernetes: `^1.25.0-0`.  
Альтернатива GitOps: **Grafana Operator**, Helm `oci://ghcr.io/grafana/helm-charts/grafana-operator` **5.25.0** (документация оператора на 24 августа 2026). Это другой инсталлятор, не «тот же чарт».

Этот текст — не мануал «скопируй `helm install`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Grafana **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API) как отдельный продукт. Ниже — как поставить слой **визуализации и алертинга** на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это не хранилище метрик, не SIEM, не замена Wazuh/Falco/WAF и не «кнопка мониторинг включена».

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Grafana** | Веб-приложение: рисует графики, дашборды, шлёт алерты. Само **не хранит** ряды метрик Kafka/Camunda. Оно *спрашивает* другие системы и показывает ответ. |
| **Data source (источник данных)** | Подключение, откуда Grafana читает: Prometheus, Loki, Elasticsearch/OpenSearch, PostgreSQL озера, Tempo и т.д. Без источника дашборд пустой. |
| **Dashboard / panel** | Экран из панелей. Панель = один запрос к источнику + картинка (график, таблица, …). |
| **Provisioning** | Дашборды, источники и алерты кладут файлами (YAML/JSON) при старте, а не только кликами в UI. Это GitOps, а не «настроил руками и забыл». |
| **Explore** | Экран «пощупать запрос» без сохранения дашборда. |
| **Unified Alerting** | Штатный алертинг Grafana (не старый «alert на панели», тот выключен). Правило = запрос к источнику + условие «когда орать». |
| **Alert rule / contact point / notification policy** | Правило «что сломалось» / «куда писать» (email, webhook, Telegram, …) / «каким маршрутом». |
| **Scheduler / Alertmanager (встроенный)** | Scheduler **оценивает** правила (ходит в Prometheus и т.п.). Встроенный Alertmanager **отправляет** уведомления. Это не отдельный процесс Prometheus Alertmanager, пока вы его сами не подключите снаружи. |
| **HA Grafana** | Несколько процессов Grafana за балансировщиком, все смотрят в **одну** общую БД (Postgres/MySQL). Active-active: любой живой узел обслуживает UI. |
| **SQLite** | Встроенный файл-БД по умолчанию. Один файл на одном диске. Для прода и для нескольких реплик **не** годится (прямо сказано в документации установки). |
| **Shared database** | Общая MySQL **8.0+** или PostgreSQL **12+**, куда все реплики Grafana пишут пользователей, дашборды, состояние алертов. |
| **Memberlist / gossip** | Протокол «посплетничать» между встроенными Alertmanager'ами, чтобы **не слать одно уведомление N раз**. Порты **9094/TCP и 9094/UDP**. |
| **`ha_peers`** | Список соседей для gossip (или DNS headless-сервиса в Kubernetes). Без этого несколько реплик = дубли писем при живом UI. |
| **Single-node evaluation** | Режим (в документации Grafana 13.x — **public preview**): правила считает **один** узел, остальные только UI. Снижает нагрузку на источники в N раз. Есть короткая дыра оценки при смене primary. |
| **Grafana Live** | WebSocket «события в браузер сразу» (правки дашборда, стримы). По умолчанию **in-memory**, лимит **100** соединений на процесс. В HA без Redis стримы не общие между подами. |
| **Image Renderer** | **Отдельный** сервис (Chromium): рисует PNG дашборда для письма. Не часть бинаря Grafana. Дефолтный токен `-`. |
| **`secret_key`** | Ключ, которым Grafana шифрует пароли источников в своей БД (AES, envelope encryption, провайдер по умолчанию `secretKey.v1`). В `defaults.ini` 13.2.0 зашито одно и то же значение на все установки мира. |
| **`admin` / `admin`** | Логин и пароль первого администратора. Ставятся **один раз** при первом старте. Потом правка `grafana.ini` пароль в БД **не меняет**. |
| **Organization / folder / RBAC** | Организация = «арендатор» внутри Grafana. Папки и роли (Viewer/Editor/Admin + finer RBAC) режут, кто какие дашборды видит. |
| **Service account** | Машинный пользователь с токеном для API (GitOps, алерты). Старые API keys вендор выводит; для автоматизации берут service account. |
| **Anonymous / externally shared dashboard** | Анонимный вход без логина / «публичная ссылка на дашборд». Для контура с гособменом и ПДн это дыра, не «удобство». |
| **Data source proxy** | Grafana **с сервера** ходит в источник от имени пользователя. Это удобно и это SSRF: Grafana видит внутреннюю сеть. |
| **`/metrics`** | Служебные метрики самого Grafana. По умолчанию **без** basic auth, пока не зададите `basic_auth_username` / `basic_auth_password`. |
| **`/api/health`** | Точка health-check для балансировщика. |
| **`root_url`** | Канонический URL, как пользователь открывает Grafana в браузере (`https://grafana.example.internal/`). Без него ломаются OAuth callback и проверка Origin у Live. |
| **Sticky session** | «Липкость» на балансировщике: один пользователь всегда на один под. Для Grafana **не обязательна**: сессии живут в общей БД. Документация HA прямо это пишет. |
| **LGTM** | Маркетинговая связка Grafana Labs: **L**oki (логи), **G**rafana, **T**empo (трейсы), **M**imir (метрики). Grafana — буква G, не весь стек. |
| **Prometheus / Mimir** | Хранилища метрик. Prometheus — локальный TSDB; Mimir — долгий/большой объём. Grafana их **запрашивает**, не заменяет. |
| **kube-prometheus-stack** | Популярный Helm «Prometheus Operator + куча экспортеров + Grafana». Grafana там **вложенный** чарт. Дефолты этого стека ≠ прод-HA Grafana. |
| **Stretch** | Один логический Grafana-кластер (одна БД, одни `ha_peers`), поды физически в нескольких ЦОДах. |

## Основные элементы системы и зависимости

### Что входит в Grafana 13.2.0 (это одно ПО)

- Процесс **`grafana`** (HTTP UI/API на порту **3000**, опционально TLS самим Grafana).
- **Конфиг** `grafana.ini` / `custom.ini` (или переменные `GF_*`).
- **БД конфигурации**: SQLite *или* Postgres/MySQL.
- **Unified Alerting** (Scheduler + встроенный Alertmanager).
- **Live** (WebSocket на том же HTTP-порту).
- Каталог **плагинов** и каталог **provisioning**.

Это не кластер с кворумом вроде Kafka/etcd. Несколько реплик Grafana — это несколько **одинаковых** процессов с общей БД и (для алертов) gossip/Redis.

### Чего в Grafana нет (частая путаница)

| Нужно системе | Это не Grafana | Зачем помнить |
|---|---|---|
| Хранить терабайты метрик/логов/трейсов | Prometheus, Mimir, Loki, Tempo, OpenSearch, … | «Поставили Grafana» ≠ «мониторинг выдержал нагрузку». Ёмкость — у источника. |
| Собрать метрики с нод и подов | kube-state-metrics, node_exporter, cAdvisor, JMX/kafka_exporter, Alloy/Agent | Grafana ничего не скрейпит с Kafka сама, пока нет источника и экспортёра. |
| SIEM / FIM / syscall-детект | Wazuh, Falco | Дашборд «красные графики» не заменяет разбор security-событий. |
| WAF / NetworkPolicy | SafeLine, политики кластера | Grafana — ещё один HTTP-вход в контур. |
| Отказоустойчивость **самой** БД Grafana | Patroni / CloudNativePG / управляемый Postgres | Документация HA Grafana: настройка HA Postgres/MySQL **вне** её гайда. Падение БД = падение всех реплик Grafana. |
| Кворум «2 из 3 Grafana-подов» | Нет | Жив хотя бы один под **и** жива БД — UI есть. Мертва БД — UI нет, даже если поды зелёные. |
| Распределение оценки алертов «каждый под считает свою долю» | В GA этого нет | По умолчанию **каждый** под считает **все** правила. Нагрузка на Prometheus × N. Single-node evaluation — preview. |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS 1.2/1.3 — не криптография по требованиям КИИ, если ИБ их выдвинет. |
| Порог RTT между ЦОДами | Нет | Для gossip есть `ha_peer_timeout` (дефолт **15s**) «если серверы в разных регионах или высокая задержка» — миллисекунд в доке нет. |
| Официальный SLA 24/7 | Нет | Есть модель HA и оговорка Alertmanager: лучше дубль уведомления, чем тишина. |

### Официальные порты (менять можно, но это контракт сети)

| Порт | Назначение |
|---|---|
| **3000/TCP** | UI, API, `/metrics`, `/api/health`, WebSocket Live (upgrade с того же HTTP) |
| **9094/TCP + 9094/UDP** | Gossip встроенных Alertmanager. Документация: **оба** протокола. Закрытый UDP между ЦОДами = сломанный HA алертинга на Memberlist |
| 5432 / 3306 | Не Grafana, а Postgres/MySQL общей БД |
| 6379 | Не Grafana, а Redis: опция HA алертинга **или** Live HA engine |
| 8081 | Типичный порт Image Renderer, если включите |

Балансировщик перед 3000 официально входит в схему HA (reverse proxy, лучше TLS termination на нём). У вас уже описан HAProxy — это как раз этот слой, не часть образа Grafana.

### Зависимости окружения (обязательны)

- **ОС:** Linux/Windows/macOS по гайду установки; в Kubernetes — контейнер.
- **БД:** для теста SQLite допустим. Для прода: **PostgreSQL 12+** или **MySQL 8.0+**. Grafana поддерживает те версии СУБД, которые на момент релиза ещё поддерживает апстрим; миграция SQLite→Postgres — **ваша** операция, не зона Grafana Support.
- **Браузер** пользователей (современный; IE не рассматриваем).
- **Kubernetes ≥ 1.25**, если идёте чартом 12.11.x.
- **Источник метрик/логов** — отдельно спроектированный. Без него Grafana — пустая рамка.
- **Балансировщик HTTP(S)** с поддержкой WebSocket, если Live нужен.
- **PKI / Ingress / HAProxy** для TLS. Сам Grafana умеет `protocol = https`, но типичный прод — TLS на прокси.
- Исходящая сеть до `stats.grafana.org`, `grafana.com`, `secure.gravatar.com`, `snapshots.raintank.io` — **по умолчанию включена** рядом флажков. В закрытом контуре её надо **выключить**, а не «надеемся, файрвол отрежет».

### Как Grafana стыкуется с вашей архитектурой

```
Микросервисы / Kafka / Camunda / интеграционный API / ноды K8s
        │  экспортёры (JMX, redis, postgres, blackbox, …)
        ▼
  Prometheus или Mimir   (+ опционально Loki / Tempo)
        ▲  PromQL / LogQL / TraceQL
        │
   Grafana × N  ◄── PostgreSQL (пользователи, дашборды, алерты)
        ▲
        │  HTTPS :443
   HAProxy / Ingress  (люди, SSO)
```

Grafana **не** участник event-sourcing, **не** ходит в госслужбы вместо интеграционного API и **не** является озером эталона. Она может *показать* метрики этих систем и *заорать*, если лаг консьюмера, очередь Camunda или 5xx интеграционного API вышли за порог — при условии, что эти сигналы **собраны** в источнике.

Пересечение с уже описанным:

- **HAProxy** — вход на Grafana и, при желании, на Prometheus.
- **Vault** — пароль БД Grafana, `secret_key`, client secret SSO, токены service account. Сама Grafana пароли источников шифрует в своей БД; это не замена Vault.
- **Wazuh / Falco** — другой контур (security). Можно *отдельным* дашбордом смотреть их метрики, если экспортёры есть. Не смешивать «SOC видит атаку» и «SRE видит CPU».
- **Kubernetes** — оркестрация подов Grafana. Диск SQLite на PVC при `replicas > 1` — ловушка.

## Краткие вводные

### Зачем вам Grafana в этой архитектуре

У вас Kubernetes, Kafka, процессный движок, 30+ интеграций, ожидание непрерывной работы и «терабайты». Типичные вопросы, на которые Grafana отвечает **если** снизу жив источник:

1. «Жив ли брокер, растёт ли лаг консьюмера, не упёрлись ли в диск» — дашборды + алерты.
2. «Интеграция с ведомством X начала отвечать 15 секунд» — не SIEM, а SLO/латентность API.
3. «Camunda-процесс завис в инциденте» — метрики движка, не BPMN-движок сам по себе.
4. «Кластер K8s деградировал в одном ЦОДе» — обзор нод/подов.

Без Grafana эти данные часто есть только в `kubectl top` и у того, кто умеет PromQL в консоли Prometheus.

### Как устроена отказоустойчивость (идея, не магия)

Это **не** Raft. Три независимых слоя:

**1) Процессы Grafana (UI + оценка алертов)**

| Что падает | Что происходит по документации |
|---|---|
| Один под Grafana при N≥2 и живой БД | Балансировщик перестаёт слать на него трафик. UI жив. Алерты: остальные поды **продолжают оценивать все правила** (дефолт). |
| Все поды Grafana | Нет UI и нет оценки правил Grafana. Источник метрик (Prometheus) при этом может быть жив — данные не пропали, пропал взгляд и встроенный алертинг. |
| Нет `ha_peers` / закрыт 9094 | UI может быть «HA», а письма/webhook **дублируются** с каждого пода. Документация: чтобы не дублировать алерты, нужны отдельные шаги. |
| Live без Redis в HA | Пользователь на поде A не видит realtime-событие, ушедшее в под B. Для классических дашбордов с refresh это часто незаметно. |

**2) Общая БД (ядро состояния Grafana)**

| Что падает | Что происходит |
|---|---|
| SQLite на PVC одного пода | Падение ноды/пода = нет дашбордов/пользователей, пока диск не вернули. Второй реплики файла нет. |
| Postgres primary, нет реплики | То же: Grafana-поды бегут, но не пишут. Это SPOF. |
| Потеря кворума Postgres (если растянули на 3 ЦОДа вслепую) | Запись дашбордов/алертов встаёт. Это уже история **PostgreSQL**, не Grafana. |

Документация HA: «сначала сделайте MySQL/Postgres высокодоступным, это **вне** данного гайда». Честный вывод: «поставили 3 реплики Grafana» без HA БД — вы нарисовали HA.

**3) Источник данных**

Падение Prometheus/Mimir = пустые панели и failed evaluation алертов. Grafana тут ни при чём. Для «система 24/7» отказоустойчивость мониторинга считается **по самому слабому** из: Grafana-поды, БД Grafana, источник метрик, сеть до них, канал уведомлений (SMTP/webhook).

Alertmanager встроенный: *availability over consistency* — возможны **редкие дубли или перестановка** уведомлений; вендор считает это лучше, чем тишина.

### Как устроено масштабирование

Официальная страница установки режет нагрузку Grafana (не Kafka!) так:

| Тир | Одновременные пользователи | Правила алертов | Источники | Дашборды |
|---|---|---|---|---|
| Small | < 25 | < 100 | < 5 | < 200 |
| Medium | 25–200 | 100–1 000 | 5–25 | 200–2 000 |
| Large | 200+ | 1 000+ | 25+ | 2 000+ |

Железо **процесса Grafana** (не Prometheus, не диск озера):

| Тир | CPU | RAM | Диск хоста БД | Инстансы |
|---|---|---|---|---|
| Минимум «чтобы стартануло» | 1 ядро | 512 МиБ | — | 1 |
| Small | 2 ядра | 2–4 ГиБ | 10–20 ГБ SSD | 1 |
| Medium | 4–8 ядер | 8–16 ГиБ | 20–50 ГБ SSD | **2** за балансировщиком |
| Large | 8–16+ ядер **на инстанс** | 16–32+ ГиБ на инстанс | 50+ ГБ SSD, высокий IOPS | **3+** |
| Large, сеть | 10 Гбит/с или быстрее | | | |

Документация прямо пишет: это стартовые точки, **не** смета под ваши терабайты; валидировать нагрузкой с **вашими** дашбордами. Диск в таблице — у **хоста БД Grafana**, не у TSDB метрик.

Три оси, которые люди путают:

1. **Больше людей смотрят дашборды** → больше реплик Grafana + CPU/RAM на под + не душить `min_refresh_interval` (дефолт не дать refresh чаще **5s**).
2. **Больше правил алертов / короткий interval** → нагрузка на **источник**. При >1000 правил или interval **< 1 мин** документация: оценка алертов может забить CPU и ухудшить дашборды; тогда выносят оценку на отдельные инстансы (remote evaluation) — это уже отдельная схема, не «replicas: 5 на том же Prometheus».
3. **Терабайты рядов** → масштаб **Mimir/Prometheus/Loki**, не `replicas` Grafana. БД Grafana остаётся маленькой (дашборды, юзеры).

Дефолт HA: **N реплик = N одинаковых запросов алертов** в Prometheus. Добавить реплик «для надёжности UI» можно убить источник. Preview `ha_single_node_evaluation = true` как раз про это; в проде его можно рассматривать только понимая статус **public preview** (ломающие изменения возможны, ограниченная поддержка Grafana Labs).

Live: ~**50 КБ RAM на WebSocket**; дефолт **max_connections = 100**. Один пользователь ≈ одно соединение на вкладку.

### Безопасность самой Grafana

Компрометация Grafana с ролью Admin = компрометация **всех паролей источников**, записанных в её БД (они зашифрованы `secret_key`; если ключ дефолтный — шифрование от своего же дефолта). Viewer с доступом к источнику видит данные запросов: метрики интеграций, лаги, иногда PII в label'ах.

Известные дефолты **13.2.0** (`conf/defaults.ini` тега `v13.2.0`):

| Параметр | Значение из коробки | Зачем это опасно |
|---|---|---|
| `admin_user` / `admin_password` | `admin` / `admin` | Первый вход в интернет = чужой Admin |
| `secret_key` | `SW2YcwTIb9zpOOhoPsMm` | Один ключ на все дефолтные инсталлы; дамп БД расшифровывается |
| `reporting_enabled` | `true` | Счётчики на `stats.grafana.org` каждые 24 часа |
| `check_for_updates` / `check_for_plugin_updates` | `true` | GET на `grafana.com` (версию не ставят сами, но контур «звонит домой») |
| `disable_gravatar` | `false` | Браузер/сервер ходит на `secure.gravatar.com` |
| `snapshots.external_enabled` | `true` | Кнопка публикации на `https://snapshots.raintank.io` |
| `cookie_secure` | `false` | Cookie сессии может уехать по HTTP |
| `/metrics` basic auth | не задан | Служебные метрики без пароля |
| Image Renderer `renderer_token` | `-` | Если рендерер включён с дефолтом — кто дотянулся до 8081, тот печатает PNG |

«Включили Grafana LoadBalancer в интернет с `admin`/`admin`» — это новый attack surface, не мониторинг.

Плагины: `allow_loading_unsigned_plugins` в проде не разворачивать «чтобы завелось». Image Renderer — отдельный Chromium; исторически были уязвимости чтения файлов через render. Нужен — свой токен, NetworkPolicy «только от Grafana», не в интернет.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём self-hosted Grafana OSS 13.2.0**, не Grafana Cloud. Облако вендора в схеме с тремя своими ЦОДами не предполагалось. Enterprise-образ без лицензии = тот же OSS-функционал; коммерческие плагины/KMS-провайдеры encryption в этом тексте **не** включаются.
2. **Лицензия OSS — AGPLv3.** Если юротдел запрещает AGPL при модификации/сетевом предоставлении — путь: не патчить Grafana **или** брать Enterprise binary (проприетарный, free-to-use по FAQ Grafana Labs) **или** коммерческая лицензия. Это юридическое допущение, не техническое.
3. **Прод крутится в Kubernetes**, инсталлятор Grafana — Helm-чарт **grafana-community/grafana 12.11.2** с образом **13.2.0** (pin по digest, не `latest`). Grafana Operator 5.25.0 — допустимая альтернатива с теми же правилами HA (общая БД + `ha_peers`).
4. **Общая БД Grafana — PostgreSQL 12+**, отдельная база `grafana`, не та же, что у Camunda/озера. HA этой БД — отдельное ПО (у вас в правилах диалога упоминался PostgreSQL как платформенный компонент). Пока Postgres не описан своим файлом — считаем, что для прода нужен **кластер Postgres**, а не docker-контейнер `postgres:latest` рядом.
5. **Три ЦОДа = три зоны отказа.** Grafana-поды можно размазать. **Postgres и gossip 9094** — нет. Пока RTT неизвестен, честный прод: не растягивать **синхронный** Postgres на три площадки вслепую; Grafana-реплики — да, если 3000 и 9094 ходят.
6. **Цель отказа: пережить 1 ЦОД** для UI Grafana, **если** в живых ЦОДах остались под Grafana **и** доступна БД. Пережить 2 из 3, если БД жила только в мёртвых двух — нельзя.
7. **Нагрузка неизвестна** — поэтому **нет** цифры «N реплик и M millicores». Есть тиры вендора и рычаги (реплики UI, не умножать оценку алертов бездумно, вынос Prometheus).
8. **Источник метрик будет** (Prometheus в кластере или Mimir). Этот документ его не проектирует. Без него «готовность Grafana» бессмысленна.
9. **SSO/IdP будет или LDAP.** Локальный `admin` в проде — break-glass, не ежедневный вход. Generic OAuth/LDAP — штатные модули OSS.
10. **Закрытый контур.** `reporting_enabled`, проверки обновлений, Gravatar, внешние snapshots — выключаем. Плагины — из **вашего** registry, не с grafana.com в рантайме.
11. **Тестовый стенд изолирован.** На нём допустимы SQLite, `admin`/`admin`, self-signed. В прод не копируем.
12. **Camunda, Kafka, озеро, интеграционный API** — объекты наблюдения, не часть Grafana. Их метрики должны появиться в источнике, иначе Grafana слепа ровно там, где деньги и гособмен.
13. **Image Renderer и Live HA на Redis в первом проде не обязательны.** Включаем, когда нужны PNG в письмах / realtime на нескольких подах. Иначе лишний Chromium и лишний Redis.
14. **Формального SLO на «алерт за 30 секунд» нет.** Оценка + `ha_peer_timeout` + SMTP — ваша политика, не обещание Grafana.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили Helm и открыли :3000».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и фильтрация UDP между ЦОДами** | Memberlist на 9094 **UDP+TCP**. Городской firewall, дропающий UDP, = дубли алертов или распад кластера Alertmanager. Тогда путь — Redis HA для alerting (документация: Memberlist предпочтителен; Redis — если прямое общение невозможно). |
| **Один K8s на 3 ЦОДа или три кластера** | От этого зависит: один Deployment Grafana + один Postgres **или** три Grafana (три правды дашбордов — плохо для дежурства). |
| **Где живёт Postgres Grafana** | Поды Grafana без локальной БД переживают зону. Postgres primary в одном ЦОДе — при смерти этой зоны Grafana во всех трёх мертва для записи. Нужен явный DR Postgres. |
| **Какой бэкенд метрик и какой retention** | Терабайты — вопрос Mimir/ Loki, не Grafana. Неверная ёмкость TSDB = «Grafana тормозит», хотя тормозит запрос в источник. |
| **Число дашбордов, refresh, правил, одновременных зрителей** | Без этого нельзя выбрать тир Small/Medium/Large. «Готовы к высокой нагрузке» без замера — не смета. |
| **Куда смотрит UI** (только внутренняя сеть? SSO?) | Публичный 443 с `admin`/`admin` — инцидент. |
| **152-ФЗ / КИИ / ПДн в метках** | PromQL может вытащить ФИО из label. Viewer Grafana = читатель этих данных. Нужна политика, что кладут в метрики. |
| **Канал алертов** (почта внутри, Telegram SaaS, webhook в PagerDuty) | Исход в интернет; дубли при кривом HA; секреты webhook в Grafana DB. |
| **Кто дежурит** | Grafana без on-call — красивые графики после аварии. |
| **Есть ли уже kube-prometheus-stack / другой Grafana** | Два Grafana без общей БД = два набора дашбордов. Вложенный Grafana стека часто оставляют на SQLite. |
| **Юридический AGPL** | Модифицированный Grafana как внутренний сервис может быть ок, может быть не ок — решает юротдел, не Helm. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **Grafana 13.2.0** и способ: пакет/Docker **или** Helm 12.11.2 **или** Operator 5.25.0. Не смешивать 12.x UI с 13.2 БД «на глаз» без upgrade guide.
2. Сначала **БД** (на тесте — SQLite), потом Grafana, потом **источник** и provisioning дашборда «Hello, Prometheus».
3. Выпустить **свои** `admin_password` (до первого старта!), `secret_key`, пароль БД, TLS **до** вывода в прод. Дефолт `secret_key` после того, как источники уже сохранены, менять больно: пароли источников надо пересохранить / штатная миграция encryption.
4. Включить здоровье: `/api/health` на LB; scrape `/metrics` **с auth**; для HA — `grafana_alertmanager_cluster_members`.
5. Алерты: либо 1 реплика на тесте, либо в проде сразу `ha_peers` + порты 9094. Не «сначала 3 реплики, gossip потом».
6. Один контролируемый алерт (например `up == 0` тестового job) должен **дойти** до contact point.
7. Только потом — SSO, папки, RBAC, on-call.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** увидеть дашборд с *вашего* Prometheus/экспортёра, понять UI, шум правил. **Не** цель: доказать, что прод переживёт падение ЦОДа и 200 одновременных зрителей.

Два официальных минимальных пути (выберите один):

**Путь A — Docker OSS** (быстрее понять продукт):

```text
docker run -d --name=grafana -p 3000:3000 grafana/grafana:13.2.0
```

Первый вход: `admin` / `admin`, вендор просит сменить пароль. Данные — SQLite внутри контейнера. Удалили контейнер без volume — удалили дашборды.

**Путь B — Helm в namespace `monitoring`** (ближе к вашему оркестратору):

- чарт `grafana-community/grafana` **12.11.2**;
- `replicas: 1`;
- SQLite (дефолтная БД Grafana) **или** маленький Postgres «для тренировки миграции»;
- Ingress/port-forward только во внутренней сети;
- образ `grafana/grafana:13.2.0`.

Режим «3 реплики + SQLite + PVC RWO» для знакомства **не нужен**: получите `Multi-Attach` или три расходящихся SQLite.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| БД | SQLite | Нет требования пережить выкат пода |
| Реплики | 1 | Нет HA-цели |
| `ha_peers` | не нужен | Один Alertmanager |
| PKI | self-signed / port-forward | Иначе команда утонет в сертификатах раньше, чем в PromQL |
| Пароль admin | сменить с `admin`, но не городить SSO | На тесте важнее контур данных |
| reporting / gravatar / snapshots | можно оставить, **если** стенд без ПДн и с интернетом | В чек-лист прода не переносить |
| Image Renderer / Live Redis | выкл | Не цель |
| CPU/memory | 512 МиБ–2 ГиБ | Не цель — ёмкость Large |

#### Чего на тесте **не** стоит упрощать

- Тег **13.2.0**, не `latest`.
- Хотя бы один источник и дашборд, который показывает **не** пусто (например `up` или CPU ноды). Проверка: панель обновилась и в Explore тот же запрос живой.
- Понимание: дашборд в UI без provisioning **умрёт** вместе с SQLite. Имеет смысл сразу сохранить JSON в git.
- Не публиковать 3000 в интернет «на минутку».
- Не ставить unsigned plugins с форума.

#### Сильные стороны такой схемы

- Поднимается за минуты (Docker) или за час (Helm).
- Совпадает с официальным quickstart.
- Дешево показывает, какие метрики у вас **уже есть**, а каких нет (часто нет лагов Kafka и SLA интеграций).

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет общей БД, нет gossip.
- Успешный график на ноутбуке **не** доказывает, что 3 реплики не умножат нагрузку на Prometheus.
- Привычка `admin`/`admin` и LoadBalancer из примера чарта уедет в прод, если не запретить явно.

Практическая рекомендация: препрод = маленький **прод-профиль** (Postgres, 2 реплики, `ha_peers`, свои секреты, SSO-заглушка или LDAP, reporting выкл), даже без боевого трафика.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер Grafana под терабайты озера» **нет** — нагрузки нет, и эти терабайты Grafana не хранит. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Grafana плохо переживает **три независимых UI** (три набора дашбордов, три набора алертов) и плохо переживает **слепой stretch Postgres**.

**Вариант A — один Kubernetes на 3 ЦОДа (зоны), одна Grafana.**

- Deployment Grafana **≥ 2** (для Medium вендор пишет 2, для Large 3+), podAntiAffinity / topology spread: **не все реплики в одном ЦОДе**.
- Один Postgres-кластер как shared database (синхронная реплика — по замеренному RTT; третья площадка чаще **асинхронный** DR, не третий синхронный узел «на глаз»).
- Headless Service + `headlessService: true` в чарте; в `grafana.ini`:
  - `unified_alerting.ha_listen_address = ${POD_IP}:9094`
  - `ha_advertise_address = ${POD_IP}:9094`
  - `ha_peers = <release>-headless:9094` (как в README чарта)
  - `ha_peer_timeout`: дефолт 15s; поднимать **только после** замера, не «на всякий случай 2 минуты».
- Перед 3000 — **HTTPS LB** (HAProxy/Ingress). Sticky **не** требуется. WebSocket: `Upgrade`/`Connection`, иначе Live (если включите) молчит.
- NetworkPolicy: 3000 только от LB/mesh; 9094 только между подами Grafana; 5432 только от Grafana к Postgres.

**Вариант B — три изолированных Kubernetes.**

Не копировать полную Grafana «как DaemonSet Falco». Falco — агент на ноде. Grafana — **общая** точка правды дашбордов.

Рабочие подварианты:

- **B1.** Поды Grafana (и Postgres) в **одном** кластере/ЦОДе; люди и SSO ходят туда. Метрики с двух других кластеров — **удалённые** Prometheus (federation / remote_write в общий Mimir). Один UI.
- **B2.** Три Grafana с тремя БД — только если готовы тройной GitOps дашбордов и тройные алерты. Обычно хуже.

**Пока топология K8s не зафиксирована, нельзя честно выбрать A или B1.** Дальше — общее.

##### Сильные / слабые стороны (A, один кластер на 3 зоны)

| Сильное | Слабое |
|---|---|
| Один набор дашбордов и алертов | Gossip 9094 и Postgres чувствуют RTT и UDP-фильтры |
| Реплики UI переживают смерть одной зоны | Смерть зоны с Postgres primary без failover = смерть Grafana везде |
| Официальная схема HA (N серверов + LB + shared DB) | Ошибка в provisioning/RBAC сразу везде |
| Оценка алертов продолжается, пока жив ≥1 под | Пока preview single-node выкл, живые поды **умножают** запросы в Prometheus |

##### Сильные / слабые стороны (B1, мозг Grafana в одном месте)

| Сильное | Слабое |
|---|---|
| Postgres и 9094 не обязаны ходить по трём ЦОДам | Падение ЦОДа с Grafana = нет UI/алертов Grafana для всех площадок |
| Проще кворум БД | Нужен явный DR: как поднять Postgres+Grafana на другой площадке **с бэкапом БД** |
| Меньше сюрпризов gossip | Путь людей/SSO к UI пересекает ЦОДы |

##### Слабое место любого stretch без замера RTT

Документация Grafana **не задаёт** «можно при 5 мс, нельзя при 40». Утверждение «3 ЦОДа в одном городе, значит Postgres синхронно на три» — **непроверенное**. Для Memberlist вендор лишь советует увеличить `ha_peer_timeout` при высокой задержке. Измерить: RTT и потери на **5432** (Postgres) и **9094 TCP/UDP** до закупки схемы.

Если UDP 9094 между зонами закрыт — не «надеемся». Либо открыть, либо **Redis** для `unified_alerting` (pub/sub; TLS-поля `ha_redis_tls_*` есть в доке). Live при этом — **отдельный** Redis engine; Sentinel для Live официально **не** поддерживается, рекомендуют Redis Cluster.

#### Grafana-поды (ядро отказоустойчивости *просмотра*)

- `replicas ≥ 2`, лучше 3 при трёх зонах (по одной в зоне, если хватает узлов).
- **Не** вешать RWO PVC с SQLite на Deployment с несколькими репликами.
- `persistence` чарта для sqlite в проде **выкл**; состояние — в Postgres.
- Rolling update + PDB: не убивать все реплики сразу (`minAvailable: 1` как минимум).
- Resources: не 512 МиБ из минимума. Старт как Small (2 CPU / 2–4 ГиБ) и смотреть CPU throttling + latency дашбордов. Limits без requests — шатание; слишком жёсткий CPU limit → медленные алерты и UI.
- `root_url` = тот HTTPS, который видит браузер. `enforce_domain = true` после того, как LB шлёт правильный `Host`.
- `GF_SECURITY_ADMIN_PASSWORD` / секрет чарта задать **до** первого старта. Потом — смена через UI/API, не через env.

**Слабое место:** чарт/`kube-prometheus-stack` «из гайда» с одной репликой и SQLite выглядит как мониторинг, ведёт себя как один диск.

#### Алертинг (ядро отказоустойчивости *дежурства*)

- `unified_alerting` включён (это дефолт современной Grafana). Старый `[alerting] enabled = false`, как в примере Helm HA.
- Gossip настроен **в тот же день**, когда `replicas > 1`.
- Проверка: метрика `grafana_alertmanager_cluster_members` (с Grafana **v12.4** префикс `grafana_`; без него дашборды со старыми именами слепые).
- Contact points не в SaaS без решения ИБ. Webhook в внутренний Alertmanager/On-call — норма.
- Понимать дефолт: **все** поды считают **все** правила. Перед третьей репликой спросить Prometheus, выдержит ли ×3.
- `ha_single_node_evaluation` — только осознанно (preview, дыра при failover primary, очередь broadcast дефолт 200; при куче правил смотреть drop-метрики).
- Внешний Alertmanager (документация «prevent duplicate notifications») — опция, если встроенный gossip не справляется; это ещё один компонент.

Падение всех Grafana-подов: **встроенные** алерты молчат. Если критичные сигналы должны жить без Grafana — дублировать правила во **внешнем** Prometheus Alertmanager. Это не часть дистрибутива Grafana, это архитектурный выбор «кто орёт, когда орёт сам мониторинг-UI».

#### Общая БД

- Отдельная роль `grafana`, отдельная database, `ssl_mode = verify-full` (для Postgres; не `disable`).
- `max_open_conn` настроить под N подов × запас, чтобы не выесть `max_connections` общего Postgres.
- Бэкап БД Grafana = бэкап дашбордов, пользователей, состояния алертов, **зашифрованных** паролей источников. Потеря БД при живом git provisioning дашбордов ещё переживаема; потеря без git — нет.
- Encryption at rest тома Postgres — средствами платформы. KMS-провайдеры envelope encryption в OSS ограничены (`available_encryption_providers` в defaults помечен как Enterprise).

#### Безопасность прода (без этого кластер не считается настроенным)

Три слоя:

1. **Секреты и идентичность**
   - Свой `secret_key` (длинный случайный) **до** заведения источников.
   - Нет `admin`/`admin`. Break-glass лежит в Vault.
   - SSO (Generic OAuth / LDAP) + маппинг групп на роли. Для OAuth `cookie_samesite = lax` (документация: `strict` ломает OAuth).
   - Service account для GitOps, не персональный Admin-токен в CI.
2. **Сеть**
   - UI только из внутренней сети / через SSO-прокси. Не LoadBalancer в интернет.
   - `/metrics` с basic auth или только с Prometheus-сети.
   - `data_source_proxy_whitelist` — не пустой в проде, когда источники известны.
   - 9094 не с мира.
3. **Данные и утечки наружу**
   - `reporting_enabled = false`
   - `check_for_updates = false`, `check_for_plugin_updates = false`
   - `disable_gravatar = true`
   - `snapshots.external_enabled = false` (а лучше и `snapshots.enabled = false`, если снимки не нужны)
   - `auth.anonymous.enabled` не включать
   - Externally shared dashboards / public — запретить политикой и RBAC (`dashboards.public:write`)
   - `cookie_secure = true`, HSTS (`strict_transport_security`) при HTTPS на LB
   - `allow_embedding = false` (дефолт; не включать без нужды iframe)
   - Плагины только подписанные, из внутреннего registry

Плюс:

- `min_tls_version` TLS1.2 (дефолт, если Grafana сама терминирует) или жёстче на HAProxy;
- не ГОСТ — если ИБ потребует СКЗИ, vanilla Grafana это не закроет;
- аудит входов: логи Grafana в тот же контур, что Wazuh/SIEM, не только в stdout пода;
- ревью, что Viewer интеграционного namespace не видит дашборд с payload гособмена.

Image Renderer: если всё же нужен — отдельный Deployment, свой `AUTH_TOKEN` ≠ `-`, NetworkPolicy ingress только от Grafana, Chromium sandbox по возможности. Иначе **не включать**.

##### Сильные / слабые стороны выбранной ИБ-схемы (OSS 13.2.0 + Postgres + SSO + выключенный «звонок домой»)

| Сильное | Слабое |
|---|---|
| Штатный HA UI без кворум-магии | Admin Grafana = ключ ко всем data source passwords |
| Дефолты известны и закрываются конфигом | Дефолты *известны всему GitHub* — цена «как в docker run» |
| RBAC/папки, SSO из коробки OSS | Ошибка Viewer на «широком» источнике = чтение внутренних метрик |
| Не облако, данные в ваших ЦОДах | AGPL; нет ГОСТ; KMS envelope — в основном Enterprise |
| `/api/health` и `/metrics` есть | `/metrics` без пароля из коробки |
| Data source proxy удобен для браузера | Grafana — SSRF-точка во внутреннюю сеть |

#### Kubernetes-специфика прода

- Pin чарта **12.11.2** и образа **13.2.0** (digest). На `latest` уедет минор без вашего решения.
- `headlessService: true` + env `POD_IP` из `status.podIP` — как в официальном K8s-фрагменте alerting HA.
- Порты контейнера: 3000, 9094 TCP, 9094 UDP.
- Ingress/HAProxy: readiness от `/api/health`, не от «TCP 3000 открыт».
- Sidecar provisioning (dashboards/datasources/alerts из ConfigMap) — удобно; тогда UI-правки будут **перезатёрты**. Выбрать один источник правды: git **или** клики.
- `initChownData` в чарте: для HA без PVC часто выключают; не копировать вслепую.
- Не ставить Grafana на те же ноды, что etcd/Kafka, без лимитов — это CPU/RAM конкуренты, не «лёгкий UI».

#### Порядок вывода в прод (этапы, не команда за командой)

1. Измерить RTT/потери между ЦОДами на 5432 и 9094 TCP **и UDP**. Решить: stretch Grafana+Postgres или мозг в 1–2 площадках; Memberlist или Redis для алертов.
2. Зафиксировать A vs B1 и **ЦОД Postgres primary**.
3. Снять оценки: зрители, дашборды, refresh, число alert rules, какие источники.
4. Поднять HA Postgres, БД `grafana`, бэкап, TLS.
5. Выпустить секреты (Vault): пароль БД, `secret_key`, admin break-glass, SSO client secret.
6. Helm 12.11.2 / Operator: ≥2 реплики, без SQLite PVC, `ha_peers`, anti-affinity, ресурсы Small как пол.
7. Закрыть исходящие дефолты (reporting, updates, gravatar, snapshots). HTTPS, `cookie_secure`, `root_url`.
8. Подключить источник (Prometheus/Mimir). Provisioning 2–3 дашбордов (K8s, Kafka, интеграционный API). Контролируемый алерт доехал.
9. SSO + RBAC. Убрать ежедневный вход под Admin.
10. Нагрузить соседством: открыть реальные дашборды, посмотреть latency источника и `grafana_alertmanager_cluster_members`. Учение «под Grafana убит»: UI жив. Учение «ЦОД без Postgres primary»: что с записью/логином. Учение «Prometheus недоступен»: алерты failed, UI жив — и это **ожидаемо**.

Без пунктов 4 (HA БД!), 6 (gossip!) и 10 у вас нет мониторинга, есть namespace с зелёным подом.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | ≥2 реплики Grafana, **Postgres HA** (не SQLite), LB на 3000, `ha_peers`+9094 TCP/UDP (или Redis), переживание **1** ЦОДа для UI *если* БД доступна; runbook на смерть ЦОДа с Postgres; источник метрик — отдельный HA |
| Производительность / масштаб | Не требуется | Тир по таблице вендора; не умножать оценку алертов репликами вслепую; терабайты — задача TSDB, не Grafana; смотреть latency дашбордов и CPU; `min_refresh_interval` |
| Безопасность | `admin` только в изоляции; :3000 не с мира | Свой `secret_key`; нет дефолт-пароля; SSO; reporting/gravatar/external snapshots выкл; `/metrics` закрыт; TLS+`cookie_secure`; whitelist proxy; pin 13.2.0; UI не публичный; unsigned plugins нет |

**Не готов к проду**, если: одна реплика с SQLite на три ЦОДа; три реплики без `ha_peers`; `admin`/`admin` или дефолтный `secret_key`; `latest`; Grafana в интернет; reporting/snapshots наружу из контура с ПДн; ждут, что Grafana *хранит* метрики Kafka; ждут, что Grafana заменит Wazuh; RTT/UDP не мерили, а gossip растянули на 3 ЦОДа; учение отказа пода/БД/источника не делали; дашборды только в UI без git и без бэкапа Postgres.
