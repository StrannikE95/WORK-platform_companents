# Zabbix 7.0.30 LTS — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Zabbix.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Zabbix — система наблюдения: проверки, пороги, эскалации. Ставите **свою** копию, не облако вендора.

Версия: **7.0.30** (LTS, 25 августа 2026). Полная поддержка линии 7.0 — до 30 июня 2027. В бой **не** брать 7.4.14 (не LTS) и не ждать 8.0, которого на дату соседнего файла на странице исходников нет.

Образы: `zabbix/zabbix-server-pgsql`, `zabbix-web-nginx-pgsql`, `zabbix-proxy-sqlite3` / `zabbix-proxy-pgsql`, `zabbix-agent2`. Метка **`alpine-7.0.30` / `ubuntu-7.0.30`**, не `latest`. Compose: https://github.com/zabbix/zabbix-docker ветка **7.0**. Документация: https://www.zabbix.com/documentation/7.0/en/manual/

У поставщика **нет** чарта «весь сервер на Kubernetes». Официальный Helm ставит **мониторинг Kubernetes из уже существующего** Zabbix. OpenShift Operator в публичных мануалах — линии 5/6, для 7.0 не брать. Бой: **официальные образы** + ваши манифесты.

Сервер — **active-passive**: живой съём и пороги только у **одной** активной ноды. Пульс HA идёт **через базу**. Размазывать сервер и PostgreSQL на несколько дата-центров здесь **не делаем**: порога задержки сети в документации нет, синхронная копия Postgres между городами убивает поток записи.

---

## О чём эта инструкция молча договорилась

1. **Мозг (сервер HA + PostgreSQL) в одном дата-центре.** Другие площадки — **прокси** (буфер съёма). Не открывайте между залами синхронную запись Postgres «потому что HA умеет across sites»: это про процесс сервера, не про вашу базу.
2. Бой — Kubernetes в каждом дата-центре отдельно, либо сервер на машинах одной площадки. Community Helm — не сертификат вендора на 7.0.30.
3. База — PostgreSQL 13–18. Oracle не берём. TimescaleDB Community — если срок хранения или поток значений выйдут за стенд.
4. Учебный стенд — закрытая сеть. Пароль `Admin`/`zabbix` сменить в день установки.
5. Цифр вашей нагрузки нет — нет фразы «хватит N ядер». Сначала меньше проверок в секунду, потом вертикаль активной ноды, потом прокси.
6. Два дата-центра: мозг в первом, группа прокси во втором. Три — прокси в каждом; третий активный сервер **не** появляется.
7. AGPLv3 с 7.0 — юридический факт; этот файл не заменяет заключение.
8. Zabbix не ходит в ведомства за бизнес-данными. Он проверяет, что API **живо**.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** увидеть хост, проверку, порог, уведомление, один агент. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Linux (Windows как сервер не заявлена) **или** Docker.
- Порт интерфейса не в интернет.
- PostgreSQL для сервера. Прокси на тесте можно не ставить.
- Сеть стенда закрыта.

### Установка (Compose — основной путь для учёбы)

Репозиторий `zabbix-docker`, ветка **7.0**, `compose_pgsql.yaml`. Метки образов **7.0.30**.

```bash
# образы: zabbix-server-pgsql, zabbix-web-nginx-pgsql, zabbix-agent2 — alpine-7.0.30 (или ubuntu-7.0.30)
docker compose -f compose_pgsql.yaml ps
# UI: http://127.0.0.1:8080 (или как в compose) — не 0.0.0.0 без нужды
```

Порты: агент **10050**, сервер/прокси **10051**, Java-шлюз **10052**, PDF **10053**, интерфейс **80/443**. TLS **не** открывает новый порт.

Сразу: войти `Admin` / `zabbix`, **сменить пароль**. Не публиковать порт 80. После 5 неудачных логинов интерфейс молчит 30 секунд — это не WAF.

Пакетный путь: https://www.zabbix.com/download — версия **7.0**, PostgreSQL, nginx/Apache; сервер + интерфейс + Agent 2 на одной машине.

На Kubernetes для учёбы: один Deployment сервера (имя ноды HA **не** задавать), один интерфейс, PostgreSQL с диском, опционально DaemonSet Agent 2. **Не** две реплики сервера без параметров HA: два писателя на одну базу.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| HA сервера | выкл | Не учимся переживать выкат |
| Прокси | выкл | Нечего разносить |
| TimescaleDB | выкл | Поток стенда не греет вычищение истории |
| TLS | можно HTTP в изоляции | Иначе сертификаты раньше порогов |
| Java-шлюз | выкл, пока нет JMX | Лишние части |
| Удалённые команды агента | выкл | Не «чтобы удобно» |
| Коннектор → Kafka | выкл | Не цель стенда |

Чего **не** упрощаем: **7.0.30** на всех компонентах; смена `Admin`/`zabbix`; одна проверка не localhost и одно **дошедшее** уведомление; не класть в проверку тело ответа интеграционного API.

### Как понять, что стенд живой

1. Последние данные растут. Порог умеет стать проблемой и вернуться. Уведомление дошло.
2. Версии сервера, интерфейса и агента совпадают по линии 7.0.30.
3. Успешный график CPU **не** доказывает запасную ноду и буфер прокси.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный compose | Нет буфера прокси, нет HA |
| Одиночка — штатный режим | «Всё в одном» уедет в бой |
| | HTTP + заводской Super Admin «чуть торчит» — инцидент |

Перед боем полезен **препрод**: 2 ноды сервера **в одном** дата-центре, отдельный Postgres с бэкапом, группа из 2 прокси, TLS, единый вход — даже без боевого потока значений.

## Бой: один живой дата-центр для мозга, прокси на площадках

**Зачем:** пережить отказ **активного процесса внутри площадки** (запасная нода рядом); пережить отказ **чужого дата-центра** буфером прокси; пережить отказ **дата-центра мозга** ценой тишины порогов, пока не восстановите Postgres и сервер. Переживание двух площадок native HA **не обещает**.

### Почему мозг не растягиваем на несколько дата-центров

Поставщик: HA *will work across sites*, *does not have specific requirements for the databases*. Перевод: **сервер** умеет разъехаться; **база** — ваша. Синхронный Postgres + пульс через ту же базу при плохой задержке сети — лотерея ложных переключений и убитого потока записи. Порога миллисекунд в документации **нет**. Поэтому сервер и writer Postgres живут **в одном** зале.

Нельзя повесить TCP-балансировщик «на все HA-поды»: запасной **не слушает** 10051.

### Как расставить машины

**В активном дата-центре (мозг):**

- PostgreSQL с запасом **этой** площадки (не синхронная копия через город). Бэкап с прогнанным восстановлением.
- Zabbix server native HA: минимум **2** ноды (активная + запасная) **в этом же зале**, разные имена и адреса (стабильный DNS, не случайные имена ReplicaSet). Третья запасная не ускоряет съём.
- Интерфейс не меньше двух копий, HTTPS, единый вход. При HA **не** прописывать адрес сервера в конфиге PHP — фронт читает активную ноду из базы.
- TimescaleDB Community на длинной истории (линейка **2.13.0–2.29.X** на 7.0.30) — осознанно, лицензия Timescale не «пакет из Debian».
- Один и тот же номер **7.0.30** на сервере, интерфейсе, прокси и агентах.

**Съём на площадках:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: сервер HA + Postgres. На обеих — **группа прокси** (не меньше двух, на разных нодах). Хосты площадки — на группу | Вторая площадка мертва: нет съёма **её** хостов. Первая мертва: пороги и эскалации молчат; прокси второй копят, пока хватает часов буфера и диска |
| **Три** | Группа прокси в каждом | То же; третий зал не даёт второго активного сервера |

Вариант «три независимых Zabbix» — только при жёсткой изоляции контуров (три экрана, три эскалации). По умолчанию хуже для дежурства.

Вариант «один сервер опрашивает три зала без прокси» — не берём: обрыв между залами = массовые ложные проблемы.

### Что должно быть до боевой установки

- Образы 7.0.30 со своего реестра.
- NTP на сервере, прокси, агенте, базе.
- Канал алертов (почта/webhook) **до** объявления HA.
- TLS на 10050/10051 **до** массовой раскатки агентов.
- Матрица с Prometheus/Wazuh: кто орёт диск, кто SNMP — до первой ночи дежурства.
- Прокси **не** в той же базе, что сервер. SQLite в памяти запрещён.

### Порядок установки в активном дата-центре

1. PostgreSQL + схема Zabbix, бэкап, прогнанное восстановление. Решить TimescaleDB.
2. Один сервер **без** HA, сменить Super Admin, HTTPS, сетевая политика.
3. TLS (не оставлять «принимать открытый текст» на боевых агентах). Agent 2 на пару нод. Проблема / восстановление + уведомление.
4. Группа прокси в этом зале, перевесить хосты, выключить один прокси — хосты должны переехать.
5. Вторая нода сервера **в этом же зале**, уникальное имя, пустой адрес во фронте. Выключить активную — сверка статуса HA и времени переключения (заводская задержка **1 мин** + 5 с при исчезновении).
6. Раскатать группы прокси на остальные площадки. Версия прокси **=** версия сервера.
7. Официальный Helm **мониторинга** Kubernetes — поверх уже живого сервера, не вместо него.

Сервер: отдельные поды со стабильным DNS. **Не** Deployment с общим диском и двумя репликами без имён HA.

Апгрейд мажорной линии HA: **остановить все ноды**, бэкап базы, обновить **одну** как одиночку, дождаться «server is running», вернуть HA. Не выкатывать обе сразу.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Имя ноды HA | уникально | Без имени процесс стартует как одиночка |
| Прокси: список серверов | все имена нод HA | Запасной не слушает порт |
| Буфер прокси | режим `hybrid` на новых 7.0 | Режим «только память» при рестарте теряет буфер |
| Часы буфера при обрыве | не меньше реального ремонта канала до мозга | Иначе дырка в истории |
| Интерфейс :80 снаружи | нет | Только HTTPS |
| Глобальные скрипты | выкл, если нет регламента | Super Admin = скрипты на сервере |
| Elasticsearch как история | нет | В документации экспериментально |
| Housekeeper без партиций на огромной истории | не оставлять | Сам становится аварией |
| TimescaleDB | переопределение срока истории **и** внутреннее вычищение | Иначе партиции не удаляются |

Агенты: предпочитать режим «сам приносит значения» — исходящие из площадки проще, чем открыть 10050 всех машин. Для группы прокси в этом режиме агент **≥ 7.0** и доступ ко **всем** членам группы.

Секреты: макросы и пароль базы — Vault (Zabbix только читает). При таких макросах между сервером и прокси **нужен TLS**. Агент на той же машине, что сервер, — другим UNIX-пользователем.

Задержку переключения HA с 1 минуты на 10 секунд на канале с джиттером не ставить: риск метания роли.

Политика сбоя подов: не давать Kubernetes снять сразу обе ноды сервера или всю группу прокси одной зоны.

### Как расти, когда появятся цифры нагрузки

1. Главный рычаг — **меньше новых значений в секунду** (интервал, не плодить обнаружение «как Prometheus без фильтра»).
2. Горизонталь съёма — **прокси**, не второй активный сервер.
3. Вертикаль — процессы опроса на **одной** активной ноде; база отдельно.
4. Формула диска соседнего файла (~90 байт на значение) — ориентир, не смета «терабайт озера».
5. Таблица Small/Medium/Large поставщика — примеры старта, не ваша закупка.

### Проверки, без которых это ещё не бой

1. Все компоненты **7.0.30**. Нет двух серверов без имён HA на одной базе.
2. Выключили активную ноду — запасная стала активной, фронт нашёл её из базы, прокси не потеряли список имён.
3. Выключили один прокси группы — хосты на живом. Рестарт прокси с `hybrid` — буфер не обнулён как при «только память».
4. Восстановили PostgreSQL на стенде. Учение «дата-центр мозга недоступен»: что алертится, что только буферизуется.
5. Нет `Admin`/`zabbix`; 10051/443 не с мира; TLS не «открытый текст» на боевых агентах.

### Что хорошо и что плохо в схеме «мозг в одном дата-центре + прокси на площадках»

| Хорошо | Плохо |
|---|---|
| Официальная модель распределённого съёма | Мозг упирается в PostgreSQL этого зала |
| Буфер прокси при обрыве канала | Пороги и эскалации в это время могут молчать |
| HA сервера внутри зала, без размазанной базы | Запасной не принимает 10051; кривой балансировщик ломает модель |
| Один экран, одна эскалация | Ошибка шаблона сразу на всех площадках |

**Не готово к бою**, если: пароль `zabbix`; HTTP UI снаружи; два сервера без имён HA; прокси в базе сервера; буфер только в памяти как единственный запас площадки; нет бэкапа Postgres; сервер и Postgres размазали на 2–3 зала; версии прокси ≠ сервер; community Helm выдан за оператор поставщика 7.0; тот же набор алертов без договора с Prometheus.
