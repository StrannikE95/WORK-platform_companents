# Camunda 8.9 — термины и сокращения

Словарь к файлу `Camunda 8.md`. Список линейный, не таблица. Сверху — слова, без которых не читаются остальные. Аналогий нет: только что это делает в коде и на диске.

---

**Процесс ОС** — запущенная программа. Брокер Zeebe, gateway, job worker — разные процессы (часто разные поды). Движок **не** вызывает ваш Java-метод внутри своей JVM.

**Файл / каталог на диске** — первичное хранилище брокера: журнал партиций (log) + снимок состояния (snapshot). Это «память живого процесса», не клиентское досье. `emptyDir` = потеря журнала при рестарте пода. Снимок диска брокера «как VM» **не** считается согласованным бэкапом кластера.

**TCP-порт** — контракт сети Orchestration Cluster: **8080** REST API gateway; **26500** gRPC клиентов и job workers; **26501** Command API gateway→брокер (внутренний протокол SBE); **26502** Internal API: Gossip + Raft между брокерами и gateway; **9600** Actuator (`/metrics`, `/ready`, backup API). UDP для Raft/Gossip вендор не описывает: это TCP. На 26501/26502 внешний мир не пускают. В одном фрагменте страницы Network ports значения environment variables для 26502/9600 скопированы ошибочно на 26501 — ориентир **поля YAML**.

**ЦОД** — отдельная площадка. Три ЦОДа в файле = три зоны отказа одного «региона» для базовой схемы RF=3. Dual-region — **ровно две** площадки. Triple-region (3 площадки как first-class HA) в доке нет.

**RTT** — время туда-обратно. Каждый commit ждёт кворум на 26501/26502. Для dual-region ориентир вендора **≤ 100 мс** (не жёсткий лимит движка). Для stretch на 3 зоны отдельной цифры нет. Мерить 26502/26501 (и 26500, если воркеры в чужом ЦОДе), не ping ICMP.

**TLS / mTLS** — шифрование канала; mTLS — оба конца показывают сертификат. Helm `values-tls.yaml` закрывает TLS **к** OpenSearch/ES/PostgreSQL/OIDC. **Не** закрывает весь gRPC между подами: нужен service mesh или своя схема. Штатный TLS JDK, не ГОСТ/СКЗИ.

**BPMN** — язык схем процессов (задачи, развилки). Схему рисуют в Modeler, исполняет движок. YAML CI и Kafka consumer BPMN не заменяют.

**DMN** — таблицы решений. Исполняются рядом с BPMN.

**Процесс (process definition)** — задеплоенная схема. Версий может быть много.

**Экземпляр процесса (process instance)** — один конкретный прогон схемы: «заявка №123».

**Orchestration Cluster** — с 8.8 это **один** артефакт: движок + Operate + Tasklist + встроенный Admin. Не три отдельных продукта, которые сами склеятся. Образ в файле: `camunda/camunda:8.9.17` (чарт **camunda-platform 14.8.5**).

**Zeebe** — движок исполнения. Хранит *состояние живых процессов*, а не клиентское досье. В переменных процесса вендор не рекомендует большие данные. Потолок порядка **~3 МБ** на экземпляр; бенчмарки считают килобайты.

**Брокер (broker)** — процесс Zeebe. Все брокеры равноправны: нет «главного сервера навсегда».

**Партиция (partition)** — кусок данных движка. Параллелизм исполнения ≈ число партиций. Партиции планируют **до** нагрузки; есть процедура cluster scaling — операция, не слайдер в UI. Официальный ориентир: партиция «типично» тянет порядка **1 ГБ** суммарного payload; 11 КБ vs 0.5 КБ в бенчмарках меняет диск **в 10–20 раз**. Это эвристика вендора, не ваша смета.

**Replication factor (RF)** — сколько копий у каждой партиции. RF=3 → 1 лидер + 2 последователя. `replicationFactor` не может быть больше числа брокеров.

**Лидер / follower** — лидер партиции обрабатывает команды. Followers копируют журнал. Упал лидер — выбирают нового. Лидерство может сползти на одну ноду; Rebalancing API Self-Managed — best effort.

**Raft** — протокол, которым брокеры договариваются, какая копия «правда». Запись **коммитится**, только когда большинство копий подтвердило.

**Кворум** — большинство. Для RF=3 кворум = 2. Живых копий меньше — партиция **не принимает** новые команды. Два брокера из 3 (два ЦОДа) — процессы **стоят**. Нечётное RF — норма для одного региона из трёх ЦОДов.

**clusterSize / partitionCount / replicationFactor** — тройка, которая должна быть **одинаковой** на всех брокерах. Стартовая тройка прода в файле: **3 / 3 / 3**, пока бенчмарк не скажет иначе. `initialContactPoints` — **все** брокеры.

**Gateway** — вход для клиентов: gRPC **26500** и REST **8080**. Клиенты **не** ходят на брокеры напрямую как на балансировщик Kafka. С 8.8 в Helm gateway по умолчанию **встроен** в брокер; его всё равно масштабируют репликами входа. Балансировщик gRPC должен понимать **долгие** стримы воркеров. Обычный HTTP L7 на 26500 рвёт стримы: нужен L4 или gRPC-aware Ingress.

**SBE** — внутренний бинарный протокол Command API на 26501.

**Gossip** — обмен составом кластера между брокерами на 26502 вместе с Raft.

**Job / job worker** — сервисная задача в BPMN становится «работой». Её забирает **отдельная программа** (ваш микросервис), делает дело, говорит движку `complete` или `fail`. Упал воркер — работы копятся в движке (официальная модель). Встроенной метрики размера backlog вендор пишет, что **нет**.

**Job type** — имя работы (`fetch-client-from-lake`). Воркеры подписываются на тип. Несколько реплик каждого type. Лишние воркеры одного типа делят работы.

**Идемпотентность** — повторный вызов той же работы не создаёт второй побочный эффект. Таймаут job > типичного времени интеграционного API (госслужбы с лагами). Иначе Zeebe отдаст работу другому воркеру — двойной вызов.

**Operate** — UI «что сейчас с процессами, где застряло». Читает **вторичное** хранилище, не диск брокера. Падение Operate ≠ падение Zeebe. Нормальная data availability latency экспорта — секунды–минуты.

**Tasklist** — UI пользовательских задач. Падение ≠ «процессы умерли», но люди не закроют задачи.

**Admin** — встроенная идентификация Orchestration Cluster (пользователи, права на процессы/задачи/API). Fine-grained authorizations с 8.8+.

**Management Identity** — *другая* идентификация: Web Modeler, Console, Optimize. Не путать с Admin. Свой PostgreSQL; не кворум Zeebe. Java 17+.

**Optimize** — аналитика по процессам. **Опциональна.** В первом проде файла выключена. Вендор: примерно **×3.4 CPU** и **×3.6 диск** Elasticsearch на реалистичном ворклоаде; на максимуме吞吐 движка падает на **25–50%**. Для Zeebe records при включённом Optimize: `minimum-age` ILM **не короче 3 дней**, лучше **≥ 7**, дефолт примера **30d**.

**Connectors** — готовые кубики «дерни HTTP / Kafka / …» в схеме. Runtime — отдельный деплой. Не замена вашего интеграционного API. Образ в строке чарта: Connectors **8.9.8**.

**Exporter** — плагин брокера: копирует события движка во **вторичное** хранилище. Без него Operate пустой, хотя процессы уже идут.

**Camunda Exporter** — актуальный экспортёр 8.8+ для Operate/Tasklist/Admin. Если он не может писать — **backpressure**: движок сам притормаживает пользовательские команды. Для Operate/Tasklist гонку с коротким ILM убрали; для Optimize — нет.

**Первичное хранилище** — диск брокера: log + snapshot.

**Вторичное хранилище (secondary storage)** — OpenSearch **или** Elasticsearch **или** RDBMS — поиск, Operate, Tasklist, API истории. С 8.9 в Helm тип **обязательно** задать явно (`orchestration.data.secondaryStorage.type`). Без него чарт **не ставится**. Смена семейства потом — **не** in-place миграция. Кластер **один** на все компоненты Orchestration Cluster (не «Operate на одном OS, Tasklist на другом» — сломали в 8.8).

**H2** — встроенная файловая/in-memory СУБД. В Camunda 8 Run — дефолт для ноутбука. **Не** для мультиброкерного прода.

**Desktop Modeler / Web Modeler** — рисовалки BPMN. Desktop — программа на ПК. Web — сервер + PostgreSQL (образ **8.9.7**). Процессы исполняются и без Web Modeler. Деплой в прод — через CI (zbctl / API), не «кнопка из браузера».

**Console / Camunda Hub** — панель управления несколькими кластерами. Hub — тема **8.10 Alpha**, не этот документ. Console в строке чарта: **8.9.88**.

**C8 Run** — локальная сборка «движок + коннекторы + H2». Только разработка. Вендор: не для production.

**Docker Compose Camunda** — официально: quick start / dev / test. Не прод.

**Stretch** — один логический кластер Zeebe, брокеры физически в разных ЦОДах. Raft ходит по **26501/26502**.

**Dual-region** — официальный сценарий: **ровно две** площадки, RF=**4**, минимум **8** брокеров (по 4). Failover **ручной**. При потере региона Raft **сразу останавливает** обработку до процедуры. RPO для Zeebe/Operate/Tasklist: **0**. RTO failover в тестах вендора: **< 1 минуты** *без* DNS; полный failback — минуты плюс restore Elasticsearch. OpenSearch и RDBMS как secondary в этом сценарии **не поддерживаются**. Только Elasticsearch, свои кластеры в каждом регионе, экспортёр пишет в оба (это не CCR OpenSearch). Optimize / Management Identity ограничены.

**Cold Recovery** — кластер в одном ЦОДе + restore из бэкапа. Падение ЦОДа = простой до restore. Отдельно от dual-region.

**RPO / RTO** — сколько данных готовы потерять / как быстро восстановиться. Формального SLA в контексте нет. Dual-region даёт опубликованные цифры **их** тестов, не ваш замер.

**Backpressure / flow control** — движок отказывает или тормозит новые команды, когда не успевает реплицировать или экспортировать. Это защита, не «баг медленности».

**CAMUNDA_LICENSE_KEY** — лицензионный ключ Self-Managed (`global.license.secret`). С 8.6 **прод без лицензии нельзя**. Без ключа UI может работать с плашкой Non-Production. Единая модель на Zeebe, Operate, Tasklist, Optimize, Identity, Connectors, Console, Web Modeler.

**OIDC** — вход через корпоративный IdP (Keycloak, Entra, Okta…). Для людей в проде — это, а не общая учётка `demo`. Дефолт Helm 8.9: `global.security.authentication.method: basic`. Учётка `demo:demo` (дефолт Basic в 8.8+) — ключ от операционки процессов.

**Self-Managed** — установка у вас, не SaaS Camunda Cloud. Не Camunda 7: там встроенный движок в Spring Boot (одна JVM). В 8 движок **всегда удалённый**. `@JobWorker` — клиент, не `JavaDelegate` / `camunda:class` внутри BPM.

**Standard support** — линейка 8.9 до **13 октября 2027**. 8.8 — до 13 апреля 2027. Апгрейд на 8.9 только с 8.8.x, не «через одну minor». 8.10 на дату файла — Alpha (chart 15.x, Helm CLI **v4**). В прод не брать.

**Helm CLI v3** — чарт 14.x (8.9); в матрице 14.8.x указан Helm **3.20.x**. Helm v4 — требование 8.10.

**OpenJDK** — Orchestration Cluster / Optimize / Connectors: **21–25**. Клиент Zeebe Java: 8+ (воркеры, не брокеры).

**Диск брокера** — официально: **≥ 1000 IOPS**, latency записи/msync в низких единицах миллисекунд, p99 **< 300 мс**, **SSD**. HDD не поддерживается. NFS — только если POSIX, не переставляет операции, не отдаёт один том **на запись двум** контейнерам. Amazon EFS вендор гарантирует; «любой NFS ReadWriteMany на троих брокеров» — порча данных.

**PVC / RWO** — том на каждого брокера. StorageClass с предсказуемым IOPS.

**OpenSearch / Elasticsearch** — secondary. Для 8.9: ES **8.19+** или **9.4+**, **или** OS **2.19+** или **3.6+**. У вас документ на OpenSearch **3.8.0** — попадает в ветку 3.6+. Не тот кластер, что бизнес-поиск, и не Wazuh indexer. Экспортёр ходит на **9200**.

**RDBMS** — третий допустимый тип secondary. PostgreSQL также для Management Identity и Web Modeler. В проде — внешний кластер / CloudNativePG, не Bitnami-subchart.

**ILM / ISM** — политики удаления/свертки индексов ES/OS.

**CCR** — кросс-кластерная репликация OpenSearch. Dual-region Camunda её не использует для secondary.

**Объектное хранилище** — для **partition backup Zeebe**, отдельно от snapshot repository OpenSearch/ES. Хранилище бэкапов переживает тот же отказ, что и кластер, или живёт вне всех трёх ЦОДов.

**backup ID** — один идентификатор (часто unix time) на согласованный бэкап Zeebe + web apps + индексы экспорта. Нативный snapshot только OS не даёт согласованной точки. Restore прогонять на другой namespace.

**Actuator :9600** — метрики, readiness, backup API. Только Prometheus и операторы бэкапа, не интернет.

**Ingress** — вход 8080/26500 с TLS, внутренняя сеть. Не raw NodePort в мир.

**PDB** — не дать Kubernetes снять сразу два брокера из трёх.

**topologySpread / anti-affinity** — по брокеру (или по паре) в зону. Не сложить двух из трёх в один ЦОД.

**StatefulSet** — контроллер брокеров.

**Bitnami Elasticsearch/PostgreSQL** — subchart чарта. В проде **выключены**.

**service mesh** — взаимный TLS между подами. Операционный налог; Helm TLS values это не закрывают.

**HPA воркеров** — по **своим** метрикам (длина работы, не CPU брокера).

**Kafka** — шина домена. Zeebe — оркестратор. Событие «клиент изменился» живёт в Kafka; процесс может среагировать через воркер/коннектор. Не дублировать «и коннектор, и свой consumer» без идемпотентности ключа экземпляра.

**Озеро / SoT** — эталон клиентских данных. В variables — идентификаторы и статусы, не досье. Тело ответа ведомства — в озеро (`requestId` / статус).

**Интеграционное API** — единственный выход во внешний мир в вашей архитектуре. Воркеры Camunda — клиенты этого API. Коннектор «напрямую в ведомство» плодит второй контур.

**zbctl** — CLI деплоя процессов.

**Spring Boot Starter** — клиент воркера; должен быть совместим с 8.9.

**Вариант A** — один Kubernetes на 3 ЦОДа, один Orchestration Cluster, RF=3, ваш OpenSearch 3.8.0. Цель: пережить **1 ЦОД**.

**Вариант B** — dual-region на 2 из 3 ЦОДов, Elasticsearch, минимум 8 брокеров, RF=4. Третий ЦОД: холодный standby, бэкапы, не член Raft.

**Вариант C** — брокеры только в одном ЦОДе + Cold Recovery.

**QPS / throughput** — нагрузки нет — нет цифры N брокеров и M партиций. Правило sizing-гайда: закладывать порядка **20×** средней нагрузки, если важны пики — **не** замена замера.

**152-ФЗ / ПДн** — переменные процесса и Operate могут содержать персональные данные и статусы госинтеракций.

Источники формулировок: глоссарий и тело `Camunda 8.md`. Новых порогов RTT и размеров диска здесь нет.
