# Backstage 1.54.0 — развёртывание и настройка

Версия ПО: **Backstage 1.54.0** (релиз основной линии 18 августа 2026; на дату подготовки документа это последний стабильный main-line релиз).  
Документация: https://backstage.io/docs/  
Релизы: https://github.com/backstage/backstage/releases/tag/v1.54.0  
Создание приложения: `npx @backstage/create-app@latest` (шаблон приложения, не «готовый продукт из коробки»).  
Образы: **своего** приложения. Официальный Docker-гайд собирает образ из репозитория app; базовый runtime в шаблоне 1.54 — `node:24-trixie-slim`.  
На Kubernetes: Backstage **задуман** как stateless Deployment + внешний PostgreSQL. Официальный путь Spotify: собрать Docker-образ → registry → Deployment YAML. Отдельный репозиторий чартов проекта: **Helm chart `backstage/backstage` 2.8.2** (17 июня 2026, `https://backstage.github.io/charts`, OCI `ghcr.io/backstage/charts/backstage`). Чарт **прямо пишет**: дефолтный образ — vanilla demo, **для прода скорее всего не подходит**; в прод кладут **свой** образ своего app.

Этот текст — не мануал «скопируй `app-config.yaml`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Backstage **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить внутренний developer portal на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** озеро эталонных клиентских данных, **не** шина событий, **не** процессный движок и **не** интеграционное API к госслужбам.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Developer portal / IDP** | Внутренний сайт для разработчиков: «какие у нас сервисы, кто владелец, где репозиторий, как поднять новый». Не портал для граждан и не UI озера ПДн. |
| **App** | *Ваш* экземпляр Backstage: монорепозиторий, который вы собрали `create-app` и дальше сами наполняете плагинами. Проект Backstage — это **фреймворк**, не готовый бинарь «скачал — работает». |
| **Core** | База платформы (конфиг, плагины, сервисы backend), которую развивает open-source проект. |
| **Plugin** | Кусок функциональности (каталог, шаблоны, документация, Kubernetes-вкладка…). Frontend-плагин рисует UI; backend-плагин — API и работу на сервере. |
| **Software Catalog** | Реестр сущностей: сервисы, API, сайты, библиотеки, люди, группы. Источник правды *о ПО организации*, не о клиентах. |
| **Entity** | Одна запись каталога (`Component`, `API`, `System`, `User`, `Group`, `Template`, …). Описывается YAML `catalog-info.yaml`. |
| **Location** | Откуда каталог берёт YAML: URL в Git, файл, discovery по организации. |
| **Entity provider** | Модуль, который *сам* кладёт сущности в каталог по расписанию или webhook (организация в GitLab, LDAP, …). |
| **Processor** | Шаг конвейера каталога: прочитать YAML, проверить, обогатить, вытащить связанные сущности. |
| **Processing loop** | Фоновый цикл: каталог периодически заново обрабатывает все сущности. Интервал — `catalog.processingInterval`. |
| **Stitching** | Финальная сборка сущности (связи, поиск по полям) после обработки. Отдельная очередь. |
| **Scaffolder / Software Templates** | «Мастер создания»: шаблон генерирует репозиторий/файлы и выполняет **действия на хосте backend**. Это не Camunda. |
| **TechDocs** | Документация рядом с кодом (Markdown → MkDocs). Может собираться *внутри* Backstage или заранее в CI. |
| **Search** | Поиск по каталогу/докам. Сам Backstage поисковиком не является: подключают Lunr, PostgreSQL или Elasticsearch/OpenSearch. |
| **Lunr** | Поиск **в памяти процесса**. В create-app это дефолт, пока нет Postgres. В проде официально **крайне не рекомендован**. |
| **Auth provider** | Способ войти: GitLab, GitHub, OIDC, SAML, proxy (ALB/IAP/Cloudflare). Один обычно для sign-in, остальные — чтобы плагины ходили во внешние API от имени пользователя. |
| **Guest** | Вход «гостем» без IdP. В доке: удобно не в проде; в Docker-гайде — **не для контейнеров**. |
| **Sign-in resolver** | Код/настройка: «этот аккаунт IdP = вот этот `User` в каталоге». Ошибка resolver = чужая учётка или вход постороннего. |
| **Backstage token** | JWT, которым UI доказывает backend «я вот этот пользователь». Ключи подписи **уникальны для инсталляции**, короткоживущие, по умолчанию **не переживают рестарт** процесса, если не задать свой keystore. |
| **Limited user token / UIP** | Урезанный токен: доказывает *кто* пользователь, но большинство API его не принимают. Им прокидывают identity между плагинами. |
| **Service-to-service auth** | Плагины backend ходят друг к другу со своими JWT; публичные ключи — `/.backstage/auth/v1/jwks.json`. |
| **Permission framework** | Отдельный слой «можно ли это действие». **По умолчанию выключен**: все залогиненные видят и делают почти всё. Включается `permission.enabled: true` + политика. |
| **Permission policy** | Ваша функция: разрешить / запретить / условно разрешить. В create-app часто стоит allow-all модуль — это не RBAC «из коробки». |
| **Proxy plugin** | Прокси из браузера на внешний HTTP (обход CORS). Опасно, если в него вшивают секреты: любой, кто дошёл до Backstage, бьёт ими во внешний API. |
| **UrlReader** | Сервис backend: «скачай этот URL». Список доверенных хостов — `backend.reading.allow`. Ошибка списка = чтение metadata облака или внутренних админок. |
| **DiscoveryService** | «По какому URL жить плагину `catalog` / `auth`». При **нескольких** backend-деплоях его надо настраивать самим: из коробки мультидеплой «сам разъедется» не обещан. |
| **app.baseUrl / backend.baseUrl** | Публичные URL UI и API. Если не совпадают с тем, что видит браузер (Ingress, TLS, путь) — логин и CORS ломаются. |
| **app-config.yaml** | Главный конфиг. Секреты — через `${ENV}` / Secret, не в git. Слои: `app-config.yaml` + `app-config.production.yaml`. |
| **Knex** | Библиотека SQL. Каждый backend-плагин получает **свою логическую БД** (или схему). |
| **pluginDivisionMode** | `database` (дефолт: отдельная БД на плагин) или `schema` (одна БД PostgreSQL, схемы на плагин). |
| **SQLite / better-sqlite3** | Файловая/in-memory БД для эксперимента. Дефолт create-app — `:memory:`: рестарт = пустой каталог. |
| **Cache store** | Кэш плагинов (Keyv): `memory` / `redis` / `valkey` / `memcache` / `infinispan`. `memory` — для локальной разработки. |
| **New backend system** | Текущий способ собирать backend: `createBackend()` + `backend.add(import('плагин'))`. Старый `src/plugins/*.ts` — миграция. |
| **Health (с 1.29)** | `/.backstage/health/v1/liveness` и `/.backstage/health/v1/readiness` — для проб Kubernetes. |
| **Host build** | Сборка JS на CI (`yarn tsc` + `yarn build:backend`), в Docker кладут уже bundle. Рекомендованный путь: быстрее и проще кэш. |
| **CNCF Incubating** | Проект в CNCF с 15 марта 2022 (принят 8 сентября 2020). Лицензия **Apache 2.0**. |
| **Release line** | Main — раз в месяц (вторник перед третьей средой). Next — еженедельно, меньше гарантий. Версия `1.54.0` **не semver продукта**: ломающие изменения бывают в minor. |
| **Skew policy** | Правила совместимости пакетов: ядро app не старше плагинов «наоборот»; frontend-плагин и его backend обновляют вместе, backend **раньше или одновременно**. |
| **Stretch** | Один логический сервис, поды/БД в нескольких ЦОДах. Для Backstage «растягивается» в первую очередь **PostgreSQL**, не Node-процесс. |

## Основные элементы системы и зависимости

### Что входит в «одно ПО» (это фреймворк из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Frontend (app)** | UI портала | По умолчанию раздаётся **тем же** backend (`plugin-app-backend`). Можно вынести в NGINX/CDN — тогда конфиг **запекается на сборке** |
| **Backend** | API плагинов, каталог, шаблоны, auth, прокси | Горизонтально: **одинаковые** реплики за балансировщиком, общая БД. Вертикально: CPU/RAM Node. Дальше — **резать** на несколько Deployment (catalog отдельно от scaffolder) |
| **Auth plugin** | Вход людей и выдача Backstage token | Для высокой изоляции — **отдельный** Deployment и **своя** БД (threat model) |
| **Catalog plugin** | Реестр сущностей, processing loop | Упирается в PostgreSQL и во внешние SCM (rate limit). Метрика: `catalog.processing.duration` |
| **Scaffolder** | Генерация репозиториев, действия на хосте | Очередь задач; тяжёлые шаблоны не должны душить каталог — поэтому их часто **выносят** |
| **TechDocs backend** | Отдать статику доков | `builder: local` считает MkDocs *в поде*; `external` только читает из S3/GCS/Azure/MinIO |
| **Search backend** | Индекс для строки поиска | Lunr = память **этого** процесса. Postgres / OpenSearch — внешний индекс |
| **Permission backend** | Решения allow/deny | Без него залогиненный = почти суперпользователь UI |
| **Proxy** | CORS-обход к внешним HTTP | Не масштабирует внешнюю систему; это дырка, если вшиты токены |

Плюс то, что **вы обязаны поставить сами** (в образе Backstage этого нет как «кластера»):

- **PostgreSQL** (прод);
- **Ingress / Gateway** со своим TLS (Node по умолчанию слушает HTTP **7007**);
- **IdP** (GitLab / Keycloak / Entra / …);
- **SCM** (GitLab/GitHub/…), откуда читается `catalog-info.yaml`;
- опционально **Redis/Valkey** (кэш), **OpenSearch** (поиск), **объектное хранилище** (TechDocs), **аутентифицирующий reverse proxy**.

### Официальные порты и URL

| Порт / путь | Назначение |
|---|---|
| **7007/TCP** | Backend (и UI, если frontend в том же процессе). В Helm: `containerPorts.backend: 7007`, Service `http-backend` |
| **3000/TCP** | Dev-сервер frontend при `yarn start` (отдельно от backend). В проде этого порта нет, если UI раздаёт backend |
| `/.backstage/health/v1/liveness` | Liveness (новый backend ≥ 1.29) |
| `/.backstage/health/v1/readiness` | Readiness |
| `/.backstage/auth/v1/jwks.json` | JWKS ключей плагина для service-to-service |
| `/api/<pluginId>/…` | HTTP API плагина (catalog, scaffolder, techdocs, …) |

UDP нет. HTTPS на 7007 **не** является встроенным «кластерным» TLS как у OpenSearch 9300: обычно TLS заканчивается на Ingress.

### Чего в Backstage нет (частая путаница)

| Нужно системе | Это не Backstage | Зачем помнить |
|---|---|---|
| Источник истины клиентских данных / «озеро эталона» | СУБД / объектное хранилище озера | Каталог хранит метаданные *сервисов*. ПДн клиентов сюда не кладут |
| Шина событий, гарантии Kafka | Apache Kafka | Backstage может *показать* топик как сущность, не заменить брокер |
| BPMN / долгоживущие бизнес-процессы | Camunda | Scaffolder — короткие job'ы создания репозитория, не процесс заявки в госорган |
| Интеграции с госслужбами | Ваше интеграционное API | В каталог можно завести *карточку* адаптера, не ходить в ведомства |
| Поиск по терабайтам логов/клиентов | OpenSearch (у вас отдельный документ) | Search в Backstage — про сущности портала и TechDocs, не про озеро |
| Кластерный консенсус / кворум | etcd, Kafka, OpenSearch manager | Несколько подов Backstage **не выбирают лидера**. Состояние — в PostgreSQL |
| Готовый RBAC «включи галочку» | Permission policy, которую пишете вы | `permission.enabled` без политики ≠ модель доступа организации |
| ГОСТ TLS / СКЗИ | Не заявлено | TLS на Ingress — обычный. Требования КИИ этим документом не закрываются |
| Официальный порог RTT между ЦОДами | Нет | Для Node-подов важен RTT до **PostgreSQL** и SCM, не «магия Backstage» |
| Гарантия «терабайты влезут» | Нет | Объём каталога ≪ объём озера. Терабайты у вас — не смета PVC Backstage |
| Демо-образ Helm как прод | Чарт 2.8.2 прямо: vanilla image не для production | Прод = свой Dockerfile своего app |

### Зависимости окружения (обязательны)

- **Node.js.** Политика проекта: ровно **две соседние чётные** версии. С релиза **1.46.0** это **22 и 24**. Шаблон Docker 1.54 — **Node 24**. Сборку `yarn` и runtime образа делают **одной** major: нативные модули иначе падают.
- **Yarn.** Getting started на дату доки: **Yarn 4.4.1** (`corepack` + `yarn set version 4.4.1`).
- **PostgreSQL в проде.** Предпочтительная БД. Политика: поддерживаются **последние 5 major**, тестируют **самый новый и самый старый** из этого окна. На август 2026 это ориентир **14…18** (PostgreSQL 18 вышел в 2025; 19 на дату документа ещё не в этом окне как «текущий ежегодный»). Пример в k8s-гайде с образом `postgres:13.2-alpine` — **учебный YAML**, не «официальная версия для прода». Модуль поиска Postgres требует **≥ 12**.
- **ОС.** Linux в контейнере. Windows-host как место продакшен-подов в вашей схеме с Kubernetes не предполагается.
- **Сеть:** стабильный DNS до PostgreSQL; от подов — до GitLab/IdP; от браузера — до `app.baseUrl`. Балансировщик HTTP перед 7007 **нормален** (это не Kafka).
- **Kubernetes (у вас заявлен):** Deployment (не StatefulSet для самого Backstage), probes на health v1, PDB, topology spread по зонам. PVC нужен **PostgreSQL и объектному хранилищу**, не «диску каталога внутри пода Backstage».
- **Секреты:** токены SCM, client secret IdP, пароль БД — Kubernetes Secret / Vault, не `app-config` в git. K8s-гайд прямо: Secret в API **base64, не шифрование**; нужен encryption at rest etcd.
- **PKI / TLS** на входе. Backstage token — свой JWT, это не замена TLS до пользователя.

### Как Backstage стыкуется с вашей архитектурой

```
Разработчики (браузер)
        │  HTTPS (Ingress + желательно auth proxy)
        ▼
   Backstage app (N реплик, порт 7007)
        │
        ├── PostgreSQL     ← состояние каталога, задач scaffolder, ключи auth
        ├── Redis/Valkey   ← опциональный кэш
        ├── OpenSearch     ← опциональный поиск портала (не озеро ПДн)
        ├── MinIO/S3       ← TechDocs, если builder=external
        ├── IdP / GitLab   ← вход людей и чтение catalog-info.yaml
        └── Kubernetes API ← плагин «статус подов» (не тот же etcd, что кластер)

Микросервисы, Kafka, Camunda, озеро, интеграционное API
        ▲
        │  только как *сущности каталога* и ссылки
        │  (metadata.name, owner, API spec, зависимости)
   catalog-info.yaml в Git  ──►  Catalog processing loop
```

Честные роли в *вашей* картине:

1. **Карта микросервисов** — кто владелец, какой репозиторий, какая OpenAPI, в каком namespace крутится.
2. **Шаблоны новых сервисов** — единообразный скелет (логгер, метрики, контракт Kafka), не оркестрация бизнес-процесса.
3. **Документация сервиса** — TechDocs рядом с кодом адаптера к госслужбе, не хранилище ответов ведомств.
4. **Вход в Kubernetes для разработчика** — вкладка статусов подов (плагин Kubernetes). Это **не** замена kubectl-админки кластера.

Нечестная роль: «положим клиентов и эталон в Catalog, озеро не нужно». Catalog не ACID-модель ПДн, не ищет по ИНН терабайты и не переживает «удалили YAML — сущность осиротела» так, как озеро должно переживать юридическую истину.

## Краткие вводные

### Зачем вам Backstage в этой архитектуре

Kafka доставляет факт. Озеро хранит истину о клиентах. Camunda ведёт процесс. Интеграционное API ходит наружу. Остаётся вопрос: **как сотня команд не потеряет свои же 30+ адаптеров**, кто за них отвечает и как завести новый сервис «как у всех».

Backstage закрывает **каталог ПО и путь разработчика**. Он горизонтально растёт репликами за счёт stateless Node и общей БД. Он **не** делает ваши микросервисы event-sourced.

### Как устроена отказоустойчивость (идея, не магия)

Это **не кворум**. Падение пода Backstage при `replicas ≥ 2` и живом PostgreSQL = пользователь попал на соседний под. Падение PostgreSQL = портал «глухой», даже если поды живы.

**1) Процесс Backstage**

| Что падает | Что происходит по ролям из документации |
|---|---|
| Один под из нескольких за Service | Остальные отвечают. Координация работы — через БД («database handles coordination») |
| Все поды одной зоны, остальные зоны живы, topology spread сделан | Сервис жив, если PostgreSQL жив |
| Единственный под (`replicas: 1`) | Выкат и падение ноды = простой UI/API |
| `builder: local` + диск пода / Docker-in-Docker | Рестарт и вторая реплика **не делят** сгенерированные доки; в проде это слабое место |
| Lunr на нескольких репликах | У каждого процесса **свой** индекс в RAM; дока Search для Lunr прямо предупреждает про мультинодовый сценарий |

Официальный горизонтальный масштаб: увеличить `replicas` у Deployment. Пример в golden-path: `replicas: 3`. Это **пример**, не расчёт под вашу нагрузку. Нагрузки у вас нет.

**2) PostgreSQL (это уже другое ПО)**

Без HA БД «HA Backstage» — табличка. Реплики каталога не копируют данные друг другу. Политика бэкапа, синхронная реплика, failover — в контуре PostgreSQL. Учебный манифест k8s-гайда: **1 replica** Postgres + `hostPath` / local PV — для minikube, в проде том должен переживать ноду.

**3) Auth-ключи**

По умолчанию signing keys **короткоживущие и теряются при рестарте**. После rolling update пользователи могут словить «неизвестный kid», пока ключи не перевыпустились. Для прода рассматривают `auth.keyStore.provider: static` (свои файлы ключей) — это в доке Auth.

**4) Внешние системы**

Упал GitLab — processing loop не обновляет YAML, портал показывает **старое**. Упал IdP — нельзя войти. Это не отказ Node.

### Как устроено масштабирование

Несколько независимых осей (golden-path Scaling):

1. **Больше пользователей и плагинов** → сначала **больше одинаковых реплик** за LB. Это простой путь; его советуют исчерпать раньше split.
2. **Каталог не успевает** (`catalog.processing.duration` растёт, сущности «запаздывают») → смотреть processingInterval, rate limit SCM, мощность Postgres, затем **вынести catalog** в отдельный Deployment.
3. **Scaffolder очередь** → отдельный backend только со scaffolder (изоляция CPU и секретов Git write).
4. **Медленный UI** → вынести frontend на CDN/NGINX; конфиг тогда не инжектится backend'ом в рантайме.
5. **Поиск** → уйти с Lunr на Postgres (десятки тысяч документов — формулировка доки) или на OpenSearch/ES.

Сигналы «пора масштабировать» из той же страницы: рост latency API, отставание catalog processing, очередь scaffolder, жалобы на медленные страницы.

Цифр «N RPS на терабайты озера» **нет** — портал не хранит озеро. Ёмкость = число сущностей каталога + индекс поиска + артефакты TechDocs.

### Безопасность самого Backstage

Компрометация портала = карта всех сервисов, токены SCM/IdP, шаблоны, которые **пишут в Git и крутят код на хосте**, прокси к внутренним API. Threat model проекта:

- Рассчитан на **защищённый контур**, не на публичный интернет. От DoS — только «зачаточная» защита; оператор ставит proxy/WAF/лимиты сам.
- Рекомендуемый вход: **аутентифицирующий reverse proxy** (AWS ALB, GCP IAP, Cloudflare Access) *плюс* нормальный sign-in.
- С backend ≥ **1.24** есть встроенная защита API от анонимов, **если не** выставлен `backend.auth.dangerouslyDisableDefaultAuthPolicy`. Frontend-бандл при этом по умолчанию **всё равно скачивается**; закрыть его — experimental public entry.
- Залогиненный пользователь **по умолчанию видит и может почти всё**. Тонкий доступ — только `permission.enabled: true` и своя policy.
- Плагины на одном хосте и с доступом к **чужой** логической БД считаются имеющими полный доступ к тому плагину. Граница = **нет** доступа к БД/кэшу соседа. Для высокой безопасности **auth — отдельный сервис со своей БД**.
- `oauth2Proxy` **не проверяет** подпись заголовков — внутренний злоумышленник может подделать identity. `awsAlb` / `cfAccess` / `gcpIap` — проверяют.
- Релиз **1.54.0** содержит **critical security fixes** плагина Kubernetes — в прод без этого патча линейки 1.54 не идти, если плагин включён.

«Поставили Helm с `image.tag: latest` и Guest» — это витрина, не портал организации.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём self-hosted Backstage 1.54.0** как свой app из `create-app`, не Red Hat Developer Hub и не SaaS. Коммерческий дистрибутив живёт по другим манифестам и поддержке.
2. **Прод крутится в Kubernetes**, образ — **собранный вами** (host build или multi-stage Dockerfile из официального Docker-гайда). Helm 2.8.2 — способ описать Deployment, не замена сборки app. Чарты пинить **версией**, не `latest`. Дефолтный `ghcr.io/backstage/backstage:latest` в чарте **не** целевой прод.
3. **Три ЦОДа = три зоны отказа** Kubernetes (`topology.kubernetes.io/zone`). Если это три зала с общим питанием — spread подов даёт ложное чувство безопасности.
4. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. Два мёртвых ЦОДа при кворуме etcd/Postgres «2 из 3» — уже другой разговор (см. документы Kubernetes/PostgreSQL).
5. **Нагрузки нет** — поэтому **нет** цифры «N реплик и M CPU». Есть сигналы (latency, processing duration, очередь scaffolder, heap Node, пул Knex) и рычаги (реплики, split backend, кэш, поисковый движок).
6. **Формального SLA / RPO / RTO нет.** Живые 3 пода ≠ юридический 24/7. RPO портала ≈ RPO PostgreSQL + то, что ещё не успел обработать catalog из Git.
7. **Корпоративный IdP и Git (GitLab/аналог) есть или будут.** Guest и `file:` locations — для теста.
8. **Идентификация людей в проде — SSO**, не Guest. Группы для permission policy приходят из sign-in resolver + User/Group в каталоге (ingestion из доверенного источника, не «каждый сам зарегистрировал Group»).
9. **Шифрование канала пользователя — TLS на Ingress.** Требования ГОСТ/СКЗИ не озвучены; vanilla Backstage их не закрывает.
10. **Тестовый стенд изолирован.** На нём допустимы SQLite, Guest, Lunr, `builder: local`. В прод их не копируем.
11. **Kafka, Camunda, озеро, интеграционное API** — объекты *каталога* и ссылки, не часть этого ПО.
12. **PostgreSQL, OpenSearch, Redis, Vault** — отдельные продукты со своими HA. Этот документ не заменяет их настройку.
13. **Лицензия Apache 2.0.** License-server нет. Следить нужно за **плагинами из npm**: threat model требует vetting как любого пакета.
14. **Один логический каталог на организацию.** Три независимых Backstage без общей БД = три карты сервисов.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «нарисовали Deployment и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Несколько реплик Backstage имеют смысл, только если они видят **одну** PostgreSQL (или осознанный active/passive). Три каталога без общей БД — три истины. |
| **RTT и стабильность до PostgreSQL** (p50/p95/p99, все пары ЦОД↔БД) | Каждый запрос каталога бьёт в БД. Высокий RTT → медленный UI, таймауты пула Knex, ложные readiness. Stretch Postgres — отдельное решение, не «Backstage умеет зоны». |
| **Где живёт Git и IdP** | Processing и логин зависят от них. Если Git только в одном ЦОДе — падение этой площадки = каталог замирает (UI со старыми данными может ещё отвечать). |
| **Нужен ли Scaffolder в проде** | Это выполнение шаблонов **на хосте** с часто широкими правами на Git. Без политики и изоляции — главный attack surface портала. |
| **TechDocs: CI или local builder** | `local` + несколько реплик + пустой диск пода = гонки и Docker-in-Docker в Kubernetes. Дока: recommended setup — **external** + объектное хранилище. |
| **Кто пользователи** (только разработка? ещё ИБ? подрядчики?) | От этого зависят permission policy, catalog.rules, нужен ли публичный entry, можно ли Guest на препроде. |
| **Какой SCM и какие токены** | `url` locations без integration не читаются. Fine-grained vs org-admin токен — разный радиус взлома. |
| **152-ФЗ / КИИ / что нельзя светить в каталоге** | В entity легко положить внутренние URL, владельцев, связи с адаптерами к госслужбам. Каталог — карта атаки. |
| **Совместимость Helm 2.8.2 с вашим Kubernetes 1.36** | Prerequisites чарта: K8s **1.25+** (в таблице requirements ещё `>= 1.19` — расхождение в README). Ваш 1.36 формально выше минимума; это не сертификат «прогнали 2.8.2 на 1.36». |
| **Нужен ли split auth/catalog/scaffolder сразу** | Threat model советует отдельный auth+БД для high-security. Сложность Discovery/Ingress растёт. На старте часто один backend, split — когда есть изоляция или нагрузка. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **релиз 1.54.0** (`@backstage/create-app` / `yarn backstage-cli versions:bump` по доке Keeping Backstage Updated). Не смешивать next-line в проде.
2. Собрать **свой** app: плагины, SignInPage **без Guest в production-конфиге**, `app.baseUrl` / `backend.baseUrl` / CORS под реальный URL.
3. Подключить **PostgreSQL** (`client: pg`, SSL по политике ИБ). Проверить, что плагины создали БД `backstage_plugin_*` (или схемы).
4. Включить **реальный auth provider** и sign-in resolver, который мапит в `user:` каталога. Прогнать логин.
5. Настроить **integrations** SCM и `catalog.locations` / providers. Задать **catalog.rules** (не оставлять возможность кому угодно заводить `User`/`Group`/`Template`).
6. Решить **Search** (не Lunr в проде) и **TechDocs** (`external` + бакет vs осознанный local только на тесте).
7. Включить **permission.enabled** и политику не allow-all, как только появятся разные роли.
8. Собрать Docker-образ **той же** Node, что в runtime; пробы на `/.backstage/health/v1/*`.
9. Выложить за Ingress с TLS. Проверить, что логин (redirect URI) проходит — в 1.54.0 allowlist OAuth **ужесточили** (breaking).
10. Метрики: OpenTelemetry (golden-path), latency API, `catalog.processing.duration`, очередь scaffolder, пул БД. `/metrics` в свежем app **нет**, пока сами не настроите (это отмечает Helm README).

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы команда увидела каталог, `catalog-info.yaml`, логин, один шаблон, TechDocs. **Не** цель: доказать отказ ЦОДа и ёмкость.

**Путь A — ноутбук / VM (быстрее понять продукт):**

```text
npx @backstage/create-app@latest
cd <app>
yarn start
```

UI: `http://localhost:3000`, backend: **7007**. Нужны Node 22 или 24, Yarn 4.4.1, порты 3000 и 7007. БД по умолчанию — SQLite in-memory.

**Путь B — Docker-образ своего app + PostgreSQL** (ближе к проде, всё ещё 1 ЦОД):

Официальный host build, затем `docker run -p 7007:7007`. Гостевой провайдер в контейнерах **не предназначен**. Нужен Postgres и не-Guest auth (хотя бы тестовый OIDC/GitLab).

На Kubernetes: Deployment `replicas: 1`, Secret с паролем БД, как в https://backstage.io/docs/deployment/k8s/ — понимать, что пример Postgres там **не HA**. Helm 2.8.2 с demo-образом — только чтобы пощупать чарт, не как эталон app.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число реплик | 1 | Нет требования пережить выкат |
| БД | SQLite или один Postgres без реплик | Нет требования пережить диск |
| Auth | Guest **или** тестовый IdP; Guest не в Docker | Дока: Guest удобен не в проде |
| Search | Lunr | Ноль сервисов; индекс умрёт с процессом — на стенде ок |
| TechDocs | `builder: local`, publisher `local` | CI и S3 ещё нет |
| Permission | выкл. или allow-all | Иначе команда не увидит сущности, пока нет policy |
| CPU | 512Mi–1Gi как «чтобы открылось» | Не цель — ёмкость |
| catalog.rules | дефолт create-app | На стенде мало сущностей |
| Split backend | нет | Учит продукт, не DiscoveryService |

#### Чего на тесте **не** стоит упрощать

- Версия **1.54.0** app и тех же плагинов (skew policy).
- Понимание, что **SQLite `:memory:`** не переживёт рестарт — иначе «на проде тоже пропадёт каталог» станет сюрпризом.
- Хотя бы один **настоящий** `catalog-info.yaml` из Git (type `url`), не только `file:` examples: в проде `file:` для боевых данных **не** рекомендуют.
- `app.baseUrl` / `backend.baseUrl` совпадают с тем, как открываете браузер.
- Запомнить: Helm demo image и Guest **не** есть «почти прод».
- Breaking 1.54: шаблоны OAuth redirect. Поймать на тесте дешевле, чем в день вывода SSO.

#### Сильные стороны такой схемы

- Поднимается за часы, совпадает с Getting Started / Docker / k8s tutorial.
- Дешево показывает, как ваши микросервисы лягут в модель Catalog (owner, API, dependsOn).
- SQLite и Lunr официально для эксперимента/dev.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет доказанной ёмкости, нет общего кэша/поиска между процессами.
- Успешный `yarn start` **не** доказывает, что SSO, permission и TechDocs-S3 заведутся.
- Guest и открытый 7007 приучают «зайти без учётки». В инциденте нужен закрытый UI и policy.

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (свой образ 1.54.0, Postgres, SSO без Guest, Search не Lunr, TechDocs external если так будет в проде, `replicas ≥ 2`), даже без боевого трафика.

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты озера» **нет** — портал их не хранит. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Backstage хорошо переживает **несколько stateless-подов** и плохо переживает **три независимых PostgreSQL «как три портала»**.

**Вариант A — один Kubernetes на 3 ЦОДа (зоны), один Backstage Deployment.**

- `replicas` ≥ 2 (для rolling update; golden-path пример — **3**).
- `topologySpreadConstraints` / anti-affinity по `topology.kubernetes.io/zone`, чтобы падение одного ЦОДа не сняло все поды.
- PDB: не отдать сразу всех подов при drain (`maxUnavailable: 1` типичная идея; в чарте PDB выключен по умолчанию — `create: false`).
- Service `sessionAffinity: None` (дефолт чарта) — sticky **не** требуется документацией масштабирования; токены живут у клиента.
- PostgreSQL — **ваш** HA-кластер (не Bitnami subchart чарта в `standalone`). Поды Backstage в трёх зонах ходят в БД; латентность БД = латентность портала.
- Кэш Redis/Valkey — если включили: тоже HA, иначе после failover кэша просто холоднее (не потеря каталога).
- Ingress один на кластер, TLS, желательно auth proxy **перед** 7007.

**Вариант B — три изолированных Kubernetes.**

- **B1. Активный портал в одном ЦОДе**, с двух других пользователи ходят по сети. Простая схема. Падение ЦОДа с подами+БД = нет портала. Спасает: Postgres с репликой/DR в другом ЦОДе + заранее прогнанный запуск Deployment там (RTO надо замерить).
- **B2. Поды Backstage в двух/трёх кластерах на **одну** PostgreSQL.** Имеет смысл только если сеть до БД приемлема и вы понимаете split-brain **БД**, не Backstage. Это решение по PostgreSQL, не по Node.
- **B3. Три независимых app.** Три каталога. Для «карты всех микросервисов организации» обычно **ошибка**, если не разведены контуры (prod/nontprod) сознательно.

**Пока топология K8s и RTT до Postgres не зафиксированы, нельзя честно выбрать A.** Дальше — общее для A как целевого «3 ЦОДа в одном городе»; B — запасной.

##### Сильные / слабые стороны (A, один кластер, поды в 3 зонах)

| Сильное | Слабое |
|---|---|
| Один каталог, один SSO, один набор плагинов | Зависимость от HA PostgreSQL и сети до него |
| Официальная модель: stateless + replicas | Падение двух ЦОДов при типичном кворуме «2 из 3» у etcd/Postgres — уже простой |
| Rolling update без окна, если PDB и ≥2 пода | Ошибка `app-config` выезжает сразу на всех |
| Пробы health v1 стандартны | RTT до БД из «дальнего» ЦОДа может сделать часть подов бесполезными (ready, но медленные) |

##### Сильные / слабые стороны (B1, мозг в одном ЦОДе)

| Сильное | Слабое |
|---|---|
| Не тащим Postgres между ЦОДами для каждого клика | Падение площадки с порталом = нет UI у всех |
| Проще отладка Discovery | Нужен явный DR: поднять поды+БД на другой площадке **с прогоном по времени** |
| | Пользователи из других ЦОДов зависят от городской сети до Ingress |

##### Сильные / слабые стороны (B2, поды везде, одна БД)

| Сильное | Слабое |
|---|---|
| UI ближе к разработчику в «своём» ЦОДе | Пишущая нагрузка и processing loop всё равно бьют в одну primary |
| | Риск двух processing loop из двух кластеров: координация через БД заявлена, но **двойной** выкат конфига и dual-cluster — больше шансов человеческой ошибки |
| | Latency cross-DC SQL |

##### Слабое место любого «размажем по городу» без замера RTT

Документация **не задаёт** порог задержки. Утверждение «три ЦОДа в одном городе, значит поды в каждом» — **непроверенное**, пока не измерен путь **под → PostgreSQL** и **под → Git/IdP**. Мерить TCP до 5432 и HTTPS до SCM, не только ping ICMP.

#### Роли и изоляция процессов

Минимальный прод (часто достаточно на старте):

- Один Deployment Backstage (все плагины), N реплик, общий Postgres.
- Auth keys: static keystore или смириться с ротацией при рестарте и кэшами JWKS.
- Не класть секреты Git write в тот же под, если завтра вынесете scaffolder — проще сразу least privilege токенов.

Усиленная изоляция (threat model / building-backends):

| Deployment | Зачем | Своя БД |
|---|---|---|
| **auth** (+ при необходимости app) | Подпись пользовательских JWT | **Да, обязательно отдельно** для high-security |
| **catalog + search** | Тяжёлый processing, не мешает шаблонам | Да (логические БД плагинов) |
| **scaffolder (+ techdocs generator, если local)** | CPU, Docker, write в Git | Да |
| **остальное** (proxy, kubernetes plugin, …) | Остаточный API | Да |

Для split **нужен свой DiscoveryService** (и/или reverse proxy, режущий `/api/catalog`, `/api/scaffolder`, …). Из коробки «поставил два Deployment и заработало» документация **не обещает**. Frontend `DiscoveryApi` тоже, если не закрыли маршрутизацию прокси.

Модули (`createBackendModule`) живут **в том же** процессе, что плагин, который расширяют. Нельзя вынести GitHub entity provider в другой Deployment отдельно от catalog.

##### Сильные / слабые стороны (один backend vs split)

| | Один процесс | Split |
|---|---|---|
| Сильное | Простой Discovery, один образ, меньше YAML | Изоляция секретов и CPU; падение scaffolder не роняет логин |
| Слабое | Компрометация плагина = доступ к общей машине и часто к нескольким БД, если credentials широкие | Свой Discovery, несколько пайплайнов выката, сложнее skew frontend/backend |

Начинать со split «на всякий случай» без требования ИБ — лишняя сложность. Игнорировать совет «отдельный auth+БД», если портал торчит шире внутренней сети — слабое место.

#### Каталог, шаблоны, доки, поиск

- **catalog.rules:** явно разрешить нужные kind. `User`/`Group` — только из доверенного provider (LDAP/GitLab org), не из произвольного PR. `Template` — узкий allow-list локаций.
- **catalog.readonly: true**, если каталог — зеркало Git и UI-регистрация локаций запрещена.
- **processingInterval** не ставить слишком коротким: сожрёте rate limit GitLab. Дока: это *желаемый минимум*, фактически может быть длиннее.
- **Scaffolder:** ограничить, кто создаёт/меняет шаблоны; permission на `execute`; по возможности user OAuth на запись в Git, а не org-admin токен в поде. Job выполняется **на хосте** пода.
- **TechDocs:** для нескольких реплик — `techdocs.builder: external`, publisher `awsS3` (MinIO: `endpoint` + `s3ForcePathStyle: true`) или GCS/Azure. Кэш TechDocs требует ещё `backend.cache`.
- **Search:** не Lunr. Практичный старт при уже живом Postgres — модуль `search-backend-module-pg`. Когда индекс и запросы вырастут — `search-backend-module-elasticsearch` с `provider: opensearch` на ваш кластер OpenSearch (отдельный документ). Смешивать индекс портала с бизнес-логами/ПДн в одном кластере — плохая идея даже если «оба OpenSearch».

#### Безопасность прода

| Слой | Правило |
|---|---|
| Guest | Нет в production SignInPage и нет в контейнере |
| `dangerouslyDisableDefaultAuthPolicy` | Не включать |
| IdP | Минимум провайдеров; resolver не принимает посторонний tenant; 1.54 — корректные redirect URI **по компонентам URL** |
| Permission | `permission.enabled: true`; убрать allow-all модуль; политика по группам из каталога |
| Auth keys | Понять рестарт; static keystore если JWKS кэшируется агрессивно |
| Auth split | Для high-security — отдельный сервис и БД |
| UrlReader | `backend.reading.allow` минимальный; **не** metadata 169.254.169.254 и внутренние админки |
| `$text` в YAML | Пользователь может прочитать то, до чего у него нет прав в Git, *через* backend. Если это проблема — отключить/заменить placeholder resolvers |
| Catalog | Нельзя регистрировать User/Group как impersonation; templates — доверенные репозитории |
| Proxy plugin | Не инжектить Authorization во upstream; резать `allowedMethods`; лучше свой тонкий backend-плагин |
| Scaffolder | Аудит actions; без «удалить любой репозиторий из шаблона» на широкой аудитории |
| Kubernetes plugin | Обновить до 1.54.0 из‑за **critical** фиксов; `skipTLSVerify: true` пишет warning в 1.54 — в проде не оставлять |
| Сеть | NetworkPolicy: 7007 с Ingress; egress в Postgres, IdP, SCM, OpenSearch, S3; не в весь кластер |
| Секреты | не в Git; Helm `extraEnvVarsSecrets`; encryption at rest |
| Frontend bundle | Если карта плагинов секретна — experimental public entry, иначе любой, кто дошёл до URL, качает JS |
| npm | Dependabot/Renovate на **ваш** `yarn.lock`; threat model: уязвимости зависимостей — обязанность оператора |
| Контур | Не светить в интернет; WAF/auth proxy. DoS-защита — ваша, не «встроена в Backstage» |

##### Сильные / слабые стороны (SSO + permission + auth proxy)

| Сильное | Слабое |
|---|---|
| Модель проекта: внутренний портал за proxy | Без policy залогиненный = слишком много |
| Гибкая policy (RBAC/ABAC/код) | Policy — ваш код, её надо сопровождать и тестировать |
| Плагины изолируются split'ом и раздельными БД | Легко «временно» дать широкий Git-токен scaffolder |
| JWT между плагинами с audience | Ошибка Discovery = доверие не тому JWKS |

#### Kubernetes-специфика прода

- Образ из **вашего** registry, тег **immutable** (не `latest`). Чарт: `backstage.image.tag` + свой repository.
- Не включать `postgresql.enabled` чарта как прод-БД (standalone Bitnami, в 2.8.2 ещё workaround-образ `bitnamilegacy/postgresql`).
- Probes: не выдумывать `/healthcheck`, если не включали старый путь; для ≥ 1.29 — **health v1**. Пример в k8s-гайде с `/healthcheck` помечен как «если включили в app».
- Resources: лимиты памяти с запасом под Node heap + нативные модули (isolated-vm у scaffolder).
- HPA в чарте есть (`targetCPUUtilizationPercentage: 80`, `maxReplicas: 100`) — **дефолты чарта, не расчёт нагрузки**. Включать после появления метрик CPU, иначе thrashing.
- `automountServiceAccountToken: true` в чарте по умолчанию — для плагина Kubernetes может быть нужно; иначе сузить RBAC SA до минимума.
- Выкат образа: сначала backend-плагины, потом frontend (skew policy), особенно при split.
- Не хранить TechDocs и SQLite на `emptyDir`, если от этого зависит прод.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть: под↔Postgres, под↔Git/IdP, пользователь↔Ingress. Решение A vs B.
2. Собрать app **1.54.0**, SSO, Postgres SSL, без Guest. Прогнать логин и OAuth redirect (breaking 1.54).
3. Зафиксировать catalog.rules, readonly если нужно, первый набор `catalog-info.yaml` из Git.
4. Выбрать Search и TechDocs **как в проде** (не Lunr/local, если прод будет другим).
5. Собрать образ, выложить `replicas ≥ 2` с spread по зонам, PDB, Ingress TLS.
6. Включить permission policy (хотя бы «админы / остальные»).
7. Пробы health, логи, OpenTelemetry. Алерт на отставание processing и 5xx.
8. Прогон «убили один под» — UI жив. Прогон «зона недоступна» на препроде.
9. Прогон restore Postgres на другой площадке (RTO). Реплики Backstage бэкапом не являются.
10. Только потом — scaffolder с write в Git, kubernetes plugin к боевым кластерам, proxy к внутренним API, split backend.

Без пунктов 8–9 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | ≥2 пода в разных зонах; HA PostgreSQL; цель — 1 ЦОД; прогнанный restore БД; не Lunr и не local-диск как единственная копия доков |
| Производительность / масштаб | Не требуется | Сначала реплики; сигналы processing/latency/очередь; кэш не memory; поиск Postgres или OpenSearch; split — по факту, не «на слайде» |
| Безопасность | Guest только в изоляции; не светить 3000/7007 в сеть | Нет Guest; SSO; permission включён; нет dangerouslyDisable; UrlReader минимальный; секреты не в git; 1.54.0 из‑за Kubernetes plugin; контур не public internet |

**Не готов к проду**, если: SQLite/` :memory:`, Guest в контейнере, Lunr на нескольких репликах как «поиск организации», Helm demo `latest`, `replicas: 1` без DR, TechDocs `local` на emptyDir в Stateful-смысле «данные в поде», `permission.enabled` выключен при разных ролях, `oauth2Proxy` торчит без проверки подписи, RTT до Postgres неизвестен, а поды уже в трёх ЦОДах, каталог назначен SoT клиентских ПДн, шаблоны scaffolder может менять любой залогиненный.
