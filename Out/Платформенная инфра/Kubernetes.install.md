# Kubernetes 1.36.4 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Kubernetes.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Kubernetes — оркестратор контейнеров. Ставите **свою** копию на виртуальные машины (или железо), не облако вендора.

Версия в этой инструкции: **Kubernetes 1.36.4**. Путь проекта: **kubeadm**. Документация: https://kubernetes.io/docs/home/  
HA kubeadm: https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/high-availability/

На дату соседнего файла тега v1.37.0 GA ещё не было — в бой не брать RC. Не прыгать через minor при обновлении: проект это **запрещает**.

Один кластер, размазанный на несколько дата-центров, здесь **не собираем**. Голосование etcd чувствительно к задержке сети; документация etcd: члены по возможности в одном дата-центре; в документации Kubernetes **нет** цифры «сколько миллисекунд ещё можно». Поэтому живой control plane — внутри одной площадки. Вторая площадка — свой независимый кластер, не вторая половина того же etcd.

На нодах — Linux и **containerd** (CRI-O допустим). Windows-ноды эта инструкция не ставит. Без CNI после `kubeadm init` поды не станут Running. Образы — с `registry.k8s.io` или с зеркала внутри контура.

---

## О чём эта инструкция молча договорилась

1. **По одному независимому кластеру на дата-центр.** Две площадки = два Kubernetes. Три = три. Общего etcd нет. Если растянуть голосование etcd на несколько городов, в документации нет порога задержки — поэтому здесь так не делаем.
2. Бой — on-prem, Linux, CRI **containerd**. Дистрибутивы (RKE2, Talos, OpenShift) меняют команды, **не** отменяют кворум etcd. Если выберете дистрибутив — те же топологические правила, другой плейбук.
3. Учебный стенд — закрытая сеть. Один control plane допустим **только там**.
4. Цифр вашей нагрузки нет — нет фразы «хватит N worker-нод». Есть минимум control plane (три машины) и рычаги роста (поды, потом ноды).
5. CNI **ещё не выбран** конкретно, но **обязан** реализовывать NetworkPolicy. Без этого объекты NetworkPolicy ничего не режут.
6. Два дата-центра: кластер в первом и кластер во втором. Три — то же. Третья площадка **не** третий etcd чужого голосования.
7. Kafka, Camunda, озеро — приложения **на** Kubernetes. Их репликация — в их инструкциях, не «scheduler сам унесёт PVC в чужой дата-центр».
8. Реестр образов: доступ к `registry.k8s.io` **или** заранее пролитые образы / зеркало.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** деплой сервисов, отладка манифестов. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Одна Linux-машина (или kind/k3d/minikube, если цель только API на ноутбуке).
- Официальный минимум kubeadm: порядка **2 CPU и 2 ГиБ RAM**, уникальные hostname / MAC / `product_uuid`.
- Swap — по текущим требованиям kubeadm/kubelet, не «как привыкли на Ubuntu».
- Сеть стенда не торчит в интернет. Порт 6443 не с мира.

Ниже — kubeadm. kind-команды зависят от локального tooling и сюда не копируются как «тот же бой».

### Установка (однонодовый kubeadm)

Порядок официальный: CRI **до** `kubeadm init`.

1. Поставить containerd, включить нужные sysctl (`ip_forward`, bridge-netfilter) — как в гайде containerd/kubeadm линии 1.36.
2. Пакеты `kubelet`, `kubeadm`, `kubectl` версии **1.36.4** (пин патч, не `1.36` «какой скачается»).
3. `kubeadm config images list` — зафиксировать фактический патч образа etcd 3.6.x на этот релиз.
4. Init без HA-endpoint (один API):

```bash
kubeadm init --kubernetes-version=v1.36.4
```

CIDR pod/service — свои; на учёбе достаточно дефолтов дистрибутива, если они согласованы с выбранным CNI. Потом на бою CIDR **разных** кластеров не должны пересекаться.

5. Сразу поставить **CNI**. Без него поды не станут Running.
6. Storage: local-path-provisioner / hostPath. Это не боевой CSI.
7. PSA: на dev-namespace профиль `baseline` уже полезен; `privileged` только системным аддонам.

`kubectl` — из `/etc/kubernetes/admin.conf`. На учебной машине control-plane часто ещё и worker: снять taint control-plane, иначе поды приложений не сядут.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Один etcd | да | Не учимся переживать падение машины |
| Без ControlPlaneEndpoint-LB | да | Один apiserver |
| Encryption at rest | можно отложить | Изолированный стенд |
| LoadBalancer / MetalLB | опционально | NodePort хватит |

Чего **не** упрощаем: версия **1.36.4**; `resources.requests` в манифестах; запрет `privileged`/hostNetwork без нужды; секреты не в Git; StatefulSet + PVC, если в бою будет диск; 6443 не с интернета.

### Как понять, что стенд живой

1. `kubectl get nodes` — Ready.
2. CoreDNS Running.
3. Тестовый Deployment встаёт и резолвит DNS внутри кластера.
4. Снесли машину — кластер пропал. Всё лежало на одном диске. Так и должно быть на тесте.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, дёшево, официальный однонодовый dev допустим | Падение единственной ноды = всё лежит |
| | Не ловит выборы etcd, CSI WaitForFirstConsumer, истечение сертификатов на трёх API |
| | Успешный kind **не** есть готовность боя |

Перед боем полезен **препрод**: 3 stacked control-plane **в одном** дата-центре, даже без боевой нагрузки.

## Бой: один живой дата-центр на кластер, второй — свой остров

**Зачем:** пережить отказ **одной машины внутри площадки** (второй/третий control-plane, автоматическая смена лидера etcd, kubelet поднимает поды на живых worker). Отказ **всего дата-центра** = этого кластера нет. Приложения на других площадках живут, только если у них **свой** Kubernetes и свои данные (репликация Kafka/БД — не этот файл).

### Почему кластер не растягиваем на несколько дата-центров

Запись в etcd идёт через Raft на большинство. Если задержка сети между площадками сопоставима с пульсом (заводские **100 ms** heartbeat, **1000 ms** election; election должен быть не меньше **10× RTT**), начнутся ложные выборы, API будет таймаутиться, **весь** кластер станет нестабильным. Документация etcd: по возможности один дата-центр. Порога в документации Kubernetes **нет**.

Четвёртый антипаттерн: etcd только в первой площадке, воркеры везде. Смерть первой = нельзя управлять кластером; рестарт подов на живых площадках не произойдёт. Это **не** отказоустойчивость, а «файлы ещё лежат».

### Как расставить машины

**В каждом дата-центре — свой Kubernetes:**

- Три stacked control-plane (дефолт kubeadm, документированный минимум HA) **или** 3 API + 3 external etcd, если готовы платить машинами за развязку диска API и etcd.
- **Балансировщик TCP :6443** перед apiserver **этой** площадки (keepalived/HAProxy на двух машинах той же площадки). DNS-имя = `ControlPlaneEndpoint`. Один VIP в чужом дата-центре = скрытая точка отказа **этого** кластера.
- Worker-ноды с ярлыком `topology.kubernetes.io/zone=<id этой площадки>`.
- Taint-пулы: `control-plane`; отдельно `platform` (Kafka, БД), `general` (микросервисы), при необходимости `ingress` / `integration-dmz`.
- CNI с NetworkPolicy, затем CSI. Диск etcd: локальный SSD/NVMe, **не NFS**.
- CIDR подов/сервисов **не пересекать** между кластерами площадок: иначе потом не склеить маршрутизацию без NAT.

**Между площадками:**

| Сколько площадок | Что где | Если умер дата-центр |
|---|---|---|
| **Две** | В каждой — полный независимый кластер (свои etcd, PKI, аддоны). GitOps накатывает желаемое состояние; PVC и лидеры Kafka — **разные** | Нет API и подов **этого** кластера. Второй жив. Время, за которое приложения на второй площадке делают то, что вы им обещали, нужно замерить |
| **Три** | Третий такой же остров | То же. Три кластера ≠ один `kubectl` на всю страну |

Снимок etcd **регулярно**; копия etcd **не** заменяет backup: команду «удали Secret» она послушно повторит. Restore прогнать на стенде.

### Что должно быть до боевой установки

- Схема «остров на площадку», согласованная с сетью и с решением по Kafka.
- Зеркало образов 1.36.4 внутри контура.
- HAProxy/keepalived на :6443 уже есть на площадке (см. `HAProxy.install.md`, если берёте HAProxy).
- NTP на всех машинах.
- CNI выбран и умеет NetworkPolicy.
- StorageClass с WaitForFirstConsumer и привязкой к зоне — чтобы том не оказался в зале A, а под в зале B.

### Порядок установки в активном дата-центре

Официальный порядок: сначала LB, потом первый control-plane, потом join остальных **по одному**. Повторить в **каждом** дата-центре.

1. Поднять LB :6443.
2. На нодах: containerd, kubeadm/kubelet/kubectl **1.36.4**.
3. Первый control-plane:

```bash
kubeadm init \
  --kubernetes-version=v1.36.4 \
  --control-plane-endpoint "<dns-lb-этой-площадки>:6443" \
  --upload-certs
```

4. Join второго и третьего control-plane (токен + certificate key из вывода init; не использовать один и тот же join-токен вечно).
5. Join workers.
6. **CNI** с NetworkPolicy, затем CSI, проверить CoreDNS.
7. Labels `topology.kubernetes.io/zone=<id>`. Внутри одной площадки можно разметить залы как подзоны, если они реально разные домены отказа.
8. Включить encryption at rest, audit, PSA, заготовки NetworkPolicy **до** боевых приложений.
9. Бэкап etcd (снимок). Проверка восстановления на стенде.

Апгрейд: сначала патч текущей minor, потом 1.36 → следующая minor **без прыжка**. Порядок: apiserver → controller-manager/scheduler → kubelet (с drain). kubelet новее API — нельзя.

### Правила конфигурации боя

| Слой | Правило |
|---|---|
| Сеть API | 6443 — только jump/VPN; etcd 2379/2380 — только control plane |
| TLS | не `insecure-skip-tls-verify` |
| Люди | OIDC / клиентские сертификаты. `admin.conf` — не процесс на 50 человек |
| RBAC | сервису свой ServiceAccount, только свой namespace. Не `cluster-admin` приложениям |
| PSA | прикладные namespace `restricted` или минимум `baseline` |
| NetworkPolicy | default-deny, затем DNS + свои зависимости. Интеграционный контур к госсети — отдельно |
| Secrets | EncryptionConfiguration **до** боевых секретов, затем `kubectl replace` существующих, чтобы перешифровать. Есть KMS → **KMSv2**. Нет → `aesgcm` (ключ не в Git). KMSv1 не использовать |
| Образы | только свой registry; не `:latest` |
| Сертификаты kubeadm | дефолт **1 год** — процедура ротации часть установки |
| Drain | ноды **по одной зоне**, не параллельно все площадки |
| PDB | на каждую критичную нагрузку с >1 репликой |

### Как расти, когда появятся цифры нагрузки

1. Замерить CPU/RAM сервисов и QPS к apiserver. Requests ≈ факт, иначе BestEffort выкинут первыми.
2. HPA на stateless. Для Kafka/БД «просто добавь под» не создаёт реплики данных.
3. Добавлять workers **внутри каждого** дата-центра по потребности **этого** кластера.
4. Следить за размером etcd (дефолт квоты **2 ГиБ**, типичный потолок **8 ГиБ**) и latency API. В etcd только метаданные.

GitOps между площадками: один desired state **не** означает одни и те же PVC и одни и те же лидеры Kafka. В overlay — endpoint БД, bootstrap Kafka. Без этого конфиги разъедутся за месяц.

### Проверки, без которых это ещё не бой

На **каждом** кластере:

1. Отказ одной control-plane ноды: API через LB жив, `kubectl` работает.
2. Drain одной worker-ноды: поды с PDB уезжают. etcd не на NFS.
3. Снимок etcd восстановлен на стенде хотя бы раз.
4. NetworkPolicy реально режет (не только объект в API).
5. Secret в etcd не plaintext (после включения encryption).
6. Учение «целый кластер площадки выключен»: приложения на другой площадке делают то, что вы им обещали (чтение, DR, простой записи) — это контракт приложений, не kube-scheduler.

### Что хорошо и что плохо в схеме «остров на дата-центр»

| Хорошо | Плохо |
|---|---|
| etcd локальный, предсказуемый; согласовано с гайдом etcd | 2–3 upgrade, 2–3 PKI, 2–3 набора аддонов |
| Blast radius ограничен площадкой | Нет единого API; приложение само активно на нескольких площадках |
| Локальный LB apiserver проще | Без GitOps конфиги разъедутся |
| | Stretch-Kafka **поверх** трёх кластеров сам не появится (см. инструкцию Kafka) |

**Не готово к бою**, если: один etcd «в уме на три ЦОДа»; PLAIN Secrets; CNI без NetworkPolicy при обещании изоляции; все реплики приложений без zone labels; cluster-admin у приложений; NFS под etcd; нет процедуры сертификатов; учебный однонодовый манифест уехал в бой; RTT не мерили, а etcd уже растянули.
