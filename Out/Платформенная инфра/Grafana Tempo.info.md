# Grafana Tempo 3.0.3 — термины и сокращения

Словарь к файлу `Grafana Tempo.md`. Список линейный, не таблица. Сверху — слова, без которых не читаются остальные. Аналогий нет: только что это делает в коде и на диске.

---

**Процесс** — запущенная программа: память и открытые файлы. Tempo — один бинарник с разным `-target` (distributor, live-store, querier, …). Несколько ролей = несколько процессов.

**Файл / каталог на диске** — то, что остаётся после рестарта. У Tempo на диске: WAL live-store/block-builder (PVC) и блоки трейсов в object storage. `backend: local` — каталог на диске процесса, вендор помечает как test/eval.

**TCP-порт** — номер в сети. OTLP gRPC **4317**, OTLP HTTP **4318**, HTTP API Tempo **3200**, внутренний gRPC **9095**, memberlist **7946** TCP+UDP, Memcached **11211**.

**ЦОД** — отдельная площадка с серверами. «Три ЦОДа» — три зоны отказа (`topology.kubernetes.io/zone`).

**RTT** — время туда-обратно по сети. Порога в миллисекундах у Tempo нет. Чувствительны: запись в Kafka, memberlist 7946, S3 API, gRPC querier↔live-store.

**TLS** — шифрование байтов в сети. На OTLP (Collector↔Tempo), HTTP/gRPC внутри, SASL_SSL до Kafka, HTTPS до S3. ГОСТ/СКЗИ не заявлено.

**CVE** — запись об ошибке безопасности. В 3.0.3 закрыты CVE через обновление Go 1.26.5, gRPC, `x/net`, `x/text` и OpenTelemetry. Чарт `tempo-distributed` 3.0.6 по умолчанию тянет **3.0.2** — образ переопределяют на 3.0.3.

**Под (Pod)** — контейнер(ы) Kubernetes, живут и умирают вместе. Live-store и block-builder — StatefulSet со стабильным порядковым номером (ordinal).

**PVC / RWO** — том Kubernetes, который можно отдать только одному поду. Без PVC рестарт live-store = дырка в свежих трейсах, пока Kafka ещё держит запись.

**NFS** — сетевая файловая система. WAL Tempo на NFS в файле запрещают.

**Object storage** — хранилище объектов (ключ + байты): S3 / GCS / Azure Blob / S3-совместимое. Долгое хранилище трейсов. Без него прод-микросервисы Tempo не живут. Локальный MinIO из гайда — test, not production.

**Трейс (trace)** — история одного запроса через систему: цепочка вызовов (API → Kafka → Camunda → внешний HTTP). Рисуется как дерево спанов.

**Спан (span)** — один шаг внутри трейса: вызов сервиса, запрос в БД, consume из Kafka. Имя, время, атрибуты (теги).

**Trace ID** — уникальный номер трейса. По нему Tempo достаёт трейс целиком (дешёвый путь). Distributor кладёт все спаны одного Trace ID на одну партицию Kafka (hash).

**Span ID** — номер конкретного шага. Родительский span ID склеивает дерево.

**OTLP** — OpenTelemetry Protocol: способ слать трейсы. gRPC обычно **4317**, HTTP — **4318**. С Tempo 2.7 приёмник по умолчанию слушает **localhost**, не `0.0.0.0`: в Kubernetes endpoint надо явно биндить.

**OpenTelemetry Collector** — отдельный процесс-посредник: принимает трейсы от приложений, батчит, сэмплирует, режет ПДн, отдаёт в Tempo. **Не часть Tempo**.

**Сэмплирование (sampling)** — писать не каждый трейс, а каждый N-й / только ошибочные / только медленные. Tempo **сам** сэмплирование не делает — Collector или SDK.

**Head-based / tail-based sampling** — решение на старте трейса / после того, как трейс уже собран (ошибки и медленные). В допущениях файла: ошибки и медленные почти 100%, успешные быстрые — N%.

**TraceQL** — язык поиска по трейсам. Дороже, чем lookup по Trace ID. Широкое окно бьёт querier.

**TraceQL metrics** — с 3.0 GA: из трейсов на лету считаются метрики (`rate()`, средняя длительность). Алертинг по ним — **experimental**.

**Монолитный режим (monolithic)** — один процесс (`-target=all`) делает всё. Kafka **не нужен**. Для теста. Grafana для прода так ставить не рекомендует. Несколько монолитов как кластер в 3.0.3 из документации убрали.

**Режим микросервисов** — каждый компонент — отдельный процесс со своим `-target`. Для прода. Нужен Kafka-совместимый брокер и object storage.

**Distributor** — вход: принимает OTLP/Jaeger/Zipkin, проверяет лимиты, в проде пишет в Kafka. Пока Kafka не подтвердила запись — клиенту «успех» не возвращают. Масштаб: больше реплик. OpenCensus в 3.0 убран.

**Kafka (для Tempo)** — буфер записи между distributor и остальными компонентами. Не бизнес-шина `client.updated`. Дефолт манифеста готов **автосоздать топик на 1000 партиций** — в проде топик создают вручную.

**Партиция Kafka (для Tempo)** — единица параллелизма write path. Live-store и block-builder привязаны к партициям. Чтобы добавить инстансы, сначала добавляют партиции, потом реплики StatefulSet.

**Live-store** — держит **свежие** трейсы в памяти + локальный WAL, чтобы искать через секунды, пока блок ещё не в object storage. Типичное окно в доке: **30 минут–1 час**.

**WAL** — файлы на диске live-store / block-builder: факт ещё не уехал в Kafka replay / object storage. После рестарта пода процесс читает эти файлы. Без PVC сегмент пропадает.

**Block-builder** — читает Kafka, собирает Apache Parquet-блоки, кладёт их в object storage. Пишет каждый блок **один раз** (RF1). Обычно 1 реплика на Kafka-партицию (`partitions_per_instance: 1`).

**Блок (block)** — файл(ы) с куском трейсов в формате Parquet. Retention удаляет старые блоки.

**vParquet4 / vParquet5** — версии формата блоков. Tempo 3.0 **не читает** vParquet3 и старше. В манифесте дефолт на дату документа — **vParquet4**.

**Backend scheduler** — один процесс, который раздаёт работы: компакция, retention, подчистка, redaction. Официально: **одновременно должен работать только один**. Падение = компакция/retention встают, приём трейсов идёт.

**Backend worker** — исполняет работы scheduler. Их можно несколько.

**Компакция (compaction)** — склеивание мелких блоков в крупные. Без неё поиск и список блоков деградируют.

**Retention / `block_retention`** — сколько хранить трейсы. Дефолт манифеста Tempo: **336 часов = 14 дней**.

**Partition ring** — список «какие партиции Tempo существуют и кто ими владеет». Расходится по кластеру через memberlist.

**Memberlist** — служебный обмен «кто жив в кластере». Порт по умолчанию **7946** TCP+UDP.

**Zone-aware live-store** — live-store'ы разложены по зонам (ЦОДам): на каждую партицию — **по одному владельцу в каждой зоне**. Чтение свежих данных: достаточно **одного** живого ответа (read quorum 1).

**Кворум чтения 1** — querier ждёт ответ от одного живого live-store партиции, не от большинства.

**RF1 (replication factor 1)** — на write path Tempo **не** копирует трейсы на три инстанса, как в 2.x. Долговечность ingest — у Kafka; долговечность истории — у object storage. Блок пишется один раз.

**Querier** — исполняет куски поискового запроса: ходит в live-store и в object storage. Масштаб — под объём поиска.

**Query-frontend** — API поиска, режет запрос на куски. Ориентир документации: **2 реплики** для HA, не «по числу ЦОДов».

**Memcached** — внешний процесс-кэш (bloom, parquet-footer, результаты поиска). Порт **11211**. Redis для кэша Tempo — **experimental**.

**Metrics-generator** — опционально: из спанов делает Prometheus-метрики (spanmetrics, service graph). В 3.0 читает из Kafka. Лимит `max_cardinality_per_label`. Легко раздуть число рядов Prometheus.

**Мультитенантность** — изоляция «организация A не видит трейсы B» по HTTP-заголовку `X-Scope-OrgID`. Клиентов, которые сами ставят этот заголовок, Tempo считает доверенными. `multitenancy_enabled` по умолчанию `false`.

**`X-Scope-OrgID`** — заголовок тенанта. Это не пароль. Прокси должен выставлять его **сам** после логина.

**Gateway** — обратный прокси перед Tempo (опция чарта). Сам Tempo **аутентификации не имеет**. Анонимный доступ к 3200/4317 = читать и писать трейсы.

**Vulture** — тестовый клиент Grafana: пишет синтетические трейсы и читает их обратно. Учение, не нагрузка прода.

**`fail_on_high_lag`** — дефолт `true` с 3.0.2+: если лаг Kafka пересекается с окном запроса — **ошибка**, а не тихий неполный результат.

**`query_frontend.query_end_cutoff`** — отсечка свежего окна (в файле оставляют **30s**).

**Overrides** — лимиты на тенанта: `ingestion.rate_limit_bytes`, `burst_size_bytes`, `max_traces_per_user`, `global.max_bytes_per_trace`. В примерах Helm (пример, не закон): 5 MB/s на тенанта, 1000 live traces, 10 MB на трейс.

**Redaction API** — в Tempo 3.0: замазать атрибуты уже записанных трейсов. Аварийный инструмент, не политика «можно писать всё».

**Jaeger / Zipkin** — старые приёмники в конфиге ещё есть. Практичный контракт файла: **только OTLP**.

**Helm `tempo-distributed`** — чарт микросервисов. 3.0.6 тянет образ 3.0.2; Kubernetes **≥ 1.25**. Tempo Operator (`TempoStack`) — другой инсталлятор.

**Tanka / Jsonnet** — эквивалент Helm-манифеста другим синтаксисом.

**SSE-KMS / SSE-S3 / SSE-C** — шифрование объектов на стороне S3. Это настройки бакета, не «Tempo сам шифрует файлы». SSE-C: ключ у Tempo, потеря ключа = не прочитать блоки.

**ACL Kafka** — кто может писать/читать топик ingest: писать — distributor; читать — live-store, block-builder, metrics-generator.

**SASL** — аутентификация клиента к Kafka. Без TLS в документе Kafka SCRAM недопустим.

**NTP** — синхронизация часов. TraceQL и окна компакции завязаны на время спанов.

**CSI / WaitForFirstConsumer** — плагин диска Kubernetes; том создаётся в той же зоне, где под, чтобы PVC не оказался в ЦОДе A, а под — в B.

**PDB** — лимит снятия подов при drain. На scheduler `minAvailable: 1` не спасёт от мёртвого ЦОДа.

**OOM** — процесс убит из-за лимита памяти. OOM live-store = дырка в свежем окне и replay из Kafka.

**Grafana** — UI поиска. У Tempo своего дашборда нет. Datasource Tempo на URL gateway.

**Loki / Prometheus / Mimir / Wazuh** — логи, метрики, SIEM. Tempo их не заменяет.

**SoT (source of truth)** — место правды по клиентам. Tempo не SoT. ПДн в атрибутах спана — утечка.

**RPO / RTO** — сколько уже принятых данных готовы потерять / за сколько снова принимать. Object storage в одном ЦОДе задаёт RPO истории при падении этой площадки.

**Кардинальность (в metrics-generator)** — сколько разных значений label. Высокая кардинальность `span_name` раздувает Prometheus.

**Image tag `latest`** — не брать. Прод: **3.0.3**. Линия 2.x — другая архитектура (ingester/compactor удалены в 3.0), in-place downgrade нет.

Источники формулировок: глоссарий и тело `Grafana Tempo.md`. Новых порогов RTT и размеров диска здесь нет.
