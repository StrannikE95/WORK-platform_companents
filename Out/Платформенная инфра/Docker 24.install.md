# Docker Engine 24.0.9 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Docker 24.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Docker Engine — демон на одной Linux-машине: собирает образы и запускает контейнеры. Это **не** Kubernetes и не кластер.

Версия в этой инструкции: **Docker Engine 24.0.9** (последний патч линии 24.0, релиз 31 января 2024).  
Линия **unmaintained**: security-поддержка 24.0 закончилась **8 июня 2024**; после 24.0.9 патчей нет. BuildKit CVE, о которых вендор писал в релиз-нотах 24.0.9, **этой сборкой не закрыты** (фикс — Engine 25.0.2+).  
Документация линии: https://docs.docker.com/engine/release-notes/24.0/

**Честно:** 24.0.9 — не безопасный runtime боевого кластера в 2026 году. Учёба — локальный Compose. Бой Kubernetes использует **containerd**, не `dockerd` как CRI. Если линию всё же ставят — только на **builder-VM**, не на worker'ы.

Stretch одного Swarm на несколько дата-центров здесь **не собираем**: порога RTT для Raft manager'ов в документации Docker нет, и Swarm **не** является путём этой платформы.

---

## О чём эта инструкция молча договорилась

1. Один Swarm на 2–3 дата-центра не поднимаем. Overlay/Raft между площадками не обещаем.
2. Бой-оркестратор — **vanilla Kubernetes 1.36.x + kubeadm** в каждом дата-центре отдельно (`Kubernetes.install.md`). CRI — **containerd**. Engine 24 **не** ставится на worker'ы.
3. Если 24.0.9 всё же фиксируют письменно — роль: стенд разработчика и **сборочные VM**. Не Kafka, не Camunda, не озеро.
4. Учебный стенд — изолированная сеть. Пароль в примере не секрет.
5. Цифр нагрузки нет — нет числа builder-VM и размера `/var/lib/docker`. Ориентир «чтобы завелось» на учёбе: 2 CPU / 4 ГиБ.
6. Пакеты Docker Inc. того времени (`docker-ce` 24.0.9), не `docker.io` дистрибутива, не Docker Desktop, не static tarball в бой.
7. Две площадки: builder хотя бы в двух. Три — лучше по одному в каждой. Общего Raft между ними нет и не нужно.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** `docker build`, Compose (Postgres/Redis рядом с сервисом), отладка Dockerfile. **Не зачем:** HA, Swarm, эмуляция Kubernetes.

### Что должно быть до установки

- Linux 64-bit (или Dev-машина с Docker Engine; Desktop — другой продукт).
- Порты стенда не торчат в интернет.
- Ядро с overlay, cgroup; диск под `/var/lib/docker` **локальный**, не NFS.
- Свободен Unix-сокет; **2375 не слушать**.

### Установка (пакеты на одну машину)

Пакеты линии **24.0.9** (репозиторий Docker Inc. того времени / зеркало). Static tarball вендор **не** рекомендует в бой — и на учёбе лучше пакеты, чтобы зависимости (containerd/runc) были явными. После установки:

```bash
docker version
# Client/Server: 24.0.9  — не «24.0 какой скачается»
# API демона линии 24.0 = 1.43; в бандле 24.0.9: runc 1.1.12 — сверять docker info
```

`daemon.json` (`/etc/docker/daemon.json`):

```json
{
  "live-restore": true,
  "storage-driver": "overlay2",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "icc": false,
  "no-new-privileges": true
}
```

Затем `systemctl restart docker`. Swarm **не** включать: `live-restore` со Swarm несовместим.

Проверка:

```bash
docker compose version
docker run --rm --network none hello-world
```

Привязка опубликованных портов — к `127.0.0.1`, не `-p 5432:5432` на все интерфейсы.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Один `dockerd` | да | Не учимся кворуму |
| Swarm | нет | Иначе нельзя live-restore; это не путь боя |
| API | только Unix-сокет | 2375 = удалённый root |
| `icc: false` | да | Default bridge без лишней связности; Compose сам сделает user-defined сеть |
| Ротация `json-file` | 10m × 3 | У драйвера **нет** max-size по умолчанию |
| Experimental containerd store | **нет** | В 24.0 это experiment |
| `--privileged` / сокет в сервисы | запрещены | Привычка уедет в CI |

Чего **не** упрощаем: `USER` не root в образе; лимиты памяти; секреты не в Git; тег образа ≠ `:latest`; 2375 не слушать.

### Как понять, что стенд живой

1. `docker version` = 24.0.9 с обеих сторон.
2. Compose поднимает сервис; рестарт `dockerd` при `live-restore` не убивает долгоживущий контейнер.
3. Нет слушателя `0.0.0.0:2375`.
4. Образ, который потом уедет в Kubernetes, собирается здесь и пушится в **staging-реестр**, не только «на ноутбуке есть».

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный Compose, те же OCI-образы | Падение VM = простой стенда |
| | Не ловит CRI, CNI, 2376 |
| | Успешный Compose **не** доказывает бой |
| | 24.0.9 приучает CI к линии без патчей |

Перед боем полезен **препрод-сборки**: отдельный хост с **тем же** `daemon.json`, push в тот же класс реестра.

## Бой: сборочные машины в двух–трёх дата-центрах, без Swarm

**Зачем:** собирать образы и пушить в реестр, переживая отказ **одной builder-машины / одного дата-центра со сборкой**. Runtime приложений — Kubernetes + containerd. Цифр «ядер под сборку» нет — ниже минимум независимости хостов, не смета.

### Почему не stretch и почему не Swarm

Swarm Raft на manager'ах — тот же класс риска, что etcd. Порога RTT в документации Docker **нет**. Платформа уже выбрала Kubernetes. Второй оркестратор и `dockerd` как CRI через cri-dockerd **не берём**: лишний hop, root-демон на каждой ноде, EOL Engine под kubelet 1.36.

Целевая роль: Engine только на CI/builder.

### Как расставить машины

На **нодах Kubernetes** Engine **нет**. CRI = containerd (`Kubernetes.install.md`).

**Builder-хосты** — независимые `dockerd`, без общего кворума:

| Сколько площадок | Что где | Если умер дата-центр со сборкой |
|---|---|---|
| **Две** | В каждой ≥1 builder; общий **реестр** (HA реестра — другой продукт) | Сборка уходит на живую площадку. Выкат приложений зависит от Kubernetes и реестра, не от Docker |
| **Три** | По builder'у в каждой (минимум два из трёх живы) | То же |

Не склеивать builder'ы Swarm «чтобы было HA»: для сборки это лишние 2377/7946/4789 между площадками.

Если 24.0.9 на builder всё же ставят — понимать: **vendor-security линии нет**. Компенсации (минимум пакетов, нет 2375, свой реестр, сканер) **не заменяют** патчи. Письменно: исключение с датой вывода **или** уход на поддерживаемый Engine (на дату соседнего файла живая линия — 29.x). Смена линии **не отменяет** правило «не dockerd как CRI».

### Что должно быть до боевой установки

- Kubernetes в каждом дата-центре; на worker'ах **нет** `dockerd`.
- Реестр организации; с прод-сети Docker Hub запрещён.
- Локальный SSD/NVMe под `/var/lib/docker`. **Не NFS.**
- NTP. `daemon.json` из git, одинаковый на всех builder'ах.
- Секреты сборки — не в демоне «как получится»; сокет не в CI-подах.

### Порядок установки (каждый builder)

1. Пакеты **24.0.9** (если линия зафиксирована) или поддерживаемый Engine — по письменному решению.
2. Тот же `daemon.json`, что на учёбе, плюс явно: **нет** `-H tcp://0.0.0.0:2375`. Удалённо — только SSH (`DOCKER_HOST=ssh://…`) или mTLS **2376**, если удальное управление доказано необходимым.
3. `live-restore: true` — если на хосте есть долгоживущие helper-контейнеры. Чистый ephemeral-builder может без него.
4. Группа `docker` — поимённо, не «все разработчики».
5. Мониторинг заполнения `/var/lib/docker` и inode. Prune — по политике, не слепой `docker system prune -a` по cron.

Не ставить Engine рядом с kubelet на той же ноде: iptables Docker vs CNI.

Безопасность каждого builder (без этого хост дырявый):

1. Зафиксировать письменно: 24.0.9 — исключение с датой вывода **или** уход на поддерживаемый Engine. Без пункта 1 vendor-security **нет**.
2. API только Unix-сокет. Группа `docker` поимённо.
3. Не монтировать `/var/run/docker.sock` в job-поды. DinD — изолированная VM, не сокет хоста.
4. Не `unconfined` seccomp, не `--privileged` без тикета. `no-new-privileges` уже в `daemon.json`.
5. Исходящий pull — только реестр организации. BuildKit CVE 2024 на 24.0.9 **не закрыты** — цитата релиз-нотов, не гипотеза.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| `storage-driver` | overlay2 | Дефолт 24.x на Linux; containerd store в 24.0 — experiment |
| `log-opts` max-size | обязательны | Иначе диск убивает хост |
| 2375 | никогда | Удалённый root |
| Сокет в контейнерах CI | нет | DinD/socket = побег на хост |
| `--privileged` сборок | нет на общем пуле | Исключение с тикетом |
| seccomp / AppArmor | не `unconfined` | «Чтобы завелось» — дыра |
| Content Trust | если ИБ требует | Не замена сканера CVE |
| Данные озера/Kafka | не в writable layer | Слой — для кода |

`userland-proxy`: дефолт true. На хосте с кучей `-p` часто ставят `false` — только поняв nft/iptables **этого** хоста.

### Как расти, когда появятся цифры нагрузки

1. Сборка упирается в CPU, диск слоёв, сеть до реестра. Горизонталь = **ещё независимые builder'ы**, не «один docker на 128 ядер» как единственная стратегия.
2. Лимиты памяти на контейнеры сборки: без них job съест хост.
3. Параллелизм CI ограничивать очередью, не надеждой на 24.0.
4. Кэш слоёв важнее «одного огромного Docker»; HA — у реестра.

### Проверки, без которых это ещё не бой

1. На worker Kubernetes: `crictl`/`containerd`, **нет** `dockerd` как CRI.
2. `docker version` на builder = зафиксированная версия.
3. Нет слушателя 2375. Попытка pull с Hub из прод-сети — отказ.
4. Убить один builder: очередь CI берёт другой; приложения в Kubernetes живы.
5. Алерт на заполнение `/var/lib/docker` срабатывает на стенде до боя.
6. Сокет не смонтирован в пайплайн-поды.

### Что хорошо и что плохо в схеме «только builder'ы, без Swarm»

| Хорошо | Плохо |
|---|---|
| Не спорит с Kubernetes и с etcd | Сам Engine не даёт HA приложений — и не должен |
| Падение builder'а не роняет бизнес-поды | Нужен живой реестр |
| Можно снять 24.0.9, не трогая кластер | Линия без патчей; BuildKit CVE 24.0.9 не закрыты |
| Нет Raft между площадками | N копий `daemon.json` разъедутся без git |

**Не готово к бою**, если: 24.0.9 на worker'ах Kubernetes; открыт 2375; группа `docker` у отдела; сокет в CI-подах; Swarm и kubelet на одних нодах; Swarm «на 2–3 ЦОДа»; `latest` с Hub; NFS как `/var/lib/docker`; нет ротации логов; cri-dockerd «потому что привыкли к docker ps».
