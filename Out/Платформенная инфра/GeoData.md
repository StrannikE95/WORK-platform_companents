# GeoData (ООО «АйТи Гео») — развёртывание и настройка

Продукт: **облачная / on-premise low-code платформа GeoData** (управление данными, BPMN-процессы, пространственный анализ, интеграции, конструкторы форм и электронных документов с ЭП).  
Вендор: ООО «АйТи Гео» (IT Geo), сайт продукта https://datageo.ru/, документация https://docs.datageo.ru/, контакты https://www.it-geo.ru/.  
Реестр отечественного ПО: запись **№ 17166 от 03.04.2023**. Свидетельство о регистрации программы ЭВМ **№ 2023612186 от 31.01.2023**.  
Версии прикладных модулей в руководстве администратора на docs.datageo.ru: **clientui / adminui / timejobexecutor / bpmncryptopro / timeeventhandler / geometry / statistic — 4.0.1**, **workflow — 4.0.2**. Публичного changelog «последний релиз на август 2026» у вендора нет — ниже опираемся на **опубликованное руководство**, а не на догадку о более новой линейке.

Этот текст — не копия мануала «скопируй yaml и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

GeoData **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить **это** ПО на ту же инфраструктуру (Kubernetes, 3 ЦОДа) и где оно **пересекается** с уже выбранными кусками архитектуры. Пересечение здесь не косметика: GeoData сама содержит процессный движок, свои очереди Kafka, свои коннекторы к СМЭВ/Росреестру/ФИАС и своё хранение.

Источники, по которым проверены факты (иначе утверждение помечено как допущение):

- https://docs.datageo.ru/ — руководство администратора (назначение, подготовка, развёртывание ОПО и ППО), разработчика и пользователя;
- https://datageo.ru/, https://datageo.ru/platform.html, https://datageo.ru/cases.html, https://datageo.ru/ai-network.html, https://datageo.ru/geodataplatform.html;
- патент РФ **RU 2790038** (состав логических компонент платформы; это описание способа, не инсталлятор).

Страница «Среда развертывания ППО» (`administrator_guide/operations/deployment_environment.html`) и глава «Аварийные ситуации» с портала документации **не были загружены** (таймаут). Если вендор там уточняет HA на 3 ЦОДа — это нужно дочитать у него, а не выдумывать.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Low-code** | Большую часть интеграций и процессов собирают в графическом редакторе, а не пишут сервис с нуля. Код всё равно есть: у GeoData это «русскоязычные команды» встроенного интерпретатора. |
| **BPMN 2.0** | Стандартная «картинка» бизнес-процесса (блоки, стрелки, шлюзы). GeoData исполняет такие модели **своим** движком `workflow`, это **не** Camunda. |
| **Интерпретатор** | Программа, которая пошагово выполняет команды, которые аналитик написал на языке платформы. Если интерпретатор упал — текущие шаги процесса не идут. |
| **Модель процесса / экземпляр** | Модель — чертёж («как должно быть»). Экземпляр — один конкретный прогон (одна заявка, один ETL-запуск). У GeoData есть реестр моделей, версий и исполняемых экземпляров. |
| **ППО** | Прикладное ПО самой GeoData: контейнеры `clientui`, `adminui`, `workflow` и остальные модули из дистрибутива. |
| **ОПО** | Общесистемное (базовое) ПО, без которого ППО не стартует: Cassandra, Kafka, Elasticsearch, PostgreSQL/PostGIS, Redis, Swift, Keycloak и т.д. Вендор перечисляет конкретные версии. |
| **Модуль аналитика (`adminui`)** | Веб-UI, в котором проектируют процессы, источники, формы, права. |
| **Модуль исполнителя (`clientui`)** | Веб-UI для тех, кто выполняет задачи процесса (кнопки, формы, документы). |
| **`workflow`** | Сервер исполнения процессов. Это «сердце» платформы. |
| **`geometry`** | Сервер пространственных операций (пересечения, буферы, работа с контурами). Ходит в **PostgreSQL/PostGIS**. |
| **`bpmncryptopro`** | Подпись электронных документов через **КриптоПро** (СКЗИ). Без лицензии/носителей ЭП этот модуль не «просто Java». |
| **`timejobexecutor` / `timeeventhandler`** | Задачи по расписанию и постановка следующих шагов процесса во времени. |
| **`statistic`** | Сбор статистики исполнения (через Kafka и Elasticsearch). |
| **Датасет** | Массив разнородных данных, который платформа загружает, валидирует, обогащает. В маркетинге и в патенте — центральная сущность. |
| **Источник данных** | Подключение, которое аналитик заводит в UI: СУБД, очередь, API. Не путать с «озером эталона» вашей архитектуры. |
| **СМЭВ 3.0** | Система межведомственного электронного взаимодействия. Готовая шина государства. Адаптер в GeoData — **клиент** к ней, не замена вашего интеграционного контура целиком, пока вы так не решите. |
| **ФИАС / ЕГРН / Росреестр** | Федеральная адресная система / реестр недвижимости / ведомство. Вендор заявляет готовые модули к ним. |
| **PostGIS** | Расширение PostgreSQL для геометрии (точки, полигоны, пространственные индексы). «Таблица с контурами зданий» обычно живёт здесь. |
| **Cassandra** | Распределённая СУБД без классических SQL-транзакций «как в Postgres». В GeoData в ней — схема исполнения процессов (`workflow_schema`). |
| **Фактор репликации (RF)** | Сколько копий данных. RF=2 значит две копии. При трёх ЦОДах RF=2 **не раскладывает** по копии на каждый ЦОД. |
| **SimpleStrategy / NetworkTopologyStrategy** | Стратегии репликации Cassandra. SimpleStrategy **не знает** про ЦОДы. NetworkTopologyStrategy знает (`dc0: 3` = три копии в логическом ЦОДе `dc0`). |
| **ZooKeeper** | Отдельный кворум для Kafka **3.x**. В Apache Kafka 4.x его уже нет (KRaft). Вендор GeoData ставит **Kafka 3.4.0 + ZooKeeper**. |
| **Swift** | Объектное хранилище OpenStack (файлы, PDF, вложения). В GeoData файловое хранилище документов — объектное; в инсталляторе это Swift. |
| **Keycloak** | Сервер логинов (OAuth/OIDC): «кто ты». UI GeoData пускает по логину/паролю через него. |
| **Nexus** | Реестр Docker-образов дистрибутива. Образы ППО пушат сюда, Kubernetes забирает отсюда. |
| **HAProxy + Keepalived** | Балансировщик HTTP/TCP + плавающий VIP. В матрице ОПО GeoData они есть (версии 2.4 / 2.2.4). Это **другое** ПО, у вас на него уже есть отдельный документ. |
| **Replica (Kubernetes)** | Сколько одинаковых подов модуля. В примерах вендора для ППО подставляют **3**. Три пода на одной ноде/в одном ЦОДе — это не три ЦОДа. |
| **onCloud / onPremise** | Облако вендора vs установка у вас. Для контура с гособменом обычно on-premise. На странице поставки как интернет-сервиса вендор пишет, что «специальные действия по установке на стороне пользователя не требуются» — это про **SaaS**, не про ваш Kubernetes. |
| **ЭП / СКЗИ / КриптоПро** | Электронная подпись / средство криптозащиты / конкретный сертифицированный продукт. Модуль `bpmncryptopro` на этом стоит. |
| **AI Network** | Надстройка GeoData: локальные LLM, YandexGPT/GigaChat, RAG, MCP, Telegram-боты. В главе установки ОПО/ППО её нет — это отдельный контур (GPU, исходящие API, данные в промптах). |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. Вендор в загруженных главах **цифр не даёт**. |
| **Stretch** | Один логический кластер, железки в нескольких ЦОДах. Для Cassandra/Kafka это свой набор правил; инсталлятор GeoData написан вокруг **одного** `dc0`. |

## Основные элементы системы и зависимости

### Что входит в «экземпляр GeoData» (это одно ПО из нескольких слоёв)

Два слоя. Их нельзя путать.

**1. Прикладные модули (ППО, контейнеры Kubernetes, namespace в примере — `geodata`):**

| Модуль | Зачем | Как вендор масштабирует в инструкции |
|---|---|---|
| **adminui** | UI аналитика (nginx + JS) | Deployment, в примере **3** реплики, отдельный Service/LB `adminui-lb` |
| **clientui** | UI исполнителя | То же, `clientui-lb` |
| **workflow** | Исполнение BPMN/скриптов | То же, `workflow-lb`, образ **4.0.2** |
| **geometry** | Пространственные расчёты | То же, `geometry-lb`; JDBC в PostgreSQL |
| **bpmncryptopro** | Подпись ЭП | То же, `bpmncryptopro-lb` |
| **timejobexecutor** | Расписание | Реплики есть, отдельный LB в таблице IP **не** указан |
| **timeeventhandler** | Постановка следующих шагов | Аналогично |
| **statistic** | Статистика исполнения | Отдельный properties (`setupstat.properties`), Kafka + Elasticsearch + Cassandra |

UI ходит в `workflow` и в Keycloak. Конфиг ППО в инструкции зашивают в файл `application-dit.properties` и **вшивают в образ** (`docker cp` + `docker commit`) перед push в Nexus.

**2. Базовое ПО (ОПО) — таблица версий из руководства администратора («Подготовка к работе»):**

| ПО | Версия в таблице вендора | Роль в GeoData |
|---|---|---|
| **Apache Cassandra** | 4.1.0 | Состояние процессов, оргструктура, метаданные исполнения (`workflow_schema`) |
| **Apache Kafka** | 3.4.0 | Внутренняя шина шагов/логов/статистики/файловых событий |
| **Elasticsearch** | 8.6.2 | Поиск/индекс экземпляров (`jobinstance` в примере statistic) |
| **PostgreSQL** | 15.2 | В первую очередь геометрия модуля `geometry` (JDBC) |
| **PostGIS** | 3.3 | Пространственные типы и функции в Postgres |
| **Redis** | 7.0.8 (в главе установки — «Redis 7.0») | Кэш/оперативные структуры; в примере конфига **один** хост |
| **OpenStack Swift** | 2.29.2 | Объектное файловое хранилище документов |
| **Keycloak** | в таблице указано **3.4**; в главе установки стоит каталог **`keycloak-21.1.2`** | Логины UI (OAuth). **Версии в двух главах не совпадают — это надо закрыть с вендором, не выбирать «на глаз».** |
| **Kubernetes** | 1.24.1 | Оркестрация ППО |
| **HAProxy** | 2.4 | Балансировка (в списке ОПО) |
| **Keepalived** | 2.2.4 | VIP к балансировщику (в списке ОПО) |
| **Nexus Repository** | 3.49.0 | Реестр образов |

ОС в инструкции по ОПО: **Ubuntu 22.04 LTS** (допускаются Debian-подобные с оговоркой). Браузеры для клиента: Chrome ≥ 81, Яндекс.Браузер ≥ 76, Opera ≥ 12, Safari ≥ 13; нужна **WebGL 1.0**.

Логические компоненты из патента RU 2790038 (не инсталлятор, но совпадает с тем, что продают): ядро управления данными, моделирование данных, BPM обработки, BPM документооборота, бизнес-аналитика, **Message Bus**.

### Служебные топики Kafka (создаёт инсталлятор, RF=2, 50 партиций)

Это **не** ваши бизнес-топики `client.updated`. Это внутренность GeoData:

- `jobtimeeventtopicprod`
- `timeeventtopicprod`
- `tokentoexecute`
- `workflowlogs`
- `workflowtokenstatus`
- `statistictopic`
- `filestorageactiontopic`
- `audittopics` (в тексте инструкции строка команды на этом топике обрезана, имя топика указано)

`offsets.topic.replication.factor=3`. Продюсер statistic в примере: `acks=all`.

### Источники, которые аналитик может подключить из UI

По руководству пользователя: **PostgreSQL, MongoDB, Cassandra, MS SQL, Oracle, Elasticsearch**; очереди **Kafka и RabbitMQ**. Готовые модули на сайте продукта: **ФИАС, Росреестр, СМЭВ 3.0, Яндекс, Почта РФ**. В кейсах также: PostGIS, geojson, PBF, XML, XLSX, REST, ЕГРН, DaData.

Это коннекторы **процессов**, не «GeoData заменяет озеро».

### Чего в GeoData нет (частая путаница)

| Нужно системе | Это не GeoData | Зачем помнить |
|---|---|---|
| Общесистемная шина событий всех микросервисов | Ваш **платформенный** Kafka (у вас отдельный документ на 4.3.1 KRaft) | У GeoData **своя** Kafka 3.4.0 + ZooKeeper и свои топики. Это не доказанная совместимость с вашим кластером 4.3.1 |
| Camunda / «процессный движок типа Camunda» | Свой `workflow` | Два BPMN-движка = два места правды по заявкам. Так не оставляют «на всякий случай» |
| Озеро эталонных клиентских данных | Cassandra GeoData — про исполнение процессов; эталон геометрии у них обычно в **PostGIS/Postgres** или во внешней БД-источнике | SoT клиентских карточек в GeoData «потому что low-code» — архитектурное решение, его нет в вашем исходном ТЗ |
| Интеграционный фасад «система сказала какие данные нужны — API само сходило в 30 ведомств и отдало нормализованное» | Частично похожий **продуктовый** контур, но это конструктор процессов + готовые адаптеры, не ваш отдельный Integration API | Либо GeoData *и есть* этот фасад, либо она ходит в ваш фасад. Оба сразу — двойные таймауты и двойной парсинг СМЭВ |
| OpenSearch как поисковый кластер платформы | Вендор ставит **Elasticsearch 8.6.2** | Не смешивать с вашим OpenSearch и с Wazuh indexer |
| Официальный оператор / Helm «GeoData на любой Kubernetes 1.36» | Дистрибутив: `docker load` tar.gz → Nexus → `kubectl apply` yaml | Совместимость манифестов 1.24 с вашим Kubernetes **не заявлена** |
| HA Redis / HA PostgreSQL «из коробки GeoData» | В инструкции Redis и Postgres — **по одному серверу** | Падение этой одной машины = деградация кэша и геометрии |
| ТрёхЦОДовая схема Cassandra/Kafka | Инсталлятор: Cassandra `dc0`, keyspace `SimpleStrategy` RF=2; Kafka без rack; Swift `region 1 zone 1` | Это схема **одной площадки с несколькими узлами**, не «пережили ЦОД» |
| ГОСТ TLS на всех каналах ОПО | Модуль ЭП — КриптоПро; у Elasticsearch в примере **`xpack.security.enabled: false`** | Подпись документов ≠ шифрование канала Cassandra/Kafka/ES |

### Зависимости окружения (обязательны)

Из руководства, без добавлений «наверное ещё нужно»:

- **Дистрибутив ППО** (`Distr/Apps/`, tar.gz образов, yaml, скрипты `setup*.sh`) — публичного Docker Hub нет.
- **Kubernetes** той версии, которую подтвердит вендор. В доке — 1.24.1; у вас в платформе планируется сильно более новая линия. Это **блокер**, пока нет письма вендора.
- **Реестр образов Nexus** (или совместимый, если вендор разрешит замену) + TLS-сертификат docker `certs.d`.
- **Кластер Cassandra 4.1.0**: вендор пишет минимум **3 узла на каждый ЦОД**, от 8 ГБ RAM и 100 ГБ диска на узел.
- **Кластер Kafka 3.4.0 + ZooKeeper**: минимум 3 узла; 4 ядра / 8 ГБ / 100 ГБ на узел (цифра вендора).
- **Кластер Elasticsearch 8.6.2**: рекомендуется 3 узла; 8 ГБ / 100 ГБ; имя кластера в примере `smartgeoelcluster`; роли `[data, master]`.
- **PostgreSQL 15.2 + PostGIS 3.3**: в инструкции один сервер; минимум 4 ГБ RAM / 2 ГБ диска — это «чтобы поставилось», не терабайты геометрии.
- **Redis 7.0**: один сервер в инструкции; 4 ядра / 4 ГБ / 20 ГБ.
- **Swift 2.29.2**: распределённое объектное хранилище; в тексте — RF=3, «рекомендуется 5 узлов, RF не больше числа узлов»; пример колец добавляет **3** IP в одном region/zone.
- **Keycloak**: в главе установки Java **OpenJDK 11** и дерево `/opt/keycloak-21.1.2`; 2 ядра / 4 ГБ / 250 ГБ.
- **SMTP** для уведомлений.
- **КриптоПро** и контур ключей ЭП — если нужны юридически значимые документы (заявлено на сайте и отдельным модулем).
- **DNS / FQDN** на все узлы ОПО и на LB ППО.
- **Исходящий доступ** к тем ведомствам и коммерческим API, которые реально включите (СМЭВ, Росреестр, Яндекс, Почта РФ, DaData). Без сети адаптер не «отказоустойчив», он просто не работает.

### Как GeoData стыкуется с вашей архитектурой

Три честных роли. Нужно выбрать **одну** до закупки, иначе получите три источника истины.

```
Вариант А (узкий): GeoData = пространственный ETL + ГИС-слой
  Озеро эталона / ваши сервисы  ──данные──►  GeoData (PostGIS-расчёты, карта)
  Kafka платформы              ──события──►  ваши микросервисы / Camunda
  Интеграционный API           ──СМЭВ──►     ведомства

Вариант Б (широкий): GeoData = процесс + интеграции + гео
  Заявка/ETL ──► GeoData.workflow ──► СМЭВ/Росреестр/ФИАС
                      │
                      ▼
              Cassandra + PostGIS + Swift
  (Camunda и «свой Integration API» тогда не дублируют тот же контур)

Вариант В (запрещённый по умолчанию): «и Camunda, и GeoData.workflow,
и своё интеграционное API, и озеро, и внутренние топики GeoData»
  — четыре места, где живёт заявка и нормализованный ответ ведомства.
```

Платформенный Kafka 4.3.1 и Kafka 3.4.0 GeoData — **разные кластеры**, пока вендор письменно не подтвердит работу клиентов 4.0.x против вашего брокера.

```
Микросервисы / Camunda / Integration API     ← ваша шина (Kafka 4.x)
        │
        │  (только если сознательно спроектировали коннектор)
        ▼
   GeoData ППО (K8s)
        │
        ├── Cassandra 4.1.0     состояние процессов
        ├── Kafka 3.4.0 + ZK    внутренние топики
        ├── Elasticsearch 8.6.2 индекс задач
        ├── PostgreSQL+PostGIS  геометрия
        ├── Redis               кэш
        ├── Swift               файлы/ЭП-документы
        └── Keycloak            логины UI
```

## Краткие вводные

### Зачем вам вообще GeoData, если уже есть Camunda и Kafka

Потому что вендор закрывает **другой** кусок, чем «микросервис написал в топик»:

1. Аналитик описывает ETL и госуслугу в одном BPMN и встроенном языке — без отдельной армии разработчиков на каждый коннектор ФИАС/ЕГРН.
2. Пространственные операции (пересечение участка с зоной, сравнение контуров зданий за два года) встроены, без отдельного GeoServer «с нуля».
3. На выходе — экранные формы исполнителю и PDF с ЭП. Это ближе к оказанию госуслуги, чем «событие в Kafka».

Это сильная сторона **продукта**. Это же и риск: команда начнёт тащить в GeoData всю бизнес-логику, а микросервисы на Kafka останутся декорацией.

### Как устроена отказоустойчивость (что реально обещает инсталлятор)

Вендор на сайте пишет «горизонтальная масштабируемость и отказоустойчивость» и «распределённая система хранения». В **руководстве администратора** это расшифровывается так:

| Компонент | Что в инструкции | Что это значит простыми словами |
|---|---|---|
| ППО в Kubernetes | 3 реплики модулей | Упал **один под** — остальные обслуживают UI/API, **если** сессии/состояние не в этом поде, а в Cassandra/Redis/Postgres |
| Cassandra | ≥ 3 узлов **на ЦОД**; `system_auth` через NetworkTopologyStrategy `dc0: 2`; рабочий keyspace **SimpleStrategy RF=2** | Переживёт падение **узла**, если вторая копия жива. SimpleStrategy **не** раскладывает копии по ЦОДам |
| Kafka 3.4 + ZK | 3 брокера; топики RF=2; offsets RF=3 | Падение 1 брокера: offsets, скорее всего, живы; **пользовательский топик с RF=2 может пережить 1 брокер, не 1 ЦОД** |
| Elasticsearch | 3 узла, master+data | Типичный маленький кластер одной площадки. Zone awareness в процитированном фрагменте **не задан** |
| Swift | RF=3, узлы в одном region/zone в примере | Файлы в трёх копиях на трёх машинах **одной** зоны |
| Redis | один `redis.host` | Нет сентинела/кластера в инструкции = **SPOF** (одна точка отказа) |
| PostgreSQL | один `geodatapostgresX` | **SPOF** для geometry |
| Keycloak | один `geodatakcX` | **SPOF** для входа в UI |

Итого: инсталлятор даёт **внутриплощадочную** устойчивость части стораджей и подов. «Упал один из трёх ЦОДов — GeoData жива» **этим текстом не доказано**.

### Как устроено масштабирование

Единицы роста разные:

- **UI (`adminui`/`clientui`)** — горизонталь подов. Это nginx со статикой и JS; упирается в `workflow` и Keycloak, не в «ещё 20 UI».
- **`workflow` / обработчики событий** — горизонталь подов **плюс** пропускная способность Cassandra и внутренних топиков Kafka (у них уже 50 партиций — это запас параллелизма внутри GeoData).
- **`geometry`** — CPU/RAM подов **и** Postgres/PostGIS. Тяжёлые пересечения полигонов не лечатся «ещё одним clientui».
- **Cassandra** — вендор явно: добавлять узлы, считать **по ЦОДам**.
- **Объём файлов** — Swift (диск колец), не Kubernetes emptyDir.
- **Объём геометрии «терабайты»** — диск и индексы PostGIS, не RF Kafka.

Нагрузки у вас нет — поэтому **нет** числа «хватит N воркеров». Есть только минимумы вендора «чтобы кластер ОПО считался кластером».

### Безопасность: что в доке опасно копировать «как в примере»

Это не придирка к стилю, это дыры, если оставить как в инструкции:

1. **Elasticsearch: `xpack.security.enabled: false`** — любой, кто достучался до 9200, читает/пишет индекс задач.
2. **Redis: `#bind 127.0.0.1` и `protected-mode no`** — Redis слушает везде без штатной защиты. Так делают на закрытой лабораторной сети, не в проде с тремя ЦОДами.
3. **Секреты в образе:** пароли Cassandra/Postgres/OAuth/JKS кладут в properties и делают `docker commit`. Слой образа хранит секрет. Ротация пароля = пересборка образа. Это слабое место поставки, его надо менять на Kubernetes Secrets / внешний vault **если вендор поддержит**, а не молча править yaml.
4. **Пароли и JKS в тексте инструкции** приведены открытым текстом. Их нельзя переносить в ваш контур.
5. **Пример `mail.smtp.ssl.trust=*`** — доверять любому сертификату SMTP.
6. Модуль ЭП (**КриптоПро**) — отдельный контур ИБ: носители, лицензии, сертифицированная ОС/среда. Он **не** чинит пункты 1–5.

Сильная сторона безопасности продукта: в UI есть раздел **«Безопасность»** с разрешениями/запретами до папки процесса, задачи, формы; субъекты — пользователь, позиция, подразделение, атрибут. Это RBAC **прикладного** уровня, не замена NetworkPolicy и TLS ОПО.

6. **RTT между ЦОДами неизвестен.** Для stretch Cassandra/Kafka это может убить латентность записи. Пока нет замера — не обещаем stretch.
7. **Нагрузки нет.** Нет ёмкости дисков Cassandra/Swift/PostGIS «под терабайты».
8. **Формального RPO/RTO/24×7 нет.** Ожидание «чтобы не падало» ≠ SLA.
9. **Keycloak 21.1.2** (глава установки) важнее строки «3.4» в сводной таблице; таблицу считаем ошибкой документации, **пока вендор не скажет иначе**.
10. **КриптоПро нужен**, если электронные документы с ЭП входят в scope (сайт и модуль это предполагают). Если ЭП выкинете — модуль `bpmncryptopro` всё равно в дистрибутиве; отключаемость без вендора не подтверждаем.
11. **AI Network не входит** в минимальный контур развёртывания ОПО/ППО.
12. **Совместимость манифестов с Kubernetes 1.36.x не проверена.** Допущение для прода: либо вендор сертифицирует ваш кластер, либо под GeoData держат отдельный кластер поддерживаемой версии.
13. Страница «Среда развертывания ППО» не прочитана. Допущение: критичных сюрпризов по составу ОПО там нет, состав уже есть в «Подготовке» и «Операциях». Если появится — этот документ обновляют.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** договора и «постановки в прод». Иначе купите продукт, который нельзя честно вписать в 3 ЦОДа.

| Пробел | Почему это ломает решение |
|---|---|
| **Роль GeoData vs Camunda vs Integration API vs озеро** | Без решения будут две BPMN-исполнялки и два пути в СМЭВ. Отказоустойчивость «системы» станет неопределённой: какая из четырёх жива — уже спор |
| **Письмо вендора: 3 ЦОДа, RTO при потере площадки, stretch vs active-passive** | Публичный инсталлятор — односайтовый. Сами «докрутить RF и rack» без поддержки = серая схема |
| **Совместимость с вашим Kubernetes (не 1.24.1)** | Deprecated API, PSA, CSI, Ingress — типичные причины «yaml из Distr не накатился» |
| **Можно ли заменить Elasticsearch→OpenSearch, Kafka 3.4→4.3 KRaft, Swift→MinIO, Nexus→Harbor** | Всё это логично для унификации платформы и **всё это не обещано**. Замена без вендора = вы сами сопровождаете форк |
| **Профиль нагрузки geometry и размер PostGIS** | «Терабайты» могут оказаться в контурах зданий, не в Cassandra. Тогда SPOF Postgres из инструкции неприемлем даже на одной площадке |
| **RTT и бандвидс между ЦОДами** | Stretch Cassandra (если пойдёте этим путём) чувствителен к задержке; Swift репликация между ЦОДами — к каналу |
| **Контур СМЭВ: тестовый / промышленный, УШ, сертификаты, регламент простоя ведомства** | HA GeoData не лечит ночь, когда Росреестр не отвечает. Нужны таймауты, идемпотентность, очередь на стороне процесса |
| **152-ФЗ / КИИ / ГОСТ / аттестованный контур** | Персональные и кадастровые данные, ЭП, исходящие в коммерческие API (Яндекс). Меняет, можно ли onCloud, куда писать логи ES без xpack, нужен ли отдельный сегмент |
| **Лицензии: GeoData, КриптоПро, Elasticsearch** | ES 8.x — не Apache 2.0 как OpenSearch. Юристы должны увидеть EULA **до** «у нас уже есть OpenSearch, поставим ES рядом» |
| **Кто патчит ОПО** | Вендор фиксирует Cassandra 4.1.0, Kafka 3.4.0, ES 8.6.2, K8s 1.24.1. Жить на них без патчей в 2026-м — отдельный риск уязвимостей. Кто имеет право поднять минор — только вендор или вы? |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод) — **порядок вендора**, его не переставлять:

1. DNS/FQDN, сеть, диски под Cassandra/Kafka/ES/Swift/Postgres.
2. ОПО в последовательности руководства (Cassandra → ES → … → Redis). Шаг можно пропустить, только если **тот же** продукт **той же** мажорной линии уже стоит и вендор это разрешил.
3. Keycloak: реалм, клиент `oauth.clientid` (в примере `workflowprod`), сертификат для UI.
4. Nexus + загрузка образов ППО.
5. Namespace Kubernetes, LB-сервисы, 3 реплики модулей, properties **без** паролей из мануала.
6. Проверка: в браузере открывается стартовая страница **модуля аналитика** после логина — так вендор определяет «система жива».
7. Отдельно: перенос процессов между стендами zip-экспортом (официальная методика: папка процессов **без** вложенных папок; связанные задачи/источники/файлы/формы попадают в архив по правилам инструкции).

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** аналитики собирают процесс, разработчики смотрят коннекторы, понятен язык платформы. **Не** цель: доказать переживание ЦОДа и терабайты PostGIS.

#### Топология (минимум, который ещё похож на продукт)

ОПО можно сжать относительно прода, но **не** в «один docker-compose со всем», если вендор такого профиля не дал. Практичный тест, согласованный с тем, как устроен дистрибутив:

- 1 Kubernetes namespace `geodata`;
- ППО: **по 1 реплике** каждого модуля (не копировать `<replicas>/3`);
- Cassandra: **3 узла всё же лучше 1** — иначе вы не увидите даже SimpleStrategy RF=2. Если железа нет — 1 узел и RF=1 **только** с пометкой «это не GeoData-кластер, это песочница»;
- Kafka 3.4 + ZK: 1 или 3 брокера; на 1 брокере топики только с RF=1;
- Elasticsearch: 1 узел `master,data`;
- Postgres+PostGIS, Redis, Swift, Keycloak, Nexus — по одному;
- HAProxy/Keepalived на тесте можно заменить Service/Ingress Kubernetes, **если** вендор не завязал лицензию/конфиг на конкретные VIP из таблицы 192.168.10.20x.

Сеть теста — изолированная. Пример вендора с `protected-mode no` и выключенным xpack **допустим только здесь**, и то лучше сразу включить пароль Redis и ES, чтобы привычка не уехала в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Реплики ППО | 1 | Нет нагрузки и нет требования HA |
| RF Cassandra/Kafka | 1 на совсем маленьком стенде | Некому реплицировать |
| КриптоПро | заглушка/тест УЦ, если юристы разрешат | Иначе стенд встанет на закупке СКЗИ |
| СМЭВ | тестовый контур или мок | Промышленный СМЭВ на тесте опасен и часто запрещён |
| AI Network | выкл | Иначе утечка датасетов в LLM |

#### Чего на тесте **не** стоит упрощать

- Имена внутренних топиков Kafka и keyspace `workflow_schema` — иначе перенос процессов на прод сломается неожиданными именами.
- OIDC через Keycloak (не «встроим basic auth навсегда»).
- Отдельный Postgres для PostGIS, не «запихнем геометрию в Cassandra» — продукт так не устроен.
- Экспорт/импорт процессов по методике вендора — это ваш CI для BPMN.

#### Сильные стороны такой схемы

- Близко к тому, как вендор реально поставляет ПО (K8s + ОПО), а не к фантазии «это просто веб-морда».
- Дешевле трёх ЦОДов.
- Позволяет решить **роль** продукта (вариант А или Б) на живых кейсах, до контракта на промышленный ОПО.

#### Слабые стороны (обязательно понимать)

- Успешный ETL на одном `workflow` **не** доказывает, что statistic + 50 партиций + RF=2 заработают.
- Стенд не ловит: rebalance Kafka, split Cassandra, латентность PostGIS, падение Keycloak, заполнение Swift.
- Если на тесте выключить Elasticsearch security, в прод это утащат копипастой.

Практическая рекомендация: препрод — **уменьшенная копия односайтового прода вендора** (3 Cassandra, 3 Kafka, 3 ES, 3 реплики ППО, RF как в инструкции), уже с TLS и секретами не в образе. Без этого первый сюрприз будет на пользователях.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «под терабайты» нет. Ниже — правила, без которых экземпляр **нельзя** называть промышленным на трёх площадках. Часть правил **не из мануала GeoData**, а из свойств ОПО, которое вендор сам велел поставить; где мануал молчит — это явно сказано.

#### Шаг 0. Макроархитектура (сделать до установки)

**Вариант P1 — один сайт активен, два других холодные/тёплые копии.**  
Ближе к тому, что описал вендор (один `dc0`). Отказ ЦОДа = процедура восстановления из бэкапов Cassandra/Postgres/Swift + включение ППО в другом ЦОДе. **RPO > 0**, RTO измеряется часами, пока не отрепетируете.

**Вариант P2 — stretch ОПО на 3 ЦОДа (один логический GeoData).**  
Нужно, чтобы «упал один ЦОД — процессы живы». Публичная инструкция этого **не собирает**. Имеет смысл **только** после проекта с вендором:

- Cassandra: **NetworkTopologyStrategy**, по ЦОДу свой DC, RF такой, чтобы переживали 1 ЦОД (типично по 3 узла на DC, как вендор и просит «3 на каждый ЦОД», но keyspace **не** SimpleStrategy RF=2);
- Kafka: **не RF=2**, а RF=3 + rack=ЦОД + min.ISR=2, и это **всё ещё Kafka 3.4+ZK**, не ваш 4.3 KRaft, пока не договорятся;
- Elasticsearch: awareness по зоне, не три master+data в одном зале;
- Swift: **разные zone = ЦОД**, не `zone 1` трижды;
- Redis: Sentinel или Cluster, узлы в разных ЦОДах, клиенты ППО это должны понимать (сейчас в properties один `redis.host` — **нужна доработка вендора**);
- PostgreSQL: Patroni/аналог + синхронная реплика; stretch Postgres на 3 ЦОДа — отдельный тяжёлый проект; часто геометрию оставляют **активной в одном ЦОДе** с репликой;
- Keycloak: infinispan-кластер / внешняя БД, не один JVM;
- ППО: `topologySpreadConstraints` по `topology.kubernetes.io/zone`, PDB, не 3 пода в одном ЦОДе.

**Пока вендор не подписал P2, честный прод — P1** (или «актив в ЦОД1 + асинхронная репликация стораджей», тоже с его схемой).

##### Сильные / слабые стороны P1

| Сильное | Слабое |
|---|---|
| Совпадает с публичным инсталлятором | Потеря активного ЦОДа = простой GeoData |
| Проще сеть и Kafka/Cassandra | Не закрывает ожидание «непрерывная работа» без оговорок |
| Меньше сюрпризов SimpleStrategy/RF=2 | Люди будут думать, что «3 реплики в K8s» = 3 ЦОДа |

##### Сильные / слабые стороны P2

| Сильное | Слабое |
|---|---|
| Шанс пережить 1 площадку | Латентность записи Cassandra/Kafka ≥ RTT; неподтверждённый вендором stretch |
| Ближе к вашему лозунгу 3 ЦОДов | Redis/Postgres/Keycloak в штатном properties — не кластер |
| Можно переиспользовать идеи ваших документов по Kafka/K8s | Два Kafka-кластера (платформа 4.x и GeoData 3.4) всё равно останутся |

#### ОПО: что поднять обязательно и как не ослабить

**Cassandra.** Минимум по вендору: 3 узла на ЦОД. Для трёх ЦОДов это уже **9** узлов, если идти в P2. Keyspace процессов **не оставлять** `SimpleStrategy / replication_factor: 2` — это прямая цитата инсталлятора и она **не** для мульти-DC. Аутентификацию, которую вендор включает (роль `dba` и т.д.), в проде не выключать. Диск 100 ГБ из мануала — пол тестовый; под нагрузку считать отдельно.

**Kafka 3.4.0 + ZooKeeper.** Отдельный кластер. Не класть внутренние топики GeoData на платформенный 4.3.1 «чтобы сэкономить». Топики с RF=2 из инструкции для прода на 3 ЦОДах **недостаточны**: при потере ЦОДа можно потерять все реплики топика. Цель, если вендор согласится: RF=3, min.ISR=2, `acks=all` (у statistic это уже есть), rack awareness. ZooKeeper — 3 или 5 узлов, не на тех же дисках, что брокерский лог, в разных ЦОДах при P2. Это другая операционка, чем KRaft из вашего документа по Kafka.

**Elasticsearch 8.6.2.** Три узла как минимум на активной площадке. **Включить** security (в примере вендора выключен). Не совмещать с OpenSearch платформы и с SIEM. Снапшоты индекса — во внешнее хранилище, реплики шардов бэкапом не являются.

**PostgreSQL 15.2 + PostGIS 3.3.** Для прода даже в P1: первичная + синхронная реплика + PITR. Модуль `geometry` без этой БД бессмысленен. Растягивать синхронный коммит на 3 ЦОДа без замера RTT нельзя.

**Redis.** Не оставлять одиночку и `protected-mode no`. Либо Sentinel/Cluster с подтверждением вендора, либо принять, что потеря Redis = потеря кэша и возможная деградация `workflow` (глубину деградации вендор в загруженных главах не расписал — это надо спросить).

**Swift.** RF=3, узлы и зоны совпадают с доменами отказа. Бэкап метаданных колец и политик. Не NFS вместо Swift, если вендор ждал Swift API.

**Keycloak 21.1.2 (по главе установки).** Для прода — не один процесс: как минимум внешняя БД Keycloak + 2 реплики в разных ЦОДах при P2, либо активный ЦОД + проверенный standby. UI GeoData без Keycloak не логинится (руководство пользователя: вход по логину и паролю).

**HAProxy 2.4 + Keepalived 2.2.4.** В матрице ОПО они есть; детальный текст их установки в выгрузке «Операций» не попал. Для VIP на `*-lb` (201–205 в примере) это логичная пара. Сверять с вашим отдельным документом по HAProxy: линейка 2.4 у GeoData **старше**, чем актуальный LTS в том документе; что ставить — решает совместимость с yaml GeoData, не «самая новая».

**Nexus.** Внутренний, с нормальным TLS, не `storepass password` из примера. Образы ППО с секретами внутри — не катить; цель — внешние Secret.

#### ППО в Kubernetes

- Отдельный namespace, NetworkPolicy: UI → workflow/Keycloak; workflow → Cassandra/Kafka/Redis/ES/Postgres/Swift; наружу — только согласованные egress (СМЭВ, Почта РФ, Яндекс).
- Реплики модулей **≥ 3** как в инструкции, размазать по зонам.
- PDB, чтобы drain ноды не убивал все `workflow` сразу.
- Не `emptyDir` для чего бы то ни было, что должно пережить под: состояние в ОПО, не в поде.
- Ресурсы CPU/RAM вендор в загруженных главах для подов **не нормирует** (есть только минимумы ОПО). Ставить requests/limits после замера на препроде, не «как у nginx 64Mi».
- Катить модули по одному; `workflow` и `timeeventhandler` одновременно — риск рассинхрона шагов (это осторожность эксплуатации, не цитата вендора).

#### Безопасность прода (без этого экземпляр не считается настроенным)

1. **Сеть:** ОПО не торчит в интернет. СМЭВ и коммерческие API — через контролируемый egress (у вас задуман интеграционный периметр; даже в варианте Б GeoData не должна «гулять» куда угодно).
2. **TLS** на Kafka, ES, Cassandra client, Postgres, Keycloak, Swift, Ingress UI. Пример с plaintext JDBC/`http://` Keycloak — только для лаборатории.
3. **Секреты** не в образе и не в git. JKS для ЭП/OAuth — в секретном томе, права только у `bpmncryptopro`/workflow.
4. **RBAC платформы:** роли аналитика и исполнителя развести; запрет «все могут экспортировать процессы» (в экспорте уезжают источники и файлы).
5. **Аудит:** топик `audittopics` / логи workflow не выключать; куда они пишутся — хранить вне того же ЦОДа, что единственная Cassandra, иначе аудит погибнет вместе с ней.
6. **ЭП:** сертифицированная среда КриптоПро, учёт токенов, регламент отзыва. Это отдельный проект ИБ.
7. **Исходящие коммерческие API** (Яндекс, DaData): персональные адреса уходят наружу. Юридическое основание и маскирование — до включения адаптера, не после инцидента.

#### Мониторинг (минимум, иначе HA декоративная)

Живость ППО ≠ «под Running». Смотреть:

- Cassandra: down-узлы, отставание, диск;
- Kafka: ISR < RF, лаг внутренних консьюмеров GeoData;
- ES: статус кластера не green, диск;
- Postgres: репликация, долгие spatial-запросы;
- Redis: память, evictions;
- Swift: незавершённые репликации;
- Keycloak: доступность токена;
- `workflow`: ошибки шагов, очередь `tokentoexecute`;
- исходящие коннекторы: таймауты СМЭВ/Росреестра (иначе «GeoData медленная», хотя лежит ведомство).

Ваш Prometheus/Grafana могут это снимать, но **экспортёры в дистрибутиве GeoData в прочитанных главах не описаны** — закладывайте стандартные экспортеры ОПО, не «из коробки GeoData».

#### Сильные стороны предлагаемого прода (P1 + ужесточение секретов/TLS)

- Опирается на **реальный** дистрибутив, а не на рекламный абзац «отказоустойчивость».
- ППО горизонталится в Kubernetes так, как вендор показал (3 реплики, отдельные LB).
- Пространство и процессы закрываются одним продуктом реестра отечественного ПО — это часто требование закупки, не технический каприз.

#### Слабые стороны (обязательно понимать)

- Публичная схема **не** является 3-ЦОД HA.
- Redis, Postgres, Keycloak в инструкции — точки отказа.
- Свой устаревший стек ОПО (K8s 1.24, Kafka 3.4+ZK, ES 8.6.2) рядом с вашей новой платформой = два мира патчей.
- Dual-run с Camunda и своим Integration API размоет источник истины.
- `docker commit` секретов — плохая поставка; без договора на нормальные Secret останетесь с этим.
- Elasticsearch с выключенным xpack в примере — прямой путь к утечке индекса задач.
