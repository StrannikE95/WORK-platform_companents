# GeoData 4.0.1 / workflow 4.0.2 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `GeoData.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

GeoData — low-code платформа процессов, форм и геометрии ООО «АйТи Гео». Это **платное** ПО: без договора и дистрибутива образы не скачать. Готового образа на Docker Hub нет.

Версии прикладных модулей из руководства администратора: **4.0.1**, движок процессов **workflow 4.0.2**. Публичного changelog «август 2026» нет — фиксируем **опубликованное руководство**. Документация: https://docs.datageo.ru/

Обычный путь прикладных модулей: `docker load` из tar.gz → реестр образов (в таблице поставщика — Nexus **3.49.0**) → `kubectl apply`. Официального Helm «на любой Kubernetes» нет.

Базовое ПО (без него прикладные модули не стартуют) — **свои** кластеры тех версий, что в таблице руководства: Cassandra **4.1.0**, Kafka **3.4.0** + ZooKeeper, Elasticsearch **8.6.2**, PostgreSQL **15.2** + PostGIS **3.3**, Redis **7.0.8**, Swift **2.29.2**. Их нельзя молча заменить платформенным Kafka 4.x, OpenSearch или «свежим» Postgres, пока поставщик письменно не разрешит.

ОС в главах установки базового ПО: **Ubuntu 22.04 LTS** (Debian-подобные — с оговоркой). Windows-сервер поставщик не заявляет.

Один кластер, размазанный на несколько дата-центров, здесь **не собираем**. Инсталлятор написан вокруг одного логического `dc0`. Глава «Аварийные ситуации» с портала **не была загружена**. Пока поставщик не подписал другую схему — живой контур в одной площадке, вторая — восстановление из бэкапа.

## О чём эта инструкция молча договорилась

1. **Один живой контур в одном дата-центре.** Cassandra, Kafka, ZooKeeper, Elasticsearch и Swift из инсталлятора не размазываем по городам. Стратегия копирования без понятия о площадках и фактор 2, кольца Swift в одной зоне — схема **одной** площадки, не «пережили дата-центр».
2. Установка **у себя**, не облако datageo.ru.
3. В документации GeoData — Kubernetes **1.24.1**. Совместимость манифестов с более новой линией **не заявлена**. До письма поставщика: отдельный кластер поддерживаемой версии **или** поставка стопорится. Накатывать yaml дистрибутива «на глаз» нельзя.
4. Платформенные Kafka 4.x, Camunda, объектное хранилище, OpenSearch — **соседние** продукты. Не подставлять их вместо базового ПО GeoData без письма.
5. Роль: пространственный контур и загрузка **или** процессы и госинтеграции в GeoData. Не оба сразу с Camunda и своим интеграционным API на те же заявки.
6. Учебный стенд — закрытая сеть. Цифр вашей нагрузки нет. Минимумы поставщика (8 ГиБ / 100 ГиБ на узел Cassandra и т.д.) — «чтобы кластер считался кластером», не смета.
7. Keycloak: в главе установки дерево **`keycloak-21.1.2`**; строка «3.4» в сводной таблице — расхождение, закрывать с поставщиком.
8. Два дата-центра: мозг в первом, восстановление во втором. Три — то же плюс вторая копия бэкапа. Третий логический дата-центр в Cassandra **не** добавляем сами.
9. AI Network в первый боевой контур не входит.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** аналитик собирает процесс, понятен язык платформы, коннекторы. **Не зачем:** доказывать отказ дата-центра и терабайты PostGIS.

### Что должно быть до установки

- Дистрибутив `Distr/Apps/` (tar.gz, yaml, скрипты). Публичного Docker Hub нет.
- Kubernetes, который **подтвердит поставщик** для этой поставки (не считать более новую линию доказанной).
- DNS, Ubuntu 22.04 для базового ПО (или Debian-подобная с оговоркой).
- Браузер с WebGL 1.0.
- Сеть стенда не торчит в интернет.

### Установка (порядок поставщика не переставлять)

1. Операционная система, синхронизация времени, диски. Каталоги данных Cassandra / Kafka / Elasticsearch / Postgres — **локальные диски**, не «сетевая папка на всякий случай».
2. Базовое ПО по руководству (Cassandra → Elasticsearch → … → Redis). Версии — как в таблице. Пропуск шага — только если тот же продукт той же мажорной линии уже есть **и** поставщик разрешил.
3. Keycloak: область, клиент входа (в примере имя `workflowprod`).
4. Реестр образов:

```bash
docker load -i <модуль>.tar.gz
docker tag … <registry>/…:4.0.1   # workflow: 4.0.2
docker push …
```

5. Пространство имён, сервисы, манифесты из дистрибутива: `kubectl apply -f …`
6. На тесте реплики прикладных модулей **1**, не копировать «3 из примера». Модули: `clientui`, `adminui`, `workflow` (**4.0.2**), `geometry`, `bpmncryptopro`, `timejobexecutor`, `timeeventhandler`, `statistic` (**4.0.1**).
7. Критерий поставщика «система жива»: стартовая страница **модуля аналитика** после логина.

Служебные топики внутренней Kafka (это **не** ваши бизнес-события): `jobtimeeventtopicprod`, `timeeventtopicprod`, `tokentoexecute`, `workflowlogs`, `workflowtokenstatus`, `statistictopic`, `filestorageactiontopic`, `audittopics`. В инструкции фактор копирования 2, 50 партиций. На одном брокере — только фактор 1 и пометка «песочница».

Cassandra: 3 узла лучше 1. Один узел и фактор 1 — только с пометкой «это не кластер, это песочница».

Пример поставщика «Redis без защиты» и «Elasticsearch без пароля» — **только** изолированный стенд. Лучше сразу пароль, чтобы привычка не уехала.

Пароли из текста инструкции и `docker commit` файла настроек **не** переносить как норму — даже на тесте лучше секрет Kubernetes, если манифест это переживёт; иначе зафиксировать долг.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Реплики прикладных модулей | 1 | Не учимся переживать падение пода |
| Копии Cassandra/Kafka | 1 на крошечном стенде | Некому копировать |
| КриптоПро | заглушка / тест, если юристы разрешат | Иначе стенд встанет на средстве криптозащиты |
| СМЭВ | тестовый контур или заглушка | Промышленный контур на тесте часто запрещён |
| AI Network | выкл | Тексты датасетов не должны уехать в модель |
| Свой Kafka 4.x / OpenSearch | не подменять базовое ПО | Нет письма о совместимости |

Чего **не** упрощаем: имена внутренних топиков и пространство ключей `workflow_schema`; вход через Keycloak; отдельный Postgres для PostGIS; экспорт процессов zip по методике (папка **без** вложенных папок).

### Как понять, что стенд живой

1. Модуль аналитика открывается, логин через Keycloak. Модули 4.0.1 / workflow 4.0.2.
2. Один процесс доходит до шага. Геометрия ходит в PostGIS, не в Cassandra.
3. Снесли виртуальную машину с единственной Cassandra — процессы пропали. Так и должно быть на тесте.
4. Успешный прогон **не** доказывает копирование, 50 партиций и падение Keycloak.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Близко к реальной поставке (архив → реестр → apply) | Нет автоматического переживания машины, нет разноса по площадкам |
| Можно выбрать роль продукта на живых кейсах | Защиту Elasticsearch с теста утащат копипастой |
| | Совместимость yaml 1.24 с вашей линией Kubernetes **не** проверена |

Перед боем полезен **препрод**: 3 Cassandra, 3 Kafka, 3 Elasticsearch, 3 реплики прикладных модулей, фактор копирования как в мануале, шифрование каналов, секреты не в образе — всё **в одном** дата-центре.

## Бой: один живой дата-центр, второй — запас из бэкапа

**Зачем:** поставить то, что поставщик умеет описать: устойчивость **внутри одной площадки** (несколько узлов базового ПО, несколько реплик прикладных модулей). Отказ **всего дата-центра** = этого контура нет, пока не восстановите Cassandra, Postgres и Swift на другой площадке и не включите прикладные модули. Цифр «сколько данных потеряете / как быстро встанете» поставщик в загруженных главах **не даёт** — мерить после сценария восстановления.

### Почему кластер не растягиваем на несколько дата-центров

Инсталлятор: Cassandra с одним логическим именем площадки, пространство ключей **без** раскладки по дата-центрам, фактор копирования **2**; Kafka без стоек, топики с фактором 2; Swift — три адреса в одном регионе/зоне; Redis, PostgreSQL и Keycloak — **по одному** хосту. «Три реплики в Kubernetes» ≠ три площадки.

Голосование Cassandra/Kafka/ZooKeeper и копирование файлов чувствительны к задержке сети; порога в документации GeoData **нет**. Доработка «как в блогах Cassandra» без письма поставщика = серая схема, этот файл её не собирает.

### Как расставить машины

**В активном дата-центре:**

- Прикладные модули: реплики **не меньше трёх**, как в инструкции, на разных нодах **этой** площадки, политика «не снимать все workflow сразу». Состояние **не** в пустом томе пода: оно в базовом ПО.
- Cassandra: минимум **3 узла на эту** площадку. Аутентификацию, которую поставщик включает, не выключать. Диск 100 ГиБ из мануала — ориентир старта.
- Kafka 3.4.0 + ZooKeeper: отдельный кластер **этой** площадки. Не класть внутренние топики GeoData на платформенный Kafka 4.x «чтобы сэкономить». ZooKeeper — не на тех же дисках, что журнал брокера.
- Elasticsearch 8.6.2: три узла на активной площадке. **Включить** защиту (в примере поставщика выключена). Снимки индекса — во внешнее хранилище. Не совмещать с OpenSearch платформы и с журналом безопасности.
- Swift: фактор 3 на узлах **этой** зоны. Не сетевая папка вместо Swift, если поставщик ждал его протокол.
- PostgreSQL 15.2 + PostGIS 3.3: в инструкции одиночка. Для боя даже в одной площадке одиночка геометрии — точка отказа. Поднять запасную копию **внутри** площадки только если поставщик подтвердит адрес, который пишут прикладные модули. Пока нет письма — принять точку отказа и компенсировать бэкапом, не молча подставить другой мажор Postgres.
- Redis: не оставлять «слушать везде, защита выкл». Либо схема с несколькими узлами **с письмом поставщика** (сейчас в настройках один хост), либо принять, что потеря Redis = потеря кэша (глубину деградации workflow поставщик в загруженных главах не расписал).
- Keycloak 21.1.2: интерфейс без него не логинится. Для боя — не один процесс без бэкапа его базы.
- HAProxy 2.4 + Keepalived 2.2.4 в матрице поставщика. Что ставить — совместимость с yaml GeoData, не самая новая линейка из `HAProxy.install.md`.
- Шифрование каналов к Cassandra, Kafka, Elasticsearch, Postgres, Keycloak, Swift и на входе — **включить**. Пример с открытым текстом — только лаборатория.
- Номера модулей зафиксировать: **4.0.1 / 4.0.2**.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: всё базовое и прикладное ПО. Вторая: копии бэкапов Cassandra / Postgres / Swift (и снимок Elasticsearch) и процедура поставщика; **не** член того же кольца и того же голосования | Экран и процессы стоят, пока не восстановите данные и не включите прикладные модули. Время простоя замерить. Копия узла **не** заменяет бэкап: команду «удали» она послушно повторит |
| **Три** | Третья: ещё одна копия бэкапа или холодный контур | То же. Три независимых набора процессов «для надёжности» — это три разных правды прав доступа, так не делают |

Не дублировать слепо:

| Уже есть на платформе | У GeoData своё | Правило |
|---|---|---|
| Kafka 4.x | Kafka 3.4.0 + ZooKeeper, свои топики | Отдельный кластер, пока нет письма |
| Camunda | свой `workflow` | Один контур заявок, не два движка «на всякий случай» |
| Объектное хранилище платформы | Swift 2.29.2 | Не подмена без поставщика |
| OpenSearch | Elasticsearch 8.6.2 | Не смешивать с поиском платформы |
| PostgreSQL другой линии | 15.2 + PostGIS 3.3 | Версия — из таблицы GeoData, пока поставщик не скажет иначе |

### Что должно быть до боевой установки

- Письмо поставщика **до** договора: Kubernetes (1.24 vs ваша линия); типовая схема на 2–3 площадки; можно ли заменить поиск/очередь/хранилище/реестр образов; как класть секреты без `docker commit`; обязательность КриптоПро; глава «Аварийные ситуации»; кто закрывает дыры базового ПО между релизами GeoData; как лицензируется Elasticsearch 8.6.2.
- Пока совместимость Kubernetes не подтверждена — **нельзя** честно накатить yaml дистрибутива на платформенный кластер.
- Пароли Cassandra, Postgres, Redis, OAuth и ключи — в Vault (или аналог). Никаких паролей из мануала.
- SMTP. Исходящий контур только к согласованным ведомствам и API.
- Роль продукта зафиксирована.
- NTP на всех машинах.

### Порядок установки в активном дата-центре

Это этапы, не замена руководства вашей поставки:

1. Закрыть пробел Kubernetes письмом. Не начинать бой на неподтверждённой версии «на глаз».
2. ОС, диски, NTP. Затем базовое ПО строго по руководству, версии зафиксировать.
3. **Включить** то, что в примере выключено: защита Elasticsearch; Redis не слушает мир; шифрование каналов.
4. Nexus (или согласованный реестр) с нормальным TLS, не учебный пароль хранилища ключей из примера.
5. `docker load` → метка **4.0.1 / 4.0.2** → push → `kubectl apply`.
6. Настройки: пароли **не** из мануала и по возможности **не** в слое образа. Цель — секрет Kubernetes, если поставщик поддержит.
7. Сетевая политика: интерфейс → workflow и Keycloak; workflow → базовое ПО; наружу — только список ведомств.
8. Проверка: логин аналитика. Затем один боевой процесс и zip-перенос по методике.
9. Бэкап Cassandra + Postgres + Swift (+ снимок Elasticsearch). Восстановление прогнать на стенде **до** пользователей.
10. Единый вход в боевом режиме; журнал (топик аудита / логи workflow) хранить так, чтобы он не погиб вместе с единственной Cassandra.

Восстановление во втором дата-центре — **тот же** порядок базового и прикладного ПО на холодном контуре, данные из бэкапа поставщика. Без прогона нет времени восстановления.

Если в договоре поставщик дал другую схему (несколько логических площадок Cassandra, кластер Redis) — следуйте **ему**. Иначе честный план: один живой зал + бэкап.

### Правила конфигурации боя

| Слой | Правило |
|---|---|
| Сеть | 443 — из сети единого входа; Cassandra, Kafka, Elasticsearch, Redis, Postgres, Swift — не из пользовательской сети |
| Исходящие | Только озеро, витрины и согласованные ведомства, не «гулять куда угодно» |
| Elasticsearch без защиты | запрещён |
| Redis «защита выкл» | запрещён |
| Доверять любому сертификату SMTP | нет |
| Секреты в образе | долг или запрет: смена пароля = пересборка |
| Стратегию копирования Cassandra сами на три площадки | не расширять |
| Внутренние топики на Kafka 4.x | нет |
| AI Network | не в минимальном контуре |
| Выгрузки процессов | в архиве уезжают источники и файлы — не «все могут экспортировать» |

Электронная подпись: КриптоПро — отдельный проект ИБ (носители, лицензии, среда). Он не чинит открытый текст базового ПО.

Катить прикладные модули по одному. `workflow` и постановщик следующих шагов одновременно — риск рассинхрона шагов (осторожность эксплуатации, не цитата поставщика).

Ресурсы подов — после замера на препроде. В загруженных главах норм CPU/RAM для подов нет.

### Как расти, когда появятся цифры нагрузки

1. Больше людей у экрана → поды интерфейса, упирается в workflow и Keycloak.
2. Тяжёлая геометрия → CPU подов geometry **и** PostGIS, не «ещё один экран».
3. Объём файлов → Swift. Терабайты контуров → диск PostGIS.
4. Cassandra — добавлять узлы на **этой** площадке, как пишет поставщик.
5. Минимумы 8 ГиБ / 100 ГиБ — ориентир «кластер существует», не список закупки.

### Проверки, без которых это ещё не бой

1. Модули 4.0.1 / workflow 4.0.2; базовое ПО тех версий, что в таблице.
2. Выключили один под workflow — интерфейс жив, **если** состояние в Cassandra/Redis.
3. Восстановили Cassandra + Postgres + Swift на стенде второй площадки по сценарию поставщика (дочитать главу аварий, когда загрузится). Самодельный «переключили DNS» без этого — не бой.
4. Elasticsearch с паролем; Redis не открыт миру; нет паролей мануала в реестре образов.
5. Нет второго движка процессов на те же заявки без решения.
6. Манифесты 1.24 на вашей линии Kubernetes либо сертифицированы письмом, либо крутятся на отдельном кластере.

### Что хорошо и что плохо в схеме «мозг в одном дата-центре»

| Хорошо | Плохо |
|---|---|
| Совпадает с публичным инсталлятором | Падение этой площадки = нет GeoData, пока не восстановите запас |
| Не выдумываем размазанное копирование | Redis, Postgres, Keycloak в мануале — точки отказа |
| Реестр российского ПО | Стек базового ПО (Kubernetes 1.24, Kafka 3.4+ZooKeeper, Elasticsearch 8.6.2) рядом с новой платформой = два мира обновлений |
