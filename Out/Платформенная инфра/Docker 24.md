# Docker Engine 24.0.9 — развёртывание и настройка

Версия ПО: **Docker Engine 24.0.9** (последний патч линии 24.0; релиз **31 января 2024**).  
Релиз-ноты линии: https://docs.docker.com/engine/release-notes/24.0/  
Документация Engine (текущий сайт вендора описывает уже более новые линии; правила ниже сверены с тем, что явно сказано про 24.0 и с документацией Swarm/daemon, которая к 24.0 применима): https://docs.docker.com/engine/

**Статус линии 24.0 (проверено 26 августа 2026):** ветка `24.0` в репозитории Moby помечена как **Unmaintained**. На [endoflife.date/docker-engine](https://endoflife.date/docker-engine) окончание security-поддержки линии 24.0 указано как **8 июня 2024**. После 24.0.9 патчей этой линии нет. На ту же дату поддерживаемая линия Engine у Docker Inc. — **29.x** (последний патч на момент проверки — 29.7.2). Линия 25.0 ещё числится с датой окончания **4 декабря 2026** — это **не** 24.0.

Этот текст — не мануал «скопируй `apt install docker-ce`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Docker Engine **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API) как отдельный продукт. Заявлен **Kubernetes**. Ниже — что Engine 24.0.9 вообще умеет, где он в этой схеме уместен, и почему его **нельзя** честно назвать прод-runtime кластера.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Docker Engine (`dockerd`)** | Демон на одной Linux-машине: принимает команды, тянет образы, запускает контейнеры. Это **не** кластер и не Kubernetes. Один `dockerd` = один хост. |
| **Docker CLI (`docker`)** | Клиент. Ходит к демону через Unix-сокет (обычно `/var/run/docker.sock`) или по сети. |
| **Образ (image)** | Шаблон файловой системы + метаданные. Неизменяемый. Идентифицируется digest'ом (sha256), тег (`:latest`) — только ярлык. |
| **Контейнер** | Запущенный процесс из образа: namespaces + cgroups ядра Linux. Падение демона по умолчанию **убивает** контейнеры (если не включён live restore). |
| **Слой (layer) / overlay2** | Драйвер хранения образов в 24.0: слои только для чтения + тонкий записываемый слой контейнера. Писать «в контейнер» как в диск — плохая идея; данные — в **volume**. |
| **Volume** | Каталог/диск, который Docker монтирует в контейнер и который переживает удаление контейнера. Это **не** репликация на другой хост. |
| **Bind mount** | Просто кусок ФС хоста внутрь контейнера. Удобно и опасно: контейнер видит (и может писать) то, что вы отдали. |
| **`daemon.json`** | Главный конфиг демона, на Linux обычно `/etc/docker/daemon.json`. Предпочтительнее флагов в unit-файле: всё в одном месте. |
| **Unix-сокет** | Файл-труба. Кто может писать в `/var/run/docker.sock`, тот **управляет демоном**. Официально: это равносильно root на хосте (можно смонтировать `/` хоста в контейнер). |
| **Группа `docker`** | Членство в группе даёт доступ к сокету **без sudo**. Официальный post-install это включает и **предупреждает**: это привилегированный доступ. |
| **TCP 2375 / 2376** | Сетевой API демона. **2375** — без TLS (удалённый root). **2376** — TLS. В 24.0.9 порт 2375 ещё может быть включён руками; это дыра, не «удобство CI». |
| **live restore** | Контейнеры **не** убиваются, если упал/перезапустили `dockerd`. Только для **standalone**-контейнеров. С **Swarm mode несовместим** (демон откажется инициализировать swarm). |
| **Swarm mode** | Встроенный оркестратор Docker: сервисы, overlay-сеть, Raft у manager-нод. Это **конкурент Kubernetes**, не плагин к нему. |
| **Manager / worker (Swarm)** | Manager хранит состояние swarm (Raft) и планирует задачи. Worker только выполняет. Manager по умолчанию тоже может принимать задачи. |
| **Кворум Swarm** | Большинство manager'ов. 3 manager'а → переживёте **одного**. Потеря кворума: уже запущенные задачи живут, **управлять** swarm нельзя. |
| **Raft (Swarm)** | Протокол согласия manager'ов. Та же идея, что у etcd/Kafka-контроллеров: запись подтверждает большинство. |
| **`--advertise-addr`** | Адрес, который manager сообщает другим. Официально: у manager — **статический IP**; если после ребута все manager'ы сменят IP, swarm зависает. |
| **Overlay-сеть (Swarm)** | Сеть контейнеров **между хостами** (VXLAN, UDP **4789** по умолчанию). Без swarm overlay для multi-host **не** поднять. |
| **Ingress routing mesh** | Опубликованный порт сервиса слушается **на каждой** ноде swarm; трафик перекладывается на живую задачу. Это балансировка Docker'а, не HAProxy. |
| **bridge / host / none** | Сети одного хоста. `bridge` — виртуальный свитч (`docker0`). `host` — контейнер в сети хоста (изоляция сети снята). `none` — без сети. |
| **BuildKit** | Сборщик образов (с Engine 23.0 — сборщик по умолчанию). В **24.0.9 вендор явно пишет**: известные CVE BuildKit **не закрыты**; фикс — Engine **25.0.2+**. |
| **containerd image store** | В 24.0 — **experimental**: хранить образы через containerd snapshotter вместо overlay2. В прод 24.0 **не** брать. (Позже, в Engine 29, это стало дефолтом на чистой установке — это уже другая линия.) |
| **runc** | Низкоуровневый runtime, который реально создаёт контейнер. 24.0.9 поднимает runc до **1.1.12** (в т.ч. CVE-2024-21626). |
| **CRI / dockershim / cri-dockerd** | Kubernetes говорит с runtime по CRI. Docker Engine CRI **не** реализует. Встроенный адаптер (dockershim) **убрали в Kubernetes 1.24**. Внешний адаптер — **cri-dockerd** (не часть Engine 24). |
| **Rootless mode** | `dockerd` от непривилегированного пользователя. Меньше ущерба при взломе демона, больше ограничений (порты <1024, часть сети, cgroup). Для вашего прода с гособменом — отдельное решение, не «включил и забыл». |
| **userns-remap** | root внутри контейнера = обычный UID на хосте. Не включено по умолчанию. Ломает часть volume/privileged-сценариев. |
| **seccomp / AppArmor / SELinux** | Профили ядра: какие системные вызовы и файлы можно. Docker по умолчанию даёт seccomp-профиль; AppArmor/SELinux — если дистрибутив их включил. `unconfined` / `--privileged` это снимает. |
| **`--privileged`** | Почти все ограничения контейнера сняты. Для интеграционного контура с госорганами — только если без этого **физически** нельзя, и это надо уметь объяснить ИБ. |
| **Content Trust / DCT** | Подписи образов (Notary). Можно заставить демон принимать только подписанное. Это не замена сканера уязвимостей и не ГОСТ. |
| **Compose (v2 plugin)** | Файл `compose.yaml`: несколько контейнеров на **одном** хосте (или на одном swarm stack). Это не оркестратор на 3 ЦОДа. В пакетах 24.0.x Compose плагин обновляли отдельно (например 24.0.7 → Compose **v2.21.0**). |
| **Docker Desktop** | Другой продукт (VM на Windows/Mac + UI). Это **не** Docker Engine 24 на сервере ЦОДа. |
| **docker-ce vs docker.io** | Пакеты Docker Inc. vs пакет дистрибутива. Для воспроизводимой версии 24.0.9 на Linux ориентир — пакеты/бинарники Docker Inc. того времени, не «что apt сам назвал docker». |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. У Engine «данные» — `/var/lib/docker` и volumes **этого хоста**. Демон соседнего хоста их не знает. |

## Основные элементы системы и зависимости

### Что входит в Docker Engine 24.0.9 (это одно ПО)

- **`dockerd`** — демон.
- **`docker`** — CLI (пакет `docker-ce-cli` в схеме Docker Inc.).
- **containerd** — в статическом бандле 24.0.9 указан **v1.7.13**; в пакетной установке containerd часто отдельный пакет — смотреть `docker info`, не запоминать «навсегда».
- **runc 1.1.12** (в 24.0.9).
- **container runtime** внутри: создание namespaces/cgroups, сети, volumes.
- Опционально: **Swarm mode** (включается `docker swarm init`, не отдельный инсталлятор).
- Опционально в пакетах CE: плагины **buildx**, **compose**.

API демона в линии 24.0 — **1.43** (это номер Engine API, не «версия Docker»).

### Чего в Docker Engine нет (частая путаница)

| Нужно системе | Это не Docker Engine 24 | Зачем помнить |
|---|---|---|
| Оркестрация подов, HPA, PDB, зоны ЦОДов как в манифестах | Kubernetes | У вас он уже выбран. Swarm — другой оркестратор с другим API. |
| CRI «из коробки» для kubelet 1.24+ | containerd / CRI-O, либо сторонний **cri-dockerd** | Engine не говорит на CRI. Два демона (kubelet → cri-dockerd → dockerd) = лишний слой и лишний blast radius. |
| Реестр образов организации | Harbor / Quay / registry:2 и т.п. | Без реестра ноды и CI не из чего собирать прод в закрытом контуре. |
| Репликация volumes между ЦОДами | СХД / CSI / rsync / приложение | Volume живёт на хосте (или на том, что смонтировали). Падение хоста = потеря локального volume. |
| Сканер CVE образов | Trivy, Grype, Scout, … | Демон образы запускает, не аудирует. |
| Секреты как Vault | HashiCorp Vault (у вас отдельный документ) | Swarm secrets / Docker secrets — только для swarm-сервисов и это не Vault. |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS демона — обычный OpenSSL/Go TLS, не криптография КИИ. |
| Официальный SLA 24/7 и патчи на 24.0 в 2026 | Нет | Линия unmaintained. |
| Порог RTT между ЦОДами для Swarm Raft | В документации Swarm **нет** миллисекунд | Stretch-swarm — гипотеза, пока сеть не замерена. |

### Зависимости окружения (обязательны)

- **Linux 64-bit** на серверах ЦОДа (Windows-контейнеры и Docker Desktop не рассматриваем — см. допущения).
- Ядро с overlay, cgroup, iptables/nft (конкретный минимум в текущих гайдах вендора — «свежее ядро дистрибутива»; старый текст про «ядро ≥ 3.10» относится к бинарной установке и **не** является сайзингом прода).
- Диск под `/var/lib/docker`: локальный SSD/NVMe. Сетевой NFS как data-root демона — путь к порче слоёв и зависаниям.
- Синхронизация времени (TLS, логи, Swarm Raft).
- Если образы не с Docker Hub: **зеркало/реестр**, иначе `docker pull` в закрытом контуре мёртв.
- Если нужен multi-host overlay: IP-связность и открытые порты Swarm **только** между нодами, не в интернет.

### Как Docker стыкуется с вашей архитектурой

```
Разработчик / CI                          Прод-нагрузка
   docker build / compose                    Kubernetes (уже выбран)
           │                                        │
           ▼                                        ▼
   Docker Engine 24                         containerd / CRI-O
   (сборка образов, тест)                   (запуск подов)
           │
           ▼
   Реестр образов ──pull──► ноды Kubernetes
```

Kafka, Camunda, интеграционное API, озеро данных в проде живут **в подах Kubernetes**, не «в docker run на трёх ВМ». Engine 24 здесь — инструмент **сборки и локального/стендового запуска**, плюс (если кто-то потребует) устаревший путь «kubelet через Docker». Второй путь ниже разобран как антипаттерн, не как рекомендация.

## Краткие вводные

### Зачем вам Docker в этой архитектуре

Микросервисы всё равно упаковываются в OCI-образы. Команда 14+ лет в приложении, а не в оркестрации, почти наверняка уже думает «контейнер = docker». Это нормально для **сборки и отладки**. Это **не** означает, что прод должен оркестрировать те же контейнеры через Swarm или через Docker-сокет на ноде Kubernetes.

Три честных роли:

1. **Стенд разработчика / CI:** `docker build`, Compose, прогон интеграций без кластера.
2. **Сборочные машины в ЦОДе:** выделенные хосты Engine, которые только собирают и пушат в реестр (без секретов прода в демоне «как получится»).
3. **Не делать:** второй оркестратор (Swarm) рядом с Kubernetes «на всякий случай»; Docker как CRI продакшн-кластера 1.36.

### Как устроена отказоустойчивость (идея, не магия)

**Один `dockerd` отказоустойчивости не даёт.** Упал хост или демон без live restore — контейнеры этого хоста мертвы. Live restore спасает от **рестарта демона**, не от смерти машины и не от `systemctl stop docker` с убийством cgroup (зависит от того, как останавливаете сервис).

Отказоустойчивость «как у Kafka/etcd» появляется **только** если включить **Swarm** и держать кворум manager'ов:

| Manager'ов | Большинство | Переживут отказ |
|---|---|---|
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 5 | 3 | 2 |

Официальный admin guide Swarm: нечётное число manager'ов; для 3 зон раскладка **1-1-1** (для пяти — 2-2-1). Потеря кворума ≠ мгновенная смерть задач на worker'ах, но нельзя scale/update/join. Восстановление кворума «магией» — `docker swarm init --force-new-cluster` (это уже авария, не штатный failover).

**В вашей схеме оркестратор уже Kubernetes.** Второй Raft-кластер (Swarm) на тех же трёх ЦОДах удваивает операционку и не лечит Kafka/Postgres. Поэтому прод-HA приложений — в документе Kubernetes, не здесь.

### Как устроено масштабирование

Две разные оси, их путают со «горизонтальным Docker»:

| Ось | Что добавляете | Что получаете | Потолок |
|---|---|---|---|
| Контейнеры на одном хосте | процессы | CPU/RAM этого сервера | ядра и диск **одной** машины; contention на `docker0`/iptables |
| Хосты с собственным `dockerd` | машины | суммарная сборка/прогон | реестр, сеть, люди, которые патчат N демонов |
| Swarm service replicas | задачи на worker'ах | как у Deployment, но API Swarm | кворум manager'ов, overlay, ingress mesh |
| Поды Kubernetes | то, что у вас в проде | HPA, зоны, PDB | см. `Kubernetes.md` |

«Терабайты» **не** кладут в записываемый слой overlay2 и не в `/var/lib/docker` «потому что удобно». Слой — для кода. Данные озера/Kafka — их тома/диски.

На одном хосте обязательны **лимиты** (`memory`, `cpus` / cgroup): без них один контейнер съедает машину. Это не HA, это защита от noisy neighbor.

### Сокет демона — это root

Официальная страница security Engine: демон работает как root (пока не rootless); кто управляет API, может смонтировать ФС хоста в контейнер. Поэтому:

- сокет не монтировать в CI-контейнеры «чтобы внутри был docker» без изоляции (DinD/socket = типичный путь побега);
- группу `docker` не раздавать всему отделу;
- **2375 без TLS не включать никогда**;
- если удалённый API нужен — SSH (`DOCKER_HOST=ssh://…`) или mTLS на **2376**, ключи как root-пароль.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать схему. Если допущение неверно — схему пересматривать, а не «чуть подкрутить daemon.json».

1. **Целевой бинарь — Docker Engine 24.0.9 CE на Linux в ваших ЦОДах**, не Docker Desktop, не Mirantis Container Runtime, не podman-совместимый сокет.
2. **Прод-оркестратор — Kubernetes** (как в `Kubernetes.md`), CRI — **containerd** (допущение того документа). Engine 24 **не** ставится на worker'ы как runtime кластера.
3. **Роль 24.0.9 в проде, если линию всё же фиксируют:** сборочные/утилитарные хосты и стенды. Не шина событий, не озеро, не Camunda.
4. **Три ЦОДа — три домена отказа.** Если это три зала с общим питанием — раскладка Swarm 1-1-1 врёт так же, как etcd 1-1-1.
5. **Нагрузки нет** — нет числа сборочных VM «хватит», нет размера `/var/lib/docker`.
6. **Формального SLA нет.** «Беспрерывная работа» не закрывает дыру unmaintained-линии.
7. **Образы приложений — OCI**, их можно собирать Docker'ом и запускать containerd; формат образа не привязывает прод к `dockerd`.
8. **Тестовый стенд изолирован** от контура гособмена. На тесте допустим один демон и Compose; секреты прода туда не копируем.
9. **ИБ может потребовать ГОСТ / запрет Docker Hub.** Тогда зеркало, свои базы образов, свой CA для 2376 — отдельные работы.
10. Если руководство **настоит** считать Swarm прод-оркестратором вместо Kubernetes — это смена архитектуры, не «настройка Docker». Ниже Swarm описан, чтобы вы могли отказать аргументированно, а не потому что это целевой путь.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** закупки «Docker на три площадки». Иначе либо поставят EOL в прод, либо получат два оркестратора.

| Пробел | Почему это ломает решение |
|---|---|
| **Зачем именно линия 24, а не поддерживаемый Engine** | 24.0.9 не получает CVE-фиксов с июня 2024. Уже в день релиза 24.0.9 вендор написал, что **BuildKit CVE этой сборкой не закрыты** (нужен 25.0.2). В августе 2026 это не «чуть старая версия», это замороженная поверхность атаки на сборочный контур. |
| **Docker — runtime Kubernetes или только CI?** | От этого зависит, появится ли cri-dockerd на каждой ноде. Для Kubernetes 1.36 штатный путь — containerd, не Engine 24. |
| **Кто владеет реестром и допускается ли Docker Hub** | Закрытый контур без зеркала = CI и стенды встанут. Публичный Hub = утечки и supply chain. |
| **RTT и потери между ЦОДами** | Нужны, если кто-то предлагает stretch-Swarm. Цифры порога в доке Docker **нет**. |
| **Профиль сборки** (частота build, размер образов, параллелизм) | Без этого нельзя сказать, сколько builder-хостов и какой диск под слои. |
| **Требования ИБ: 152-ФЗ, КИИ, rootless, запрет privileged, DCT** | Меняют, можно ли вообще 24.0.9 (часто ответ ИБ — «нет, нет патчей»). |
| **Кто патчит хосты 24/7** | Unmaintained Engine + живой kernel/runc дистрибутива — развилка: либо живёте на патчах ОС (и всё равно в незакрытом Engine), либо уходите с 24. |
| **Есть ли уже «docker.sock в Jenkins»** | Это скрытый cluster-admin хоста. Пока сокет торчит в job'ы — модель безопасности демона фикция. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и «прод» builder'ов):

1. Зафиксировать **24.0.9** только если есть письменный стоп-фактор; иначе смена линии — **первый** шаг, не последний. Если фиксируете 24 — понимать, что требование «безопасность» этим документом **не закрывается**.
2. Ставить **пакеты**, не «распаковал static tarball в `/usr/bin`»: вендор для static сам пишет, что это не прод (нет автообновлений зависимостей).
3. Вынести `daemon.json`: storage `overlay2` (дефолт 24.x на Linux), ротация логов, live restore **только если нет Swarm**, userland-proxy осознанно.
4. Закрыть API: только Unix-сокет; удаление 2375; 2376/SSH лишь если удальное управление доказано необходимым.
5. Не давать приложению `--privileged`, не монтировать сокет, лимиты памяти/CPU, read-only root FS где возможно.
6. Диск и inode `/var/lib/docker` в мониторинг (переполнение = все контейнеры хоста).
7. Образы — со своего реестра, не `latest` в проде.
8. Бэкап: volumes и (если Swarm) каталог `/var/lib/docker/swarm` **со остановленным** manager'ом, как в admin guide; ключ auto-lock хранить отдельно.

Дальше — два режима.

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** собирать образы, поднимать Compose (Postgres/Redis рядом с сервисом, mock интеграций), отлаживать Dockerfile. **Не** цель: доказать HA трёх ЦОДов и не цель: эмулировать Kubernetes.

#### Топология

- 1 Linux VM, один `dockerd` 24.0.9.
- Сеть: default bridge + именованные user-defined bridge для Compose (DNS между контейнерами по имени сервиса). Overlay/Swarm **не** нужны.
- Хранение: overlay2 на локальном диске; volumes для БД стенда.
- `live-restore: true` — чтобы обновление демона не роняло долгоживущий стенд. Swarm не включаем, конфликта нет.
- Compose-плагин той же поставки CE.
- PSA/Restricted здесь нет (это Kubernetes). Вместо этого: не запускать privileged, не мапить `/var/run/docker.sock` в сервисы.

Минимум, чтобы «вообще завелось» (не сайзинг): 2 CPU / 4 ГиБ RAM хватит для мелкого Compose. Это не доказательство готовности интеграционного контура.

Пример направления `daemon.json` на тесте (не копия «всего мануала», смысл настроек):

```json
{
  "live-restore": true,
  "storage-driver": "overlay2",
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "icc": false,
  "no-new-privileges": true
}
```

- **`icc: false`** — контейнеры на default bridge не ходят друг к другу без явной сети. Для Compose всё равно создаётся user-defined сеть, там связность есть.
- **`no-new-privileges`** — запрет повышения привилегий через setuid. Ломает редкий софт; на тесте полезно поймать это рано.
- Ротация логов: у `json-file` **по умолчанию нет** max-size; без неё стенд убивает диск.

Не слушать `-H tcp://0.0.0.0:2375` даже «только в VLAN теста».

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Один демон | да | Некому строить кворум |
| Без TLS API | да, **только Unix-сокет** | Нет удалённых клиентов |
| Swarm | нет | Иначе нельзя live-restore, и это не прод-путь |
| DCT / подписи | можно отложить | Изолированный стенд |
| Rootless | можно отложить | Сложность vs польза на одном ноутбуке |
| Experimental containerd store | **нет** | В 24.0 это experiment |

#### Чего на тесте **не** стоит упрощать в Dockerfile/Compose

- `USER` не root в образе (иначе в Kubernetes PSA `restricted` всё равно сломается).
- `HEALTHCHECK` или хотя бы понятный liveness для критичных процессов.
- Явные лимиты памяти в Compose (`mem_limit` / `deploy.resources` — в зависимости от версии файла).
- Секреты не в Git и не в `environment:` в репозитории.
- Тег образа = digest или неизменяемый tag сборки, не `:latest`.

#### Сильные стороны такой схемы

- Поднимается за часы.
- Совпадает с тем, как разработчики уже думают о контейнерах.
- Образы те же OCI, что потом уедут в Kubernetes.

#### Слабые стороны (обязательно понимать)

- Падение VM = простой всего стенда.
- Стенд **не** ловит: Swarm Raft, overlay MTU между ЦОДами, iptables-конфликт с CNI Kubernetes, истечение клиентских сертификатов 2376, поведение cri-dockerd.
- Успешный Compose **не** является доказательством готовности прода.
- **24.0.9 на тесте приучает CI к линии без патчей.** Имеет смысл на тесте уже собирать тем же major, что уйдёт в builder-прод (поддерживаемый Engine), а 24 держать только если без него не стартует легаси-сборка.

Практическая рекомендация: препрод-сборка — отдельный хост с тем же `daemon.json`, что у builder'ов, плюс push в **тот же** класс реестра (хотя бы staging). Иначе первый сюрприз — «на ноутбуке собралось, в ЦОДе pull по политике ИБ запрещён».

### Прод: 3 ЦОДа, нагрузка

Ниже — правила. Число builder-нод «под терабайты» **не** ставится: нагрузки нет. Терабайты — не в Docker.

#### Шаг 0. Выбор макророли (сделать до установки)

Четыре варианта. Для заявленной архитектуры целевой — **C**. Остальные — чтобы не согласиться на них молча.

**Вариант C (целевой при уже выбранном Kubernetes) — Engine только на CI/builder и служебных хостах, не на worker'ах Kubernetes.**

- В каждом ЦОДе N независимых `dockerd` (нет общего кворума — и не нужен).
- Отказоустойчивость сборки: **N+1 хостов**, очередь CI подхватывает другой builder. Упал один демон — не падает Kafka и не падает интеграционное API.
- Общее состояние — **реестр образов** (HA реестра — другой продукт).
- На нодах Kubernetes — containerd, как в документе Kubernetes.

**Вариант D — Swarm как оркестратор прода на 3 ЦОДа (1 manager + workers в каждой зоне, managers 1-1-1).**

- Официальный HA Swarm: нечётные manager'ы, зоны, drain manager'ов от нагрузки, бэкап `/var/lib/docker/swarm`, `--advertise-addr` статикой.
- **Конфликт с Kubernetes:** два оркестратора, два способа секретов, две сети, две процедуры обновления.
- `live-restore` выключен.
- Overlay + UDP 4789 между ЦОДами: VXLAN без аутентификации; вендор: порт не на периметр; для недоверенной сети — encrypted overlay (`--opt encrypted`) + ESP (протокол 50), и **штраф производительности, который надо мерить**.
- Пока RTT неизвестен, stretch-Swarm **нельзя** честно обещать.

**Вариант E — Docker Engine + cri-dockerd как CRI Kubernetes.**

- Технически возможно (адаптер вне ядра Kubernetes).
- Слабое: лишний hop, сокет/демон root на каждой ноде, линия 24 без патчей, расхождение с допущением `Kubernetes.md` (containerd).
- Сильное: если какой-то легаси-инструмент **обязан** видеть `docker.sock` на ноде — это обычно лечится выносом сборки, а не возвратом dockershim.

**Вариант F — все etcd/Kubernetes как задумано, плюс «ещё Swarm на тех же машинах».**

- Не рекомендуется: порты, iptables, cgroup, диск `/var/lib/docker` vs kubelet — взаимные сюрпризы. Официальной схемы «Swarm и kubelet на одном хосте как прод» нет.

##### Сильные / слабые стороны C (builders only)

| Сильное | Слабое |
|---|---|
| Не спорит с Kubernetes и с etcd | Сам Engine не даёт HA приложений — и не должен |
| Падение builder'а не роняет бизнес-поды | Нужен живой реестр, иначе деплой встал |
| Простая модель: хост = демон | N копий `daemon.json` разъедутся без конфигурации-как-кода |
| Можно выкинуть 24.0.9, не трогая кластер | ИБ всё равно спросит, почему builder без патчей |

##### Сильные / слабые стороны D (Swarm на 3 ЦОДа)

| Сильное | Слабое |
|---|---|
| Документированный кворум и раскладка по 3 AZ | Второй оркестратор; команда учит не тот API |
| Routing mesh даёт вход на любую ноду | Mesh и VXLAN чувствительны к MTU/UDP между ЦОДами; порога RTT нет |
| Секреты/configs swarm | Это не Vault; не закрывает 30+ госинтеграций |
| | Не переживает 2 ЦОДа при 3 manager'ах |
| | 24.0.9 без патчей на всей оркестрации |

##### Сильные / слабые стороны E (cri-dockerd)

| Сильное | Слабое |
|---|---|
| Привычный `docker ps` на ноде | Kubernetes 1.24+ штатно без dockershim; лишний адаптер |
| | Root-демон на каждой ноде |
| | EOL Engine под kubelet 1.36 — несовместимо с требованием безопасности |

Дальше как **консервативный прод** описан **вариант C**. Вариант D — только если Kubernetes отменяют (этого в контексте нет).

#### Отказоустойчивость builder-хостов (вариант C)

- Минимум **два** builder'а в **разных** ЦОДах (лучше по одному в каждом из трёх): очередь CI не должна иметь единственную точку.
- Хосты независимы: нет общего Raft. Не пытайтесь «склеить» их Swarm «чтобы было HA» — для сборки это лишняя связность UDP/2377.
- `live-restore: true` на builder'е имеет смысл, если на нём кроме сборки крутятся долгоживущие helper-контейнеры. Чистый ephemeral-builder (контейнер сборки умер — и ладно) может жить без live-restore.
- Диск: отдельный том под `/var/lib/docker`; мониторинг заполнения и inode; периодический prune **по политике** (не слепой `docker system prune -a` по cron без исключений — снесёте кэш, который как раз ускоряет сборку).
- Реестр и кэш слоёв важнее «одного огромного Docker». HA самого registry — не этот документ.

Падение ЦОДа с одним из builder'ов: сборка переезжает на другие. **Выкат** в прод при падении ЦОДа зависит от Kubernetes и реестра, не от Docker.

#### Если всё же Swarm (вариант D) — только каркас, не целевой путь

Официальные порты **между нодами swarm** (не в интернет):

| Порт | Зачем |
|---|---|
| TCP **2377** | управление swarm / Raft |
| TCP и UDP **7946** | gossip / discovery overlay |
| UDP **4789** (можно сменить) | VXLAN data path. Вендор: не держать на периметре, VXLAN без аутентификации |
| IP protocol **50** (ESP) | если overlay с `--opt encrypted` |

Manager'ы: 3 (1-1-1) как старт; 5 (2-2-1), если часто гасите manager на бэкап (гайд: на время stop manager'а кворум тоньше). Manager'ы `drain`, чтобы Raft не делил CPU с Kafka-подобной нагрузкой. Worker'ы — масштаб нагрузки.

Бэкап: остановить Docker на **одном** manager, скопировать `/var/lib/docker/swarm` (включая ключи шифрования Raft). Hot-backup вендор считает менее предсказуемым. Restore — на чистый `/var/lib/docker/swarm` + `swarm init --force-new-cluster`. Auto-lock: unlock-ключ обязателен для restore, хранить не рядом с бэкапом на том же диске.

Пока RTT между ЦОДами не измерен — **не обещать**, что 1-1-1 будет стабилен. Тот же класс риска, что stretch-etcd.

#### Производительность и масштабирование (C, нагрузка неизвестна)

Правила роста, не цифры «купите 16 ядер»:

- Сборка упирается в **CPU, диск слоёв, сеть до реестра**. Горизонталь = больше независимых builder'ов, не «один docker с 128 ядрами» как единственная стратегия (вертикаль тоже бывает нужна для огромного моно-образа).
- Не хранить данные озера в overlay2 writable layer.
- `json-file` без max-size на нагруженном хосте заполняет диск — это инцидент доступности.
- `userland-proxy` по умолчанию **true**: отдельный процесс на опубликованный порт. На хосте с кучей `-p` это шум; на Linux часто ставят `false`, полагаясь на iptables. Менять только поняв firewall (nft/iptables) этого хоста.
- iptables, которые пишет Docker, конфликтуют с «чужим» firewall на том же хосте. На Kubernetes-ноде этот конфликт — одна из причин **не** ставить Engine рядом с kubelet.
- Лимиты памяти на контейнеры сборки: без них `docker build` съест хост и соседние job'ы.
- Параллелизм CI ограничивать: 24.0 не сделает из одной машины бесконечный farm.

Для Swarm (если D): вендор прямо пишет, что **больше manager'ов = хуже write** состояния (больше round-trip Raft). Масштаб нагрузки — **worker'ы**, не «9 manager'ов». Routing mesh удобен и добавляет hop; для тяжёлого трафика смотрят publish mode `host` + внешний балансировщик (это уже HAProxy/сеть ЦОДа).

#### Безопасность (без этого «экземпляр» дырявый)

Минимум на каждом прод-хосте с 24.0.9:

1. **Патч-статус.** Честно зафиксировать: линия без vendor-fix. Компенсации (не замена патчей): минимум пакетов на хосте, нет входящего 2375/2376 из недоверенных сетей, запрет privileged, свой реестр, сканер образов. ИБ может всё равно запретить 24 — и будет права.
2. **API только локальный сокет.** Удалённо — SSH или mTLS :2376. Ключи 2376 = root. Группа `docker` — поимённо, не AD-группа «все разработчики».
3. **Не монтировать `/var/run/docker.sock`** в контейнеры приложений и в «удобный CI на Kubernetes». DinD — изолированная VM/pod с жёсткой политикой, не сокет хоста.
4. **Профили:** не отключать seccomp (`unconfined`), не отключать AppArmor/SELinux «чтобы завелось». `--privileged` — исключение с тикетом.
5. **`no-new-privileges`**, drop capabilities, read-only root, явный `USER`.
6. **userns-remap** — плюс к изоляции, минус к совместимости volume; на builder'ах часто не включают из-за кэша/права на артефакты. Решение сознательное, не дефолт «потом».
7. **Content Trust** — если ИБ требует подписи; это не сканер CVE.
8. **Логи аудита хоста** (кто ходил к сокету) — через ОС/SIEM (Wazuh у вас отдельным документом), не «Docker сам SIEM».
9. **Исходящий pull:** только реестр организации. Docker Hub с builder'а в контуре гособмена — канал утечки и подмены.
10. **BuildKit CVE 2024** на 24.0.9 **не закрыты** (цитата релиз-нотов 24.0.9). Сборочный контур на 24.0.9 уязвим известными дырами сборщика. Это не гипотеза.

ГОСТ TLS Engine не закрывает. Если требование есть — контур СКЗИ отдельно (как в других документах этой папки).

##### Сильные / слабые стороны схемы «сокет локально + лимиты + свой реестр + без privileged»

| Сильное | Слабое |
|---|---|
| Соответствует официальной модели «сокет = root, не светить TCP» | Не лечит unmaintained 24.0 и незакрытый BuildKit |
| Совместимо с выносом сборки от Kubernetes | Люди всё равно попросят сокет «на пять минут» |
| Не зависит от Swarm | userns-remap/rootless могут сломать привычные сборки |
| | DCT и сканер — отдельные системы, их надо реально включить |

#### Порядок вывода в прод (этапы, не команда за командой)

1. Решить письменно: 24.0.9 — исключение или уходим на поддерживаемый Engine. Если исключение — дата вывода и компенсационные контроли ИБ.
2. Зафиксировать роль **C** (не D/E), согласовать с документом Kubernetes (CRI = containerd).
3. Поднять реестр (staging/prod) и запрет прямого Hub с прод-сети.
4. Выкатить 2–3 builder'а в разных ЦОДах, одинаковый `daemon.json` из git, мониторинг диска/демона/очереди CI.
5. Убрать docker.sock из пайплайнов, которые могут работать без него.
6. Прогнать: убийство одного builder'а, заполнение диска (чтобы увидеть алерт до продакшн-инцидента), попытка pull с Hub (должна падать).
7. Не включать Swarm «про запас».

Без пункта 1 у вас нет безопасности. Без пункта 6 у вас нет отказоустойчивости сборки, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется от одного `dockerd` | Для **приложений** — Kubernetes, не Docker. Для **сборки** — ≥2 независимых builder'а в разных ЦОДах + HA реестра. Swarm 1-1-1 — только если Kubernetes снят с роли оркестратора |
| Производительность / масштаб | Не требуется | Горизонталь builder'ов; лимиты; диск под слои; не класть терабайты в overlay2; не путать scale Swarm manager'ов с scale worker'ов |
| Безопасность | Изолированная сеть, Unix-сокет, без privileged | **Линия 24.0.9 сама по себе не обеспечивает** vendor-security. Плюс: нет 2375, свой реестр, сокет не в приложениях, профили ядра включены, BuildKit-CVE осознаны |

**Не готов к проду**, если: Engine 24.0.9 стоит на worker'ах Kubernetes «потому что привыкли к docker», открыт 2375, `docker` группа у всего отдела, сокет в CI-подах, Swarm и Kubernetes на одних нодах, `latest` с Docker Hub в интеграционном контуре, live-restore вместе со Swarm, NFS как `/var/lib/docker`, нет ротации логов, RTT неизвестен, а stretch-Swarm уже в презентации руководству.

**Честный вывод ментора:** требование «безопасность» для платформенного ПО в 2026 году с линией **24.0** не выполняется вендорской поддержкой. Имеет смысл трактовать этот файл как «как удержать 24.0.9 в узкой роли CI, пока не уйдёте», а runtime прода оставить containerd под Kubernetes.
