# Camunda 8.9 — развёртывание и настройка

Версия ПО: **Camunda 8.9** (на дату подготовки документа — текущая линейка **Standard support** до **13 октября 2027**).  
Целевой патч для Kubernetes: Helm-чарт **`camunda-platform` 14.8.5** → образ Orchestration Cluster `camunda/camunda:8.9.17` (матрица https://helm.camunda.io/camunda-platform/version-matrix/camunda-8.9/). Соседние образы той же строки чарта: Connectors `8.9.8`, Optimize `8.9.17`, Management Identity `8.9.8`, Web Modeler `8.9.7`, Console `8.9.88`.  
Документация линейки: https://docs.camunda.io/ (Supported environments: https://docs.camunda.io/docs/reference/supported-environments/)  
Репозиторий чарта: `https://helm.camunda.io`, чарт `camunda/camunda-platform`.

**8.10** на дату документа — **Alpha** (Camunda Hub, chart 15.x, нужен Helm CLI **v4**). В прод этого файла **не** берём. Линейка **8.8** ещё в standard support до 13 апреля 2027; апгрейд на 8.9 — только с 8.8.x, не «через одну minor».

Этот текст — не мануал «скопируй Helm values и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Camunda 8 **было** в исходной архитектуре («процессы на процессном движке типа Camunda»). Ниже — как поставить **Self-Managed** движок на ту же инфраструктуру: Kubernetes, 3 ЦОДа, Kafka как шина, озеро как источник истины, интеграционное API как единственный выход во внешний мир. Это **не** замена Kafka, **не** озеро клиентских данных и **не** интеграционная шина к 30+ госслужбам.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **BPMN** | Язык схем процессов (прямоугольники «задачи», ромбы «решения»). Схему рисуют в Modeler, исполняет движок. |
| **DMN** | Таблицы решений («если доход > X — риск средний»). Исполняются рядом с BPMN. |
| **Процесс (process definition)** | Задеплоенная схема. Версий может быть много. |
| **Экземпляр процесса (process instance)** | Один конкретный прогон схемы: «заявка №123». |
| **Orchestration Cluster** | С 8.8 это **один** артефакт: движок + Operate + Tasklist + встроенный Admin. Не три отдельных «продукта, которые сами склеятся». |
| **Zeebe** | Движок исполнения. Хранит *состояние живых процессов*, а не клиентское досье. |
| **Брокер (broker)** | Процесс Zeebe. Все брокеры равноправны: нет «главного сервера навсегда». |
| **Партиция (partition)** | Кусок данных движка (как шард). Параллелизм исполнения ≈ число партиций. |
| **Replication factor (RF)** | Сколько копий у каждой партиции. RF=3 → 1 лидер + 2 последователя. |
| **Лидер / follower** | Лидер партиции обрабатывает команды. Followers копируют журнал. Упал лидер — выбирают нового. |
| **Raft** | Протокол, которым брокеры договариваются, какая копия «правда». Запись **коммитится**, только когда большинство копий подтвердило. |
| **Кворум** | Большинство. Для RF=3 кворум = 2. Живых копий меньше — партиция **не принимает** новые команды. |
| **Gateway** | Вход для клиентов: gRPC **26500** и REST **8080**. Клиенты **не** ходят на брокеры напрямую как на «балансировщик Kafka». С 8.8 в Helm gateway по умолчанию **встроен** в брокер; его всё равно масштабируют репликами входа. |
| **Job / job worker** | Сервисная задача в BPMN становится «работой». Её забирает **отдельная программа** (ваш микросервис), делает дело, говорит движку `complete` или `fail`. Движок **не** вызывает ваш Java-метод внутри своей JVM. |
| **Job type** | Имя работы (`fetch-client-from-lake`). Воркеры подписываются на тип. |
| **Operate** | UI «что сейчас с процессами, где застряло». Читает **вторичное** хранилище, не диск брокера. |
| **Tasklist** | UI пользовательских задач (человек нажал «одобрить»). |
| **Admin** | Встроенная идентификация Orchestration Cluster (пользователи, права на процессы/задачи/API). |
| **Management Identity** | *Другая* идентификация: Web Modeler, Console, Optimize. Не путать с Admin. |
| **Optimize** | Аналитика по процессам. **Опциональна.** Дорого по диску/CPU вторичного хранилища. |
| **Connectors** | Готовые кубики «дерни HTTP / Kafka / …» в схеме. Runtime — отдельный деплой. Не замена вашего интеграционного API. |
| **Exporter** | Плагин брокера: копирует события движка во **вторичное** хранилище (OpenSearch / Elasticsearch / RDBMS). Без него Operate пустой, хотя процессы уже идут. |
| **Camunda Exporter** | Актуальный экспортёр 8.8+ для Operate/Tasklist/Admin. Если он не может писать — срабатывает **backpressure**: движок сам притормаживает пользовательские команды. |
| **Первичное хранилище** | Диск брокера: журнал партиций (log) + снимок состояния (snapshot). Это «память живого процесса». |
| **Вторичное хранилище (secondary storage)** | OpenSearch **или** Elasticsearch **или** RDBMS — поиск, Operate, Tasklist, API запросов истории. С 8.9 в Helm тип **обязательно** задать явно (`orchestration.data.secondaryStorage.type`). |
| **H2** | Встроенная файловая/in-memory СУБД. В Camunda 8 Run — дефолт для ноутбука. **Не** для мультиброкерного прода. |
| **Desktop Modeler / Web Modeler** | Рисовалки BPMN. Desktop — программа на ПК. Web — сервер + PostgreSQL. Процессы исполняются и без Web Modeler. |
| **Console / Camunda Hub** | Панель управления несколькими кластерами. Hub — тема 8.10 Alpha, не этот документ. |
| **C8 Run** | Локальная сборка «движок + коннекторы + H2». Только разработка. |
| **Docker Compose Camunda** | Официально: quick start / dev / test. Не прод. |
| **clusterSize / partitionCount / replicationFactor** | Тройка, которая должна быть **одинаковой** на всех брокерах. `replicationFactor` не может быть больше числа брокеров. |
| **Stretch** | Один логический кластер Zeebe, брокеры физически в разных ЦОДах. Raft ходит по **26501/26502**. |
| **Dual-region** | Официальный сценарий Camunda: **ровно две** площадки, RF=**4**, минимум **8** брокеров (по 4). Failover **ручной**. OpenSearch и RDBMS как secondary в этом сценарии **не поддерживаются**. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. |
| **Backpressure / flow control** | Движок отказывает или тормозит новые команды, когда не успевает реплицировать или экспортировать. Это защита, не «баг медленности». |
| **CAMUNDA_LICENSE_KEY** | Лицензионный ключ Self-Managed. Без него компоненты пишут Non-Production и в проде вы **не** в рамках лицензии 8.6+. |
| **OIDC** | «Войти через корпоративный IdP» (Keycloak, Entra, Okta…). Для людей в проде — это, а не общая учётка `demo`. |
| **mTLS** | Оба конца TLS показывают сертификат. Для брокеров/клиентов — отдельная настройка; Helm values-tls **не** закрывает весь pod-to-pod gRPC сам по себе (в комментарии чарта прямо: нужен service mesh или своя схема). |

## Основные элементы системы и зависимости

### Что входит в Camunda 8.9 Self-Managed (это платформа из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Zeebe brokers** | Исполнение BPMN/DMN, журнал, Raft | Горизонтально: брокеры + партиции. RF и зоны — для HA, не «ещё QPS» |
| **Gateway** (часто embedded) | Вход gRPC/REST | Реплики входа; партиции на брокерах должны быть готовы заранее |
| **Operate / Tasklist / Admin** | Наблюдение, человеческие задачи, RBAC кластера | Читают secondary storage; HA UI ≠ HA движка |
| **Exporter → OpenSearch/ES/RDBMS** | Чтобы UI и поисковые API видели процессы | Скорость экспорта ограничивает *видимость* и при застое — сам движок |
| **Connectors runtime** | Исполнение коннекторных задач из схемы | Несколько реплик; идемпотентность на вас |
| **Optimize** | Отчёты по процессам | Отдельный импортёр; официально сильно нагружает ES/OS |
| **Management Identity + Keycloak** | Вход в Modeler/Console/Optimize | Свой PostgreSQL; не кворум Zeebe |
| **Web Modeler** | Совместная рисовалка | PostgreSQL; падение ≠ остановка уже задеплоенных процессов |
| **Клиенты / job workers** | Ваши микросервисы | Масштабируются **отдельно** от брокеров. Лишние воркеры одного типа делят работы |

Плюс *рядом*, но это уже другое ПО (у вас часть описана отдельно): **OpenSearch 3.8.0**, PostgreSQL (CloudNativePG — путь, который Camunda рекомендует вместо Bitnami-subchart в проде), объектное хранилище для **бэкапов Zeebe**, Ingress/балансировщик, IdP.

### Официальные порты Orchestration Cluster (менять можно, контракт сети лучше не плодить)

| Порт | Назначение | Кому открывать |
|---|---|---|
| **8080/TCP** | REST API gateway (клиенты, часть UI/API) | Воркеры, приложения, Ingress. Не в интернет без TLS и Auth |
| **26500/TCP** | gRPC клиентов и job workers | То же. Балансировщик gRPC должен понимать **долгие** стримы воркеров |
| **26501/TCP** | Command API: gateway → брокер (внутренний протокол SBE) | Только внутри кластера Zeebe |
| **26502/TCP** | Internal API: Gossip + Raft между брокерами и gateway | Только брокеры и gateway. Это «9300 OpenSearch / inter-broker Kafka» |
| **9600/TCP** | Actuator: `/metrics`, `/ready`, backup API | Prometheus, операторы бэкапа. Не в интернет |

В YAML брокера порты такие. В одном фрагменте страницы Network ports значения *environment variables* для 26502/9600 скопированы ошибочно на 26501 — ориентир **поля YAML**, не эта опечатка.

UDP для Raft/Gossip как отдельный контракт вендор не описывает: это TCP-порты выше.

Клиентов направляют на **Gateway** (Service/Ingress 8080 и 26500). На 26501/26502 внешний мир не пускают.

### Чего в Camunda 8 нет (частая путаница, особенно если знаете Camunda 7)

| Нужно системе | Это не Camunda 8 | Зачем помнить |
|---|---|---|
| Встроенный движок в Spring Boot (одна JVM, общий Hibernate) | Camunda **7** | В 8 движок **всегда удалённый**. `@JobWorker` — клиент, не «listener внутри BPM». |
| Шина событий, гарантии `acks=all`, consumer group | Apache Kafka | Zeebe — оркестратор. Событие «клиент изменился» живёт в Kafka; процесс *может* на него среагировать через воркер/коннектор. |
| Озеро / SoT клиентских данных | Ваше озеро / БД | В переменных процесса вендор **не** рекомендует большие данные. Потолок порядка **~3 МБ** на экземпляр; бенчмарки считают килобайты. |
| Интеграции с 30+ госслужбами | Ваше интеграционное API | Camunda говорит «нужны данные клиента»; API само ходит наружу. Коннектор Camunda «напрямую в ведомство» плодит второй контур интеграций. |
| Поиск по ФИО/ИНН по всем клиентам | OpenSearch *бизнес-кластера* | Operate ищет **процессы**, не население РФ. |
| Прозрачный failover «умер ЦОД — сами переключились» как у DNS | Dual-region Camunda | Официально failover **ручной**; при потере региона Raft **сразу останавливает** обработку до процедуры. |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS JDK. |
| Официальный порог RTT для *трёх* ЦОДов | Нет | Для dual-region есть ориентир **≤ 100 мс** RTT (не жёсткий лимит движка). Для stretch на 3 Зоны отдельной цифры нет. |
| Гарантия «терабайты влезут в Zeebe» | Нет | Терабайты — озеру и Kafka. В движке — идентификаторы и короткие переменные. |
| Бесплатный прод Self-Managed с 8.6 | Нет | Dev/test — да; **production требует лицензию** (единая модель на Zeebe, Operate, Tasklist, Optimize, Identity, Connectors, Console, Web Modeler). |
| Triple-region (3 площадки как first-class HA) | Нет в доке | Есть: 3 AZ **одного** региона (RF=3) и dual-region (2 площадки, RF=4). Третьего региона как кворумной схемы нет. |

### Зависимости окружения (обязательны)

- **Java на Orchestration Cluster / Optimize / Connectors: OpenJDK 21–25.** Management Identity: 17+. Клиент Zeebe Java: 8+ (это воркеры, не брокеры).
- **Kubernetes:** вендор рекомендует Helm на certified Kubernetes. Чарт 14.x (8.9) работает с Helm CLI **v3** (в матрице 14.8.x указан Helm **3.20.x**). Helm v4 — требование **8.10**, не 8.9.
- **Диск брокера.** Официально: **≥ 1000 IOPS**, latency записи/msync в **низких единицах миллисекунд**, p99 **< 300 мс**, **SSD**. HDD не поддерживается. NFS — только если POSIX, не переставляет операции, не отдаёт один том **на запись двум** контейнерам (иначе порча данных). Amazon EFS вендор гарантирует; «любой NFS с шары на троих брокеров ReadWriteMany» — путь к порче, не к HA.
- **PVC / RWO** на каждого брокера. `emptyDir` = потеря журнала при рестарте пода.
- **Вторичное хранилище 8.9:** Elasticsearch **8.19+** или **9.4+**, **или** OpenSearch **2.19+** или **3.6+**, **или** поддержанный RDBMS. У вас уже есть документ на **OpenSearch 3.8.0** — для 8.9 это **попадает** в ветку 3.6+. Кластер **один** на все компоненты Orchestration Cluster (не «Operate на одном OS, Tasklist на другом» — это сломали ещё в 8.8).
- **PostgreSQL** — для Management Identity (и части фич) и Web Modeler, если они нужны. В проде — внешний кластер / CloudNativePG, не Bitnami-subchart «чтобы чарт поднялся».
- **IdP (OIDC)** для прода. Дефолт чарта: `global.security.authentication.method: basic`.
- **Бэкап:** (1) snapshot repository на OpenSearch/ES, (2) отдельное объектное хранилище для **partition backup Zeebe**. Снимок диска брокера «как VM» **не** считается согласованным бэкапом кластера.
- **Сеть:** стабильный DNS/IP брокеров на 26501/26502; клиентам — до gateway. Балансировщик «как HTTP round-robin на 26502 всех брокеров» ломает Raft так же, как VIP на Kafka inter-broker.

### Как Camunda стыкуется с вашей архитектурой

```
Люди / API «запусти процесс»
        │  REST 8080 / gRPC 26500
        ▼
   Gateway  ──26501/26502──►  Zeebe brokers (3+ в разных ЦОДах)
        │                              │
        │                         диск партиций (SoT *состояния процесса*)
        │                              │
        │                         Exporter
        ▼                              ▼
   Job workers (микросервисы)     OpenSearch Camunda (Operate/Tasklist)
        │                         ≠ ваш поисковый OpenSearch
        ├─► Kafka          (события домена)
        ├─► озеро эталона  (клиент как SoT)
        └─► интеграционное API  (госслужбы; ждут лаги; отдают нормализованное)

Optimize (опционально) ──читает экспорт──► тот же или отдельный OS/ES
Web Modeler / Identity ──PostgreSQL──► не на пути исполнения
```

Честные роли в *вашей* картине:

1. **Оркестрация длинных сценариев** — «запросили выписку → ждём дни → пришёл ответ → развилка → человек». Это то, зачем процессный движок, а не Kafka consumer в одиночку.
2. **Компенсации и видимость** — Operate видит, на каком шаге заявка; воркер знает только свою работу.
3. **Человеческие задачи** — Tasklist / ваш UI поверх API задач.

Нечестные роли:

- «Положим XML клиента в переменную процесса — будет озеро». Переменные раздувают диск Zeebe, экспорт, Optimize и упираются в лимит размера.
- «Camunda вместо Kafka». Движок не шина.
- «Коннекторы Camunda ходят в 30 ведомств». У вас уже проектируется API, которое **само** выбирает интеграции. Воркеру процесса достаточно вызвать **это** API и положить в процесс *нормализованный* идентификатор/статус, не сырой SOAP.

## Краткие вводные

### Зачем вам Camunda 8, а не «просто Kafka + код»

Kafka доставляет факт. Озеро хранит истину. Интеграционное API ходит наружу с лагами в дни. Остаётся вопрос: **кто помнит, что заявка ждёт третью госсистему, и что делать, когда она пришла, а вторая уже протухла**.

Camunda 8 — удалённый оркестратор с репликацией Raft. Микросервисы остаются глупыми воркерами: взял job, сходил в озеро/API/Kafka, вернул маленький результат.

Если команда думает «Camunda 7 в Spring Boot» — это **другой продукт**. Здесь нет `camunda:class` в той же JVM. Схема и воркеры живут раздельно; упал воркер — работы копятся в движке (официальная модель), упал кворум брокеров — **не стартуют** новые шаги ни у кого.

### Как устроена отказоустойчивость (идея, не магия)

Это **кворум Raft на каждую партицию** плюс **живой экспорт** во вторичное хранилище плюс **согласованный бэкап**. Путать «docker compose с одной нодой» с HA — главная ошибка.

**1) Брокеры и RF**

Официальные примеры кворума:

| RF | Кворум записи | Сценарий из доки |
|---|---|---|
| **3** | лидер + ещё **1** follower | Один регион, **3 зоны**. Один брокер (одна зона) может умереть без потери закоммиченных данных |
| **5** | лидер + **2** follower | Терпите потерю **двух** брокеров; дороже диском и сетью |
| **4** | исключение | Только **dual-region**: копии всегда на обеих площадках; потеря **целого** региона → кворума нет, обработка **встаёт**, оператор делает failover. Данные при правильной схеме не теряются (RPO 0) |

Нечётное RF — норма для одного «региона из трёх ЦОДов». Чётное RF «на троих ЦОДах как в Kafka RF=3» **не** является описанным паттерном Camunda.

**2) Что падает — что происходит**

| Что падает | Что происходит |
|---|---|
| Один брокер из 3 при RF=3, копии в разных ЦОДах | Выборы лидера на затронутых партициях. Закоммиченное живо. Незакоммиченное — по правилам Raft |
| Два брокера из 3 (два ЦОДа) | Кворума нет. Партиции не коммитят. Процессы **стоят** |
| Все брокеры в одном ЦОДе | Падение площадки = падение движка. «Три пода в одном node pool» — не 3 ЦОДа |
| Gateway / Ingress | Движок может быть жив, воркеры не достучатся. Несколько реплик gateway |
| OpenSearch Camunda (exporter не пишет) | Сначала Operate отстаёт (секунды–минуты — нормальная «data availability latency»). Потом **backpressure** душит команды по всему кластеру. HA Zeebe без HA secondary — дырявая |
| Job workers | Движок копит jobs. Процессы не идут вперёд. Это **не** падение Raft, но для бизнеса = простой |
| Нет бэкапа Zeebe+OS с одним backup ID | Реплики не спасают от «удалили PVC / кривой rolling / шифровальщик» |

**3) Dual-region — не «три ЦОДа сами»**

Официально сертифицированная схема на **две** Kubernetes-площадки. При гибели региона обработка **останавливается немедленно**, пока не выполнят runbook (failover RTO в тестах вендора: **< 1 минуты** *без* DNS; полный failback — минуты плюс restore Elasticsearch). RPO для Zeebe/Operate/Tasklist в этой схеме: **0**. Failover **не автоматический**.

OpenSearch как secondary в dual-region: **не поддерживается**. Только Elasticsearch, свои кластеры в каждом регионе, экспортёр пишет в оба (это не CCR OpenSearch).

**4) UI**

Падение Operate ≠ падение Zeebe. Падение Tasklist ≠ «процессы умерли», но люди не закроют задачи.

### Как устроено масштабирование

Несколько независимых осей:

1. **Больше параллельных экземпляров / сервисных задач** → больше **партиций** и брокеров. Партиции планируют **до** нагрузки; это не «шарды OpenSearch, которые можно добавить дешёвым template». Есть процедура cluster scaling — это операция, не слайдер в UI.
2. **Больше входа (воркеры, старты процессов)** → больше gateway/реплик входа, **если** партиции уже тянут.
3. **Тяжёлые переменные** → диск Zeebe, объём экспорта, латентность. Официальный ориентир: партиция «типично» тянет порядка **1 ГБ суммарного payload**; 11 КБ vs 0.5 КБ в бенчмарках меняет диск **в 10–20 раз**. Это эвристика вендора, не ваша смета.
4. **Operate/поиск** → мощность **отдельного** OpenSearch, не «добавим брокер Zeebe».
5. **Optimize** → по нагрузкам 8.8/8.9 вендор: примерно **×3.4 CPU** и **×3.6 диск** Elasticsearch на реалистичном ворклоаде; на максимуме吞吐 движка падает на **25–50%**. Включать «на всякий случай» — купить второй поисковый кластер зря.
6. **Воркеры** считаются отдельно. Здоровый throughput кластера **не** значит, что backlog jobs тает. Встроенной метрики размера backlog вендор прямо пишет, что **нет**.

Нагрузки у вас нет — поэтому **нет** цифры «N брокеров и M партиций». Есть сигнады: backpressure, latency commit, лаг экспорта, лаг Optimize, диск брокера, IOPS.

Правило большого пальца из sizing-гайда: закладывать порядка **20×** средней нагрузки, если важны пики и латентность. Это **не** замена замера.

### Безопасность самого Camunda 8

Компрометация Orchestration Cluster = кто угодно стартует процессы, читает переменные (часто ПДн и статусы госинтеракций), закрывает чужие задачи, дергает воркеры. Учётка `demo:demo` (дефолт Basic в линейке 8.8+) равносильна ключу от операционки процессов.

Официально / из чарта:

- С 8.6 **прод Self-Managed без лицензии нельзя**. Ключ: `CAMUNDA_LICENSE_KEY` / `global.license.secret`. Без ключа UI может работать с плашкой Non-Production — это не «значит можно в банк».
- Дефолт аутентификации Helm 8.9: **basic**. Для прода — **OIDC**, свой IdP; Admin кластера и Management Identity — **разные** контуры, в проде оба смотрят на корпоративный IdP.
- Compose / C8 Run / basic `demo` — стенд. В интернет 8080/26500 так не выкладывают.
- Helm `values-tls.yaml` закрывает TLS **к** OpenSearch/ES/PostgreSQL/OIDC. **Не** закрывает весь gRPC между подами: для этого вендор отсылает на service mesh.
- Секреты коннекторов и клиентские секреты OIDC — в Secret/Vault, не в Git и не в BPMN.
- At-rest журнала Zeebe — шифрование тома/CSI. Встроенного «encrypt partition» как замены диску нет.

«Поднять C8 Run и выдать 8080 разработчикам в VPN» — нормальный стенд. «Тот же YAML в прод» — инцидент.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём Camunda 8.9 Self-Managed**, не SaaS Camunda Cloud и не Camunda 7. SaaS и C7 живут по другим манифестам, лицензиям и модели отказов.
2. **Прод крутится в Kubernetes**, инсталлятор — официальный Helm `camunda-platform` **14.8.5** (пинить версию чарта и appVersion, не `latest`). Bitnami Elasticsearch/PostgreSQL из чарта — только оценка; в проде **выключены**.
3. **Вторичное хранилище прода — отдельный кластер OpenSearch 3.8.0** (ваш уже описанный контур), тип Helm: `opensearch`. Не тот кластер, что бизнес-поиск, и не Wazuh indexer. Dual-region с OpenSearch **нельзя** — если выберете dual-region, secondary станет **Elasticsearch**, это смена допущения.
4. **Три ЦОДа = три зоны отказа одного «региона»** для базовой схемы RF=3. Если это три зала с общим питанием/ядром — stretch даёт ложное чувство безопасности.
5. **Цель отказа базовой схемы: пережить 1 ЦОД из 3**, не 2 из 3. Два мёртвых ЦОДа при 3 брокерах снимают кворум.
6. **Dual-region (2 из 3 ЦОДов) не выбран по умолчанию:** он требует Elasticsearch, ручной runbook, остановку обработки на время failover и сеть 26500–26502 между **двумя** Kubernetes. Третий ЦОД в этой схеме не даёт «кворум 2 из 3» для Zeebe.
7. **Нагрузки нет** — нет сметы ядер. Есть рычаги (партиции, брокеры, воркеры, что класть в variables, Optimize вкл/выкл).
8. **Формального SLA / RPO / RTO нет.** Dual-region даёт *опубликованные* RPO 0 / RTO failover < 1 мин без DNS — это цифры **их** тестов и **их** процедуры, не ваш замер.
9. **Лицензия Enterprise Self-Managed для прода будет.** Без этого юридически схемы прода нет, сколько бы брокеров ни поставили.
10. **Корпоративный OIDC будет.** Basic/demo — для теста.
11. **Интеграции с госслужбами идут только через ваше интеграционное API.** Воркеры Camunda — клиенты этого API. Camunda Connectors в ведомства не плодим без отдельного решения архитектуры.
12. **В переменных процесса — идентификаторы и статусы, не досье.** Терабайты остаются в озере; Kafka несёт события изменений.
13. **Шифрование канала — TLS JDK / mesh.** ГОСТ не озвучен.
14. **Тестовый стенд изолирован.** C8 Run, Compose, H2, RF=1 на нём допустимы. В прод их не копируем.
15. **Optimize в первом проде выключен**, пока нет заказчика на отчёты и отдельного бюджета OpenSearch (×3–4).
16. **Web Modeler не на критическом пути исполнения.** Рисовать можно Desktop Modeler; деплой — через CI ( zbctl / API ), не «кнопка из браузера в прод».

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили Helm и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потери на 26501/26502 между ЦОДами** (p50/p95/p99, все пары) | Каждый commit ждёт кворум. Высокий или плавающий RTT → медленные процессы, ложные fail брокера, постоянный backpressure. Stretch станет источником аварий. Dual-region: ориентир вендора **≤ 100 мс**, не гарантия вашей сети. |
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Stretch Raft требует pod-to-pod маршрутизации 26501/26502. Иначе это не один кластер. Dual-region требует **два** K8s с DNS/peering и открытыми 9200/26500/26501/26502. |
| **Лицензия на прод** | С 8.6 без ключа прод Self-Managed нелегален. Закупка — не «потом, когда заработает Operate». |
| **Профиль процессов** (сколько экземпляров/день, сколько сервисных задач, пик за 2 часа, размер variables) | Без этого партиции и диск — гадание. Вендор просит бенчмарк **вашей** модели, не чужой слайд. |
| **Что в variables** (ПДн? PDF? ответ ведомства целиком?) | 152-ФЗ, размер партиции, экспорт в OpenSearch, утечка через Operate. |
| **Отдельный OpenSearch для Camunda vs общий с поиском** | Экспортёр и Optimize бьют I/O. Общий кластер = Operate убил поиск по клиентам (или наоборот). Плюс RBAC и ILM разные. |
| **Нужен ли dual-region** (RPO 0 ценой ручного failover и Elasticsearch) vs stretch 3 AZ vs «мозг в одном ЦОДе + cold restore» | Пока RTT и модель отказа не зафиксированы, выбор — лотерея. **Трёхрегиональной** схемы у вендора нет. |
| **Кто воркеры и какой у них HA** | Кластер Zeebe green, а интеграционное API лежит → процессы стоят на jobs. Это надо мониторить как часть Camunda, не «как другое ПО». |
| **Где бэкап Zeebe и snapshot OS** | Если бакет только в одном ЦОДе — падение этой площадки убивает единственную согласованную точку восстановления. Диск брокера ≠ бэкап. |
| **IdP, кто видит чужие заявки** | Basic `demo` в проде. Fine-grained authorizations 8.8+ надо спроектировать, иначе любой оператор видит все процессы. |
| **gRPC-балансировщик и streaming workers** | Обычный HTTP L7 на 26500 рвёт стримы. Нужен L4 или gRPC-aware Ingress. |
| **IOPS диска брокера** | Медленный PVC = commit latency = «движок тупит» при живом кворуме. Вендор: SSD, ≥1000 IOPS. |
| **Совместимость чарта 14.8.5 с вашей версией Kubernetes** | «Certified K8s» не заменяет проверку CSI, topology.spread, PDB. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **8.9.x** и **тот же** патч у Connectors/Optimize/Identity, если они есть. Источник истины версий — матрица Helm, не ручные теги «поновее».
2. Выбрать **secondary storage** (`opensearch` / `elasticsearch` / `rdbms`) **до** первого `helm install`. С 8.9 без `orchestration.data.secondaryStorage.type` чарт **не ставится**. Смена семейства потом — **не** in-place миграция.
3. Поднять брокеры: одинаковые `clusterSize`, `partitionCount`, `replicationFactor`; `initialContactPoints` со **всеми** брокерами (иначе хуже переживается split сети).
4. Выпустить **лицензию** (прод), **OIDC**, TLS до OpenSearch и Ingress **до** боевых процессов.
5. Настроить **backup**: repository на OpenSearch **и** store для Zeebe; прогнать backup API с **одним** backup ID и **restore** на другой namespace. Снимок VM брокера не считается.
6. Включить метрики `:9600/metrics` (backpressure, disk, exporter, gateway latency) и лаг индексов Camunda в OpenSearch.
7. Задеплоить **пустой** процесс с одной сервисной задачей, живой воркер, убедиться что экземпляр **доходит до конца** и виден в Operate.
8. Прогнать «убили один брокер» / «убили воркер» / «остановили OpenSearch на 2 минуты» — понять разные классы отказа.
9. Только потом — Optimize, Connectors bundle, Web Modeler, тонкий RBAC, dual-region.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики рисовали BPMN, деплоили, писали `@JobWorker`, смотрели Operate. **Не** цель: доказать отказ ЦОДа, Raft на 26502 между площадками и ёмкость.

Три официальных минимальных пути (выберите один, не смешивайте привычки):

**Путь A — Camunda 8 Run** (быстрее понять продукт): локальная сборка Orchestration Cluster + Connectors, secondary по умолчанию **H2**. Вендор прямо: **не для production**.

**Путь B — Docker Compose** из developer quickstart: то же ограничение — quick start / test. Образы Linux amd64/arm64; Windows/macOS как host — только dev.

**Путь C — Helm в dev-кластере** с `values-local.yaml` (kind/minikube): ближе к проду, но ресурсы урезаны. Всё ещё не копия прода.

На Kubernetes теста: `clusterSize: 1`, `replicationFactor: 1`, `partitionCount: 1`, маленький PVC, OpenSearch может быть single-node **отдельный** namespace (или H2 только если сознательно не тестируете экспорт). Не копировать этот values в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число брокеров / RF | 1 / 1 | Нет требования пережить выкат |
| Партиции | 1 | Иначе команда отлаживает Raft вместо BPMN |
| Secondary | H2 (C8 Run) или маленький OS | H2 не учит ILM и бэкап OS — на препроде OS обязателен |
| PKI / Auth | basic, локальные пользователи | Иначе утонете в IdP раньше, чем в job worker |
| Лицензия | Non-Production | Стенд не прод; привычка «без ключа» не должна уехать на бой |
| CPU/диск | как в values-local / C8 Run | Не цель — ёмкость |
| Optimize / Web Modeler | выкл | Не нужны, чтобы понять воркер |
| Connectors | по желанию | Ваш контур всё равно через своё API |
| Бэкап Zeebe | можно отложить на день | Нельзя забыть на препроде |

#### Чего на тесте **не** стоит упрощать

- Версия **8.9.x** на движке и **совместимый** клиент воркера (Spring Boot Starter под 8.9).
- Воркеры **снаружи** движка, маленький payload (id клиента, не JSON досье). Иначе в проде «переиграть» раздует партиции.
- Понимание: процесс **не** транзакция с PostgreSQL озера. Сходили в озеро — записали id/версию в variable.
- Запомнить: C8 Run с H2 **не** есть «почти прод».
- Не выключать авторизацию «навсегда»: в 8.8+ API по умолчанию закрываются; привычка открытого 8080 уедет в бой.

#### Сильные стороны такой схемы

- Поднимается за часы, совпадает с официальным C8 Run / Compose.
- Дешево показывает, что команда умеет job workers, а не `JavaDelegate` Camunda 7.
- Официально предназначена для development/testing.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет Raft между площадками, нет доказанной ёмкости экспорта в ваш OpenSearch 3.8.0.
- Успешный прогон на H2 **не** доказывает, что Camunda Exporter переживёт ILM и что backpressure при падении OS ведёт себя приемлемо.
- Basic `demo` приучает «зайти без IdP».

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (3 брокера, RF=3, свой OpenSearch, OIDC хотя бы stage, backup API), даже без боевого трафика.

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты озера» **нет** — нагрузки нет, и терабайты **не должны** жить в Zeebe. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Zeebe плохо переживает **три независимых правды** (три движка без общего Raft) и плохо переживает **слепой stretch** по 26502.

**Вариант A — один Kubernetes на 3 ЦОДа (зоны), один Orchestration Cluster (целевой для «3 ЦОДа в одном городе», пока RTT мал).**

- `clusterSize: 3` (или 6, **кратно зонам**), `replicationFactor: 3`, `partitionCount` — кратно 3, число от модели нагрузки (старт часто 3, не 1).
- По брокеру (или по паре) в зону; topologySpread / anti-affinity. Не сложить двух из трёх в один ЦОД.
- Клиенты: Ingress TLS на **8080**, gRPC-aware на **26500**, несколько реплик gateway.
- Secondary: **ваш OpenSearch 3.8.0** как отдельный кластер (см. `OpenSearch.md`): 3 manager в 3 зонах, replica ≥ 1, awareness. Exporter ходит на **9200** этого кластера, не на бизнес-поиск.
- Цель: пережить **1 ЦОД**. Два ЦОДа — кворум снят, процессы стоят.

**Вариант B — официальный dual-region на 2 из 3 ЦОДов.**

- Два Kubernetes, сеть между ними: 9200, 26500, 26501, 26502.
- `clusterSize` кратно 2, минимум **8**; `replicationFactor: **4**`; чётные/нечётные broker id в разных регионах (так раскладывает Helm).
- Secondary **только Elasticsearch** (по два кластера, экспортёр пишет в оба). **OpenSearch 3.8.0 сюда не подставить** — ограничение вендора, не «пока не проверили».
- Потеря региона: обработка **стоп** → ручной failover. RPO 0 при v2 API. Optimize, Management Identity в этой схеме ограничены/не поддержаны как в single-region.
- Третий ЦОД: холодный standby, бэкапы, не член Raft.

**Вариант C — мозг в одном ЦОДе + Cold Recovery.**

- Кластер RF=3 внутри одной площадки (локальные зоны зала). Падение ЦОДа = простой до restore.
- Спасает только **прогнанный** backup/restore Zeebe+OpenSearch. RTO надо замерить себе; вендор описывает Cold Recovery отдельно от dual-region.

**Пока топология K8s и RTT не зафиксированы, нельзя честно выбрать A.** Дальше — общее для A как наиболее прямого чтения «3 ЦОДа, один город, OpenSearch уже выбран»; B — если юридически нужен RPO 0 на гибель площадки **и** вы готовы сменить secondary на Elasticsearch; C — если сеть между ЦОДами для Raft неприемлема.

##### Сильные / слабые стороны (A, stretch 3 AZ)

| Сильное | Слабое |
|---|---|
| Совпадает с таблицей вендора «RF=3, 3 зоны» | Латентность 26502 = латентность **каждого** commit |
| Один bootstrap, один Operate, ваш OpenSearch 3.8.0 | Падение двух ЦОДов снимает кворум |
| Нет ручного failover при потере **одной** зоны | Нет официального порога RTT для трёх площадок |
| Проще dual-region операционно | Ошибка модели процесса сразу везде |
| | Не путать с dual-region: здесь нет RPO 0 «на гибель региона при RF=4» |

##### Сильные / слабые стороны (B, dual-region)

| Сильное | Слабое |
|---|---|
| Единственная сертифицированная схема «две площадки, RPO 0» | OpenSearch **нельзя**; ломает уже выбранный стек OS 3.8 |
| Опубликованы RTO/RPO и runbook | При падении региона процессы **встают**, пока оператор не отработает процедуру |
| | Минимум 8 брокеров, два ES, сложная сеть/DNS |
| | Failover ручной; ошиблись в процедуре — неконсистентность |
| | Optimize / часть Identity — ограничения |

##### Сильные / слабые стороны (C, один ЦОД + бэкап)

| Сильное | Слабое |
|---|---|
| 26502 не ходит между городами | Падение ЦОДа движка = нет оркестрации на всех трёх |
| Проще кворум и диск | RPO/RTO = как часто бэкап и как быстро restore; это надо мерить |
| OpenSearch остаётся 3.8.0 | Клиенты с других ЦОДов всё равно ходят на gateway через город |

##### Слабое место любого stretch без замера RTT

Документация **не задаёт** порог задержки для трёх ЦОДов. Утверждение «один город — значит можно размазать Raft» — **непроверенное**. Городская сеть бывает и долями миллисекунды, и «через firewall 40 мс с потерями». Мерить **26502/26501** (и 26500, если воркеры в чужом ЦОДе), не ping ICMP.

#### Роли, кворум, партиции

- Все брокеры с **одинаковыми** clusterSize / partitionCount / RF.
- RF=3, брокеры в **трёх** зонах. Нечётное число брокеров для схемы A.
- После старта новые брокеры **присоединяются** процедурой scaling, а не поднимают второй кластер с тем же именем.
- Лидерство партиций может сползти на одну ноду (у каждой партиции свои выборы). Для выравнивания есть Rebalancing API Self-Managed — best effort, не «всегда идеально».
- Gateway: несколько реплик; `initialContactPoints` — **все** брокеры.

#### Вторичное хранилище и экспорт

- Отдельный OpenSearch 3.8.0, ILM/ISM: вендор для Zeebe records при включённом Optimize рекомендует `minimum-age` **не короче 3 дней**, лучше **≥ 7**, дефолт примера **30d**. Слишком короткий ILM + отстающий Optimize = дырки в аналитике (для Operate 8.8+ архитектура Camunda Exporter эту гонку для Operate/Tasklist убрала; для Optimize — нет).
- Учётки экспорта — least privilege, не `admin` кластера OS.
- Retention Operate и диск OS считать **от событий процесса**, не от терабайт озера.
- Optimize выключен, пока не измерили. Если включат — бюджет OS ×3–4 или **второй** кластер OS только под Optimize (официальная рекомендация при конкуренции I/O).

#### Воркеры и интеграции

- Воркеры — Deployment с HPA по **своим** метрикам (длина работы, не CPU брокера). Несколько реплик каждого `job type`.
- Таймаут job > типичного времени интеграционного API (госслужбы с лагами!). Иначе Zeebe отдаст работу другому воркеру, получите двойной вызов. Идемпотентность на стороне API обязательна.
- Не класть ответ ведомства в variable: положить `requestId` / статус, тело — в озеро.
- Kafka: воркер **или** inbound connector читает топик и стартует/продолжает процесс. Не дублировать «и коннектор, и свой consumer» без идемпотентности ключа экземпляра.

#### Снапшоты / backup

- Инициировать **через API компонентов** (Zeebe + web apps + индексы экспорта) с **одним** backup ID (часто unix time). Нативный snapshot только OS **не** даёт согласованной точки.
- Снимок дисков брокеров по отдельности — запрещённый путь (явно в backup-гайде).
- Restore прогонять на другой namespace. Без этого у вас нет DR, есть надежда.
- Хранилище бэкапов переживает тот же отказ, что и кластер, или живёт вне всех трёх ЦОДов.

#### Безопасность прода

| Слой | Правило |
|---|---|
| Лицензия | `global.license.secret`, ключ не в Git |
| Auth | OIDC; нет `demo:demo`; authorizations на процессы/задачи |
| Admin vs Management Identity | Разные контуры; оба на корпоративный IdP |
| Ingress 8080/26500 | TLS, внутренняя сеть / mTLS mesh; не raw NodePort в мир |
| 26501/26502 | NetworkPolicy только брокеры+gateway |
| 9600 | Только мониторинг/бэкап |
| OpenSearch | HTTPS, свои учётки экспорта, не demo OS |
| Секреты коннекторов | Vault/K8s Secret |
| At-rest | CSI encryption томов брокеров и OS |
| BPMN в Git | Не класть секреты в схему; ревью моделей как код |

##### Сильные / слабые стороны (OIDC + authorizations + NetworkPolicy)

| Сильное | Слабое |
|---|---|
| Единый вход с людьми, fine-grained права с 8.8 | Два identity (Admin и Management) легко разъехать |
| Воркеры — клиенты с client credentials, не «как человек в Operate» | Ошибка роли = «почему процесс не стартует» |
| Mesh закрывает то, что Helm TLS values не закрывают | Mesh — отдельный операционный налог |
| | Не ГОСТ |

#### Kubernetes-специфика прода

- Два namespace как в production-гайде: `orchestration` (кластер, connectors, опционально Optimize) и `management-and-modeling` (Identity, Console, Web Modeler), если моделирование вообще в контуре.
- StatefulSet брокеров, RWO PVC, StorageClass с предсказуемым IOPS (не «default HDD»).
- PDB: не дать Kubernetes снять сразу два брокера из трёх.
- Topology spread по зоне = ЦОД.
- Ресурсы: CPU брокера влияет на latency (вендор упоминает порядка 3.5 core как ориентир *старых* замеров latency — это **не** ваша смета, а намёк не душить CPULimit в ноль).
- Не ставить брокеры на overlay с большим jitter без замера. Если pod-сеть между ЦОДами хуже VM — вопрос hostNetwork / отдельные VM. Только по замерам 26502.
- `orchestration.clusterSize` / `partitionCount` / `replicationFactor` в values прода: стартовая тройка **3 / 3 / 3**, пока бенчмарк не скажет иначе. Не 1/1/1.
- Bitnami subcharts: `elasticsearch.enabled: false`, свой OS. PostgreSQL Identity/Modeler — CloudNativePG или внешний.
- Выкат: не обновлять dual-region оба региона сразу (кворум). Для схемы A — rolling по одному брокеру, ждать healthy партиций.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами на 26501/26502/26500/9200. Решение A vs B vs C.
2. Закрыть лицензию и OIDC.
3. Поднять OpenSearch 3.8.0 **для Camunda** (или Elasticsearch, если B).
4. Поставить Helm 14.8.5, 3 брокера, RF=3, свои values без Bitnami DB.
5. Прогнать backup+restore.
6. Выложить воркер «эхо» + один процесс. Убить брокер — экземпляр должен продолжить.
7. Подключить первый реальный процесс: озеро по id, интеграционное API, Kafka.
8. Синтетическая нагрузка на **препроде того же размера**, что прод. Снять backpressure, commit latency, лаг экспорта, диск.
9. Прогон «ЦОД недоступен» на препроде: выключить зону, проверить кворум, что OpenSearch ещё пишет, что бэкап доступен.
10. Настроить алерты: потеря кворума, диск брокера, exporter lag, OS yellow/red, воркеры 0 replicas, лицензия.

Без пункта 9 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Схема A: 3 брокера / RF=3 / 3 зоны; цель — 1 ЦОД; OpenSearch Camunda HA; backup Zeebe+OS с restore; воркеры ≥2 на тип |
| Производительность / масштаб | Не требуется | Партиции как единица масштаба; SSD ≥1000 IOPS; маленькие variables; экспорт не на том же OS, что поиск клиентов; рост брокеров пачками по зонам; воркеры отдельно |
| Безопасность | Basic в изоляции | Лицензия; OIDC; нет demo; TLS Ingress; 26501/26502 закрыты; секреты не в Git; at-rest на томах |

**Не готов к проду**, если: C8 Run / Compose / H2, RF=1 на нескольких ЦОДах, все брокеры в одной зоне, demo/basic в открытой сети, нет лицензии, Camunda пишет в тот же OpenSearch что Wazuh или поиск клиентов, dual-region на OpenSearch, терабайты в variables, интеграционные коннекторы в обход вашего API, нет прогнанного backup restore, RTT между ЦОДами неизвестен, а схема уже stretch, ждут автоматического переживания **двух** ЦОДов на трёх брокерах.
