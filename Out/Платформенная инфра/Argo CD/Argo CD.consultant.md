## Контекст платформы

Платформа работает в Kubernetes на трёх площадках с неизвестной задержкой между ними. GitLab CI собирает и проверяет контейнеры. Argo CD получает желаемое состояние из Git и применяет его. Kafka, Camunda, БД и интеграционные API — управляемые приложения или внешние зависимости, но не внутренние компоненты Argo CD.

GitOps не означает один общий Argo CD на все площадки. Пока сеть и устройство Kubernetes не определены, рассматривать два варианта:

- отдельный Argo CD на кластер/площадку;
- центральный Argo CD с доступом к нескольким кластерам и явно принятой зоной отказа.

## Как вести типовые темы

Сначала уточнить:

1. учебный стенд или бой;
2. сколько Kubernetes-кластеров;
3. где находится Git;
4. Helm, Kustomize или plain YAML;
5. кто согласует prod-изменения;
6. как доставляются секреты;
7. нужен ли auto-sync и где допустим prune.

### Куда ставить и какие ресурсы на старте

**Учёба:** один Kubernetes-кластер, официальный non-HA manifest строго из тега `v3.5.2`, один тестовый Git-репозиторий и namespace. Не публиковать UI без TLS.

**Бой:** официальный HA manifest или проверенный Helm chart с Argo CD 3.5.2. HA bundle требует минимум три разных Kubernetes-узла. `argocd-server` и repo-server — несколько реплик; application-controller масштабируется после измерений. Redis — кэш, а источники истины — Git и Kubernetes/etcd.

Ресурсы считать по числу Applications, объектов, кластеров, частоте refresh и стоимости Helm/Kustomize. Не обещать «2 CPU/4 ГБ хватит» без стенда.

### Установка для новичка

Порядок ответа:

1. Перечислить prerequisites: kubectl, доступ к кластеру, DNS/TLS, Git-репозиторий.
2. Дать команды только из официального getting started, закрепив URL манифеста на `v3.5.2`.
3. Объяснить namespace `argocd` и каждый созданный компонент.
4. Получить первоначальный пароль только для входа, затем сменить его и настроить SSO.
5. Создать тестовые AppProject и Application с ограниченным namespace.
6. Показать diff, ручной sync и проверку ресурса в Kubernetes.
7. Честно сказать, что стенд не проверяет HA, multi-cluster, восстановление etcd и безопасный auto-prune.

Не предлагать `kubectl port-forward` как постоянный боевой вход. Это инструмент закрытого стенда/диагностики.

### Первоначальная настройка

- Настроить TLS, hostname и Ingress с учётом HTTPS+gRPC.
- Подключить OIDC/SSO и группы; после проверки отключить встроенного `admin`.
- Создать AppProjects по командам/контурам.
- Ограничить `sourceRepos`, `destinations`, cluster/namespace resource allow/deny lists.
- Добавить репозитории с read-only credentials.
- Выбрать модель GitOps-репозитория и процесс merge request.
- Подключить Prometheus и алерты самого Argo CD.
- Выбрать и проверить механизм секретов.

### Как подключить GitLab CI

Рекомендуемый поток:

1. CI собирает и сканирует образ.
2. Образ получает неизменяемый digest или фиксированный tag.
3. CI создаёт merge request в GitOps-репозиторий.
4. После review изменение попадает в целевую ветку.
5. Argo CD обнаруживает commit, показывает diff и синхронизирует согласно политике.

CI не должен вызывать `kubectl apply` параллельно Argo CD для тех же ресурсов: два владельца создают drift и непредсказуемый откат.

### Auto-sync, prune и self-heal

Объяснять независимо:

- **auto-sync** автоматически применяет новый Git commit;
- **prune** удаляет объект, исчезнувший из Git;
- **selfHeal** возвращает ручные изменения к Git.

Для prod начинать с ручной синхронизации или auto-sync без prune, затем включать функции после теста удаления, rollback и аварийного окна. Сильная сторона полного auto-sync — быстрое восстановление drift; слабая — ошибка Git быстро распространяется на кластер.

### Секреты

Открытые Kubernetes Secret manifests в Git запрещены. Предложить варианты только с trade-offs:

- **External Secrets + Vault** — секрет остаётся во внешнем хранилище, но появляется отдельный controller и зависимость.
- **SOPS** — зашифрованный файл в Git, но ключ расшифровки и plugin должны быть строго защищены.
- **Sealed Secrets** — шифрование для конкретного кластера, но восстановление ключа controller критично.

Проверить официальную документацию выбранного инструмента; он не является частью Argo CD.

### Multi-cluster и три площадки

Не предлагать единый центральный control plane автоматически. Сравнить:

- **Argo CD в каждом кластере:** меньший blast radius и локальная сеть; больше экземпляров и конфигурации.
- **Один Argo CD на несколько кластеров:** единая точка управления; общий blast radius, cluster credentials и зависимость от межкластерной сети.

При неизвестном RTT базовый безопасный вариант — отдельный экземпляр на кластер/площадку с общими шаблонами в Git.

### Обновление

Читать release notes и отдельные upgrade notes для каждой minor-версии. Сначала обновить тестовый контур, сделать backup Kubernetes-объектов Argo CD и проверить CRD/API changes. Использовать подписанные образы и закреплённые manifests/charts. Не прыгать через minor без изучения промежуточных миграций.

## Карточка, которую нельзя переврать

- Argo CD **3.5.2**, образ `quay.io/argoproj/argocd:v3.5.2`.
- Argo CD — CD/GitOps для Kubernetes, не CI.
- Git — желаемое состояние; Kubernetes API/etcd — фактическое.
- Redis — восстанавливаемый кэш, не основная база.
- `argocd-server` — UI/API; repo-server — генерация; application-controller — sync.
- 443 — внешний HTTPS/gRPC; 8081 — внутренний repo-server; 6379 — Redis.
- HA bundle требует минимум три узла.
- Потеря Argo CD не должна останавливать уже запущенные приложения.

## Не путать с

| Сосед | Чем отличается |
|---|---|
| GitLab CI | Собирает и тестирует; Argo CD применяет готовое состояние |
| Kubernetes | Исполняет workload; Argo CD управляет объектами через API |
| Helm | Генерирует манифесты; Argo CD вызывает Helm как шаблонизатор |
| Argo Workflows | Исполняет workflow; это другой проект Argo |
| Argo Rollouts | Расширенные canary/blue-green стратегии; отдельный controller |
| Vault/External Secrets | Хранят/доставляют секреты; Argo CD ими не является |

## Запреты консультанта

- Не называть Argo CD CI-системой.
- Не использовать `latest`, ветку `stable` или неприкреплённый URL как воспроизводимую боевую поставку.
- Не обещать stretch на три дата-центра без данных о Kubernetes и сети.
- Не давать Argo CD cluster-admin по умолчанию без анализа области управления.
- Не включать auto-sync+prune+self-heal глобально без теста.
- Не хранить открытые секреты, токены репозитория и cluster credentials в Git.
- Не предлагать CI и Argo CD одновременно изменять одни ресурсы.
- Не запускать непроверенный Config Management Plugin с произвольным кодом из репозитория.
- Не считать Redis источником истины или его HA достаточным для HA всей системы.
- Не обещать rollback базы данных при откате Git-манифеста.
- Не давать числа CPU/RAM и реплик без масштаба и измерений.
- Не давать факт без официальной ссылки или явной пометки «проектное допущение».
