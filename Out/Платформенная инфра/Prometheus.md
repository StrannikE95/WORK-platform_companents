# Prometheus 3.13.2 LTS — развёртывание и настройка

Версия ПО: **Prometheus 3.13.2** (LTS, релиз 29 июля 2026; на дату подготовки документа это текущая LTS-линия на https://prometheus.io/download/).  
Позже вышел **3.14.0** (17 августа 2026) — это latest, не LTS. В прод этого документа берём **3.13.2**, чтобы совпасть с тем, что реально кладёт актуальный Kubernetes-стек, а не «поставили latest вчера вечером».

Документация: https://prometheus.io/docs/  
Образы: `quay.io/prometheus/prometheus:v3.13.2` (в Helm-чарте — `v3.13.2-distroless`).  
На Kubernetes официально поддерживаемый путь сообщества: **kube-prometheus-stack 88.3.0** (11 августа 2026) — Prometheus Operator **v0.93.0**, Prometheus **v3.13.2-distroless**, Alertmanager **v0.33.1**, node-exporter **v1.12.1-distroless**. Требование чарта: Kubernetes **≥ 1.25**.  
Отдельно latest Alertmanager — **0.34.0** (16 августа 2026). С чартом 88.3.0 его **не** подмешивать «на глаз»: пара версий должна быть той, что чарт/оператор проверяли.

Этот текст — не мануал «скопируй `prometheus.yml`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Prometheus **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API). Ниже — как поставить систему метрик и алертов на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это не замена логов (Loki/OpenSearch), не шина событий, не SIEM и не «кнопка наблюдаемость включена».

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Метрика** | Число, которое меняется во времени: сколько запросов, сколько секунд, сколько байт. Не лог и не событие Kafka. |
| **Time series (ряд)** | Одна метрика + набор меток (labels) + значения с временем. `http_requests_total{job="api",code="500"}` — это **один** ряд. |
| **Label** | Ключ-значение на ряде (`job`, `instance`, `code`). Ими потом режут графики. Каждый **уникальный набор** labels = новый ряд в RAM и на диске. |
| **Cardinality (кардинальность)** | Сколько разных рядов получилось. `user_id` / UUID клиента / номер заявки в label — классический способ убить Prometheus. |
| **Sample (сэмпл)** | Одно значение ряда в конкретный момент. Официально на диске в среднем **1–2 байта** на сэмпл. |
| **Scrape (съём)** | Prometheus сам ходит по HTTP на `/metrics` цели и **забирает** цифры (pull). Цель не пушит в него постоянно. |
| **scrape_interval** | Как часто снимать. В спецификации конфига дефолт **1m**. В примере first steps — 15s. Это не «чем чаще, тем лучше». |
| **scrape_timeout** | Сколько ждать ответа цели. Дефолт **10s**, не может быть больше interval. Если RTT между ЦОДами съедает это окно — цель будет `DOWN`. |
| **Target** | Конкретный адрес, с которого снимают (`kafka-0:9308`, под Camunda, node-exporter на ноде). |
| **Job** | Группа однотипных целей в `scrape_configs` (`job_name: kafka`). |
| **Service discovery (SD)** | Prometheus сам находит цели (Kubernetes, DNS, файлы), а не только список IP руками. |
| **kubernetes_sd_configs** | SD из API Kubernetes: поды, сервисы, ноды, endpoints. |
| **Relabeling** | Переписать/выкинуть labels **до** записи в базу. Главный фильтр «не снимать мусор». |
| **honor_labels** | Поверить labels, которые прислала цель. Нужно для federation и Pushgateway. Снимает защиту «цель не может притвориться чужой». |
| **PromQL** | Язык запросов к рядам. Grafana и алерты говорят на нём. |
| **TSDB** | Локальная база Prometheus на диске. **Не кластер**: один процесс — один каталог. |
| **WAL** | Журнал «ещё не уехало в блок». После краша Prometheus его проигрывает. Сегменты по 128 МБ; минимум три файла. |
| **Block** | Кусок TSDB обычно на **2 часа**. Потом компактируется в более длинные. |
| **Retention** | Сколько хранить. Если не задать ни время, ни размер — **15d**. В kube-prometheus-stack 88.3.0 дефолт чарта — **10d**. |
| **Head** | Текущий кусок в памяти (ещё не закрытый 2-часовой блок). |
| **Remote write** | Отдать снятые сэмплы ещё куда-то (долгое хранилище). Протокол 1.0 стабилен; 2.0 в доке — experimental. |
| **Remote read** | Читать старые сэмплы извне. Официально **не** стабильный API; PromQL всё равно считается **внутри** этого Prometheus — чужая база не станет «распределённым PromQL». |
| **Federation** | Один Prometheus снимает **выбранные** ряды с другого через `/federate`. Официальный способ вырасти на много ЦОДов. |
| **Recording rule** | Заранее посчитать тяжёлый PromQL и писать результат как новый ряд. Чтобы дашборд не молотил сырые ряды каждую секунду. |
| **Alerting rule** | Условие на PromQL: если столько-то времени правда — отправить алерт в Alertmanager. |
| **`for:`** | Сколько условие должно держаться, прежде чем алерт станет firing. Практики проекта: без `for` один неудачный scrape может дёрнуть тревогу. |
| **Alertmanager** | Другой бинарь той же экосистемы: группирует, молчит (silence), дедуплицирует, шлёт в почту/мессенджер/webhook. |
| **Silence** | «Не орём по этому алерту до времени T». В HA-кластере Alertmanager силенсы **реплицируются** gossip'ом. |
| **Pushgateway** | Промежуточная коробка, куда **короткие** batch-джобы пушат метрики, а Prometheus их снимает. Не замена pull для обычных сервисов. |
| **Exporter** | Процесс рядом с ПО, которое само не умеет `/metrics`: переводит JMX/SNMP/систему в формат Prometheus. |
| **Node exporter** | Метрики машины: CPU, диск, FS, сеть. На Linux/Unix. |
| **kube-state-metrics** | Метрики **объектов** Kubernetes (сколько ReplicaSet, статус PVC), не «нагрузка ноды». |
| **Prometheus Operator** | Контроллер Kubernetes: вы описываете CRD (`Prometheus`, `ServiceMonitor`, `PrometheusRule`), он собирает конфиг и поды. |
| **ServiceMonitor / PodMonitor** | CRD «сними вот этот Service/Pod». Оператор **не** использует аннотацию `prometheus.io/scrape` как основной способ. |
| **PrometheusRule** | CRD с alerting/recording rules. |
| **Shard** | Разрезать цели между несколькими Prometheus: каждый снимает **свою** часть. Это масштаб съёма, не «один TSDB на троих». |
| **Replica (HA Prometheus)** | Два (и больше) **одинаковых** сервера снимают **одни и те же** цели. Это отказоустойчивость, не шардирование. Базы у них **разные**. |
| **external_labels** | Метки, которые этот экземпляр добавляет, когда говорит с внешним миром (Alertmanager, federation, remote write). Ими отличают реплики (`replica: A` / `replica: B`). |
| **Grafana** | Рекомендованный проектом UI для графиков. **Другое ПО**. Чарта кладёт его рядом; этот документ его не настраивает. |
| **Thanos / Mimir / аналог** | Внешнее хранилище и слой дедупликации запросов. FAQ и Operator упоминают Thanos. Это **не** часть бинаря Prometheus. Без него два HA-реплики дают **два** слегка разных TSDB. |
| **Metrics Server / Prometheus Adapter** | Чтобы HPA в Kubernetes ел кастомные метрики. Чарта kube-prometheus-stack **явно не ставит** Adapter. См. документ по Kubernetes. |
| **Active series** | Ряды, которые сейчас «живые» в head. FAQ: один инстанс умеет **десятки миллионов** active series. Это потолок порядка, не ваш замер. |

## Основные элементы системы и зависимости

### Что входит в «Prometheus» как экосистему (это несколько бинарей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Prometheus server** | Снимает, хранит, считает правила, отдаёт PromQL | Вертикально: CPU/RAM/диск. Горизонтально: **ещё инстансы** (HA-реплики и/или шарды). Встроенного кластера TSDB **нет** |
| **Alertmanager** | Маршрутизация алертов, silence, дедуп | HA-кластер gossip (Memberlist). Кворума/голосовании **нет** |
| **Node exporter** | Метрики ОС | По числу машин (DaemonSet / пакет на VM) |
| **kube-state-metrics** | Состояние объектов K8s | Несколько реплик (stateless), если API-сервер жив |
| **Клиентские библиотеки** | Приложение само отдаёт `/metrics` | Вместе с репликами приложения |
| **Exporters** (JMX, Blackbox, SNMP, …) | То, что не инструментировано | По числу снимаемых инстансов |
| **Pushgateway** | Короткоживущие job'ы | Обычно один на контур; это **не** HA-хранилище |

Плюс на Kubernetes: **Prometheus Operator** (один под в чарте; его падение не останавливает уже запущенный Prometheus, но останавливает применение новых ServiceMonitor/Rule).

### Официальные порты (менять можно, но это контракт сети)

| Компонент | Порт | Назначение |
|---|---|---|
| Prometheus | **9090/TCP** | UI, HTTP API, свой `/metrics`. Дефолт `--web.listen-address=0.0.0.0:9090` |
| Pushgateway | **9091/TCP** | Приём push. 9092 специально **не** занят проектом (коллизия с Kafka) |
| Alertmanager | **9093/TCP** | UI/API алертов |
| Alertmanager cluster | **9094** TCP+UDP | Gossip. При TLS-транспорте — только TCP |
| Node exporter | **9100/TCP** | Метрики машины |
| Цель приложения | обычно **`/metrics`** на порту сервиса | Контракт съёма |

### Чего в Prometheus нет (частая путаница)

| Нужно системе | Это не Prometheus | Зачем помнить |
|---|---|---|
| Кластер TSDB «как у Kafka / OpenSearch» | Нет. Цитата storage: local storage *is not clustered or replicated* | Два пода Prometheus ≠ одна база с replica-шардами |
| 100% точность для биллинга | Официально **не** тот инструмент | Пропуски scrape, агрегация, float64 — норма модели |
| Логи / трассировки / события Camunda | FAQ: логи в Prometheus не класть | Рядом — Loki/OpenSearch/Jaeger, не «ещё одна метрика» |
| Шина Kafka / озеро эталона / интеграционное API | Нет | Prometheus **наблюдает** их, не заменяет |
| Автовыбор лидера TSDB при падении ЦОДа | Нет | Второй инстанс уже сам снимает те же цели; «переехать диск» — ваш runbook |
| Дедуп запросов при `replicas: 2` через Service | Нет. Чарта прямо: Service даёт доступность, **не** дедуп | Без Thanos Query (или аналога) графики могут «прыгать» |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS — Go `crypto/tls`, минимум TLS 1.2, цель — оценка Qualys **A** |
| Порог RTT между ЦОДами | Нет | Есть `scrape_timeout` (дефолт 10s) и gossip Alertmanager (probe **1s**) — это не «можно при 40 мс» |
| Гарантия «терабайты озера влезут в TSDB» | Нет | Диск считают от **сэмплов/с × retention × 1–2 байта**, не от объёма клиентских данных |

### Зависимости окружения (обязательны)

- **ОС:** бинарь Go, Linux x86_64/ARM64 в проде типичен. Windows-сборка сервера есть; node_exporter — про Unix.
- **Диск TSDB:** локальная POSIX-ФС. Официальный CAUTION: **NFS (включая AWS EFS) не поддерживается**; не-POSIX — риск нечинящейся порчи. В Kubernetes это **block CSI / local SSD**, не NFS StorageClass «для удобства».
- **Не сеть как единственное хранилище.** Проект специально: сервер автономен, без зависимости от distributed storage — чтобы во время аварии мониторинг ещё отвечал.
- **Kubernetes (если идёте чартом):** кластер ≥ 1.25, CSI под PVC Prometheus/Alertmanager, RBAC, возможность снимать kubelet/cAdvisor (часто отдельный Service в `kube-system`).
- **Сеть pull:** Prometheus должен **достучаться HTTP(S)** до каждой цели. В трёх изолированных кластерах «один центральный Prometheus» без сети до подов — фантазия.
- **Люди и канал алертов:** почта/мессенджер/on-call. Alertmanager без приёмника — колокольчик в пустоту.
- **PKI**, если включаете TLS на 9090 и mTLS на 9094. Basic Auth без TLS = пароль в открытую (это пишет security model).

### Как Prometheus стыкуется с вашей архитектурой

```
Микросервисы / Camunda / интеграционное API / Kafka (JMX или свой /metrics)
        │  pull HTTP /metrics   (не event-sourcing)
        ▼
   Prometheus replica A  ──┐
   Prometheus replica B  ──┤  одинаковый scrape + разные external_labels
        │                  │
        │  alerts на ВСЕ Alertmanager (не через LB)
        ▼
   Alertmanager cluster (gossip :9094)
        │
        ▼
   on-call / webhook

Ноды K8s ── node_exporter :9100
API K8s  ── kube-state-metrics
        ── cAdvisor / kubelet

Опционально: remote write → долгое хранилище
Опционально: global Prometheus ── /federate ── per-ЦОД Prometheus
```

Prometheus **не** пишет в Kafka бизнес-события и **не** ходит в госслужбы. Он снимает числа с тех, кто уже крутится. Если интеграционное API «само выбирает интеграции» — в метриках должны быть **задержки, ошибки, очередь ожидания**, а не сырой payload ответа ведомства.

## Краткие вводные

### Зачем вам Prometheus в этой архитектуре

У вас Kubernetes, микросервисы, Kafka, процессный движок, 30+ интеграций, ожидание непрерывной работы и **нет замеров нагрузки**. Без метрик вы не отличите «Kafka тормозит» от «Camunda ждет внешний API 40 секунд» от «узел ЦОДа забился диском».

Типичные дыры, которые логи и WAF **не** закрывают сами:

1. Сейчас больно или нет (latency, error rate, saturation) — до того, как пользователь напишет.
2. HPA/ёмкость: без рядов не из чего масштабировать (Adapter — отдельно).
3. Алерты «диск TSDB / WAL / scrape fail / Alertmanager split», иначе мониторинг умрёт тихо.
4. Доказательства для руководства: не «готовы к высокой нагрузке», а график `prometheus_tsdb_head_series` и latency интеграций.

Проект сам формулирует нишу: числовые ряды, динамические сервисы, **надёжность важнее биллинговой точности**. Во время аварии этот ящик ещё должен открываться.

### Как устроена отказоустойчивость (идея, не магия)

Это **не один кластер**, а несколько независимых приёмов. Путать их — главная ошибка.

**1) Prometheus server (TSDB)**

Официальный FAQ: *run identical Prometheus servers on two or more separate machines*. Operator: те же цели и правила, **разный** external label, чтобы отличить реплики. Съём и оценка правил **не** синхронны до миллисекунды — ответы PromQL на A и B могут чуть расходиться. Для алертов это обычно неважно (`for:` держит условие). Для графиков — sticky session на Service **или** слой дедупа (Thanos Query и т.п.).

| Что падает | Что происходит |
|---|---|
| Один из двух HA-реплик | Второй продолжает снимать и алертить. Дырка в **его** локальном TSDB на время жизни этого пода. История второго реплики цела. |
| Оба в одном ЦОДе, ЦОД мёртв | Нет метрик **этого** контура, если не было реплики в другом ЦОДе и не было federation/remote write. |
| Диск / порча TSDB | Процесс может не стартовать. Официально: бэкап **снимком**; без снимка риск потерять WAL (последние ~2–3 часа). NFS «чтобы PVC жил» — путь к порче, не к HA. |
| Operator под | Уже запущенные Prometheus/Alertmanager живут. Новые ServiceMonitor/Rule не применятся, пока Operator не встанет. Чарта: Operator — **один** под. |

Следствие: HA **съёма и алертов** = ≥2 Prometheus + Alertmanager-кластер. HA **истории графиков** = либо смириться с локальным диском каждой реплики, либо remote write / объектное хранилище (уже другое ПО).

**2) Alertmanager**

Настоящий кластер: gossip, репликация силенсов и журнала уведомлений. Дизайн: **fail-open** — при split-brain лучше **два** письма, чем ноль. Кворума нет: жив один — уведомления идут. Типичный размер в доке: **2–3** в одном ЦОДе, **4–5** в multi-DC / особо критичном. Чёт/нечет **не** важен (это не Raft).

Критично: Prometheus шлёт алерты **на все** инстансы Alertmanager, **не** через балансировщик. LB между ними — официальный anti-pattern (SPOF и ломает модель).

Порт **9094** должен быть открыт между членами. Advertise-address — **IP:port**, не hostname. По умолчанию gossip **без шифрования**; для WAN док требует **mTLS**.

Алерты сами **не** пишутся на диск Alertmanager: их регулярно пересылает Prometheus.

**3) Exporters / цели**

Падение цели = ряд `up=0` (если Prometheus жив). Падение node_exporter на ноде = слепая эта нода, не весь кластер. kube-state-metrics без HA API-сервера бесполезен: источник — Kubernetes.

### Как устроено масштабирование

Четыре независимые оси (официальные, не блог-рецепты):

1. **Меньше рядов / реже scrape** — главный рычаг. Док storage: урезать series эффективнее, чем удлинить interval (сэмплы в ряде хорошо жмутся).
2. **Больше железа одному Prometheus** — FAQ: один инстанс тянет tens of millions active series. Это потолок порядка. Ваш потолок узнается по RAM, CPU PromQL, compaction и диску.
3. **Функциональные шарды** — Operator: шарда X снимает сервисы A/B/C, шарда Y — D/E/F. Предпочтительнее «автошарда по адресу».
4. **Иерархическая federation** — официально для *tens of data centers and millions of nodes*: детальный Prometheus в площадке, глобальный снимает **агрегаты** через `/federate`.

Формула диска (storage.md):

```text
needed_disk_space ≈ retention_seconds × ingested_samples_per_second × (1…2 байта)
```

Нагрузки у вас нет → **цифры PVC «под терабайты озера» выдумать нельзя**. Озеро клиентских данных и TSDB — разные объёмы. Кардинальность labels интеграционного API (`request_id`, `client_inn`) раздует ряды быстрее, чем «много гигабайт в MinIO».

Retention по размеру: вендор советует **не больше 80–85%** диска — остальное на двойное место во время compaction.

Чарта 88.3.0 по умолчанию: **`replicas: 1`**, retention **10d**. Это стенд, не прод-HA.

### Безопасность самого Prometheus

Модель безопасности проекта жёсткая и честная:

- Считается, что **недоверенный** пользователь **уже** может открыть HTTP Prometheus и логи → он видит **все** ряды и отладку.
- Менять конфиг, флаги, rule files могут только **доверенные**.
- Эндпоинты **не** торчат в интернет: UI, API, `/metrics` целей, `/pprof`. Иначе DoS «дорогим запросом» — ожидаемое поведение, не «дыра под CVE».
- `--web.enable-admin-api` (удаление рядов) и `--web.enable-lifecycle` (`/-/reload`, `/-/quit`) по умолчанию **выключены**.
- Метрики **не** считаются секретом. Если в label попал ПДн / токен — это уже ваша утечка, Prometheus её «не спрячет».
- `honor_labels: true` и открытый Pushgateway = любой, кто дотянулся, может **нарисовать любой ряд**.
- Blackbox/SNMP-exporter с целью из URL: кто дошёл до exporter, может заставить его сходить «куда угодно» (плюс утечка community string / basic auth). TLS client cert на этот риск не тот.
- Grafana в proxy mode: права на дашборд **не** равны правам на PromQL — кто открыл Explore, тот гоняет произвольные запросы.
- CSRF на admin-ручке нет специально (чтобы curl работал). Обратный прокси должен **резать** `/api/*/admin/` и `/-/quit`.

Компрометация Prometheus = карта вашей инфраструктуры, RPS интеграций, имена сервисов, иногда идентификаторы в кривых labels. Это не «просто графики».

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Self-hosted Prometheus 3.13.2 LTS**, не Grafana Cloud / AMP / аналог. Облако вендора в схеме с тремя своими ЦОДами не предполагалось.
2. **Прод в Kubernetes**, инсталлятор — **kube-prometheus-stack 88.3.0** (Operator 0.93.0). Образы из **вашего** registry, теги как в чарте (`v3.13.2-distroless`, Alertmanager `v0.33.1`), не `latest`. Если поставите бинарём на VM рядом с K8s — правила HA те же, меняется только оркестрация диска.
3. **Не подмешиваем 3.14.0 в чарт 88.3.0** без проверки совместимости Operator. Latest существует; этот документ его не объявляет «прод-стандартом».
4. **Три ЦОДа = три зоны отказа.** Пока RTT неизвестен, честный прод: **локальный съём** (Prometheus видит цели своей площадки с запасом до `scrape_timeout`), а не один процесс, который scrape'ит три ЦОДа вслепую.
5. **Цель отказа: пережить 1 ЦОД** для алертов и текущего съёма, не 2 из 3 и не «вечная история графиков без remote write».
6. **Нагрузка неизвестна** — поэтому **нет** цифры «N Gi PVC и M millicores». Есть сигналы (`prometheus_tsdb_head_series`, RAM, scrape fail, compaction, `up`) и рычаги (labels, interval, шарды, federation).
7. **«Система 24/7» ≠ «ни один scrape не пропущен».** Проект сам отказывается от 100% точности. SLA на полноту рядов надо отдельно решить с бизнесом.
8. **On-call будет.** Правила без маршрута в Alertmanager — декорация.
9. **Корпоративный PKI есть или будет.** TLS на 9090 и mTLS на 9094 в проде; self-signed — для теста.
10. **Приложения сами отдают `/metrics`** (или рядом стоит exporter). «Поставили чарт — увидели Camunda и Kafka» **не** случится без ServiceMonitor и без экспорта на стороне продукта.
11. **Grafana — сосед**, не часть этого документа. Дефолтный admin/пароль чарта в прод не переносится (это уже Grafana).
12. **Thanos/Mimir не обязательны**, чтобы считать Prometheus «поставленным». Они нужны, когда хотите **одну** дедуплицированную историю и долгое хранение. FAQ их упоминает; это отдельный проект и отдельный диалог.
13. **Лицензия Apache 2.0.** License-server нет. Сборка бинарей у проекта идёт на чужой CI: кого это смущает — собираете сами (security model).
14. **Тестовый стенд изолирован.** На нём допустимы `replicas: 1`, emptyDir, без TLS. В прод это не копируем.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «helm install и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потери между ЦОДами** | `scrape_timeout` по умолчанию 10s. Gossip Alertmanager пробивает пиров раз в 1s. Порога в мс у проекта нет. Stretch «один Prometheus на три ЦОДа» без замера — лотерея `UP`/`DOWN`. |
| **Один K8s на 3 ЦОДа или три кластера** | От этого зависит: один Prometheus CR или три + federation. Pull не работает сквозь глухой firewall. |
| **Где живут цели** (Kafka/Camunda в каком ЦОДе) | Съём лучше **рядом** с целью. Иначе авария канала ЦОД↔ЦОД = «всё красное», хотя сервисы живы. |
| **Кардинальность** (будут ли `client_id`, `inn`, `trace_id` в метриках интеграций) | Один «удобный» label важнее терабайт озера: съест RAM head. |
| **Срок хранения рядов и 152-ФЗ** | Дефолт 15d (чарт 10d). Год истории = диск и, если в labels ПДн, юридический объект. |
| **Куда торчит 9090/9093** | Публичный UI = карта инфраструктуры. Security model исходит из того, что кто видит HTTP — видит всё. |
| **Кто принимает алерты** | Без приёмника HA Alertmanager бессмысленна. |
| **StorageClass: local vs NFS** | NFS официально не поддерживается. «Общий PVC на два реплики» ещё и невозможно корректно: у каждой реплики **свой** диск. |
| **Нужен ли HPA по кастомным метрикам** | Adapter чарт не ставит. Решите отдельно, иначе HPA останется на Metrics Server. |
| **Закрытый контур / свои registry** | Образы quay.io/ghcr.io должны быть зеркалом. Иначе чарт не встанет. |
| **Стык с уже описанными Wazuh/Falco/HAProxy** | Три источника «диск полный» / «под рестартится». Нужна матрица: кто алертит, кто логирует, кто блокирует. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **Prometheus 3.13.2** + способ: бинарь/compose **или** kube-prometheus-stack **88.3.0**. Не смешивать 2.x и 3.x «на глаз».
2. Сначала **диск и сеть съёма**, потом правила алертов, потом красота Grafana.
3. Включить метрики самого Prometheus: `up`, `prometheus_tsdb_head_series`, `prometheus_target_interval_length_seconds`, `prometheus_rule_evaluation_failures_total`, `alertmanager_cluster_members`.
4. Поставить **хотя бы одну** цель, которая не «сам себя»: node_exporter или `/metrics` вашего API. Проверка: `up{job="..."} == 1` и ряд растёт.
5. Подключить Alertmanager и **одно** тестовое правило с `for:` (практики проекта: ориентир **не меньше 5 минут**, если нет особой причины). Убедиться, что уведомление дошло.
6. Только потом — ServiceMonitor на Kafka/Camunda/интеграции и борьба с кардинальностью.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** увидеть scrape, PromQL, шум дефолтных kube-правил, понять UI. **Не** цель: доказать, что прод переживёт падение ЦОДа и кардинальность интеграционного API.

Два официальных минимальных пути (выберите один):

**Путь A — бинарь Linux** (быстрее понять продукт):

- Скачать `prometheus-3.13.2.linux-amd64.tar.gz` с prometheus.io/download (считать checksum).
- Пример first steps: процесс слушает **:9090**, снимает сам себя с `/metrics`.
- Рядом при желании Alertmanager 0.33.1 (как в чарте) на :9093 — чтобы увидеть цепочку алерта, не только график.

**Путь B — Kubernetes, чарт как есть** (ближе к проду):

- `kube-prometheus-stack` **88.3.0**, namespace вроде `monitoring`.
- Оставить **`replicas: 1`** у Prometheus и Alertmanager.
- StorageClass, который на тесте можно даже emptyDir (история переживёт только жизнь пода).
- Не открывать LoadBalancer 9090 в интернет.

Режим «replicas: 2 + Thanos + federation на Minikube» для знакомства **не нужен**: создаст ложное чувство HA и сгорит по RAM.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Реплики Prometheus / AM | 1 | Нет требования пережить выкат |
| TLS / basic auth | можно без | Иначе команда утонет в PKI раньше, чем в PromQL |
| Retention | дефолт чарта 10d или меньше | Нет боевой истории |
| PVC | маленький / emptyDir | Не цель — ёмкость |
| Federation / remote write | выкл | Нечего агрегировать |
| Pushgateway | выкл | Без batch-job только лишняя дыра |
| Кардинальность приложений | одно demo-приложение | Сначала увидеть дефолтные kube-ряды |

#### Чего на тесте **не** стоит упрощать

- Версия **3.13.2** (или явный осознанный 3.14.0 на бинаре, но не «чарт 88.3.0 + latest»).
- Хотя бы один `up==1` не про сам Prometheus.
- Понимание: дефолт чарта **не HA**. Успешный график CPU ноды **не** доказывает, что два реплики и gossip 9094 заработают на трёх ЦОДах.
- Не включать `honor_labels` «чтобы заработало» на всём подряд.
- Не класть в labels идентификаторы клиентов «для удобства отладки».

#### Сильные стороны такой схемы

- Поднимается за часы.
- Совпадает с first steps / values чарта.
- Дешево показывает, какие ряды уже орёт Kubernetes mixin.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет второго TSDB, нет доказанной кардинальности Kafka/Java.
- Service перед единственным подом — не HA.
- Привычка `helm install` с `replicas: 1` уезжает в прод вместе с values.

Практическая рекомендация: препрод = маленький **прод-профиль** (2 Prometheus, ≥2 Alertmanager, свои PVC block-storage, TLS внутри кластера, один ServiceMonitor на настоящее приложение), даже без боевого трафика.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «гигабайт PVC под терабайты озера» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Prometheus не выбирает за вас «один Kubernetes или три». Он плохо переживает **один слепой scrape на три площадки** и плохо переживает **три независимых правды для дежурного** без federation/общего Alertmanager.

**Вариант A — один Kubernetes на 3 зоны, один Prometheus HA-pair.**

- `prometheus.prometheusSpec.replicas: 2`, `podAntiAffinity: "hard"`, `externalLabels.cluster` задан.
- Topology spread: реплики **в разных ЦОДах**, не на двух нодах одной стойки.
- Alertmanager `replicas: 3` (по одному в зоне) **или** минимум 2. Кворума нет: смысл в «живой хотя бы один + fail-open», не в нечётном числе. Док: 2–3 типично для одного DC; 4–5 для multi-DC. На трёх ваших ЦОДах разумная старт-точка — **3**.
- Gossip 9094 между зонами: **mTLS**, измеренный RTT. Нет цифры «можно». Есть факт: probe каждую секунду и settle при старте.
- PVC **по одному на под**, RWO, **не NFS**.
- Не чистить replica external labels (`replicaExternalLabelNameClear`) — чарт это прямо запрещает для HA.

**Вариант B — иерархия (официальный масштаб на много DC).**

- В каждом ЦОДе свой Prometheus (лучше тоже `replicas: 2` внутри площадки) — детальные instance-ряды, короткий retention.
- Глобальный Prometheus снимает **агрегаты** (`job:`-ряды / recording rules) через `/federate` с `honor_labels: true`.
- Алерты «горит инстанс» — локально. Алерты «горит платформа» — глобально. Иначе дубли и споры.

**Вариант C — три изолированных Kubernetes без federation.**

Три TSDB, три набора правил, три Grafana. Имеет смысл только если on-call **готов** жить в трёх консолях. Обычно хуже A/B.

**Пока топология K8s не зафиксирована, нельзя честно выбрать A или B.** Дальше — общее.

##### Сильные / слабые стороны (A, один кластер на 3 зоны)

| Сильное | Слабое |
|---|---|
| Один набор ServiceMonitor/Rule, один on-call | Scrape и gossip ходят меж ЦОД: RTT бьёт по `up` и по дедупу AM |
| Официальный HA-pair + AM cluster почти про это | Падение сети между зонами: AM **намеренно** шлёт дубли (fail-open) |
| Operator один | Operator всё равно один под: выкат CR во время его смерти встанет |
| Проще, чем Thanos «с порога» | История графиков = два локальных диска; без дедупа UI «прыгает» |

##### Сильные / слабые стороны (B, per-DC + federation)

| Сильное | Слабое |
|---|---|
| Официальный рецепт *tens of data centers* | Два слоя правил; легко забыть, где живёт алерт |
| Съём локальный: авария канала ≠ ложный DOWN всего | Глобальный Prometheus — SPOF «общей картины», его тоже надо HA |
| Кардинальность instance-рядов не едет на глобальный | `/federate` с широким `match[]` превращается в второй полный TSDB |
| | `honor_labels` на federation — осознанный риск подмены labels |

##### Слабое место любого решения без замера RTT

Документация **не задаёт** миллисекунды. Утверждение «три ЦОДа в одном городе, значит один scrape на все ноды» — **непроверенное**. Городская сеть бывает и 0.5 мс, и «через кривой firewall 40 мс с потерями». Мерить надо путь **Prometheus → /metrics цели** и **AM:9094 ↔ AM:9094** до закупки схемы.

#### Prometheus server (ядро отказоустойчивости *съёма*)

Минимум для «пережить 1 под / 1 зону съёма»:

- **≥ 2** реплики с одинаковыми scrape/rules и разными `external_labels`.
- Anti-affinity / topology spread по ЦОДу.
- PVC: local/block, размер от формулы сэмплов, не дефолт чарта «чтобы стартануло». `retention.size` ≤ 80–85% PVC.
- WAL compression **вкл** (в 3.x это норма; чарт 88.3.0: `walCompression: true`).
- `--web.enable-admin-api` / `enable-lifecycle` в проде только если понимаете, кто дойдёт до ручки; иначе оставить выкл и reload через Operator/SIGHUP из доверенного контура.
- `sample_limit` / `label_limit` / `target_limit` на опасных job (интеграции, Kafka JMX): лучше отвалить цель, чем положить весь TSDB.
- Recording rules на тяжёлые дашборды **до** того, как Grafana начнёт молотить сырой PromQL по терабайтам истории (истории у вас ещё нет — привычку закладывать сейчас).

Шардирование: сначала **функциональное** (отдельный Prometheus на Kafka-платформу, отдельный на интеграционное API), не автоматический shard по hash адреса. Operator честно пишет: автошард усложняет запросы и просит federation/Thanos Ruler.

**Слабое место:** `replicas: 2` + общий Kubernetes Service без sticky/дедупа = «мониторинг высокодоступный», а дежурный смотрит на два немного разных графика. Это не баг — так устроена модель.

#### Alertmanager (ядро отказоустойчивости *уведомлений*)

- Список **всех** AM в `alerting.alertmanagers` каждого Prometheus. Не Ingress/LB.
- `replicas ≥ 2`, лучше 3 по зонам.
- 9094 открыт между ними, advertise IP, одинаковые `--cluster.peer-timeout` (дефолт **15s** — им же строится задержка по позиции пира).
- mTLS на gossip, раз ЦОДы разные.
- PVC на силенсы/nflog (в чарте retention силенсов по умолчанию **120h** — это не retention метрик).
- Приёмники: без templating секрета в label алерта (security model: кто шлёт алерт, тот выбирает email).
- Мониторить `alertmanager_cluster_members`, `alertmanager_cluster_failed_peers`. Несовпадение размера кластера = split-brain, дубли ожидаемы.

Падение ЦОДа с одним AM: остальные шлют. Падение сети между ЦОДами: **дубли уведомлений** — это задокументированная цель дизайна, не авария. Объясните это on-call заранее.

#### Съём ваших систем (иначе платформа слепая)

| Источник | Что обычно снимают | Чего не делать |
|---|---|---|
| **Kubernetes** | kubelet, cAdvisor, kube-state-metrics, node_exporter DaemonSet **с tolerations** на tainted-ноды Kafka/control-plane | Аннотации `prometheus.io/scrape` как основной способ (оператор их не считает заменой ServiceMonitor) |
| **Микросервисы** | RED: rate, errors, duration. Histogram latency | `user_id`, `trace_id`, URL path с UUID в labels |
| **Kafka** | JMX exporter (проектный Java-путь) или метрики самого продукта, если есть | Снимать «каждый топик×partition×consumer» без лимитов — взрыв рядов |
| **Camunda** | Если движок отдаёт `/metrics` — ServiceMonitor. Иначе это пробел продукта, не Prometheus | Выдумывать экспортер «на коленке» в этом документе |
| **Интеграционное API** | Число вызовов внешней системы, ошибки, возраст ожидания лага, **без** тела ответа | Метрика на каждый ИНН/запрос ведомства |
| **Озеро данных** | Лаг репликации, размер, ошибки job — как **числа** | Метрика на каждую клиентскую запись |

Pushgateway — только эфемерные batch (официальная ниша). Постоянные сервисы должны быть pull. Иначе honor_labels + открытый 9091 = точка подмены рядов.

#### Безопасность прода (без этого кластер не считается настроенным)

Три слоя:

1. **Сеть** — 9090/9093/9091/9100 не с мира; 9094 только между AM; NetworkPolicy; scrape целей по внутренней сети. Reverse proxy режет admin/lifecycle/pprof.
2. **Идентичность** — `--web.config.file`: TLS + Basic Auth (пароли **bcrypt**) или mTLS клиентских сертификатов. Без TLS basic auth запрещён смыслом модели. Образы pin по тегу **и digest**, свой registry.
3. **Данные** — labels без ПДн; диски PVC шифровать средствами платформы (в самом Prometheus at-rest «ГОСТ-кнопки» нет); retention как политика, не как «15 дней потому что дефолт».

Плюс:

- RBAC Operator минимальный, но честный: он создаёт/правит StatefulSet и секреты в namespace.
- Admission webhook правил (в чарте включён) ломает выкат при мёртвом Operator — осознанный риск, который README считает приемлемым.
- Бэкап: **снимки** TSDB, не `cp` каталога на живую. Учитывать дырку WAL (~часы).
- Не публиковать 9090 «для удобства разработчиков». Отдельный Grafana с SSO и своей политикой — лучше, чем все ходят в Explore Prometheus.
- `insecure_skip_verify` на scrape — только стенд.

##### Сильные / слабые стороны выбранной ИБ-схемы (чарт 88.3.0 + HA-pair + AM cluster + TLS)

| Сильное | Слабое |
|---|---|
| Модель безопасности описана проектом без иллюзий | Любой, кто открыл 9090, видит все ряды — сеть важнее «ролей внутри Prometheus» (ролей как у Wazuh API нет) |
| TLS и bcrypt из коробки сервера | CSRF на admin-ручках нет; нужен прокси |
| Pull: цель сама не должна уметь писать в TSDB | `honor_labels` / Pushgateway / Blackbox это ломают |
| Автономия локального диска при аварии сети хранения | Тот же диск — SPOF истории этой реплики |
| Apache 2.0, без облачной лицензии | Не ГОСТ; supply-chain сборки на чужом CI |

#### Kubernetes-специфика прода

- Чарт **88.3.0**, не `main`. CRD чарт **не обновляет** при обычном helm upgrade — мажор чарта = ручное обновление CRD (README).
- Prometheus и Alertmanager — **StatefulSet + PVC**. Два реплики = два тома.
- Дефолт `replicas: 1` **переопределить**.
- PDB: не убивать сразу обе реплики при drain.
- node_exporter: DaemonSet, **tolerations** на системные taint, иначе слепые самые важные ноды (как у Falco/Wazuh).
- ServiceMonitorSelector: понять, видит ли Prometheus чужие namespace. Дефолт чарта завязан на label релиза — «поставили exporter в другой namespace и тишина».
- Ресурсы: requests/limits по факту `head_series` и query load. Throttle CPU → отставание scrape и правил.
- Rolling update: пока под вниз, вторая реплика должна нести съём. При `replicas: 1` выкат = дырка.
- Не ждать, что чарт поставит Prometheus Adapter. Для HPA — отдельное решение (см. Kubernetes.md).

#### Порядок вывода в прод (этапы, не команда за командой)

1. Измерить RTT/потери: Prometheus↔цели и AM↔AM на 9094. Решить: A (stretch HA) или B (per-DC + federation).
2. Зафиксировать retention и запрет high-cardinality labels (письменно, в ревью метрик).
3. Зеркало образов 3.13.2 / AM 0.33.1 / operator 0.93.0.
4. Поднять чарт с **replicas Prometheus=2**, AM≥2, block PVC, свои TLS, **не** дефолтный Grafana в интернет.
5. Проверить `up` по kube-компонентам и `alertmanager_cluster_members == N`.
6. ServiceMonitor на одно реальное приложение (интеграционное API или Kafka) с `sample_limit`.
7. Recording + alerting rules с `for:`, тестовый page в on-call.
8. Наблюдать неделю: head series, RAM, scrape duration vs timeout, dropped samples.
9. Учение «под Prometheus в ЦОД-1 убит»: алерты идут со второй реплики. Учение «ЦОД AM изолирован»: придут **дубли** — это успех fail-open, не баг. Учение «CSI NFS по ошибке»: не делать.
10. Только если история и дедуп запросов стали требованием — отдельный проект remote write / Thanos. Не «обязательная галочка дня один».

Без пунктов 1, 4 (`replicas: 2` + не NFS), 7 и 9 у вас нет мониторинга платформы, есть namespace `monitoring`.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | ≥2 Prometheus с разными external_labels и своими PVC; AM-кластер ≥2 (лучше 3 по ЦОДам), **без LB** на пути алертов; переживание **1** ЦОДа для текущего съёма и уведомлений; runbook на порчу TSDB/WAL; Operator не единственная надежда уже идущего scrape |
| Производительность / масштаб | Не требуется | Лимиты кардинальности; формула диска от **сэмплов**, не от озера; functional shards / federation при росте; recording rules; ресурсы не «как в demo»; локальный съём при неизвестном RTT |
| Безопасность | UI не с мира | 9090/9093 закрыты; TLS(+auth); 9094 mTLS между ЦОДами; pin 3.13.2; без Pushgateway «для всех сервисов»; labels без ПДн; admin API выкл |

**Не готов к проду**, если: `replicas: 1` на три ЦОДа; общий NFS-PVC; LB перед Alertmanager; `latest`; 9090 из LoadBalancer в интернет; `honor_labels` на всём; `trace_id` в labels; ждут, что Prometheus заменит логи и Kafka; ждут 100% данных для биллинга; RTT не мерили, а scrape тянется через три площадки; учение отказа реплики/зоны не делали; чарт 88.3.0 «как есть» с дефолтным одним подом.
