# Zabbix 7.0.30 LTS — развёртывание и настройка

Версия ПО: **Zabbix 7.0.30** (LTS, релиз 25 августа 2026; источники: https://www.zabbix.com/download_sources и политика жизненного цикла https://www.zabbix.com/life_cycle_and_release_policy).  
Полная поддержка линии **7.0 LTS**: до **30 июня 2027**; ограниченная — до **30 июня 2029**.  
В тот же день вышел **7.4.14** — это текущая *standard*-линия, не LTS. Полная поддержка 7.4 — до выхода 8.0 LTS; ограниченная заявлена на **Q4 2026**. Линия **8.0 LTS** в политике значится как Q3 2026, но на странице исходников на дату подготовки документа её **нет**. В прод этого файла берём **7.0.30**, а не «вчерашний latest».

Документация: https://www.zabbix.com/documentation/7.0/en/manual/  
Образы (официальные, Docker Hub `zabbix/`): `zabbix-server-pgsql`, `zabbix-web-nginx-pgsql` (или Apache), `zabbix-proxy-sqlite3` / `zabbix-proxy-pgsql`, `zabbix-agent2`, `zabbix-java-gateway`, `zabbix-web-service`. Пин патч-тег линии 7.0.30 (`alpine-7.0.30` / `ubuntu-7.0.30` — смотреть фактические теги на Hub), **не** `latest`.  
Compose: репозиторий https://github.com/zabbix/zabbix-docker , ветка **7.0**.  
На Kubernetes **первого** оператора/чарта «поставь весь Zabbix 7.0 в прод» у вендора нет. Официальный Helm в `git.zabbix.com` (ZT/kubernetes-helm) ставит компоненты **мониторинга Kubernetes из уже существующего** Zabbix, а не сам сервер. OpenShift Operator в старых мануалах застрял на линиях 5.0/6.0 — для 7.0 его не брать. Целевой путь прода: **официальные образы** + ваши манифесты (или осознанный community-Helm, это уже не вендор).

Этот текст — не мануал «скопируй `docker compose up`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Zabbix **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить систему мониторинга (хосты, SNMP, доступность, триггеры, эскалации) на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** замена Prometheus (у вас отдельный документ), **не** SIEM (Wazuh), **не** логи (OpenSearch) и **не** шина событий.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Хост (host)** | То, что наблюдаете: сервер, под, коммутатор, URL интеграционного API. Не путать с hostname Linux. |
| **Элемент данных (item)** | Одна проверка на хосте: CPU, `net.tcp.service`, SNMP OID, HTTP-код. |
| **Триггер (trigger)** | Условие «это плохо»: выражение над item'ами. Сработал → **проблема (problem)**. |
| **Событие (event)** | Факт: триггер сработал / восстановился, авторегистрация и т.д. |
| **Медиа / action** | Куда и как слать: почта, webhook, скрипт. Без action триггер орёт только в UI. |
| **NVPS** | New Values Per Second: сколько новых значений в секунду падает в сервер. Грубо `число item / средний интервал`. Главный рычаг нагрузки на БД. |
| **History** | Сырые значения item'ов за N дней. Потом housekeeper (или drop partition в TimescaleDB) их вычищает. |
| **Trends** | Почасовые min/max/avg/count. Период часа **не** настраивается. Нужны для длинных графиков. |
| **Housekeeper** | Процесс сервера: удаляет устаревшие history/trends/events. По умолчанию раз в час. На большой БД без партиций он сам становится аварией. |
| **Zabbix server** | Мозг: считает триггеры, пишет историю, шлёт action. **Не** кластер с кворумом шардов. |
| **Native HA** | Несколько процессов `zabbix_server` на **одной** БД. Живой сбор и триггеры — только у **одной** active-ноды; остальные **standby**. |
| **HANodeName** | Уникальное имя ноды HA. Без него сервер стартует **standalone**. |
| **NodeAddress** | `адрес:порт` ноды; фронтенд ходит на **активную** по записи в БД. |
| **Failover delay** | Сколько ждать, прежде чем standby станет active, если старая active исчезла молча. Диапазон **10 с – 15 мин**, дефолт **1 мин**. |
| **Standby** | Нода HA, которая **не** собирает данные, **не** слушает порты, почти не держит коннекты к БД. Живёт только HA-manager. |
| **Frontend** | PHP-UI + API. Данных мониторинга в нём нет — они в БД. Несколько копий фронта = несколько PHP-процессов на ту же БД. |
| **Zabbix proxy** | Посредник: собирает у хостов **своего** контура, буферизует, отдаёт серверу. Своя **отдельная** БД (не серверная!). |
| **Active proxy** | Прокси сам стучится на сервер (удобнее через firewall: исходящее из ЦОДа). |
| **Passive proxy** | Сервер стучится на прокси. |
| **Proxy group** | Группа прокси 7.0+: сервер сам раскладывает хосты и делает failover, если прокси молчит дольше failover period (дефолт **1 мин**, диапазон 10 с – 15 мин). |
| **ProxyBufferMode** | Куда прокси кладёт ещё не отгруженные данные: `disk` / `memory` / `hybrid`. Новые установки 7.0: **hybrid**. Режим `memory` при рестарте **теряет** буфер. |
| **ProxyOfflineBuffer** | Сколько часов прокси хранит данные, если сервер недоступен. |
| **Agent / Agent 2** | Агент на машине. Порт **10050**. Agent 2 — на Go, с плагинами (PostgreSQL, MongoDB, Redis и др.). |
| **Passive check** | Сервер/прокси **спрашивает** агента. Нужен доступ к 10050 хоста. |
| **Active check** | Агент **сам** забирает список item'ов и присылает значения. Список нод — в `ServerActive`. Для proxy group в active-режиме нужен агент **≥ 7.0**. |
| **Trapper** | Приём значений, которые **пушат** (`zabbix_sender`). Тот же порт **10051**. |
| **Java gateway** | Отдельный процесс для JMX. Порт **10052**. |
| **Web service** | Генерация PDF-отчётов (нужен Chrome). Порт **10053**. К HA сбора не относится. |
| **LLD** | Low-level discovery: сам нашёл диски/интерфейсы/поды и завёл item'ы. |
| **Template** | Набор item/trigger/LLD, который вешают на хосты. Без шаблонов вы утонете в ручной работе. |
| **PSK** | Общий секрет для TLS. Identity **не** секрет: его шлют открытым текстом. |
| **TLSConnect / TLSAccept** | Чем шифруем исходящее / что принимаем входящим: `unencrypted`, `psk`, `cert`. |
| **Vault (в Zabbix)** | Подтягивание секретов из HashiCorp Vault KV v2 или CyberArk. Zabbix только **читает**. |
| **Connector** | Поток item values / events наружу по HTTP NDJSON. Для Kafka вендор даёт отдельный **Kafka connector** (Go), это не брокер. |
| **Super Admin** | Учётка, которой можно всё, включая скрипты на сервере. Дефолт: пользователь `Admin`. |

## Основные элементы системы и зависимости

### Что входит в «Zabbix» (это несколько процессов, не один бинарь)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Server (active)** | Сбор (если без прокси), триггеры, history, action | Вертикально: процессы poller/trapper/db syncer на **одной** active-ноде. Горизонтально сбор — **прокси**, не «ещё один active server» |
| **Server (standby)** | Перехватить роль, если active умер | 1–2 штуки в других зонах. Они **не** делят нагрузку съёма |
| **Frontend** | UI и JSON-RPC API | Несколько реплик Deployment + LB. Состояние — в БД |
| **PostgreSQL (+ опционально TimescaleDB)** | Конфиг, history, trends, events, таблица HA-нод | Это **другое ПО**. Native HA Zabbix БД **не** кластеризует |
| **Proxy** | Съём «на месте», буфер при обрыве до сервера | По ЦОДам / сегментам. Внутри площадки — **proxy group** |
| **Agent 2** (предпочтительно) / agent | Метрики ОС и плагины | По числу машин (DaemonSet / пакет). Не кластер |
| **Java gateway** | JMX (Kafka, Camunda, Tomcat…) | Обычно 1–N рядом с Java-парком; это не HA сервера |
| **Web service** | PDF-отчёты | Stateless, по желанию |
| **Kafka connector** | Слить values/events в Kafka | Отдельный бинарь вендора, не часть `zabbix_server` |

### Официальные порты (менять можно, это контракт сети)

| Компонент | Порт | Назначение |
|---|---|---|
| Agent / Agent 2 | **10050/TCP** | Passive checks |
| Server / Proxy / Trapper | **10051/TCP** | Active proxy/agent, trapper, связь прокси↔сервер |
| Java gateway | **10052/TCP** | JMX |
| Web service | **10053/TCP** | Отчёты |
| Frontend | **80 / 443** | HTTP(S) UI и API |

Шифрование TLS **не** открывает новый порт: тот же 10050/10051 принимает и plaintext, и TLS. Firewall режет по адресам и политике `TLSAccept`, не «отдельным TLS-портом».

Исходящие TCP обычно явно не открывают. **NTP/chrony** на всех компонентах вендор называет *strongly recommended*: без общего времени триггеры и HA-heartbeat живут в кривой вселенной.

### Чего в Zabbix нет (частая путаница)

| Нужно системе | Это не Zabbix | Зачем помнить |
|---|---|---|
| Active-active сервер «как три Kafka-брокера» | Нет. Цитата HA: *Only one node can be active at a time* | Два `replicas: 2` без `HANodeName` = два сервера, дерущихся за одну БД, или два независимых мозга |
| Кворум Raft / replica-шарды history | Нет | History живёт в **PostgreSQL**. Упал диск БД без реплики и бэкапа — нет графиков и часто нет failover HA (heartbeat идёт **через БД**) |
| Кластер TSDB «как Prometheus replicas» | Другая модель | Prometheus: две независимые базы. Zabbix: одна БД, серверы по очереди |
| Озеро эталона / SoT клиентов | Нет | Zabbix хранит *метрики наблюдения*, не клиентские карточки |
| Шина Kafka / процессы Camunda | Нет | Может *наблюдать* их и *стримить* events в Kafka (connector) |
| SIEM / syscall | Wazuh / Falco | Другой контур, другая команда |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS — GnuTLS/OpenSSL 1.2/1.3 |
| Порог RTT между ЦОДами | Нет | Есть failover delay (дефолт 1 мин) и timeout item'ов. Миллисекунд в доке **нет** |
| Гарантия «терабайты озера влезут» | Нет | Диск считают от **NVPS × retention × ~90 байт**, не от объёма клиентских данных |
| Официальный Kubernetes Operator на 7.0 | Нет | Образы есть. Оператор OpenShift в публичных мануалах — линии 5/6 |
| Elasticsearch как боевое history | Док: **experimental**, только history | В прод этого файла не кладём |

### Зависимости окружения (обязательны)

- **ОС сервера:** UNIX. Цитата requirements: Windows как платформа *server* не заявлена. Агенты — Linux и Windows (agent 2: Windows 10 / Server 2016+).
- **СУБД сервера:** одна из поддерживаемых. В этом документе — **PostgreSQL 13–18** (18.x с 7.0.20). Oracle с 7.0 **deprecated**. Для сжатия партиций history/trends вендор просит **TimescaleDB Community Edition** (линейка **2.13.0–2.29.X** на 7.0.30; 2.29.X — с 7.0.30). Community Edition — отдельная лицензия Timescale, не «просто расширение из Debian».
- **СУБД прокси:** SQLite3 **или** MySQL/PostgreSQL. **Нельзя** указать ту же БД, что у сервера. In-memory SQLite (`:memory:`) официально запрещён (мультипроцесс).
- **Frontend:** PHP **8.0–8.5** (8.5.x с 7.0.25), Apache 2.4+ или Nginx 1.20+, расширения pgsql/gd/bcmath/mbstring/xml/…; для SAML — php-openssl.
- **Сеть:** сервер должен достучаться до БД; прокси — до сервера (active) или наоборот (passive); агенты — по выбранной модели. Stretch «сервер в ЦОД-1, агенты в ЦОД-3 без прокси» упирается в RTT item timeout, не в магию продукта.
- **Kubernetes (у вас заявлен):** CSI под PostgreSQL (RWO, не «общий NFS на два primary»); стабильные DNS-имена для `HANodeName`/`NodeAddress`; NetworkPolicy на 10051/10050/443. Frontend — несколько подов; **server HA — не Deployment с общим PVC**.
- **Часы:** синхронизация времени на server, proxy, agent, БД, K8s-нодах.
- **Канал алертов:** SMTP/webhook/on-call. UI без action — музей триггеров.
- **PKI или PSK**, если включаете TLS (в проде включать).

### Как Zabbix стыкуется с вашей архитектурой

```
Хосты ЦОД-1 (агенты, SNMP, HTTP checks интеграций)
        │  active checks / SNMP
        ▼
   Proxy group ЦОД-1  ── буфер ──┐
                                 │  :10051  TLS
Хосты ЦОД-2                      ▼
   Proxy group ЦОД-2  ────────►  Zabbix server HA
                                 │  active  (ЦОД-A)
Хосты ЦОД-3                      │  standby (ЦОД-B)
   Proxy group ЦОД-3  ────────►  │
                                 ▼
                          PostgreSQL (+ TimescaleDB)
                          ← единственное «общее место правды»
                                 ▲
                          Frontend × N  :443
                                 │
                                 ▼
                          on-call / webhook

Опционально: connector → Kafka connector → ваш Kafka
Опционально: секреты макросов/БД из Vault KV v2
```

Zabbix **не** ходит в госслужбы за бизнес-данными и **не** заменяет интеграционное API. Он проверяет, что API **живо**, что лаг/ошибки в допустимых пределах (если вы такие item'ы завели), что Kafka/Camunda/K8s-ноды отвечают. Payload ответа ведомства в item класть не надо: это ПДн и раздувание history.

Стык с **Prometheus** (он у вас уже описан): два полных контура «снимаем всё и орём обо всём» = двойные инциденты и спор, кто прав. Честное разделение ролей нужно **до** установки, не после первой ночи дежурства. Типичная (не единственная) нарезка: Prometheus — кардинальность микросервисов и K8s `/metrics`; Zabbix — железо, SNMP, ICMP, сертификаты, «порт ведомства открыт», эскалации для NOC. Это допущение, не требование вендора.

## Краткие вводные

### Зачем вам Zabbix в этой архитектуре

У вас Kubernetes, 3 ЦОДа, 30+ интеграций, Kafka, Camunda, ожидание непрерывной работы и **нет замеров нагрузки**. Prometheus закрывает pull-метрики приложений. Остаётся слой, который хорошо делает:

1. Доступность «снаружи процесса»: ICMP, TCP, HTTP, SNMP железа ЦОДа.
2. Единое окно проблем с эскалациями (не PromQL в Explore).
3. Буфер сбора на площадке (proxy), когда канал до «мозга» моргнул.
4. Авторегистрация/LLD парка агентов.

Без этого «24/7» остаётся надеждой: вы узнаете, что интеграционное API молчит, от пользователя или от тикета ведомства.

### Как устроена отказоустойчивость (идея, не магия)

Это **не один механизм**. Путать native HA сервера с HA базы и с proxy group — главная ошибка.

**1) Zabbix server (native HA)**

Несколько `zabbix_server` + **одна** БД. Active пишет heartbeat (last access) каждые **5 секунд**. Standby смотрит на этот timestamp.

| Что падает | Что происходит по документации |
|---|---|
| Active корректно остановился и успел сменить статус на stopped | Другая нода поднимается **примерно за 5 с** |
| Active исчез (kill -9, сеть, ЦОД) | Standby ждёт **failover delay + 5 с** (дефолт delay = 1 мин) |
| Нет ни одной standby | Failover **некуда**. Это standalone с красивым именем |
| Связь active с БД потеряна дольше `failover delay − 5 с` | Active **обязан** бросить работу и уйти в standby. Мозг без БД не живёт |
| БД мертва / нет кворума PostgreSQL | Heartbeat не пишется. Native HA **не из чего** выбрать лидера. Сбор на прокси может ещё идти в буфер |

Вендор прямо: решение *opt-in*, *will work across sites*, *does not have specific requirements for the databases that Zabbix recognizes*. Перевод на человеческий: **сервер** умеет разъехаться по площадкам; **БД** вы обеспечиваете сами.

Standby **не слушает** 10051. Нельзя повесить TCP-балансировщик «на все HA-поды» и ждать, что пассивный примет агентов. Прокси и агенты получают **список имён нод** (`Server=` через запятую для passive, через `;` для active proxy / `ServerActive`).

Frontend: **не** прописывать `address:port` сервера в `zabbix.conf.php` при HA — он читает активную ноду из таблицы в БД.

**2) База**

Падение PostgreSQL = нет UI, нет новых history на сервере, нет HA-выбора. Прокси с `ProxyOfflineBuffer` продолжают копить (пока хватает часов и диска). Это **деградация сбора**, не «Zabbix пережил ЦОД».

Реплика PostgreSQL и бэкап — отдельный контур (Patroni / CloudNativePG / вендорная СУБД). В этом файле цифр «синхронная реплика при вашем RTT» **нет**: RTT неизвестен, а sync replica с большим RTT убивает NVPS.

**3) Прокси и proxy group**

Сбор живёт ближе к целям. Обрыв ЦОД↔мозг: данные в буфере прокси, не «дырка навсегда», если buffer и диск посчитаны.

Proxy group (7.0+): хосты вешают **на группу**, не на один прокси. Упал прокси — хосты раскидывают. Агент 7.0+ в active mode должен уметь достучаться **до всех** членов группы (firewall), иначе failover active checks зависнет. Passive: в `Server=` агента перечислить все прокси группы.

Прокси **не** заменяет упавший сервер: он не считает глобальные триггеры и не шлёт ваши action'ы.

**4) Frontend**

Падение UI ≠ падение сбора. Один под frontend — SPOF **просмотра и API автоматизации**. Сессии PHP по умолчанию локальные: без sticky на LB или общего session store дежурный будет «вылогиниваться» между репликами.

**5) Агенты и цели**

Упал агент = слепой хост (`agent.ping` / `ZBX_NOTSUPPORTED`). Упал Java gateway = слепой JMX, не весь Zabbix.

### Как устроено масштабирование

Четыре оси, которые вендор реально разделяет:

1. **Меньше NVPS** — главный рычаг. Реже interval, не плодить LLD «по каждому поду каждую метрику как в Prometheus без relabel».
2. **Вертикаль active-сервера** — больше pollers/trappers/препроцессоров, БД на **отдельных** машинах (для Large/Very large вендор это *highly recommended*).
3. **Прокси** — разрезать парк по ЦОДам и по типу съёма (SNMP отдельно от agent). Это и масштаб, и blast radius.
4. **БД** — TimescaleDB Community: партиции + compression, housekeeper **дропает партиции**, если включены Override history/trend period **и** internal housekeeping. Иначе партиции копятся, а в UI висят предупреждения.

Ориентиры железа из requirements — **примеры старта**, не смета вашего прода. Вендор прямо: *each installation is unique*, бенчмарк на staging обязателен.

| Размер (пример вендора) | Метрик* | CPU | RAM | Смысл |
|---|---|---|---|---|
| Small | 1 000 | 2 | 8 ГиБ | Стенд / маленький контур |
| Medium | 10 000 | 4 | 16 ГиБ | Начало боя |
| Large | 100 000 | 16 | 64 ГиБ | БД лучше отдельно |
| Very large | 1 000 000 | 32 | 96 ГиБ | БД отдельно |

\*1 «метрика» в этой таблице = 1 item + 1 trigger + 1 graph. Amazon EC2 в таблице — иллюстрация класса, не требование облака.

Формулы диска (байты; ~90 байт/значение — ориентир **MySQL**, для PostgreSQL «может отличаться»):

```text
history ≈ days × (items / refresh_rate) × 24 × 3600 × ~90
trends  ≈ days × (items / 3600) × 24 × 3600 × ~90
events  ≈ days × events_per_sec × 24 × 3600 × (~330 + tags×100)
config  ≈ обычно ≤ 10 МБ
```

Пример из доки: 3000 item / 60 с = 50 NVPS, 30 дней history ≈ 10.9 ГиБ. Нагрузки у вас нет → **нельзя** честно сказать «N ТБ под терабайты озера». Озеро клиентов и history Zabbix — разные объёмы. Логи интеграций в item типа `log` раздувают диск быстрее чисел.

Текст/лог: ориентир вендора **~500 байт** на значение, «точно предсказать нельзя».

### Безопасность самого Zabbix

Компрометация Super Admin = карта инфраструктуры, возможность **глобальных скриптов** на сервере, доступ к макросам (пароли SNMP, community, иногда реквизиты). Это не «просто графики».

Официально и проверяемо:

- Первый вход: пользователь **`Admin`**, пароль **`zabbix`**. Вендор: сменить **сразу** после первого логина.
- После 5 неудачных логинов UI **молчит 30 секунд** (грубая защита от перебора, не WAF).
- Дефолт аутентификации — **internal**. Пароль: минимум 8, обрезка после 72 символов; сложность включается в Users → Authentication.
- TLS 1.2/1.3, PSK или сертификаты. PSK identity — не секрет. Для PFS на PSK: GnuTLS или OpenSSL **≥ 1.1.0**. LibreSSL для agent 2 **не** поддерживается.
- Агент на той же машине, что server/proxy, лучше **другим UNIX-пользователем**: иначе агент читает `DBPassword` из конфига сервера.
- Глобальные скрипты на сервере: резать `EnableGlobalScripts=0`, если не нужны. На прокси remote commands по умолчанию выкл. На агенте `system.run` по умолчанию выкл.
- HTTP auth фронта можно выключить: `$ALLOW_HTTP_AUTH=false` в `zabbix.conf.php` (setup.php параметр сотрёт).
- Секреты макросов и учёт БД — в Vault KV v2 (у вас есть отдельный документ по Vault). Между server и proxy при vault-макросах **нужен TLS**, иначе сервер пишет warning.
- Frontend в iframe с другого домена — same-origin; страница **того же** домена внутри фрейма получит JS-доступ к UI.
- Стриминг connector'ом: это ещё один выход ПДн/топологии. URL, TLS verify, не «в Kafka без ACL».

«Поднять compose и выдать 80/Admin/zabbix в сеть» — новый периметр, не мониторинг.

Лицензия с 7.0: **AGPLv3**. Для контура с госинтеграциями это юридический факт, не «опенсорс как Linux». Продуктовому/правовому блоку нужно явно решить, приемлемо ли. Этот файл не заменяет юрзаключение.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Self-hosted Zabbix 7.0.30 LTS**, не Zabbix Cloud и не 7.4.14. Облако вендора в схеме с тремя своими ЦОДами не предполагалось.
2. **Бэкенд — PostgreSQL** (LTS из диапазона 13–18; разумный якорь — **16**, пока у вас нет стандарта). MySQL не запрещён; Oracle не берём (deprecated).
3. **TimescaleDB Community** на проде для history/trends, если retention больше «нескольких недель» или NVPS выйдет за стенд. На тесте достаточно чистого PostgreSQL.
4. **Прод крутится в Kubernetes** образами вендора. Community Helm (например, чарты с Artifact Hub) — опция команды, **не** сертификат вендора на 7.0.30.
5. **Три ЦОДа = три зоны отказа.** Пока RTT неизвестен, честный сбор — **прокси в каждом ЦОДе**, а не один server, который poll'ит три площадки вслепую.
6. **Цель отказа: пережить 1 ЦОД** для *сбора* (прокси + buffer) и для *обработки*, только если жива БД (реплика/failover PostgreSQL — отдельное решение). Пережить 2 из 3 ЦОДов native HA **не обещает**.
7. **Нагрузка неизвестна** — поэтому **нет** цифры «N ядер и M ТБ PGDATA». Есть сигналы (queue, NVPS, cache, housekeeper, proxy buffer) и рычаги (interval, прокси, процессы, TimescaleDB).
8. **«Система 24/7» ≠ «ни один item не пропущен».** Прокси буферизует; триггеры на сервере в это время могут не считаться.
9. **On-call и media type будут.** Иначе HA бессмысленна.
10. **Корпоративный PKI есть или будет.** PSK допустим для агентов, если PKI не успевает; identity не класть секреты.
11. **Разделение с Prometheus/Grafana/Wazuh** согласовано: кто алертит диск, кто — `CrashLoop`, кто — SNMP UPS.
12. **Тестовый стенд изолирован.** На нём допустимы один server, SQLite-прокси, HTTP, пароль не-`zabbix` но простой. В прод это не копируем.
13. **Юристы приняли AGPLv3** (или выбрали другой продукт). Если нет — этот документ не запускают в прод.
14. **Интеграционное API и Kafka** — цели мониторинга и опциональный sink connector'а, не часть инсталлятора Zabbix.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «накатили образы и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потери между ЦОДами** (p50/p95/p99, все пары) | Item timeout, HA heartbeat через БД, sync-реплика PostgreSQL. Порога в мс у Zabbix **нет**. Stretch БД без замера — лотерея. |
| **Один Kubernetes на 3 ЦОДа или три кластера** | От этого зависит: одни Service DNS для HA-нод или три входа + прокси. |
| **Где живёт PostgreSQL при падении ЦОДа** | Native HA сервера **не** спасает мёртвую БД. Это главный SPOF, о котором в слайде «поставили Zabbix HA» часто забывают. |
| **Что именно снимаете** (только ноды K8s? SNMP? 30 HTTP ведомств? логи?) | Разный NVPS, retention, нужны ли Java gateway и SNMP trap-контур. |
| **Срок хранения history/trends и 152-ФЗ** | Формула диска и состав item'ов (не класть ПДн в текст item). |
| **Куда торчит 443 / 10051** | Публичный UI с `Admin`/`zabbix` = инвентаризация сети для атакующего. |
| **Кто принимает проблемы** | Без media HA сервера — зелёный под. |
| **Совместимость версий** | Прокси = версия сервера. Passive agent в proxy group — версия как у прокси. Active agent для group — ≥ 7.0. |
| **Матрица с Prometheus** | Иначе два pager'а на один диск. |
| **Закрытый контур / свои registry** | Образы Docker Hub должны быть зеркалом. |
| **Лицензия Timescale Community vs Apache** | Без Community нет официально требуемого compression path. |
| **AGPLv3** | Модификации, отдаваемые как сетевой сервис, могут требовать раскрытия исходников — это не «деталь README». |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **7.0.30** на server, frontend, proxy, agent 2, java gateway. Не смешивать 7.0 и 7.4 «на глаз».
2. Поднять **PostgreSQL** (на тесте можно рядом; на проде — отдельный контур с бэкапом). Прогнать schema Zabbix, не «пустой postgres и надежда».
3. Поднять **один** server, сменить `Admin`/`zabbix`, закрыть UI сетью.
4. Поставить **хотя бы одну** цель не «сам себя»: агент на ноде или HTTP check. Проверка: Latest data растёт, триггер умеет стать PROBLEM и OK.
5. Подключить media и одно action. Убедиться, что уведомление **дошло**.
6. Включить TLS (хотя бы PSK) на 10051/10050 **до** массовой раскатки агентов.
7. Только потом — шаблоны на Kafka/Camunda/K8s, прокси по ЦОДам, HA-нода, TimescaleDB.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** увидеть host/item/trigger/action, UI, API, один агент. **Не** цель: доказать отказ ЦОДа, NVPS интеграций и proxy group.

Два официальных минимальных пути (выберите один):

**Путь A — пакеты Linux** (быстрее понять файлы конфига):

- Инструктор с https://www.zabbix.com/download : версия **7.0**, ваша ОС, PostgreSQL, nginx или Apache.
- Компоненты на одной машине: server + frontend + agent 2 + PostgreSQL.
- Сразу сменить пароль `Admin`. Не публиковать :80.

**Путь B — официальный Docker Compose** (ближе к образам прода):

- Клонировать `zabbix-docker`, ветка **7.0**, `compose_pgsql.yaml` (или Makefile из README репозитория).
- Это **быстрый** путь вендора, не топология 3 ЦОДов.

На Kubernetes для теста: один Deployment server (`HANodeName` не задавать), один frontend, один PostgreSQL с PVC, опционально DaemonSet agent 2. Не включать `replicas: 2` у server «чтобы как в проде» без HA-параметров: получите двух писателей или сломанный старт.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| HA server | выкл (standalone) | Нет требования пережить выкат |
| Прокси / proxy group | выкл | Нечего разносить по ЦОДам |
| TimescaleDB | выкл | NVPS стенда не греет housekeeper |
| TLS | можно HTTP внутри изолированной сети | Иначе команда утонет в PKI раньше, чем в триггерах |
| Java gateway / web service | выкл, пока нет JMX/PDF | Лишние движущиеся части |
| Retention | короткая history | Нет боевой истории |
| Сложность паролей / SAML | после смены дефолта | Сначала увидеть продукт |
| Connector → Kafka | выкл | Не цель стенда |

#### Чего на тесте **не** стоит упрощать

- Версия **7.0.30** (или явный пин 7.0.x, но один на все компоненты).
- Смена **`Admin` / `zabbix`** в день установки.
- Хотя бы один item не про localhost-сервер и одно дошедшее уведомление.
- Понимание: успешный график CPU **не** доказывает, что standby подхватит роль и что прокси переживёт обрыв до ЦОД-мозга.
- Не включать `AllowKey=system.run` «чтобы удобно отладить».
- Не класть в item текст ответов интеграционного API «для отладки».

#### Сильные стороны такой схемы

- Поднимается за часы, совпадает с официальным download/compose.
- Дешево показывает шум шаблонов «из коробки» на *вашем* Linux.
- Standalone официально штатный режим (HA — opt-in).

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет буфера прокси, нет доказанной ёмкости БД.
- Привычка compose-all-in-one уезжает в прод вместе с одним PostgreSQL без бэкапа.
- HTTP и дефолтный Super Admin на тесте, который «чуть-чуть торчит» — уже инцидент.

Практическая рекомендация: препрод = маленький **прод-профиль** (2 HA-ноды server, отдельный PostgreSQL с бэкапом, 1 proxy group из 2 прокси, TLS, свой пароль/SSO, один реальный шаблон приложения), даже без боевого NVPS.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты озера» **нет**. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Zabbix плохо переживает **три независимых Super Admin-правды** и плохо переживает **один poller на три ЦОДа без прокси**.

**Вариант A — мозг (server HA + PostgreSQL) в одном логическом контуре, съём локальный.**

- В каждом ЦОДе **proxy group** (≥2 прокси, anti-affinity по нодам). Хосты ЦОДа мониторятся группой.
- Active proxy: исходящие 10051 к списку `HANodeName` серверов.
- Server HA: минимум **2** ноды (active + standby) в **разных** ЦОДах, если сеть до БД стабильна; третья — по желанию (лишняя standby не ускоряет съём).
- PostgreSQL: отдельный HA-контур. Пока RTT не измерен — **не** обещать sync-stretch на 3 площадки. Честные развилки: (A1) primary+sync replica в двух ЦОДах после замера; (A2) primary в одном ЦОДе + async replica + прогнанный failover (RPO > 0).
- Frontend ≥ 2 в разных зонах, HTTPS, SSO, sticky или общий session store.

Это целевой рисунок «3 ЦОДа в одном городе»: сбор переживает падение канала до мозга (buffer), обработка — пока жива БД.

**Вариант B — три независимых Zabbix.**

Три БД, три UI, три набора триггеров. Имеет смысл только при жёсткой изоляции контуров. Обычно хуже для on-call.

**Вариант C — один server без прокси, poll напрямую в три ЦОДа.**

Допустимо только если RTT стабильно меньше item timeout **и** вы приняли, что обрыв межЦОД = массовый PROBLEM. Для «высокой нагрузки без замеров» это плохая ставка.

**Пока топология K8s и место БД не зафиксированы, нельзя честно выбрать A1 vs A2.** Дальше — общее для A.

##### Сильные / слабые стороны (A, прокси на площадках + native HA)

| Сильное | Слабое |
|---|---|
| Официальная модель distributed monitoring | Мозг всё равно упирается в PostgreSQL |
| Buffer на прокси при аварии канала | Триггеры/action в это время могут молчать |
| Proxy group закрывает падение одного прокси | Агенты 7.0+ должны достучаться до **всех** прокси группы |
| HA server переживает падение active-процесса/площадки *если БД жива* | Standby не слушает порты; кривой LB на 10051 ломает модель |
| Один UI, одна матрица эскалаций | Ошибка шаблона сразу на всех трёх ЦОДах |

##### Сильные / слабые стороны (мозг и БД в одном ЦОДе)

| Сильное | Слабое |
|---|---|
| Нет stretch PostgreSQL | Падение этого ЦОДа = нет обработки, пока не поднимете БД+server в другом; остаются только буферы прокси |
| Проще кворум БД | RTO надо **замерить** restore/failover, не написать в слайде «HA есть» |
| | Frontend в мёртвом ЦОДе бесполезен — реплики UI нужны в живых |

##### Слабое место любого решения без замера RTT

Документация **не задаёт** миллисекунды. Утверждение «три ЦОДа в одном городе, значит БД можно размазать синхронно» — **непроверенное**. Мерить путь **прокси → server:10051**, **server → PostgreSQL**, **frontend → PostgreSQL**, не ping ICMP «на всякий случай».

#### Server HA (ядро отказоустойчивости *обработки*)

- На каждой ноде: уникальный `HANodeName`, корректный `NodeAddress` (тот адрес, по которому фронт достучится до **этой** ноды, когда она active).
- Прокси: все имена нод в `Server=` (`,` для passive, `;` для active).
- Агенты, которые ходят **на сервер напрямую** (минуя прокси): `Server=` / `ServerActive=` со всеми нодами; для active HA-нод разделитель `;`.
- Failover delay: дефолт 1 мин часто ок. Ставить 10 с на WAN с джиттером — риск флаппинга. Менять через `zabbix_server -R ha_set_failover_delay=...`.
- Upgrade major: **остановить все ноды**, бэкап БД, апгрейд **одной** в standalone (`HANodeName` закомментировать), дождаться «server is running» в System information, вернуть HA, потом остальные. Minor: по очереди, начиная с той, что уже жива.
- Мониторить сами ноды: `zabbix[cluster,discovery,nodes]`, Reports → System information, `ha_status`.

**Слабое место:** люди ставят два пода server в одном StatefulSet без разных `HANodeName` / с общим volume — это не HA.

#### PostgreSQL / TimescaleDB (ядро отказоустойчивости *данных*)

- БД **не** в том же поде, что server.
- Бэкап + **прогнанный restore**. Реплики server не заменяют pg_basebackup/PITR.
- TLS к БД: `DBTLSConnect=verify_full` (сервер) и галки Verify на фронте; роли least privilege (`zbx_srv` / `zbx_web` в гайде шифрования).
- TimescaleDB: Override item history/trend period **и** Enable internal housekeeping для history/trends — иначе партиции не дропаются. Сжатие — Community Edition, как пишет requirements.
- `work_mem` вендор предлагает поднимать с дефолта 4 МБ на больших инсталляциях — по плану запросов, не «на всякий случай 1 ГБ».
- Housekeeper на огромной history без партиций = ночные тормоза. Это сигнал переходить на TimescaleDB/партиции, не крутить `HousekeepingFrequency` в ноль и забывать.

#### Прокси

- Своя БД: SQLite3 на маленьком прокси (PVC!), PostgreSQL — если прокси крупный или SQLite упёрся в писателей.
- Новые 7.0: `ProxyBufferMode=hybrid` + ненулевой `ProxyMemoryBufferSize`. Не оставлять `memory` на проде: рестарт пода = дырка в history.
- `ProxyOfflineBuffer` ≥ времени, за которое вы реально чините канал до мозга (часы). Дефолт смотреть в `zabbix_proxy.conf` вашей сборки, не гадать в инциденте.
- Версия прокси = версия сервера.
- Java/SNMP/внешние проверки, которые должны пережить failover внутри group: **одинаковое** окружение на всех членах группы (док proxy group это подчёркивает).

#### Frontend

- HTTPS, не 80 снаружи.
- Несколько реплик, не в одной зоне.
- SSO (SAML: в доке есть Entra ID / Okta / OneLogin) для людей; API-токены для автоматизации, не пароль Super Admin в CI.
- При HA server — пустой адрес сервера в `zabbix.conf.php`.
- Секреты БД фронта: Vault или Secret, не git. Кэш `$DB['VAULT_CACHE']` — осознанно (TTL, PrivateTmp).

#### Съём: агенты, SNMP, HTTP, JMX

- Предпочитать **active checks**: исходящие из ЦОДа проще, чем открыть 10050 всех подов наружу.
- Agent 2 на Linux; плагины PostgreSQL/Redis/Mongo — вместо самописных UserParameter, где плагин закрывает задачу.
- Kubernetes: официальный helm **мониторинга** K8s (ZT/kubernetes-helm) + шаблоны HTTP, либо Prometheus как источник (в Zabbix есть discovery via Prometheus — не дублировать те же ряды без нужды).
- HTTP checks 30+ ведомств: интервал и timeout завязать на **известные лаги** интеграционного API, иначе вечный PROBLEM.
- Java gateway — только если JMX реально нужен и не закрыт Prometheus JMX exporter (снова матрица).

#### Безопасность прода

| Слой | Правило |
|---|---|
| Дефолты | Нет `Admin`/`zabbix`; нет Guest, если не нужен; нет открытого 80 |
| Канал 10050/10051 | `TLSConnect`/`TLSAccept` не `unencrypted`; PSK или cert |
| БД | TLS `verify_full`, раздельные роли, нет `trust` в pg_hba для сети ЦОДов |
| Сеть | NetworkPolicy: 10051 — прокси и HA-ноды; 10050 — только свой прокси/сервер; 443 — IdP и операторы |
| Скрипты | `EnableGlobalScripts=0`, если нет регламента; агент не под пользователем server |
| Секреты | Vault KV v2 для макросов/DB; TLS server↔proxy обязателен при vault-макросах |
| Аудит | Срок audit log + партиции (в 7.0 есть подготовка auditlog к partitioning) |
| Connector | Только нужные tag filter; mTLS/ACL на приёмнике Kafka |
| At-rest | Шифрование томов PGDATA и PVC прокси |

##### Сильные / слабые стороны (TLS + RBAC + SSO)

| Сильное | Слабое |
|---|---|
| Один порт, TLS опционален по соединению | Легко оставить часть агентов plaintext «на время» |
| PSK проще сертификатов на тысячах железных SNMP-не-агентов | PSK identity открытым текстом; ротация PSK — ручная дисциплина |
| Сертификаты лучше привязывают identity | Нужен PKI и не забыть `TLSAccept` |
| SAML закрывает людей | API и агенты SSO не пользуются — отдельные токены/PSK |
| Vault не держит пароль БД в git | Зависимость: Vault лёг → макросы не обновятся до `secrets_reload` / cache |

#### Kubernetes-специфика прода

- Server HA: **отдельные** поды со стабильным DNS (`zabbix-server-a`, `zabbix-server-b`), не случайные ReplicaSet-имена в `HANodeName`.
- Не монтировать PGDATA как `emptyDir`.
- PDB: не снять сразу оба HA-сервера и не снять всю proxy group одной зоны.
- Topology spread: два прокси группы не на одной ноде.
- Ресурсы server: лимиты с запасом под пик housekeeper и препроцессинг. OOM active-ноды = failover через delay, не «мгновенно».
- Rolling: для major — процедура HA из доки, не `kubectl rollout` всех нод сразу.
- Agent 2: DaemonSet + hostNetwork **только если** иначе не снять сеть хоста; иначе больше attack surface.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть: 10051, PostgreSQL, 443. Решение A1/A2/C.
2. Поднять PostgreSQL с бэкапом и прогнанным restore. Решить TimescaleDB.
3. Один server standalone, схема БД, сменить Super Admin, HTTPS, NetworkPolicy.
4. Включить TLS. Поставить agent 2 на пару нод. Прогнать PROBLEM/OK и action.
5. Ввести proxy group в одном ЦОДе, перевесить хосты на группу, убить один прокси — хосты должны переехать.
6. Вторая HA-нода server, `HANodeName`, пустой адрес в frontend. Убить active — сверка `ha_status` и времени failover.
7. Раскатать прокси на остальные ЦОДы. Шаблоны на реальное ПО (Kafka/K8s/интеграции) с разумным interval.
8. Нагрузить хотя бы синтетикой, снять NVPS, queue, CPU БД, размер PGDATA. По результату — процессы сервера и класс железа (таблица вендора — старт, не финал).
9. SSO, Vault, connector в Kafka — если нужны.
10. Прогон «ЦОД недоступен» на препроде: изолировать зону прокси; изолировать active-server; отдельно — учения по БД. Зафиксировать, что алертится, а что только буферизуется.

Без пункта 10 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Прокси+buffer в каждом ЦОДе; proxy group ≥2; server HA ≥2 ноды; PostgreSQL с бэкапом и понятным failover; цель — 1 ЦОД для сбора; обработка — пока жива БД |
| Производительность / масштаб | Не требуется | NVPS как единица нагрузки; прокси режут съём; вертикаль только active-ноды; TimescaleDB на длинной history; не дублировать кардинальность Prometheus |
| Безопасность | Смена `Admin`/`zabbix`; UI не в интернет | TLS 10050/10051; HTTPS; SSO; нет plaintext DB; Vault или эквивалент; скрипты выкл; матрица с другими алертами |

**Не готов к проду**, если: пароль `zabbix`, HTTP UI снаружи, два server без `HANodeName` на одной БД, прокси в той же БД что server, `ProxyBufferMode=memory` на единственном буфере площадки, нет бэкапа PostgreSQL, все прокси в одном ЦОДе «мозга», RTT неизвестен а PostgreSQL уже stretch-sync, версии прокси ≠ сервер, Zabbix назначен SoT клиентских данных, тот же набор алертов без договорённости с Prometheus/Wazuh.
