# SonarQube Server 2026.1.5 LTA — развёртывание и настройка

Версия для прода: **SonarQube Server 2026.1.5** (Long-Term Active / LTA; патч 7 августа 2026).  
На дату подготовки документа это текущий LTA-патч линии 2026.1. Активная поддержка LTA — до 30 января 2027, security-фиксы — до 2 августа 2027 (по таблице endoflife.date, сверка 7 августа 2026).

Latest на ту же дату: **2026.4.1** (7 августа 2026). Официальный Helm-чарт `sonarsource/sonarqube` / `sonarqube-dce` **2026.4.1** ставит именно Latest, не LTA. Community Build (бесплатная линейка, это уже **не** «Community Edition») на странице загрузок: **26.8.0.126808**; чарт 2026.4.1 по умолчанию тянет Community **26.7.0.124771**.

Документация LTA: https://docs.sonarsource.com/sonarqube-server/2026.1/  
Helm: https://artifacthub.io/packages/helm/sonarqube/sonarqube и `.../sonarqube-dce`  
Образы: линейка `sonarqube` на Docker Hub / зеркале вендора; Community — отдельный тег/флаг `community.enabled=true`.

Этот текст — не мануал «скопируй values.yaml», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

SonarQube **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API). Ниже — как поставить платформу статического анализа кода на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это не замена WAF, Falco, Wazuh и не «кнопка качество включена».

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **SAST** | Статический анализ: смотрит **исходный код** в момент сборки, не то, что процесс делает в рантайме. |
| **SonarQube Server** | Коммерческий продукт (Developer / Enterprise / Data Center). Лицензия **на инстанс в год** от объёма **LOC**. |
| **SonarQube Community Build** | Бесплатная отдельная линейка. Не путать с Server. У Community **нет** LTA: поддерживается только свежий релиз. |
| **LTA (Long-Term Active)** | «Долгая» линейка Server: первый релиз года. Для прода с ожиданиями «без сюрпризов» обычно берут её, а не Latest. |
| **Latest** | Промежуточный релиз каждые ~2 месяца. После следующего Latest стандартная поддержка предыдущего **кончается**. |
| **LOC (Lines of Code)** | Лицензионная единица Server: сколько строк кода инстанс имеет право анализировать. Не «терабайты озера». |
| **Scanner (сканер)** | Программа **в CI** (Maven/Gradle/CLI/.NET/npm…). Она сканирует репозиторий и **отправляет отчёт** на сервер. Сервер сам репозиторий с диска разработчика не читает. |
| **Quality Gate** | Порог «можно сливать / нельзя»: покрытие, баги, уязвимости. В коммерческих редакциях умеет **блокировать merge** PR. |
| **Web process** | Процесс UI и REST API. Принимает людей и отчёты сканеров. |
| **Compute Engine (CE)** | Фоновый движок: берёт отчёт сканера из очереди и превращает его в issues/метрики. Узкое место «сканы зависли в очереди». |
| **Background task** | Задача в очереди CE. Смотреть: *Administration → Projects → Background Tasks* (`pending_count` / `pending_time`). |
| **CE worker** | Сколько отчётов CE обрабатывает параллельно. Менять число — **Enterprise и выше**, в UI. На DCE число **глобальное**, на каждом application node оно **повторяется**. |
| **Elasticsearch / Search node** | Поисковый индекс issues и кода. В Developer/Enterprise он **вшит в тот же процесс**. В DCE — **отдельные** search-ноды, это отдельный ES-кластер. |
| **Application node** | Нода DCE с Web + CE. Масштаб «больше одновременных сканов и UI» = больше этих нод. |
| **DCE (Data Center Edition)** | Единственная редакция Server, в которой вендор даёт **кластер и HA** самого SonarQube. |
| **Hazelcast** | Встроенная шина между application nodes. Ставить Hazelcast отдельно **не нужно**. |
| **JWT** | Токен сессии в cookie. Поэтому балансировщику **не** нужны sticky sessions — так написано в требованиях DCE. |
| **H2** | Встроенная файловая БД. С 2026.1 Helm **больше не кладёт PostgreSQL в чарт**. H2 — только тест. В проде **запрещена** вендором. |
| **JDBC** | Строка подключения к внешней БД (`jdbc:postgresql://…`). В Helm 2026.1+ это обязательный `jdbcOverwrite.*`. |
| **Force user authentication** | «Без логина нельзя». По умолчанию **включено**. Выключение открывает кусок API анонимно — список есть в доке. |
| **Token (`sonar.token` / `SONAR_TOKEN`)** | Ключ для сканера и API вместо пароля. `sonar.login`/`sonar.password` помечены как deprecated. |
| **JIT / SCIM** | JIT — пользователь создаётся при первом входе через IdP. SCIM — автосинхронизация пользователей/групп (Entra/Okta: **Enterprise+**). |
| **sonar-administrators** | Встроенная группа админов. Вендор **настоятельно** советует переименовать: при синхронизации групп с IdP это типичный путь захвата. |
| **Quality profile** | Набор правил языка (Java, Python, …). |
| **Branch / PR analysis** | Анализ веток и pull request, не только `main`. Это **Developer+**, в Community Build этого фокуса нет. |
| **PVC / RWO** | Диск пода. Search-ноды без постоянного диска после рестарта **теряют индекс**. Access mode в чарте — `ReadWriteOnce`. |
| **vm.max_map_count** | Лимит ядра Linux на mmap. Для ES в доке 2026.1: **≥ 524288** (не путать со старым 262144 из части гайдов Docker). |
| **High disk watermark** | ES при ~90% диска начинает экономить, при **95%** может закрыть индексы на запись. Поэтому «10% свободного диска» — не пожелание, а порог движка. |
| **Active-Cold Standby** | Официальный пример DR: второй кластер **холодный**, БД реплицируется, трафик переключается. **Не** Active/Active: вендор прямо пишет, что read-only реплика БД для живого SonarQube **не поддерживается**. |
| **Forced Elasticsearch reindex** | После failover Kubernetes-кластера вендор требует **принудительную переиндексацию ES**. UI может встать, данные в PostgreSQL живы — индекс надо отстроить заново. |

## Основные элементы системы и зависимости

### Что входит в «одно ПО» (и что — нет)

SonarQube — это **сервер отчётов**, не сканер на каждой ноде Kafka.

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Scanner** | Анализ кода в CI | Горизонтально: больше агентов CI. Это **не** часть StatefulSet SonarQube |
| **Application (Web + CE)** | UI, API, разбор отчётов | Community/Developer/Enterprise: **один** процесс. DCE: **≥ 2** application nodes, дальше — ещё ноды / HPA |
| **Search (Elasticsearch)** | Поиск issues/кода | Вшит в единственный процесс **или** 3+ search nodes в DCE |
| **База (ваша)** | Источник истины настроек, пользователей, истории анализов | Отдельный PostgreSQL (реже Oracle/SQL Server) со **своей** HA. SonarQube БД не кластеризует |

Плюс то, что **вы обязаны поставить сами** (вендор это не привозит как часть образа):

- внешняя БД (в проде);
- reverse proxy / load balancer перед 9000 (в DCE — обязательно);
- Ingress/Gateway **свой**, не nginx из чарта;
- IdP (Keycloak / Entra / GitLab…), если не хотите локальных учёток;
- CI, который вызывает scanner.

### Редакции — это не «тариф UI», это разные машины отказа

| Нужно | Community Build | Developer | Enterprise | **Data Center** |
|---|---|---|---|---|
| Бесплатно / без LOC-лицензии Server | да | нет | нет | нет |
| Branch / PR analysis | нет (это добавка Developer) | да | да | да |
| Несколько CE workers из UI | нет | нет | да | да |
| Кластер application + search, HA самого SQ | **нет** | **нет** | **нет** | **да** |
| HPA application nodes в Kubernetes | нет | нет | нет | да (в чарте `sonarqube-dce`) |
| SAML SSO, token lifetime, session timeout | по матрице — коммерческие | да | да | да |
| SCIM (Entra/Okta) | нет | нет | да | да |

Фраза из документации редакций: DCE — для very large / mission-critical, фокус **HA, redundancy, autoscaling in Kubernetes**.  
В community-треде сотрудник Sonar: *HA isn’t supported in any edition below Data Center Edition.* Это не «блог», это прямое подтверждение модели продукта.

**Следствие для вашей задачи «3 ЦОДа, без сбоев»:** без лицензии DCE у SonarQube **нет** штатного кластера. Можно сделать устойчивую **БД** и холодный стенд — это уже не HA приложения, это DR.

### Официальные порты DCE (менять можно, это контракт сети)

| Откуда → куда | Порт (default) | Свойство |
|---|---|---|
| Reverse proxy → App | **9000** | `sonar.web.port` — UI и API, сюда же CI |
| App → Search | **9001** | `sonar.cluster.node.search.port` |
| Search → Search | **9002** | `sonar.cluster.node.es.port` (кластер ES) |
| App → App | **9003** | `sonar.cluster.node.port` (Hazelcast) |
| App → PostgreSQL | **5432** | ваша БД, не часть образа |

Три TCP-сети, которые вендор просит мыслить отдельно: Hazelcast (app↔app), ES (search↔search), search (app↔search). Их можно сегментировать (`sonar.web.host`, `sonar.cluster.node.host`, `sonar.cluster.search.hosts`, …).

В Developer/Enterprise снаружи обычно виден только **9000** (+ JDBC до БД). Вшитый ES наружу не торчат как отдельный продукт — но ядро всё равно требует `vm.max_map_count` и диск.

### Чего в SonarQube нет (частая путаница)

| Нужно системе | Это не SonarQube | Зачем помнить |
|---|---|---|
| HA без DCE («два пода Deployment») | Нет. Второй процесс Community/DE/EE — это второй **инстанс**, не кластер | Получите две БД / конфликт JDBC / «две правды» |
| Active/Active на read-replica PostgreSQL | Нет. Цитата DR-гайда: *does not support access to a database in read-only format for Active/Standby or Active/Active* | Реплика БД ≠ второй живой SQ |
| Пережить 2 из 3 ЦОДов на 3 search-нодах | Не обещается | Кворум ES из трёх нод переживает **одну** зону |
| Порог RTT между ЦОДами | Нет цифры | Search nodes: *same region*, разные AZ — да; миллисекунд нет |
| Скан работающего контейнера / syscall | Falco | Другое время жизни, другой слой |
| Логи хоста, FIM, SIEM | Wazuh | SQ хранит issues кода, не syslog Kafka |
| Шина бизнес-событий / Camunda / озеро эталона | Нет | Опционально webhook в CI, не источник истины клиентских данных |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS прокси и PKCS#12 для ES — не криптография КИИ |
| Анализ «терабайт озера» | Нет | Лицензия и ёмкость считаются в **LOC и отчётах CI**, не в TB сырых данных |
| Rolling upgrade без простоя кластера DCE | Нет. Цитата cluster-доки: *Cluster downtime is required for upgrades or plugin installations* | Планируйте окно |
| Плагины «поставил на одну ноду — разъехались сами» | Нет | Плагины **не шарятся**, ставить на **все** application nodes, при установке **все** app nodes стопают |
| ArgoCD как проверенный путь | *Not currently fully supported or validated* | GitOps — ваш риск, не гайд вендора |
| Azure Fileshare PVC | Известный слом прав NTFS | На AKS — другой StorageClass |
| Fargate / App Runner / Azure App Service | *not supported* (ES prerequisites) | Не «K8s в облаке = любой serverless» |

### Зависимости окружения (обязательны)

- **ОС сервера:** Linux x64/AArch64, Windows x64, macOS x64/AArch64. z/OS нет. Прод у вас — Linux-ноды Kubernetes.
- **Java (только ZIP):** JDK **21 или 25**. Образы Docker/Helm уже несут свою JVM.
- **Ядро под ES:** `vm.max_map_count ≥ 524288`, `fs.file-max ≥ 131072`, у пользователя SQ `nofile ≥ 131072`, `nproc ≥ 8192`, **seccomp** включён, **`/tmp` writable** (ES 8/9, в 2026.4 — ES 9.4.3).
- **Диск search:** локальный **SSD**. Вендор: *Do not use remote-mounted storage (NFS, SMB/CIFS, NAS)*. RAID-зеркало «для ES» не нужно — реплики ES и primary хранилище = БД.
- **БД продакшена:** отдельная машина/кластер, **низкая задержка** до нод SQ. PostgreSQL **14–18**, charset **UTF-8**. H2 — не прод (нет репликации, HA, нормальных бэкапов — формулировка вендора).
- **Kubernetes:** официальные чарты `sonarqube` (Community/Developer/Enterprise) и `sonarqube-dce` (только DCE). Совместимость версий K8s — в README чарта, не выдумывать. CSI + StorageClass, который умеет RWO **в нужной зоне** (search-под после бинда PVC обычно не переедет в другой ЦОД).
- **Helm 2026.1.0+:** встроенный PostgreSQL-subchart **удалён**. Нет `jdbcOverwrite` → либо H2 (тест), либо инстанс не о том.
- **Сеть CI → SQ:** сканеры с build-агентов должны ходить на HTTPS VIP. Self-signed на прокси = доверие сертификата **на всех агентах и в IDE**.
- **Лицензионный ключ** Developer/Enterprise/DCE — иначе коммерческий образ не станет «кластером». Community Build ключа DCE не заменит.

### Как SonarQube стыкуется с вашей архитектурой

```
Репозитории (микросервисы, интеграционное API, BPMN/Camunda как код, Helm, SQL…)
        │  SonarScanner в CI (не на ноде Kafka)
        ▼
   HTTPS 443 ──► ваш Ingress/LB ──► application nodes :9000
                                      │
                                      │  JDBC, низкая задержка
                                      ▼
                                 PostgreSQL (HA — ваша)
                                      ▲
                         search nodes (DCE)  ES :9001/:9002
```

SonarQube **не** участвует в event-sourcing и **не** ходит в госслужбы. Он отвечает на вопрос: «этот коммит / PR можно вливать по правилам качества и SAST?». Пересечение с Falco/Wazuh почти пустое: они смотрят рантайм и хост, SQ — дерево исходников в пайплайне.

## Краткие вводные

### Зачем вам SonarQube в этой архитектуре

У вас много сервисов, интеграционное API на 30+ госслужб, процессный движок, ожидание непрерывной поставки. Типичные дыры, которые Kubernetes и Kafka **не** закрывают:

1. Уязвимость и «горящий» Quality Gate **до** выкладки, а не после инцидента в контуре гособмена.
2. Единый порог для Java/TS/Python/IaC (Helm, Docker, Kubernetes-манифесты — в коммерческих языковых пакетах это есть; набор языков зависит от редакции).
3. Блок merge, если gate красный — дисциплина, а не «сканер в Jenkins, который все игнорируют».

Это слой **supply chain / code review**, не слой 24/7 рантайма. Падение SonarQube **не должно** ронять Kafka и Camunda. Падение SonarQube **должно** быть заложено в CI: либо пайплайн ждёт, либо (хуже) люди льют в обход gate.

### Как устроена отказоустойчивость (идея, не магия)

Три разных контура. Путать их — главная ошибка.

**1) Приложение SonarQube**

| Редакция | Что падает | Что происходит |
|---|---|---|
| Community / Developer / Enterprise | Единственный хост/под | UI, API, приём отчётов — **всё**. CI красный. Данные живы, **если** жива PostgreSQL и есть бэкап. Референс-архитектуры вендора так и говорят: resiliency = мониторинг + бэкап БД + быстрый restore; *If high availability is critical, DCE is recommended*. |
| DCE, дефолтная топология (2 app + 3 search) | Один application node | Цитата: *one application node and one search node can be lost without impacting users*. LB не должен слать трафик на мёртвую ноду (health check — требование к балансировщику). |
| DCE | Два application nodes из двух | Нет UI/API. Search и БД могут быть живы — пользователям всё равно темно. Поэтому в проде не оставлять `replicaCount: 2` как «магическое HA на 3 ЦОДа»: два пода в одной зоне = один ЦОД убивает оба. |
| DCE | Плагин / апгрейд | Нужен **простой всего кластера**. Это не Kafka rolling. |

**2) Search (Elasticsearch)**

| Что падает | Что происходит |
|---|---|
| Одна search-нода из трёх (и шардные реплики на месте) | Дефолтная топология это переживает вместе с одним app node |
| Две search-ноды / два ЦОДа, где они жили | Кворум из трёх — как у любого ES: запись/стабильность кластера под вопросом. Вендор **не** обещает «два ЦОДа из трёх» |
| Весь индекс после failover K8s | Официально: **forced reindex**. Пока индекс строится — поиск/часть UI деградируют, PostgreSQL при этом может быть цела |
| Диск ≥ 90–95% | Индексы read-only / падение ES. «Терабайты» здесь ни при чём: это заполненный PVC search |

Вендор: три search node можно разнести по **разным AZ одной region**. Это ближайшая честная проекция на «3 ЦОДа в одном городе» — **если** вы измеряете задержку и трактуете город как одну region. Stretch ES «на всякий случай на три площадки» без RTT — не из гайда.

**3) База PostgreSQL (настоящий источник истины)**

Индекс ES можно перестроить. Потеря диска search — больно, но штатный путь есть. Потеря PostgreSQL без бэкапа — потеря инстанса: пользователи, настройки, история анализов, лицензионное состояние.

HA БД — **Patroni / облачный HA / ваша схема PostgreSQL**, не фича SonarQube. Официальный DR-пример: primary + replica PostgreSQL (geo-replication), **writer endpoint**, два K8s-кластера SQ, балансировщик с **priority** на primary. Второй SQ **холодный**. После включения replica-кластера — reindex ES.

**4) Сканеры**

Сканер падает вместе с агентом CI. Это нормально. Пока SQ мёртв, отчёты не принять: очередь CE не накапливается «на сканере бесконечно» как обещание вендора. Политика CI (ждать / падать / идти без gate) — ваше решение, его нет в контексте.

### Как устроено масштабирование

Четыре независимые оси:

1. **Больше репозиториев / чаще PR** → очередь CE (`pending_count`, `pending_time`). Enterprise+: больше CE workers **и** больше heap `sonar.ce.javaOpts` (память **делится** между workers). DCE: workers × число application nodes. HPA в DCE целится в CPU application pods, *initial goal — improve PR analysis time so background tasks do not pile up*. Search nodes HPA **не** масштабирует.
2. **Больше UI и приёма отчётов** → больше application nodes (DCE). Helm HPA: `minReplicas: 2`, `maxReplicas: 10`, по умолчанию **выключен**. Вендор: не ставить `minReplicas` ниже 2; автоскейл **дорожает**; на время длинного апгрейда HPA **выключить**.
3. **Больше индекса issues** → RAM/диск **search** (SSD, не NFS), не «ещё один Kafka broker». Ориентир валидации вендора на БД **200M issues**: search **8 vCPU / 32 GB RAM** (16 GB под ES), app **4 vCPU / 16 GB**. Это *minimum recommendation to build your cluster*, не ваш расчёт.
4. **Тяжёлый сам скан** (большой Java-граф) → CPU/RAM **агента CI**. 2026.4 обещает ускорение taint-анализа; это про сканер, не про то, что DCE «проглотит любой монолит».

Референс-архитектуры (не DCE, один хост SQ):

| Ориентир LOC | Хост SQ (идея) | PostgreSQL (идея) |
|---|---|---|
| до ~10M | отдельно от БД; в «small» таблице хоста: **2 ядра / 4 GB** как старт | **2 vCPU / 8 GB / 30 GB** tablespace |
| до ~50M (Enterprise) | **8 ядер / 16 GB** как large-scale | **4 vCPU / 16 GB / 150 GB**; +30% места, если включён Advanced Security |

Вендор: usage patterns сильно разные, **мониторить и подкручивать**. Неизвестная нагрузка у вас = эти таблицы — единица пересчёта, не смета.

Helm defaults — **не** capacity plan:

| Чарт | Память (default) | PVC search |
|---|---|---|
| `sonarqube` (не DCE) | request 2048M / limit 6144M под все редакции | data — смотреть values; это стенд |
| `sonarqube-dce` | search 3072M, app 4096M (под Xmx search 2G / app 3G и правило ~80%) | **5G** на search — для прода с «огромным объёмом» это заведомо мало как план |

Дефолт HPA app: 400m–800m CPU и 3072M RAM — *designed to work with default resources*, не с таблицей 16 GB.

### Безопасность самого SonarQube

Компрометация SQ = компрометация **карты вашего кода**: findings по интеграциям с госслужбами, секреты, которые правила ещё не вычистили, токены CI, список проектов. Токен админа = полный инстанс.

Известные заводские секреты (как пароли overlay у Wazuh — нельзя оставлять):

| Секрет | Значение из документации / чарта |
|---|---|
| Первый вход продукта | **`admin` / `admin`**, сразу просит смену |
| Helm `setAdminPassword.newPassword` | дефолт **`AdminAdmin_12$`** (публичный values) |
| Helm `setAdminPassword.currentPassword` | **`admin`** (чтобы hook сменил заводской) |
| Группа админов | **`sonar-administrators`** — переименовать |
| JWT DCE | `applicationNodes.jwtSecret` — без своего значения кластер сессий не тот |

Force authentication по умолчанию **включён**. Выключите — анонимно торчат в том числе `api/users/search`, `api/system/status`, куски quality profiles/rules (полный список в доке user-accounts). Для контура с госинтеграциями выключать это в проде нельзя «чтобы Jenkins без токена ходил».

Сканер: только `sonar.token`, не пароль в `settings.xml` в Git.

Прокси: HTTPS на входе. Терминация TLS — требования Operating the server / securing behind proxy.

DCE: включить **ES authentication** (`sonar.cluster.search.password` / Helm `searchNodes.searchAuthentication`) и **TLS** app↔search (`nodeEncryption.enabled` в Helm). Иначе 9001/9002 — открытый поисковый кластер во внутренней сети.

FIPS: SQ на RHEL «с ограничениями». Известные: ES authentication в DCE на FIPS **не работает** (PEM пока не поддерживается); SAML с подписью/шифрованием assertion — **ещё нет**. Webhook secret в FIPS ≥ 16 символов.

«Включили Helm с встроенным ingress-nginx и H2 и открыли LoadBalancer» — это новый attack surface, не контур качества.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Self-hosted SonarQube Server**, не SonarQube Cloud. Три своих ЦОДа облако вендора не заменяют.
2. **Для прода, который должен переживать отказ узла приложения, берём DCE.** Без DCE ниже честно описан только «один узел + HA PostgreSQL + холодный DR». Нельзя написать «Community в трёх ЦОДах = HA» — это противоречит модели продукта.
3. **Версия прода — 2026.1.5 LTA**, не Latest 2026.4.1. Причина: вы не валидируете ответы, ожидание непрерывной работы, у Latest окно поддержки ~до следующего релиза. Если платформа сознательно сидит на Helm «всегда latest» — это другое допущение (больше фич, короче поддержка, в 2026.4 ещё и переезд на ES 9 с пересборкой индекса).
4. **Прод крутится в Kubernetes**, инсталлятор DCE — Helm **`sonarqube-dce`**. Тест без лицензии DCE — чарт **`sonarqube`** с `community.enabled=true` **или** Developer, если ключ уже есть.
5. **Три ЦОДа = три зоны отказа одной region** (город). Search nodes вендор разрешает разносить по AZ **внутри region**. Пока RTT неизвестен, честный прод — либо один логический DCE-кластер после **замера** задержки app↔search↔БД, либо не растягивать ES на все три площадки вслепую и держать search+БД в 1–2 площадках, а третья — cold DR.
6. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. На трёх search-нодах (по одной на ЦОД) потеря двух площадок снимает кворум ES. Отдельного SLA «два ЦОДа» у вендора нет.
7. **Нагрузка и LOC неизвестны** — нет цифры «N application nodes и M терабайт PVC». Есть сигналы (очередь CE, heap, диск search, latency JDBC) и рычаги (workers, ноды, SSD, PostgreSQL).
8. **Формального SLA на CI нет.** «Система 24/7» про бизнес-контур. SQ может лежать, пока Kafka жив. Нужна явная политика: блокирует ли красный/недоступный SQ поставку в контур гособмена.
9. **CI и IdP будут.** Без пайплайна SQ — пустой UI. Без IdP в проде останетесь с локальным `admin`.
10. **PostgreSQL — ваша платформенная БД** (не Oracle/MSSQL, если не решите иначе). HA БД проектируется отдельно (как любой прод-PostgreSQL), этот файл её не подменяет.
11. **Тестовый стенд изолирован.** На нём допустимы H2 / один под / дефолтный пароль *внутри песочницы*. В прод их не копируем.
12. **Camunda, Kafka, озеро, интеграционное API** — **проекты в SQ** (их репозитории), не рантайм-зависимости SQ. Ноды брокеров SQ не мониторит.
13. **Лицензия DCE куплена или будет куплена до прода.** Иначе раздел «прод 3 ЦОДа» ниже для приложения SQ неисполним; остаётся EE/DE + DR.
14. **Не используем ArgoCD как единственный путь выката**, пока вендор пишет, что это не fully supported.
15. **PKCS#12 для ES** собирается алгоритмом, который читает JVM образа (в доке 2026.1 всё ещё пометка *readable by Java 17* — проверять на вашей JVM 21/25, не игнорировать).

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «helm install и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **Редакция и бюджет LOC** | Без DCE нет HA приложения. Без Developer нет нормального PR-gate. Без цифры LOC нельзя ни лицензию, ни «small vs 50M» железо |
| **RTT и потери между ЦОДами** (особенно app↔search :9001/:9002, search↔search :9002, JDBC) | Вендор требует low latency до БД и same region для search. Городская сеть бывает разной. Без замера stretch ES — лотерея |
| **Один Kubernetes на 3 ЦОДа или три кластера** | От этого зависит: один DCE с topologySpread или официальный **два кластера** Active-Cold Standby |
| **Где живёт writer PostgreSQL** | SQ не ходит в read-only replica. Падение ЦОДа с writer = падение инстанса, пока не сработает **ваш** failover БД |
| **Политика CI при недоступном SQ** | Не спроектировали — в инциденте либо встанет весь релизный поезд, либо все обойдут gate |
| **IdP и судьба группы `sonar-administrators`** | Синхронизация групп с IdP + дефолтное имя = типовой захват админки |
| **Куда смотрит UI** (только внутренняя сеть?) | Публичный 443 с `admin`/`admin` или `AdminAdmin_12$` — инцидент |
| **StorageClass: локальный SSD vs сеть vs «один NFS на три search»** | Второе вендор запрещает для ES. Третье — SPOF и латентность |
| **Нужен ли FIPS / ГОСТ** | DCE ES-auth и часть SAML на FIPS официально ограничены |
| **Плагины** (свой language pack, LDAP-кастом) | Выкат = простой **всего** DCE; забыть ноду = расхождение |
| **Срок хранения issues / 152-ФЗ** | В индексе и БД может оказаться фрагмент кода с ПДн. Политика retention — ИБ, не дефолт Helm 5G |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **продукт и версию**: Community Build **или** Server 2026.1.5 LTA + редакция. Не смешивать Community 26.8 с образом DCE 2026.1 «на глаз».
2. Сначала **PostgreSQL UTF-8** (даже на серьёзном тесте; H2 — только «пощупать UI за час»). Потом SonarQube. Потом CI-сканер.
3. Выпустить **свои** пароли, JWT, JDBC secret, сертификаты прокси **до** первого боевого проекта.
4. Сменить `admin`/`admin` (или Helm-дефолт `AdminAdmin_12$`). Переименовать `sonar-administrators`. Включить HTTPS. Оставить Force authentication.
5. Прогнать **один** репозиторий до зелёного/красного Quality Gate в UI и увидеть background task *SUCCESS*.
6. Включить метрики: очередь CE, heap Web/CE/ES, диск search, latency JDBC, health application nodes.
7. Только потом — профили правил, блок merge, IdP, размазывание по ЦОДам.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** увидеть проект, отчёт сканера, шум правил на *вашем* Java/Helm, понять UI и Quality Gate. **Не** цель: доказать, что прод переживёт падение ЦОДа и сотню параллельных PR.

Два официальных минимальных пути (выберите один):

**Путь A — Docker / ZIP, один хост** (быстрее понять продукт):

- Образ Community или Developer.
- UI: `http://localhost:9000`, вход `admin`/`admin`, смена пароля.
- БД: лучше сразу маленький PostgreSQL рядом, не H2, если стенд живёт дольше недели (H2 не умеет нормальный бэкап/HA — это буквально причина «not recommended in production»).
- Ядро Linux: `vm.max_map_count=524288` и лимиты файлов/тредов из pre-installation.

**Путь B — Kubernetes, чарт `sonarqube`  (не `sonarqube-dce`)** — ближе к вашему оркестратору:

- `community.enabled=true` **или** `edition=developer` + ключ;
- **своя** JDBC-строка на стендовый PostgreSQL (`jdbcOverwrite.*`); не оставлять H2, если на стенде будут реальные проекты;
- свой Ingress выключен (`ingress-nginx.enabled=false` — рекомендация production use case; на тесте можно временно включить, понимая, что зависимость deprecated);
- `initSysctl` на тесте часто оставляют `true` (privileged), чтобы не драться с ядром; в прод его выключают и чинят sysctl на нодах;
- пароль админа — свой, не `AdminAdmin_12$`, даже на тесте, если до стенда есть сеть кроме вашей.

Режим «три search-ноды DCE на ноутбуке» для знакомства **не нужен**: создаст ложное чувство HA и сгорит по RAM. DCE без ключа всё равно не взлетит как кластер.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Кластер DCE | нет | Нет требования пережить узел |
| Replica search | вшитый ES в одном поде | Иначе yellow/кворум на одном диске |
| PKI | self-signed / HTTP внутри песочницы | Иначе команда утонет в сертификатах раньше, чем в правилах |
| IdP / SAML | локальные пользователи | На тесте важнее контур данных |
| HPA | выкл | Нет нагрузки |
| PVC 5G | можно | Нет истории issues |
| CE workers | дефолт | Нет Enterprise-очереди |
| CPU/memory | как в чарте | Не цель — ёмкость |

#### Чего на тесте **не** стоит упрощать

- Внешняя PostgreSQL, если стенд не однодневный.
- Хотя бы один скан реального сервиса (интеграционное API или маленький Java). Проверка: задача в Background Tasks = SUCCESS, issues видны.
- Понимание: **сканер живёт в CI**, сервер без пайплайна пустой.
- Force authentication оставить включённым, если стенд хоть как-то маршрутизируется.
- Запомнить: успех на одном поде **не** доказывает DCE и не доказывает JDBC через три ЦОДа.

#### Сильные стороны такой схемы

- Поднимается за часы.
- Совпадает с Try-out / Helm non-DCE.
- Дёшево показывает шум правил на вашем коде (Camunda XML, клиенты гос-API, Helm).

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет доказанной ёмкости CE, нет LB на два app node.
- Зелёный gate на игрушечном репозитории **не** доказывает, что очередь CE выдержит монорепу.
- Дефолтные пароли и встроенный ingress приучают «открыть и зайти».
- Community Build без PR-анализа легко уехать в прод «потому что на тесте хватало» — для микросервисов это ловушка.

Практическая рекомендация: препрод = маленький **прод-профиль** (DCE 2+3 или хотя бы EE на отдельной PostgreSQL, свои секреты, HTTPS, один проект из CI, свой Ingress), даже без боевого трафика.

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты озера» **нет** — нагрузки и LOC нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

SonarQube не выбирает за вас «один Kubernetes или три». Он плохо переживает **три независимых инстанса** (три лицензии, три quality gate, три правды для разработчиков) и плохо переживает **слепой stretch ES**.

**Вариант A — один Kubernetes на 3 зоны, один DCE.**

- Чарт `sonarqube-dce`, `searchNodes.replicaCount: 3`, `applicationNodes.replicaCount: ≥ 2`.
- `searchNodes.topologySpreadConstraints` **до** установки: `topology.kubernetes.io/zone`, `whenUnsatisfiable: DoNotSchedule`, `maxSkew: 1` — это пример из README чарта 2026.4.x. Иначе три PVC search могут родиться в одном ЦОДе; при смерти зоны «HA из манифеста» окажется двумя подами в pending (диск привязан к зоне).
- Application nodes: spread с `ScheduleAnyway` (они stateless относительно ES-диска; состояние — в PostgreSQL + JWT).
- Перед 9000 — **ваш** Ingress/Gateway + health check. Не `ingress-nginx` из чарта (вендор: testing only; зависимость ещё и deprecated).
- PostgreSQL: кластер с failover **writer** (Patroni и т.п.) с низкой задержкой до app nodes. Размазать writer «поровну на 3 ЦОДа» без понимания кворума БД — отдельная ошибка, не фича SQ.

**Вариант B — три изолированных Kubernetes.**

Не ставить по полноценному DCE «в каждый кластер как Falco DaemonSet». Falco — агент на ноде. SonarQube — **общий** сервер отчётов.

Рабочие подварианты B:

- **B1 (ближе к вендору).** Один primary DCE + **cold replica** DCE в другом кластере/ЦОДе + репликация PostgreSQL + переключение трафика (их пример — Azure Front Door с priority; у вас это может быть городской LB). После failover — **forced ES reindex**. Это официальная схема DR, не Active/Active.
- **B2.** Один DCE в «домашнем» ЦОДе, из двух других ЦОДов только CI-сканеры ходят на VIP. Search/JDBC **не** растягивать. Падение домашнего ЦОДа = нет SQ, пока не B1.
- **B3.** Три полноценных SQ — только если готовы тройную лицензию и тройные профили. Обычно хуже.

**Пока топология K8s не зафиксирована, нельзя честно выбрать A или B1.** Дальше — общее.

##### Сильные / слабые стороны (A, один кластер на 3 зоны)

| Сильное | Слабое |
|---|---|
| Один quality gate, одна лицензия, один IdP | RTT бьёт по ES cluster state и JDBC |
| Официальная DCE-топология 2+3 почти про AZ | Search PVC часто зональные: DoNotSchedule без нод во всех зонах = pending |
| Можно потерять 1 app + 1 search | Два ЦОДа из трёх — не цель этой схемы |
| HPA app nodes | HPA не лечит медленную БД; вендор предупреждает про стоимость и bottleneck |

##### Сильные / слабые стороны (B1, primary + cold)

| Сильное | Слабое |
|---|---|
| Совпадает с документом DR | Второе плечо **не** обслуживает трафик, пока его не включили |
| ES не обязан жить на 9002 между всеми тремя ЦОДами постоянно | RTO включает reindex; вендор не даёт вам минуты в этом файле — их нет в цитате |
| Падение ЦОДа primary отрабатывается runbook'ом | Пока runbook руками и «почти» автоматический DNS — это не 24/7 magically |

##### Слабое место любого stretch без замера RTT

Документация **не задаёт** порог миллисекунд. Утверждение «3 ЦОДа в одном городе, значит ES можно размазать» — **непроверенное**. Измерить RTT/потери на 9001/9002/5432 **до** закупки схемы.

#### Search nodes (ядро отказоустойчивости *поиска*)

Минимум для «пережить 1 узел / 1 зону»:

- **ровно дефолтный минимум 3** search node, идентичные по CPU/RAM/диску (требование: all search nodes identical);
- по одной машине/ноде на процесс (рекомендация вендора);
- SSD, не NFS;
- PVC размер от объёма индекса, **не 5G из values**;
- 10%+ свободного диска всегда;
- heap ES: ориентир вендора «50% RAM ноды, не больше 32 GB»; в валидации 200M issues — **16 GB из 32** на search;
- `vm.max_map_count=524288` на **каждой** ноде, где живёт search, **без** privileged `initSysctl` в проде (sysctl делает администратор кластера);
- topology spread **до** первого PVC;
- ES authentication + TLS (`searchAuthentication`, `nodeEncryption`) — иначе внутренняя сеть читает индекс кода.

**Слабое место:** три пода search в одной зоне + PVC 5G + `initSysctl: true` в restricted-кластере. Выглядит как DCE, ведёт себя как один диск.

#### Application nodes (ядро отказоустойчивости *приёма сканов и UI*)

- Минимум **2**, идентичные. Балансировщик: HTTP, **без** sticky, **с** health check.
- `jwtSecret` — свой, одинаковый на всех app nodes (иначе сессии и CSRF разъедутся).
- Масштаб CE: смотреть Background Tasks. Workers в UI (EE/DCE) **глобальны**: 4 workers × 2 node = **8** после рестарта всех app. Память CE увеличить **до** увеличения workers.
- HPA: включать только когда нет bottleneck на БД/диске/сети (официальный troubleshooting autoscaling). На апгрейд — выкл.
- Плагины: выкат только с простоем **всех** app nodes; чеклист «на каждой ноде одинаковый набор».
- Не класть БД, app и search в один Docker-хост/одну VM: для Docker-прода вендор прямо говорит *different Docker hosts*.

Падение 1 app node: переживается. Падение ЦОДа, где жили **оба** app: не переживается, сколько ни пиши `replicaCount: 2`. Anti-affinity/spread обязательны.

#### PostgreSQL (ядро отказоустойчивости *данных*)

- Отдельный от SQ хост/кластер, UTF-8, роли не `postgres` суперюзер в приложении без нужды.
- JDBC через TLS (`ssl=true` в URL — настраиваете вы; вендор требует низкую задержку, не «обязательный mTLS в одной фразе» — TLS БД всё равно делайте стандартом платформы).
- HA: синхронный/кворумный failover **writer**. Read-replica для живого SQ **не использовать**.
- Бэкап PITR. Restore репетировать. Индекс ES после restore/failover кластера — reindex.
- Ресурсы: начать с таблиц 10M/50M LOC и **смотреть** CPU/IO. Advanced Security → +30% tablespace (если купите).

Без учения «убили writer, приложение пережило failover БД» у вас нет прода SQ, есть надежда.

#### Сканеры и CI

- Токены project/global с правом Execute Analysis, срок жизни, ротация. Не пользовательский пароль.
- Quality Gate в проверке PR (Developer+). Политика: красный gate = нельзя в `main`.
- Агенты CI доверяют корпоративному CA прокси.
- Монорепа / 30+ интеграций: очередь CE будет скакать пачками. Это сигнал масштабировать CE/app, не «купить ещё Kafka».
- Сканер **не** ставить DaemonSet на ноды брокеров.

#### Безопасность прода (без этого кластер не считается настроенным)

Три слоя:

1. **Секреты и идентичность** — нет `admin`/`admin`, нет `AdminAdmin_12$`, свой JWT, свой JDBC secret, свой ES password/PKCS12; IdP (SAML/LDAP/GitLab — что есть у вас); группа админов переименована; токены не в Git; `monitoringPasscode` Helm — не из примера.
2. **Сеть** — 9001/9002/9003 не с мира; 9000 только через HTTPS-прокси; JDBC только с app nodes; NetworkPolicy; сегментация frontend/backend/search, если сеть это умеет.
3. **Данные** — шифрование PVC и томов БД средствами платформы; settings encryption (`sonar.secretKeyPath`) для паролей в конфиге; политика: фрагменты кода с ПДн в индексе.

Плюс production use case Helm:

- `ingress-nginx.enabled=false`, свой Ingress/Gateway;
- `initSysctl.enabled=false`, `initFs.enabled=false`, restricted namespace;
- memory **request = limit** (вендор: memory non-compressible);
- свой registry, pin тега **2026.1.5** (digest), не `latest`;
- PodDisruptionBudget так, чтобы выкат не снял сразу 2 из 3 search.

##### Сильные / слабые стороны выбранной ИБ-схемы (DCE Helm + свой Ingress + ES TLS + IdP + pin LTA)

| Сильное | Слабое |
|---|---|
| Единственный вендорский путь HA SQ | Лицензия DCE; без неё схема не существует |
| JWT без sticky, health check LB | Компрометация JWT secret = подделка сессий |
| ES auth/TLS документированы | PKCS#12/SAN надо собрать под DNS подов; ошибка SAN = кластер не встанет |
| Force auth по умолчанию | Выключение открывает API списком из доки |
| SAML/SCIM в коммерческих редакциях | FIPS ломает часть SAML и DCE ES-auth |
| Не ГОСТ | Если ИБ потребует СКЗИ — vanilla TLS это не закроет |
| Restricted PSS для app-контейнеров | Пока `initSysctl` включён — privileged init всё равно есть |

#### Kubernetes-специфика прода

- Чарт **`sonarqube-dce`**, values `applicationNodes` (не deprecated `ApplicationNodes`).
- Search — **StatefulSet + PVC**. App — Deployment (масштабируется, в т.ч. HPA).
- JDBC только из K8s Secret, не plaintext `jdbcOverwrite.jdbcPassword` (поле deprecated).
- Минимум нод в разных зонах, иначе DoNotSchedule search не разместится.
- Rolling search: полагаетесь на то, что 3 ноды переживают 1. Выкат двух сразу — риск кворума.
- После смены major ES (если когда-нибудь пойдёте на 2026.4): индекс в новый каталог (`es9` в release notes) — заложить время переиндексации.
- Мониторинг: Prometheus по гайду вендора (отдельная страница monitoring), не «живёт под».

#### Порядок вывода в прод (этапы, не команда за командой)

1. Измерить RTT/потери между ЦОДами на 5432, 9001, 9002, 9003. Решить: stretch A или B1/B2.
2. Зафиксировать редакцию (DCE) и LOC. Без ключа дальше только самообман.
3. Снять оценки: число репозиториев, частота PR, языки, нужен ли блок merge.
4. Поднять HA PostgreSQL UTF-8, проверить failover writer **без** SQ.
5. Sysctl на нодах (`524288` / file-max / seccomp), StorageClass SSD зональный.
6. Установить DCE 2026.1.5: 3 search + ≥2 app, свои секреты, ES auth+TLS, свой Ingress HTTPS.
7. Сменить админа, переименовать админ-группу, подключить IdP, запретить анонимный анализ.
8. Подключить один сервис из CI токеном, дождаться SUCCESS, настроить Quality Gate.
9. Неделя шума правил, exceptions, **потом** обязательный блок merge.
10. Нагрузить очередью (пачка PR) и смотреть `pending_*`, heap, диск, JDBC.
11. Учения: убить 1 app; убить 1 search (другая зона); убить ЦОД без writer БД; убить ЦОД с writer (срабатывает ли Patroni); для B1 — failover на cold и **reindex**.

Без пунктов 4, 6 (spread+TLS), 10 и 11 у вас нет платформы качества, есть namespace `sonarqube`.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | **DCE** 2+ app / 3 search, spread по зонам, LB health, HA **writer** PostgreSQL, runbook 1 ЦОД; DR либо B1 (cold + reindex), либо честный RTO «SQ лежит, бизнес жив». Переживание **2** ЦОДов не обещать |
| Производительность / масштаб | Не требуется | Очередь CE под контролем; workers только с запасом heap/CPU/БД; HPA осторожно; PVC search не 5G «как в чарте»; сканер масштабируется CI, не StatefulSet SQ |
| Безопасность | Дефолт паролей только в изоляции; UI не с мира | Нет заводских паролей/JWT; HTTPS; force auth; IdP; ES auth+TLS; 9001–9003 закрыты; pin 2026.1.5; токены в CI; админ-группа переименована |

**Не готов к проду**, если: Community/DE/EE «в трёх ЦОДах для HA»; H2 или PostgreSQL из старого subchart; один search PVC на NFS; `admin`/`admin` или `AdminAdmin_12$`; встроенный ingress-nginx в интернет; `latest`; DCE без ключа; три полноценных инстанса без причины; read-replica как второй живой SQ; RTT не мерили, а ES растянули на 3 ЦОДа; нет учения отказа writer и одной search-зоны; CI обходит Quality Gate; ждут, что SQ заменит Falco/Wazuh/WAF; ждут, что SQ проанализирует озеро клиентских данных вместо репозиториев.
