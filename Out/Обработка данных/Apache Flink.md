# Apache Flink 2.2.1 — развёртывание и настройка

Версия ПО: **Apache Flink 2.2.1** (релизная дата 15 мая 2026; это последний патч линии 2.2).  
Документация линейки: https://nightlies.apache.org/flink/flink-docs-release-2.2/  
Образ: `flink:2.2.1-java17` (официальный Docker Hub `library/flink`; Java 17 — рекомендуемая версия рантайма в доке 2.2).

На Kubernetes официальный путь: **Apache Flink Kubernetes Operator 1.15.0** (26 мая 2026). Анонс оператора: он **валидирован против Flink 2.2**; матрица 1.15.0 — `2.2.x, 2.1.x, 2.0.x, 1.20.x, 1.19.x`. Helm: `https://archive.apache.org/dist/flink/flink-kubernetes-operator-1.15.0/`. Образы оператора: Docker Hub `apache/flink-kubernetes-operator` и GHCR `ghcr.io/apache/flink-kubernetes-operator`.

Коннектор к вашей шине: **Apache Flink Kafka Connector 5.0.0** (совместим с Flink 2.1.x и **2.2.x** по таблице загрузок проекта). Коннекторы выпускаются **отдельно** от ядра Flink — их версию пинят явно.

На дату документа последний стабильный релиз *самого* Flink — **2.3.0** (25 июня 2026). Анонс оператора **1.15.0** линейку 2.3 **не перечисляет**. Nightlies `operator-docs-main` — это незарелизенная ветка, не контракт 1.15.0. Поэтому прод на Kubernetes в этом файле — **2.2.1 + оператор 1.15.0**. Переход на 2.3.0 — только после оператора, который это явно подтвердит, либо без оператора (тогда вы сами несёте lifecycle).

Этот текст — не мануал «скопируй YAML и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Flink **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить потоковый движок на ту же инфраструктуру. Это **не** шина событий, **не** озеро эталона, **не** Camunda и **не** интеграционное API к госслужбам.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Job (задание)** | Одна запущенная программа Flink: читает потоки, считает, пишет результат. Живёт, пока её не остановили (streaming) или пока не дочитала вход (batch). |
| **JobGraph** | Внутренний граф операторов, который клиент/JobManager собирает из вашего `main()`. |
| **JobManager (JM)** | «Мозг» кластера: планирует задачи, следит за чекпоинтами, держит REST/UI. В один момент лидер **один**. Без HA это единая точка отказа. |
| **TaskManager (TM)** | «Руки»: на них крутятся операторы (source / map / window / sink). Падение TM — не гибель кластера, если есть чекпоинт; задание **перезапускается** с последнего снимка. |
| **Slot (слот)** | Единица вместимости TM. `taskmanager.numberOfTaskSlots` — сколько параллельных кусков задания TM готов принять. |
| **Parallelism (параллелизм)** | На сколько параллельных задач режется оператор. Грубо: «сколько рук одновременно читают/считают». |
| **Application mode** | На каждое приложение — свой мини-кластер. `main()` выполняется на JobManager. Для прода — основной режим: изоляция ресурсов. |
| **Session mode** | Один кластер, много заданий. Дешевле на тесте. В проде: шумный сосед, одна упавшая TM бьёт несколько job. |
| **SessionJob** | Задание, которое оператор сажает в уже существующий session-кластер. |
| **Checkpoint (чекпоинт)** | Автоснимок состояния задания + позиций во входных потоках. Нужен, чтобы после сбоя продолжить **как будто сбоя не было** (для *managed state*). Lifecycle ведёт Flink, снимки частые и «лёгкие». |
| **Savepoint** | Снимок «для людей»: смена версии Flink, смена графа, переезд. Вы создаёте и удаляете сами. Дороже чекпоинта, зато переносимее. |
| **State backend** | Где **рабочее** состояние живёт *между* чекпоинтами: куча JVM (`HashMapStateBackend`) или диск RocksDB (`EmbeddedRocksDBStateBackend`). |
| **Checkpoint storage** | Куда **копия** состояния уезжает при чекпоинте: куча JobManager (только стенд) или файловая/объектная система (`FileSystemCheckpointStorage`). |
| **HA (JobManager)** | Несколько JM, из них один лидер. Адрес лидера и указатели на чекпоинты лежат во внешнем HA-сервисе (Kubernetes или ZooKeeper) плюс каталог `high-availability.storageDir`. |
| **Standby JobManager** | Запасной JM уже запущен. Ускоряет смену лидера. **Не** делает падение лидера прозрачным: задание всё равно перезапускается. Это формулировка оператора, не домысел. |
| **Exactly-once (у Flink)** | Каждый входной факт **один раз повлияет на managed state**. Это не «каждый байт ровно один раз прошёл через сеть» и не «sink снаружи тоже магически идемпотентен». Для Kafka-sink нужен отдельный `DeliveryGuarantee`. |
| **At-least-once** | После рестарта часть записей может обработаться повторно. Проще и быстрее, дубли возможны. |
| **Barrier / alignment** | Служебные метки в потоке, которые «выравнивают» чекпоинт по всем входам. Для exactly-once alignment нужен. |
| **Unaligned checkpoint** | Чекпоинт без полного выравнивания: быстрее при backpressure, но **нельзя** использовать для произвольного апгрейда графа / minor-апгрейда Flink (таблица checkpoints vs savepoints). |
| **RocksDB** | Встроенная LSM-база на локальном диске TM. Состояние может быть больше кучи. Доступ медленнее heap. Единственный из стабильных backend'ов с **инкрементальными** чекпоинтами. |
| **ForStStateBackend** | Disaggregated state (SST на S3/HDFS). В доке 2.2 прямо: **experimental, not fully available for production**. |
| **KafkaSource / KafkaSink** | Актуальные API коннектора. Старые `FlinkKafkaConsumer` / `FlinkKafkaProducer` — наследие, в 1.15 producer уже deprecated. |
| **DeliveryGuarantee** | Гарантия sink в Kafka: `NONE` (дефолт sink!), `AT_LEAST_ONCE`, `EXACTLY_ONCE` (транзакции Kafka, коммит на чекпоинте). |
| **transactionalIdPrefix** | Префикс `transactional.id` для exactly-once sink. Должен быть **уникален** среди job на одном Kafka-кластере. |
| **uid оператора** | Стабильное имя оператора в графе. Без него смена кода ломает восстановление state из savepoint. |
| **Watermark** | Метка «события старше этого времени больше не жду» для окон по event-time. Не про HA, но без неё окна в интеграциях с лагами ведомств будут врать. |
| **Backpressure** | Оператор не успевает — тормозит тех, кто пишет в него. Это защита, не «Flink медленный». |
| **REST / Web UI** | Управление и просмотр job. Порт **8081**. Это внешний контур: CLI, UI, оператор. Не путать с внутренним RPC JM↔TM. |
| **Operator (Kubernetes)** | Отдельная программа: смотрит CR `FlinkDeployment` / `FlinkSessionJob` / `FlinkStateSnapshot` и делает то, что иначе делал бы человек (выкат, savepoint, HA, откат). |
| **Native Kubernetes** | Flink сам создаёт поды JM/TM без оператора. Cluster lifecycle — на вас. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро подняться. У Flink RPO ≈ «не дальше последнего **успешного** чекпоинта», не «ноль, как у Kafka `acks=all`». |
| **Shuffle** | Пересылка записей между TM (network buffers). Ходит по внутренней сети. Stretch TM по ЦОДам = shuffle между ЦОДами. |

## Основные элементы системы и зависимости

### Что входит в Apache Flink 2.2.1 (это одно ПО из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **JobManager** | Планирование, чекпоинты, REST | Вертикаль CPU/RAM. Для HA — standby-реплики, не «ещё JM от QPS обработки» |
| **TaskManager** | Счёт, окна, сеть shuffle, локальный RocksDB | Горизонтально: больше TM и/или слотов. Параллелизм job должен быть согласован с числом слотов |
| **Клиент** | Собрать граф и сдать (CLI / REST / SQL Client). В application mode `main()` на JM | Не масштабируют «как сервис» |
| **HA-сервис** | Выборы лидера JM | Kubernetes HA (без ZooKeeper) или ZooKeeper. На K8s типичен Kubernetes HA |
| **Checkpoint / HA storage** | Долговечные снимки и метаданные JM | Отдельное **внешнее** хранилище. Это не PVC одной TM |
| **Плагины FS** | S3/MinIO, HDFS, … | JAR из `opt/` → `plugins/` **в образе** до старта |
| **Коннекторы** | Kafka, JDBC, … | Отдельные релизы; кладутся в job-jar или образ |

Плюс *рядом*, но это уже другое ПО: **Apache Kafka 4.3.1** (у вас отдельный документ), объектное хранилище чекпоинтов (MinIO / S3-совместимое), Prometheus, Schema Registry, озеро (Iceberg/Paimon/своя СУБД), **Flink CDC** (отдельный Apache-проект). Их HA проектируется отдельно.

### Официальные порты (менять можно, но это контракт сети)

| Порт | Назначение |
|---|---|
| **8081/TCP** | REST API и Web UI JobManager. Дефолт `rest.port` / `rest.bind-port` |
| **6123/TCP** | RPC JobManager (`jobmanager.rpc.port`). На HA-сетапах TM **находят** лидера через HA-сервис, статическое «все знают 6123» — модель standalone без HA |
| **blob / TM RPC / TM data** | Часто **0** = ОС выдаёт свободный порт. В NetworkPolicy нельзя «разрешить только 6123» и считать внутренний трафик закрытым |

UDP нет. Клиенты и люди ходят на **8081**, не на RPC TM.

### Чего в Apache Flink нет (частая путаница)

| Нужно системе | Это не Flink | Зачем помнить |
|---|---|---|
| Шина событий, хранение лога «навсегда» | Apache Kafka | Flink **читает и пишет** Kafka. Retention, RF, ACL — у брокеров |
| Источник истины клиентских данных / озеро | СУБД, объектное хранилище, warehouse | Flink держит *рабочее* состояние job. Чекпоинт — не «копия озера» |
| Camunda / BPMN | Process engine | Flink не исполняет пользовательские процессы «заявка №123». Может *питать* Camunda событиями или материализовать проекции |
| Интеграции с госслужбами | Ваше интеграционное API | Flink может нормализовать уже полученные события; ходить в ведомства «вместо API» — сломать контур ожидания лагов |
| Реестр схем Avro/JSON/Protobuf | Schema Registry (Apicurio и т.п.) | Без схем стримы из 30+ интеграций разъедутся |
| UI «нарисовать пайплайн для бизнеса» | Отдельные продукты (Ververica и т.п.) | Open-source Flink UI — операторский, не витрина |
| Гарантия end-to-end exactly-once «с любым sink» | Идемпотентный/транзакционный sink | JDBC «просто INSERT» при рестарте даст дубли, даже если Flink state exactly-once |
| Официальный порог RTT между ЦОДами | Нет | Нет rack-awareness как у Kafka `broker.rack` |
| Шифрование state **на диске TM** из коробки | LUKS / CSI encryption | OSS Flink не заменяет шифрование тома RocksDB |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS JDK — не криптография КИИ, если ИБ её выдвинет |
| ZooKeeper «обязательно» | Нет на Kubernetes | ZooKeeper HA *можно*, но это ещё один кворум. Оператор для K8s считает Kubernetes HA обычным выбором |

### Зависимости окружения (обязательны)

- **Java.** Док 2.2: **Java 17 рекомендуется** (дефолт Docker-образов с Flink 2.0). Java 11 поддерживается. Java 21 в 2.2 — **experimental**. Для прода пинить **17** на JM, TM и в job-jar (или явно проверить 21 на стенде — это не «готово»).
- **ОС.** Linux x86_64 / ARM64. Прод на Windows-host для TM в схеме с Kubernetes не предполагается.
- **Диск TM.** Для RocksDB — **локальный** быстрый диск (SSD). Рабочее состояние ≠ чекпоинт. `emptyDir` на TM переживёт рестарт пода только пока жив узел и пока вы сознательно это приняли; чекпоинт должен быть **вне** пода.
- **Сеть TM↔TM и TM↔JM.** Shuffle и RPC чувствительны к потере пакетов и RTT. Это не HTTP-ретраи «как у REST».
- **Долговечная FS для чекпоинтов и HA metadata.** Док: для всех HA-сетапов — `FileSystemCheckpointStorage` (S3, HDFS, GCS, смонтированный том). `JobManagerCheckpointStorage` (куча JM) — local development / очень маленькое state. Плагин **flink-s3-fs-presto** в доке S3 назван рекомендуемым *для чекпоинтов в S3*. MinIO и прочие S3-compatible — через `s3.endpoint` (+ часто `s3.path.style.access: true`).
- **Kubernetes.** CSI; для RocksDB — диск с предсказуемым IOPS. Чекпоинты **не** кладут на RWO-том одной TM как единственную копию. Оператор ставится Helm-чартом **тегом 1.15.0**, не `latest`.
- **PKI** для прода, если включаете SSL REST/internal. Self-signed «чтобы UI открылся» — только стенд.
- **Kafka** (в вашей архитектуре почти наверняка): живой кластер с RF/min.ISR как в документе Kafka; для exactly-once sink — транзакции и `transaction.timeout.ms`.

### Как Flink стыкуется с вашей архитектурой

```
Микросервисы, Camunda, интеграционное API
        │  produce / consume
        ▼
   Kafka (шина)                    ← отдельный документ
        │
        ├──► Flink jobs            ← этот документ
        │       │  чекпоинты / savepoints
        │       ▼
        │    объектное хранилище (S3/MinIO)   ← не озеро эталона
        │       │
        │       └──► Kafka (проекции) / озеро / OpenSearch / БД
        ▼
Озеро эталонных данных (SoT)       ← не Flink
```

Честные роли Flink у вас:

1. **Потоковая материализация** — из топиков Kafka собрать проекцию в озеро / поисковый индекс / другой топик (обогащение, дедуп, окна).
2. **Буфер сложной обработки** — то, что неудобно делать в микросервисе: join потоков, session windows, exactly-once в транзакционный sink.
3. **Непрерывный ETL** ограниченных выгрузок (batch API Flink), если появится.

Нечестные роли:

- «положили клиентов только в keyed state Flink — вот и озеро»;
- «Flink ходит в 30 ведомств вместо интеграционного API»;
- «чекпоинт в S3 = бэкап эталона».

## Краткие вводные

### Зачем вам Flink в этой архитектуре

Kafka доставляет факт. Озеро хранит истину. Camunda ведёт процесс. Интеграционное API ходит наружу. Остаётся вопрос: **как непрерывно и согласованно превращать поток событий в проекции**, когда данные большие, внешние системы отвечают с лагом, и один и тот же факт читают несколько контуров.

Flink закрывает долгий stateful streaming: окна, keyed state, чекпоинты, коннектор к Kafka с настраиваемой доставкой. Он **не** заменяет шину и **не** является SoT.

Если вся обработка — «прочитал JSON, записал в БД» без окон и без требования согласованного рестарта, Flink может оказаться лишним слоем. Это развилка продукта, не «надо потому что event-sourcing».

### Как устроена отказоустойчивость (идея, не магия)

Это **не** кворум данных как у Kafka (RF=3 на каждом сообщении). Это **снимки + переигрывание входа**.

**1) Чекпоинт**

Пока чекпоинтинг выключен, при падении TM задание либо умрёт, либо (если нет restart strategy) не восстановит state. Док: если чекпоинтов нет, дефолтная restart strategy — **не рестартовать**.

Когда чекпоинтинг включён:

- периодически все операторы снимают managed state и позиции источников;
- снимок уезжает в checkpoint storage;
- при сбое Flink откатывается на последний **успешный** чекпоинт и перечитывает Kafka **с сохранённых offset**.

Следствия, которые легко пропустить:

| Что падает | Что происходит |
|---|---|
| Одна TM, чекпоинт свежий, storage жив | Job перезапускается (целиком или регионом). Дубли на sink зависят от DeliveryGuarantee |
| JM без HA | Новые submit нельзя; running job **падают** (формулировка HA Overview) |
| JM с Kubernetes HA, storageDir жив | Новый лидер поднимает job с HA-метаданных / последнего чекпоинта. Оператор: job **всё равно рестартится**, standby только ускоряет |
| Потерян каталог чекпоинтов / HA metadata | Восстановление **из Flink** невозможно. Остаётся вход в Kafka (если retention ещё держит) и ручной старт «с нуля» или из savepoint, если он был в другом месте |
| Чекпоинт только в куче JM | Падение JM = нет снимка. Для HA док прямо рекомендует filesystem storage |
| Kafka retention короче, чем дыра без чекпоинта | Offset из снимка указывает в уже вычищенный лог → дырка или падение source |

**RPO** ограничен интервалом чекпоинта плюс временем, пока чекпоинт ещё не завершился. Интервал «как в туториале 10 секунд» на большом RocksDB-state может не успевать и будет душить job. Цифры интервала **нет** в вашей нагрузке — её нет.

**2) Savepoint ≠ чекпоинт**

Плановый выкат версии, смена параллелизма, смена backend — через savepoint (canonical, если меняете backend). Чекпоинт оптимизирован «тот же код, быстрый рестарт». Путать их — типичная причина «после релиза state не встал».

Оператор: автоматическое HA-восстановление идёт с **последнего чекпоинта**, не с периодических savepoint. Savepoint — ручная точка fork/backup.

**3) Exactly-once до Kafka и дальше**

Цепочка честная только если:

- чекпоинтинг включён, режим `EXACTLY_ONCE` (alignment);
- KafkaSink `DeliveryGuarantee.EXACTLY_ONCE` + уникальный `transactionalIdPrefix`;
- потребители проекции читают с `isolation.level=read_committed`;
- `transaction.timeout.ms` на брокере **больше**, чем max(длительность чекпоинта) + max(время рестарта). Иначе брокер абортит транзакцию → риск потери (док коннектора, `ProducerFencedException`).

Видимость записей в топике **задерживается до чекпоинта**. Это не баг.

Дефолт KafkaSink — `DeliveryGuarantee.NONE`. «Поставили Flink, значит exactly-once» — **неверно**.

**4) Оператор сам по себе**

Падение оператора **не** роняет уже бегущие job. Но пока оператора нет, никто не вылечит пропавший JM Deployment и не сделает reconcile. Для прода: leader election оператора + `replicas: 2` (не наоборот: два реплики *без* election = два активных контроллера, конфликт).

### Как устроено масштабирование

Несколько независимых осей:

1. **Больше CPU на оператор** → поднять **parallelism** (и дать столько слотов: TM × `numberOfTaskSlots`).
2. **Больше места под state** → RocksDB + локальный диск; не раздувать кучу «как у Spring».
3. **Больше входного Kafka** → parallelism source **не выше** числа партиций топика (лишние субаски простаивают). Сначала партиции Kafka, потом Flink.
4. **Autoscaler оператора** — отдельная функция: смотрит lag/utilization и меняет parallelism вершин. Включать **после** стабильного чекпоинта и метрик, не в день первого деплоя.
5. **JM** почти не масштабируют «от MB/s». Ему нужна RAM под метаданные job; много мелких session-job на одном JM — антипаттерн прода.

Память TM задаётся **явно**: `taskmanager.memory.process.size` (для контейнера это размер пода) **или** `taskmanager.memory.flink.size`, не оба сразу (док: конфликт → возможен отказ старта). Для RocksDB managed memory не обнуляют (в отличие от рекомендации zero managed memory для HashMap).

«Терабайты в озере» сами по себе не равны терабайтам **state Flink**. State — окна, агрегаты, буферы join, Kafka offsets. Если job — stateless map, state крошечный. Если «окно 90 дней по всем клиентам в keyed state» — state может стать главным диском.

### Безопасность самого Flink

Компрометация JM REST = возможность **остановить job, снять savepoint, читать метрики, иногда влиять на submit**. Компрометация TM = доступ к рабочей копии state (ПДн, ответы ведомств в keyed state) и к сетевому контуру Kafka.

Официально:

- Внутренний трафик (RPC Pekko, blob, TM data) и внешний REST — **разные** SSL-флаги: `security.ssl.internal.enabled` / `security.ssl.rest.enabled` и уточняющие `pekko.ssl.enabled`, `blob.service.ssl.enabled`, `taskmanager.data.ssl.enabled`.
- REST по умолчанию **не аутентифицирует клиента**. Док SSL: mutual TLS можно включить, но рекомендуемый паттерн — REST только на loopback/pod-local + sidecar-прокси (Envoy/NGINX) с нормальной аутентификацией.
- Секреты в манифесте `FlinkDeployment`: оператор **логирует diff CR** (FLINK-30306). Ключи MinIO/Kafka в YAML = ключи в логах всех, кто читает логи оператора.
- Kerberos для Kafka — штатный путь коннектора, если у брокеров GSSAPI. Иначе — тот механизм, что выбрали в документе Kafka (SCRAM/OAUTH поверх TLS).

Открытый 8081 в интернет с plaintext — это не «удобный мониторинг», это панель управления кластером.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём Apache Flink 2.2.1 + Kafka Connector 5.0.0**, не Ververica Platform, не Amazon Managed Flink, не Cloudera. Управляемые сервисы живут по другим манифестам.
2. **Прод крутится в Kubernetes**, целевой инсталлятор — **Flink Kubernetes Operator 1.15.0**, режим **Native** (не Standalone mode оператора: док HA прямо — `--host` с IP пода ломает leader election). Чарты пинить **1.15.0**.
3. **Application mode, один `execute()` на приложение**, если нужна HA. Док: HA в application mode **не поддерживается** для multi-`execute()` приложений.
4. **Три ЦОДа = три зоны отказа.** Если это три зала с общим питанием — «размазать TM» даёт ложное чувство безопасности.
5. **Целевой отказ: пережить падение 1 ЦОДа для *обработки* не тем же механизмом, что Kafka stretch.** У Flink нет официального stretch-кластера с репликацией state по стойкам. Ниже это разобрано как отдельная макроархитектура, не как «поставьте 3 JM в 3 ЦОДа и будет как у брокеров».
6. **Нагрузки нет** — поэтому **нет** числа TM, параллелизма и размера RocksDB. Есть сигналы (lag Kafka, duration чекпоинта, backpressure, heap, disk TM) и рычаги.
7. **Формального SLA / RPO / RTO нет.** Успешный чекпоинт ≠ юридический 24/7. RPO ≠ 0.
8. **Корпоративный PKI есть или будет** для REST/internal TLS. Hostname verification не выключают «чтобы завелось».
9. **Идентификация людей** к UI — через прокси/SSO, не общая дырка 8081. Сервисы к Kafka — отдельные учётки из документа Kafka.
10. **Шифрование канала — TLS JDK.** ГОСТ/СКЗИ не озвучены.
11. **Тестовый стенд изолирован.** На нём допустимы 1 JM, HashMap, чекпоинт на `file://`, без TLS. В прод это не копируем.
12. **Kafka, Camunda, озеро, интеграционное API** — источники/приёмники, не часть этого ПО. Контракт: uid операторов, ключ партиции, схема, идемпотентность sink, watermark под лаги ведомств.
13. **Чекпоинты живут в S3-совместимом хранилище**, доступном из всех ЦОДов, где вы собираетесь поднимать job. Бакет только в одном ЦОДе = RTO упирается в этот ЦОД.
14. **ForSt и native S3 filesystem из 2.3** в прод 2.2.1 **не** берём (experimental / другая линейка).
15. **Лицензия Apache 2.0** на ядро. Отдельного license-server нет. Следить за составом коннекторов и UDF.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили оператор и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **Зачем именно Flink** (какие job, какой state, какой sink) | Без этого нельзя выбрать backend, интервал чекпоинта, parallelism и даже «нужен ли Flink» |
| **RTT, потери, полоса между ЦОДами** (не ICMP ping, а TCP между будущими TM и до object storage) | Shuffle и выгрузка чекпоинта едут по этой сети. Высокий RTT → долгий чекпоинт, backpressure, ложные fail TM |
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Kubernetes HA хранит lease/ConfigMap **в etcd этого кластера**. Три изолированных K8s ≠ один HA-домен Flink |
| **Где физически бакет чекпоинтов и его репликация** | Падение ЦОДа с бакетом убивает восстановление job, даже если Kafka жива |
| **Retention топиков Kafka vs интервал чекпоинта и max downtime** | Слишком короткий retention + долгий простой = нельзя replay |
| **Профиль лагов интеграций** | Watermark и окна: если ведомство отвечает часами, «watermark 10 секунд» порежет опоздавшие факты |
| **RPO/RTO и что значит «упал ЦОД»** | Flink не даёт RPO=0. Если «ни одного события нельзя переиграть» — это другое требование, чем чекпоинт раз в минуту |
| **152-ФЗ / ПДн в keyed state** | State на диске TM и в S3 — это персональные данные, не «кэш ради скорости» |
| **Совместимость job-jar, коннектора 5.0.0 и брокера 4.3.1** | Коннектор тестируют против линейки Flink, не против «любого Kafka на свете». Прогон на **вашем** 4.3.1 обязателен |
| **Нужен ли exactly-once до внешнего мира** | Если sink — обычный HTTP в озеро без идемпотентности, транзакции Kafka не спасут |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **Flink 2.2.1**, Java **17**, коннектор Kafka **5.0.0**, оператор **1.15.0**. Не смешивать major/minor «как получится».
2. Собрать **свой образ**: базовый `flink:2.2.1-java17` + job-jar + плагин S3 (`opt/flink-s3-fs-presto-2.2.1.jar` → `plugins/s3-fs-presto/`) + любые extra connectors.
3. Выделить **checkpoint + HA directory** на долговечной FS. Проверить, что JM *и* TM туда пишут (IAM/ключи, сеть, clock).
4. Включить **checkpointing** и осмысленный **restart** (при включённом checkpointing дефолт — `exponential-delay`; док его рекомендует, чтобы редкий сбой рестартовался быстро, а лавина — не долбила Kafka).
5. Задать **state backend**. Стенд с крошечным state — HashMap допустим. Прод с неизвестным/большим state — **EmbeddedRocksDBStateBackend** + инкрементальные чекпоинты.
6. Проставить **uid** всем stateful операторам **до** первого боевого savepoint.
7. Безопасность REST: не публиковать 8081; TLS/прокси. Секреты — в Secret/CSI, не в CR (логи оператора).
8. Метрики: duration/size чекпоинта, число failed checkpoint, Kafka source lag, backpressure, heap TM, disk RocksDB, restart count.
9. Прогон: дождаться **успешного** чекпоинта → убить TM → убедиться, что job встал с того же offset/state. Для Kafka-sink exactly-once — смотреть, что `read_committed` потребитель не видит дублей.
10. Только потом — autoscaler, unaligned checkpoints, blue/green оператора, ForSt.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики написали job, увидели UI, прочитали тестовый топик Kafka, отладили watermark/uid. **Не** цель: доказать отказ ЦОДа и ёмкость RocksDB.

Два официальных минимальных пути (выберите один):

**Путь A — локально / один контейнер** (быстрее понять продукт):

```text
docker run --rm -it -p 8081:8081 flink:2.2.1-java17 jobmanager
# в другом терминале / втором контейнере — taskmanager с jobmanager.rpc.address
```

Либо дистрибутив: `bin/start-cluster.sh` (standalone). UI: `http://localhost:8081`.  
Чекпоинт можно оставить в куче JM или на локальный `file:///tmp/flink-cp` — **только** здесь.

**Путь B — оператор в dev-namespace** один `FlinkDeployment`: 1 JM, 1 TM, маленький parallelism, `upgradeMode: stateless` пока граф прыгает каждый час. Пример compose/dev YAML оператора **не** копировать в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число JM / TM | 1 / 1 | Нет требования пережить выкат |
| HA | выкл | Иначе команда утонет в storageDir раньше, чем в DataStream API |
| State backend | HashMap (дефолт) | State крошечный; RocksDB имеет смысл, когда уже есть окна |
| Checkpoint storage | JobManager heap или local file | Док прямо: development / tiny state |
| REST TLS | нет, сеть изолирована | Иначе PKI раньше первой job |
| Kafka guarantee | AT_LEAST_ONCE или даже NONE на игрушечном топике | На тесте важнее увидеть запись; **в коде** лучше сразу ставить тот guarantee, который будет в проде, иначе тест врёт |
| Session cluster | можно | Несколько учебных job на одном кластере |
| CPU/RAM | как в примерах | Не цель — ёмкость |

#### Чего на тесте **не** стоит упрощать

- Версия **2.2.1** и коннектор **5.0.0** — те же, что в проде.
- **uid** операторов и явные имена топиков.
- Понимание, что без checkpointing рестарт **не** восстановит state (дефолт restart = none).
- Не коммитить в git «работает на HashMap без uid» как прод-манифест.

#### Сильные стороны такой схемы

- Поднимается за часы, совпадает с Docker/standalone гайдами.
- Дешево показывает watermarks на *ваших* запоздалых событиях интеграций.
- Single JM официально нормален для development.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет shuffle между узлами, нет выгрузки чекпоинта в S3.
- Успешный map на одной TM **не** доказывает, что RocksDB-чекпоинт уложится в интервал и что MinIO переживёт площадку.
- PLAINTEXT 8081 приучают «зайти без учётки».

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (оператор, application mode, HA + S3, RocksDB, TLS на REST хотя бы внутри mesh, 2 TM, прогон kill TM), даже без боевого трафика.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты озера» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Flink **плохо** копирует паттерн Kafka «один кластер, RF=3, rack awareness». State не реплицируется по ЦОДам как партиция брокера. Официального «stretch Flink на 3 DC» в доке **нет**.

**Вариант A — активный Flink в одном ЦОДе (или в одном K8s-кластере), чекпоинты на хранилище, которое переживает этот ЦОД.**

- JM + TM живут там, где низкий RTT shuffle (обычно одна площадка / тесно связанные зоны).
- Kafka stretch (как в документе Kafka) продолжает принимать события, пока живы 2 из 3 ЦОДов.
- Падение ЦОДа с Flink = **остановка обработки** до восстановления job **в другом ЦОДе** из чекпоинта/savepoint.
- RTO = время: поднять JM/TM + скачать state из S3 + replay Kafka с checkpoint offset. Это **замер**, не слайд. Чем больше RocksDB-state, тем дольше restore (док прямо: RocksDB медленнее heap).
- Нужен заранее прогнанный runbook: тот же образ, тот же `transactionalIdPrefix` (осторожно: конфликт транзакций, если старый job ещё жив), доступ к бакету.

**Вариант B — TM и JM «размазаны» по 3 ЦОДам одного Kubernetes.**

- Один логический job, shuffle и RPC ходят между ЦОДами.
- Kubernetes HA (lease) зависит от **etcd** этого кластера: если K8s сам stretch, вы уже приняли риск etcd+сеть; если нет — варианта B нет.
- Нет порога RTT у проекта Flink. Утверждение «город, значит можно» — **непроверенное**.
- Выкат/PDB: снять сразу много TM одной зоны = большой рестарт и шторм к S3.

**Вариант C — три независимых Flink (по ЦОДу) + разделение входных топиков.**

- Локальный shuffle быстрый.
- Ровно-один раз обработать общекластерный факт **нельзя** «само получится»: получите либо двойную обработку, либо ручной active-passive.
- Это уже несколько экземпляров, не один.

**Пока топология K8s, RTT shuffle и репликация бакета не зафиксированы, нельзя честно выбрать B.** Дальше A — целевой «честный» для неизвестной сети; B — только после замера; C — если обработка изначально шардирована по площадкам.

##### Сильные / слабые стороны (A)

| Сильное | Слабое |
|---|---|
| Shuffle локальный, чекпоинты предсказуемее | Падение ЦОДа Flink = простой обработки (Kafka при этом может быть жива) |
| Понятный DR: restore из S3 на другой площадке | RTO надо **измерить** на реалистичном state |
| Согласуется с «Kafka stretch + мозг в одном месте» | Нужна дисциплина: не оставить два job с одним transactionalIdPrefix |
| Меньше сюрпризов etcd/lease между ЦОДами | Нет автоматического «как ISR, сам продолжил в другом DC» |

##### Сильные / слабые стороны (B)

| Сильное | Слабое |
|---|---|
| Один bootstrap, один job, TM могут пережить локальный узел | Латентность shuffle = латентность job |
| Потенциально переживает отказ **части** TM в одном ЦОДе без переезда кластера | Нет официальной методики «3 DC»; чекпоинт может стать ночным кошмаром по сети |
| | Падение двух ЦОДов / etcd — вне модели |
| | Сетевой шторм между ЦОДами выглядит как деградация Flink, не «сеть виновата» |

##### Сильные / слабые стороны (C)

| Сильное | Слабое |
|---|---|
| Изоляция площадок | Нет единой exactly-once картинки |
| | Три образа, три HA-каталога, тройной ops |

##### Слабое место любого варианта без замера restore

«Терабайты» + RocksDB + чекпоинт в другом ЦОДе могут дать RTO **часы**, если это не прогоняли. Документация не даёт формулы минут. Без прогона kill TM / kill namespace у вас нет отказоустойчивости, есть надежда.

#### Режим деплоя и оператор

- **Application cluster** на каждый боевой пайплайн (или на тесно связанную пачку, но с пониманием blast radius).
- Session в проде — только если сознательно делите «песочницу SQL» и готовы к noisy neighbor. Не смешивать с job, которые кормят озеро эталона.
- HA job:

```text
high-availability.type: kubernetes
high-availability.storageDir: s3p://<bucket>/flink/ha/...
execution.checkpointing.dir: s3p://<bucket>/flink/checkpoints/...
```

`s3p://` — схема плагина Presto, если одновременно нужен Hadoop FS на `s3a://` для FileSink (док S3).  
`file:///flink-data/ha` из примеров оператора — **не** HA на 3 ЦОДа: это том пода.

- `spec.jobManager.replicas` ≥ 2, если хотите короче failover JM. Помнить: job всё равно restart.
- Оператор: `kubernetes.operator.leader-election.enabled: true`, уникальный `lease-name`, `replicas: 2`, `strategy: RollingUpdate`, topologySpread по узлам/зонам. Миграция с 1 реплики — через scale-to-zero (док: иначе старый под без election + новый с election = два активных).
- `upgradeMode`: для stateful прода — `savepoint` или `last-state` (последний требует живых HA metadata). Stateless — только для job без state.
- Native mode оператора, не Standalone, если нужна Job HA.

#### Чекпоинты и state (обязательные правила)

| Параметр | Прод-правило | Зачем |
|---|---|---|
| Checkpointing | включён | Иначе нет восстановления |
| Storage | filesystem на S3/HDFS, не JM heap | HA Overview + Checkpoints page |
| Backend | RocksDB + incremental, пока не доказали что state влезает в heap | Диск vs куча; инкрементальные снимки только у RocksDB среди стабильных |
| ForSt | нет | experimental |
| Unaligned | по умолчанию не включать | Ломает произвольный upgrade (таблица vs savepoints) |
| Externalized checkpoints | RETAIN хотя бы на препроде, пока нет отдельной политики savepoint | Иначе cancel job = нет точки restore |
| Интервал | подобрать **замером** duration checkpoint < interval с запасом | Слишком часто — backpressure; слишком редко — большой RPO и длинный replay |
| Restart | оставить/явно задать exponential-delay | Док: меньше лавина на Kafka при массовом фейле |
| uid | обязательны | Savepoint/rescale |
| Savepoint | перед сменой версии Flink / графа / backend | Canonical, если меняете backend |

Плагин S3 кладётся в образ **до** старта. Access key в `flink-conf` док считает discouraged относительно IAM; на self-hosted MinIO ключи всё равно будут — только не в Git и не в тексте CR.

Каталоги старых `job-result-store` оператор **не** чистит (workaround FLINK-27569): нужна процедура GC, **последний** каталог не трогать.

#### Kafka-стык (у вас это главный вход)

- Source: оффсеты живут в **state Flink**. Commit в Kafka (`commit.offsets.on.checkpoint`) — чтобы людям/лагам было видно progress; **падение commit не ломает** целостность checkpoint (метрика `commitsFailed` в доке).
- Parallelism source ≤ partitions.
- Sink: **не оставлять NONE** на пайплайнах, которые кормят озеро/других консьюмеров, если это не сознательный fire-and-forget.
- Exactly-once: уникальный prefix, `transaction.timeout.ms` с запасом, потребители `read_committed`, внутренние топики транзакций Kafka с RF=3 (это уже документ Kafka).
- Не апгрейдить **одновременно** Flink и версию Kafka-коннектора (официальный upgrade guide коннектора).
- Продюсер Flink всё ещё подчиняется `acks` брокера: док коннектора предупреждает, что «даже после ack возможна потеря», если брокер настроен слабо. Ваш прод Kafka должен оставаться на `acks=all` / min.ISR=2.

#### Масштабирование TM

- Добавлять TM **и** поднимать parallelism (плюс autoscaler позже). Пустые TM без слотов job не ускоряют.
- Rescale stateful job — через savepoint/checkpoint, который это умеет (таблица: aligned checkpoint / savepoint — да; произвольный upgrade с unaligned — нет).
- Диск RocksDB считать от **рабочего state**, не от объёма озера.
- Network buffers / TM memory — отдельные ручки; «просто 64g кучи» отберёт память у managed/RocksDB и сети.

#### Безопасность прода

| Слой | Правило |
|---|---|
| REST 8081 | Не в интернет. Bind на внутренний Service; Ingress только через SSO/прокси. Док: sidecar auth как рекомендуемый паттерн |
| REST TLS | `security.ssl.rest.enabled: true` в проде |
| Internal SSL | включить для RPC/blob/data между JM и TM, свои сертификаты |
| mTLS REST + HA | на старых линейках (1.18) оператор фиксировал конфликт; на 2.2.1 всё равно проверять handshake оператора на стенде, не включать вслепую оба |
| Секреты | K8s Secret / Vault CSI; не поля CR (логи оператора) |
| NetworkPolicy | 8081 — оператор, прокси, админы; RPC/data — только JM/TM; к Kafka — как в документе Kafka; к S3 — JM+TM |
| RBAC K8s | оператор не cluster-admin «на весь мир», если можно сузить; webhook включён осознанно (Helm `--set webhook.create=false` — только отладка) |
| At-rest | шифрование томов TM (RocksDB) и бакета чекпоинтов |
| Аудит | кто ходил на REST, кто менял CR | 
| Job jar | подпись/скан артефакта; UDF — тот же контур, что и код микросервисов |

##### Сильные / слабые стороны (TLS + прокси + RBAC K8s)

| Сильное | Слабое |
|---|---|
| Штатный SSL без отдельной лицензии | Два контура (internal + REST), легко включить один и забыть второй |
| Прокси даёт нормальный SSO, которого у REST нет из коробки | Ещё один компонент в HA |
| Kubernetes HA без ZooKeeper | Зависимость от API server / etcd |
| Не зависит от облачного IAM | Не ГОСТ; ключи MinIO всё равно надо крутить |

#### Kubernetes-специфика прода

- Отдельные pod template JM и TM (ресурсы, диски, affinity).
- TM: anti-affinity / topology spread, чтобы один узел не унёс половину параллелизма без нужды. Для варианта A — **не** размазывать TM по ЦОДам «для галочки HA».
- PDB: не дать Kubernetes снять все TM сразу.
- Лимит памяти пода = `taskmanager.memory.process.size` (+ маленький запас на sidecar, если есть). Лимит = только `-Xmx` без модели Flink → OOM или отказ старта.
- RocksDB: volume с IOPS, не NFS как рабочий каталог TM (NFS уместнее обсуждать как *checkpoint store*, и то с осторожностью; штатный путь чекпоинтов — S3-compatible).
- Rolling: смена образа job = stateful upgrade через оператор, не `kubectl delete pod` «как у stateless».
- Blue/green есть у оператора (с 1.14) — для job, которым нельзя окно рестарта; это **два** кластера и удвоенные слоты на время, не бесплатно.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть: TM↔TM, TM↔Kafka, TM/JM↔S3. Решение A vs B.
2. Поднять бакет чекпоинтов с репликацией, прогнать put/get из каждого ЦОДа, откуда *можете* запускать Flink.
3. Поставить оператор 1.15.0 с leader election (когда replicas > 1).
4. Собрать образ 2.2.1-java17 + presto S3 plugin + connector 5.0.0 + job.
5. Выкатить **небоевой** application job: HA + RocksDB + checkpoint в S3 + REST не снаружи.
6. Дождаться стабильных чекпоинтов. Убить TM. Убить JM. Сверить state/offset.
7. Включить нужный Kafka DeliveryGuarantee, прогнать дубли на `read_committed`.
8. Прогнать restore на **другой** namespace/площадке по runbook варианта A.
9. Снять duration checkpoint / lag / CPU на синтетике. Выставить parallelism и число TM.
10. Подключить первый реальный топик. Savepoint-процедура перед сменой jar.
11. Только потом — autoscaler, второй job, blue/green.

Без пунктов 6–8 у вас нет отказоустойчивости.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Checkpointing + filesystem storage + Kubernetes HA; прогнанный kill TM/JM; DR-restore из бакета, который переживает ЦОД job; цель отказа — **не** «как Kafka RF=3 само» |
| Производительность / масштаб | Не требуется | Parallelism ↔ слоты ↔ партиции Kafka; RocksDB если state не игрушечный; память через process.size; рост TM после замера, не «на всякий случай 100» |
| Безопасность | 8081 только в изоляции | REST не в интернет; TLS; секреты не в CR; шифрование томов и бакета; NetworkPolicy |

**Не готов к проду**, если: checkpointing выключен; storage в куче JM; `DeliveryGuarantee.NONE` на пайплайне в озеро; HashMap при немереном keyed state; demo `file://` HA на одном PVC; 8081 снаружи; оператор `replicas: 2` без leader election; ForSt в бою; Flink 2.3.0 на операторе 1.15.0 без новой матрицы; Flink назначен SoT клиентских данных; RTT/shuffle не мерили, а TM уже в трёх ЦОДах.
