# Apache Flink 2.2.1 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Apache Flink.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Apache Flink — движок потоковой обработки. Ставите **свою** копию, не облако вендора.

Версии: **Flink 2.2.1**, образ `flink:2.2.1-java17` (Java **17** — рекомендуемый рантайм документации 2.2; Java 21 в 2.2 — экспериментально). На Kubernetes — **оператор 1.15.0** (матрица: `2.2.x`, не **2.3.0**). Коннектор к шине: **Kafka Connector 5.0.0**.

Документация: https://nightlies.apache.org/flink/flink-docs-release-2.2/

На дату соседнего файла latest самого Flink — **2.3.0**. Анонс оператора **1.15.0** линейку 2.3 **не перечисляет**. Бой на Kubernetes — **2.2.1 + 1.15.0**, не 2.3.0 «потому что новее».

Kafka остаётся шиной. Flink — обработка, **не** эталон данных и **не** замена брокера.

Один кластер (выбор лидера JobManager и обмен рабочих) на несколько дата-центров здесь **не собираем**. Аренда выбора лидера лежит в Kubernetes **этого** кластера; порога задержки сети для обмена рабочих в документации нет.

---

## О чём эта инструкция молча договорилась

1. **Живой Flink в одном дата-центре.** Выбор лидера и обмен рабочих не размазываем по городам. Другие залы: **отдельный** выкат и переигрывание входа из Kafka той площадки (копия топиков — отдельный контур Kafka).
2. Бой — Kubernetes в каждом дата-центре отдельно. Оператор — Helm **1.15.0**, режим Native.
3. Режим приложения: один запуск на приложение, если нужен запас лидера. Несколько запусков в одном приложении + запас документация **не поддерживает**.
4. Учебный стенд — закрытая сеть. Цифр нагрузки нет — нет числа рабочих «хватит для боя».
5. Снимки боя — объектное хранилище. Куча JobManager — только стенд.
6. Два дата-центра: активный Flink в первом; во втором — независимый выкат (запас до переключения **или** своё задание на своей Kafka). Три — то же в третьем. Два живых задания с одним префиксом транзакций Kafka на одном кластере брокеров — конфликт.
7. Экспериментальный backend состояния на объектке в 2.2 в бой не берём.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** написать задание, увидеть UI, прочитать тестовый топик, отладить имена операторов. **Не зачем:** отказ дата-центра и ёмкость RocksDB.

### Что должно быть до установки

- Docker **или** учебный Kubernetes.
- Порт 8081 свободен на этой машине.
- Java 17, если собираете архив задания без Docker.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name flink-jm \
  -p 127.0.0.1:8081:8081 \
  flink:2.2.1-java17 jobmanager
```

Привязка к `127.0.0.1` обязательна. UI — `http://127.0.0.1:8081`.

Рабочий — в той же Docker-сети, адрес менеджера = имя контейнера (не копировать чужие хосты из старых compose). Снимок на стенде — куча менеджера или локальный файл — **только** здесь.

Проверка: UI открывается, в версии — **2.2.1**. Архив задания с коннектором **5.0.0**, не старый потребитель Kafka из гайдов пятилетней давности.

На Kubernetes для учёбы: оператор **1.15.0** с архива Apache (не `latest`). Минимальный объект: 1 менеджер, 1 рабочий, параллелизм 1, выкат без состояния, пока граф прыгает. Этот YAML **не** в бой.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| 1 менеджер / 1 рабочий | да | Некому строить запас |
| Запас / объектка | выкл | Иначе каталог снимков раньше первого API |
| Состояние | куча (завод) | Состояние крошечное |
| TLS REST | нет | Сеть закрыта |
| Несколько учебных заданий на одном кластере | можно | Экономия |
| Гарантия Kafka | можно без гарантии на игрушечном топике | **В коде** лучше сразу тот режим, что в бою |

Чего **не** упрощаем: Flink **2.2.1**, коннектор **5.0.0**, Java **17**; стабильные имена операторов с состоянием; понимание — без снимков завод **не** перезапускает задание с восстановлением.

### Как понять, что стенд живой

1. Версия 2.2.1, UI только с этой машины.
2. Задание запускается, преобразует, останавливается.
3. Рестарт менеджера без внешнего хранилища снимков — состояние потеряно: это ожидаемо.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный образ | Нет запаса лидера, нет обмена между узлами, нет объектки |
| Один менеджер официален для разработки | Успешное преобразование ≠ снимок RocksDB в интервал |
| | Открытый 8081 приучает «без учётки» |

Перед боем полезен **препрод**: оператор, режим приложения, запас лидера + объектка, RocksDB, 2 рабочих, прогон «убить рабочую» — **в одном** дата-центре.

---

## Бой: один живой дата-центр, второй — переигрывание входа

**Зачем:** пережить отказ **рабочей или JobManager внутри площадки** (снимок + новый лидер); пережить отказ **целого дата-центра** ценой ненулевой потери хвоста: поднять **другой** Flink на другой площадке и переиграть вход из Kafka этой площадки. Цифр рабочих нет.

### Почему кластер не растягиваем на несколько дата-центров

Снимок и обмен рабочих — не три копии каждого события. Выбор лидера хранит указатели во внешнем каталоге + аренду **этого** Kubernetes. Разнести менеджеров по городам = гнать аренду и внутренний вызов через город. Официального «stretch на 3 зала» в документации **нет**. Порог задержки проектом **не задан**.

### Как расставить машины

**В активном дата-центре** — одно логическое задание (лучше отдельный мини-кластер на пайплайн):

- Запас JobManager: тип `kubernetes` (типичный выбор оператора) **или** ZooKeeper, оба — **только ноды этого зала**.
- Копий менеджера не меньше **двух** (запасной **ускоряет** смену лидера; задание **всё равно перезапускается**).
- Рабочие: несколько подов, на разных нодах **внутри** зала, **не** «по чужим залам для галочки».
- Снимки и метаданные лидера — файловая система на объектке (схема плагина Presto, если так собираете образ).
- Образ: база `flink:2.2.1-java17` + архив задания + плагин S3 из `opt/` в `plugins/` + коннектор **5.0.0**.
- Kafka — **локальный** кластер этой площадки.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: живой Flink. Вторая: **отдельный** оператор и выкат (тёплый запас или своё задание на Kafka второй площадки) | Обработка в первой остановилась. Переигрывание на второй со снимка/сейвпоинта **или** с позиции локальной Kafka. Хвост можно потерять. Дубли возможны |
| **Три** | Третий независимый экземпляр | То же; третий Flink не делает «три копии состояния» |

Ровно один раз обработать общекластерный факт «само» при двух активных Flink **нельзя**: либо двойная обработка, либо актив-пассив и сценарий. Префикс транзакций уникален среди заданий на **одном** кластере Kafka; после переключения старое задание должно быть мертво.

Оператор: две реплики **только** с выбором лидера. Падение оператора **не** роняет уже бегущие задания, но не вылечит пропавший менеджер.

### Что должно быть до боевой установки

- Диски с предсказуемой скоростью. RocksDB рабочего — локальный SSD, не сетевая папка как рабочий каталог. Снимок **не** единственная копия на томе одной рабочей.
- Объектное хранилище, куда пишут менеджер **и** рабочие. Бакет только в первом зале = восстановление во втором упирается в этот бакет.
- Сетевая политика: 8081 — прокси/админы/оператор, не интернет; внутренний обмен — только менеджер↔рабочие; к Kafka и объектке — по их документам.
- Секреты — секрет Kubernetes / Vault, **не** поля манифеста: оператор пишет разницу в журнал.

### Порядок установки в активном дата-центре

1. Поставить оператор **1.15.0** (Helm конкретного тега). Выбор лидера включить **до** числа реплик больше одной (миграция с одной реплики — через ноль, иначе два активных контроллера).
2. Собрать свой образ **до** первого боевого задания: без плагина S3 снимок в бакет не уедет.
3. Выкатить **небоевое** задание: запас лидера + RocksDB + снимок в объектку + REST не снаружи.
4. Дождаться стабильных снимков. Убить рабочую. Убить лидера менеджера. Сверить состояние и позицию.
5. Включить нужную гарантию Kafka, прогнать дубли на потребителе подтверждённых записей.
6. Прогнать восстановление в **другом** пространстве имён / на другой площадке по заранее написанному сценарию.

Смысл боевого объекта (не полный файл — сверять с документацией оператора 1.15.0):

```yaml
apiVersion: flink.apache.org/v1beta1
kind: FlinkDeployment
metadata:
  name: proj-job
spec:
  image: <registry>/flink-job:2.2.1-java17
  flinkConfiguration:
    high-availability.type: kubernetes
    high-availability.storageDir: s3p://<bucket>/flink/ha/...
    execution.checkpointing.dir: s3p://<bucket>/flink/checkpoints/...
    # интервал снимка — замером: длительность меньше интервала с запасом; не копировать 10 с из учебника
  jobManager:
    replicas: 2
  # рабочие и параллелизм — после замера; выкат со сейвпоинтом или с последнего состояния; file:// как запас — не бой
```

Путь `file://` из примеров оператора — том пода, **не** запас на отказ площадки.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Снимки | включены, хранилище не куча менеджера | Иначе нет восстановления |
| Состояние | RocksDB + инкрементальные снимки, пока не доказали что влезает в кучу | Диск vs куча |
| Снимки без полного выравнивания | по умолчанию не включать | Ломает произвольную смену графа |
| Внешние снимки после отмены | оставлять, пока нет политики сейвпоинтов | Иначе отмена = нет точки восстановления |
| Перезапуск | нарастающая пауза при включённых снимках | Документация: меньше лавина на Kafka |
| Приёмник Kafka без гарантии | не оставлять на пайплайне в озеро | Заводской режим приёмника — без гарантии |
| «Ровно один раз» | уникальный префикс; таймаут транзакции брокера больше снимка+рестарта; потребители читают подтверждённое | Иначе риск потери или дублей |
| Параллелизм источника | не выше числа партиций | Лишние руки простаивают |
| REST 8081 | не с мира; TLS + прокси (сам REST клиента не опознаёт) | Панель управления кластером |
| Память пода | размер процесса Flink (+ запас рядом живущего контейнера), не «только куча Java» | Иначе отказ старта или убийство пода |

ZooKeeper допустим, если он уже есть **в этом зале**. Это ещё одно голосование; на Kubernetes типичен выбор лидера через Kubernetes. ZooKeeper между залами — тот же запрет размазывать.

Политика сбоя подов: не снимать всех рабочих сразу. Смена образа задания = выкат через оператор, не «удали под как у сервиса без состояния».

### Как расти, когда появятся цифры нагрузки

1. Замерить лаг Kafka, длительность/размер снимка, торможение, кучу рабочего, диск RocksDB, рестарты.
2. Параллелизм ↔ слоты (рабочие × число слотов) ↔ партиции Kafka. Пустые рабочие без слотов задание не ускоряют.
3. Сначала партиции Kafka, потом Flink. Смена параллелизма задания с состоянием — через сейвпоинт / снимок, который это умеет.
4. Автомасштаб оператора — **после** стабильных снимков, не в день первого выката.
5. JobManager почти не масштабируют «от мегабайт в секунду». Много учебных заданий на одном менеджере — антипаттерн боя.

«Терабайты озера» ≠ терабайты состояния. Время восстановления большого снимка **замерить**, формул минут в документации нет.

### Проверки, без которых это ещё не бой

Внутри площадки:

1. Образ 2.2.1-java17, оператор 1.15.0, коннектор 5.0.0. Не 2.3.0.
2. Дождаться **успешного** снимка → убить рабочую → задание встало с той же позиции/состояния.
3. Убить лидера менеджера → новый лидер, задание перезапустилось, каталог метаданных жив.
4. 8081 снаружи — отказ. Секреты не в тексте манифеста.

Между площадками:

5. Копия тестового топика дошла до Kafka второй площадки (это контур Kafka, не этот файл).
6. Учения: остановить Flink первой площадки, поднять выкат второй по сценарию (тот же образ, не два живых приёмника «ровно один раз» с одним префиксом), переиграть вход. Замерить простой и хвост данных.

### Что хорошо и что плохо в схеме «запас внутри зала + отдельный Flink на другой площадке»

| Хорошо | Плохо |
|---|---|
| Обмен рабочих и аренда лидера — локальная сеть | Падение зала Flink = простой обработки, пока переигрывание |
| Согласовано с запретом размазывать Kubernetes | Хвост данных можно потерять; дубли; ручное переключение |
| Выбор лидера без обязательного ZooKeeper | Зависимость от Kubernetes **этого** зала и от бакета |
| | Два активных задания без дисциплины = двойная обработка |

**Не готово к бою**, если: снимки выкл; хранилище в куче менеджера; приёмник без гарантии в озеро; куча при немереном состоянии; учебный файл как запас; 8081 снаружи; оператор две реплики без выбора лидера; экспериментальный backend в бою; **Flink 2.3.0 на операторе 1.15.0**; выбор лидера «на три зала в уме»; Flink назначен эталоном карточек.
