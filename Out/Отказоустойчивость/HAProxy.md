# HAProxy 3.4.3 — развёртывание и настройка

Версия ПО: **HAProxy 3.4.3** (патч линии 3.4 LTS, опубликован 29 июля 2026; на дату подготовки документа это последний стабильный патч текущей LTS).  
Сайт проекта: https://www.haproxy.org/  
Документация линейки 3.4: Starter Guide https://docs.haproxy.org/3.4/intro.html · Management https://docs.haproxy.org/3.4/management.html · Configuration https://docs.haproxy.org/3.4/configuration.html  
Образ: официальный Docker Hub `haproxy:3.4.3` (теги `3.4`, `lts`; Alpine-вариант `haproxy:3.4.3-alpine`).

Линия 3.4 — LTS: на haproxy.org для неё указана поддержка **до Q2 2031**. Нечётные линии (сейчас 3.3, 3.5-dev) живут около года и по правилам проекта **не** кладут туда, откуда нельзя быстро откатиться. В прод берём **уже вышедший патч 3.4.3**, не `latest` и не `3.5-dev`.

Этот текст — не мануал «скопируй `haproxy.cfg`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

HAProxy **не было** в исходном описании архитектуры (Kafka, Camunda, озеро данных, интеграционное API) как отдельный продукт. Ниже — как поставить балансировщик на ту же платформу с Kubernetes и тремя ЦОДами. Это не замена WAF, не Ingress «из коробки Kubernetes» и не шина событий.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Load balancer (балансировщик)** | Штука, которая принимает соединения снаружи и раскидывает их на несколько живых серверов. HAProxy — это процесс, который это делает для **TCP и HTTP** (и, при сборке с QUIC, для HTTP/3). |
| **Reverse proxy (обратный прокси)** | Клиент стучится не в приложение, а в HAProxy. HAProxy проверяет/терминирует TLS, выбирает бэкенд и пересылает. Так устроен вход HTTP. |
| **Frontend** | «Вход»: на каком IP:порту слушаем, TLS или нет, HTTP или TCP. |
| **Backend** | «Ферма»: список серверов + алгоритм (roundrobin, leastconn, …) + проверки живости. |
| **Listen** | Frontend и backend в одном блоке. Удобно для простого TCP (например 6443 → api-серверы). |
| **mode http / mode tcp** | HTTP: HAProxy понимает заголовки, URL, cookies. TCP: просто байтовый тоннель (gRPC без разбора, Postgres, kube-apiserver). Kafka почти всегда **не** кладут в HTTP-режим. |
| **Server / check** | Реальный origin и периодический health check. Мёртвый сервер из балансировки **вычёркивается**. |
| **backup server** | Запасной origin: в игру, когда основные мертвы. |
| **maxconn** | Потолок одновременных соединений (глобально и на frontend/backend). Без него процесс съест FD/RAM и умрёт некрасиво. |
| **nbthread** | Сколько рабочих потоков внутри **одного** worker-процесса. С 2.5 многопроцессный `nbproc` **удалён**; масштаб по CPU — потоки, не «ещё 4 процесса HAProxy». По умолчанию HAProxy заводит поток на каждое доступное ядро. |
| **master-worker** | Режим: отдельный master следит за worker'ами и умеет reload по `SIGUSR2`, не заставляя systemd жонглировать кучей PID. Для systemd это штатный путь (`-W` / `master-worker`). |
| **Reload / `-sf`** | «Мягкая» смена конфига: новый процесс берёт порты, старый дожёвывает уже открытые сессии. Это **не** zero-drop: в Management Guide прямо описаны короткие окна, где при высокой нагрузке часть новых коннектов может отвалиться. |
| **hard-stop-after** | Сколько старый worker имеет право жить после reload. Без лимита «зависшие» keep-alive сессии держат старый процесс часами. |
| **Runtime API / stats socket** | Unix (реже TCP) сокет: снять сервер с фермы, посмотреть сессии, обновить TLS-ticket keys. Это пульт, не веб-админка. |
| **stats page** | Встроенная HTML-статистика. Удобно на тесте. В интернет её **не** выставляют. |
| **PROMEX** | Встроенный Prometheus-exporter (`http-request use-service prometheus-exporter`). В исходниках **не** собирается по умолчанию (`USE_PROMEX=1`); в официальном Docker-образе и типичных пакетах обычно уже есть — проверять `haproxy -vv` («Built with the Prometheus exporter as a service»). |
| **Stick-table** | Таблица в RAM: «этот клиент → тот сервер», счётчики запросов/коннектов для rate limit. **Не** диск и не БД. Reload без peers **обнуляет** таблицу. |
| **Peers** | Протокол, которым несколько HAProxy (или старый и новый процесс при reload) **копируют** stick-table друг другу. Без peers у каждого узла своя правда о лимитах и липкости. |
| **localpeer** | Имя «кто я в секции peers». Должно совпасть с записью `peer` или задаётся явно. |
| **VRRP / Keepalived** | Протокол/демон **плавающего VIP**. HAProxy сам IP между машинами **не** таскает. Официальный Starter Guide: HAProxy хорошо стыкуется с keepalived; для failover IP рекомендуют VRRP/CARP, а не Heartbeat. Keepalived — **другое ПО**. |
| **VIP (virtual IP)** | Адрес, который в каждый момент «держит» один узел пары. Клиенты и DNS смотрят сюда, а не на физические IP балансировщиков. |
| **PROXY Protocol** | Короткий бинарный префикс от балансировщика с реальным IP клиента. Нужен, когда за HAProxy ещё один прокси/WAF и HTTP-заголовкам нельзя слепо верить. Спецификацию проект ведёт сам (`proxy-protocol.txt`). |
| **X-Forwarded-For (XFF)** | Текстовый заголовок с цепочкой IP. Имеет смысл только если **доверяете** тому, кто его поставил. |
| **Health check** | Периодический зонд бэкенда (TCP/HTTP/…). Частота и таймауты — часть отказоустойчивости, не «галочка check». |
| **SO_REUSEPORT** | Опция ядра: новый процесс может bind'иться на тот же порт, не заставляя старый сначала отпустить. На Linux это стабильно с ядра **3.9**; без неё окна дропа при reload больше. |
| **chroot + user** | После старта HAProxy уходит в клетку ФС и сбрасывает привилегии. Официально: после старта файлы с диска он **не** читает (сертификаты — до bind). |
| **TLS offload** | Расшифровка TLS на HAProxy, до origin — HTTP или заново TLS (re-encrypt). |
| **ssl-passthrough** | TCP-режим: TLS не разбираем, выбираем бэкенд по SNI/порту. Сертификат живёт на origin. |
| **QUIC / HTTP/3** | HTTP поверх UDP. В 3.4 это **опциональная** сборка (`USE_QUIC`), не «HAProxy стал UDP-балансировщиком чего угодно». Starter Guide по-прежнему пишет, что HAProxy **не** packet/UDP LB и не делает NAT/DSR. |
| **Data Plane API** | Отдельный sidecar от HAProxy Technologies: REST на конфиг и runtime. **Не** входит в бинарь 3.4.3. |
| **Ingress Controller** | Отдельный продукт `haproxytech/kubernetes-ingress`. На дату документа latest = **3.2.13** (14 августа 2026), и он собран **с HAProxy 3.2**, не с 3.4.3. Это не «тот же инстанс». |
| **ControlPlaneEndpoint** | VIP/DNS перед несколькими `kube-apiserver`. Часто как раз listen TCP :6443 на HAProxy (см. документ по Kubernetes). |
| **Anycast / BGP** | Один и тот же VIP анонсируется с нескольких ЦОДов. Нужен, когда VRRP не пересекает границы L2/маршрутизации. Это сеть ЦОДа, не фича HAProxy. |
| **RPO / RTO** | Сколько готовы потерять / как быстро восстановиться. У HAProxy «данные» — это **конфиг и stick-table**, не клиентская база. |

## Основные элементы системы и зависимости

### Что входит в HAProxy 3.4.3 (это одно ПО)

- Бинарь `haproxy` + один или несколько файлов конфигурации.
- Встроенные frontend/backend/listen, ACL, maps, stick-tables, peers, health checks, runtime CLI, (при сборке) PROMEX, HTTP compression/cache **в RAM**, Lua.
- Утилита проверки конфига: `haproxy -c -f …` — обязательный шаг **до** reload.

Отдельного «кластера HAProxy» с кворумом, как у etcd/Kafka, **нет**. Несколько процессов — это несколько независимых прокси, которые вы склеиваете VIP'ом, DNS, Anycast и/или peers.

### Чего в HAProxy нет (частая путаница)

| Нужно системе | Это не HAProxy | Зачем помнить |
|---|---|---|
| Плавающий VIP между двумя VM | Keepalived / VRRP / CARP / BGP | Без этого два HAProxy — два разных IP |
| Понять HTTP-атаку как WAF | SafeLine / другой WAF; Enterprise-WAF вендора | Community умеет rate limit, ACL, ботов «на коленке», но это не семантический WAF |
| Ingress-объекты Kubernetes → маршруты | Ingress Controller (другой репозиторий и **другая** линия HAProxy) | Бинарь 3.4.3 сам CRD не читает |
| Динамически править конфиг по REST | Data Plane API (отдельный процесс) | Без него — файл + reload / runtime socket |
| Kafka advertised listeners / bootstrap | Клиенты Kafka ходят **напрямую** к брокеру-лидеру | «HAProxy :9092 на все брокеры» ломает протокол так же, как HTTP-LB перед брокерами |
| Балансировка UDP «вообще» / NAT / DSR | IPVS, маршрутизаторы, eBPF-LB | Официальный список «HAProxy is not» |
| Хранить ответы на диске как CDN | Varnish (Starter Guide прямо отсылает туда) | Кэш HAProxy — RAM, чтобы **себе** сэкономить, не origin |
| ГОСТ TLS / СКЗИ | Не заявлено для vanilla OpenSSL-сборки | Если требование ИБ — отдельный контур |
| Единый stateful-кластер на 3 ЦОДа | Нет | Состояние — локальная RAM (+ peers, если включили) |

### Зависимости окружения (обязательны)

- **ОС:** Linux (типичный прод). Официальные пакеты/Docker — Linux amd64/arm64. Windows как хост балансировщика проектом не описывается.
- **Ядро Linux ≥ 3.9**, если хотите нормальный reload через `SO_REUSEPORT` (Management Guide). Для Docker-образа 2.4+ ещё: ядро ≥ 4.11, если слушаете порты &lt; 1024 не от root (`net.ipv4.ip_unprivileged_port_start=0`).
- **Не swap.** Starter Guide: машина **never ever** не должна уходить в swap; CPU нельзя искусственно душить «долей ядра» гипервизора на нагруженном прокси.
- **Системные лимиты:** `ulimit -n` / `LimitNOFILE` согласованы с `maxconn` (каждое соединение ≈ несколько FD).
- **Syslog** (или stdout в контейнере) + ротация. Без логов вы не отличите «бэкенд тупит» от «мы режем клиентов».
- **Часы (NTP):** TLS, логи, peers. Расхождение ломает отладку и часть TLS.
- **PKI** для frontend-сертификатов и (если нужно) mTLS к origin.
- **Keepalived** — только если выбран VIP внутри одного L2/маршрутного домена. Это отдельный пакет, отдельный выкат.
- **Kubernetes (у вас заявлен):** оркестрация приложений. Сам HAProxy на краю чаще живёт **на VM/bare metal** или в hostNetwork; Ingress Controller — отдельное решение со своей версией движка.

Официальный ориентир по CPU (не ваш замер): Starter Guide считает, что **одного ядра хватает &gt;99% установок**; много потоков нужны в основном под TLS и каналы **&gt; ~40 Gbps**. Первая реакция на странный перф часто — **уменьшить** число CPU у процесса, чтобы не прыгать между сокетами разных физических CPU. Это контринтуитивно и сказано авторами, не «народная мудрость».

Цифры бенчмарков в том же разделе (Core i7 3.7 GHz, HAProxy **1.6**, ядро 3.10, 10GbE) — **порядок величины 2010-х**, не ёмкость вашего периметра. Более свежий публичный бенчмарк вендора: HAProxy 2.4, 64 ядра Graviton2, ~2 млн HTTPS RPS / 100 Gbps — тоже чужое железо. Для вас оба набора — только «TLS дороже plaintext», не план закупки.

### Как HAProxy стыкуется с вашей архитектурой

Два разных места, их нельзя смешать в одну «ферму на всё»:

```
Клиенты, браузеры, входящие HTTP/колбэки ведомств
        │
  DNS / городской LB / Anycast     ← не входит в HAProxy
        │
  HAProxy (периметр ЦОДа)          ← этот документ, роль A
        │
  SafeLine WAF / Ingress / Integration API
        │
  микросервисы, Camunda
        │
  Kafka, озеро данных              ← HAProxy сюда обычно НЕ ставят
```

```
kubeadm HA:
  kubectl / controllers
        │
  HAProxy listen :6443             ← этот документ, роль B
        │
  kube-apiserver (по экземпляру на control-plane)
```

Правильное место HAProxy — **вход TCP/HTTP** и **HA control plane**. Он не заменяет:

- SASL/TLS Kafka и прямой доступ клиента к брокеру;
- семантику Integration API («какие ведомства дергать»);
- NetworkPolicy внутри кластера;
- WAF на содержимое HTTP (у вас на это отдельный продукт).

Если повесить HAProxy **и** отдать тот же Service наружу в обход — балансировщик становится декорацией.

## Краткие вводные

### Зачем вам HAProxy в этой архитектуре

1. **Отказ одной VM/пода origin** не должен ронять вход: health check вычёркивает мёртвых.
2. **Несколько реплик Integration API / портала / Ingress** в одном ЦОДе нужно склеить в один IP.
3. **kube-apiserver** в HA по kubeadm требует ControlPlaneEndpoint — часто это HAProxy.
4. **Три ЦОДа:** клиент должен попадать на **живой** вход площадки. Это уже VIP/DNS/Anycast **перед** или **вместо** «одного HAProxy на город».

### Как устроена отказоустойчивость (идея, не магия)

HAProxy **stateless по задумке** (Starter Guide): takeover должен быть возможным без «восстановления БД балансировщика».

| Что падает | Что происходит |
|---|---|
| Один origin в backend | Check снимает его, остальные получают трафик |
| Процесс HAProxy на узле | Этот VIP/под **мёртв**, пока не перезапустится или пока Keepalived/K8s не перенесёт IP |
| Один ЦОД | Узлы двух других **не** «выбирают нового лидера HAProxy». Нужен городской механизм (DNS/Anycast/LB), который перестанет слать на мёртвую площадку |
| Reload | Короткие окна дропа новых коннектов; старые сессии доживают на старом worker |
| Stick-table без peers | После reload/падения узла липкость и rate-limit **с нуля** |

Следствие: HA входа = **минимум два живых HAProxy**, которые снаружи выглядят как один адрес, плюс health check, плюс (если нужны лимиты/липкость) **peers**. Один процесс на три ЦОДа отказоустойчивости **не даёт**.

Keepalived решает задачу «два NIC в одном широковещательном домене делят VIP». Он **не** решает «три ЦОДа в одном городе», пока сеть не даёт либо растянутый L2 (обычно плохая идея), либо unicast VRRP **и** маршрутизацию VIP, либо BGP/Anycast.

### Как устроено масштабирование

Два независимых рычага:

1. **Вертикально** — ядра под TLS (`nbthread`, но не больше, чем полезно по NUMA), `maxconn`, NIC queues, **не swap**. TLS handshake жрёт CPU; keep-alive дешевле. Официальное правило большого пальца: порядок RPS падает примерно **в 10 раз** от TLS keep-alive к TLS resume и ещё раз к полному handshake с RSA.
2. **Горизонтально** — ещё узлы за VIP/DNS/Anycast. Каждый узел — свой процесс, свой `maxconn`. Это умножает ёмкость **и** даёт HA.

HPA «replicas: 50» в Kubernetes **без** стабильного IP и без peers даёт 50 независимых лимитеров и ломает sticky sessions.

«Терабайты озера» на размер HAProxy почти не влияют. Влияют: **новые TLS-сессии/с**, размер заголовков, keep-alive vs close, websocket/long-poll интеграций, не «объём Kafka на диске».

### Безопасность самого HAProxy

Процесс на периметре видит (в HTTP-режиме) URL, заголовки, часто cookies, при offload — содержимое до origin. Stats socket и stats page — это **полный пульт** фермы. Выставить `:8404` в интернет = отдать карту бэкендов и кнопки drain.

После старта бинарь специально **не** ходит в ФС: компрометация процесса не равна «читает весь диск», но равна «видит трафик, который через него идёт».

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём community HAProxy 3.4.3**, не HAProxy Enterprise / HAProxy One. Лицензия, WAF, центральная консоль у коммерческой линейки другие.
2. **Целевая роль прода — L4/L7 на выделенных Linux VM (или hostNetwork-поды) на краю ЦОДа**, плюс отдельный маленький listen для kube-apiserver, если control plane свой. Ingress Controller 3.2.13 — **запасной** путь «всё внутри K8s», с движком **3.2**, не 3.4.3.
3. **Перед фермой HAProxy (меж ЦОДами) есть или будет механизм направления клиентов на живую площадку**: DNS с health, городской ADC, Anycast. Сам HAProxy три ЦОДа в один VIP не склеит.
4. **Внутри ЦОДа для пары HAProxy есть L2 или unicast VRRP + маршрутизируемый VIP.** Если ИТ скажет «только L3, VIP нельзя» — Keepalived бесполезен, нужен BGP или внешний LB.
5. **Три ЦОДа = три домена отказа.** На каждый живой ЦОД — свой вход HAProxy (лучше пара). Stretch «один Keepalived на три зала» не рассматривается.
6. **Нагрузки HTTP/TLS нет** — поэтому **нет** числа узлов и ядер «хватит для прода». Есть минимум размещения (вход в каждом ЦОДе) и правило роста.
7. **Формального SLA нет.** Схема «пара в ЦОДе + городской failover» переживает отказ 1 ЦОДа **по входу**, если DNS/Anycast это умеют. Это не юридический 24/7.
8. **HAProxy не ставится перед брокерами Kafka** как единственный `:9092`. Исключение — осмысленный TCP с **отдельным frontend на каждый брокер** и честными advertised listeners; это отдельный дизайн, его здесь нет.
9. **Корпоративный PKI есть или будет.** Hostname verification и нормальные цепочки; «ssl verify none на origin в проде» не считаем настройкой.
10. **Шифрование канала — обычный TLS OpenSSL-сборки.** ГОСТ не озвучен; vanilla 3.4.3 его не закрывает.
11. **Тестовый стенд изолирован.** На нём допустим HTTP и открытый stats. Прод-TLS и закрытый runtime socket на тест один в один не копируем, но **health check и `haproxy -c` перед reload** лучше включить сразу.
12. **Camunda, озеро, Integration API** — origin'ы (или живут за Ingress/WAF). Их таймауты (лаги ведомств) должны попасть в `timeout server` / `timeout tunnel`, иначе HAProxy рвёт легитимные долгие опросы.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** закупки VIP и «постановки в прод».

| Пробел | Почему это ломает решение |
|---|---|
| **Есть ли городской LB / Anycast / DNS failover между 3 ЦОДами** | Без этого три HAProxy — три острова. Keepalived внутри ЦОДа город не спасёт. |
| **L2 / возможность VIP внутри ЦОДа** | Нет L2 и нет BGP — нет классической пары active-passive. |
| **RTT и потери между ЦОДами** | На проверку локального origin почти не влияет. Влияет на: Anycast/гео-DNS, peers **между** ЦОДами (обычно **не** делают), и на соблазн тащить HTTP origin «в чужой ЦОД». |
| **Какой трафик реально идёт через HAProxy** (только входящий HTTP? 6443? gRPC Camunda? колбэки ведомств? websocket?) | От этого зависят mode, таймауты, TLS vs passthrough, нужен ли WAF за/перед HAProxy. |
| **Профиль нагрузки** (новые коннекты/с, RPS, доля TLS, размер заголовков, пик) | Без этого нельзя сказать ни `maxconn`, ни ядра. «Готовы к высокой» без замера — пустая фраза. |
| **Топология Kubernetes** (один кластер на 3 зоны или три кластера) и где Ingress | HAProxy перед Ingress, вместо Ingress, или только 6443 — три разных схемы обхода и реального IP. |
| **Где стоит SafeLine** | Порядок «клиент → HAProxy → WAF → origin» vs «клиент → WAF → HAProxy» меняет PROXY/XFF и health checks. |
| **Требования ИБ: ГОСТ, 152-ФЗ, КИИ, запрет привилегированных подов** | Меняют TLS, hostNetwork, возможность Ingress Controller. |
| **Нужна ли липкость / rate-limit на периметре** | Тогда peers обязательны; иначе два узла = двойная квота атакующему и «прыгающий» пользователь. |
| **Долгие интеграции (минуты ожидания ведомства)** | Дефолтные `timeout server` порядка секунд **убивают** сценарий Integration API. Это надо замерить, не угадать. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **3.4.3** (`haproxy -v`), не `latest`. Проверить `haproxy -vv`: OpenSSL, PROMEX, QUIC (нужен ли он вообще).
2. Один главный `haproxy.cfg` (+ дробление `-f`, если файлов много), в Git; применение только через `haproxy -c` затем reload.
3. `defaults`: явные `timeout connect/client/server` (и `timeout tunnel` для websocket/long-poll). Молчаливые дефолты — источник ночных обрывов.
4. Health check на каждый server; `option httplog` / `tcplog`; логи не в контейнер «навсегда без ротации».
5. Runtime socket **только** unix + права; stats/metrics не с мира.
6. TLS: современные `ssl-min-ver`, cipher suite, отдельные bind `:443 ssl crt …`; редирект 80→443 осознанно (не ломая health check LB).
7. Мониторинг: процесс жив, `maxconn` не упирается, status бэкендов, latency, ошибки reload, очередь.
8. Учение: выключить один origin, выключить один HAProxy, сделать reload под синтетикой.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** понять frontend/backend, научить приложения ходить на VIP/DNS балансировщика, отладить health check и таймауты интеграций. **Не** цель: доказать отказ ЦОДа и TLS-ёмкость прода.

#### Топология

Одна VM или один Deployment/Pod:

- образ `haproxy:3.4.3` **или** пакет 3.4.3 с той же линии;
- один frontend HTTP `:80` на тестовый Service/Ingress;
- `mode http`, roundrobin, `check`;
- stats `:8404` **только** на loopback/VPN;
- без Keepalived, без peers, без TLS (если сеть закрыта);
- `master-worker` всё равно лучше включить: тот же путь reload, что в проде.

Для роли B (kube-apiserver) на тесте часто хватает одного listen TCP на единственный api-сервер — это не HA, это «чтобы kubeconfig смотрел в одно место».

Community Ingress Controller на тесте допустим как эксперимент «как Ingress», но это **другая** версия движка; не смешивайте его `haproxy.cfg` с ручным 3.4.3.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Один процесс | да | Некому делить VIP |
| PLAINTEXT | да, если сеть закрыта | Иначе утонете в PKI до маршрутов |
| Keepalived / peers | нет | Нет второго узла |
| Жёсткий `maxconn` | мягкий запас | Нет нагрузки |
| stats HTML | можно | Учиться смотреть ферму |

#### Чего на тесте **не** стоит упрощать

- Всегда `haproxy -c` перед reload.
- Реальные **таймауты** под долгие интеграции — иначе в проде «внезапно» начнут рваться колбэки.
- Клиенты ходят **на адрес HAProxy**, не в обход на под.
- Хотя бы один HTTP check, а не только TCP :443 (TLS-порт может быть открыт, а приложение мертво).
- Версия образа pinned, не `haproxy:latest`.

#### Сильные стороны такой схемы

- Поднимается за часы; совпадает с Docker Hub quickstart и Starter Guide («исполняемый файл + конфиг»).
- Дешёвая.
- Достаточна, чтобы поймать ошибку mode/таймаутов до прода.

#### Слабые стороны (обязательно понимать)

- Падение VM = нет входа, если DNS указывает только сюда.
- Стенд **не** ловит: окна reload под нагрузкой, VRRP split-brain, peers, CPU TLS, NUMA.
- Успешный тест на одном процессе **не** является доказательством трёх ЦОДов.

Практическая рекомендация: препрод = **пара HAProxy + Keepalived (или два пода + Service) + TLS**, даже без боевого RPS. Иначе первый сюрприз — «после reload пропал rate-limit» или «VIP застрял на мёртвой машине».

---

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под высокую нагрузку» **нет**. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

**Вариант A — целевой: в каждом ЦОДе пара HAProxy 3.4.3 (VIP внутри площадки) + городской механизм на три VIP.**

```
                 клиенты
                    │
         DNS / Anycast / городской ADC
            ┌───────┼───────┐
            ▼       ▼       ▼
         VIP-ЦОД1 VIP-ЦОД2 VIP-ЦОД3
            │       │       │
         HAProxy  HAProxy  HAProxy     по 2 узла + Keepalived (если есть L2/VIP)
            │       │       │
         WAF / Ingress / API **этого** ЦОДа
```

- Падение 1 узла в ЦОДе: VRRP/K8s переносит VIP (или Service исключает под).
- Падение 1 ЦОДа: городской слой перестаёт слать сюда. HAProxy в других залах об этом **не договаривается**.
- Origin — **локальный** (не тащить HTTP через город «на всякий случай»).

**Вариант B — Anycast: один и тот же VIP анонсируется с HAProxy каждого ЦОДа (BGP).**  
Мощно, если сеть это умеет. Сложность и split-horizon — на сетевиках. Peers между ЦОДами всё равно обычно **не** включают (RTT, партиционирование таблицы, смысл rate-limit «на город» vs «на площадку»).

**Вариант C — только Ingress Controller 3.2.13 в Kubernetes.**  
Имеет смысл, если вход = HTTP(S) в кластер и вы сознательно живёте на линии **3.2**. Снаружи всё равно нужен MetalLB/BGP/внешний VIP. **Не** закрывает kube-apiserver и не заменяет WAF. Не обещает те же фичи, что 3.4.3 (dynamic backends 3.4 и т.д.).

**Вариант D — один HAProxy на всю систему.**  
Не удовлетворяет отказу площадки. Для прода не рассматривать.

**Пока нет ответа «как клиент выбирает ЦОД при аварии» — нельзя честно включить A в план «просто шесть VM».** Дальше описывается **вариант A**.

##### Сильные / слабые стороны варианта A

| Сильное | Слабое |
|---|---|
| Отказ 1 ЦОДа не гасит вход, если DNS/Anycast живой | Зависимость от **другого** ПО/сети на межЦОДовый failover |
| Отказ 1 VM внутри ЦОДа закрывается Keepalived/K8s | Keepalived — свой split-brain, свои скрипты track |
| Конфиг и версия одинаковые, выкат по площадкам | Три копии `haproxy.cfg`; без GitOps разъедутся |
| Совпадает с официальной моделью «stateless + VRRP» | VRRP не масштабируется на 3 ЦОДа сам |
| Апгрейд: снять узел с VIP → reload/restart → вернуть | Reload не zero-drop; катить все площадки сразу = риск |

##### Keepalived (обязательные условия, не рецепт `keepalived.conf`)

- Ставить **только** если VIP реален в этой сети.
- Приоритет VRRP снижать, когда HAProxy мёртв (`track_script` / health), иначе VIP висит на машине, где прокси уже нет — это классический простой.
- Unicast VRRP, если нет мультикаста между двумя машинами — решение сети, не HAProxy.
- Не растягивать один VRRP-инстанс на три ЦОДа.

##### Сильные / слабые стороны Keepalived рядом с HAProxy

| Сильное | Слабое |
|---|---|
| Официально рекомендуемый класс failover IP | Другой демон, другой выкат, свой мониторинг |
| Быстрее типичного DNS TTL | Нужен L2 или продуманный unicast+маршруты |
| Пара в одном зале понятна эксплуатации | Split-brain = два VIP-холдера или ноль |

#### Узлы, CPU, сеть

**Минимум HA входа:** 2 процесса в ЦОДе × 3 ЦОДа = 6. Это минимум **размещения**, не ёмкость.

Дальше рост:

- упёрлись в CPU TLS на пике новых рукопожатий → сначала вертикаль и reuse сессий (keep-alive), потом **ещё пара** в том же ЦОДе в пул (если городской LB умеет N бэкендов) или больше ядер **без** прыжков между NUMA;
- добавлять ёмкость лучше **равномерно по ЦОДам**, иначе весь запас в одном зале.

На каждом узле:

- выделенная VM или tainted-ноды; не соседствовать с Kafka-брокерами, которые выбивают кэш и IRQ;
- `nbthread` начать с числа ядер **сокета**, не «все 128 потоков на двух сокетах» без замера (Starter Guide: межсокетный трафик — тормоз);
- `maxconn` по RAM: официальный порядок из sizing (железо 1.6!) — тысячи TLS-коннектов на ГБ; у вас свой замер, не копировать 8000 как закон;
- `ulimit` ≥ запаса над `maxconn`;
- IRQ: на тяжёлом TCP официальный Management Guide советует **выключить irq_balance** и руками развести очереди NIC и потоки HAProxy. На тесте с 2 ядрами это рано; на 40 Gbps — уже предмет настройки, не «оставим дефолт ОС»;
- NTP, лимиты conntrack, если трафик идёт через netfilter (часто лучше **не** фильтровать datapath лишними iptables).

Peers **внутри ЦОДа** (два узла одной пары): да, если есть stick-table (липкость, rate-limit). Канал peers — отдельный порт, **не** мир; лучше TLS или изолированный VLAN. Peers **между ЦОДами**: обычно нет (разный смысл лимита, RTT, партицион при отказе сети).

#### Обязательные настройки «долговечности» входа

| Настройка | Прод-значение | Зачем |
|---|---|---|
| Версия | pinned **3.4.3** на всех узлах | Иначе поведение ACL/TLS разъедется |
| `master-worker` | да | Штатный reload |
| Проверка конфига | `haproxy -c` в CI и в unit-файле перед reload | Иначе «синтаксис убил вход» |
| Reload | `-sf` / SIGUSR2, не `kill -9` | Сохранить сессии |
| `hard-stop-after` | явное значение (минуты, по длине ваших сессий) | Не копить старые worker'ы |
| Health check | HTTP к origin (или TCP+TLS к api-серверу) | TCP :443 врёт |
| `option redispatch` / retry | осознанно | Иначе клиент навсегда прилипнет к мёртвому серверу при частичных сбоях |
| Peers | если stick-table есть | Reload и второй узел не обнуляют политику |
| VIP failover | track состояния HAProxy | VIP без прокси = чёрная дыра |
| Апгрейд | по одному узлу, VIP снят | Окна reload × 3 ЦОДа сразу недопустимы |
| Origin | этот ЦОД | Не строить скрытую зависимость от чужого зала |

Прогон «узел недоступен»: выключить VM HAProxy, убедиться что VIP уехал и клиенты живы.  
Прогон «ЦОД недоступен»: выключить вход площадки, убедиться что городской слой перестал слать сюда, две другие отвечают **тем же** TLS и теми же маршрутами.  
Прогон reload: под синтетикой; зафиксировать долю 502/connection reset. Management Guide: ориентир **~1 обрыв на 10000 новых коннектов/с на один reload** (не гарантия на вашем ядре).

Без этих прогонов у вас нет отказоустойчивости, есть надежда.

#### Масштабирование под нагрузку (когда цифры появятся)

Порядок, не гадание:

1. Замерить: новые TLS/с, RPS keep-alive, размер заголовков, concurrent, пик интеграций.
2. Снять CPU (`haproxy` vs softirq), `maxconn` usage, очередь backend, latency p99.
3. Если CPU в HAProxy при plaintext — часто виноваты логи/regex/Lua, не «мало ядер».
4. Если CPU в handshake — сессии, tickets, железо AES-NI, не слепой `nbthread=128`.
5. Если FD/maxconn — сначала лимиты и keep-alive, потом горизонталь.
6. Горизонталь = новые узлы в пул городского LB / новые Anycast-инстансы, не «ещё replicas без VIP».

Кэш RAM и compression включать точечно: они жрут CPU и память; Starter Guide предупреждает, что это не замена Varnish.

#### Безопасность прода (без этого периметр не считается настроенным)

Слои:

1. **Сеть**
   - На мир: только 80/443 (и реально нужные listen). Не stats, не runtime, не peers, не 6443 control plane.
   - 6443 kube-apiserver — только из административных сетей / внутренних CIDR, не «как у сайта».
   - Peers и stats socket — unix или внутренний VLAN + firewall.
   - Origin принимает трафик **только** с IP HAProxy (и WAF, если он следующий hop). Иначе балансировщик обходят.

2. **Процесс**
   - `user`/`group` не root после bind (в официальном образе 2.4+ уже `USER haproxy`).
   - `chroot` если ставите с пакета и понимаете пути сертификатов (в контейнере часто уже минимальный ФС).
   - Не `privileged` в K8s без нужды; hostNetwork — осознанно (нужен для VIP/host ports).

3. **TLS**
   - `ssl-min-ver TLSv1.2` (лучше 1.3 где клиенты умеют); слабые шифры выключить глобально (`ssl-default-bind-options` / cipher list).
   - Приватники сертификатов — файлы с правами, не ConfigMap в Git.
   - К origin: re-encrypt или mTLS, если сеть ЦОДа не считается доверенной.
   - TLS tickets: при нескольких узлах ключи надо **синхронизировать** (CLI умеет обновлять secrets) — иначе резюме сессий прыгает между узлами впустую. Это легко забыть.

4. **Идентификация и пульт**
   - Stats page: auth + не интернет; лучше вообще только PROMEX на localhost и scrape с агента.
   - Runtime API: unix socket, группа админов; TCP stats с паролем — запасной вариант хуже unix.
   - Data Plane API, если появится: TLS, отдельная учётка, не мир.

5. **Заголовки и реальный IP**
   - За городским LB: ждать PROXY Protocol **или** XFF только от доверенных hop. `forwardfor` слепо с мира = подделка IP.
   - WAF/приложение должны доверять IP только с адресов HAProxy.

6. **ACL / rate-limit**
   - Stick-table + peers в ЦОДе, если лимитируете. Иначе атакующий бьёт квоту × число узлов.
   - Allowlist IP ведомств **до** жёстких антибот-правил на тех же URL.
   - Это не замена WAF.

7. **Поставка**
   - Образ/пакет из вашего registry, digest pinned.
   - Конфиг — GitOps; ручной `vi` на одном ЦОДе = дрейф политики входа.
   - Секреты не в Git.

8. **Наблюдаемость**
   - PROMEX `/metrics` с localhost; логи в центральный сборщик (в логах HTTP будут URL — вопрос 152-ФЗ).
   - Алерт: backend DOWN, `maxconn` saturating, failed reload, Keepalived сменил state, истекающий сертификат.

##### Сильные / слабые стороны выбранной ИБ-схемы

| Сильное | Слабое |
|---|---|
| Узкая поверхность: после старта нет обхода ФС | Процесс всё равно видит трафик периметра |
| Unix socket вместо веб-админки | Операторы часто открывают stats «на час» и забывают |
| TLS offload в одном месте | Компрометация узла = компрометация ключей сайтов (если не passthrough) |
| Origin закрыт firewall | Один «временный» NodePort/Ingress в обход = дыра |
| Не ГОСТ | Если СКЗИ обязательны — community OpenSSL-сборка не ответ |

#### Kubernetes-специфика (как жить с фактом «у нас K8s»)

Честная схема для **3.4.3**:

- Кластер — приложения, Kafka, Camunda, Integration API.
- HAProxy 3.4.3 — **рядом**: dedicated VM или DaemonSet/hostNetwork на edge-нодах, VIP через Keepalived/MetalLB/BGP.
- Не HPA по CPU без понимания `maxconn` и без peers.
- `hostNetwork` + `NET_BIND_SERVICE`, не полный privileged, если хватает.
- ConfigMap/Secret → файл, reload по sidecar/`kill -HUP` (официальный Docker: `SIGHUP` → wrapper → `-sf`). Помнить окна дропа.
- Anti-affinity: два пода HAProxy **не** на одной ноде и не в одной зоне, если это «пара ЦОДа».

Если вход должен быть «чистый Ingress»:

- отдельный релиз **Ingress Controller 3.2.13**, pin образа;
- не ждать, что это тот же 3.4.3;
- снаружи всё равно VIP;
- CRD v1 `ingress.v1.haproxy.org` вендор планирует убирать в линии 3.4 контроллера — закладывать v3 заранее, если пойдёте этим путём.

Control plane: маленький dedicated HAProxy (или тот же, но **другой frontend** с жёстким ACL) на 6443. Смешивать интернет-:443 и api-сервер на одном bind без ACL — плохая привычка.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Закрыть таблицу пробелов: городской failover, VIP внутри ЦОДа, карта портов, таймауты интеграций, место WAF.
2. Зафиксировать 3.4.3 и артефакт (deb/rpm/Docker digest).
3. Поднять **один** узел на препроде: HTTP→origin, логи, metrics.
4. Включить TLS и закрыть stats.
5. Второй узел, Keepalived или Service, учение «узел мёртв».
6. Peers, если нужны таблицы.
7. Прогон reload под нагрузкой; выставить `hard-stop-after`.
8. Повторить шаблон в ЦОД 2 и 3; конфиг из одного Git.
9. Включить городской failover; учение «ЦОД мёртв».
10. Только потом боевые DNS. Синтетика с TLS. По результату — ядра и число пар.
11. Катить апгрейды по одному узлу; внутри 3.4 патчи автор считает безвредными для конфига, **мажор** — читать Breaking changes, не «просто latest».

Без пунктов 5, 7 и 9 у вас нет отказоустойчивости.

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | Пара HAProxy на ЦОД + VIP/K8s Service; городской failover на 3 площадки; health check; переживает 1 VM и 1 ЦОД **по входу**; origin локальный |
| Производительность / масштаб | Не требуется | `maxconn`/FD по замеру; `nbthread` без NUMA- locа; горизонталь = узлы, не слепой HPA; TLS учитывается отдельно от plaintext; не swap |
| Безопасность | Stats не в интернет; тестовый HTTP допустим | TLS 1.2+; runtime/stats/peers закрыты; origin не в обход; pin 3.4.3; GitOps конфига; реальный IP только от доверенных hop |

**Не готов к проду**, если: один процесс на три ЦОДа; `haproxy:latest`; stats :8404 с мира; нет health check; Kafka через один TCP frontend на все брокеры; Keepalived без track процесса; peers нет, а rate-limit «есть»; reload без `-c` и без `hard-stop-after`; origin публикуется напрямую; городской отказ ЦОДа не учений; Ingress Controller 3.2 выдают за «мы на 3.4.3»; ждут, что HAProxy заменит WAF и Integration API.

## Источники (чтобы не принимать на веру)

- Релизы и LTS-окно 3.4 (Q2 2031), пакет 3.4.3 от 2026/07/29: https://www.haproxy.org/
- Что HAProxy делает и **не** делает, VRRP/keepalived, stick-tables и peers, sizing и оговорки бенчмарков, odd/even ветки: https://docs.haproxy.org/3.4/intro.html
- Reload/`-sf`, окна дропа, `SO_REUSEPORT` и ядро 3.9, master-worker, `nbproc` (исторический, с 2.5 удалён), irq_balance: https://docs.haproxy.org/3.4/management.html
- Ключевые слова конфига (nbthread, maxconn, timeouts, ssl, quic, prometheus-exporter): https://docs.haproxy.org/3.4/configuration.html
- Официальный образ `haproxy:3.4.3`, reload через SIGHUP: https://hub.docker.com/_/haproxy
- PROMEX не в дефолтной сборке исходников, `USE_PROMEX=1`: addons/promex в исходниках HAProxy
- Ingress Controller **3.2.13**, собран с HAProxy **3.2** (не 3.4): https://github.com/haproxytech/kubernetes-ingress/releases · https://www.haproxy.com/blog/announcing-haproxy-kubernetes-ingress-controller-3-2
- Анонс линии 3.4 (dynamic backends, cpu-affinity, OpenTelemetry; OpenTracing deprecated): https://www.haproxy.com/blog/announcing-haproxy-3-4
- PROXY protocol: `proxy-protocol.txt` в документации той же линейки 3.4

Утверждения вида «N Gbps на нашу ферму» или «Keepalived сам склеит три ЦОДа» в документации HAProxy **отсутствуют** — поэтому в этом файле их нет. Порог RTT, при котором peers или Anycast «ещё можно», проектом **не задан**; пока замер сети не сделан, межЦОДовый stateful (stick-table на город) в план не кладём.
