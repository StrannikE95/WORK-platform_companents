# HAProxy 3.4.3 — термины и сокращения

Словарь к файлу `HAProxy.md`. Список линейный, не таблица. Сверху — слова, без которых не читаются остальные. Аналогий нет: только что это делает в коде и на диске.

---

**Процесс** — запущенная программа `haproxy`. Отдельного «кластера HAProxy» с кворумом, как у etcd/Kafka, **нет**. Несколько процессов — независимые прокси, которые склеивают VIP, DNS, Anycast и/или peers.

**Файл / каталог на диске** — конфиг (`haproxy.cfg` + дробление `-f`). После старта при `chroot` бинарь файлы с диска **не** читает (сертификаты — до bind). Stick-table — RAM, не диск. Проверка до reload: `haproxy -c -f …`.

**TCP-порт** — вход frontend (80/443, 6443 для apiserver). Stats/runtime/peers — не с мира. Каждое соединение ≈ несколько файловых дескрипторов (FD); `ulimit -n` / `LimitNOFILE` согласованы с `maxconn`.

**ЦОД** — отдельная площадка. Stretch «один Keepalived на три зала» не рассматривается. На каждый живой ЦОД — свой вход (лучше пара). Origin — **локальный**.

**RTT** — время туда-обратно. На проверку локального origin почти не влияет. Влияет на Anycast/гео-DNS, peers **между** ЦОДами (обычно **не** делают) и на соблазн тащить HTTP origin «в чужой ЦОД». Порог, при котором peers или Anycast «ещё можно», проектом **не задан**.

**TLS** — шифрование. Offload — расшифровка на HAProxy. Re-encrypt — заново TLS до origin. vanilla OpenSSL-сборка, не ГОСТ/СКЗИ. `ssl-min-ver` TLSv1.2 (лучше 1.3 где клиенты умеют). При нескольких узлах TLS ticket keys надо **синхронизировать** (CLI умеет обновлять secrets).

**Load balancer (балансировщик)** — принимает соединения снаружи и раскидывает их на несколько живых серверов. HAProxy делает это для **TCP и HTTP** (и, при сборке с QUIC, для HTTP/3).

**Reverse proxy (обратный прокси)** — клиент стучится не в приложение, а в HAProxy. HAProxy проверяет/терминирует TLS, выбирает бэкенд и пересылает. Так устроен вход HTTP.

**Frontend** — вход: на каком IP:порту слушаем, TLS или нет, HTTP или TCP.

**Backend** — список серверов + алгоритм (roundrobin, leastconn, …) + проверки живости.

**Listen** — frontend и backend в одном блоке. Удобно для простого TCP (например 6443 → api-серверы).

**mode http / mode tcp** — HTTP: HAProxy понимает заголовки, URL, cookies. TCP: байтовый тоннель (gRPC без разбора, Postgres, kube-apiserver). Kafka почти всегда **не** кладут в HTTP-режим. «HAProxy :9092 на все брокеры» ломает протокол.

**Server / check** — реальный origin и периодический health check. Мёртвый сервер из балансировки **вычёркивается**. TCP :443 врёт, если порт открыт, а приложение мертво — нужен HTTP check (или TCP+TLS к api-серверу).

**backup server** — запасной origin: в игру, когда основные мертвы.

**maxconn** — потолок одновременных соединений (глобально и на frontend/backend). Без него процесс съест FD/RAM. Официальный порядок из sizing на железе **1.6** — тысячи TLS-коннектов на ГБ; **не** копировать 8000 как закон.

**nbthread** — сколько рабочих потоков внутри **одного** worker-процесса. С 2.5 многопроцессный `nbproc` **удалён**; масштаб по CPU — потоки. По умолчанию поток на каждое доступное ядро. Начинать с числа ядер **сокета**, не «все 128 потоков на двух сокетах» без замера. Starter Guide: межсокетный трафик — тормоз. Первая реакция на странный перф часто — **уменьшить** число CPU у процесса. Ориентир: одного ядра хватает **>99%** установок; много потоков в основном под TLS и каналы **> ~40 Gbps**.

**NUMA** — память и ядра привязаны к сокету CPU. Прыжки между сокетами на нагруженном прокси вредны.

**master-worker** — отдельный master следит за worker'ами и умеет reload по `SIGUSR2`. Для systemd штатный путь (`-W` / `master-worker`). Официальный Docker: `SIGHUP` → wrapper → `-sf`.

**Reload / `-sf`** — новый процесс берёт порты, старый дожёвывает уже открытые сессии. Это **не** zero-drop: в Management Guide описаны короткие окна, где при высокой нагрузке часть новых коннектов может отвалиться. Ориентир **~1 обрыв на 10000 новых коннектов/с на один reload** (не гарантия на вашем ядре). Не `kill -9`.

**hard-stop-after** — сколько старый worker имеет право жить после reload. Без лимита «зависшие» keep-alive сессии держат старый процесс часами.

**SO_REUSEPORT** — опция ядра: новый процесс может bind'иться на тот же порт, не заставляя старый сначала отпустить. На Linux стабильно с ядра **3.9**; без неё окна дропа при reload больше. Для Docker-образа 2.4+ ещё: ядро ≥ 4.11, если слушаете порты < 1024 не от root (`net.ipv4.ip_unprivileged_port_start=0`).

**Runtime API / stats socket** — Unix (реже TCP) сокет: вывести сервер из backend, посмотреть сессии, обновить TLS-ticket keys. Пульт, не веб-админка. Только unix + права; TCP stats с паролем — запасной вариант хуже.

**stats page** — встроенная HTML-статистика. Удобно на тесте. В интернет **не** выставляют. Выставить `:8404` в интернет = карта бэкендов и кнопки drain.

**PROMEX** — встроенный Prometheus-exporter (`http-request use-service prometheus-exporter`). В исходниках **не** собирается по умолчанию (`USE_PROMEX=1`); в официальном Docker-образе и типичных пакетах обычно уже есть — проверять `haproxy -vv` («Built with the Prometheus exporter as a service»). Скрейп с localhost.

**Stick-table** — таблица в RAM: «этот клиент → тот сервер», счётчики запросов/коннектов для rate limit. Reload без peers **обнуляет** таблицу. HPA `replicas: 50` без стабильного IP и без peers даёт 50 независимых лимитеров.

**Peers** — протокол, которым несколько HAProxy (или старый и новый процесс при reload) **копируют** stick-table. Без peers у каждого узла своя правда о лимитах и липкости. Канал — отдельный порт, не мир; лучше TLS или изолированный VLAN. Peers внутри ЦОДа — да, если есть stick-table. Между ЦОДами — обычно нет.

**localpeer** — имя «кто я в секции peers». Должно совпасть с записью `peer` или задаётся явно.

**VRRP / Keepalived** — протокол/демон **плавающего VIP**. HAProxy сам IP между машинами **не** таскает. Starter Guide: HAProxy хорошо стыкуется с keepalived; для failover IP рекомендуют VRRP/CARP, а не Heartbeat. Keepalived — **другое ПО**. Приоритет VRRP снижать, когда HAProxy мёртв (`track_script` / health), иначе VIP висит на машине без прокси. Unicast VRRP — если нет мультикаста. Не растягивать один VRRP-инстанс на три ЦОДа.

**VIP (virtual IP)** — адрес, который в каждый момент «держит» один узел пары. Клиенты и DNS смотрят сюда, а не на физические IP балансировщиков.

**CARP** — аналог VRRP (BSD). В рекомендациях Starter Guide рядом с VRRP.

**Heartbeat** — старый демон failover IP. Для failover IP его не рекомендуют вместо VRRP/CARP.

**PROXY Protocol** — короткий бинарный префикс от балансировщика с реальным IP клиента. Нужен, когда за HAProxy ещё один прокси/WAF и HTTP-заголовкам нельзя слепо верить. Спецификация проекта: `proxy-protocol.txt`.

**X-Forwarded-For (XFF)** — текстовый заголовок с цепочкой IP. Имеет смысл только если **доверяете** тому, кто его поставил. `forwardfor` слепо с мира = подделка IP.

**Health check** — периодический зонд бэкенда (TCP/HTTP/…). Частота и таймауты — часть отказоустойчивости.

**chroot + user** — после старта HAProxy меняет корневой каталог ФС и сбрасывает привилегии. В официальном образе 2.4+ уже `USER haproxy`. Компрометация процесса не равна «читает весь диск», но равна «видит трафик, который через него идёт».

**TLS offload** — расшифровка TLS на HAProxy, до origin — HTTP или заново TLS (re-encrypt). Компрометация узла = компрометация ключей сайтов, если не passthrough.

**ssl-passthrough** — TCP-режим: TLS не разбираем, выбираем бэкенд по SNI/порту. Сертификат живёт на origin.

**SNI** — имя хоста в ClientHello TLS, до расшифровки. Нужно для passthrough-выбора бэкенда.

**QUIC / HTTP/3** — HTTP поверх UDP. В 3.4 **опциональная** сборка (`USE_QUIC`), не «HAProxy стал UDP-балансировщиком чего угодно». Starter Guide: HAProxy **не** packet/UDP LB и не делает NAT/DSR.

**NAT / DSR** — трансляция адресов / Direct Server Return. Не функции HAProxy. Для UDP/NAT/DSR — IPVS, маршрутизаторы, eBPF-LB.

**Data Plane API** — отдельный sidecar от HAProxy Technologies: REST на конфиг и runtime. **Не** входит в бинарь 3.4.3.

**Ingress Controller** — отдельный продукт `haproxytech/kubernetes-ingress`. На дату документа latest = **3.2.13** (14 августа 2026), собран **с HAProxy 3.2**, не с 3.4.3. Бинарь 3.4.3 сам CRD не читает. CRD v1 `ingress.v1.haproxy.org` вендор планирует убирать в линии 3.4 контроллера — закладывать v3 заранее, если пойдёте этим путём. Снаружи всё равно нужен MetalLB/BGP/внешний VIP.

**ControlPlaneEndpoint** — VIP/DNS перед несколькими `kube-apiserver`. Часто listen TCP :6443. Смешивать интернет-:443 и api-сервер на одном bind без ACL — плохая привычка. 6443 только из административных сетей.

**Anycast / BGP** — один и тот же VIP анонсируется с нескольких ЦОДов. Нужен, когда VRRP не пересекает границы L2/маршрутизации. Это сеть ЦОДа, не фича HAProxy. Split-horizon — на сетевиках.

**RPO / RTO** — сколько готовы потерять / как быстро восстановиться. У HAProxy «данные» — **конфиг и stick-table**, не клиентская база.

**LTS** — линия 3.4: поддержка **до Q2 2031**. Нечётные линии (3.3, 3.5-dev) живут около года и **не** кладут туда, откуда нельзя быстро откатиться. Патч **3.4.3** опубликован 29 июля 2026. Не `latest` и не `3.5-dev`. Внутри 3.4 патчи автор считает безвредными для конфига; **мажор** — читать Breaking changes. Анонс 3.4: dynamic backends, cpu-affinity, OpenTelemetry; OpenTracing deprecated.

**ACL** — правила на заголовки/IP/path. Не замена WAF.

**maps** — внешние файлы соответствий для ACL.

**Lua** — встроенный скриптовый язык в процессе. На перф plaintext часто виноваты логи/regex/Lua, не «мало ядер».

**HTTP compression / cache в RAM** — экономия себе, не CDN. Starter Guide отсылает за дисковым кэшем к Varnish. Жрут CPU и память.

**option httplog / tcplog** — формат логов. URL в HTTP-логах — вопрос 152-ФЗ.

**timeout connect / client / server / tunnel** — явные таймауты в `defaults`. Дефолтные `timeout server` порядка секунд **убивают** долгие опросы Integration API. `timeout tunnel` — websocket/long-poll.

**option redispatch / retry** — иначе клиент навсегда прилипнет к мёртвому серверу при частичных сбоях.

**keep-alive** — повторное использование TCP/TLS сессии. Дешевле полного handshake. Официальное правило: порядок RPS падает примерно **в 10 раз** от TLS keep-alive к TLS resume и ещё раз к полному handshake с RSA.

**irq_balance** — демон разноса прерываний NIC. На тяжёлом TCP Management Guide советует **выключить** и руками развести очереди NIC и потоки HAProxy. На тесте с 2 ядрами рано; на 40 Gbps — предмет настройки.

**conntrack / netfilter** — учёт соединений ядром. Часто лучше **не** фильтровать datapath лишними iptables.

**swap** — Starter Guide: машина **never ever** не должна уходить в swap; CPU нельзя искусственно душить «долей ядра» гипервизора на нагруженном прокси.

**Syslog** — или stdout в контейнере + ротация.

**NTP** — часы для TLS, логов, peers.

**hostNetwork / NET_BIND_SERVICE** — под слушает порты ноды без полного privileged, если хватает для VIP/host ports.

**SafeLine / WAF** — семантический фильтр HTTP. Community HAProxy умеет rate limit, ACL, ботов «на коленке», но это не WAF. Порядок «клиент → HAProxy → WAF → origin» vs наоборот меняет PROXY/XFF и health checks.

**MetalLB** — VIP для Service в Kubernetes на железе.

**Роль A** — периметр ЦОДа: входящий HTTP/колбэки ведомств.

**Роль B** — listen :6443 перед kube-apiserver.

**Вариант A (макро)** — в каждом ЦОДе пара HAProxy 3.4.3 (VIP внутри площадки) + городской механизм на три VIP. Минимум размещения: 2×3 = **6** процессов, не ёмкость.

**Вариант B** — Anycast: один VIP с HAProxy каждого ЦОДа (BGP).

**Вариант C** — только Ingress Controller 3.2.13. Сознательно линия **3.2**, не 3.4.3.

**Вариант D** — один HAProxy на всю систему. Для прода не рассматривать.

**HAProxy Enterprise / HAProxy One** — коммерческие линейки. Файл — community 3.4.3. Лицензия, WAF, центральная консоль другие.

**Бенчмарки в доке** — Core i7 3.7 GHz, HAProxy **1.6**, ядро 3.10, 10GbE — порядок величины 2010-х. Более свежий: HAProxy 2.4, 64 ядра Graviton2, ~2 млн HTTPS RPS / 100 Gbps — чужое железо. Для вас оба набора — только «TLS дороже plaintext», не план закупки.

**GitOps** — конфиг в Git; ручной `vi` на одном ЦОДе = дрейф политики входа.

Источники формулировок: глоссарий и тело `HAProxy.md`. Новых порогов RTT и размеров диска здесь нет.
