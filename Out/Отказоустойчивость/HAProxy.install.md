# HAProxy 3.4.3 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `HAProxy.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

HAProxy — балансировщик TCP и HTTP. Ставите **community 3.4.3** (LTS линии 3.4, поддержка на haproxy.org **до Q2 2031**). Образ: `haproxy:3.4.3` (не `latest`, не `3.5-dev`).

Документация: введение https://docs.haproxy.org/3.4/intro.html · управление https://docs.haproxy.org/3.4/management.html · конфигурация https://docs.haproxy.org/3.4/configuration.html

Роли на платформе: вход TCP **6443** перед API Kubernetes (см. `Kubernetes.install.md`); при необходимости — вход TCP/HTTP периметра площадки. Это не WAF, не Ingress-контроллер и не шина Kafka.

Ingress-контроллер `haproxytech/kubernetes-ingress` **3.2.13** собран с движком **3.2**, не 3.4.3 — другой продукт; в этом файле его не ставим как «тот же экземпляр».

Один процесс (или один Keepalived) на несколько дата-центров здесь **не собираем**. У процесса нет голосования как у etcd. Устойчивость — **пара внутри зала**; между площадками — независимые экземпляры + DNS/край.

---

## О чём эта инструкция молча договорилась

1. **Пара HAProxy + Keepalived живёт внутри одного дата-центра.** Два зала = две пары. Три = три пары. Общего VIP на город у HAProxy нет.
2. Берём community 3.4.3, не Enterprise.
3. Боевой control plane — kubeadm HA в каждом зале. Балансировщик 6443 — на двух машинах **той же** площадки.
4. Учебный стенд — закрытая сеть. Цифр нагрузки нет — нет ядер и потолка соединений «хватит для боя».
5. Keepalived — **другое ПО**. Ставить только если VIP реален. Нет VIP — пара всё равно два процесса, снаружи их склеивает что-то ещё (Service/DNS).
6. Anycast/BGP на три зала — **решение сети**, не кластеризация HAProxy. Копирование таблиц памяти между залами обычно **не** включают.
7. HAProxy **не** ставим единственным `:9092` перед всеми брокерами Kafka.

---

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** понять вход и ферму, проверку синтаксиса, проверку живости; чтобы kubeconfig или тестовый HTTP ходили в одно место. **Не зачем:** отказ дата-центра и ёмкость TLS.

### Что должно быть до установки

- Docker **или** Linux-пакет линии 3.4.3.
- Для роли API Kubernetes: куда слушает единственный api-сервер. Для HTTP: тестовый origin.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

Конфиг на хосте (пример входа к API Kubernetes; на учёбе часто один api-сервер — это не запас):

```
global
    log stdout format raw local0
    maxconn 256

defaults
    mode tcp
    timeout connect 5s
    timeout client  1m
    timeout server  1m
    option tcplog

listen k8s-api
    bind *:6443
    mode tcp
    option tcp-check
    server cp1 <адрес-apiserver-с-контейнера>:6443 check
```

Адрес сервера — тот, куда контейнер **реально** достучится. Слепой `127.0.0.1` внутри контейнера — это сам HAProxy, не хост.

```bash
docker run -d --name haproxy-dev \
  -v ${PWD}/haproxy.cfg:/usr/local/etc/haproxy/haproxy.cfg:ro \
  -p 127.0.0.1:6443:6443 \
  haproxy:3.4.3
```

Привязка к `127.0.0.1` обязательна. Статистику на учёбе — только loopback, лучше вообще не слушать снаружи.

Проверка:

```bash
docker exec haproxy-dev haproxy -v
docker exec haproxy-dev haproxy -c -f /usr/local/etc/haproxy/haproxy.cfg
```

В строке версии — **3.4.3**. Затем `kubectl` / запрос на `https://127.0.0.1:6443` — ответ api-сервера, не таймаут.

HTTP-роль на учёбе — отдельный вход в режиме HTTP на тестовый origin, тот же образ, bind на localhost (другой порт хоста, если 80 занят).

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Один процесс | да | Некому делить VIP |
| TLS | нет | Иначе сертификаты раньше проверки живости |
| Keepalived / копирование таблиц | нет | Нет второго узла |
| master-worker | лучше сразу | Тот же reload, что в бою |
| HTML-статистика | можно на loopback | Учиться смотреть ферму |

Чего **не** упрощаем: всегда проверка синтаксиса перед reload; хотя бы TCP-проверка (для HTTP — **HTTP-проверка**, не только «порт 443 открыт»); клиенты ходят **на адрес HAProxy**, не в обход; таймауты под долгие интеграции, если этот стенд их имитирует; образ **3.4.3**, не `latest`.

### Как понять, что стенд живой

1. `haproxy -v` = 3.4.3.
2. Origin выключен → проверка вычёркивает (на одном сервере вход умрёт — это ожидаемо).
3. Рестарт контейнера: конфиг с тома на месте.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный образ | Падение процесса = нет входа |
| Совпадает с введением | Не ловит окна reload, VIP, CPU TLS |
| | Успех на одном процессе ≠ две–три площадки |

Перед боем полезен **препрод**: пара + Keepalived (или два пода + Service) + TLS в **одном** дата-центре, даже без боевого потока.

---

## Бой: пара в одном дата-центре, второй зал — свой независимый вход

**Зачем:** пережить отказ **одной машины или пода HAProxy внутри зала**; пережить отказ **целого дата-центра** ценой того, что городской слой перестанет слать на эту площадку. Цифр гигабит в секунду нет.

### Почему не один VIP на несколько дата-центров

HAProxy **задуман без своего склада** (введение): несколько процессов — несколько независимых прокси. Keepalived делит VIP в одном домене маршрутизации. Растянуть один VRRP на три зала — скрытая точка отказа и риск двух держателей адреса, не устойчивость. Копирование таблиц памяти через город обычно не делают: другой смысл лимита, разрыв таблицы при разделении сети.

### Как расставить машины

**Внутри каждого дата-центра** — пара:

- 2 процесса **3.4.3** (машины или поды с сетью хоста на разных нодах);
- VIP через **Keepalived** (слежение: HAProxy жив, иначе VIP на мёртвом прокси — классический простой) **или** Kubernetes Service, если это не control plane;
- роль API Kubernetes: listen TCP **6443** → api-серверы **этого** кластера;
- роль HTTP (если нужна): вход HTTPS → WAF/Ingress/**локальный** origin;
- имя control plane = DNS этого VIP. Один VIP «в чужом зале» = точка отказа **этого** Kubernetes.

**Между площадками:**

| Сколько площадок | Что где | Если умер первый дата-центр |
|---|---|---|
| **Две** | Пара+VIP в первом, такая же независимая пара во втором. Клиенты/kubectl смотрят в endpoint **своего** кластера | API и вход первого мертвы. Второй жив. Общего `kubectl` нет |
| **Три** | Третья пара | То же |

Городской HTTP-вход (браузеры): DNS/внешний балансировщик **или** Anycast, если сеть так решила. Anycast **не** делает из трёх HAProxy один кластер: нет общего состояния, нет единого reload. Сложность «кто куда пойдёт» — на сетевиках.

Origin — **этот** зал. Не тащить HTTP через город. Слушатели Kafka — мимо этого балансировщика.

### Что должно быть до боевой установки

- Linux, ядро ≥ 3.9 (для нормального мягкого reload). **Не swap**.
- Лимит дескрипторов согласован с потолком соединений.
- NTP. Журнал + ротация.
- Сертификаты для 443, если терминируете TLS. 6443 — только админские сети.
- Конфиг в git; применение: проверка синтаксиса, затем reload (не убивать процесс насильно).

### Порядок установки пары (повторить в каждом дата-центре)

Официальный порядок для kubeadm: **сначала балансировщик**, потом первый control plane (`Kubernetes.install.md`).

1. Две машины площадки, пакет или образ **3.4.3**, пользователь не root после открытия порта (официальный образ уже так).
2. Конфиг роли 6443 (и отдельно HTTP, если нужен — **разные bind**, список доступа на 6443).
3. Keepalived: VIP внутри зала; скрипт слежения за процессом/портом HAProxy; **не** один VRRP на три зала.
4. DNS control plane → VIP. Проверить инициализацию Kubernetes с этим endpoint.
5. Метрики с localhost; страница статистики не с мира.

Смысл listen 6443 (не полный боевой файл):

```
defaults
    mode tcp
    timeout connect 10s
    timeout client  1m
    timeout server  1m

listen k8s-api
    bind <vip>:6443
    mode tcp
    option tcplog
    option tcp-check
    server cp1 <ip-cp1>:6443 check
    server cp2 <ip-cp2>:6443 check
    server cp3 <ip-cp3>:6443 check
```

Таймауты HTTP-роли под интеграционное API — **из замера** лагов ведомств, не завод «секунды»: иначе балансировщик рвёт легитимный длинный опрос. Отдельный таймаут туннеля — для websocket.

Проверка конфига в конвейере и в unit-файле: `haproxy -c -f /etc/haproxy/haproxy.cfg`.

На каждом узле: выделенная машина или помеченные ноды; не соседствовать с брокерами, которые выбивают кэш процессора; NTP; лимиты conntrack, если трафик идёт через фильтрацию пакетов (часто лучше **не** фильтровать путь данных лишними правилами).

Копирование таблиц **внутри пары**: да, если есть липкость или лимит частоты. Канал — отдельный порт, не мир. Между залами — обычно нет.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Версия | pinned **3.4.3** на всех узлах пары | Иначе поведение списков доступа и TLS разъедется |
| master-worker | да | Штатный reload |
| Сколько жить старому процессу после reload | явно, по длине ваших сессий | Не копить старые процессы часами |
| Проверка живости | TCP+проверка API / HTTP к origin | Голый «порт 443 открыт» врёт для HTTP |
| Копирование таблиц | если есть липкость/лимит **внутри зала** | Reload иначе обнуляет политику |
| Копирование между залами | обычно нет | Не городской склад состояния |
| Потоки | начать с ядер **сокета**, не «все 128» без замера | Введение: межсокетный трафик — тормоз |
| Потолок соединений | по памяти **после замера** | Цифры sizing из гайдов 1.6 — не ваш план |
| Повтор на другой сервер при частичном сбое | осознанно | Иначе клиент навсегда прилипнет к мёртвому |

Ориентир введения: **одного ядра хватает >99% установок**. Это не замер вашего периметра. Бенчмарки 2010-х / чужое железо в `HAProxy.md` **не** копировать в закупку.

Reload не «ноль оборванных»: руководство по управлению описывает короткие окна потери **новых** соединений (ориентир порядка **1 обрыв на 10000** новых соединений в секунду на один reload — не гарантия на вашем ядре). Катить **все** площадки сразу нельзя. Обновление: снять узел с VIP → reload → вернуть.

Ключи возобновления TLS-сессий между узлами пары надо **синхронизировать** — иначе возобновление прыгает впустую.

### Как расти, когда появятся цифры нагрузки

1. Замерить новые TLS/с, запросы keep-alive, одновременные соединения, использование потолка, CPU vs прерывания сети.
2. Упёрлись в рукопожатие — keep-alive и билеты сессий, не слепой «128 потоков».
3. Упёрлись в дескрипторы — лимиты и keep-alive, потом ещё узлы **в этой** паре.
4. Горизонталь между залами — новые независимые пары, не «реплики без VIP».
5. HPA «50 подов» без VIP и без копирования таблиц = 50 лимитеров.

Кэш в памяти и сжатие — точечно; введение: это не замена дискового кэширующего прокси.

При странной скорости на открытом тексте часто виноваты журналы, регулярные выражения и вставки на языке Lua, не «мало ядер». На тяжёлом TCP руководство по управлению советует на больших каналах разводить очереди сетевой карты вручную; на тесте с двумя ядрами это рано.

### Безопасность (без этого периметр не настроен)

1. На мир — только нужные входы (80/443). Не статистика, не пульт, не канал таблиц, не **6443**.
2. Пульт — unix-сокет, группа администраторов. Статистика с мира = карта бэкендов и снятие с фермы.
3. Минимум TLS 1.2 (лучше 1.3 где клиенты умеют). Ключи не в git. «Не проверять сертификат origin» в бою не настройка. Повторное шифрование до origin, если сеть зала не считается доверенной.
4. Реальный IP клиента: протокол PROXY **или** заголовок только от доверенных хопов. Слепо дописывать цепочку с мира = подделка.
5. Origin принимает трафик **только** с IP HAProxy (и WAF). Иначе балансировщик обходят.
6. Конфиг из git; ручная правка на одном зале = дрейф политики входа.
7. После bind — не root. Клетка файловой системы — если ставите с пакета и понимаете пути сертификатов.
8. Журналы HTTP содержат URL — вопрос персональных данных. Алерт: ферма мертва, потолок соединений, неудачный reload, Keepalived сменил состояние, истекающий сертификат.

### Проверки, без которых это ещё не бой

Внутри зала:

1. `haproxy -v` = 3.4.3 на обоих узлах.
2. Выключить один HAProxy: VIP уехал (слежение сработало), `kubectl` / HTTP живы.
3. Выключить один api-сервер: проверка сняла его, 6443 отвечает.
4. Reload под синтетикой; есть лимит жизни старого процесса; доля обрывов зафиксирована.

Между залами: выключить вход первого — городской слой (если он есть) не шлёт сюда; kubectl второго смотрит в **свой** endpoint. Anycast, если включили, проверяют сетевики: это не «кластер HAProxy встал».

### Что хорошо и что плохо в схеме «пара в зале + независимые площадки»

| Хорошо | Плохо |
|---|---|
| Отказ машины закрывается VIP внутри зала | Keepalived — свой риск двух держателей адреса |
| Согласовано с kubeadm HA и запретом размазывать | 2–3 копии конфига; без git разъедутся |
| Нет своего склада, понятный reload | Городской failover — DNS/внешний вход/Anycast, не бинарь |
| | Anycast ≠ кластер HAProxy: нет общего состояния |

**Не готово к бою**, если: один процесс на три зала; `haproxy:latest`; статистика с мира; нет проверки живости; Kafka через один TCP-вход на все брокеры; Keepalived без слежения за прокси; VRRP растянут на залы; лимит частоты «есть», копирования таблиц нет; reload без проверки синтаксиса; VIP control plane в чужом зале; Ingress-контроллер 3.2 выдают за 3.4.3.
