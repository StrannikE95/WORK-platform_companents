# ClickHouse 26.7.5.10 — термины и сокращения

Словарь к файлу `ClickHouse.md`. Список линейный, не таблица. Сверху — слова, без которых не читаются остальные. Аналогий нет: только что это делает в коде и на диске.

---

**Процесс** — запущенная программа: память и открытые файлы. `clickhouse-server` принимает SQL и хранит таблицы. `clickhouse-keeper` — отдельный процесс координации. На одной машине совмещать в проде вендор не рекомендует.

**Файл / каталог на диске** — то, что остаётся после рестарта. Данные сервера: `/var/lib/clickhouse` (parts таблиц). Keeper: Raft-лог и снимки на своём томе. **Не NFS** как data dir. `emptyDir` для данных OSS = потеря parts при рестарте пода.

**TCP-порт** — номер в сети. HTTP **8123**, HTTP+TLS **8443**, native **9000**, native+TLS **9440**, копирование parts между репликами **9009** / TLS **9010**, Keeper клиент **9181** / TLS **9281**, Raft Keeper **9234**, Prometheus-метрики **9363** (если включили). Эмуляции MySQL **9004** / PostgreSQL **9005** / gRPC **9100** в проде выключают.

**ЦОД** — отдельная площадка с серверами. Stretch = ноды в нескольких ЦОДах, Keeper и копирование parts ходят по сети между площадками.

**RTT** — время туда-обратно. Порога в мс нет. Дефолты Keeper: heartbeat **500 мс**, окно выборов **1–2 с**. Если RTT/jitter сопоставимы — ложные выборы лидера. Мерить **9234** и **9009**, не ICMP ping.

**TLS** — шифрование байтов в сети. Клиенты: 8443/9440. Между репликами: 9010. Keeper: 9281 и Raft `secure`. OpenSSL, не ГОСТ/СКЗИ.

**Под (Pod)** — контейнер(ы) Kubernetes. Отдельные CHI (серверы) и CHK (Keeper). Topology spread: не сложить две реплики шарда и двух Keeper в одну зону.

**PVC / RWO** — том одному поду. На каждую реплику и каждый Keeper свой том, StorageClass с предсказуемым IOPS. `Retain`. Shrink диска Kubernetes не умеет.

**CSI** — плагин диска Kubernetes.

**Helm / оператор** — для self-hosted OSS в файле: **Altinity Kubernetes Operator 0.27.3** (CR `ClickHouseInstallation` / `ClickHouseKeeperInstallation`). Не ClickHouse Cloud / Private (там SharedMergeTree + object storage).

**Сервер (clickhouse-server)** — процесс, который принимает SQL, хранит таблицы, отвечает на запросы. «Нода данных».

**Шард (shard)** — кусок данных на диске: часть строк таблицы. Параллелизм хранения и скана = шарды. У каждого шарда свой набор реплик. ClickHouse сам не раскладывает данные по новым нодам: решардинг дорогой.

**Реплика** — копия **одного шарда** на другом сервере (другой процесс, другой диск). Нужна, чтобы падение ноды не уничтожило данные шарда. Вендор: **не меньше трёх** реплик на шард (on-prem). Репликация **таблицы**, не всего сервера.

**Кластер в `remote_servers`** — именованный список шардов и реплик в конфиге XML. По нему работают `ON CLUSTER` и движок `Distributed`.

**MergeTree** — основной движок таблиц: колоночное хранение, данные пишутся **частями (parts)** и в фоне сливаются (merge). Не транзакционная СУБД с многотабличным COMMIT как PostgreSQL. Голый MergeTree при падении ноды просто исчезает.

**ReplicatedMergeTree** — MergeTree + репликация через Keeper. Без него «три сервера» — три разные базы. `CREATE`/`DROP`/`RENAME` сами по репликам не едут.

**Distributed** — таблица-прокси: `SELECT`/`INSERT` размазывает запрос по шардам. Сама данные не хранит. Под ней — Replicated*.

**Part (кусок)** — файл(ы) на диске с порцией вставленных строк. Слишком много мелких parts — merge не успевает, INSERT начинают отклоняться (**Too many parts**).

**ORDER BY** — ключ сортировки строк на диске. От него зависит, сколько данных пропустит запрос. Меняется только через новую таблицу. Это не PRIMARY KEY PostgreSQL.

**TTL** — правило «через N дней удали / перенеси» на диске. Без него объём съест диск сам.

**Мутация (`ALTER UPDATE` / `DELETE`)** — переписывание parts на диске. Дорого. Не замена OLTP, где правят по одной строке.

**ClickHouse Keeper** — процесс-координатор репликации и распределённого DDL. Замена ZooKeeper, свой Raft (выбор лидера голосованием процессов). Смешанный кластер Keeper+ZooKeeper **невозможен**. Вендор: dedicated hosts в production. `force_sync` по умолчанию **true**: каждое признание записи идёт через fsync диска.

**Raft** — алгоритм, которым процессы Keeper выбирают лидера и пишут лог на диск. Без лидера реплицируемые таблицы — **read-only**.

**Кворум Keeper** — большинство живых процессов Keeper. Для 3 нод большинство = 2. Если живых меньше — нет лидера, реплицируемые таблицы уходят в **read-only**, новые `ON CLUSTER` не проходят.

**`ON CLUSTER`** — DDL сразу на все ноды кластера (через Keeper). Без этого `CREATE TABLE` создаст таблицу **только на той ноде, куда вы подключились**.

**Макросы `{shard}` / `{replica}`** — подстановки в пути Keeper и в имена реплик, чтобы один и тот же SQL работал на всех нодах. Путь в Keeper уникален на таблицу; клонировать путь = сломать репликацию.

**`internal_replication`** — в `remote_servers`: `true` = Distributed пишет **в одну** здоровую реплику, дальше копирует ReplicatedMergeTree. `false` (дефолт движка Distributed) = пишет во **все** реплики сам — для ReplicatedMergeTree хуже.

**`insert_quorum`** — сколько реплик должны подтвердить INSERT, чтобы клиент получил успех. Дефолт: подтверждение **с одной** реплики. Если эта реплика умерла до копирования — блок **пропал**. Значение < 2 = выключен; `'auto'` = большинство реплик. При 3 репликах и цели «пережить 1 ЦОД» в файле — **2**.

**`insert_quorum_parallel`** — можно ли слать следующий quorum-INSERT, пока предыдущий ещё не дошёл. Выключено — строгая последовательность, ниже пропускная способность.

**`select_sequential_consistency`** — читать только то, что уже лежит на кворуме реплик. Иначе SELECT может не увидеть только что «успешно» вставленное на другой реплике.

**HTTP 8123 / HTTPS 8443** — REST/HTTP интерфейс (JDBC-over-HTTP, curl, многие драйверы).

**Native 9000 / 9440** — свой TCP-протокол. Им говорят `clickhouse-client`, межсерверные Distributed-запросы, часть драйверов. 9440 — то же с TLS.

**Interserver 9009 / 9010** — передача parts **между репликами**. Сюда клиенты не ходят. VIP «как один адрес на все 9009» ломает копирование.

**Keeper 9181 / 9281 / 9234** — клиентский порт (9181 рекомендуется; в XML дефолт тега `tcp_port` исторически 2181, как у ZooKeeper). 9281 — TLS клиента. 9234 — Raft между нодами Keeper. На Keeper внешний трафик не пускают.

**`users.xml` / `users.d`** — файловые учётки. Вендор рекомендует **SQL-driven** пользователей (`CREATE USER`). Учётки из XML **не входят** в `BACKUP`.

**SQL access control** — пользователи, роли, квоты, row policy через SQL. Это то, что умеет бэкапиться вместе с кластером.

**`default` (пользователь)** — встроенная учётка. В Docker без пароля **нет сетевого доступа**; с `CLICKHOUSE_SKIP_USER_SETUP=1` её открывают. В проде это дыра. Туториал репликации: без пароля *discouraged*.

**Named collection** — именованный набор секретов (S3-ключи) в конфиге сервера, а не в тексте SQL пользователя. В 26.7 пользовательский SQL **больше не подхватывает** облачные credentials процесса по умолчанию.

**Stretch-кластер** — один логический кластер, ноды в нескольких ЦОДах.

**RPO / RTO** — сколько данных готовы потерять / как быстро восстановиться.

**Too many parts** — мелких кусков слишком много: merge не успевает, INSERT отклоняются. Цена «пишем по одной строке из каждого микросервиса».

**Async insert** — с 26.3 (есть и в 26.7) включён по умолчанию: мелкие INSERT сервер сам пакует. Не отменяет батчи на стороне Kafka Connect. Для exactly-once вендор требует `wait_for_async_insert`.

**`BACKUP` / `RESTORE`** — выгрузка таблиц/баз в S3-совместимое хранилище. Реплики не заменяют бэкап: `DROP TABLE` уедет на копии. SQL-пользователи восстановятся; `users.xml` — нет. Инкремент: `SETTINGS base_backup = S3(...)`.

**Object storage (бэкап)** — бакет для BACKUP. Если только в одном ЦОДе — падение этой площадки убивает бэкап.

**Kafka engine + MV** — встроенная таблица: читает топик, пишет через materialized view. Семантика **at-least-once**; дубли возможны. Quorum задаётся профилем пользователя, не на MV.

**Kafka Connect Sink** — отдельное Java-ПО. `exactlyOnce` через KeeperMap. Для прода в файле предпочтителен. Connect тоже ходит в Keeper.

**KeeperMap** — структура в Keeper для exactly-once коннектора.

**`listen_host`** — на каких интерфейсах слушать. Задавать явно. `0.0.0.0` без NetworkPolicy — весь интерфейс.

**`<ip>::/0</ip>`** в users.xml — вендор называет небезопасным без firewall.

**`secret` кластера** — в `remote_servers` для Distributed: иначе любой, кто достучался до 9000, может прикинуться шардом.

**`server_id` (Keeper)** — не переиспользовать и не перемешивать при замене ноды.

**`async_replication` (Keeper)** — с 23.9+; в 26.7 умеет. По умолчанию выключена ради совместимости. Включать, когда все ноды кворума её умеют.

**`ruok` / `mntr`** — проверка Keeper по TCP: живой процесс ≠ член кворума.

**fsync / `force_sync`** — вызов ОС «запиши буфер на диск сейчас». Медленный диск Keeper = медленный DDL и репликация всего кластера.

**ulimit nofile** — в Docker-гайде `--ulimit nofile=262144:262144`.

**LTS 26.3** — линейка с длинной поддержкой. Патч в файле: **26.3.21.7-lts**. Не смешивать 26.7 и 26.3 в одном кластере.

**SharedMergeTree** — модель Cloud/Private, не этого OSS-развёртывания.

**OLAP / OLTP** — профиль: тяжёлые сканы и агрегации vs короткие правки одной строки. ClickHouse — колоночный OLAP.

**SoT** — ClickHouse не источник истины клиентских карточек. Витрины и аналитика, не точечный UPDATE ФИО.

**Image tag `latest`** — не брать. Прод: **26.7.5.10** на server и Keeper.

**PDB** — не дать Kubernetes снять сразу два Keeper или две реплики одного шарда.

**NetworkPolicy** — клиенты → 8443/9440; 9009/9010 — только серверы; 9181/9234 — серверы и Keeper; 9363 не в интернет.

Источники формулировок: глоссарий и тело `ClickHouse.md`. Новых порогов RTT и размеров диска здесь нет.
