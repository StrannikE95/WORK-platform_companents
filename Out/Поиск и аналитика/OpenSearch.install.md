# OpenSearch 3.8.0 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `OpenSearch.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

OpenSearch — поисковый движок: индексы, поиск, агрегации. Ставите **свою** копию, не облако Amazon и не тот же кластер, что Wazuh indexer.

Версия в этой инструкции: **OpenSearch 3.8.0**. Образ: `opensearchproject/opensearch:3.8.0`. Dashboards — тот же тег, см. `OpenSearch Dashboards.install.md`.

На Kubernetes целевой путь — **OpenSearch Kubernetes Operator** (репозиторий `https://opensearch-project.github.io/opensearch-k8s-operator/`). Helm-чарты проекта — запасной ручной путь. Документация: https://docs.opensearch.org/latest/

Таблица проекта: operator **3.0.0+** умеет OpenSearch до latest 3.x. Перед боем прогоните **именно 3.8.0** на стенде: отдельного отчёта «этот релиз оператора сертифицирован под 3.8.0» нет. Чарты фиксируйте тегом релиза, не `latest`.

Один кластер, размазанный на несколько дата-центров, здесь **не собираем**. Состояние кластера и копии шардов ходят по порту 9300; в документации нет цифры «сколько миллисекунд ещё можно». Поэтому живой кластер — внутри одной площадки. Вторая площадка — снимок и восстановление **или** отдельный кластер, который только читает копию индекса.

Java в комплекте линии 3.6.1+: таблица вендора 21 / 25 / 26; в бандле на момент той таблицы — **25.0.4+7**. Свой JDK — через `OPENSEARCH_JAVA_HOME`. На хосте `vm.max_map_count ≥ 262144`.

## О чём эта инструкция молча договорилась

1. **Один живой «мозг» в одном дата-центре.** Тройка cluster manager (ноды, которые выбирают руководителя кластера) и data-ноды **одного** кластера живут **в одной площадке**. Между площадками — отдельный кластер, который тянет индекс и **только читает**, **или** клиенты ходят поиском на первую площадку, **или** восстановление из снимка. Не открывайте между дата-центрами порт 9300, если не строите осознанно другой контур.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`, если есть).
3. Учебный стенд — закрытая сеть. Учебные сертификаты допустимы **только там**.
4. Цифр вашей нагрузки нет — нет фразы «хватит N data-нод». Есть сигналы (куча, отказ в записи, порог диска) и рычаги (ноды, шарды, политика жизни индексов).
5. Бакет для снимков в бою **есть или будет**. Копии шардов бэкап не заменяют: команду «удали индекс» они послушно повторят. Если бакет живёт только в той же площадке, что кластер, падение площадки убивает и поиск, и бэкап.
6. Два дата-центра: кластер в первом; второй — ведомая копия индекса **или** только клиенты на 9200 / восстановление из снимка. Три дата-центра: то же. Третья площадка — **не** третий cluster manager чужого голосования.
7. Wazuh indexer — **отдельный** кластер, другой контур прав.
8. С 2.12 без своего пароля `admin` учебный контейнер **не стартует**.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** писать mapping, пакетно записывать документы, подключить Dashboards и пайплайн из Kafka. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- На localhost свободен порт 9200.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name os-dev \
  -p 127.0.0.1:9200:9200 \
  -e "discovery.type=single-node" \
  -e "OPENSEARCH_INITIAL_ADMIN_PASSWORD=DevAdmin_12Str0ng" \
  opensearchproject/opensearch:3.8.0
```

Привязка к `127.0.0.1` обязательна: порт слушает только эта машина.

Режим `discovery.type=single-node` **обходит** нормальный поиск соседей — только учёба и тест. С 2.12 без пароля admin учебный конфиг **не стартует**.

Проверка — в JSON должна быть версия **3.8.0**:

```bash
curl -sk -u admin:DevAdmin_12Str0ng https://127.0.0.1:9200
```

На одной ноде число копий шарда = **0**, иначе вечный yellow: копию некуда положить.

`DISABLE_SECURITY_PLUGIN=true` не включайте «чтобы curl без пароля»: привычка уедет в бой.

Альтернатива вендора — docker compose из гайда (2 ноды + Dashboards). Примеры compose помечены как **не для боя**. Учебный конфиг ставится, пока не задать `DISABLE_INSTALL_DEMO_CONFIG=true`.

На Kubernetes для учёбы: один объект кластера с одной репликой, маленький диск; либо Helm `singleNode: true`. Этот YAML в бой не копируйте.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Число нод | 1 | Не учимся переживать обновление |
| Копии шарда | 0 | Копию некуда положить |
| Сертификаты | учебные / самоподписанные | Иначе сертификаты раньше mapping |
| Снимок | можно отложить на день | На препроде репозиторий уже обязателен |
| Политика жизни индексов | минимум | Сначала увидеть объём тестовых логов |
| Индекс | явный `_id` из Kafka | Повтор той же пачки не плодит документы |

Чего **не** упрощаем: номер версии **3.8.0** = Dashboards; главные шарды задаются при создании индекса; compose вендора **не для боя**; 9200 не с интернета.

### Как понять, что стенд живой

1. `curl` к 9200, version 3.8.0.
2. Документ записался и ищется. Контейнер перезапустили без тома — индекс пуст (если не было диска). Так и должно быть на тесте.
3. 9200 не с мира.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Часы, официальный Docker-гайд | Нет голосования руководителя, нет 9300 между машинами, нет раскладки копий по зонам |
| Одна нода официально нормальна для теста | Успешный поиск **не** доказывает боевую схему |
| | Учебные сертификаты приучают заходить как `admin` |

Перед боем полезен **препрод**: 3 выделенных cluster manager + data, свои сертификаты, копии ≥ 1, снимок — всё **в одном** дата-центре.

## Бой: один живой дата-центр, второй — запас из снимка или копия только для чтения

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три cluster manager, копии шарда ≥ 1). Отказ **всего дата-центра** = этого кластера нет для записи, пока не восстановите снимок на другой площадке или не переключите клиентов. Чтение возможно с ведомого кластера (данные чуть устаревшие: подтягивание асинхронное). Время простоя и хвост потерянных документов нужно замерить.

Официальный паттерн «три manager в трёх зонах» в документации — про зоны **доступной** сети. Городскую сеть между дата-центрами мы не принимаем за такую без замера, а порога задержки проект **не даёт**. Поэтому голосование и копии шардов не растягиваем на несколько городов.

### Почему кластер не растягиваем на несколько дата-центров

Порт 9300 — не HTTP-балансировщик «на все ноды». Высокая или плавающая задержка → медленные выборы руководителя, отложенное назначение шардов, yellow. Жёсткий запрет класть копию в ту же зону на три площадки ещё и оставляет yellow, пока мёртвая зона не вернётся: копии сознательно не переезжают, чтобы не забить диск живых площадок. Падение двух площадок из трёх при одном manager на площадку всё равно снимает большинство голосов.

Полезные факты из схемы «три площадки», которые **остаются внутри одной площадки**:

- Выделенные cluster manager: роль только `cluster_manager`, боевые индексы на них **не** кладут. Клиентов на них не посылают.
- Нечётное число manager. **3** — официальный «почти всегда». **5** имеет смысл, если боитесь сценария «зона + ещё одна manager-нода»; это уже диск и RAM на состояние кластера, не бесплатно.
- После первого запуска список имён для bootstrap **не** используют как постоянное членство. Новые manager **присоединяются** к существующему кластеру, а не поднимают второй с другим UUID.
- Data на старте: роли `data` и `ingest`. Выделить ingest или coordinating — когда появится профиль нагрузки.
- Копии ≥ 1 на многонодовом кластере. Шаблоны индексов и политика жизни индексов — **до** первого боевого документа. Не плодить индекс «на каждый микросервис на каждый час» без политики: каждый индекс и шард живут в состоянии кластера и в куче.
- Hot-warm в документации есть. Включать **после** того, как поняли, какие индексы реально остывают. Иначе получите неназначенные копии, как в учебном примере с одним «горячим» узлом.
- В **3.8.0** для S3-совместимого снимка дефолт шифрования на стороне сервера сменился на **AES256**. Если ваш MinIO или шлюз отвергает заголовок — явно вернуть `bucket_default`. Не узнавать это в ночь инцидента.

### Как расставить в активном дата-центре

Один кластер:

- Три **выделенных** cluster manager, anti-affinity по машине **этой** площадки.
- Data-ноды на разных машинах этой же площадки, диск local SSD, **не NFS**, не `emptyDir`.
- `cluster.initial_cluster_manager_nodes` — **один раз** на первый запуск, одинаковый список.
- Копии ≥ 1.
- Клиенты на Service **9200** (coordinating / ingest).
- HTTP TLS включён (`plugins.security.ssl.http.enabled: true` — дефолт plugin **false**).
- TLS на 9300 обязателен, пока работает Security plugin. Проверку имени хоста в сертификате **не** выключать «чтобы завелось».
- Учебный конфиг выключен (`DISABLE_INSTALL_DEMO_CONFIG=true`), своих учебных сертификатов в образе нет.
- Куча Java ~½ RAM, `Xms = Xmx`; лимит пода **выше** кучи (поиск читает файлы через mmap).
- Образ **3.8.0** на всех нодах.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: кластер записи. Вторая: **нет** прямого 9300 к первой. Либо ведомый кластер только читает индекс, либо клиенты ходят на 9200 первой, либо запас — восстановление из бакета | Нет записи в этот кластер. Ведомый **сам писателем не становится** — отдельная процедура. Восстановление из снимка — замерить время |
| **Три** | Третья как вторая: ещё один ведомый / только клиенты / только снимок | То же. Три независимых «правды индекса» без копирования между кластерами хуже |

Копирование между кластерами: плагин на **обоих**; Security включён на обоих или выключен на обоих. Маски индексов («копируй всё подходящее») надо сопровождать. Это **не** прозрачное переключение записи.

Не кладите «все manager в первой площадке, а data в трёх»: падение первой оставит диски, но **без** руководителя кластера. Это не переживание площадки, а «файлы ещё лежат».

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемой скоростью, один том на один под. В restricted-кластере `vm.max_map_count` решить явно (оператор часто ставит init-контейнером).
- Бакет снимков, который **переживает** гибель этой площадки.
- Свои сертификаты. Проверка имени хоста включена.
- Сетевая политика: клиенты и Dashboards → 9200; 9300 — только ноды **этого** кластера (плюс ведомый, если копируете индекс); 9600 не в интернет.
- Политика сбоя подов: не давать Kubernetes снять сразу два manager. Выкат оператора ждёт **green** после каждой ноды. Жёлтый кластер из-за жёсткой раскладки копий во время аварии зоны **остановит** выкат — это надо понимать, не «сломался оператор».
- Не менять единицу диска `G` ↔ `Gi` без бэкапа: оператор предупреждает, что пересоздаст шаблоны томов.

### Порядок установки в активном дата-центре

1. Поставить оператор (Helm тега релиза линейки 3.x). Перед боем — прогон **именно 3.8.0** на стенде.
2. Описать кластер: отдельный пул `cluster_manager` × 3 + пул `data`; версия **3.8.0**. Topology spread / anti-affinity: не сложить всех manager и все копии шарда на одну машину.
3. Security: свои сертификаты, свой admin, не учебный комплект. Утилита заливки ролей — только с административным сертификатом по HTTPS 9200.
4. Зарегистрировать репозиторий снимков, прогнать создание **и** восстановление (в другой namespace / кластер, не только «SUCCESS на create»). Первый снимок тяжёлый, дальше легче.
5. Залить шаблоны индексов (шарды, копии, mapping) и политику жизни индексов **до** боевого потока. Главные шарды потом дёшево не поменять.
6. Выложить тестовый индекс, прогнать пакетную запись и поиск, убить data-под, убедиться что документ читается.
7. Подключить первый реальный пайплайн (лучше из Kafka, с буфером).
8. Dashboards — `OpenSearch Dashboards.install.md`, тот же дата-центр, тот же кластер.

Если в договоре или политике есть Helm-чарты вместо оператора — тот же смысл: изолированные manager, свои сертификаты, не `singleNode`.

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Учебные сертификаты | запрещены | Документация: общеизвестны и поэтому небезопасны |
| Dual-mode SSL | только миграция | Не постоянный бой |
| Клиенты на manager | нет | Вендор: трафик на ingest / coordinating / data |
| Политика жизни индексов | горячий → удаление или снимок | Иначе диск съедят «терабайты» сами |
| `admin` у приложений | нет | Отдельные внутренние пользователи / JWT / mTLS |
| HTTP 9200 | только HTTPS | Дефолт plugin — HTTP |
| Секреты | не в Git; keystore оператора + Vault / Secret | Иначе ключ от индекса в репозитории |
| Шифрование томов | включить на CSI | В OSS нет «галочки encrypt index» как замены диску |
| Аудит Security | отдельный индекс со своей политикой жизни | Не смешивать с боевыми документами |

`securityadmin.sh` — только с административным DN, по HTTPS. Права на индексы и документы выдаются процессом, не «всем admin».

### Как расти, когда появятся цифры нагрузки

1. Объём и поиск → data-ноды + размер шарда (замер, не слайд).
2. Индексация → пакеты, не одиночные POST; при необходимости отдельный пул ingest.
3. Тяжёлые агрегации → coordinating, чтобы не душить кучу data-нод.
4. Manager почти не масштабируют «от числа поисков»; им RAM под состояние кластера.

### Проверки, без которых это ещё не бой

1. Version 3.8.0 на **всех** нодах. Здоровье кластера green (или yellow осознанный). Нет смеси мажоров.
2. Выключили одну data-ноду: документ читается (копия на другой ноде). Выключили один manager: голосование живо.
3. Восстановили снимок в чистый кластер на стенде.
4. Без TLS и без роли — отказ. 9300 с мира закрыт.
5. Учение «активный дата-центр выключен»: ведомый только читает **или** честный простой поиска; перевод записи на ведомого — по заранее написанному сценарию, не «сам». Кластер не общий с Wazuh. Порт 9300 между площадками закрыт — и это **ожидаемо**.

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + снимок или копия для чтения»

| Хорошо | Плохо |
|---|---|
| Голосование и копии шардов — локальная сеть | Падение этой площадки = нет записи (и поиска, если нет ведомого) |
| Не зависит от неизвестной задержки между городами | Ведомый только читает; при восстановлении из снимка можно потерять хвост |
| Один поисковый кластер для разработчиков | Клиентский 9200 через город — уже ваша сеть, не магия OpenSearch |
| | Два контура прав, если поднимаете второй кластер |

**Не готово к бою**, если: режим одной ноды; 0 копий на нескольких нодах; учебные сертификаты; Security plugin выключен; данные на NFS или в пустом томе Kubernetes; один кластер по 9300 на 2–3 дата-центра; общий с Wazuh indexer; OpenSearch назначен эталоном карточек клиентов; нет снимка; учебный манифест уехал в бой.
