# OpenSearch Dashboards 3.8.0 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `OpenSearch Dashboards.md`.

Кластер поиска: `OpenSearch.md` и `OpenSearch.install.md`.

Этот файл — **как поставить и настроить** веб-интерфейс. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

OpenSearch Dashboards — веб-интерфейс к кластеру OpenSearch (Discover, дашборды, часть админки прав). Это **другое ПО**, чем сам поиск: процесс на Node.js, порт **5601**. Нарисованные объекты живут **в индексах** `.kibana*` / `.opensearch_dashboards*` кластера, не на диске пода.

Версия в этой инструкции: **OpenSearch Dashboards 3.8.0**. Образ: `opensearchproject/opensearch-dashboards:3.8.0`. Версия UI **обязана** совпасть с версией OpenSearch (**3.8.0**); плагины — major.minor.patch.

На Kubernetes — секция `spec.dashboards` **оператора** вместе с кластером; Helm-чарт `opensearch/opensearch-dashboards` — запасной путь. Документация: https://docs.opensearch.org/latest/install-and-configure/install-dashboards/

Ставьте UI **вместе с OpenSearch той площадки**, куда указывает список адресов кластера. Реплики интерфейса без живого 9200 — красный экран, не устойчивость поиска. Список адресов — ноды **одного** кластера (разъяснение maintainer на форуме проекта), не «leader и ведомый как запасные друг друга».

---

## О чём эта инструкция молча договорилась

1. **Один живой кластер в одном дата-центре** — как в `OpenSearch.install.md`. Реплики UI смотрят на **локальный** кластер своей площадки. Не смешивать URL пишущего и ведомого кластера в одном списке «как один кластер».
2. Если OpenSearch только в первой площадке — UI тоже в первой (иначе каждый клик Discover едет через город без пользы для устойчивости данных).
3. Бой — Kubernetes в каждом дата-центре отдельно.
4. Учебный стенд — закрытая сеть; HTTP и учебный пользователь процесса допустимы только там.
5. Цифр «сколько аналитиков» нет. Минимум боя: **не меньше двух** реплик в том дата-центре, где кластер.
6. Два дата-центра: UI у кластера в первой площадке; у ведомой копии индекса во второй — **отдельный** UI (только чтение) **или** нет UI там. Три дата-центра: то же. Wazuh indexer — **не** источник этого UI.
7. Сессия — cookie; Redis для нескольких реплик UI официально не требуется. Одинаковый секрет cookie (минимум **32 символа**) на всех репликах **этого** Deployment.
8. Срок сессии по умолчанию — **1 час** (3 600 000 мс), при активности продлевается. Это штатно.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** открыть Discover, настроить шаблон индекса, потыкать админку прав. **Не зачем:** доказывать отказ дата-центра и N сессий.

### Что должно быть до установки

- Уже запущен OpenSearch 3.8.0 (см. `OpenSearch.install.md`), сеть Docker `os-net` или localhost.
- На localhost свободен порт 5601.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

Файл `opensearch_dashboards.yml` как в гайде установки: адреса на контейнер кластера, проверка сертификата кластера `none` допустима **только здесь**, учётка `kibanaserver`.

```bash
docker run -d --name osd-dev \
  --network os-net \
  -p 127.0.0.1:5601:5601 \
  -v "$PWD/opensearch_dashboards.yml:/usr/share/opensearch-dashboards/config/opensearch_dashboards.yml:ro" \
  opensearchproject/opensearch-dashboards:3.8.0
```

Привязка к `127.0.0.1` обязательна. Тег **3.8.0**, не `latest` (гайд OpenSearch иногда показывает `latest` — не копировать).

Проверка: браузер `http://127.0.0.1:5601`, логин admin кластера, шаблон индекса, документ **виден**.

На Kubernetes для учёбы: включить dashboards в объекте кластера, 1 реплика, HTTP. Этот values в бой не копируйте.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Реплики | 1 | Нет цели пережить выкат |
| TLS 5601 | HTTP | Иначе сертификаты раньше Discover |
| Проверка сертификата кластера | `none` как в docker-гайде | Самоподписанный кластер |
| Пользователь процесса | demo **только в изоляции** | Кластер с 2.12 всё равно требует свой admin |
| Секрет cookie | дефолт | Одна реплика |
| Снимок `.kibana*` | можно отложить на день | На препроде нельзя забыть |

Чего **не** упрощаем: версия = кластеру; картинки живут в `.kibana*`, не в контейнере UI; 5601 не в интернет.

### Как понять, что стенд живой

1. Логин, Discover показывает тестовый индекс.
2. Удалили том UI — дашборды на месте. Удалили `.kibana*` — нет. Так и должно быть: состояние в кластере.
3. Привычку Helm «сначала убить все поды» не считать нормой боя.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Совпадает с официальным Docker-гайдом | Нет доказательства, что cookie примут несколько реплик |
| Один процесс | Учебный пользователь процесса и дефолтный секрет cookie приучают «так оставим» |
| | Успех на одном поде ≠ Ingress + единый вход |

Перед боем полезен **препрод**: ≥ 2 реплики, свои пароли, TLS на Ingress, согласованный флаг cookie, поочерёдный выкат, снимок `.kibana*` — в **одном** дата-центре, рядом с кластером.

## Бой: UI рядом с кластером той же площадки

**Зачем:** пережить отказ **пода UI внутри дата-центра** кластера. Отказ дата-центра с OpenSearch = нет интерфейса, сколько ни ставьте UI в «пустых» площадках. Падение UI ≠ падение 9200.

Официальный паттерн «реплики по трём зонам» имеет смысл **только если** с каждой зоны открыт 9200 до того же кластера. Если кластер живёт в одной площадке, раскладка UI на три города даёт ложное чувство устойчивости: интерфейс поднимется, поиск мёртв.

Полезные факты из схемы «три площадки», которые **остаются внутри одной площадки**:

- Минимум **2** реплики; лучше **3** по разным машинам **этого** дата-центра, если цель — пережить одну машину без потери UI.
- Бюджет сбоя подов: не снять все реплики сразу (при двух — хотя бы одна живая; при трёх разумнее две).
- Одинаковый секрет cookie на всех подах (один Secret).
- Если Helm — сменить дефолт выката с «убить все сразу» на поочерёдное обновление. Иначе устойчивость на бумаге, простой на каждом выкате.
- Пробы в чарте бьют в TCP 5601: это «порт открыт», не «логин и `.kibana` зелёные». Дополнительно смотреть статус UI и здоровье кластера.
- Память: не оставлять 512M из values. Выставить request/limit по стенду; размер кучи V8 **ниже** лимита. README чарта говорит про 4–8 ГиБ *доступно* на хосте — это не ваша смета числа людей.
- Автомасштабирование включать только после профиля: иначе реплики вырастут из-за тяжёлой агрегации, которую лечат шардами OpenSearch.
- Снимок кластера должен включать шаблон **`.kibana*`**. Проверять **восстановление** этих индексов, не только «под UI жив». Документация тенантов прямо: бэкап — снимок индексов тенантов.
- Многотенантность по умолчанию в конфиге Security **включена**. На стороне UI docker-гайд тоже ставит её включённой. В схеме плагина в коде свой дефолт `false` — **не полагаться на дефолт**, задать явно и согласовать с конфигом кластера.
- Личный тенант на каждого пользователя плодит индексы. Если пользователей сотни, а тенанты не нужны — сознательно выключить по политике, а не «как в учебнике».
- Боевые дашборды уметь накатить из **NDJSON** (импорт сохранённых объектов), иначе единственная копия — в кластере.

### Почему не размазываем UI отдельно от кластера

Список адресов кластера — ноды **одного** кластера. Список пишущего и ведомого как запасные = неподдерживаемая лотерея. Задержка UI = задержка до 9200. Реплики UI во второй площадке при мёртвом 9200 первой дают ложное чувство устойчивости.

TLS: для людей лучше валидный сертификат на Ingress; внутри — сгенерированный оператором или свой Secret. Классика поломки логина: Ingress уже HTTPS, до пода HTTP, а cookie помечена «только HTTPS» — логин «не работает». Или наоборот, cookie без этой пометки на открытом HTTP.

ACS-адрес SAML должен быть **стабильным** именем балансировщика, не IP пода, и попасть в белый список XSRF (`/_opendistro/_security/saml/acs`). Несколько реплик это не меняет: URL один.

### Как расставить в активном дата-центре

UI **без своего склада данных** (Deployment, том поиска не нужен). `emptyDir` для кэша Node допустим, в отличие от data-нод OpenSearch.

**Внутри дата-центра, где живёт кластер:**

- Реплики ≥ 2 (лучше 3 по машинам **этой** площадки).
- Адреса кластера — Service coordinating **этого** кластера, HTTPS, полная проверка сертификата.
- Свой пользователь процесса (не demo); роль `kibana_server`. Людей этим логином **не** пускать.
- Свой секрет cookie ≥ 32 символов, один Secret на Deployment. Если браузер ходит HTTPS — cookie только по HTTPS.
- Ingress TLS; флаг cookie согласовать с тем, где заканчивается HTTPS.
- Бюджет сбоя подов; если Helm — поочерёдный выкат.
- `NODE_OPTIONS=--max-old-space-size=…` **ниже** лимита памяти.
- Дефолт Helm 100m CPU / 512M RAM **не** копировать.
- Версия **3.8.0** = кластеру.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | UI только у кластера первой площадки. Если во второй есть ведомая копия индекса — **отдельный** UI на неё, свой `.kibana*`, не админка прав «как на пишущем» | Нет UI пишущего кластера. UI второй площадки, если есть, видит только ведомого (только чтение) |
| **Три** | Не ставить UI «во все зоны для устойчивости», если 9200 только в первой | То же |

Честный запас UI = запас кластера (восстановление снимка, включая `.kibana*`) + выкатить UI к новому 9200.

Несколько источников в одном UI — отдельное решение (второй контур прав в одной сессии). Timeline с этим режимом **не** поддерживается. Wazuh в этот UI не подключать.

### Что должно быть до боевой установки

- Живой OpenSearch 3.8.0 в том же дата-центре, HTTP TLS на 9200, пользователь процесса создан.
- Заголовок `securitytenant` в белом списке вместе с `Authorization` — иначе UI стартует **красным** (документация).
- Снимок кластера включает `.kibana*`. Проверять восстановление этих индексов.
- Единый вход (OpenID Connect / SAML) + запасной парольный вход (`?auto_login=false`, если включён авторедирект). `admin` в UI ежедневно запрещён.
- Секреты: пароль пользователя процесса, cookie, client secret OpenID Connect. Оператор без вашего секрета **генерирует** пароль в `<cluster>-dashboards-password` — лучше demo, но Secret включить в эксплуатацию. Смена Secret OpenID Connect **без** рестарта подов не подхватывается (документация оператора). Невалидный ключ в дополнительном конфиге = UI **не стартует**.

### Порядок установки в активном дата-центре

В объекте кластера OpenSearch:

```yaml
spec:
  dashboards:
    enable: true
    version: "3.8.0"
    replicas: 2
    # tls: лучше валидный сертификат на Ingress; внутри — generate или Secret
```

1. Иметь выбранную схему OpenSearch и рабочий 9200 с TLS.
2. Создать Secret: пользователь процесса, секрет cookie, секреты единого входа.
3. Включить dashboards: версия 3.8.0, реплики ≥ 2, разнос по машинам, бюджет сбоя, поочерёдный выкат (если Helm).
4. Согласовать HTTPS Ingress и флаг cookie.
5. Проверить логин, шаблон индекса, что падение **одного** пода не разлогинивает (cookie общий) и балансировщик не отдаёт 502.
6. Убедиться, что `.kibana*` в политике снимка и восстановление прогнано.
7. Подключить единый вход на препроде, запасной парольный вход.
8. Учение «под UI убит»: интерфейс жив с другой реплики. Учение «9200 недоступен»: честно ожидаем красный экран.

Helm-запас: число реплик ≥ 2, выкат поочерёдный, ресурсы не 100m/512M из values.

Не отдавать Service типом NodePort / LoadBalancer в мир «чтобы проверить». Не ставить лимит памяти = куча V8.

### Правила конфигурации боя

| Слой | Правило |
|---|---|
| Сеть | 5601 не в интернет без единого входа. Сетевая политика: Ingress → UI → 9200 coordinating. Метрики — только Prometheus |
| Пользователь процесса | Не пускать людей этим логином |
| Многотенантность | Задать явно, согласовать с конфигом кластера. Личный тенант × сотни пользователей = сюрприз кучи cluster manager |
| SAML | Стабильный URL балансировщика, не IP пода; в белом списке XSRF |
| Аноним | Не включать на персональных данных |
| Пробы | TCP 5601 в чарте = «порт открыт», не «`.kibana` зелёный» |
| Proxy-заголовки | Только если UI недоступен в обход proxy |
| Секреты | Не в Git, не в ConfigMap открытым текстом |
| Аудит | Аудит Security plugin на кластере; отдельно — журнал доступа Ingress |

### Как расти, когда появятся цифры нагрузки

1. Больше людей → реплики UI **в том же дата-центре**.
2. Тяжелее Discover → **кластер** OpenSearch, не пятый Dashboards.
3. Автомасштабирование только после профиля.

### Проверки, без которых это ещё не бой

1. Версия UI = 3.8.0 = кластеру.
2. Логин, шаблон индекса. Убить один под: балансировщик не 502, cookie принимается другой репликой.
3. `.kibana*` в снимке, восстановление прогнано.
4. Учение «под UI убит» vs «9200 недоступен»: второе — честно красный экран.
5. Нет дефолтного секрета cookie, нет `kibanaserver` / `kibanaserver`.

### Что хорошо и что плохо в схеме «UI рядом с локальным кластером»

| Хорошо | Плохо |
|---|---|
| Короткий путь до 9200 | Падение дата-центра кластера = нет интерфейса |
| Горизонталь без Redis | Утечка секрета cookie = подделка сессий |
| Сохранённые объекты в снимке кластера | Реплики UI в чужом дата-центре без 9200 бесполезны |
| | Дефолт Helm «убить все сразу» = простой UI на каждом выкате, если забыли сменить |

**Не готово к бою**, если: одна реплика; Helm «убить все сразу»; проверка сертификата выкл; дефолтный секрет cookie; учебный пользователь процесса; 5601 опубликован; версии разъехались; UI размазан «для устойчивости» при кластере в одном дата-центре; Wazuh и бизнес-поиск в одном UI; нет снимка `.kibana*`.
