# ClickHouse 26.7.5.10 — развёртывание и настройка

Версия ПО: **ClickHouse 26.7.5.10-stable** (релизная дата 21 августа 2026; на дату подготовки документа это последний стабильный патч линии 26.7).  
Документация: https://clickhouse.com/docs/  
Образы: `clickhouse/clickhouse-server:26.7.5.10`, `clickhouse/clickhouse-keeper:26.7.5.10`.  
На Kubernetes целевой путь для **self-hosted OSS** (данные на диске реплик): **Altinity Kubernetes Operator 0.27.3** (релиз 12 августа 2026; CR `ClickHouseInstallation` / `ClickHouseKeeperInstallation`). Это не ClickHouse Cloud и не ClickHouse Private (там другая модель: SharedMergeTree + объектное хранилище).

Этот текст — не мануал «скопируй и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

ClickHouse **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить аналитическую СУБД на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** замена озера эталонных данных, **не** OLTP и **не** шина событий.

Альтернатива по политике обновлений: линейка **LTS 26.3** (на дату документа последний патч **26.3.21.7-lts**, 22 августа 2026). Вендор по умолчанию рекомендует `stable`; LTS — если внутренние правила запрещают частые major. **Не смешивать** 26.7 и 26.3 в одном кластере.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Сервер (clickhouse-server)** | Процесс, который принимает SQL, хранит таблицы, отвечает на запросы. «Нода данных». |
| **Реплика** | Копия **одного шарда** на другом сервере. Нужна, чтобы падение ноды не уничтожило данные шарда. |
| **Шард (shard)** | Кусок данных. Параллелизм хранения и скана = шарды. У каждого шарда свой набор реплик. |
| **Кластер в `remote_servers`** | Именованный список шардов и реплик в конфиге. По нему работают `ON CLUSTER` и движок `Distributed`. Это не «автоматический Hadoop». |
| **MergeTree** | Основной движок таблиц: колоночное хранение, данные пишутся **частями (parts)** и в фоне сливаются (merge). Не транзакционная СУБД «как PostgreSQL». |
| **ReplicatedMergeTree** | MergeTree + репликация через Keeper. Без него «три сервера» — три разные базы, а не одна отказоустойчивая. |
| **Distributed** | Таблица-прокси: `SELECT`/`INSERT` размазывает запрос по шардам. Сама данные не хранит. |
| **Part (кусок)** | Файл(ы) на диске с порцией вставленных строк. Слишком много мелких parts — кластер захлёбывается merge и может **отклонять INSERT**. |
| **ORDER BY** | Ключ сортировки на диске. Это не «PRIMARY KEY из PostgreSQL»: от него зависит, сколько данных пропустит запрос. Меняется только через новую таблицу. |
| **TTL** | Правило «через N дней удали / перенеси». Без него «терабайты» съедят диск сами. |
| **Мутация (`ALTER UPDATE` / `DELETE`)** | Переписывание частей на диске. Дорого. ClickHouse не замена OLTP, где строки правят по одной. |
| **ClickHouse Keeper** | Координатор репликации и распределённого DDL (создание таблиц на всех нодах). Замена ZooKeeper, свой Raft. Смешанный кластер Keeper+ZooKeeper **невозможен**. |
| **Кворум Keeper** | Большинство голосов Raft. Для 3 нод большинство = 2. Если живых меньше — нет лидера, реплицируемые таблицы уходят в **read-only**. |
| **`ON CLUSTER`** | DDL сразу на все ноды кластера (через Keeper). Без этого `CREATE TABLE` создаст таблицу **только на той ноде, куда вы подключились**. |
| **Макросы `{shard}` / `{replica}`** | Подстановки в пути Keeper и в имена реплик, чтобы один и тот же SQL работал на всех нодах. |
| **`internal_replication`** | В `remote_servers`: `true` = Distributed пишет **в одну** здоровую реплику, дальше копирует ReplicatedMergeTree. `false` (дефолт движка Distributed) = пишет во **все** реплики сам — для ReplicatedMergeTree это хуже и плодит расхождения. |
| **`insert_quorum`** | Сколько реплик должны подтвердить INSERT, чтобы клиент получил успех. Дефолт: подтверждение **с одной** реплики. Если эта реплика умерла до копирования — блок **пропал**. Кворум < 2 = выключен; `'auto'` = большинство реплик. |
| **`insert_quorum_parallel`** | Можно ли слать следующий quorum-INSERT, пока предыдущий ещё не дошёл. Выключено — строгая последовательность, ниже пропускная способность. |
| **`select_sequential_consistency`** | Читать только то, что уже лежит на кворуме реплик. Иначе SELECT может не увидеть только что «успешно» вставленное на другой реплике. |
| **HTTP 8123 / HTTPS 8443** | REST/HTTP интерфейс (JDBC-over-HTTP, curl, многие драйверы). |
| **Native 9000 / 9440** | Свой TCP-протокол. Им говорят `clickhouse-client`, межсерверные Distributed-запросы, часть драйверов. 9440 — то же с TLS. |
| **Interserver 9009 / 9010** | Передача частей **между репликами** (репликация данных). 9010 — TLS. Сюда клиенты не ходят. |
| **Keeper 9181 / 9281 / 9234** | Клиентский порт Keeper (9181 рекомендуется таблицей портов вендора; в XML дефолт тега `tcp_port` исторически 2181, как у ZooKeeper). 9281 — TLS клиента. 9234 — Raft между нодами Keeper. |
| **`users.xml` / `users.d`** | Файловые учётки. Вендор рекомендует **SQL-driven** пользователей (`CREATE USER`). Учётки из XML **не входят** в `BACKUP`. |
| **SQL access control** | Пользователи, роли, квоты, row policy через SQL. Это то, что умеет бэкапиться вместе с кластером. |
| **`default` (пользователь)** | Встроенная учётка. В Docker без пароля **нет сетевого доступа**; с `CLICKHOUSE_SKIP_USER_SETUP=1` её открывают «чтобы завелось». В проде это дыра. |
| **Named collection** | Именованный набор секретов (S3-ключи и т.п.) в конфиге сервера, а не в тексте SQL пользователя. В 26.7 пользовательский SQL **больше не подхватывает** облачные credentials процесса по умолчанию. |
| **Stretch-кластер** | Один логический кластер, ноды в нескольких ЦОДах. Keeper и репликация ходят по сети между площадками. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. |
| **Too many parts** | Состояние, когда мелких кусков слишком много: merge не успевает, INSERT начинают отклоняться. Типичная цена «пишем по одной строке из каждого микросервиса». |

## Основные элементы системы и зависимости

### Что входит в ClickHouse OSS (это одно ПО из нескольких процессов)

| Компонент | Зачем | Как масштабируется |
|---|---|---|
| **clickhouse-server** | Данные + SQL | Вертикаль (больше CPU/RAM/диск на реплику) **раньше**, чем новые шарды. Горизонталь: шарды (ёмкость/скан) и реплики (HA и чтение) |
| **ClickHouse Keeper** | Метаданные реплик, `ON CLUSTER` | Нечётное число, типично **3** dedicated. Не масштабируют «от QPS аналитики» |
| **clickhouse-client / HTTP** | Клиенты | Stateless относительно данных |
| **Движки таблиц** | MergeTree / Replicated\* / Distributed / Kafka / … | Выбираются **на таблицу**, не «на кластер галочкой HA» |

Плюс *рядом*, но это уже другое ПО: **Kafka Connect ClickHouse Sink**, Vector/Fluent Bit, Grafana, объектное хранилище под `BACKUP`. Их HA проектируется отдельно.

ZooKeeper **не нужен**, если ставите Keeper. Вендор Keeper рекомендует; ZooKeeper 3.4.5+ ещё допустим, смешанный кворум — нет.

### Официальные порты (менять можно, это контракт сети)

| Порт | Назначение |
|---|---|
| **8123/TCP** | HTTP |
| **8443/TCP** | HTTP + TLS |
| **9000/TCP** | Native TCP, Distributed |
| **9440/TCP** | Native + TLS |
| **9009/TCP** | Interserver: копии parts между репликами |
| **9010/TCP** | Interserver + TLS |
| **9181/TCP** | Keeper, клиенты (рекомендованный) |
| **9281/TCP** | Keeper клиент + TLS |
| **9234/TCP** | Keeper Raft |
| **9363/TCP** | Prometheus-метрики (если включили endpoint) |
| **9004 / 9005 / 9100** | Эмуляция MySQL / PostgreSQL / gRPC — в проде **выключают**, если не используете |

Клиентов кладут на 8123/8443 или 9000/9440. **На Keeper и на 9009 внешний трафик не пускают.**

Балансировщик HTTP перед 8123/8443 допустим. Native 9000 тоже можно закрыть Service/LB для **клиентов**. Репликация 9009 и Raft 9234 — **прямое** соединение нода↔нода (как transport 9300 у OpenSearch). VIP «как один адрес на все 9009» ломает копирование parts.

### Чего в ClickHouse нет (частая путаница)

| Нужно системе | Это не ClickHouse | Зачем помнить |
|---|---|---|
| Источник истины клиентских карточек / «озеро эталона» | Озеро / транзакционная СУБД | ClickHouse — колоночный OLAP: быстрый скан и агрегации, слабые точечные UPDATE/DELETE, нет нормальных многотабличных транзакций |
| Шина событий и consumer group | Apache Kafka | Сюда данные **попадают** из Kafka, не заменяют её |
| Camunda / BPMN | Process engine | Можно хранить *аналитику* по процессам, не исполнять их |
| Интеграции с госслужбами | Ваше интеграционное API | Сюда — нормализованные факты *для отчётов*, не хождение в ведомства |
| Exactly-once из коробки у Kafka engine | ClickHouse Kafka Connect Sink (`exactlyOnce` + KeeperMap) | Встроенный Kafka-движок — **at-least-once**; дубли возможны |
| Автошардирование «добавил ноду — данные сами разъехались» | Нет | Решардинг дорогой. Вендор: сначала вертикаль, шарды — когда одна машина уже мала |
| Гарантия INSERT на все реплики по умолчанию | Нужен `insert_quorum` | Дефолт — подтверждение **одной** реплики |
| Замена бэкапа репликами | `BACKUP`/`RESTORE` (S3 и др.) | Реплика спасает от падения **ноды**. Не спасает от `DROP TABLE`, кривого TTL, шифровальщика |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный OpenSSL/TLS — не криптография по требованиям КИИ, если ИБ их выдвинет |
| Официальный порог RTT между ЦОДами | Нет | Raft Keeper и quorum-INSERT ходят по сети; миллисекунд в доке **нет** |
| Гарантия «терабайты влезут» | Нет | Диск = сжатый объём × (реплики) × запас под merge/мутации/бэкап. Нагрузки у вас нет |

### Зависимости окружения (обязательны)

- **ОС.** Linux x86_64 / ARM64 как основной контур. Прод на Windows-host в схеме с Kubernetes не предполагается.
- **Диск сервера.** Локальные **SSD/NVMe**, POSIX. Для производительности вендор прямо указывает provisioned IOPS SSD (или эквивалент). **Не NFS / не «сетевая папка как `/var/lib/clickhouse`».** Merge и INSERT чувствительны к латентности fsync.
- **Диск Keeper.** Отдельный быстрый том под Raft-лог и снимки. `force_sync` по умолчанию **true**: каждое признание записи идёт через fsync. Медленный диск Keeper = медленный DDL и репликация **всего** кластера. Ориентир из туториала вендора: **~4 ГиБ RAM** на Keeper «пока серверы данных не выросли»; это не замер вашего кворума.
- **Файловые дескрипторы.** В Docker-гайде: `--ulimit nofile=262144:262144`.
- **Сеть:** стабильный DNS/IP каждой ноды на 9000/9009 и каждого Keeper на 9181/9234. Для `host` в конфиге вендор просит **имя, а не сырой IP**, если хост может смениться: смена hostname у Keeper = вывести и ввести сервер в кворум, иногда это невозможно (не хватит живых).
- **Kubernetes:** CSI с **RWO** PVC на каждую реплику и каждый Keeper; StorageClass с предсказуемым IOPS. Для данных OSS **не** `emptyDir` (это потеря parts при рестарте пода). `emptyDir` как кэш — модель ClickHouse Private/Cloud, не этого документа.
- **PKI** для прода. Self-signed «из туториала» — только стенд.
- **Репозиторий бэкапов** (S3-совместимый), доступный с нод. Реплики его не заменяют.
- **Java на ClickHouse не нужна.** Это C++. Java понадобится рядом, если ставите **Kafka Connect**.

### Как ClickHouse стыкуется с вашей архитектурой

```
Микросервисы, Camunda, интеграционное API
        │  события
        ▼
   Kafka  ──►  Kafka Connect Sink (предпочтительно)
        │         или Kafka engine + MV (at-least-once, встроено)
        ▼
   ClickHouse (OLAP: отчёты, витрины, логи, аудит интеграций)
        ▲
        │  SQL / HTTP / native
   BI, сервисы чтения, Grafana

Озеро эталонных данных  ──остаётся SoT──►  (в ClickHouse можно *скопировать* то, что надо считать)
PostgreSQL / операционные БД  ──не этот контур──►  точечные транзакции
```

Честные роли в *вашей* картине:

1. **Аналитическая проекция** эталона и фактов интеграций — «сколько обращений, какие сроки, какие ошибки ведомств», а не «дай клиента по ИНН и поправь ФИО».
2. **Наблюдаемость большого объёма** (логи сервисов/Camunda), если не упрётесь в OpenSearch как в основной поиск.
3. **Витрины** для отчётов, которые Kafka и озеро сами по себе плохо считают за секунды.

Нечестная роль: «положим клиентов только в ClickHouse, озеро потом». Точечные правки, юридически значимые карточки и процессный стейт Camunda здесь живут плохо: мутации дорогие, кворум INSERT — про блоки, не про строки.

## Краткие вводные

### Зачем вам ClickHouse в этой архитектуре

Kafka доставляет факт. Озеро хранит истину. Camunda ведёт процесс. Интеграционное API ходит наружу. Остаётся вопрос: **как считать агрегаты по терабайтам** (сроки интеграций, полнота эталона, нагрузка сервисов), не убивая транзакционную БД и не превращая OpenSearch в warehouse.

ClickHouse закрывает колоночный скан, сжатие, шарды, реплики. Он **не** делает микросервисы event-sourced — он может быть одним из консьюмеров шины.

### Как устроена отказоустойчивость (идея, не магия)

Это **кворум Keeper** плюс **копии шарда** плюс **явный quorum на INSERT**. Путать «три контейнера с MergeTree» с HA — главная ошибка.

**1) Keeper**

| Что падает | Что происходит |
|---|---|
| Один Keeper из 3 | Остаётся 2, кворум есть, выбирается другой лидер |
| Два Keeper из 3 (два ЦОДа, по одному Keeper) | Кворума нет. Нет лидера. Реплицируемые таблицы — **read-only**. Новые `ON CLUSTER` не проходят |
| Keeper совмещён с тяжёлым clickhouse-server на тех же дисках | Нагрузка аналитики бьёт по fsync Raft → «странно медленный DDL и репликация» |
| Все Keeper в одном ЦОДе | Падение площадки = нет координации, даже если данные реплик живы в других ЦОДах |

Вендор: *we strongly recommend using dedicated hosts for ClickHouse keeper in production*. Совмещать на одном процессе «можно», для прода — нет.

«Never» при трёх Keeper в трёх зонах значит «при потере **одной** зоны», не «при потере двух».

**2) Данные (реплики + insert_quorum)**

| Что падает | Что происходит |
|---|---|
| Одна реплика, данные уже успели скопироваться | Чтение с оставшихся. Запись жива, если живых реплик ≥ `insert_quorum` |
| Реплика, на которую только что успешно записали **без** quorum, умерла до копирования | Блок **потерян**. Это штатное поведение дефолта, не баг |
| ЦОД при 3 репликах 1+1+1 и `insert_quorum=2` | Остаются 2 копии, запись может продолжаться; латентность INSERT включает сеть до второй площадки |
| ЦОД при `insert_quorum=3` | Запись **встанет**, пока нет трёх живых реплик |
| Нет `BACKUP`, погибли все копии шарда / сделали `DROP` | Данных нет. Реплика не бэкап |

Репликация **таблицы**, не «всего сервера». На одной ноде могут быть и ReplicatedMergeTree, и голый MergeTree (последний при падении ноды просто исчезает).

`CREATE`/`DROP`/`RENAME` **сами по репликам не едут** — нужен `ON CLUSTER` (или повторить DDL). Иначе получите «на одной ноде таблица есть, на другой нет».

**3) Клиентский вход (LB / Service)**

Падение одного сервера при правильном LB ≠ падение кластера. Один Service без антиаффинити всех реплик в одном ЦОДе — SPOF **площадки**, не протокола.

**4) Пайплайн перед кластером**

Connect / Kafka engine упал — ClickHouse хранит старое, новое не приходит. Буфер должен быть **в Kafka**, не «в надежде что sink не умрёт».

### Как устроено масштабирование

Несколько независимых осей (их нельзя путать):

1. **Больше объёма и тяжёлых сканов** → сначала **вертикаль** реплик (CPU/RAM/диск). Вендор прямо: ClickHouse сам не шардирует; решардинг дорогой; «берите машину побольше, чтобы не шардировать рано».
2. **Когда одна реплика уже не влезает** → **шарды**. Данные при INSERT в Distributed надо ключом шардирования разложить самим (или приложением писать в нужный шард).
3. **HA и чтение** → **реплики шарда**. Вендор: **не меньше трёх реплик на шард** (или две, если диск — Amazon EBS; у вас on-prem ЦОДы, EBS нет — ориентир **3**).
4. **Keeper** почти не масштабируют «от QPS отчётов». Ему важны fsync и число операций метаданных. Документация репликации: на каждый блок INSERT в Keeper уходит порядка **десяти записей**; рекомендация «не чаще одного INSERT в секунду» относится к **мелким** вставкам в координатор, не к строкам. Поток строк может быть огромным, если батчи крупные. «Несколько сотен INSERT/с на весь кластер в один Keeper» — формулировка вендора про нагрузку на координатор, не смета вашего склада.

Ориентиры, которые **есть** у вендора и которые **нельзя** принять за смету вашего прода:

- RAM не ниже **8 ГиБ** даже на малых объёмах; для «частого доступа» отношение RAM:диск примерно **1:30–1:50**; для длинного хранения **1:100–1:130** (пример: 100 ГиБ RAM на 10 ТБ данных на реплику).
- CPU:warehouse — линейки memory-optimized; целевая утилизация CPU для ad-hoc warehouse в тексте вендора — порядка **10–20%** (запас под пик, не «загрузить на 90%»).
- Примеры «Fortune 500» в том же гайде — чужие кластеры (сотни ТБ, десятки реплик). Это иллюстрация, не ваш BOM.

С версии **26.3** (есть и в 26.7) **async insert включён по умолчанию**: мелкие INSERT сервер сам пакует. Это не отменяет батчи на стороне Kafka Connect. Миллионы одиночных строк из 30 интеграций всё равно рождают parts и давят Keeper.

### Безопасность самого ClickHouse

Компрометация кластера с витринами клиентов или аудитом гос-интеграций = компрометация **ПДн и ответов ведомств**. Учётка `default` без пароля и открытый 8123 в интернет равносильны ключу от склада.

Официально / из инсталляторов:

- Пользователь `default` без пароля; в Docker сетевой доступ у него **выключен**, пока не зададите пароль/`CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT`.
- `CLICKHOUSE_SKIP_USER_SETUP=1` открывает `default` «небезопасным образом» — только лаборатория.
- Туториал репликации сам пишет: *In this example, the default user is configured without a password for simplicity. In practice, this is discouraged.*
- `listen_host` надо задавать явно, иначе нода может слушать не то, что вы думаете; `0.0.0.0` без NetworkPolicy — весь интерфейс.
- В `users.xml` открыть `<ip>::/0</ip>` вендор называет небезопасным, если нет нормального firewall.
- Учётки только в XML не попадут в `BACKUP`.
- В 26.7 SQL пользователя по умолчанию **не берёт** server-side cloud credentials для S3.

«Поднять `docker run` из гайда и выдать 8123 в интернет» — это новый attack surface, не аналитическая платформа.

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Берём self-hosted OSS ClickHouse 26.7.5.10**, не ClickHouse Cloud и не ClickHouse Private. Облако и Private живут на SharedMergeTree + object storage: другие диски, другие операторы, другие обещания консистентности. Их манифесты сюда копировать нельзя.
2. **Прод крутится в Kubernetes**, целевой инсталлятор — **Altinity Operator 0.27.3**. Чарты/манифесты пинить **тегом релиза**, не `latest`. Перед продом — прогон именно **26.7.5.10** на стенде: оператор умеет много версий ClickHouse, «latest» не заменяет проверку CRD.
3. Если политика обновлений требует LTS — **весь** кластер на **26.3.21.7-lts**, не «серверы 26.7, Keeper 26.3».
4. **Три ЦОДа = три зоны отказа.** Если это три зала с общим питанием — stretch даёт ложное чувство безопасности.
5. **Stretch (один кластер на 3 ЦОДа)** принимается как целевой для прода **только если** сеть Keeper (9234) и interserver (9009) достаточно быстрая и стабильная. Порога RTT у проекта **нет**. Пока RTT не измерен — это гипотеза.
6. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. Три Keeper по одному на ЦОД это переживают; два мёртвых ЦОДа — нет.
7. **Нагрузки нет** — поэтому **нет** цифры «N шардов и M терабайт PVC». Есть сигналы (parts, replication delay, CPU, RAM, disk, лаг Kafka) и рычаги (вертикаль, реплики, шарды, TTL, батчи).
8. **Формального SLA / RPO / RTO нет.** Живые 3 реплики ≠ юридический 24/7 и ≠ «ни один факт интеграции не потерян, если sink отстал».
9. **Корпоративный PKI есть или будет.** Self-signed — для теста.
10. **Идентификация:** люди — отдельные SQL-пользователи/SSO-обвязка снаружи; сервисы — свои учётки, least privilege на базы/таблицы. Общий `default` у приложений — запрещён.
11. **Шифрование канала — TLS OpenSSL.** Требования ГОСТ/СКЗИ не озвучены; vanilla ClickHouse их не закрывает.
12. **Тестовый стенд изолирован.** На нём допустимы single-node, HTTP без TLS и слабые лимиты. В прод их не копируем.
13. **Kafka, Camunda, озеро, интеграционное API** — источники и потребители, не часть этого ПО. Контракт: батч INSERT, ключ шарда, схема колонок, TTL, идемпотентность на уровне блока.
14. **Лицензия Apache 2.0** у OSS ClickHouse. Отдельного license-server нет. Следить нужно за обвязкой (Connect, UI, оператор — свои лицензии).
15. **Питание из Kafka в проде** — **ClickHouse Kafka Connect Sink** с `exactlyOnce` (KeeperMap), не ставка «только Kafka engine на сервере». Engine оставляем как упрощение стенда / запасной контур. Connect — отдельный кластер с собственным HA (это не этот файл).

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили оператор и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потери между ЦОДами** на 9234 (Raft), 9181, 9009, 9000 (p50/p95/p99, все пары) | Дефолты Keeper: heartbeat **500 мс**, окно выборов **1–2 с**. Если RTT/jitter сопоставимы — ложные выборы лидера и уход реплицируемых таблиц в read-only. Quorum-INSERT не быстрее, чем доставка блока на вторую площадку |
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Stretch требует pod-to-pod (9009/9234). Иначе — один кластер в одном ЦОДе + DR через `RESTORE`, не один экземпляр |
| **Что именно кладёте в ClickHouse** (витрины эталона? аудит 30+ интеграций? сырые логи? всё сразу?) | Разный `ORDER BY`, TTL, шардирование, класс диска, RBAC. «Терабайты» без состава — не смета |
| **Профиль: INSERT/с и размер батча vs одновременные тяжёлые SELECT** | Иначе купите CPU «под отчёты», а умрёте на parts; или наоборот |
| **Срок хранения и 152-ФЗ/КИИ** | TTL, что можно класть в колонки (ПДн в OLAP!), куда уезжает `BACKUP` |
| **Где живёт бакет бэкапа** | Если только в одном ЦОДе — падение этой площадки убивает бэкап |
| **Нужна ли запись при падении 1 ЦОДа** | Тогда `insert_quorum=2` (при 3 репликах), не 3. Иначе «HA на чтение» без HA на запись |
| **StorageClass: local SSD vs сеть** | Медленный PVC = рост parts, отставание реплик, лаг sink при «живом» SQL |
| **Совместимость оператора 0.27.3 с вашей версией Kubernetes** | Релиз оператора не заменяет проверку в вашем контуре |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **26.7.5.10** на **server и Keeper** (или весь контур на LTS 26.3.21.7). Не `latest`.
2. Выбрать роли: Keeper **отдельно** в проде; на тесте допустимо combined.
3. Поднять кворум Keeper, проверить `echo ruok \| nc ...` / `mntr` (живой процесс ≠ член кворума; `ruok` это прямо пишет документация).
4. Поднять серверы, прописать `zookeeper`/`keeper` nodes, `macros`, `remote_servers`.
5. Выпустить **своих** пользователей и TLS **до** боевых клиентов. Не оставлять пустой пароль `default`.
6. Создать таблицы **ReplicatedMergeTree `ON CLUSTER`**, не голый MergeTree «на одной ноде».
7. Зарегистрировать диск/endpoint для **`BACKUP TO S3`** и сделать первый снимок тестовой таблицы (проверка, что restore вообще работает).
8. Задать **TTL / ORDER BY** до боевого потока. ORDER BY потом дешево не поменять.
9. Включить метрики: `system.replicas`, parts, disk, query log, Keeper `mntr`, лаг консьюмера Kafka.
10. Прогнать батч INSERT и SELECT. Убедиться, что падение одной реплики на проде оставляет таблицу читаемой **и** что INSERT с `insert_quorum=2` проходит.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики писали SQL, подбирали `ORDER BY`, смотрели сжатие ваших JSON/событий из Kafka. **Не** цель: доказать отказ ЦОДа и ёмкость.

**Путь A — один контейнер** (быстрее понять продукт):

```text
docker run -d \
  --name ch-dev \
  --ulimit nofile=262144:262144 \
  -p 8123:8123 -p 9000:9000 \
  -e CLICKHOUSE_PASSWORD=<strong-password> \
  -e CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT=1 \
  clickhouse/clickhouse-server:26.7.5.10
```

Проверка: `clickhouse-client` или `curl 'http://localhost:8123/?user=default&password=...'`.  
Без пароля в Docker `default` **не слушает сеть** — это не «сломанный образ».

**Путь B — официальный compose-пример репликации** (`cluster_1S_2R`: 2 сервера + 3 Keeper). Вендор даёт его как **учебный** docker-compose, не как прод. В примере часто `default` без пароля — *discouraged in practice*.

На Kubernetes: один `ClickHouseInstallation` с 1 репликой, маленький PVC, без отдельного CHK. Не копировать этот YAML в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число серверов | 1 | Нет требования пережить выкат |
| Keeper | нет (обычный MergeTree) | Иначе команда утонет в Raft раньше, чем в `ORDER BY` |
| Реплики | 0 | Некому копировать |
| TLS | нет, сеть изолирована | Иначе PKI раньше SQL |
| Пароль | свой сильный `CLICKHOUSE_PASSWORD` | Без него с хоста не зайдёте; в интернет всё равно не открываем |
| CPU/диск | минимальные | Не цель — ёмкость |
| Kafka engine | можно | На стенде проще, чем поднимать Connect |
| BACKUP | можно отложить на день | Нельзя «забыть навсегда» — на препроде бакет обязателен |

#### Чего на тесте **не** стоит упрощать

- Версия **26.7.5.10** (или сразу LTS, если прод будет LTS).
- Таблицы с явным `ORDER BY` под **ваши** запросы («по client_id + дате», «по id интеграции + времени»), не `ORDER BY tuple()`.
- Батчи INSERT, не «INSERT каждой строки из цикла». Async insert дефолтен с 26.3, но схема «30 интеграций по одной строке» всё равно врёт про прод.
- Понимание, что **голый MergeTree на одной ноде не реплицируется**. Успешный SELECT на ноутбуке **не** доказывает `insert_quorum` и Raft.

#### Сильные стороны такой схемы

- Поднимается за часы, совпадает с официальным Docker-гайдом.
- Дешево показывает кардинальность, сжатие и «какие GROUP BY взрывают RAM» на *ваших* данных.
- Single-node официально нормален для development.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет Keeper, нет 9009 между площадками.
- Успешный отчёт на одном узле **не** доказывает, что quorum-INSERT переживёт RTT и что `ON CLUSTER` создаст таблицу везде.
- HTTP без TLS и учётка `default` приучают «зайти как получится».

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (3 Keeper + 1 шард × 3 реплики, TLS, `insert_quorum=2`, BACKUP), даже без боевого трафика.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты озера» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

ClickHouse плохо переживает **три независимых правды** (три склада клиентов) и плохо переживает **слепой stretch** по Raft.

**Вариант A — один Kubernetes на 3 ЦОДа (зоны), один кластер.**

- 3 dedicated Keeper (по одному в зоне) + реплики **пачками по 3**.
- Старт ёмкости: **1 шард × 3 реплики** (по реплике в ЦОД). Это минимум **размещения**, не терабайты.
- Таблицы: только **ReplicatedMergeTree** (или Replicated\* из семейства) для того, что должно пережить ноду.
- `remote_servers`: `internal_replication=true`.
- Профиль записи: `insert_quorum=2` или `'auto'` (при 3 репликах большинство = 2). `insert_quorum=3` остановит запись при падении одной площадки.
- `insert_quorum_parallel=1`, если не нужна линеаризация INSERT. Иначе пропускная способность кворум-записи просядет.
- Клиенты: Service/LB на 8443/9440, не на Keeper.
- Антиаффинити / topology spread: не сложить две реплики шарда и двух Keeper в одну зону.

**Вариант B — три изолированных Kubernetes, сеть 9009/9234 между ними нет или RTT неприемлем.**

- **B1. Один кластер в одном ЦОДе**, клиенты с остальных ходят SQL на него. Простой кворум Keeper. Падение этого ЦОДа = нет аналитики ни у кого. Спасает `BACKUP` + заранее прогнанный `RESTORE` на другой площадке (RTO надо замерить).
- **B2. Три независимых кластера.** Нет единого SELECT «по всем ЦОДам» без прикладного слоя. Для SoT это даже хорошо (не плодить три истины), для «единый отчёт по стране» — плохо.

**Пока топология K8s и RTT не зафиксированы, нельзя честно выбрать A.** Дальше — общее для A как целевого «3 ЦОДа в одном городе»; B — запасной.

Не рекомендую «Keeper все в ЦОД-1, реплики в трёх ЦОДах»: падение ЦОД-1 оставляет данные, но **без** координации (read-only). Это не переживание площадки, а «диск ещё лежит».

##### Сильные / слабые стороны (A, stretch)

| Сильное | Слабое |
|---|---|
| Один SQL-кластер, один набор таблиц, один RBAC | Латентность Raft и quorum-INSERT = латентность межЦОДовой сети |
| Падение 1 ЦОДа при 3 Keeper + 3 репликах + quorum=2 может оставить и чтение, и запись | Падение двух ЦОДов снимает кворум Keeper |
| Официальный паттерн dedicated Keeper | Без замера RTT — лотерея выборов и read-only |
| Клиентам один endpoint | Ошибка `ORDER BY`/TTL сразу везде |

##### Сильные / слабые стороны (B1, мозг в одном ЦОДе)

| Сильное | Слабое |
|---|---|
| 9234/9009 не ходят между ЦОДами | Падение ЦОДа с кластером = нет аналитики на всех трёх |
| Проще кворум и диск | Нужен очень явный DR: restore **с прогоном по времени** |
| | Клиентский SQL через город: это уже ваша сеть |

##### Слабое место любого stretch без замера RTT

Документация **не задаёт** порог задержки. Утверждение «три ЦОДа в одном городе, значит можно размазать Keeper» — **непроверенное**. Городская сеть бывает и долями миллисекунды, и «через кривой firewall 40 мс с потерями». Мерить **9234 и 9009**, не ping ICMP «на всякий случай». Если p99 сопоставим с heartbeat 500 мс — вариант A снимать, не «подкрутить timeouts вслепую» без понимания, что вы размениваете скорость обнаружения мёртвого лидера.

#### Keeper и кворум

- Dedicated: отдельный Deployment/CHK, отдельные PVC, отдельные ноды (taint), не соседствовать с тяжёлым merge.
- Нечётное число. **3** — старт. **5** (например 2+2+1) переживает два отказа **процессов**, но не два ЦОДа из трёх.
- `server_id` не переиспользовать и не перемешивать при замене ноды (прямое предупреждение вендора).
- `async_replication` у Keeper с версии 23.9+ рекомендуется включить, когда **все** ноды кворума её умеют (26.7 умеет); по умолчанию выключена ради совместимости.
- ACL digest на znode — «don't neglect», формулировка доки репликации.
- После потери кворума серверы с ReplicatedMergeTree не «сами станут одиночными MergeTree». Они ждут Keeper.

#### Шарды, реплики, таблицы

- Боевые факты: `ENGINE = ReplicatedMergeTree` + `CREATE ... ON CLUSTER`.
- Путь в Keeper уникален на таблицу (`/clickhouse/tables/{shard}/.../{uuid}`). Клонировать путь = сломать репликацию.
- `Distributed` — для чтения/записи по шардам, не вместо репликации. Под ним — Replicated\*, `internal_replication=true`.
- Не плодить шард «на всякий случай»: решардинг — отдельный проект.
- TTL с первого дня. Срок — решение ИБ/бизнеса, не дефолт вендора.
- `ORDER BY` под фильтры отчётов. Плохой ключ = полный скан терабайт при живом CPU.

Запись из приложений:

- Батчи. Connect sink, не «по строке из REST».
- `insert_quorum=2` (3 реплики, цель — 1 мёртвый ЦОД).
- Идемпотентность блоков: повтор того же блока на ReplicatedMergeTree **дедуплицируется**, если строки те же и в том же порядке. Kafka rebalance это предположение может сломать — ещё один довод за Connect `exactlyOnce`, а не за «надеемся на дедуп блока».

##### Сильные / слабые стороны (insert_quorum=2 при 3 репликах)

| Сильное | Слабое |
|---|---|
| Подтверждённый INSERT пережил одну ноду/ЦОД (если копии в разных зонах) | Латентность ≥ записи на вторую площадку |
| Соответствует цели «система должна работать» при 1 отказе | При одновременном выкате реплик в двух ЦОДах quorum может не набраться — выкат **по одному ЦОДу** |
| `'auto'` не надо пересчитывать при смене числа реплик | SELECT без `select_sequential_consistency` может не сразу видеть свежий блок |

`insert_quorum=1` или 0 в проде на реплицируемых фактах = вы сознательно приняли RPO «последний батч мог исчезнуть с одной нодой».

#### Снапшоты / BACKUP

- `BACKUP TABLE` / `BACKUP DATABASE` в S3-совместимое хранилище. Проверять **RESTORE** на другой namespace/кластер, не только статус `BACKUP_CREATED`.
- Инкремент: `SETTINGS base_backup = S3(...)`. Каталог инкремента ≠ каталог базы.
- SQL-пользователи восстановятся; `users.xml` — нет. Значит прод-учётки должны быть SQL-driven.
- Секреты S3 — named collection / конфиг сервера, не логин/ключ в тексте запроса пользователя (ломается ещё и политикой 26.7).
- Бакет должен переживать тот же отказ, что и кластер, или жить вне всех трёх ЦОДов.

#### Поток из Kafka

| Путь | Семантика (документация ClickHouse) | Куда |
|---|---|---|
| **Kafka table engine + MV** | at-least-once; дубли при потере offset после успешного INSERT; дедуп блока помогает не всегда | Стенд; простой контур |
| **Kafka Connect Sink, `exactlyOnce=true`** | exactly-once через KeeperMap; официальный коннектор ClickHouse | Прод |
| Писать из приложения батчами | Зависит от вашего кода | Имеет смысл, если Connect нельзя |

Quorum для Kafka engine **не задаётся на MV** — только профилем пользователя (`insert_quorum` в profile). Для Connect — `clickhouseSettings: insert_quorum=2,...`. С async insert и exactly-once вендор требует дождаться персиста (`wait_for_async_insert`), иначе offset уедет раньше данных.

Connect — **отдельное** ПО (Java, своё HA). Не забыть: он тоже ходит в KeeperMap на вашем кворуме.

#### Безопасность прода

| Слой | Правило |
|---|---|
| `default` | Свой пароль или учётка удалена/ограничена localhost; нет `CLICKHOUSE_SKIP_USER_SETUP`; нет `<ip>::/0</ip>` без периметра |
| HTTP | В проде **8443**, 8123 закрыт или только localhost |
| Native | **9440**, `secure` в `remote_servers` |
| Interserver | **9010**, не 9009 plaintext между ЦОДами |
| Keeper | Клиент 9281, Raft `secure` |
| Пользователи | SQL-driven, роли на базы, квоты на «тяжёлый SELECT»; сервисы ≠ аналитики |
| `secret` кластера | В `remote_servers` для Distributed, иначе любой, кто достучался до 9000, может прикинуться шардом |
| Сеть | NetworkPolicy: клиенты → 8443/9440; 9009/9010 — только серверы; 9181/9234 — серверы и Keeper; 9363 не в интернет |
| Секреты | не в Git; K8s Secret / Vault; named collections |
| At-rest | шифрование томов/CSI; в OSS нет «галочки encrypt table» как замены диску |
| Лишние порты | MySQL/PostgreSQL/gRPC эмуляции выключить |
| 26.7 S3 | пользовательский SQL не должен рассчитывать на env-credentials сервера |

##### Сильные / слабые стороны (TLS + SQL ACL)

| Сильное | Слабое |
|---|---|
| В бандле, без отдельной лицензии | Три слоя TLS (клиент, interserver, Keeper) легко сломать при выкате |
| SQL ACL бэкапится вместе с данными | Ошибка GRANT = «почему sink не пишет»; нужен процесс выдачи |
| `networks` режет лишние IP даже при утечке пароля | Не ГОСТ |
| Оператор умеет прокидывать users/files | Туториалы с пустым `default` слишком удобные — их копируют |

#### Kubernetes-специфика прода

- Отдельные CHK и CHI. В 0.27.x CHI может ссылаться на CHK **по имени** (`zookeeper.keeper.name`) — не руками хардкодить список DNS, который разъедется при scale Keeper.
- Topology spread: Keeper max skew 1 по `topology.kubernetes.io/zone`; реплики шарда — в разные зоны.
- PDB: не дать Kubernetes снять сразу два Keeper или две реплики одного шарда.
- Ресурсы server: лимиты памяти с запасом под запрос (GROUP BY может spill на диск, если включить external aggregation — это **медленно**, не «бесплатная RAM»).
- Не ставить data на overlay с большим jitter без замера. Если pod-сеть между ЦОДами хуже VM — ноды иногда лучше на hostNetwork / вне K8s. Это решение **по замерам**.
- Rolling upgrade: по **одной** зоне. Две зоны сразу при quorum=2 могут остановить запись.
- PVC `Retain`. Shrink диска Kubernetes не умеет — размер с запасом, не «потом уменьшим».
- `emptyDir` для `/var/lib/clickhouse` в OSS-репликации = потеря реплики при переезде пода.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами на 9234/9009/9440. Решение A vs B.
2. Выделить ноды: Keeper (маленькие, быстрый диск), server (SSD, RAM по профилю). Зоны.
3. Поставить оператор **0.27.3**, описать CHK×3 + CHI 1×3, версия **26.7.5.10**, свои cert.
4. Включить TLS и SQL ACL **до** боевых таблиц.
5. Создать replicated-таблицы `ON CLUSTER`, проверить `system.replicas`.
6. Прогнать `BACKUP` + `RESTORE`.
7. Включить `insert_quorum=2` на профиле ingest-пользователя. Убить одну реплику, проверить чтение и запись.
8. Подключить первый реальный пайплайн (Connect из Kafka, с буфером).
9. Нагрузить хотя бы синтетикой: parts, merge, replication delay, RAM на GROUP BY. По результату — вертикаль, потом шарды.
10. Прогон «ЦОД недоступен» на препроде: выключить зону, проверить кворум Keeper (`mntr`), SELECT, INSERT с quorum, что бэкап-бакет ещё доступен.

Без пункта 10 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | 3 dedicated Keeper в 3 зонах; 3 реплики шарда в 3 зонах; ReplicatedMergeTree; `insert_quorum=2` (или auto); цель — 1 ЦОД; BACKUP с прогнанным RESTORE |
| Производительность / масштаб | Не требуется | Сначала вертикаль; шарды когда одна машина мала; батчи INSERT; SSD не NFS; TTL; клиенты не на Keeper; рост реплик пачками по зонам |
| Безопасность | Пароль `default` в изоляции; без `SKIP_USER_SETUP` | Нет пустого `default` в сеть; TLS 8443/9440/9010 + Keeper TLS; SQL ACL; 8123 не в интернет; секреты не в git; at-rest на томах |

**Не готов к проду**, если: один MergeTree без Keeper, `insert_quorum` выключен на фактах, которые нельзя терять, `internal_replication=false` на ReplicatedMergeTree, `CLICKHOUSE_SKIP_USER_SETUP`, plaintext 8123/9009 между ЦОДами, данные на NFS/`emptyDir`, все реплики в одной зоне, нет BACKUP, RTT между ЦОДами неизвестен, а схема уже stretch, ClickHouse назначен SoT клиентских карточек, Kafka engine без понимания at-least-once выдан за exactly-once.
