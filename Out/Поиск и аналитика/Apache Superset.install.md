# Apache Superset 6.1.0 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `Apache Superset.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

Apache Superset — платформа дашбордов поверх SQL. Ставите **свою** копию, не облако вендора. Само терабайты не хранит: цифры живут в складе, который вы подключите.

Версия в этой инструкции: **Apache Superset 6.1.0**. Образ: `apache/superset:6.1.0`. На Kubernetes официальная страница установки описывает **Helm** `https://apache.github.io/superset`, чарт **`superset/superset` 0.21.1** (`appVersion` 6.1.0).  
**Superset Operator 0.2.0** — альтернатива (PostgreSQL и Redis приносите сами), **не** дефолт страницы «Installing on Kubernetes».  
Документация: https://superset.apache.org/docs/installation/kubernetes

Нужны **PostgreSQL** (метаданные: дашборды, пользователи, зашифрованные пароли источников; в доке 10.x–17.x) и **Redis** (кэш, очередь задач, результаты длинного SQL Lab). Ключ приложения **обязан** быть своим: с 2.1.0 дефолт на не-debug запрещает старт; документация Helm ещё знает строку `thisISaSECRET_1234` — её тоже не оставлять. Рекомендация вендора: `openssl rand -base64 42`.

Один стек, размазанный на несколько дата-центров, здесь **не собираем**. Веб и worker — процессы без своего склада фактов, но Postgres и Redis синхронны; порога задержки у проекта нет. Поэтому живой стек — внутри одной площадки. Вторая площадка — люди ходят в UI первой **или** независимый стек (своя база, свой Redis, выгрузка дашбордов из git).

Официальной поддержки Windows нет (документация Compose). С 6.1.0 пакеты в Docker ставят через **`uv pip install`**, не старый bootstrap `pip` на каждом старте от root.

---

## О чём эта инструкция молча договорилась

1. **Один живой «мозг» в одном дата-центре.** Веб, worker, beat, Postgres метаданных и Redis **одного** стека живут **в одной площадке**. Между площадками — независимый стек **или** люди ходят в UI первой. Третья площадка — **не** второй писатель в ту же базу метаданных.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`, если есть). Сабчарты Bitnami Postgres/Redis чарта — **стенд**; в бою `postgresql.enabled: false`, `redis.enabled: false`.
3. Учебный стенд — закрытая сеть; `admin` / `admin` только там.
4. Цифр вашей нагрузки нет — нет фразы «хватит N реплик». Терабайты живут в **складе**, не в базе метаданных.
5. Склад или озеро как SQL-источник будет. Без витрины Superset — пустая рамка.
6. Два дата-центра: стек в первом; второй — доступ к UI первого **или** свой стек. Три дата-центра: то же.
7. Будильник расписаний (Celery beat) — **ровно 1**. Отчёты с PNG в первом бою не обязательны (иначе браузер без окна + SMTP).
8. Grafana — дашборды инфраструктуры, не замена этому UI.

---

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** открыть Explore, один SQL-источник, понять отличие от Grafana. **Не зачем:** доказывать отказ дата-центра и SQL Lab по боевому озеру.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- На localhost свободен порт 8088.
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

Compose вендор **не** поддерживает как устойчивость и бой; для «пощупать» — тег релиза. Пример доки иногда приводит `TAG=5.0.0` — брать **6.1.0**, сверять digest на Docker Hub.

Минимально (один контейнер; внешний Postgres на стенде предпочтительнее SQLite в томе):

```bash
docker run -d --name superset-dev \
  -p 127.0.0.1:8088:8088 \
  -e SUPERSET_SECRET_KEY="$(openssl rand -base64 42)" \
  apache/superset:6.1.0
```

Привязка к `127.0.0.1` обязательна. После старта внутри контейнера — миграция базы, `superset init`, создание admin (команды из getting started текущей 6.1.0). Не стартовать с `CHANGE_ME_TO_A_COMPLEX_RANDOM_SECRET`.

Вход: `http://127.0.0.1:8088`. Путь Compose (`docker-compose-image-tag.yml`, `TAG=6.1.0`) — том метаданных **не бэкапится** (дока). Удалили том — удалили дашборды.

На Kubernetes для учёбы: Helm 0.21.1, одна реплика, свой ключ в секрете, сабчарты Postgres+Redis **допустимы на тесте**. Этот values в бой не копируйте.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| База метаданных | SQLite или Postgres сабчарта | Нет цели пережить выкат |
| Redis | сабчарт или без (лёгкий compose) | Нет цели асинхрона |
| Реплики веба и worker | 1 | Нет цели устойчивости |
| Отчёты / beat | выкл | Не цель |
| Ключ приложения | свой, даже на тесте | Иначе не-debug не стартует / известный ключ Helm |
| SQL Lab | только синтетика | Боевое озеро не подключать |
| Роль при саморегистрации `Admin` | **не** копировать из примера OAuth | Привычка уедет в бой |

Чего **не** упрощаем: тег **6.1.0**; хотя бы один чарт не пустой; выгрузка дашборда в git; 8088 не с мира; не superuser озера.

### Как понять, что стенд живой

1. `/health` → `OK` (это **не** проверка Postgres и склада).
2. Explore живой. Рестарт без тома — дашборды пропали, если SQLite в контейнере. Так и должно быть на тесте.
3. Root из чарта не считать нормой боя.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты–час, официальный quickstart | Нет устойчивости Postgres и Redis |
| Дешёво показывает, каких витрин нет | Успех на ноутбуке ≠ 5 реплик не убьют лимит соединений озера |
| | `admin` / `admin` и root bootstrap уедут в бой |

Перед боем полезен **препрод**: внешний Postgres, Redis, 2 веб, ≥ 1 worker, свой секрет, источник только на чтение — всё **в одном** дата-центре.

## Бой: один живой дата-центр, второй — запас из бэкапа или отдельный стек

**Зачем:** пережить отказ **пода веба или worker внутри площадки**. Отказ дата-центра с Postgres метаданных = нет BI, пока не поднимете запас. Склад — отдельный проект отказоустойчивости. Терабайты цифр хранит озеро, **не** база метаданных Superset.

Официальная модель «N веб за балансировщиком + общая БД» не требует раскладывать Postgres синхронно на три города. Документация **не задаёт** «можно при 5 мс, нельзя при 40». Утверждение «три дата-центра в одном городе, значит Postgres синхронно на три» — непроверенное.

### Почему стек не растягиваем на несколько дата-центров

База метаданных и Redis — синхронные клиенты с веба и worker. Размазать Postgres на 2–3 дата-центра — история PostgreSQL, не фича Superset. Два beat = двойные письма. Результаты SQL Lab на диске пода = пользователь на вебе A не заберёт результат worker B.

Полезные факты из схемы «три площадки», которые **остаются внутри одной площадки**:

- Веб ≥ 2 (дефолт чарта **1** — это не бой). Worker ≥ 2 (дефолт чарта **1**). Beat = 1, и только если нужны письма с PNG; реплик beat **не** скейлить.
- Разнос по машинам: **не все веб на одной**. Beat — точка отказа расписаний: падение машины beat = не уходят отчёты, экран жив.
- Бюджет сбоя подов на веб: не убивать все сразу. В values чарта бюджет по умолчанию **выключен** — включить.
- Поочерёдное обновление; время на завершение пода больше таймаута Gunicorn (в values есть явная подсказка).
- **Не** SQLite. Состояние — в Postgres. Сабчарт Postgres в бою **выкл**; свой кластер. То же для Redis.
- TLS к базе метаданных: в чарте 0.21.1 поле есть, дефолт **false** — в бою включить, на стороне клиента `verify-full`, не только `require`, если доверяете своему удостоверяющему центру. TLS к Redis — аналогично, дефолт чарта **false**.
- Готовый образ **со своими драйверами**, не скрипт с `apt` / `uv pip` на каждом старте от root. Документация k8s: для боя «соберите свой образ в CI». README чарта предлагает `runAsUser`, например **1000**, если bootstrap больше не нужен. Дефолт чарта — **root (0)**, в бою так не рекомендуется.
- Пробы чарта бьют в `/health` (начальная задержка 15 с). Это не «Postgres ответил».
- `SUPERSET_ENV=production` — чтобы включился лимит попыток входа. Для нескольких подов задайте хранилище лимитов на Redis, иначе счётчики **по процессу**.
- История SQL Lab **не** чистится, пока не включите задачи очистки на beat (дока Configuring). Иначе база метаданных распухнет запросами, не дашбордами.
- `task_acks_late` в дефолтном конфиге проекта = **False**; пример асинхронной доки показывает `True`. Не копировать вслепую: это про повтор задач при убийстве worker, не про «магия быстрее».
- Проверка worker в чарте по умолчанию — `celery inspect ping` с начальной задержкой **120 с**.
- Breaking чарта 0.21.1: labels `app.kubernetes.io/*`. Обновление со старого релиза без удаления Deployment может упасть на неизменяемый selector — это в README.
- Вебсокеты чарта: community-образ `oneacrefund/superset-websocket:latest` — в контур с персональными данными **не** тащить `latest`. Функция глобальных асинхронных запросов в 6.1.0 помечена как testing. Для первого боя оставить **выкл**.
- Ingress в чарте по умолчанию выкл; не включать с `chart-example.local` и без TLS.
- Не ставить веб на те же ноды, что etcd/Kafka, без лимитов.

Если отчёты всё же нужны — отдельный образ с Chrome, внутренний URL для съёмки (`http://...:8088/`), внешний HTTPS для людей в письме. `--no-sandbox` в примере Helm нужен из‑за root; если ушли с root — пересмотреть аргументы. Иначе **не включать** отчёты. Вебхуки отчётов: только HTTPS (уже дефолт). SMTP внутрь, не личный Gmail из примера Helm.

### Как расставить в активном дата-центре

Один стек:

- Веб ≥ 2, worker ≥ 2, beat = 1 (beat только если отчёты нужны).
- Postgres база `superset` с переключением **в этой площадке** (не та же, что Grafana / Camunda / озеро); TLS `verify-full`.
- Redis с переключением **в этой площадке**; логические базы как в чарте (0 — очередь задач, 1 — кэш).
- Ключ приложения свой **до** подключения источников. Смена потом: предыдущий ключ + команда перешифровки секретов.
- Образ **6.1.0 с драйвером склада**, собранный в CI, не root.
- Сабчарты Postgres и Redis выкл.
- HTTPS-балансировщик на 8088, проверка `/health`; «липкость» для дефолтных cookie **не** обязательна. Если включите сессии на сервере в Redis — тоже общий Redis, не липкость.
- Доверять заголовкам прокси, cookie только по HTTPS, `SUPERSET_ENV=production`.
- Канонический публичный URL для адреса возврата OAuth (`https://<host>/oauth-authorized/<provider>`).
- Чарт **0.21.1**, digest образа зафиксирован.
- Сетевая политика: 8088 только от балансировщика; 5432 и 6379 только от веба / worker / beat / init; склад — только от веба и worker, **не** от Ingress.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: весь стек. Вторая: люди ходят в UI первой **или** независимый стек (своя БД, свой Redis, выгрузка из git) | Нет этого BI, пока запас или второй стек. Склад может быть жив — панели пустые. Время простоя замерить |
| **Три** | То же. Три полных Superset — тройные права, обычно хуже | То же |

Не копировать полный Superset «в каждый дата-центр как второй Grafana»: получите три правды дашбордов. Не открывать SQL Lab на главной копии эталона. Читать **реплику** озера.

### Что должно быть до боевой установки

- Postgres и Redis с переключением в активной площадке.
- Vault: ключ приложения, пароль БД, Redis, единый вход, пароли складов.
- Сетевая политика как выше.
- Драйвер склада в образе.
- Init Job: миграция + init один раз; создание admin затем выключить. `superset db upgrade` только через Job / пайплайн, не руками с трёх подов сразу.

### Порядок установки в активном дата-центре

```bash
helm repo add superset https://apache.github.io/superset
helm upgrade --install superset superset/superset --version 0.21.1 \
  --namespace bi --create-namespace \
  -f superset-prod-values.yaml
```

Смысл values:

```yaml
image:
  repository: apache/superset   # не scarf.sh в закрытом контуре
  tag: "6.1.0"
extraSecretEnv:
  SUPERSET_SECRET_KEY: "<свой>"
supersetNode:
  replicas:
    replicaCount: 2
supersetWorker:
  replicas:
    replicaCount: 2
supersetCeleryBeat:
  enabled: false          # true только с браузером без окна, SMTP и beat=1
postgresql:
  enabled: false
redis:
  enabled: false
```

В 0.21.1 старый путь `supersetNode.connections.*` ещё может читаться как совместимость — не держать два источника правды с `database.*` / `cache.*`. `secretEnv.create: false` + Vault / External Secrets — нормальный боевой путь.

Flower (5555) не включать без нужды.

Если в политике есть Operator 0.2.0 вместо Helm — те же правила: свои Postgres и Redis, секреты через `*From`, не сабчарты стенда.

### Правила конфигурации боя

| Слой | Правило |
|---|---|
| Ключ приложения | Свой до источников; не константа 6.1.0 и не `thisISaSECRET_1234` |
| Admin | Нет `admin` / `admin`. Запасная учётка в Vault. Единый вход + синхронизация ролей при каждом входе (иначе роли «залипнут» с первого входа). Саморегистрация **не** в Admin. Типично Gamma или своя роль без SQL Lab |
| API-ключи Flask-AppBuilder | По умолчанию выкл — включать только под CI с ограниченными правами |
| Кэш чартов | Redis, не «кэша нет» при «высокой нагрузке» |
| Результаты SQL Lab | Общий Redis, не файлы пода |
| Заголовки безопасности | Оставить включёнными. Iframe / встраивание — отдельное решение, не включать без гостевого секрета |
| Небезопасные URI баз | Не выключать запрет |
| Импорт наборов данных | Сузить список URL (дефолт «откуда угодно» — запрос с пода куда угодно) |
| Scarf | Образ `apache/superset`, аналитика выкл |
| Public / аноним | Не включать на персональных данных |
| Шаблоны в SQL | Не включать без письменной модели угроз |
| SQL Lab | Узкая роль; учётка БД только SELECT на витрины. Фильтры приложения **плюс** права на складе |
| Выгрузка CSV | Не всем Gamma |
| Режим «зритель обходит проверки набора данных» | Не включать |
| Список запрещённых SQL-функций | Не вычищать «чтобы version() работал» |
| Сеть | UI только из внутренней сети / через прокси единого входа. Не LoadBalancer в интернет |

Плюс: не ГОСТ — если информационная безопасность потребует отдельную криптографию, обычный Superset это не закроет. Ревью, что Gamma интеграционного пространства имён не видит содержимое гособмена. Admin — штучные учётки; вендор не считает XSS при правах Admin уязвимостью.

### Как расти, когда появятся цифры нагрузки

1. Люди → реплики веба + Gunicorn (пример доки «10 воркеров gevent» — **пример**; BigQuery SDK с gevent несовместим).
2. Тяжёлый SQL → worker + склад, не «ещё под».
3. Считать соединения: (веб + worker) × процессы × пул к метаданным **и** к озеру.
4. Не автообновление дашборда каждые 10 с на тяжёлые агрегации. Агрегации — во витринах склада. Потолки UI: 50 000 строк у чарта, 100 000 у SQL Lab.

### Проверки, без которых это ещё не бой

1. Версия 6.1.0, `/health`, логин через единый вход. Ключ приложения не из констант 6.1.0 и не `thisISaSECRET_1234`.
2. Убить веб-под: экран жив. Убить worker: синхронный чарт жив, асинхрон нет.
3. Недоступен склад: экран жив, панели пустые — ожидаемо.
4. Восстановили Postgres метаданных на стенде. Выгрузка дашбордов в git существует. Бэкап БД = дашборды, пользователи, фильтры, **зашифрованные** пароли источников. Живой git ещё переживаем; потеря без git — нет.
5. Учение «активный дата-центр выключен»: простой или второй независимый стек. Двух beat нет.

`helm install` из краткой шпаргалки с одной репликой, Postgres из сабчарта, root и без своего ключа выглядит как BI, ведёт себя как один диск плюс известный ключ.

### Что хорошо и что плохо в схеме «стек в одном дата-центре»

| Хорошо | Плохо |
|---|---|
| Postgres и Redis не ходят между городами | Падение этой площадки = нет этого BI, пока не поднимете запас |
| Apache 2.0, без своего ключа не-debug не стартует | Admin = ключ ко всем паролям источников и к SQL |
| Один набор фильтров и прав | `/health` слеп к БД и складу |
| | SQL Lab обходит «красивые» чарты |
| | Ошибка в роли или наборе данных сразу у всех |

**Не готово к бою**, если: одна реплика + SQLite или Postgres из сабчарта; ключ из констант или `thisISaSECRET_1234`; `admin` / `admin`; `latest`; root + apt в bootstrap; Public на персональных данных; кэша нет и «готовы к нагрузке»; SQL Lab под superuser озера; два beat; Postgres растянули на 2–3 дата-центра; ждут, что Superset хранит терабайты или заменяет Grafana; дашборды только в UI без git и без бэкапа Postgres; учение отказа пода / БД / склада не делали.
