# ClickHouse 26.7.5.10 — установка и конфигурирование

Связанный документ (зачем система, из каких программ состоит, порты, железо): `ClickHouse.md`.

Этот файл — **как поставить и настроить**. Настройки с учебной машины в бой не копируйте.

## Что вы ставите

ClickHouse — колоночная база для отчётов и агрегатов по большим таблицам. Ставите **свою** копию, не облако вендора.

Версия в этой инструкции: **26.7.5.10-stable**. Образы:

- `clickhouse/clickhouse-server:26.7.5.10` — считает SQL и хранит таблицы;
- `clickhouse/clickhouse-keeper:26.7.5.10` — отдельная программа, которая помнит, какие копии таблиц живы, и проводит создание таблиц сразу на всех узлах.

На Kubernetes — оператор Altinity **0.27.3** (готовые объекты «кластер серверов» и «кластер Keeper»). Документация: https://clickhouse.com/docs/

Если политика обновлений запрещает частые крупные релизы — **весь** кластер ставят на линейку с длительной поддержкой **26.3.21.7-lts**. Серверы на 26.7, а Keeper на 26.3 (или наоборот) **нельзя**.

Один кластер, размазанный на несколько дата-центров, здесь **не собираем**. Голосование Keeper и копирование файлов таблиц между машинами чувствительны к задержке сети; в документации нет цифры «сколько миллисекунд ещё можно». Поэтому живой кластер — внутри одной площадки. Вторая площадка — снимок и восстановление, не вторая половина того же кластера.

---

## О чём эта инструкция молча договорилась

1. Тройка Keeper и копии таблиц **одного** кластера живут в **одном** дата-центре. Между площадками — отдельный кластер **или** восстановление из снимка. Не открывайте между дата-центрами порты копирования кусков (9009) и голосования Keeper (9234), если не строите осознанно другой контур.
2. Бой — Kubernetes в каждом дата-центре отдельно (см. `Kubernetes.install.md`).
3. Учебный стенд — закрытая сеть. Keeper на одной машине с сервером допустим **только там**.
4. Цифр вашей нагрузки нет — нет фразы «хватит N шардов». Сначала увеличивают CPU/RAM/диск одной копии; новые шарды — когда одна машина уже мала.
5. Бакет для снимков в бою **есть или будет**. Копии таблиц бэкап не заменяют: команду «удали таблицу» они послушно повторят.
6. Два дата-центра: кластер в первом; второй — восстановление из снимка **или** свой отдельный кластер (единого `SELECT` по обоим без прикладного слоя не будет). Три дата-центра: то же. Третья площадка — **не** третий Keeper чужого голосования.
7. Поток из Kafka в бою — отдельная программа ClickHouse Kafka Connect в режиме «записать ровно один раз». Встроенный Kafka-движок на сервере на стенде допустим; он может записать одно и то же дважды.

## Учебный стенд: одна площадка, без нагрузки

**Зачем:** писать SQL, подобрать ключ сортировки таблицы, посмотреть, как сжимаются ваши события. **Не зачем:** доказывать отказ дата-центра.

### Что должно быть до установки

- Docker **или** однонодовый Kubernetes.
- На localhost свободны порты 8123 (HTTP) и 9000 (свой протокол клиента).
- Сеть стенда не торчит в интернет.

### Установка (Docker — основной путь для учёбы)

```bash
docker run -d --name ch-dev \
  --ulimit nofile=262144:262144 \
  -p 127.0.0.1:8123:8123 \
  -p 127.0.0.1:9000:9000 \
  -e CLICKHOUSE_PASSWORD=dev \
  -e CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT=1 \
  clickhouse/clickhouse-server:26.7.5.10
```

Привязка к `127.0.0.1` обязательна: порт слушает только эта машина.

Без пароля в Docker встроенный пользователь `default` **не принимает сетевые подключения**. Это не «сломанный образ», так задумано. Режим «пропустить настройку пользователя» на стенд **не** включайте: привычка уедет в бой.

Проверка — в ответе должна быть версия **26.7.5.10**:

```bash
curl -s "http://127.0.0.1:8123/?user=default&password=dev" --data-binary "SELECT version()"
```

Потом заведите **отдельного** пользователя для приложения, не ходите в базу как `default`:

```sql
CREATE USER app IDENTIFIED BY 'dev-app';
CREATE DATABASE analytics;
GRANT SELECT, INSERT ON analytics.* TO app;
```

На Kubernetes для учёбы: один объект серверов с одной копией, маленький диск, без отдельного Keeper. Этот YAML в бой не копируйте.

### Какие настройки на тесте упрощаем

| Параметр | На тесте | Зачем так |
|---|---|---|
| Число серверов | 1 | Не учимся переживать обновление |
| Keeper | не ставим, обычная таблица без копий | Иначе голосование раньше, чем SQL |
| TLS | нет, сеть закрыта | Иначе сертификаты раньше запросов |
| Встроенный Kafka-движок | можно | На стенде проще, чем поднимать Connect |
| Снимок в S3 | можно отложить на день | На препроде бакет уже обязателен |
| Доступ «с любого IP» в файле пользователей | запрещён | Даже на тесте за файрволом стенда |

Чего **не** упрощаем: номер версии **26.7.5.10** (или сразу вся линейка с длительной поддержкой, если бой будет на ней); явный ключ сортировки под ваши фильтры; вставки **пакетами**, не строка из цикла; понимание — таблица без Keeper **не копируется** на другую машину.

### Как понять, что стенд живой

1. `SELECT version()` возвращает 26.7.5.10.
2. Приложение ходит пользователем `app`, не `default` без пароля в сеть.
3. Контейнер перезапустили с томом — данные на диске на месте.

### Что хорошо и что плохо в такой схеме

| Хорошо | Плохо |
|---|---|
| Минуты, официальный Docker-гайд | Нет Keeper, нет копирования между машинами, нет правила «подожди две копии» |
| Одна нода официально нормальна для разработки | Успешный SELECT **не** доказывает боевую схему |
| | HTTP без шифрования приучает «зайти как получится» |

Перед боем полезен **препрод**: 3 Keeper + 1 шард из 3 копий, TLS, подтверждение записи двумя копиями, снимок — всё **в одном** дата-центре.

## Бой: один живой дата-центр, второй — запас из снимка

**Зачем:** пережить отказ **одной машины или пода внутри площадки** (три Keeper, три копии шарда, запись подтверждается двумя копиями). Отказ **всего дата-центра** = этого кластера нет, пока не восстановите снимок на другой площадке или не переключите клиентов на второй независимый кластер. При архивном восстановлении часть свежих данных можно потерять — это нужно замерить.

### Почему кластер не растягиваем на несколько дата-центров

Keeper выбирает лидера голосованием. Если задержка сети между площадками сопоставима с пульсом (заводские **500 мс**), начнутся ложные выборы, и реплицируемые таблицы уйдут в **только чтение**. Копирование кусков таблицы по порту 9009 не быстрее сети. Документация **не задаёт** порог. «Keeper в трёх дата-центрах» при потере двух площадок всё равно снимает большинство голосов.

### Как расставить в активном дата-центре

Один кластер:

- Три **отдельных** Keeper, свои диски, не на тех же томах, что тяжёлое слияние кусков данных.
- Старт: **один шард, три копии** на разных нодах **этой** площадки. Это минимум размещения, не «хватит терабайтов».
- Боевые факты — только **реплицируемый MergeTree**, создание через `ON CLUSTER` (команда уходит на все узлы, не только на тот, куда вы подключились).
- В списке шардов включить «копии сам догоняет сосед»: Distributed пишет в **одну** живую копию, дальше копирует движок таблицы. Иначе Distributed сам пишет во все копии и плодит расхождения.
- Пользователь, который пишет данные: подтверждение INSERT с **двух** копий из трёх (или режим «большинство»). Если потребовать все три — запись встанет при падении одной машины.
- Клиенты ходят на 8443 (HTTP с TLS) или 9440 (свой протокол с TLS), **не** на порты Keeper.
- Один и тот же номер версии **26.7.5.10** на серверах **и** на Keeper.
- Диск: локальный SSD / NVMe, **не сетевая папка**, не пустой том Kubernetes как каталог данных.

**Между площадками:**

| Сколько площадок | Что где | Если умер активный дата-центр |
|---|---|---|
| **Две** | Первая: кластер. Вторая: **нет** прямого копирования кусков и голосования Keeper к первой. Клиенты либо ходят SQL в первую, либо у них свой кластер. Запас: восстановление из бакета | Нет аналитики этого кластера, пока не восстановите снимок или не переключите на второй кластер. Время простоя замерить |
| **Три** | Третья как вторая | То же. Три независимых кластера ≠ один запрос «по всей стране» без кода над ними |

Не кладите «все Keeper в первой площадке, а копии данных в трёх»: падение первой оставит диски, но **без** координации (только чтение). Это не переживание площадки, а «файлы ещё лежат».

### Что должно быть до боевой установки

- Kubernetes активной площадки; диски с предсказуемой скоростью, один том на один под.
- Бакет снимков, который **переживает** гибель этой площадки (иначе бэкап умер вместе с кластером).
- Сетевая политика: клиенты → 8443/9440; копирование кусков — только сервер↔сервер; Keeper — только серверы и Keeper.
- Пользователи заводятся командами SQL (учётки из XML-файла в снимок кластера **не входят**).
- Оператор 0.27.3 уже прогнан с образом **26.7.5.10** на стенде.

### Порядок установки в активном дата-центре

1. Поставить оператор Altinity **0.27.3** (манифест или Helm **конкретного тега**, не `latest`).
2. Три Keeper, образ `clickhouse-keeper:26.7.5.10`.
3. Кластер серверов: ссылка на Keeper **по имени объекта**, не руками зашитый список DNS (при добавлении Keeper список разъедется). Версия **26.7.5.10**. Копии разнести по разным нодам **этой** площадки.
4. Включить TLS **до** боевых таблиц: клиенты 8443/9440, копирование кусков 9010, Keeper 9281 и шифрование голосования.
5. Создать таблицы реплицируемого MergeTree с `ON CLUSTER`. Проверить системную таблицу копий: все живы.
6. Прогнать снимок и **восстановление** в другой namespace. Ключи S3 — в наборе на сервере, не в тексте SQL пользователя (в 26.7 пользовательский SQL по умолчанию облачные ключи процесса больше не подхватывает).

### Правила конфигурации боя

| Параметр | В бою | Зачем |
|---|---|---|
| Пользователь `default` | Свой пароль или только localhost; не пропускать настройку пользователя | Учебник без пароля сам просит так не делать |
| Сколько копий подтверждают INSERT | 2 при трёх копиях | Завод — подтверждение **одной**; блок может пропасть вместе с этой машиной |
| Distributed пишет во все копии сам | выкл: пусть копии догоняют друг друга | Иначе расхождения |
| Эмуляции MySQL / PostgreSQL / gRPC | выкл, если не используете | Лишние открытые порты |
| TTL и ключ сортировки | с первого дня | Ключ сортировки потом меняется только новой таблицей |
| Секрет кластера в списке шардов | задать | Иначе любой, кто достучался до native-порта, может прикинуться шардом |

Политика сбоя подов: не давать Kubernetes снять сразу два Keeper или две копии одного шарда. Обновление **по одной** ноде: две сразу при пороге «две копии» могут остановить запись.

### Как расти, когда появятся цифры нагрузки

1. Сначала больше CPU / RAM / диск на существующие копии. Поставщик: не плодить шарды рано.
2. Новые шарды — когда одна машина мала. Перекладка уже лежащих данных — отдельный проект.
3. Писать пакетами. С 26.3 сервер сам склеивает мелкие INSERT, но миллионы одиночных строк всё равно душат диск и Keeper.
4. Отношение RAM к диску 1:30 … 1:130 из гайда поставщика — ориентир, не смета вашего боя.

### Проверки, без которых это ещё не бой

1. `SELECT version()` = 26.7.5.10 на **всех** серверах и Keeper активной площадки. Нет смеси 26.3 и 26.7.
2. У Keeper видно большинство. Выключили одну копию данных: чтение живо, запись с порогом «две копии» проходит.
3. Восстановили снимок в чистый кластер на стенде.
4. Учение «активный дата-центр выключен»: восстановление во второй по заранее засечённому времени **или** клиенты на второй кластер. Порты копирования и голосования между площадками закрыты — и это **ожидаемо**.

### Что хорошо и что плохо в схеме «кластер в одном дата-центре + снимок»

| Хорошо | Плохо |
|---|---|
| Голосование Keeper и копирование кусков — локальная сеть | Падение этой площадки = нет аналитики, пока не восстановите снимок |
| Не зависит от неизвестной задержки между городами | При восстановлении можно потерять хвост данных; второй кластер — второй набор таблиц |
| Один SQL-кластер для разработчиков | Если приложения во втором дата-центре — их SQL идёт через город |
| | Выгрузка из Kafka «ровно один раз» — отдельная отказоустойчивость, не этот файл |

**Не готово к бою**, если: одна таблица без Keeper; подтверждение INSERT выключено на фактах, которые нельзя терять; Distributed сам пишет во все копии; пропущена настройка пользователя; открытый HTTP и копирование кусков «на три дата-центра»; данные на NFS или в пустом томе Kubernetes; смешаны 26.7 и 26.3; ClickHouse назначен эталоном карточек клиентов; учебный манифест уехал в бой.
