# OpenSearch 3.8.0 — развёртывание и настройка

Версия ПО: **OpenSearch 3.8.0** (релизная дата 4 августа 2026; на дату подготовки документа это последний стабильный релиз линии 3.x).  
Документация: https://docs.opensearch.org/latest/  
Образы: `opensearchproject/opensearch:3.8.0`, `opensearchproject/opensearch-dashboards:3.8.0`.  
На Kubernetes официальные пути: **OpenSearch Kubernetes Operator** (Helm-репозиторий `https://opensearch-project.github.io/opensearch-k8s-operator/`) и отдельно **Helm charts** проекта (`opensearch` / `opensearch-dashboards`, appVersion 3.8.0). Ниже для прода в Kubernetes целевой путь — оператор: он закрывает rolling upgrade, TLS, расширение томов. Helm-чарты — запасной, более «ручной» путь.

Этот текст — не мануал «скопируй и запусти», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

OpenSearch **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить поисково-аналитический кластер на ту же инфраструктуру с Kubernetes и тремя ЦОДами. Это **не** замена озера эталонных данных, **не** шина событий и **не** тот же кластер, что Wazuh indexer.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Кластер** | Несколько процессов OpenSearch, которые считают себя одной системой: общее имя, общее состояние, общие индексы. |
| **Нода (node)** | Один процесс OpenSearch. Роли можно разделять (см. ниже) или совмещать. |
| **Cluster manager** | Нода, которая ведёт *состояние кластера*: кто жив, какие индексы есть, где лежат шарды. Раньше это называли master. Выбирается голосованием. |
| **Cluster-manager-eligible** | Нода, которая *может* стать cluster manager. Не все eligible обязаны быть dedicated. |
| **Кворум** | Большинство eligible-нод. Для 3 cluster manager большинство = 2. Если живых меньше — кластер **не выбирает** manager: создание индексов, аллокация шардов, стабильная запись под вопросом. |
| **Data-нода** | Хранит шарды на диске, индексирует и ищет. Это «рабочие руки» и основной диск/RAM. |
| **Ingest-нода** | Гоняет документ через pipeline *до* записи в индекс (разбор JSON, grok, enrich). Можно совмещать с data. |
| **Coordinating-нода** | Принимает запрос клиента, раздаёт его по шардам, склеивает ответ. У каждой ноды эта роль есть по умолчанию; *dedicated* — когда `node.roles: []`. |
| **Индекс** | Именованный набор документов (похоже на «таблицу», но схема гибче и это не СУБД). |
| **Документ** | Одна JSON-запись в индексе. |
| **Шард (shard)** | Кусок индекса. Параллелизм хранения и поиска = шарды. |
| **Primary shard** | «Главный» кусок. Число primary задаётся **при создании** индекса; потом только re-index в новый индекс. |
| **Replica shard** | Копия primary на другой ноде. Нужна, чтобы падение ноды не дырявило индекс. Число replica можно менять позже. |
| **Green / yellow / red** | Здоровье кластера. Green — все primary и replica на месте. Yellow — все primary есть, части replica нет (поиск ещё идёт). Red — не хватает primary: часть данных недоступна. |
| **Zone / shard allocation awareness** | «Осведомлённость о зоне/ЦОДе». OpenSearch старается не класть primary и replica одного шарда в одну зону. |
| **Forced awareness** | Жёсткий вариант: replica **никогда** не поселяется в ту же зону, что primary. Если зона умерла, кластер остаётся yellow и **не** перекладывает копии в оставшиеся зоны (чтобы не убить их диском). |
| **Discovery / seed hosts** | Список адресов, куда нода стучится при старте, чтобы найти cluster manager. Без него мультинодовый кластер не соберётся. |
| **cluster.initial_cluster_manager_nodes** | Список имён нод для **первого** bootstrap кластера. Нужен один раз, одинаковый на всех eligible. Ошибка здесь = два кластера с разными UUID («split» при старте). |
| **Transport** | Внутренний протокол нода↔нода. Порт **9300**. TLS на этом слое для Security plugin **обязателен**. |
| **REST / HTTP** | API для клиентов. Порт **9200**. TLS на этом слое в настройках plugin **по умолчанию выключен** (`plugins.security.ssl.http.enabled`, default `false`) — в проде его включают явно. |
| **Security plugin** | Встроенный модуль: TLS, пользователи, роли, аудит. В дистрибутиве OpenSearch он есть. |
| **Demo certificates** | Комплект самоподписанных сертификатов «чтобы завелось». Документация прямо: для прода **небезопасны**, потому что общеизвестны. |
| **OPENSEARCH_INITIAL_ADMIN_PASSWORD** | С версии **2.12** при установке demo-конфига нужен свой пароль `admin`. Слабый пароль → процесс **не стартует**. |
| **securityadmin.sh** | Утилита, которой заливают/снимают конфиг Security plugin (роли, внутренние пользователи). Ходит на **HTTPS 9200**, нужен admin-сертификат из `plugins.security.authcz.admin_dn`. |
| **ISM** | Index State Management: через N дней сжать / перенести / удалить индекс. Без этого диск съедят «терабайты» сами. |
| **Snapshot / repository** | Бэкап индексов во внешнее хранилище (S3-совместимое, shared FS, HDFS…). Реплики шардов **не** заменяют snapshot: они не спасают от «удалили индекс» и от гибели всех копий. |
| **CCR (cross-cluster replication)** | Плагин: follower-кластер **тянет** индекс с leader. Follower **read-only**. Это уже два кластера, не один stretch. |
| **OpenSearch Dashboards** | Веб-UI (поиск, визуализации, часть админки Security). Порт **5601**. Stateless относительно данных кластера. |
| **Data Prepper** | Отдельная программа проекта OpenSearch: принимает логи/трейсы, ковертирует, пишет в кластер. **Не** плагин и **не** входит в пакет «поставил OpenSearch». |
| **Performance Analyzer** | Плагин метрик ноды, порт **9600**. Это не Prometheus из коробки. |
| **JVM heap (`-Xms` / `-Xmx`)** | Куча Java-процесса. Официально: примерно **половина RAM** машины/пода, `Xms = Xmx`. Остальная RAM — кэш файлов ОС (Lucene читает сегменты с диска через mmap). |
| **vm.max_map_count** | Лимит ядра Linux на число mmap. Официально **≥ 262144**, иначе нода падает. Даже в Docker значение ставится **на хосте**. |
| **PVC / RWO** | Постоянный диск пода Kubernetes, который можно отдать только одному поду. Data-нода без него теряет индекс при рестарте. |
| **emptyDir** | Диск «пока жив под». Для data-нод в проде это потеря данных. |
| **Stretch-кластер** | Один логический кластер, ноды физически в нескольких ЦОДах. Общаются по **9300**. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. |

## Основные элементы системы и зависимости

### Что входит в OpenSearch 3.8.0 (это одно ПО из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **Cluster manager** | Состояние кластера, выборы, аллокация | Вертикаль RAM/CPU; для HA — **нечётное** число dedicated, типично **3** в разных зонах. Добавлять «ещё manager от нагрузки поиска» бессмысленно |
| **Data** | Хранение, индекс, поиск | Горизонтально: ноды + шарды. Диск и heap растут вместе с данными |
| **Ingest** | Препроцесс документов | Отдельный пул, если pipeline тяжёлый |
| **Coordinating** | Вход клиентов | Пара dedicated при тяжёлом поиске; иначе хватает data-нод |
| **Dashboards** | UI | Несколько реплик Deployment на тот же кластер |
| **Плагины** | Security (в бандле), ISM, snapshot-репозитории, CCR, PA, … | Ставятся на **все** ноды кластера одинаковым набором |

Плюс *рядом*, но это уже другое ПО: **Data Prepper**, Fluent Bit / Vector / Kafka Connect, экспорт в Prometheus. Их HA проектируется отдельно.

### Официальные порты (менять можно, но это контракт сети)

| Порт | Назначение |
|---|---|
| **9200/TCP** | REST API (приложения, Dashboards, `securityadmin.sh`, снапшоты) |
| **9300/TCP** | Transport: нода↔нода и cross-cluster (CCR / cross-cluster search) |
| **5601/TCP** | OpenSearch Dashboards |
| **9600/TCP** | Performance Analyzer |

UDP нет. Порт **443** в таблице вендора относится к *Amazon OpenSearch Service*, не к self-hosted.

Клиентов официально направляют в порядке: ingest → coordinating → data. **На cluster manager внешний трафик не посылают.**

### Чего в OpenSearch нет (частая путаница)

| Нужно системе | Это не OpenSearch | Зачем помнить |
|---|---|---|
| Источник истины клиентских данных / «озеро эталона» | СУБД, объектное хранилище, warehouse | OpenSearch — поисковый движок: near-real-time, документная модель, нет нормальных ACID-транзакций «как в PostgreSQL». Копия для поиска ≠ SoT |
| Шина событий / гарантии Kafka (`acks=all`, consumer group) | Apache Kafka | Индексация в OpenSearch — **другой** контур. Потерял документ на ingest — Kafka об этом не узнает, если нет своего outbox |
| Camunda / оркестрация процессов | Process engine | OpenSearch может хранить *аудит* процессов, не исполнять BPMN |
| Интеграции с госслужбами | Ваше интеграционное API | Сюда можно складывать нормализованные ответы *для поиска*, не ходить в ведомства |
| SIEM «из коробки» | Wazuh (у вас отдельный документ) | Wazuh indexer **уже** OpenSearch-совместимый кластер. Склеивать его с бизнес-поиском — смешать алерты ИБ и клиентский поиск в одном RBAC |
| ГОСТ TLS / СКЗИ | Не заявлено | Штатный TLS JDK — не криптография по требованиям КИИ, если ИБ их выдвинет |
| Официальный порог RTT между ЦОДами | Нет | Awareness «умеет» зоны; миллисекунд в доке **нет** |
| Гарантия «терабайты влезут» | Нет | Диск = объём × сжатие × (1 + replica) × запас под merge/snapshot. Нагрузки у вас нет |
| Замена бэкапа репликами | Нет | Replica спасает от падения **ноды**. Не спасает от `DELETE index`, кривого mapping, шифровальщика |

### Зависимости окружения (обязательны)

- **Java.** Дистрибутив Linux кладёт Adoptium JDK в каталог `jdk`. Для линии 3.6.1+ таблица вендора: совместимы **21, 25, 26**; в бандле на момент этой таблицы — **25.0.4+7**. Свой JDK — через `OPENSEARCH_JAVA_HOME` / `JAVA_HOME`. Документация установки приводит путь вида `.../opensearch-3.8.0/jdk`.
- **ОС.** Linux x86_64 / ARM64 как основной контур. Windows-сборка есть, но прод на Windows-host для data-нод в вашей схеме с Kubernetes не предполагается.
- **Диск ноды.** Официально: **не сетевая ФС** как хранилище ноды в проде (латентность и I/O). Предпочтительно **SSD на хосте**. Snapshot-репозиторий — другое: он как раз внешний.
- **Ядро Linux:** `vm.max_map_count ≥ 262144`; swap лучше выключить; `bootstrap.memory_lock=true` + `memlock` unlimited; `nofile ≥ 65536`.
- **Сеть:** стабильный IP/DNS до каждой ноды на **9300**; клиентам — до coordinating/ingest на **9200**. Балансировщик HTTP перед 9200 допустим (это не Kafka). Балансировщик «как один VIP на 9300 всех нод» ломает модель transport.
- **Kubernetes (у вас заявлен):** CSI с **RWO** PVC на каждую data/manager-ноду; StorageClass с предсказуемым IOPS. Оператор по умолчанию ставит `vm.max_map_count` init-контейнером. Для data **не** `emptyDir` (у оператора при `emptyDir` для upgrade прямо требуют `general.drainDataNodes: true`, иначе потеря данных).
- **PKI** для прода. Demo-сертификаты Security plugin — только стенд.
- **Репозиторий снапшотов**, доступный всем нодам (S3-совместимое / MinIO / иной поддержанный тип). Без него «пережили ЦОД» = «если повезло с дисками».

### Как OpenSearch стыкуется с вашей архитектурой

```
Микросервисы, Camunda, интеграционное API
        │  (опционально: логи / поисковая проекция эталона)
        ▼
   Kafka  ──►  Data Prepper / Connect / Fluent Bit   ← это не OpenSearch
        │
        ▼
   OpenSearch cluster (поиск, аналитика, observability)
        ▲
        │  UI
   OpenSearch Dashboards

Озеро эталонных данных  ──остаётся SoT──►  (в OpenSearch можно *скопировать* то, что надо искать)
Wazuh indexer           ──отдельный кластер──►  не этот
```

Типичные честные роли в *вашей* картине:

1. **Observability** — логи и (если решите) трейсы сервисов, Camunda, интеграционного API.
2. **Поисковая проекция** справочников/клиентов — чтобы UI искал «по ИНН / ФИО / адресу» быстро. Запись истины всё равно в озеро/БД; сюда — поток изменений из Kafka.
3. **Аудит** вызовов интеграционного API (что запросили, что отдали после нормализации) — если это не уйдёт в отдельный SIEM.

Нечестная роль: «положим клиентов только в OpenSearch, озеро потом». При yellow/red, смене mapping и ошибке ingest вы получите дырявый SoT.

## Краткие вводные

### Зачем вам OpenSearch в этой архитектуре

Kafka доставляет факт. Озеро хранит истину. Camunda ведёт процесс. Интеграционное API ходит наружу. Остаётся вопрос: **как люди и сервисы это находят и разбирают**, когда данных терабайты и 30+ внешних систем.

OpenSearch закрывает полнотекст, фильтры, агрегации, дашборды по логам. Он горизонтально растёт шардами. Он **не** делает ваши микросервисы event-sourced — он может быть одним из консьюмеров шины.

### Как устроена отказоустойчивость (идея, не магия)

Это **кворум метаданных** плюс **копии шардов**. Путать «три ноды в docker-compose» с HA — главная ошибка.

**1) Cluster manager**

| Что падает | Что происходит по ролям из документации |
|---|---|
| Один dedicated manager из 3 | Остаётся 2, кворум есть, выбирается другой. Два «простаивают», пока все живы — так и задумано |
| Два manager из 3 (два ЦОДа с по одной eligible) | Кворума нет. Кластер не выбирает manager. Это **не** «переживём два ЦОДа на трёх нодах» |
| Все eligible совмещены с data и стоят в одном ЦОДе | Падение площадки = падение и кворума, и данных |

Официальная формулировка: *Three dedicated cluster manager nodes in three different zones is the right approach for almost all production use cases. This configuration ensures your cluster never loses quorum.* «Never» здесь значит «при потере **одной** зоны из трёх», не «при потере двух».

**2) Данные (data-ноды + replica)**

| Что падает | Что происходит |
|---|---|
| Одна data-нода при `number_of_replicas ≥ 1` и копии на разных узлах | Индекс ещё доступен (часто yellow, пока replica не восстановится) |
| Нода при **0 replica** | Дырка или red. На одном узле replica **некуда** положить — поэтому на single-node replica ставят 0 |
| ЦОД при awareness: replica жила в другой зоне | Данные живы. Без awareness OpenSearch мог сложить обе копии в один ЦОД — тогда площадка уносит индекс |
| ЦОД при **forced** awareness | Копии в мёртвую зону не переезжают → yellow, оставшиеся зоны не забиваются чужими replica. Это плата за стабильность |
| Нет snapshot, погибли все копии шарда | Данные нет. Реплика не бэкап |

Дефолт OSS OpenSearch: **1 primary + 1 replica** на индекс (`index.number_of_shards` default 1, `cluster.default_number_of_replicas` default 1). Это две копии, не три. На три ЦОДа «по копии в каждый» нужно **2 replica** (итого 3 копии) и диск ×3 относительно «только primary».

**3) Dashboards**

Падение UI ≠ падение кластера. Один под Dashboards — SPOF **просмотра**. API 9200 при этом может быть жив.

**4) Ingest-пайплайн перед кластером**

Data Prepper / Connect упал — OpenSearch хранит старое, новое не приходит. Буфер должен быть **в Kafka**, не «в надежде что Prepper не умрёт».

### Как устроено масштабирование

Несколько независимых осей:

1. **Больше объёма и поиска** → больше **data-нод** + разумный размер шарда. Primary нельзя «добавить на лету».
2. **Больше индексирования** → больше data/ingest, bulk, не мелкие одиночные POST.
3. **Больше одновременных тяжёлых запросов** → coordinating-ноды, чтобы aggregations не душили heap data-нод.
4. **Cluster manager** почти не масштабируют «от QPS поиска». Им нужна RAM под cluster state (много индексов/шардов = толстый state).

Ориентиры, которые **есть** у вендора / проекта, и которые **нельзя** принять за смету вашего прода:

- Куча: **~половина RAM**, `Xms = Xmx`. Дефолт процесса **1g/1g**, если не задать. Процентные `-XX:MaxRAMPercentage` **перебиваются** этим дефолтом — вендор просит задавать `-Xms/-Xmx` явно.
- Пример RPM-гайда: хост 8 ГиБ → куча 4g.
- Блог проекта OpenSearch: если не указать, индекс создаётся с **1 primary + 1 replica**; слишком много мелких шардов ест heap, слишком мало крупных — плохо распределяет нагрузку. Точной «обязательной» цифры ГиБ на шард в install-гайде нет — размер выбирают бенчмарком (`OpenSearch Benchmark`), не слайдом.
- Data-ноды в зонах добавляют **кратно числу зон** (для трёх ЦОДов — пачками по 3), чтобы не получить перекос.

«Терабайты в озере» сами по себе OpenSearch не наполняют. Наполняет то, что вы **решите туда писать**: все логи Kafka, полный снимок клиентов, архив интеграций без ISM.

### Безопасность самого OpenSearch

Компрометация кластера с клиентским поиском или логами интеграций = компрометация **ПДн, ответов госслужб, карты сервисов**. Учётка `admin` и demo-сертификаты равносильны ключу от всего индекса.

Официально:

- Demo-сертификаты «только для демонстрации»; `plugins.security.allow_unsafe_democertificates: true` в доке помечен как непригодный для прода (*well known and therefore unsafe*).
- С 2.12 без `OPENSEARCH_INITIAL_ADMIN_PASSWORD` (или без своего Security config) контейнер с demo-конфигом **не встанет**.
- `DISABLE_SECURITY_PLUGIN=true` в docker-примерах — для лаборатории. В проде plugin включают, HTTP TLS включают, demo выключают (`DISABLE_INSTALL_DEMO_CONFIG=true`).
- Transport TLS обязателен, если Security plugin работает. HTTP TLS надо **включить** (`plugins.security.ssl.http.enabled: true`), иначе 9200 может остаться открытым HTTP.
- Dual-mode SSL (`plugins.security_config.ssl_dual_mode_enabled`) — только на время миграции, не как постоянный прод.

«Поднять `docker compose` из гайда и выдать 5601 в интернет» — это новый attack surface, не поисковая платформа.

2. **Прод крутится в Kubernetes**, целевой инсталлятор — **OpenSearch Kubernetes Operator** линейки 3.x (таблица совместимости проекта: operator **3.0.0+** → OpenSearch до *latest 3.x*). Чарты оператора пинить **тегом релиза**, не `latest`. Перед продом — прогон именно **3.8.0** на стенде: таблица «latest 3.x» живая, отдельного отчёта «operator X сертифицирован под 3.8.0» в этом документе нет.
3. **Три ЦОДа = три зоны отказа** (`node.attr.zone`). Если это три зала с общим питанием — stretch даёт ложное чувство безопасности.
4. **Stretch (один кластер на 3 ЦОДа)** принимается как целевой для прода **только если** сеть 9300 достаточно быстрая и стабильная. Порога RTT у проекта **нет**. Пока RTT не измерен — это гипотеза.
5. **Цель отказа: пережить 1 ЦОД**, не 2 из 3. Три cluster manager по одному на ЦОД это переживают; два мёртвых ЦОДа — нет.
6. **Нагрузки нет** — поэтому **нет** цифры «N data-нод и M терабайт PVC». Есть сигналы (heap, queue, rejected, yellow/red, disk watermark, lag ingest из Kafka) и рычаги (ноды, шарды, ISM, что писать).
7. **Формального SLA / RPO / RTO нет.** Green-кластер при живой replica ≠ юридический 24/7 и ≠ «ни один лог не потерян, если Prepper отстал».
8. **Корпоративный PKI есть или будет.** Demo PKI — для теста.
9. **Идентификация людей** в проде — SSO (SAML/OIDC через Dashboards + backend roles), не общая учётка `admin`. Сервисы — отдельные internal users или JWT/mTLS, least privilege на индексы.
10. **Шифрование канала — TLS JDK.** Требования ГОСТ/СКЗИ не озвучены; vanilla OpenSearch их не закрывает.
11. **Тестовый стенд изолирован.** На нём допустимы single-node, demo-сертификаты и слабые лимиты. В прод их не копируем.
12. **Kafka, Camunda, озеро, интеграционное API** — источники данных и клиенты 9200, не часть этого ПО. Их контракт: bulk/ingest, idempotent `_id` где нужно, схема полей, ILM/ISM.
13. **Отдельный кластер от Wazuh indexer.** Смешивать алерты ИБ и бизнес-поиск в одном Security realm — плохая идея даже если «оба OpenSearch».
14. **Лицензия Apache 2.0.** Отдельного license-server нет — плюс для закрытого контура. Следить нужно за составом плагинов (не все сторонние плагины Apache 2.0).

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «поставили оператор и забыли».

| Пробел | Почему это ломает решение |
|---|---|
| **RTT и потери на 9300 между ЦОДами** (p50/p95/p99, все пары) | Cluster state и репликация шардов ходят по transport. Высокий или плавающий RTT → медленные выборы, delayed unassigned, ложные fail нод, yellow. Stretch станет источником аварий. |
| **Один Kubernetes на 3 ЦОДа или три изолированных** | Stretch на 9300 требует pod-to-pod (или host) маршрутизации. Иначе — три кластера + CCR, не один экземпляр. |
| **Что именно кладёте в OpenSearch** (логи? проекция клиентов? аудит интеграций? всё сразу?) | Разный размер шарда, replica, ISM, RBAC и класс диска. «Терабайты» без состава — не смета. |
| **Срок хранения и 152-ФЗ/КИИ** | ISM, шифрование томов, что можно индексировать (ПДн в full-text!), куда уезжает snapshot. |
| **Где живёт snapshot-репозиторий** | Если бакет только в одном ЦОДе — падение этой площадки убивает бэкап. Репозиторий должен переживать тот же отказ, что и кластер, или быть вне всех трёх. |
| **Профиль запросов** (индексация MB/s vs тяжёлые aggregations vs векторный поиск 3.8) | Иначе купите data-ноды «под логи», а получите heap на фасетах по клиентам. |
| **Куда смотрит Dashboards** (только внутренняя сеть? SSO?) | Публичный 5601 с demo `admin` — инцидент. |
| **StorageClass: local SSD vs сеть** | Вендор прямо против NFS как *диска ноды*. Медленный PVC = очередь index, rejected, отставание от Kafka при живом кластере. |
| **Совместимость оператора с 3.8.0 на вашей версии Kubernetes** | Таблица «latest 3.x» не заменяет проверку CRD/Helm-чарта. |
| **Нужен ли CCR** (active-passive) vs stretch | Пока сеть не замерена, выбор — лотерея. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Зафиксировать **OpenSearch 3.8.0** и **тот же** тег Dashboards. Не смешивать major. Оператор/Helm — совместимый релиз.
2. Выставить хостовые лимиты (`vm.max_map_count`, swap, `nofile`, memory lock) **до** первого пода.
3. Поднять ноды: сначала кворум cluster manager, затем data. Задать `cluster.name`, `node.name`, `discovery.seed_hosts`, при первом старте — `cluster.initial_cluster_manager_nodes`.
4. Выпустить **свои** сертификаты и пользователей **до** боевых клиентов. Не оставлять demo.
5. Зарегистрировать **snapshot repository** и сделать первый снимок пустого/тестового индекса (проверка, что репозиторий вообще работает).
6. Задать **index templates** (shards, replica, mapping, refresh) и **ISM** **до** боевого потока. Primary потом дешево не поменять.
7. Включить метрики: `_cluster/health`, `_cat/shards`, heap, rejected, disk; лаг консьюмера Kafka, если он питает индекс.
8. Прогнать контролируемую запись и поиск. Убедиться, что документ **виден** и что падение одной data-ноды на проде оставляет индекс читаемым.
9. Только потом — SSO, тонкий RBAC, hot-warm, векторные индексы 3.8, если они вообще нужны.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** чтобы разработчики писали и искали документы, отлаживали mapping, подключали Dashboards и пайплайн из Kafka. **Не** цель: доказать отказ ЦОДа и ёмкость.

Два официальных минимальных пути (выберите один):

**Путь A — один контейнер** (быстрее понять продукт):

```text
docker run -d -p 9200:9200 -p 9600:9600 \
  -e "discovery.type=single-node" \
  -e "OPENSEARCH_INITIAL_ADMIN_PASSWORD=<strong-password>" \
  opensearchproject/opensearch:3.8.0
```

Проверка: `curl https://localhost:9200 -ku admin:"<strong-password>"`.  
`discovery.type=single-node` **обходиt** нормальный discovery — только dev/test.

**Путь B — docker compose из install-гайда** (2 ноды OpenSearch + Dashboards на bridge-сети). Вендор прямо пишет: примеры compose **не для production**. Demo-конфиг (self-signed, внутренние пользователи) ставится, если не задать `DISABLE_INSTALL_DEMO_CONFIG=true`.

На Kubernetes: один `OpenSearchCluster` с одним node pool, 1 replica, маленький PVC; либо Helm `singleNode: true`. Не копировать этот YAML в прод.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Число нод | 1 (или 2 в compose) | Нет требования пережить выкат |
| Replica | 0 на single-node | Иначе вечный yellow: копию некуда положить |
| Роли | все в одном процессе | Dedicated manager на ноутбуке не учит продукт |
| PKI | demo / self-signed | Иначе команда утонет в сертификатах раньше, чем в mapping |
| Пароль | свой сильный `OPENSEARCH_INITIAL_ADMIN_PASSWORD`, сеть изолирована | С 2.12 без пароля demo не встанет; в интернет всё равно не открываем |
| Security plugin | включён (как в образе) | Выключать `DISABLE_SECURITY_PLUGIN` имеет смысл только если сознательно тестируете «голое» API; привычка выключать уедет в прод |
| CPU/heap | 512m–1g как в примерах Docker | Не цель — ёмкость |
| Snapshot | можно отложить на день | Нельзя «забыть навсегда» — на препроде репозиторий обязателен |
| ISM | минимум | Сначала увидеть реальный объём тестовых логов |

#### Чего на тесте **не** стоит упрощать

- Версия **3.8.0** на нодах и Dashboards.
- Клиентский код с явным индексом и `_id` (идемпотентность ingest из Kafka). Иначе в проде «переиграть событие» размножит документы.
- Понимание, что **primary shards** задаются при создании. Поиграть с template на тесте дешевле, чем re-index терабайтов.
- Запомнить: compose с demo-сертификатами **не** есть «почти прод».

#### Сильные стороны такой схемы

- Поднимается за часы, совпадает с официальным Docker-гайдом.
- Дешево показывает mapping и шум запросов на *ваших* JSON из интеграций/Camunda.
- Single-node официально предназначен для development/testing.

#### Слабые стороны (обязательно понимать)

- Нет модели отказа ЦОДа, нет доказанной ёмкости, нет 9300 между площадками.
- Успешный поиск на одном узле **не** доказывает, что cluster state переживёт RTT и что replica разложится по зонам.
- Demo PKI и открытый 9200 приучают «зайти с admin». В инциденте нужен закрытый UI и RBAC.

Практическая рекомендация: препрод = маленькая **копия прод-топологии** (3 manager + data кратно зонам, свои cert, replica ≥ 1, ISM, snapshot), даже без боевого трафика.

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер под терабайты озера» **нет** — нагрузки нет. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

OpenSearch плохо переживает **три независимых правды** (три индекса клиентов) и плохо переживает **слепой stretch** по 9300.

**Вариант A — один Kubernetes на 3 ЦОДа (зоны), один кластер.**

- 3 dedicated `cluster_manager` (по одному в зоне) + data-ноды **пачками по 3**.
- `node.attr.zone` + `cluster.routing.allocation.awareness.attributes: zone`.
- Для «не убить оставшиеся ЦОДы ребалансом» — **forced awareness** на три значения зон. Следствие: при падении зоны кластер **yellow**, пока зона не вернётся (или пока оператор сознательно не снимет force). Это штатное поведение из доки, не баг.
- Replica: минимум **1** (дефолт) *при работающем awareness*. Если нужна копия **в каждом** из трёх ЦОДов — `number_of_replicas: 2` (три копии) и диск считать заранее.
- Клиенты ходят на Service/LB **9200** (coordinating/ingest), не на manager.
- Dashboards: **≥ 2** реплики + anti-affinity.

**Вариант B — три изолированных Kubernetes, сеть 9300 между ними нет или RTT неприемлем.**

- **B1. Один кластер в одном ЦОДе**, клиенты с остальных ходят на 9200. Простой кворум. Падение этого ЦОДа = нет поиска ни у кого. Спасает snapshot + заранее прогнанный restore на другой площадке (RTO надо замерить).
- **B2. Три кластера + CCR.** Leader принимает запись, follower read-only тянет индекс. Полезно для чтения «рядом с приложением» и как тёплый простой. Это **не** прозрачный failover записи: промоушен follower в leader — отдельная процедура, не «сам выберется». Плагин должен стоять на **обоих** кластерах; Security plugin — либо включён на обоих, либо выключен на обоих.

**Пока топология K8s и RTT не зафиксированы, нельзя честно выбрать A.** Дальше — общее для A как целевого «3 ЦОДа в одном городе»; B — запасной.

##### Сильные / слабые стороны (A, stretch)

| Сильное | Слабое |
|---|---|
| Один bootstrap, один индекс, один RBAC | Латентность и стабильность 9300 = латентность кластера |
| Официальный паттерн «3 manager в 3 зонах» | Падение двух ЦОДов снимает кворум |
| Awareness раскладывает копии | Без замера RTT — лотерея yellow/split |
| Клиентам один 9200 | Ошибка mapping/шаблона сразу везде |
| Forced awareness бережёт диск живых зон | Пока мёртвая зона лежит, replica не восстановится (yellow) |

##### Сильные / слабые стороны (B1, мозг в одном ЦОДе)

| Сильное | Слабое |
|---|---|
| 9300 не ходит между ЦОДами | Падение ЦОДа с кластером = нет поиска на всех трёх |
| Проще кворум и диск | Нужен очень явный DR: restore snapshot на другой площадке **с прогоном по времени** |
| | Клиентский путь 9200 через город: это уже ваша сеть, не магия OpenSearch |

##### Сильные / слабые стороны (B2, CCR)

| Сильное | Слабое |
|---|---|
| Запись локальна на leader; чтение можно приблизить | Follower **read-only**; RPO > 0 (асинхронный pull) |
| Переживание гибели leader-площадки *для чтения* | Переключение записи — ручной/сценарный процесс |
| Официальный плагин под «географически далёкие ДЦ» | Два Security realm, два ISM, два мониторинга; wildcard replication надо сопровождать |

##### Слабое место любого stretch без замера RTT

Документация **не задаёт** порог задержки. Утверждение «три ЦОДа в одном городе, значит можно размазать» — **непроверенное**. Городская сеть бывает и долями миллисекунды, и «через кривой firewall 40 мс с потерями». Мерить **9300** (и 9200, если клиенты чужие), не ping ICMP «на всякий случай».

#### Роли и кворум

- Dedicated cluster manager: `node.roles: [ cluster_manager ]`. На них **не** кладут боевые индексы.
- Data: `node.roles: [ data, ingest ]` на старте; выделить ingest/coordinating — когда появится профиль нагрузки.
- Нечётное число manager. **3** — официальный «почти всегда». **5** имеет смысл, если боитесь сценария «зона + ещё одна manager-нода»; это уже диск/RAM на cluster state, не бесплатно. Вендор для типичного прода пишет три.
- После первого bootstrap список `cluster.initial_cluster_manager_nodes` не используют как «постоянный членство». Новые manager **присоединяются** к существующему кластеру, а не бутстрапят второй.

#### Индексы, шарды, ISM

- Шаблоны **до** первого документа.
- Replica ≥ 1 в проде на многонодовом кластере. На тесте с 1 нодой — 0.
- Не плодить индекс «на каждый микросервис на каждый час» без ISM: каждый индекс и шард живут в cluster state и в heap manager/data.
- ISM: горячий индекс → (опционально warm) → delete/snapshot. Срок хранения — решение ИБ/бизнеса, не дефолт вендора.
- Hot-warm в доке есть (`node.attr.temp` + ISM). Включать **после** того, как поняли, какие индексы реально остывают. Иначе получите unassigned replica, как в учебном примере с одним hot-узлом.

#### Снапшоты

- Репозиторий зарегистрировать сразу. Проверять **restore** на другой namespace/кластер, не только `SUCCESS` на create.
- Снапшот инкрементальный относительно репозитория; первый тяжёлый, дальше легче — формулировка Snapshot Management.
- S3-совместимое хранилище: в **3.8.0** дефолт `server_side_encryption_type` сменился на **AES256**. Если ваш MinIO/совместимый шлюз отвергает заголовок — явно вернуть `bucket_default` (breaking change 3.8.0). Не узнавать это в ночь инцидента.
- Репозиторий типа `fs` требует путь, **доступный всем нодам**. Это не «PVC одной data-ноды».

#### Безопасность прода

| Слой | Правило |
|---|---|
| Demo | `DISABLE_INSTALL_DEMO_CONFIG=true`, `allow_unsafe_democertificates: false`, своих demo-файлов в образе нет |
| Transport 9300 | TLS, свои cert, `enforce_hostname_verification: true` (выключать «чтобы завелось» нельзя считать продом) |
| HTTP 9200 | `plugins.security.ssl.http.enabled: true`, только HTTPS |
| Пользователи | нет общего `admin` у приложений; роли на индексы; SSO для людей |
| Сеть | NetworkPolicy: 9200 — клиенты и Dashboards; 9300 — только ноды (+ CCR, если B2); 5601 — внутренняя сеть; 9600 не в интернет |
| Секреты | не в Git; operator keystore + Vault/K8s Secret |
| At-rest | шифрование томов/CSI; в OSS нет «галочки encrypt index» как замены диску |
| Аудит | Security audit в отдельный индекс/поток, со своим ISM |

`securityadmin.sh` — только с admin DN, по HTTPS. Случайный «поправили roles.yml на одной ноде» **не** разъедется сам, если выключен `allow_default_init_securityindex`.

##### Сильные / слабые стороны (TLS + Security plugin + RBAC)

| Сильное | Слабое |
|---|---|
| В бандле, без отдельной лицензии | Двухслойный TLS (9300 и 9200) и admin-сертификат легко сломать при выкате |
| FGAC по индексам/документам | Ошибка роли = «почему сервис не пишет»; нужен процесс выдачи |
| Оператор умеет управлять TLS | Demo-путь в Docker/Helm слишком удобный — его копируют в прод |
| Не зависит от облачного IAM | Не ГОСТ; mTLS клиентов тяжелее паролей, но лучше привязывает identity |

Если появится корпоративный IdP — подключать его к Dashboards/Security, не плодить локальных людей.

#### Kubernetes-специфика прода

- Отдельные node pool в CR: `cluster_manager` и `data` (как isolated controller/broker у Kafka).
- Topology spread / anti-affinity: не сложить все replica шарда и всех manager в одну зону.
- PDB: не дать Kubernetes снять сразу два manager или слишком много data одной зоны.
- Ресурсы: лимит памяти **выше** кучи. Если лимит = `-Xmx`, не останется RAM на Lucene/mmap — нода будет жить в GC и page fault.
- Не ставить data на overlay с большим jitter без замера. Если pod-сеть между ЦОДами хуже VM — ноды иногда лучше на hostNetwork / вне K8s. Это решение по замерам.
- Rolling upgrade оператора: он ждёт **green** после каждой ноды. Жёлтый кластер из-за forced awareness во время аварии зоны **остановит** выкат — это надо понимать, не «сломался оператор».
- Не менять unit диска `G`↔`Gi` без бэкапа: оператор предупреждает, что пересоздаст VolumeClaimTemplates.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Замерить сеть между ЦОДами на 9300/9200. Решение A vs B.
2. Выделить ноды, local SSD, зоны `node.attr.zone`.
3. Поставить оператор, описать кластер **3.8.0**, isolated manager, свои cert.
4. Включить Security и HTTP TLS **до** боевых индексов.
5. Зарегистрировать snapshot repository, прогнать create+restore.
6. Залить index templates (replica, mapping) и ISM.
7. Выложить тестовый индекс, прогнать bulk+search, убить data-под, убедиться что документ читается.
8. Подключить первый реальный пайплайн (лучше из Kafka, с буфером).
9. Нагрузить хотя бы синтетикой, снять heap/reject/latency. По результату — число data-нод и шардов.
10. Прогон «ЦОД недоступен» на препроде: выключить зону, проверить кворум manager, поиск, что делает forced awareness, что snapshot ещё доступен.

Без пункта 10 у вас нет отказоустойчивости, есть надежда.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | 3 dedicated manager в 3 зонах; data кратно зонам; replica ≥ 1 + awareness; цель — 1 ЦОД; snapshot с прогнанным restore |
| Производительность / масштаб | Не требуется | Шарды как единица масштаба; куча ~½ RAM, `Xms=Xmx`; SSD не NFS; ISM; клиенты не на manager; рост data-нод пачками |
| Безопасность | Demo PKI только в изоляции; свой admin-пароль | Нет demo; TLS 9300+9200; RBAC; 5601 не в интернет; секреты не в git; at-rest на томах |

**Не готов к проду**, если: `discovery.type=single-node`, replica 0 на нескольких нодах, demo-сертификаты, `DISABLE_SECURITY_PLUGIN`, данные на NFS/`emptyDir`, все ноды в одной зоне, нет snapshot, RTT между ЦОДами неизвестен, а схема уже stretch, кластер общий с Wazuh indexer, OpenSearch назначен SoT клиентских данных.
