# Luxms BI 12.x — развёртывание и настройка

Версия ПО: линейка **Luxms BI 12.x**. На дату подготовки документа:

- последний релиз с отдельной страницей notes на сайте вендора — **12.0.2** (карты WMS/WFS, стабильность): https://luxmsbi.ru/products/relizy/
- портал HTML-документации вендор помечает как **12.1.0**: https://luxmsbi.ru/products/documentation/ → https://luxmsbi.ru/docs/
- notes **12.0.0**: https://luxmsbi.ru/products/relizy/luxms-bi-12-0-0-release-notes/ (апгрейд с 11.x — **не** «просто yum update», есть отдельный upgrade-guide)

Точную сборку пакетов (12.0.2 vs 12.1.0) фиксируют **договором и доступом к персональному репозиторию**, не публичный Docker Hub. Ниже правила для линейки **12.x** и совместимого стороннего стека из текущей «Технической информации».

Это **коммерческое** ПО (реестр российского ПО, рег. № **3366**). Без лицензии и репозитория вендора «скачать и поднять как Grafana OSS» нельзя.

Этот текст — не мануал «скопируй `apt install`», а правила, без которых экземпляр **не** будет одновременно отказоустойчивым, масштабируемым и безопасным.

Luxms BI **не было** в исходном списке «Kafka / Camunda / озеро / интеграционное API». Ниже — как поставить слой **бизнес-аналитики и визуализации** на ту же инфраструктуру с тремя ЦОДами. Это **не** озеро эталонных данных, **не** шина событий, **не** интеграционный контур к 30+ госслужбам и **не** замена Grafana/Prometheus (операционный мониторинг) и не замена Wazuh.

## Глоссарий терминов

| Термин | Простыми словами |
|---|---|
| **Luxms BI / ВУК** | Платформа бизнес-аналитики: дэшборды, отчёты, self-service. Юридическое имя в реестре — «Визуальный управленческий контроль Luxms BI». В запросе «Lux MS» — это оно. |
| **Датацентричная / двухзвенная архитектура** | Основная бизнес-логика живёт **в PostgreSQL** (хранимые процедуры PL/pgSQL), а не в толстом Java-приложении. Между браузером и ответом БД вендор ставит короткий путь: **Nginx**. |
| **Атлас** | Набор аналитических приложений/дэшбордов в одном контуре (как «проект» внутри BI). |
| **Датасет** | Логическая единица: данные + настройки визуализации, которые фронт показывает пользователю. |
| **Куб** | Массив «размерности × факты» для аналитики (не OLAP-куб SSAS, а модель вендора). |
| **Дэш / дэшборд** | Один визуальный блок / экран из блоков. |
| **Front-end** | HTML5/JS в браузере. Сервер его **раздаёт**, логику ответа считает ядро в БД и микросервисы. |
| **luxmsbi-web** | Веб-вход: отдельный Nginx + Lua (`luxmsbi-web.service`), **не** системный nginx ОС. |
| **luxmsbi-appserver** | Java-сервис управления платформой и (в mono-сборке) работы с источниками. HTTP API. |
| **appserver-mono** | «Всё в одном» Java-пакете: управление + источники. Для теста удобно; для высокой нагрузки источники выносят. |
| **luxmsbi-datagate / Data Gateway Framework** | Вынесенный доступ к внешним JDBC/источникам. Чтобы BI **не** тащила чужие БД через тот же процесс, что UI. |
| **luxmsbi-importer** | Старый Java-импортёр по расписанию. В руководстве администратора линейки **9.2** прямо: для **новых** внедрений **не** рекомендуют, оставляют для уже живущих инсталляций. |
| **Data Boring** | Встроенный ETL/ELT no/low-code (часть поставки). Это **не** ваше интеграционное API к ведомствам. |
| **BINS (luxmsbi-bins)** | Сервис WebSocket: чтобы у другого пользователя дэшборд обновился без F5. |
| **KeyDB** | Форк Redis: сессии, лимиты логина, pub/sub для realtime. Порт как у Redis: **6379**. |
| **NATS / JetStream** | Внутренняя шина и хранилище объектов (конфиги, сгенерированные отчёты) между компонентами. Это **не** замена вашей Apache Kafka. |
| **FDW** | Foreign Data Wrapper PostgreSQL: «таблица», которая на самом деле читает **другую** систему. Живой запрос в источник без обязательного копирования. |
| **Слои данных (горячие / тёплые / холодные)** | Идея вендора: то, что крутят на дэшборде, держат быстро (часто ClickHouse/Greenplum/витрина); архив — дешевле и медленнее. |
| **MPP СХД** | Массово-параллельное хранилище под большие объёмы. В линейке Luxms целевые: **ClickHouse / Arenadata QuickMarts**, **Greenplum / Arenadata DB**. Ядро метаданных при этом всё равно PostgreSQL. |
| **Patroni** | Надстройка над PostgreSQL: выбирает **лидера**, поднимает реплику, если лидер умер. Сама Postgres «кластером» не становится. |
| **DCS / Consul** | «Записная книжка», в которой Patroni пишет «кто сейчас лидер». Вендор в 12.x указывает **Consul 1.16.1**. Без живого DCS Patroni не знает, кого считать primary. |
| **HAProxy (у Luxms)** | В их схеме не только вход HTTPS. Ещё **пул соединений к Postgres** и разделение read/write (лидер vs реплики). У вас HAProxy уже описан отдельно. |
| **SSO / Keycloak** | Единый вход. Вендор заявляет Keycloak, LDAP/AD, ЕСИА, JWT API-токены. |
| **RLS** | Ограничение строк: пользователь видит не всю таблицу, а «свои» филиалы/объекты. |
| **Роли лицензии Viewer / Creator / Admin** | Это **лицензионный** потолок (не отменяется настройкой), плюс обычные права внутри атласа. Viewer — смотреть; Creator — источники и ETL; Admin — всё, включая пользователей. |
| **Self-service** | Сам подключил источник, сам собрал витрину и дэшборд. Только Creator/Admin. |
| **АРМ сотрудника безопасности** | Отдельный UI для ИБ: сессии, аудит, инциденты. Не путать с Admin, который рисует дэшборды. |
| **ФСТЭК 4 УД, сертификат № 5055** | Сертифицированная **сборка 11.0.x** (таблица компонентов на сайте, дата сертификата **15.04.2026**, поддержка этой версии до **15.04.2031**). **12.x в этой таблице нет.** |
| **Enterprise Cluster UL / L350** | Лицензия «2 промышленных сервера в балансировке», отказоустойчивость, большие данные. Потолок **1000 одновременных сессий** в описании UL. |
| **DEVL** | Лицензия на тест / непродуктовые среды. |
| **Appliance** | Готовая VM (в руководстве 9.2 — ESXi с демо-датасетами) для учёбы, не прод. |
| **Stretch** | Один логический кластер (Postgres/NATS/Consul), железо в нескольких ЦОДах. |
| **RPO / RTO** | Сколько данных готовы потерять / как быстро восстановиться. |

## Основные элементы системы и зависимости

### Что входит в поставку Luxms BI 12.x (это платформа из нескольких ролей)

| Роль | Зачем | Как масштабируется |
|---|---|---|
| **PostgreSQL / Postgres Pro (ядро)** | Метаданные, права, логика на PL/pgSQL, часто и витрины | HA = **Patroni + DCS**, не «два docker postgres». Ёмкость аналитики больших объёмов часто **выносят** в ClickHouse/Greenplum |
| **Расширения Postgres** | Обязательны: `pgsql-http`, `redis_pub_sub` / redis-pubsub, **plv8**, `redis_fdw` (в ФСТЭК-сборке — keydb-fdw) | Ставятся **из пакетов вендора**, не «на глаз с GitHub» |
| **luxmsbi-web (Nginx + Lua)** | HTTPS-вход, раздача UI, прокси на appserver/bins/БД | Горизонтально: несколько web-узлов за балансировщиком |
| **luxmsbi-appserver / mono** | API управления, часть работы с источниками | Несколько инстансов; для нагрузки источники → datagate |
| **luxmsbi-datagate / jdbc** | Хождение в чужие БД | Выделенные узлы, чтобы тяжёлый JDBC не убил UI |
| **luxmsbi-bins** | WebSocket / realtime | Зависит от KeyDB и БД |
| **luxmsbi-gateway** | Шлюз в составе поставки (есть в ФСТЭК-таблице 11.x) | Не путать с **вашим** интеграционным API к ведомствам |
| **Data Boring** | ETL внутри BI | Отдельный процесс; расписание и объём — ваша нагрузка на диск/CPU |
| **NATS + JetStream** | Конфиги, отчёты, pub/sub между компонентами | Кластер из нескольких серверов, диск `/opt/nats` |
| **KeyDB** | Сессии, антибрут, realtime | Репликация active-replica (как описывал вендор для KeyDB) |
| **headless-chrome** | PNG/экспорт визуализаций (есть в сертифицированном составе 11.x) | Отдельный тяжёлый процесс; не в интернет |
| **Consul + Patroni** | HA ядра БД | Кворум Consul; один Postgres **primary** |

Плюс *рядом*, но это уже другое ПО: **Keycloak** (SSO), **HAProxy**, объектное/файловое место под отчёты, ClickHouse/Greenplum как MPP, ваш **Kafka** только как *источник* для витрин.

### Порты (контракт сети)

Публично в документации **12.x** явно разобраны порты **NATS**. Остальные порты Java/web-слоя ниже — из **руководства системного администратора линейки 9.2** (community PDF). Перед продом **сверить** с sysadm-guide **той сборки 12.x**, что в договоре: имена пакетов и порты Java могли сдвинуться.

| Порт | Назначение | Источник | Кому открывать |
|---|---|---|---|
| **443/TCP** (снаружи) | HTTPS для людей | Практика; TLS вендор для нагрузки рекомендует **на балансировщике**, не на каждом luxmsbi-web | Только внутренняя сеть / SSO-прокси |
| **80/TCP** | HTTP web, если ещё не унесли на LB | 9.2 | Не в интернет |
| **5432/TCP** | PostgreSQL | 9.2 + здравый смысл | web, appserver, datagate, Patroni, HAProxy-пул. Не мир |
| **6379/TCP** | KeyDB | 9.2 | web, bins, БД-расширения. Не мир |
| **4222/TCP** | NATS клиенты | **12.x** appendix NATS | appserver и др. компоненты BI |
| **6222/TCP** | NATS cluster (маршруты узлов) | **12.x** | Только узлы NATS между собой |
| **8222/TCP** | NATS monitor | **12.x** пример конфига | Операторы, не мир |
| **8888/TCP** | В 12.x пример NATS: **WebSocket** (`websocket.port`). В 9.2 тот же номер — HTTP API **BINS** | **Конфликт номеров при совмещении на одном хосте — проверять на вашей сборке** | Не мир |
| **8080/TCP** | appserver HTTP | 9.2 | С web/LB |
| **8200/TCP** | datagate HTTP | 9.2 | С web/внутренних |
| **8192/TCP** | importer HTTP | 9.2 | Если importer ещё жив |
| **8889/TCP** | gateway | 9.2 | С web |
| **8282/TCP** | lua-webapi | 9.2 | localhost / web |
| **7200 / 7192/TCP** | RSocket appserver / importer | 9.2 | Внутри контура |

### Чего в Luxms BI нет (частая путаница)

| Нужно системе | Это не Luxms BI | Зачем помнить |
|---|---|---|
| Источник истины клиентских карточек | Озеро / ваша СУБД эталона | BI может **скопировать** витрину или читать FDW. Копия ≠ эталон. Расхождение через неделю — типичный сюрприз. |
| Шина событий, `acks=all`, consumer group | Apache Kafka | Luxms **умеет брать** Kafka как источник. Это подписка аналитики, не замена шины микросервисов. |
| Оркестрация BPMN | Camunda | Дэшборд «сколько заявок зависло» ≠ исполнение процесса. |
| Единственный выход к 30+ ведомствам | Ваше интеграционное API | Data Boring/JDBC из BI в СМЭВ/госAPI — обход архитектуры и дыра ИБ. |
| Операционный мониторинг K8s/Kafka | Grafana + Prometheus/Mimir | Другой контур, другие зрители, другие данные. |
| Официальный Helm-оператор «как у Grafana» | **В публичных docs 12.x не найден** | Штатный путь — **пакеты Linux** + (для прода) **Ansible вендора после согласования схемы**. Kubernetes у вас есть; это не значит, что вендор ведёт Luxms как Helm-чарт. |
| Кворум «2 из 3 процессов luxmsbi-web» | Нет | Упал Postgres primary без failover — UI «живой» nginx бесполезен. |
| ГОСТ TLS / СКЗИ «из коробки 12.x» | Отдельный контур ИБ | ФСТЭК 4 УД — про **сертифицированную сборку 11.0.x** и процессы вендора, не про «любой 12.1 с Let's Encrypt». |
| Порог RTT между ЦОДами | Нет | Patroni/Consul/NATS/синхронная реплика Postgres порога в миллисекундах в публичных docs Luxms **не задают**. |
| Официальный SLA 24/7 | Нет | Есть кластерные схемы и лицензии с формулировкой горячего резерва. Цифры «пять девяток» вендор в tech-info **не публикует**. |
| Бесплатный образ `luxmsbi:latest` на Docker Hub | Нет | Репозиторий **персональный**, с аутентификацией. |

### Зависимости окружения (обязательны)

Из текущей tech-info 12.x (https://luxmsbi.ru/docs/overviews/general-overview/tech-info) и страниц совместимости:

- **ОС (заявлено вендором):** Astra Linux SE **1.7 / 1.8**, РЕД ОС **7.3 / 8.0**, Альт СП **10**, Rocky Linux **9**, MosOS Arbat **15.5**. Не «любой Ubuntu с Docker».
- **Ядро СУБД платформы:** PostgreSQL **15 или 17**, либо Postgres Pro **15/17**, Tantor **15**, Jatoba **5**. Пакеты для PostgreSQL/Postgres Pro **13** вендор **прекратил с 01.12.2025**. CentOS 7 / PG 11 — с 2024.
- **Рядом в составе:** Nginx 1.xx, LuaJIT 2.1, Node.js **18/20**, OpenJDK **17**, KeyDB **6.x**, ClickHouse **25.3** (если берёте MPP), NATS **2.11.6**, Consul **1.16.1**, Patroni **3.2.x**.
- **Железо (официально, на весь сервер Luxms BI, не «на под»):**
  - минимум: **8 ядер ≥ 2 ГГц, 24 ГиБ RAM, 500 ГиБ** полезного диска, чтение **≥ 150 МБ/с**;
  - ориентир на **100 одновременных пользователей:** **16 ядер, 32 ГиБ, 1 ТиБ**, тот же порог диска.
- **Браузеры** (tech-info): Chrome 90+, Firefox 85+, Safari 14+, Edge 89+, Яндекс 21+; IE — от 10 (для нового контура IE не рассматриваем).
- **NTP** на всех узлах кластера (явная рекомендация админ-гайда).
- **Лицензия + базовая техподдержка** (вендор: поддержка — обязательное условие покупки лицензий, **30% в год** от стоимости; без неё нет обновлений ядра).

Источники данных *для витрин* (не ядро): PostgreSQL, ClickHouse, MySQL, Oracle, MS SQL, Kafka, JDBC, потоки (MQTT, Redis, …), то что умеет NiFi — через витрины/CSV. Российские/Arenadata — отдельный список на https://luxmsbi.ru/docs/overviews/compatibility/dbms.

### Как Luxms стыкуется с вашей архитектурой

```
Люди (аналитики, руководители, ИБ)
        │  HTTPS :443
        ▼
 HAProxy / Ingress          ← TLS, не «голый» luxmsbi-web в интернет
        │
 luxmsbi-web × N  ── KeyDB ── BINS (realtime)
        │
        ├── appserver / datagate  ── JDBC/FDW ──► витрины озера / ClickHouse
        │                              ✗ не в госслужбы напрямую
        ├── Data Boring (ETL) ──► запись витрин  ✗ не SoT
        └── PostgreSQL (Patroni) ◄── Consul DCS
                ▲
                └── NATS (внутри BI, не Kafka)

Микросервисы / Camunda / интеграционный API / Kafka
        │  экспорт в озеро / витрины (ваш контур)
        ▼
 Озеро эталонных данных     ← источник истины
        ▲
        └── Luxms читает (FDW/JDBC) или получает копию ETL
```

Пересечение с уже описанным:

- **HAProxy** — вход на BI и (по схеме вендора) пул к Postgres.
- **Kafka** — источник для витрин, не транспорт ядра Luxms (ядро внутренне на NATS).
- **Vault** — пароли БД `bi`, KeyDB, NATS, JDBC к озеру, client secret Keycloak. Дефолты `bi`/`bi` из старых гайдов в прод не живут.
- **Wazuh / Falco / WAF** — другой контур. Журнал Luxms можно **отдавать** в SIEM (вендор это заявляет), это не замена Falco.
- **Grafana** — здоровье самой платформы (Nginx, Postgres, NATS), не бизнес-дэшборды.
- **Kubernetes** — у вас оркестратор. Для Luxms честный дефолт: **отдельные VM/ноды с пакетами** *или* контейнеры **поставкой вендора**, если она будет в договоре. Публичного оператора уровня Strimzi/Grafana Operator нет.

## Краткие вводные

### Зачем вам Luxms в этой архитектуре

Озеро терабайт и 30+ интеграций сами по себе не дают руководителю картинку «что с заявками и клиентами». Luxms закрывает слой:

1. Дэшборды и self-service по **уже нормализованным** данным.
2. Разграничение «филиал видит своё» (роли + RLS), аудит для ИБ.
3. Импортозамещение BI (реестр, российские ОС/СУБД, при необходимости — **отдельная** ФСТЭК-сборка).

Если положить в Luxms «сырой» ответ ведомства в обход интеграционного API — вы получите второй интеграционный контур без контракта, ретраев и очистки, плюс ПДн в BI-витрине.

### Как устроена отказоустойчивость (идея, не магия)

Это **не** один Raft на весь продукт. Несколько слоёв, каждый со своим отказом:

**1) Вход (web × N + балансировщик)**

| Что падает | Что происходит |
|---|---|
| Один luxmsbi-web при N≥2 | LB перестаёт слать трафик. UI жив |
| Все web | Нет UI. Данные в Postgres/ClickHouse **на месте** |
| HTTPS только на одном web без LB | Выкат nginx = простой всех людей |

**2) Ядро PostgreSQL (Patroni)**

| Что падает | Что происходит |
|---|---|
| Реплика | Чтение можно пережить; запись идёт на лидера |
| Лидер, кворум Consul жив | Patroni выбирает нового лидера. Короткий простой записи. Клиенты должны ходить **через** VIP/HAProxy, не на зашитый IP старого лидера |
| Потеря кворума Consul (например 2 из 3 серверов DCS в мёртвом ЦОДе) | Patroni **не знает**, кого считать лидером → запись BI встаёт |
| Диск лидера, нет валидной реплики / бэкапа | Потеря метаданных, прав, локальных витрин |

Вендор в админ-гайде: кластер Postgres **рекомендует Patroni + Consul**; HAProxy — чтобы приложения не держали по соединению на каждый запрос и отличали лидера от реплик.

**3) KeyDB и NATS**

Без KeyDB ломаются сессии, антибрут (он на KeyDB и завязан), realtime. Без NATS — обмен между Java-компонентами и выкладка отчётов в кластере. Оба нужны **кластером**, не «один контейнер рядом».

**4) Источник витрин**

Падение озера/ClickHouse = пустые дэши при живом UI. Это не «упал Luxms», это упал **источник**. Для 24/7 картинки бизнеса HA считается по самому слабому: web, Postgres, NATS, KeyDB, витрина, сеть, SSO.

### Как устроено масштабирование

Три оси, которые путают:

1. **Больше людей смотрят дэши** → больше CPU/RAM web+БД, пул соединений (HAProxy), лимит сессий лицензии (в UL вендор пишет **не более 1000 одновременных**). Железо tech-info — про **100** одновременных на 16 ядер / 32 ГиБ — это **ориентир вендора**, не ваш замер.
2. **Тяжёлые запросы / self-service / JDBC «в живую»** → нагрузка на **источник** и на datagate, не на «ещё один nginx».
3. **Терабайты** → витрины на **ClickHouse/Greenplum** (или ваше озеро), **не** раздувание единственного PostgreSQL метаданных. Ядро Luxms остаётся Postgres; MPP подключают «чтобы скорость на больших объёмах».

Горизонталь: web, appserver, datagate, узлы MPP. Вертикаль: диск и RAM Postgres/ClickHouse. Добавить третий ЦОД **без** кворума Consul и без схемы «кто primary» отказоустойчивости не добавляет.

Вендор: на одном хосте «обычно до **100 активных**»; дальше — дублирование сервисов и кластер БД. Числа **вашей** нагрузки нет — поэтому ниже нет «купите 12 серверов».

### Безопасность самой Luxms

Компрометация учётки **Admin** = права на пользователей, источники, выгрузки. Self-service Creator, который получил JDBC в озеро клиентов, читает **эталон** так же, как интеграционный сервис, только из браузера.

Заявленное вендором (маркетинг + tech-info, не аудит вашей инсталляции): роли, RLS, АРМ ИБ, журнал (открытие дэша, фильтры, загрузка файлов), Keycloak, парольные политики, SIEM, ЕСИА, API JWT.

ФСТЭК: сертификат **№ 5055 от 15.04.2026**, 4 уровень доверия. Состав **не 12.x**, а пакеты **11.0.x** (web 11.0.2, appserver-mono 11.0.4, pgpro15, nats 2.11.11, …). Для ГИС/КИИ/ИСПДн аттестация считается **по сертифицированной сборке + контуру**, не по фразе «у вендора есть ФСТЭК».

Опасные дефолты, которые **публично видны** (пример NATS 12.x и админ-гайд 9.2):

| Что | Как из коробки / из примера | Зачем это опасно |
|---|---|---|
| Учётка БД в примере Lua | `dbuser="bi"`, `dbpass="bi"` (гайд 9.2) | Первый же сканер на 5432 |
| Антибрут | `max_login_attempts = 0` — **выкл** (9.2) | Подбор пароля |
| Лимит API | `rpmlimit = 0` — **выкл** (9.2) | Скрейп API |
| NATS пример 12.x | `no_tls: true`, `no_auth_user` | Шифрования и нормальной аутентификации нет, пока не включите |
| KeyDB при разносе хостов (9.2) | `protected-mode no`, снять `bind 127.0.0.1` | Открытый Redis-протокол без ACL |
| TLS к Postgres | Вендор **рекомендует не шифровать** во внутреннем сегменте «для нагрузки» | Прямо противоречит ожиданиям ИБ на контур с ПДн/гособменом. Решение — ваше, не «вендор сказал можно plaintext» |
| HTTPS на узлах web | Для highload вендор **не** рекомендует TLS на самих Luxms-web, а на **отдельном** LB | Нормально, **если** LB ваш (HAProxy) и до него люди не ходят HTTP |

ИИ-аналитик с 12.0.0 — **отдельное расширение лицензии**. Куда уходят промпты (локальная модель vs внешний API) в публичных notes **не расписано**. В контуре с клиентскими ПДн это отдельное решение ИБ, не «включим в чекбоксе».

## Допущения

Ниже то, чего **не было** в контексте, но без чего нельзя дать конкретную схему. Если допущение неверно — схему надо пересмотреть.

1. **Продукт — Luxms BI (ГК Luxms / реестр 3366)**, не Luxon, не Microsoft, не «любой российский BI».
2. **Новый контур без требования «только ФСТЭК-сборка»** ставим на **12.x** (pin из репозитория, ориентир notes **12.0.2**). Если ИБ/регулятор требует сертификат № 5055 — это **другой** дистрибутив **11.0.x**, не «12.x с тем же сертификатом».
3. **On-prem в ваших трёх ЦОДах**, не VK Cloud SaaS.
4. **Поставка пакетами** в персональный репозиторий (dnf/apt/zypper, как у демо-атласа). Ansible прода — **после** схемы, согласованной с вендором (так они сами пишут для продуктовых инсталляций).
5. **Прод ядра БД — PostgreSQL 15 или 17 (или Postgres Pro 15/17) + Patroni 3.2.x + Consul 1.16.1**, как в tech-info. Не Bitnami `postgres:latest` в том же namespace, что микросервисы.
6. **Терабайты фактов не живут только в Postgres ядра.** Для объёма — витрины озера и/или ClickHouse 25.3 / Arenadata. Иначе «BI тормозит», хотя тормозит диск одного Postgres.
7. **Luxms не ходит в госслужбы.** Только чтение из озера / витрин, которые наполнил интеграционный контур.
8. **SSO будет** (Keycloak/AD). Локальный Admin — break-glass в Vault, не ежедневный вход.
9. **Три ЦОДа = три домена отказа.** Если это три зала с общим UPS — схема «пережить ЦОД» лжёт.
10. **Stretch Patroni/Consul/NATS на 3 площадки — гипотеза до замера RTT.** Пока RTT неизвестен, честный прод: кворум DCS и primary Postgres не размазывать вслепую синхронно на три стороны.
11. **Цель отказа прода: пережить 1 ЦОД** для UI и **записи**, только если в живых ЦОДах остался кворум Consul **и** новый Postgres primary **и** web. Пережить 2 из 3, если DCS жили только в мёртвых двух — нельзя.
12. **Нагрузки нет** — нет числа узлов «хватит». Есть минимум HA (дубли web, Patroni, кластер NATS/KeyDB) и лицензионный потолок сессий.
13. **Kubernetes не является штатным инсталлятором Luxms в публичных docs.** Для теста допустим один VM. Для прода рядом с K8s — выделенные VM/Stateful-ноды **или** контейнеры, если вендор их даст и поддержит. Самодельный Helm без их runbook — вы сами vendor support.
14. **ИИ-модуль 12.x в первом проде выкл**, пока нет ответа «где инференс» и лицензии.
15. **Importer 9.2 для новых инсталляций не берём** — Data Boring + datagate.
16. **Формального SLO «дэшборд за 2 секунды» нет.** Скорость — свой замер на ваших кубах.

## Критически важные условия, которых нет в исходном контексте

Их нужно закрыть **до** «дали доступ к репозиторию и открыли :443».

| Пробел | Почему это ломает решение |
|---|---|
| **12.x vs ФСТЭК 11.0.x** | ГИС/КИИ/ИСПДн на несертифицированной линейке могут быть запрещены. Две ветки обновлений, не одна. |
| **SKU лицензии vs 3 ЦОДа** | Enterprise Cluster в прайсе tech-info — **2** промышленных сервера. Три площадки + MPP — отдельное согласование лицензий (узлы vs именованные пользователи, 1000 сессий). |
| **RTT и UDP/TCP между ЦОДами** | Consul (gossip), Patroni, NATS 6222, репликация Postgres. Городской firewall режет — «кластер» не соберётся. |
| **Один K8s на 3 ЦОДа или три кластера** | От этого зависит: один Patroni или три «правды» атласов (обычно плохо). |
| **Где primary Postgres и кворум Consul** | Web в трёх зонах при мозге БД в одной — переживают зону UI, не зону БД. |
| **Что является витриной для BI** | Живой FDW в озеро vs ETL-копия. Без решения будет либо нагрузка на SoT, либо рассинхрон. |
| **ПДн / 152-ФЗ в кубах** | Self-service и выгрузка Excel. Viewer с широким датасетом = читатель клиентов. RLS и запрет выгрузок — политика, не дефолт. |
| **ИИ-аналитик** | Риск утечки ПДн в модель. |
| **Профиль нагрузки** | 20 руководителей ≠ 800 self-service. Tech-info даёт 100 пользователей как репер, не вашу смету. |
| **Кто владеет репозиторием пакетов и Ansible** | Без вендора нет дистрибутива. Зеркало в закрытом контуре — отдельная работа. |
| **ГОСТ / СКЗИ** | Сертификат 4 УД не заменяет СКЗИ на канале, если ИБ его требует. |
| **Соседство с Grafana** | Два BI без границы «ops vs business» = ПДн в мониторинге или CPU метрик на бизнес-дэшах. |

## Краткое описание ключевых этапов и элементов развертывания

Общий каркас (и тест, и прод):

1. Закрыть лицензию, **ветку** (12.x или ФСТЭК 11.0.x), доступ к репозиторию, перечень пакетов из **вашего** sysadm-guide.
2. Сначала **ОС из матрицы** + NTP + разделы диска, потом **Postgres + обязательные расширения**, потом NATS/KeyDB, потом appserver, потом web, потом SSO.
3. Выпустить **свои** пароли БД/KeyDB/NATS **до** первого пользовательского входа. Примеры `bi`/`bi` и `no_auth_user` из доки не копировать.
4. Один атлас + один запрос к **вашей** витрине (не демо-CSV). Проверка: дэшборд не пустой.
5. Бэкап ядра Postgres (метаданные, права, локальные датасеты). Реплика Patroni **не** заменяет backup: ошибочный DROP и «накатили ETL» реплика послушно повторит.
6. Только потом — второй узел web, Patroni, SSO, АРМ ИБ, выгрузки.

Дальше — два режима.

---

### 1 инстанс: тестовый стенд, 1 ЦОД, без нагрузки

**Цель стенда:** увидеть свой дэшборд по витрине из озера (или демо-атлас), понять роли Viewer/Creator, не утонуть в Patroni. **Не** цель: доказать падение ЦОДа и 1000 сессий.

Официальные минимальные пути (выберите один):

**Путь A — пакеты на одну VM** (ближе к проду):

- ОС из матрицы (для теста часто Rocky 9 / РЕД ОС / Astra).
- Минимум железа tech-info можно **не** требовать 24 ГиБ, если это песочница без нагрузки; вендор для «надёжности в инфраструктуре» на одном узле в гайде 9.2 пишет **от 8 vCPU / 32 ГиБ**. Для знакомства с UI хватит меньше — **не** переносить это в прод как «официальный минимум».
- Пакеты ядра: Postgres 15/17 + расширения вендора, KeyDB, NATS (кластерный блок в конфиге **не** включать), appserver-mono, luxmsbi-web, bins, при необходимости Data Boring.
- Демо-атлас: пакет `bi-pg-ds-demo174` (для 12.0.0+), команды вида `dnf/apt/zypper install bi-pg-demo174` — только если репозиторий открыт.
- Вход с jump-хоста, не LoadBalancer в интернет.

**Путь B — Appliance VM** (ещё быстрее понять продукт): вендор для обучения предлагает готовый образ. Состав и гипервизор — в **текущем** гайде поставки, не в PDF 7.0 (там ещё CentOS 7 / OVA).

Режим «3 реплики web + один Postgres без Patroni» для знакомства **не нужен**: получите три UI с одной точкой отказа и иллюзию HA.

#### Что сознательно упрощаем

| Параметр | На тесте | Почему можно |
|---|---|---|
| Patroni / Consul | выкл | Нет цели пережить падение VM |
| NATS cluster | один узел, JetStream на локальный диск | Нет трёх ЦОДов |
| KeyDB replica | один | Нет HA-цели |
| MPP ClickHouse | выкл, если витрина маленькая | Не цель терабайты |
| PKI | self-signed / SSH-туннель | Иначе команда утонет в сертификатах раньше, чем в кубах |
| SSO | локальные учётки, пароль не `bi`/`bi` | На тесте важнее контур данных |
| ИИ 12.x | выкл | Лицензия и ИБ |
| ФСТЭК-сборка | не обязательна | Если тест не аттестационный стенд |

#### Чего на тесте **не** стоит упрощать

- ОС и **версию Postgres из матрицы 12.x**, не PG 13 «потому что привыкли».
- Обязательные расширения (`plv8`, http, redis/keydb fdw, pubsub). Без них ядро «как в доке» не встанет.
- Хотя бы один датасет с **вашими** полями (или честно демо, но тогда в голове пометка «это не озеро»).
- Web и 5432 **не** с мира.
- Понимание: всё состояние на одном диске VM. Снесли VM — снесли атласы.

#### Сильные стороны такой схемы

- Совпадает с официальным «один сервер / DEVL».
- Дешево показывает, есть ли у вас **вообще** витрина, которую BI может прожевать (часто нет: сырой Kafka JSON, нет ключей, нет согласованных справочников).

#### Слабые стороны (обязательно понимать)

- Нет модели отказа, нет пула HAProxy, нет SSO.
- Успешный дэш на одной VM **не** доказывает, что FDW в озеро не убьёт SoT в проде.
- Привычка plaintext Postgres и `bi`/`bi` уедет в прод, если не запретить явно.

Практическая рекомендация: препрод = маленький **прод-профиль** (Patroni на 2–3 VM в одном ЦОДе, два web, HAProxy, свои секреты, Keycloak-заглушка, NATS с TLS/учётками), даже без боевых пользователей.

---

### Прод: 3 ЦОДа, нагрузка

Цифр «ядер Luxms под терабайты озера» **нет** — нагрузки нет, и эти терабайты ядро Postgres **не должно** хранить целиком. Ниже правила, без которых экземпляр не считается готовым.

#### Шаг 0. Макроархитектура (сделать до установки)

Luxms плохо переживает **три независимых инсталляции** (три набора атласов, три правды прав доступа) и плохо переживает **слепой stretch синхронного Postgres на 3 ЦОДа**.

**Вариант A — один логический контур на 3 ЦОДа (stretch).**

- Web/appserver: минимум **по одному** живому входу в двух ЦОДах, лучше по экземпляру в каждой зоне (лицензия на узлы — уточнить).
- **Один** Patroni-кластер, `postgresql` primary + реплики; Consul **3** сервера (кворум 2) — по одному в ЦОД *только если* сеть Consul это переживёт.
- NATS: кластер, уникальный `server_name` (FQDN), `routes` без «сам на себя»; JetStream на диск, не emptyDir.
- KeyDB: репликация, не один узел в ЦОДе-1.
- Перед людьми — **HAProxy/Ingress HTTPS**. Sticky для сессий: смотреть, как у вас хранится cookie `LuxmsBI-User-Session`; в гайде 9.2 nginx `hash $upstream_cookie consistent` на appserver — значит **липкость к appserver желательна**, иначе «сессия на одном Java, запрос на другом».
- TLS: терминация на HAProxy. Postgres SSL — **включить**, пока ИБ не подписала исключение; рекомендация вендора «plaintext внутри» для вашего контура с гособменом слабая.
- NetworkPolicy / firewall: 443 с SSO-сети; 5432/6379/4222/6222/Consul — только роли BI.

**Вариант B — мозг в 1–2 ЦОДах, остальные только читают UI через WAN.**

- Patroni+Consul+NATS+KeyDB+Postgres primary **не** растягивать на три площадки.
- Web можно ближе к людям, но тогда сессии/KeyDB всё равно должны быть согласованы с мозгом (иначе «то залогинен, то нет»).
- Смерть ЦОДа с primary = простой записи и, скорее всего, UI, пока не отработан **DR runbook** (promote реплики + DNS VIP).

**Пока топология K8s и RTT не зафиксированы, нельзя честно выбрать A или B.** Дальше — общее.

##### Сильные / слабые стороны (A, stretch на 3 ЦОДа)

| Сильное | Слабое |
|---|---|
| Один атлас, одни права, один SSO | Consul/Patroni/NATS чувствуют RTT и потери; split-brain DCS = стоп записи |
| Переживание отказа **одного** ЦОДа *если* кворум собран из оставшихся | Два ЦОДа из трёх мертвы → кворум из 3 узлов Consul, скорее всего, мёртв |
| Соответствует идее «горячий резерв» лицензий Cluster | Лицензия «2 сервера» может **не** покрывать 3 площадки + MPP |
| Официальная идея «все компоненты масштабируются» | Нет публичного порога RTT — это ваш замер, не обещание |

##### Сильные / слабые стороны (B, мозг в одной площадке)

| Сильное | Слабое |
|---|---|
| Кворум Consul/Postgres предсказуем | Падение ЦОДа мозга = нет BI для всех |
| Проще сопровождение Patroni | Нужен явный DR: бэкап + как поднимать primary в ЦОД-2 |
| Меньше сюрпризов NATS gossip | Путь людей к UI пересекает ЦОДы |

##### Слабое место любого stretch без замера RTT

Утверждение «три ЦОДа в одном городе, значит синхронный Postgres на три» — **непроверенное**. Измерить RTT и потери на **5432**, **6222**, **Consul gossip**, **6379** до закупки схемы. Если между ЦОДами только HTTP через прокси — Patroni **не** взлетит.

#### Слой БД (ядро отказоустойчивости *данных BI*)

- Patroni **3** узла как минимум для переживания 1 отказа (2 = переживают отказ реплики, отказ одного из двух при сети хуже). Расклад по ЦОДам — после RTT.
- Приложения **никогда** не пишут на hostname конкретного лидера: VIP / HAProxy, как в приложении вендора про HAProxy.
- Отдельный диск под `$PGDATA` (гайд: начать с 10 ГиБ — это **пустое ядро**, не терабайты фактов; `noatime`, не NFS как data dir).
- Расширения только из пакетов под вашу мажор Postgres 15/17.
- Бэкап: вендор в 9.2 намекал «WAL archive для аналитики не копить, дешевле перегрузить витрину, хранить бэкапы 3–7 дней». Для **метаданных, ролей, дэшбордов** это слабо: их **не** перегрузишь из озера. Политика: витрины можно пересчитать; **ядро BI** — как у любой СУБД (регулярный backup + проверка restore).
- MPP ClickHouse/Greenplum — **отдельный** HA-проект. «Поставили Luxms Cluster» ≠ «ClickHouse переживает ЦОД».

#### Слой приложения (ядро отказоустойчивости *просмотра*)

- ≥2 luxmsbi-web, ≥2 appserver (или mono, если вендор так согласует).
- `upstreams.conf` не с `127.0.0.1` на всё. Consul DNS (`*.service.consul`) — штатный приём гайда; тогда resolver в nginx обязателен.
- Data Boring и datagate при тяжёлом ETL — **не** на тех же CPU, что web.
- headless-chrome, если экспорт PNG нужен: изолировать, как любой Chromium.
- Rolling-обновления: не обновлять Postgres и web «в один день без окна», пока нет Patroni switchover runbook.

#### NATS и KeyDB

- NATS: включить `cluster` + JetStream на постоянный диск (`/opt/nats` в гайде — старт **10 ГиБ**, для отчётов может быть мало). Сменить `server_name`, выкинуть `no_tls: true` и `no_auth_user` из примера. `max_payload: 16MB` в примере — потолок сообщения, не диск.
- KeyDB: пароль/ACL, bind не «весь мир», репликация. `protected-mode no` из гайда 9.2 в прод **не** тащить без компенсирующего firewall.

#### Безопасность прода (без этого кластер не считается настроенным)

Три слоя:

1. **Секреты и идентичность**
   - Нет `bi`/`bi`. Пароли в Vault.
   - SSO Keycloak/AD + маппинг групп. Admin break-glass в сейфе.
   - Лицензионные роли не путать с RBAC атласа: купили мало Creator — self-service не «включим галкой».
   - API JWT с сроком жизни, не бессрочный Admin-токен в CI.
   - АРМ ИБ включить в процесс, не «потом».
2. **Сеть**
   - UI только из корпоративной сети / через SSO-прокси.
   - 5432, 6379, 4222, 6222, Consul, Data Boring 1880 — не с пользовательского VLAN.
   - WAF (у вас SafeLine) на 443 — BI это ещё один HTTP-вход с выгрузками.
   - Исходящие с datagate: **только** озеро/витрины, не подсеть интеграционного API к ведомствам.
3. **Данные**
   - RLS на клиентские срезы.
   - Запрет бесконтрольного Excel на ПДн.
   - Журналы в SIEM/Wazuh, не только `/var/log/luxmsbi`.
   - ИИ выкл или локальная модель с запретом сырых ПДн в промпте.
   - Плагины/кастомный React (bi-magic-resources) — ревью как свой код, не npm с интернета в рантайме.

Плюс: pin версии пакетов; зеркало репозитория в контуре; SELinux/Mandat не выключать «чтобы встало» на Astra без решения ИБ.

##### Сильные / слабые стороны выбранной ИБ-схемы (12.x on-prem + Patroni + SSO + витрины из озера)

| Сильное | Слабое |
|---|---|
| Логика рядом с данными, меньше лишних app-серверов | Ядро = Postgres: дыра в SQL/роли БД = дыра во всём BI |
| Реестр РФ, российские ОС/СУБД, опция ФСТЭК 11.x | **12.x ≠ сертифицированная таблица 11.0.x** |
| Keycloak, АРМ ИБ, аудит, RLS — заявлены как продукт | Качество настройки — ваше; дефолты примеров слабые |
| On-prem, не облако вендора | Персональный репозиторий и закрытость исходников без опции в договоре |
| Короткий путь Nginx→БД | Lua у nginx + FDW = мощный и опасный доступ к данным |
| Можно не копировать SoT (FDW) | Живой FDW бьёт по озеру; копия ETL устаревает |

#### Kubernetes-специфика (если всё же кладёте в K8s)

Публичного «официального Helm 12.0.2» нет — это ограничение, не придирка.

Если вендор в договоре даёт чарты/оператор — следуйте **им**. Если нет:

- Postgres/NATS/KeyDB/Consul — **StatefulSet + PVC**, не Deployment с emptyDir.
- Не резать один PVC на три реплики Postgres.
- Антиаффинитет по зоне ЦОДа.
- Не ставить ClickHouse и Patroni на одни ноды с etcd/Kafka без лимитов.
- Честный план B: Luxms на VM, в K8s только Ingress/HAProxy и приложения домена.

Самописный чарт без поддержки вендора = вы чините split-brain Patroni сами.

#### Порядок вывода в прод (этапы, не команда за командой)

1. Измерить RTT/потери между ЦОДами на портах Postgres, Consul, NATS, KeyDB. Решить A vs B.
2. Зафиксировать линейку **12.x или ФСТЭК 11.0.x**, SKU лицензии, число узлов.
3. Согласовать с вендором схему и взять **их** Ansible/runbook (они сами так предлагают для прода).
4. Поднять Consul кворум → Patroni → проверка `patronictl list` → HAProxy к лидеру.
5. NATS кластер с TLS/учётками → KeyDB с паролем → appserver → web за HAProxy.
6. Закрыть дефолты (пароли, `no_tls`, антибрут, bind). HTTPS на LB. Vault.
7. Подключить **витрину озера** (JDBC/FDW), не госAPI. Один боевой атлас. Проверка RLS.
8. SSO + АРМ ИБ + выгрузка журнала в SIEM.
9. Бэкап ядра + **учебный restore** на стенде. Учение «убит web». Учение «убит ЦОД без primary»: что с записью. Учение «озеро недоступно»: UI жив, дэши пустые — и это **ожидаемо**.
10. Нагрузка соседством:  N одновременных сессий на **ваших** кубах, смотреть CPU Postgres, пул соединений, латентность FDW. Пока этого нет — «готовы к высокой нагрузке» неверно.

Без пунктов 4 (HA БД!), 6 (секреты!) и 9 (restore/учения) у вас нет платформы, есть VM с красивым UI.

## Сводка: что считать «экземпляр готов»

| Требование | Тест (1 ЦОД) | Прод (3 ЦОДа) |
|---|---|---|
| Отказоустойчивость | Не требуется | ≥2 web, Patroni с кворумом DCS, кластер NATS и KeyDB, LB на 443, переживание **1** ЦОДа *если* кворум и primary живы; runbook на смерть ЦОДа с primary; витрины — отдельный HA |
| Производительность / масштаб | Не требуется | Не класть терабайты в единственный Postgres ядра; MPP/озеро; пул соединений; не превышать лицензионные сессии; замер на ваших кубах, не «16 ядер = 100 людей» как смета |
| Безопасность | Свои пароли; порты не с мира | SSO; нет примеров `bi`/`bi` и NATS `no_tls`; антибрут; TLS на LB и (по ИБ) до Postgres; datagate не в ведомства; RLS на ПДн; ФСТЭК-сборка если регулятор требует; ИИ выкл или согласован; журналы в SIEM |

**Не готов к проду**, если: один хост «как тест» на три ЦОДа; три web без Patroni; `bi`/`bi` или NATS из example; 12.x там, где обязали сертификат 11.0.x; BI ходит в госAPI; эталон клиентов живёт только в датасете Luxms; RTT не мерили, а Consul растянули на 3 ЦОДа; restore ядра не делали; лицензия «2 сервера» а узлов пять; ждут, что Luxms заменит Kafka, Camunda или Grafana.
